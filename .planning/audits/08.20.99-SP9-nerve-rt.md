## nerve_rt/ Service

**Endpoints:**
- `GET /health` — Redis-Ping, antwortet `{"status": "ok", "redis": bool}`
- `WS /ws/{session_token}` — Haupt-WebSocket-Endpoint für Audio-Sessions

**WebSocket-Handling:**
`nerve_rt/routers/ws_router.py` nimmt Verbindungen auf `/ws/{token}` entgegen. Token wird gegen Redis validiert (HGET `nerve:session:{token}`, single-use, 60s TTL). Bei gültigem Token: `SessionManager.handle_session()` startet 3 parallele asyncio-Tasks:
1. `_audio_receiver` — empfängt binäre Audio-Frames + JSON-Control-Nachrichten
2. `_stt_forwarder` — leitet Audio-Queue an Deepgram weiter
3. `_analysis_loop` — 2s-Timer, Transkript-Buffer → Claude → WS-Push an Browser

**Deepgram-Code:**
`nerve_rt/services/stt/deepgram_adapter.py` — **eigener, separater Adapter**. Nutzt `client.listen.asyncwebsocket.v("1")` (asyncio-nativer Deepgram-Client). Explizit dokumentierter Unterschied zur Flask-Version die `client.listen.websocket.v("1")` (sync/threading) nutzt. Gleiche Optionen (nova-2, linear16, 16kHz, endpointing 900ms), aber vollständig eigene Implementierung.

**Infrastruktur:**
- Port 8001 (uvicorn), `RT_PORT` ENV-Override möglich
- Redis-Bridge für Session-Token-Validierung und Result-Publishing
- `nerve-rt.service` (systemd) gestartet seit 2026-04-23
- Nginx routet `/ws/` → `127.0.0.1:8001`

## Flask Audio-Pfad

**services/deepgram_service.py:**
Sync Deepgram-Client (`client.listen.websocket.v("1")`). Läuft in Flask-SocketIO-Event-Handlers. Registriert über `register_audio_handlers(sio)`:
- `@sio.on('start_live_session')` → `_open_deepgram_connection(sid, mode)`
- `@sio.on('audio_chunk')` → `connection.send(data)` an Deepgram
- `@sio.on('stop_live_session')` → `_close_deepgram_connection(sid)`
- `@sio.on('disconnect')` → schließt Deepgram-Connection

**Port/Namespace:**
Flask-SocketIO nutzt den Standard-Flask-Port (8000 via Gunicorn). Kein separater Namespace für Audio. Socket.IO verbindet sich auf denselben Host/Port wie die Website selbst (`io({})` ohne explizite URL).

**Kein Feature-Flag / Fallback-Logik:**
Es gibt **keinen Code** in Flask der prüft ob `nerve-rt` aktiv ist und ggf. auf Flask-Pfad fällt. Beide Pfade existieren vollständig unabhängig voneinander.

## Frontend-Verbindung

**pip-launcher.js, Zeile 1344:**
```js
state.socket = io({
  reconnectionAttempts: 3,
  reconnectionDelay: 2000,
  transports: ['websocket', 'polling']
});
```
- Keine explizite URL → verbindet auf denselben Origin wie die Seite
- Kein Port 8001, kein `/ws/`-Pfad
- Nginx routet alles ohne `/ws/`-Prefix → Port 8000 (Flask/Gunicorn)

**Audio-Flow Frontend:**
1. `io()` → Socket.IO-Verbindung zu Flask (Port 8000)
2. `socket.emit('start_live_session', {...})` → triggert Flask `handle_start_live_session`
3. AudioWorklet konvertiert Float32 → Int16 PCM, postet Buffer
4. `socket.emit('audio_chunk', e.data)` → Flask leitet an Deepgram weiter
5. Flask emittet `transcript`, `coaching`, `keyword_einwand_match` zurück

**Kein Zugriff auf Port 8001:**
Weder in `pip-launcher.js`, noch in anderen JS-Dateien gibt es Referenzen auf Port 8001, `/ws/`-Endpoints, ws_token-Anfragen oder nativen WebSocket-Konstruktoren.

## BEFUND

**Audio läuft über: Flask-SocketIO (Port 8000/8000 via Gunicorn)**

**Begründung:**
Das Frontend verbindet ausschließlich via `io()` ohne URL auf den Flask-Server (Port 8000 hinter Nginx). Audio-Chunks werden über `socket.emit('audio_chunk')` übertragen. Flask/deepgram_service.py verarbeitet sie mit dem sync Deepgram-Client. Der nerve_rt-Service (Port 8001) ist zwar deployed und läuft, aber **das Frontend spricht ihn nie an**.

Der kritische fehlende Link ist die **Token-Schnittstelle**: `nerve_rt/routers/ws_router.py` erwartet, dass Flask zuerst ein Session-Token in Redis unter `nerve:session:{token}` ablegt und der Browser dann `WebSocket(/ws/{token})` öffnet. Diese Logik ist **in Flask nie implementiert** worden — kein Route-Handler schreibt den Redis-Token, kein JS-Code fragt einen Token-Endpoint an oder öffnet eine native `/ws/`-WebSocket-Verbindung.

## Empfehlung

**nerve_rt ist NOT live-integriert.** Es ist ein vollständig ausgebauter aber unverbundener Service.

**Fehlende Verbindungsstücke für nerve_rt-Integration:**

1. **Flask-Route `/api/get_ws_token`** — muss `secrets.token_urlsafe(32)` generieren, `HSET nerve:session:{token}` in Redis schreiben (user_id, mode, profile_id, system_prompt), Token mit 60s TTL an Frontend zurückgeben.

2. **Frontend (pip-launcher.js)** — muss vor `_openPipAndMic()` den Token fetchen, dann eine native `WebSocket(wss://nerve.app/ws/{token})`-Verbindung öffnen statt `io()`. Audio-Chunks als binäre ArrayBuffer-Frames senden.

3. **Analyse-Ergebnisse zurück zum Frontend** — nerve_rt pusht Analysis-Updates direkt via WebSocket. Das bisherige Polling via `/api/ergebnis` müsste deaktiviert oder durch den WS-Push ersetzt werden.

**Risiken bei aktuellem Zustand:**
- nerve_rt-Service läuft und verbraucht Ressourcen, liefert aber null Wert für User
- Redis ist als Dependency konfiguriert — fällt Redis aus, startet nerve_rt nicht (aber Flask läuft weiter, da Flask Redis nur optonal für Rate-Limiting nutzt)
- `.env.example` enthält kein `REDIS_URL` → nerve_rt fällt auf `redis://127.0.0.1:6379` default zurück; wenn Redis auf dem VPS nicht läuft, kann nerve_rt beim Start crashen ohne den Flask-Service zu stören

**Empfohlene Aktion:**
Entweder Integration vollenden (3 Schritte oben) oder nerve_rt-Service stoppen bis Integration geplant ist. Keiner der toten Pfade verursacht aktiv Fehler, aber der laufende Service erzeugt log-noise und potenziell unnötige Redis-Abhängigkeit.
