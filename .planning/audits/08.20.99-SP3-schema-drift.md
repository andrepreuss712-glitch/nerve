## Drift-Findings

### KRITISCH (alter Name noch aktiv, neue v4-Profile bekommen leere Ergebnisse)

**DRIFT-K1: `training_service.py` — 3x `profile_data.get('einwaende', [])` ohne `einwaende_detail`-Fallback**
- Dateipfad: `services/training_service.py` Zeilen 576, 733, 951
- v4-Profile haben kein `einwaende`-Feld im JSON (nach Migration gedroppt).
- Ergebnis: Training-Prompts erhalten immer leere Einwand-Liste → Training-Qualität degradiert still.
- Fix: `profile_data.get('einwaende_detail') or profile_data.get('einwaende') or []`

**DRIFT-K2: `pip-launcher.js:2187` — `state.profileDaten.einwaende` ohne `einwaende_detail`-Fallback**
- Zeile 2187: `var prof = (state.profileDaten && state.profileDaten.einwaende) || [];`
- Funktion: Slot-0 Profil-Gegenargument-Lookup (BUG-10 Fix) beim Einwand-Matching.
- v4-Profile: `profileDaten.einwaende` ist undefined → `prof = []` → Profil-Gegenargument wird nie gefunden → Haiku-formulierte GA statt authoritativem Profil-GA.
- Zeilen 1849 und 1885 im selben File machen es bereits richtig (`einwaende_detail || einwaende`).
- Fix: `var prof = (state.profileDaten && (state.profileDaten.einwaende_detail || state.profileDaten.einwaende)) || [];`

**DRIFT-K3: `training_service.py:731,732` — `profile_data.get('produkt')` und `profile_data.get('branche')` ohne Fallback**
- Zeile 731: `produkt = profile_data.get('produkt', 'ein Produkt')` — kein `basis.produktbeschreibung` Fallback
- Zeile 732: `branche = profile_data.get('branche', 'B2B')` — Top-Level `branche` in v3+ JSON nicht vorhanden (DB-Column)
- Funktion: `_build_personality_system_prompt()` — Personality-Training-Modus
- Ergebnis: Produkt = `'ein Produkt'` statt echtem Produkt; Branche = `'B2B'` statt echter Branche.
- Fix: Produkt wie in Zeile 579 (`basis.get('produktbeschreibung') or profile_data.get('produkt', ...)`); Branche aus Profile-Objekt übergeben (wird von aufrufendem Code via `profile.branche` DB-Column geliefert).

### WARNUNG (partiell migriert / stille Fehler möglich)

**DRIFT-W1: `routes/onboarding.py:229` — `_basis.get('einwaende_detail', [])` liest aus sub-dict**
- Zeile 229: `'einwaende': len(_basis.get('einwaende_detail', []))`
- `_basis` ist das `basis`-Sub-Dict der Profile-Daten. `einwaende_detail` liegt jedoch **top-level** in ProfileSchema, nicht unter `basis`.
- Ergebnis: Zähler ist immer 0 → Response-JSON `{"einwaende": 0}` falsch im Onboarding-Feedback.
- Gleiche Zeile: `_basis.get('phasen', [])` für `phasen`-Zähler hat dasselbe Problem (phasen ist auch top-level).

**DRIFT-W2: `routes/onboarding.py:230` — `_basis.get('phasen', [])` liest aus sub-dict**
- Zeile 230: `'phasen': len(_basis.get('phasen', []))`
- Analog zu DRIFT-W1: `phasen` ist top-level, nicht in `basis`.
- Ergebnis: Phasen-Zähler immer 0 nach v3-Migration.

**DRIFT-W3: `services/precall_service.py:534` — `ki.stil` nach Migration immer leer**
- Zeile 534: `ki_stil = ((profil_daten or {}).get('ki') or {}).get('stil', '')`
- `ki.stil` wird in v1->v2 Migration in `ki.ton` gemergt und entfernt.
- Ergebnis: `ki_stil` ist immer `''` für alle migrierten Profile. Der Wert direkt daneben (`ki_ton`) ist korrekt.
- Risiko: PreCall-Briefing-Prompt nutzt `ki_stil` für Ton-Anweisung — diese ist immer leer.

**DRIFT-W4: `training_service.py:953` — `basis.get('firmenname')` und `profile_data.get('firma')` — beide nie gesetzt**
- `firmenname` ist kein Feld in BasisSchema (kein Schema-Feld, kein alter Feldname).
- `firma` war kein Schema-Feld in ProfileSchema (liegt in `meta.firma`).
- Ergebnis: `firma`-Variable in Coaching-Prompt ist immer `''`.

### INFO (toter Schema-Key / Phantom-Access ohne Runtime-Fehler)

**DRIFT-I1: `value.roi_argumente` — 0 Konsumenten**
- Feld im Schema definiert (`ValueSchema.roi_argumente: List[str]`), `_ValueReadSchema` ebenfalls.
- Kein einziger Lesezugriff in services/, routes/, templates/, static/ gefunden.
- Das Feld wird vom Detail-Editor (in `profile_editor.html`) vermutlich nicht geschrieben.
- Grep auf `roi_argumente` in templates/profile_editor.html ergibt keinen Treffer.
- Status: Dead Schema-Key. Kann entweder geprunt oder für künftigen Wert-Pitch-Modul reserviert werden.

**DRIFT-I2: `meta.firma` und `meta.rolle` — nur Write-Pfade, keine Lese-Konsumenten**
- Felder werden in Wizard-Create (`routes/profiles.py:151-154`) und Onboarding geschrieben.
- Kein service liest `meta.firma` oder `meta.rolle` für Prompt-Building.
- Möglicherweise für zukünftige Personalisierung vorgesehen. Kein aktiver Nutzen derzeit.

**DRIFT-I3: `schema_version` default im Schema auf `3`, LATEST ist `4`**
- `ProfileSchema.schema_version: int = 3` — Default-Wert ist v3, nicht v4.
- `ProfileReadSchema.schema_version: int = 3` — gleicher Default.
- Neue Objekte die direkt über `ProfileSchema()` instantiiert werden (ohne `_migrate_profile_data`) erhalten `schema_version=3`.
- In Praxis kein Problem da Wizard immer `_migrate_profile_data()` aufruft. Aber Fallstrick für Unit-Tests.
