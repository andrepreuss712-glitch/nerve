### 1a. Nimmt `finish()` einen Timeout-Parameter? → **NEIN.**

```python
# deepgram/clients/common/v1/abstract_sync_websocket.py:451
def finish(self) -> bool:
# :467-469
        if self._listen_thread is not None:
            self._listen_thread.join()          # <— unbegrenzt, kein Argument
            self._listen_thread = None
```

Der von NERVE genutzte Konkrete-Client erbt und joint danach **noch zweimal**:

```python
# deepgram/clients/listen/v1/websocket/client.py:527
def finish(self) -> bool:
    if super().finish() is False: ...            # :534  <- HIER hängt es (abstract:468)
    if self._flush_thread is not None:  self._flush_thread.join()       # :544-546
    if self._keep_alive_thread is not None: self._keep_alive_thread.join()  # :549-552
    if self._listen_thread is not None: self._listen_thread.join()      # :554-556 (No-Op, s.o. schon None)
```

Keine der vier `join()`-Aufrufe hat ein `timeout=`. Es gibt in 3.10.0 **keinen** Konfigurations-Schalter, der das begrenzt (kein `termination_*`-Option greift auf den Join; die `termination_exception_*`-Optionen steuern nur, ob Exceptions durchgelassen werden, z.B. `:410`, `:425`).

**Neuere Versionen:** identisch unbegrenzt.
`curl .../v3.11.0/.../abstract_sync_websocket.py` → `468: self._listen_thread.join()`
`curl .../v4.8.1/.../abstract_sync_websocket.py` → `468: self._listen_thread.join()`
(v5.x/v7.x haben die Datei umstrukturiert — nicht geprüft, und durch `<5` in `requirements.txt` ohnehin gesperrt. Aktuellste PyPI-Version: `7.6.0`.)
→ **Ein SDK-Upgrade löst das Problem nicht.** Ein Warten auf einen Upstream-Fix ist keine Option.

### 1b. Gibt es einen dokumentierten/de-facto sicheren Weg, die Verbindung aufzugeben?

Es gibt keinen offiziellen. Aber die Reihenfolge in `_signal_exit()` macht das Aufgeben **erstaunlich billig** — der ganze Aufräum-Teil ist bereits VOR dem Join erledigt:

```python
# abstract_sync_websocket.py:485-527  (_signal_exit, gerufen aus finish():463)
self._close_message()        # :492  -> sendet {"type":"CloseStream"} (listen/client.py:523-524)
self._emit(Close, ...)       # :504  -> ruft _make_on_close(sid) SYNCHRON im Aufrufer-Faden
time.sleep(0.5)              # :513  <- Auflegen kostet immer >=0.5s, unvermeidbar
self._exit_event.set()       # :516
self._socket.close()         # :523
self._socket = None          # :527
```

Heißt: **wenn `finish()` beim Join hängt, ist der Socket schon zu, `_exit_event` schon gesetzt und der Close-Handler schon gelaufen.** Der Join ist reine Hygiene. Ihn zu überspringen verliert nichts Fachliches.

Wichtig für die Verklemmungs-Betrachtung: `_signal_exit()` läuft **im Aufrufer-Faden**, und `_emit(Close)` ruft dort `_make_on_close(sid)` (`deepgram_service.py:347-359`) — der macht nur `print` + `sio.emit`, **nimmt keinen `_session_state_lock`**. Der `finish()`-Vorlauf ist also riegel-frei; die einzige Klemme ist der Join.

### 1c. Was bleibt liegen, wenn der Lausch-Faden nie gejoint wird?

| Ressource | Zustand nach Aufgabe | Bewertung |
|---|---|---|

## 3. Das `[SLOW] requeue_pending`-Tick-Muster

**Fundort:** `services/slow_lane.py`. Das Muster hat vier Teile:

| Teil | Ort | Wie |
|---|---|---|
| **Registry** | `slow_lane.py:79` `def register_periodic_tick_hook(fn)`; Aufruf `slow_lane.py:867` `register_periodic_tick_hook(_requeue_pending_safety_net)` auf **Modul-Ebene** | Kein harter Tick-Body — Hooks werden registriert. `_periodic_tick` (`:344-353`) iteriert sie mit **per-Hook `try/except`** (ein Hook-Fehler killt weder den Tick noch die anderen Hooks). |
| **Takt** | `slow_lane.py:790-795`: `slow_lane.get(timeout=SLOW_LANE_TICK)` → bei `queue.Empty` → `_periodic_tick()` | `SLOW_LANE_TICK = 5.0` (`:57`). Die 30s kommen aus einer **Zähler-Drosselung**, nicht aus dem Timer: `_REQUEUE_EVERY_N_TICKS = 6` (`:68`), `_tick_count % 6 != 0 → return` (`:332-335`). |
| **Faden** | `app.py:2423` `threading.Thread(target=slow_lane_consumer, daemon=True).start()`, innerhalb `if _os_guard.environ.get('NERVE_TESTING') != '1':` (`app.py:2410`) | Ein **einziger** Daemon-Faden neben `analyse_loop`/`coaching_loop` (`app.py:2415-2416`). Kein APScheduler, kein SocketIO-Background-Task. |
| **Log** | `slow_lane.py:323` `print(f"[SLOW] requeue_pending: {n} re-enqueued")` | `print` → stdout → journald (`Environment=PYTHONUNBUFFERED=1`, `nerve.service:22`) → `inspect.sh logs`. Zusätzlich ein **Start-Beleg-Log** (`:781-782`), damit eine leere Registry sofort sichtbar ist statt still. |

**Gunicorn-Neustart-Verhalten:** Der Faden überlebt einen Neustart **nicht** — er wird bei jedem Prozess-Start neu erzeugt, weil `app.py` beim Worker-Boot importiert wird (`--workers 1`, kein `preload_app` → Import im Worker). Genau deshalb hat `_requeue_pending` einen **Bootstrap-Aufruf** vor der Schleife (`slow_lane.py:784-788`) und die Docstring bei `:301-304` erklärt es explizit. Für den Wachhund ist das unproblematisch: er hat keinen Zustand, der einen Neustart überleben müsste.

### Zwei Fallen des Musters, die der Wachhund erbt

- **F-1: Der Tick feuert NUR bei leerer Queue** (`:793` `except queue.Empty`). Ist die Slow Lane beschäftigt (Call-Ende-Merge, Event-Flut), werden Ticks **übersprungen**. Für `requeue_pending` ist das Absicht (dann gibt's ohnehin Arbeit); für einen Wachhund heißt es: **er kann genau in der Situation stumm bleiben, in der viel passiert.** Der Verklemmungsfall ist allerdings gutartig — bei geklemmtem `_session_state_lock` produziert niemand neue Slow-Lane-Items, die Queue läuft leer, der Tick feuert. Trotzdem im Plan benennen.
- **F-2: Der Hook läuft IM Consumer-Faden.** Ein `lock.acquire(timeout=2)` blockiert damit die Slow Lane für bis zu 2s pro Tick. Bei 30s-Drosselung sind das ≤6,7% Auslastungsverlust in einer Bahn, die per Definition langsam sein darf (Punkt 25: Slow Lane ist nicht die schnelle Bahn). Akzeptabel — aber ein eigener Daemon-Faden wäre ebenso legitim und entkoppelt (Discretion).

### ➜ ACTIONABLE RECOMMENDATION (Q3)

**Dem Muster folgen, nicht neu erfinden:**

### 4c. Signal-Wahl: **SIGUSR1 mit `chain=True`** — nicht SIGUSR2

| Signal | Master (arbiter) | Worker | Verdikt |
|---|---|---|---|
| **SIGUSR1** | `arbiter.py:286-292` `handle_usr1`: `log.reopen_files()` **+ `kill_workers(SIGUSR1)`** → leitet ans Worker weiter | `base.py:177` `signal.signal(SIGUSR1, self.handle_usr1)`, `:188-189` `handle_usr1 → self.log.reopen_files()` | **BELEGT, EMPFOHLEN.** Bereits belegt, aber harmlos: `reopen_files()` ist idempotent. Mit `faulthandler.register(SIGUSR1, chain=True)` wird nach dem Dump gunicorns Handler weiterhin aufgerufen. Und: der Master **leitet weiter** → `systemctl kill -s SIGUSR1 nerve` funktioniert. |
| **SIGUSR2** | `arbiter.py:294-300` `handle_usr2`: **erzeugt einen neuen Arbiter (Live-Deployment-Re-Exec)** | `base.py:32-34`: `SIGNALS` enthält `USR2`, `init_signals` setzt alle auf `SIG_DFL` (`:170-171`) und registriert USR2 **nicht** neu → Default-Disposition = **Prozess-Beendigung** | **GEFÄHRLICH.** Bei `KillMode=control-group` (systemd-Default, `nerve.service` setzt nichts anderes) trifft `systemctl kill -s SIGUSR2 nerve` **auch den Master** → ungewollter Re-Exec mitten in der Diagnose. Und ohne unsere Registrierung würde SIGUSR2 den Worker schlicht töten. |

**Konsequenz:** SIGUSR1 nehmen, `chain=True` ist Pflicht (sonst gehen gunicorns Log-Reopens verloren — mit `--access-logfile -`/`--error-logfile -` heute folgenlos, aber eine stille Regression für später).

### 4d. Wohin geht der Abzug, und ist er lesbar?

- `faulthandler.register(signal, file=sys.stderr, all_threads=True, chain=True)` schreibt **direkt auf den Datei-Deskriptor** (umgeht Python-Puffer).
- `--error-logfile -` → stderr bleibt der Prozess-stderr → systemd fängt es → **journald**.
- `scripts/inspect.sh:126-129`: `logs)` → `journalctl -u "$SERVICE_NAME" -n "$N" --no-pager`, Default `N=200` (`inspect.sh:213`).
- **JA, lesbar** — aber zwei Vorbehalte:
  - **Umfang:** 64 gthread-Fäden + 3 Daemons + SDK-Fäden → der Dump ist realistisch mehrere hundert Zeilen. `inspect.sh logs 200` schneidet ihn ab. Im Plan `inspect.sh logs 3000` (oder `logs-errors`, das aber auf `error|fehler|exception|traceback|critical` grept und `Thread 0x...`-Kopfzeilen mitnimmt, weil „Traceback" im faulthandler-Format vorkommt) vorgeben.
  - **journald-Ratenbegrenzung:** `nerve.service` setzt **kein** `LogRateLimitIntervalSec`/`LogRateLimitBurst`. Bei systemd-Defaults (10000 Nachrichten/30s pro Dienst) reicht es für einen Dump; bei mehreren Dumps kurz hintereinander plus Anruf-Logs kann journald „Suppressed N messages" melden und Teile verwerfen. `[ASSUMED]` A4 (Default-Konfiguration von journald auf dem Host nicht geprüft — `inspect.sh` hat kein Kommando dafür). Sichere Variante: `faulthandler` **zusätzlich** in eine Datei unter `logs/` schreiben (Datei-Objekt offenhalten!) — siehe Empfehlung.

**Daraus folgt hart:** Der Verklemmungs-Test darf **keine** neue Abhängigkeit einführen (Punkt 27 + Deploy-Realität) und muss sich **selbst** begrenzen. Und noch schärfer: **das Gate hat keinen Timeout.** Ein Test, der hängt, hängt `deploy.sh` unbegrenzt an — das ist schlimmer als ein roter Test, weil der Deploy dann manuell abgebrochen werden muss und der Wächter niemandem was sagt.

`signal.alarm` ist ebenfalls **ungeeignet**: es feuert nur im Haupt-Faden, unterbricht laufende C-Aufrufe (DB-Treiber!) und kollidiert mit der Signal-Landschaft. Nicht verwenden.

### 5b. Das tragfähige Muster (keine neue Abhängigkeit)

Drei Fäden, alle `daemon=True`, Ergebnis über eine Liste/`queue.Queue`:

```
Haupt-Faden (Test)                Halter-Faden H              Aufruf-Faden C
------------------------------    -----------------------     ---------------------------
start H                           acquire lock
warte auf H-Bereit-Event  <-----  set(held_event)
start C                                                       ruf handle_manual_ewb(...)
C.join(timeout=N)                                             lege (ok/err) in Ergebnis ab
set(release_event)         ----->  release im finally
H.join(timeout=2)
ASSERT auf Ergebnis
teardown: sid poppen
```

Warum jeder Baustein nötig ist:

| Baustein | Grund |
|---|---|
| `daemon=True` **für beide** Fäden | Im ROTEN Lauf kehrt C **nie** zurück. Ohne `daemon` blockiert der Faden das Prozess-Ende → pytest hängt nach dem letzten Test. |
| `held_event` (Halter meldet Bereitschaft) | Ohne Handshake ist der Test zeitabhängig → Flake. `time.sleep(0.1)` ist **keine** Synchronisation. |
| `release_event` + `finally: release()` im Halter | **Kritisch:** wird der Riegel nicht freigegeben, hängen ALLE folgenden Tests der Suite (98 `with`-Stellen, `conftest`-Fixtures, `_baseline_cleanup_guard`) → das Gate hängt für immer. Freigabe MUSS in `finally` und MUSS auch bei Assertion-Fehler laufen ⇒ Freigabe **vor** dem `assert`, oder das ganze Konstrukt in eine Fixture mit `yield` legen. |
| Freigabe **vor** dem `assert` | Damit ein im-RED-hängender C-Faden anschließend fertig läuft und keine halb-mutierte `_session_state`-Zeile hinterlässt. |
| `C.join(timeout=N)` als Zeitgrenze | Ersetzt `pytest-timeout` vollständig, ohne Abhängigkeit. Der ROT-Beleg ist dann das `assert`-Ergebnis („nicht zurückgekehrt"), **nicht** ein Hänger. |
| eigene Wegwerf-`sid` + Teardown-Pop | Muster `tests/test_stabil1_beenden_guard.py:101-103` (`_cleanup_sid`) und `:106-115` (`_clear_leaked_sessions_for_user`). |

**N-Wert (Discretion):** `N = 10.0` empfohlen. Begründung: das Produktions-Zeitlimit liegt bei ~2s (Wachhund) bzw. ~5s (`finish()`); N muss deutlich darüber liegen, damit ein langsamer, aber korrekter GREEN-Lauf nicht flakt, und deutlich unter der Gate-Geduld liegen. Präzedenz: `tests/test_live_session_ghost_sid.py:36` nutzt `TIMEOUT_S = 10` für genau diesen Zweck (Deadlock-Stresstest, `t.join(timeout=…)` bei `:68`).
