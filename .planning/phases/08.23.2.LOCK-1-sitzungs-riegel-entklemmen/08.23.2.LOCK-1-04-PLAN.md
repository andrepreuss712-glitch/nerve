### Schicht 4 — Edge-Case- und RACE-Analyse (die vier Pflicht-Fragen)

**Frage 1 — Zwei Fäden gleichzeitig?**
Genau ein Faden kann den inneren `threading.Lock` halten. Die Halter-Felder werden **nur** vom
jeweils erfolgreichen Erwerber geschrieben — also immer von genau einem Faden. Kein Schutz für
die Felder nötig (und **kein** zweiter Riegel darum herum: das wäre der Anfang einer
Riegel-Ordnung und damit eines neuen Verklemmungs-Risikos).

**Frage 2 — Ein anderer Faden schreibt mitten hinein?**
**Kritische Reihenfolge in `release()`:** die Halter-Felder werden **VOR** `self._lock.release()`
gelöscht. Andernfalls könnte ein wartender Faden den Riegel sofort übernehmen und seine Felder
setzen — und unser nachgelagertes Löschen würde **den neuen Halter wegwischen**. Der Wachhund
läse dann `None` und meldete „Halter unbekannt", obwohl er bekannt ist.
Beim Lesen (Wachhund) kann ein Feld dagegen veralten oder `None` werden — das ist harmlos und
wird dort defensiv behandelt (Task 2).

**Frage 3 — Der Aufruf bricht mittendrin ab?**
`acquire` setzt die Felder erst **nach** erfolgreichem Erwerb. Schlägt der Erwerb fehl, bleibt
alles unverändert. `__exit__` ruft `release()` immer, auch bei Exception im `with`-Körper — das
ist das Kontext-Manager-Protokoll und exakt das heutige Verhalten.

**Frage 4 — Doppelt ausgeführt?**
`release()` auf einem nicht gehaltenen Riegel wirft `RuntimeError` — **wie heute bei
`threading.Lock`**. Das Verhalten wird **nicht** abgeschwächt: ein doppeltes `release` ist ein
Programmfehler und soll laut sein.

**Weitere Edge-Cases:**
1. **KEIN RLock.** Der Aufsatz umschließt `threading.Lock()`, nicht `RLock`. Wieder-Eintritt
   desselben Fadens verklemmt weiterhin — das ist ein bewusst gesetzter Design-Zwang
   (`services/live_session.py:594-605`: „KEIN RLock"), und
   `close_moment`/`get_or_open_moment` sind genau darauf gebaut. Als Kommentar in die Klasse.
2. **`__slots__`** spart Speicher und verhindert versehentliche neue Felder. Kein `__dict__`

3. **Zeit-Erfassung: genau EIN C-Aufruf beim Erwerb** (Cross-AI-Fund B5, optionaler Teil).

    LATENZ (Punkt 25): ein Python-__enter__/__exit__-Paar kostet grob 1-2 us pro Erwerb
    statt ~0.1 us beim C-Riegel. Nach Teil 1 nimmt der 10-Hz-Ton-Weg diesen Riegel GAR

                 'holder_since')

    def __init__(self, name: str):
        self._lock = threading.Lock()
        self._name = name
        self.holder_thread = None        # str  — Faden-Name des aktuellen Halters
        self.holder_ident = None         # int  — Faden-Kennung (fuer den faulthandler-Abzug)
        self.holder_since = None         # float monotonic — Halte-DAUER; die Uebernahme-
                                         # UHRZEIT wird daraus erst beim Loggen abgeleitet

    def acquire(self, blocking: bool = True, timeout: float = -1) -> bool:
        got = self._lock.acquire(blocking, timeout)
        if got:
            _t = threading.current_thread()
            self.holder_thread = _t.name
            self.holder_ident = _t.ident
            self.holder_since = time.monotonic()   # EIN C-Aufruf, kein zweiter fuer die Uhrzeit
        return got

    def release(self) -> None:
        # REIHENFOLGE IST LOAD-BEARING: erst die Felder loeschen, DANN freigeben.
        # Umgekehrt koennte ein wartender Faden den Riegel sofort uebernehmen und seine
        # Felder setzen — und unser nachgelagertes Loeschen wuerde den NEUEN Halter
        # wegwischen. Der Wachhund meldete dann 'Halter unbekannt', obwohl er bekannt ist.
        self.holder_thread = None
        self.holder_ident = None
        self.holder_since = None
        self._lock.release()

    def locked(self) -> bool:
        return self._lock.locked()

    def __enter__(self):
        self.acquire()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.release()
        return False

    def __repr__(self):
        return f"<_TracedLock {self._name} holder={self.holder_thread!r}>"

### Schicht 4 — Edge-Case- und RACE-Analyse (die vier Pflicht-Fragen)

**Frage 1 — Zwei Fäden gleichzeitig?**
`_lockwatch_tick` läuft **ausschließlich** im einen Slow-Lane-Consumer-Faden
(`app.py:2423`, ein Faden). Die drei Zähler werden nur von ihm geschrieben. Kein Schutz nötig
— **und das gehört als Kommentar dokumentiert**, sonst liest der nächste Audit einen
ungeschützten globalen Zähler.

**Frage 2 — Ein anderer Faden schreibt mitten hinein?**
Die Halter-Felder können sich **während** der Formatierung ändern (der Halter gibt frei). Genau
dagegen: **einmal** in lokale Variablen lesen, dann formatieren. Ein `None` in einem der
Felder darf die Log-Zeile **nicht** sprengen → alle vier defensiv behandeln
(`'unbekannt'`-Fallback). Ein `holder_since`, das zwischen Lesen und Rechnen `None` wird, kann
so keinen `TypeError` erzeugen.

**Frage 3 — Der Aufruf bricht mittendrin ab?**
**P-3, die gefährlichste Falle dieses Plans:** gelingt `acquire`, und wirft danach irgendetwas
(Format-Fehler, `AttributeError`), hält plötzlich **der Wachhund** den Riegel für immer — der
Wächter würde zur Ursache. Zwei Schichten dagegen: (a) im Erfolgsfall wird unter dem Riegel
**nichts** getan (`try: pass / finally: release()`), (b) die Log-Zeile steht im **Fehl**-Zweig,
also **ohne** Riegel.

**Frage 4 — Doppelt ausgeführt?**
`register_lockwatch_hook()` zweimal aufzurufen registriert den Hook zweimal → doppelte Log-Zeilen
und doppelte Zähler. In `app.py` gibt es genau **einen** Aufruf, im `NERVE_TESTING`-Guard. Die
Funktion wird trotzdem **idempotent** gebaut: sie prüft, ob `_lockwatch_tick` schon in
`_PERIODIC_TICK_HOOKS` steht, und registriert dann nicht erneut.
