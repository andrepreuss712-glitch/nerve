<decisions>
## Implementation Decisions

### D-01: Alembic Migration 0004 — call_events CHECK-Constraint

**BLOCKER-Entscheidung:** `call_events.event_type` CHECK-Constraint (`ck_call_events_event_type`) enthält `'mode_switch'` nicht → INSERT schlägt auf Postgres fehl (SQLite enforces CHECK nicht → stiller Bug lokal).

- **D-01a:** Alembic Migration 0004 erstellen die den CHECK-Constraint um `'mode_switch'` UND `'mode_initial'` erweitert.
- **D-01b:** Migration-Chain: 0001 → 0002 → 0003 → 0004 (head). Idempotent via Alembic-interner alembic_version-Tabelle.
- **D-01c:** Beide neuen event_types in Migration 0004 — nicht nur mode_switch. Begründung: mode_initial wird ebenfalls benötigt (siehe D-04).
- **D-01d:** Migration 0004 ist ein ALTER TABLE auf PostgreSQL (Constraint drop + recreate). Für SQLite render_as_batch=True in alembic/env.py bereits vorhanden (gesetzt in Phase 08.23.2.C.1).

### D-02: gatekeeper.py Restbestand

- **D-02a:** `gatekeeper.py` BLEIBT als Datei (nicht löschen). Modul-Heimat für populate_context_notes() ist semantisch korrekt für Phase 08.23.2.I.
- **D-02b:** Zu löschen aus gatekeeper.py: `classify_contact()`, `apply_hysteresis()`, `detect_trigger_phrases()`, `detect_uwg_hard_block()`, `get_gatekeeper_phase_for_window()`.
- **D-02c:** `_names_match()` wird EBENFALLS gelöscht — nur von classify_contact() genutzt, nach dessen Löschung Dead Code. CLAUDE.md Punkt 3 Pruning-Pflicht.
- **D-02d:** `populate_context_notes()` bleibt unverändert als Foundation-Stub für Phase 08.23.2.I. Foundation-Code-Register-Eintrag existiert bereits, prüfen ob er current ist.
- **D-02e:** gatekeeper.py wird zur Single-Function-Datei — akzeptabel weil Modul-Heimat semantisch sinnvoll.
- **D-02f:** Imports in gatekeeper.py die nur von gelöschten Funktionen genutzt werden (anonymization.extract_entities, ki_logik.TRIGGER_PHRASES etc.) ebenfalls entfernen → kein toter Import-Ballast.

### D-03: Toggle-Button Design (pip-mode-indicator)

**Implementierungs-Pflichtliste — Plan-Agent muss jeden Punkt 1:1 umsetzen:**

- **D-03a:** `<span id="pip-mode-indicator">` wird zu `<button type="button" id="pip-mode-indicator">` migriert. Kein neues separates DOM-Element.
- **D-03b:** `aria-label` dynamisch: "Modus wechseln zu Entscheider" (wenn aktuell Sekretär) / "Modus wechseln zu Sekretär" (wenn aktuell Entscheider).
- **D-03c:** CSS `cursor: pointer` bei Hover.
- **D-03d:** Hover-State: Hintergrundfarbe leicht ändern via `var(--pip-gatekeeper-bg-hover)` (neuer Token, analog zu --pip-gatekeeper-bg aber leicht dunkler/heller für Feedback).
- **D-03e:** Mindest-Klick-Fläche: 32px Höhe, ausreichend Padding für zuverlässiges Treffen im Cold-Call.
- **D-03f:** Button-Label zeigt IMMER den aktuellen Modus ("Sekretär" oder "Entscheider"), NICHT das Ziel.
- **D-03g:** Tastatur-Focus via Tab + Enter als sekundärer Interaktions-Pfad (button-Element bringt das kostenlos mit). Kein primärer Shortcut.
- **D-03h:** CSS-Token-only — keine hardcoded Hex-Farben. --pip-gatekeeper-bg-hover muss in nerve.css definiert werden.
- **D-03i:** Klick-Handler in pip-launcher.js: emittet `socket.emit('manual_mode_toggle', {category: ...})` (bestehender Pattern bleibt, nur Klick-Target ändert sich von keydown zu button-click).

### D-04: call_events — mode_switch + mode_initial

**Skip-Guard + Initial-Event-Pattern:**

- **D-04a:** Skip-Guard im manual_mode_toggle-Handler (deepgram_service.py): wenn `call_id` im Session-State None ist → State wechseln wie bisher, aber KEIN call_events-INSERT. Log-Zeile: `[pip] mode_switch: call_id not set, skip event`. Kein Crash, kein UX-Problem.
- **D-04b:** `create_call_for_sid()` schreibt nach Call-Record-Anlage einen `mode_initial`-Event:
  - `event_type='mode_initial'`
  - `payload={'mode': current_mode_from_session_state, 'category': contact_category_from_session_state, 'sid': sid, 'timestamp': monotonic()}`
  - call_id aus dem soeben angelegten Call-Record
- **D-04c:** Zweck von mode_initial: Post-Call-Analyse kennt den Startpunkt auch wenn User vor Anruf getoggled hat. Ohne mode_initial → call_events leer → Analyse geht fälschlicherweise von Default Sekretär aus auch wenn User zu Entscheider gewechselt hat.
- **D-04d:** mode_switch-Event payload (unverändert aus Req-6): `{old_mode, new_mode, old_category, new_category, timestamp}`.
- **D-04e:** Migration 0004 muss BEIDE event_types abdecken: 'mode_switch' + 'mode_initial'. (Verknüpft mit D-01c.)

### Claude's Discretion

- CSS-Token-Werte für `--pip-gatekeeper-bg`, `--pip-gatekeeper-text`, `--pip-gatekeeper-bg-hover`: konkrete Farbwerte wählen die Light-Mode-konform und nicht Amber (--pipeline-warning-bg) sind. Teal-Variante oder Neutral-Blau bevorzugt, da Gatekeeper kein Fehler-/Warn-Zustand ist.
- Reihenfolge der Plan-Tasks: Planner entscheidet ob Löschen zuerst oder Hinzufügen zuerst.
- Badge-default-Token-Werte (--badge-default-bg, --badge-default-text) für Z.2582 Fix: konkrete Farben nach eigenem Ermessen (Light-Mode-konform, lesbar).
