# Phase 08.5 Plan 06: Profile Editor FAQ CRUD + Tabu-Begriffe Summary

Profile editor gains database-backed FAQ section (sec-faqs, section 14) and tabu terms tag-input (sec-tabu, section 15). Five new org-isolated API endpoints enable full CRUD for profile_faqs table and JSON-stored tabu_begriffe list.

## What Was Built

### Task 1: Backend (routes/profiles.py)

**Helper function:**
- `_require_own_profile(profile_id)` — returns `(Profile, db)` if `profile.org_id == g.org.id`, else `(None, db)`. Used by all 3 profile-scoped endpoints.

**5 new endpoints:**

| Endpoint | Method | Function |
|----------|--------|----------|
| `/api/profile/<pid>/faqs` | GET | `api_faqs_list` — returns `{faqs: [{id, frage_muster, antwort, kategorie, used_count}]}` |
| `/api/profile/<pid>/faqs` | POST | `api_faqs_create` — validates frage/antwort/kategorie, creates ProfileFaq row |
| `/api/profile/faqs/<faq_id>` | PUT | `api_faqs_update` — org-isolated update, validates each field independently |
| `/api/profile/faqs/<faq_id>` | DELETE | `api_faqs_delete` — org-isolated delete |
| `/api/profile/<pid>/tabu` | POST | `api_tabu_update` — sanitizes list (strip, dedupe, 80-char max, 50-item max), merges into `profile.daten['basis']['tabu_begriffe']` |

**Constants and validation:**
- `_FAQ_KATEGORIEN = {'Technik', 'Preis', 'Referenzen', 'DSGVO', 'Produkt', 'Sonstiges'}`
- `_MAX_FRAGE_LEN = 2000`, `_MAX_ANTWORT_LEN = 2000`
- `_MAX_TABU_ITEM_LEN = 80`, `_MAX_TABU_COUNT = 50`
- All 5 endpoints: `@login_required` + org-isolation

**tabu_begriffe canonical location:** `profile.daten['basis']['tabu_begriffe']` (same path as Plan 03's read path).

### Task 2: Frontend

**templates/profile_editor.html changes:**
- Added sidebar nav links: section 14 "FAQ-Datenbank", section 15 "Tabu-Begriffe"
- Added `ALL_SECS` entries for `sec-faqs` and `sec-tabu`
- Added `window.PROFILE_DATEN = {{ daten | tojson | safe }}` for tabu initial load
- Added `sec-faqs` section with `<template id="tpl-faq-row">` for safe row cloning
- Added `sec-tabu` section with `#tabu-tags-container`, `#tabu-tag-input`, `#vi_tabu_begriffe`
- Added `<script src="{{ url_for('static', filename='profile_editor.js') }}">` at end of block

**static/profile_editor.js (new file):**

| Function | Purpose |
|----------|---------|
| `loadFaqs()` | GET /api/profile/<pid>/faqs, renders each row via renderFaqRow() |
| `renderFaqRow(faq)` | Clones <template>, wires blur/change → persistFaq, delete → deleteFaq |
| `persistFaq(row)` | PUT if row has data-faq-id, POST if new — requires both frage+antwort |
| `deleteFaq(row)` | confirm() → DELETE /api/profile/faqs/<id> → row.remove() |
| `loadTabu()` | Reads from window.PROFILE_DATEN.basis.tabu_begriffe or hidden input |
| `renderTabuChip(term)` | Creates chip with textContent (not innerHTML), X button removes |
| `saveTabu()` | POST /api/profile/<pid>/tabu with current tabuList |

**UX details:**
- FAQ rows autosave on blur (only when both frage_muster and antwort are non-empty)
- Tabu term added via Enter key, removed via chip × button
- Each chip removal immediately triggers saveTabu() POST
- used_count displayed as read-only "N×" label per FAQ row

var PROFILE_ID = {{ profile.id if profile else 'null' }};

## tabu_begriffe Canonical Location

`profile.daten['basis']['tabu_begriffe']` — list of strings under the `basis` sub-dict.

Plan 03 (claude_service.py integration) should read from `daten.get('basis', {}).get('tabu_begriffe', [])`. This is the canonical path. The `api_tabu_update` endpoint always writes to this location.

## fetch-wrapper / apiClient Reuse

No shared `apiClient` helper exists in this codebase. All existing CRUD in `profile_editor.html` (skripte, opener) uses raw `fetch()`. `profile_editor.js` follows the same pattern — raw `fetch` with `credentials: 'same-origin'`.

## All 5 Endpoints Return JSON on Success and Error Paths

Confirmed:
- `api_faqs_list`: `jsonify({faqs: [...]})` or `jsonify({'error': 'not_found'})`, 404
- `api_faqs_create`: `jsonify({'id': ..., 'used_count': ...})`, 201 or `jsonify({'error': ...})`, 400/404
- `api_faqs_update`: `jsonify({'ok': True})` or `jsonify({'error': ...})`, 400/403/404
- `api_faqs_delete`: `jsonify({'ok': True})` or `jsonify({'error': ...})`, 403/404
- `api_tabu_update`: `jsonify({'ok': True, 'count': N})` or `jsonify({'error': ...})`, 400/404

## Deviations from Plan

**[Rule 2 - Auto-add] Used existing CSS classes for tag chips**

The plan suggested adding new `.tag-chip` and `.tag-x` CSS rules but `profile_editor.html` already defines `.tag-chip` and `.tag-rm` classes (lines 150-166 of the CSS block) that match the design system. The new tabu section reuses these existing classes rather than duplicating them. The plan's suggested CSS would have overridden or conflicted with existing styles.

**[Rule 3 - Adjustment] FAQ rows styled using existing .block / .btn-rm classes**

The plan's suggested `.faq-row` and `.faq-meta` CSS rules were not needed since the `block`, `btn-rm`, and other existing classes achieve the same layout. No new CSS was added.

## Known Stubs

None — FAQ CRUD is fully wired to the new endpoints. Tabu list is fully wired to `api_tabu_update`. No hardcoded empty values flow to UI rendering.

## Threat Model Mitigations Applied

- **T-08.5-06-01 (Cross-org FAQ read):** `_require_own_profile()` checks `profile.org_id == g.org.id` on every profile-scoped endpoint. PUT/DELETE endpoints query Profile directly and check org_id.
- **T-08.5-06-02 (Prompt injection via FAQ antwort):** Not applicable here — FAQ antwort is not interpolated into any system prompt by this plan.
- **T-08.5-06-03 (XSS via FAQ antwort):** `renderFaqRow()` uses `<template>` cloneNode + `.value` assignment. `renderTabuChip()` uses `createTextNode()`. No `innerHTML` with user data.
- **T-08.5-06-05 (Invalid kategorie):** `_FAQ_KATEGORIEN` whitelist enforced on create and update.
- **T-08.5-06-06 (Tabu term list bloat):** 50-item limit + 80-char-per-item limit enforced server-side.
- **T-08.5-06-07 (Non-string tabu items):** `isinstance(b, str)` check skips non-strings.

## Threat Flags

None — no new network endpoints or auth paths beyond the 5 planned endpoints. All endpoints are under the existing `profiles_bp` blueprint with `@login_required`.
