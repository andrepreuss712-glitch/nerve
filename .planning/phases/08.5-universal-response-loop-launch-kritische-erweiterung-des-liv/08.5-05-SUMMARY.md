## Deviations from Plan

**1. [Rule 2 - Architecture] generate_response/generate_response_with_mood: version resolved for logging, not prompt override**

- **Found during:** Task 2
- **Issue:** `generate_response` receives a pre-built `system_prompt` from callers in `routes/training.py`. The callers use `build_customer_prompt`/`build_personality_prompt` to build prompts — swapping to override `system_prompt` internally would break the caller-built persona context (name, firma, schwierigkeit substitutions).
- **Fix:** Version is resolved + logged inside the function. The system prompt passed by caller is used for the API call unchanged. This preserves zero-regression while adding FT traceability.
- **Future work:** Full prompt-override from DB requires either (a) threading `user_id` through all callers + moving prompt-build inside the functions, or (b) a separate `user_id` param addition. Deferred per D-07 Step F.

**2. [Rule 3 - Deviation] _SCORING_FALLBACK_TEMPLATE without f-string substitutions**

- **Found during:** Task 1
- **Issue:** `generate_scoring` inline prompt is a complex f-string with dynamic content (gespraech, schwierigkeit, stimmungsverlauf, etc.). Extracting it as a static template would require a templating mechanism to re-inject these variables.
- **Fix:** `_SCORING_FALLBACK_TEMPLATE` is a static header string (the intent/instructions part). The full dynamic prompt is still built as an f-string in `generate_scoring`. The preamble acts as a future DB-configurable override hook.
- **Impact:** None — scoring behavior identical, version tag is logged correctly.

## Known Stubs

None — all 4 modules route through prompt_versions with live DB lookup. Fallbacks to constants ensure zero-regression when prompt_versions rows are placeholder seeds (from Wave 1) or missing.
