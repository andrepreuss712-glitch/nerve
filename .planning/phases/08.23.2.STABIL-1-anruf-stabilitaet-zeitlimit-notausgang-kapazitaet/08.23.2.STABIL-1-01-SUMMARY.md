# Phase 08.23.2.STABIL-1 Plan 01: Per-Request LLM Timeout Summary

One-liner: Per-request Anthropic client copies (`with_options(timeout=..., max_retries=...)`) on 15 HTTP-reachable call-sites replace the SDK's 600s/2-retry default, keeping the module-wide client (and its two live streams) untouched — fixing the `/api/beenden` hang that blocked both failed live calls.

## What Was Built

**Task 1 — Constants + helper.** `config.py` gained `HTTP_LLM_TIMEOUT_S` (20s), `HTTP_LLM_TIMEOUT_LONG_S` (45s), `HTTP_LLM_MAX_RETRIES` (default `0`, env-overridable). `services/claude_service.py` gained `http_llm_client(long_running=False)`, which returns a `claude_client.with_options(...)` copy — the module-level `claude_client = anthropic.Anthropic(...)` at line 27 is untouched (verified: no `timeout=`/`max_retries=` in the constructor).

**Task 2 — 15 call-sites converted.** Every `claude_client.messages.create(` at an HTTP-reachable call-site now reads `http_llm_client().messages.create(` (STANDARD, 11 sites) or `http_llm_client(long_running=True).messages.create(` (LANG, 4 sites). Arguments, cost-hooks (`log_api_cost`), and existing error handling are byte-for-byte unchanged — only the receiver of `.messages.create(` was swapped.

**Task 3 — 5 runtime tests** in `tests/test_stabil1_http_llm_timeout.py`: HTTP path sets `with_options(timeout<=20, max_retries<=1)`; LANG path sets `timeout==HTTP_LLM_TIMEOUT_LONG_S, max_retries==0`; daemon path (`analysiere_mit_claude`) never calls `with_options`; the module client stays the same object (`is`-comparison) after an HTTP call; config arithmetic stays under 55s. `usage=None` on all fake responses keeps the cost-hooks inert so no test needs a real DB — except `generate_postcall_analysis`, whose duplicate-guard + persist step mocks `database.db.get_session`.

## Call-Sites Without a Surrounding `except` (STABIL-2 Candidates)

Per plan rule (Leitsatz 2 / scope boundary): where a call-site lacks a surrounding `except`, this is **noted**, not fixed, in this plan.

**Found — `routes/training.py` `training_respond()` (lines ~413-580) has ZERO `try`/`except` anywhere in the function.** It calls three LLM functions directly:
- `services/training_service.py:868` `generate_response_with_mood` (called at `routes/training.py:456`)
- `services/training_service.py:808` `generate_response` (called at `routes/training.py:479` and `:557`)

Neither `generate_response` nor `generate_response_with_mood` itself wraps its `messages.create` call in a `try`/`except` (the `try` inside each only wraps the post-call cost-hook logging, not the LLM call). When these two functions are called from `training_start()` (routes/training.py:164-397, which DOES have a `try`/`except`) the exception is caught by the caller. When called from `training_respond()`, there is **no catch at any level** — an `anthropic.APITimeoutError` (or any other SDK exception) would propagate unhandled out of the Flask view, returning a 500 instead of the graceful degradation seen elsewhere (e.g. `crm_service` → `app_routes.py:302-316`).

All other 13 of the 15 converted call-sites are covered by a `try`/`except` — either immediately around the call (`generate_postcall_analysis`, `get_or_generate_weekly_report`, `validate_user_text`, `classify`, `_generiere_briefing`, `_generiere_empfehlungen`, `generate_personalized_skript`, `generate_help_suggestion`, `generate_scoring`, `_generate_live_preview`, `api_training_personality_generate`) or at the immediate caller (`generate_crm_export` ← `app_routes.py:302-316`, `_generate_weekly_summary` ← its own function-level `try`).

**Recommendation for STABIL-2:** wrap `training_respond()`'s three LLM-touching sections in `try`/`except`, mirroring the pattern already used in `training_start()`/`training_help()`/`training_end()`. Not built in this plan (scope boundary, no new try/except per plan rule).

## K2 — Multi-Call Route Residual Risk (Documented, Not Fixed Here)

The per-call timeout is per **individual** LLM call, not per HTTP request. Four routes make two sequential LLM calls in the same request and can together exceed 60s even with the new limits:

- `routes/dashboard.py:524` + `:582` (`index()`) — **2× LANG (45s each)**, worst case ~90s. **Sharpest residual risk** — every dashboard load runs `_generate_weekly_summary` (no cache, `dashboard.py:523-524`) synchronously while holding a DB connection open (`:445`→`:620`).
- `precall_service.py:257` + `:279` (`recherche_firma`) — STANDARD + STANDARD.
- `training.py:618` + `:649` (`training_end`) — LANG + STANDARD.
- `learning.py:42` + `:96` (`api_postcall_analysis`) — LANG + STANDARD.

With `HTTP_LLM_MAX_RETRIES=0` (K1), STANDARD is now hard-capped at 20s, so the mixed routes fall to ~40-65s worst case; the pure 2×-LANG dashboard route remains the sharpest open risk at up to ~90s.

**Root fix (STABIL-2 candidate, not built here):** cache `_generate_weekly_summary` — it currently has no cache and runs on every dashboard load with a 45s Sonnet budget, holding the DB connection open the whole time. This plan does not touch it (scope boundary: single-call timeout only).
