## Corrected Connection Budget (K1)

**Original plan table was wrong** — it claimed `nerve-rt.service` has "its own pool (~2 aktiv)". Verified false by grep: `nerve_rt/services/session_manager.py:73-77` does `from database.db import SessionLocal` — it imports the **same** `database/db.py` module, same `DATABASE_URL`, same engine object. There is no separate nerve-rt pool.

**Corrected reasoning:** the pool change (20+15) raises nerve-rt's effective cap to 35 too.

| Verbraucher | max Verbindungen |
|---|---|
| Haupt-App (gunicorn/Flask) | pool_size 20 + max_overflow 15 = **35** |
| `nerve-rt.service` (shares the same engine/pool) | same cap, up to **35** |
| Wartung (`psql`, `inspect.sh`, Deploy-Gate) | wenige |
| **Worst-case Summe** | **70 of 97 usable** (max_connections=100, 3 reserved) |

70/97 is still safe — the pool fills lazily and nerve-rt draws real connections only when active. The optional env-override to hold nerve-rt at a lower cap (e.g. 5+3, via `deploy/nerve-rt.service`) was evaluated and **deliberately skipped** — not required since 70/97 already has headroom, and adding it would touch a file outside this plan's declared scope without a corresponding need.

## K2 Note (awareness only, no change)

Routes that hold a DB session open across a 45s LANG call (`dashboard.py:445`->`:620`) pin a pool connection for the call's duration. `pool_timeout=10s` (not the SQLAlchemy default 30s) is the correct choice here: a fast, visible `TimeoutError` instead of a request hanging for up to half a minute under pool exhaustion. The root fix (caching the dashboard summary so the session isn't held open across the LLM call) is deferred to STABIL-2 — this plan does not touch `dashboard.py`.

## Decisions Made
- Corrected the plan's budget-reasoning table (K1) to reflect the shared-engine reality (70/97, not "nerve-rt eigener Pool").
