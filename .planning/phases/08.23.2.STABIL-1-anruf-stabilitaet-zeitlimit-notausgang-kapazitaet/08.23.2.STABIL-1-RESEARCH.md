## 3. Fehler 3 — Kapazität

### 3.1 Ist-Stand

| Beleg | Wert |
|---|---|
| `deploy/nerve.service:26-27` | `--workers 1 --threads 4` |
| `deploy/nerve.service:29` | `--timeout 120` (killt gthread **nicht** pro Request) |
| `deploy/nerve.service:23` | Kommentar „optimal for CX22 (2 vCPU, 4 GB RAM)" — **stale**, s. 3.2 |
| `app.py:47` | `async_mode='threading'` |
| `database/db.py:17` | `create_engine(_DATABASE_URL, connect_args=_connect_args)` — **keine Pool-Parameter** → SQLAlchemy-Default `pool_size=5`, `max_overflow=10`, `pool_timeout=30` |

Jede WS-Verbindung belegt für die gesamte Anruf-Dauer einen Thread → **max ~3 parallele Calls**.

### 3.2 Prod-Fakten (SSH read-only, 2026-07-23)

```
$ nproc                      -> 4
$ free -m (total)            -> 7745 MB   (nicht 2 vCPU / 4 GB — Unit-Kommentar ist veraltet)
$ SHOW max_connections       -> 100
$ SHOW superuser_reserved_connections -> 3
$ SHOW shared_buffers        -> 128MB
$ pg_stat_activity           -> nerve_app|nerve|2, postgres|*|2, idle|4
$ systemctl (nerve*)         -> nerve.service (gunicorn) + nerve-rt.service (FastAPI/uvicorn)
$ live ExecStart             -> identisch mit deploy/nerve.service (threads 4)
```

**Verbindungs-Budget:** 100 − 3 reserviert = **97 nutzbar**, geteilt mit `nerve-rt.service` (eigener Prozess, eigener Pool, gleicher `DATABASE_URL`-Key in `/etc/nerve/.env`).
Ein Pool von `pool_size=20 + max_overflow=15` = **max 35** Verbindungen aus der Haupt-App ist damit sicher (35 + nerve-rt + psql-Wartung ≪ 97).

### 3.3 Warum der Pool sonst der neue Engpass wird

64 Threads, die alle DB anfassen, gegen einen 5+10-Pool: der 16. gleichzeitige Request wartet `pool_timeout=30 s` und bekommt dann `TimeoutError`. Der Engpass wäre nur von gunicorn nach SQLAlchemy gewandert. → Pool **muss** in derselben Änderung mit.

### 3.4 Keine zusätzlichen Worker

`--workers 1` **bleibt**. Mehr als ein Worker ohne Socket.IO-`message_queue` + Sticky-Sessions zerreißt die Rooms (jeder Worker hätte eigene In-Memory-Rooms). Steht so im ROADMAP-Eintrag, hier bestätigt: `app.py:47` `async_mode='threading'` ohne `message_queue`-Parameter.
