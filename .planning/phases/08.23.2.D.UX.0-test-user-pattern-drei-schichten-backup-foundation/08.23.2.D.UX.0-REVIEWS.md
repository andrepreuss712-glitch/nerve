## Gemini Review

### 1. Summary
The phase establishes a robust, highly secure foundation for isolating and backing up anonymized training data. The 3-layer backup strategy and the use of an IONOS S3 WORM configuration directly address catastrophic risks (ransomware, account compromise) while rigidly respecting DSGVO constraints. The architectural decisions (like separating the schema and delaying the `is_test_user` filter to write-time) are well-thought-out. However, there are two high-severity execution flaws—an email guard bypass and a PostgreSQL authentication trap—that will cause silent failures in production if not corrected.

### 2. Strengths
* **Write-Time-Filter Contract (C-03):** Pushing the `is_test_user` filtering to the application layer (D.UX.1) instead of using complex cross-schema `JOIN`s during `pg_dump` is an excellent architectural decision. It keeps the backup script clean, ensures `training.*` can be dumped in its entirety, and preserves the ADR rule of zero foreign keys to `public.*`.
* **Ransomware Protection Architecture:** The interaction between the 30-day COMPLIANCE WORM lock and the 365-day rotation script is logically sound. Objects cannot be deleted for 30 days (guaranteeing a ransomware-proof recovery window), and the rotation script safely cleans up objects only after 365 days when the WORM lock has long expired.
* **Role Isolation:** Splitting the `CREATE ROLE` into a Runbook step ensures passwords stay out of VCS, while keeping the schema layout and `GRANT`s predictably versioned in Alembic.
* **Graceful Health Degradation:** The `/api/health` route safely swallows file `IOError`s and falls back to `None` before the first monthly S3 restore test runs, preventing application crashes.

### 3. Concerns
* **HIGH** — Plan 01, Task 3: Email guard bypass via string iteration. In `_send(payload)`, if `payload.get('to')` is passed as a single string (e.g., `'andre-test@nerve.local'`) instead of a list, `any(r.endswith('@nerve.local') for r in recipients)` will iterate over individual characters (`'a'`, `'n'`, `'d'`, ...). The condition will evaluate to `False` and the test email will be sent, defeating the guard.
* **HIGH** — Plan 03, Task 2: PostgreSQL Peer Authentication failure in the S3 backup script. `pg_dump -U nerve_anon_worker -d nerve` defaults to connecting over a local Unix socket. Because the systemd service runs as `User=root`, Postgres will see the OS user `root` trying to authenticate as the DB user `nerve_anon_worker`. This violates default `peer` authentication in `pg_hba.conf`, causing connection rejection and entirely ignoring the `PGPASSWORD` environment variable.
* **MEDIUM** — Plan 03, Task 2: Bash `pipefail` trap. The S3 rotation pipeline uses `grep '^training-'`. Because `set -euo pipefail` is active, if `grep` ever finds no matching files, it will exit with `1`, causing the entire pipeline to fail and the script to immediately abort before logging completion. (This is unlikely to happen immediately because a file is uploaded right before the check, but it makes the script brittle).

### 4. Suggestions
* **Fix the Email Guard (Plan 01, Task 3):** Normalize the `recipients` variable to a list before iterating to ensure strings are handled correctly.
  ```python
  recipients = payload.get('to', [])
  if isinstance(recipients, str):
      recipients = [recipients]
  if any(r.endswith('@nerve.local') for r in recipients):
      # ...
  ```
* **Fix the S3 Backup Script (Plan 03, Task 2):** Add `-h 127.0.0.1` to the `pg_dump` command. Forcing a TCP connection bypasses `peer` authentication and triggers the `host` rules in `pg_hba.conf` (like `scram-sha-256` or `md5`), which will correctly consume the provided `PGPASSWORD`.
  ```bash
  pg_dump -h 127.0.0.1 -U nerve_anon_worker -d nerve \
      --schema=training --no-owner --no-acl \
      | gzip > "$TMP_FILE"
  ```
* **Harden the S3 Rotation Pipeline (Plan 03, Task 2):** Protect the `grep` command from aborting the script by wrapping it to absorb the exit code:
  ```bash
  aws s3 ls "s3://${BUCKET}/" --endpoint-url "$IONOS_ENDPOINT" \
      | awk '{print $4}' \
      | (grep '^training-' || true) \
      | while read -r obj; do
  ```
* **Postgres Downgrade Edge-Case (Plan 01, Task 1):** In `downgrade()`, `DROP SCHEMA IF EXISTS training` will fail if the schema is not empty. This is safe for now (as `transcript_archive` is dropped immediately prior), but remember that future D.UX.1 objects in the `training` schema will need to be dropped in their own respective downgrades to prevent blockages.

### 5. Risk Assessment
**MEDIUM**. Fundamentally, the architectural design is excellent and highly secure (LOW risk). However, the execution contains two deterministic bugs (the email guard iteration and the Postgres peer-auth drop) that will cause failures in production during the execution of these plans. Once these specific implementation flaws are addressed, the phase will be exceptionally solid and ready for deployment.

   Plan 03 Task 2 pg_hba.conf finding — make the pg_hba host-auth line for

   wrap as `(grep '^training-' || true)`. Same pattern also applies to the Plan 02

### BLOCKER 3 — Role-check too shallow (Plan 01, D-07 / Persistenz-Schicht-Verifikation)
The current D-07 verification proves only the *connection-user NAME* (from `DATABASE_URL`
/ `inspect.sh env-keys`). A user named `nerve_app` can still be a cluster **SUPERUSER**
or the **OWNER** of the `training` schema — in which case the whole `training.*` GRANT
isolation (D-06) is silently void: a superuser/owner bypasses GRANTs entirely.
- **Action:** D-07's evidence block (in Plan 01's `## 5. Persistenz-Schicht-Verifikation`)
  MUST include `psql -c '\du <app-role>'` output showing the role's attribute list
  (proves NOT `Superuser`), PLUS an owner-check on the `training` schema
  (`SELECT nspname, r.rolname AS owner FROM pg_namespace n JOIN pg_roles r ON n.nspowner=r.oid WHERE nspname='training';`
  — must NOT be the app role). The name-from-env-keys check alone is insufficient.
- If the app role IS superuser/owner → record as Finding (per D-07 this phase only
  verifies + flags; full restriction is G/MEET Wave 1), but the verification itself
  must be deep, not name-only.

### BLOCKER 4 — IONOS Object-Lock COMPLIANCE goes hard-30d on first write (Plan 03, Task 1+2)
Plan 03 Task 1 (`03:144-146`) sets bucket **default-retention COMPLIANCE 30d** at
creation, and Task 2 (`03:227-232`) uploads real objects with `retain-until = now+30d`.
COMPLIANCE means NOBODY (not even root/master-key) can delete before expiry. If the
endpoint / object format / bucket is misconfigured, the very first upload is **30 days
of un-deletable garbage**.
- **Action — staged WORM bring-up:**
  1. Create the bucket with Object-Lock **enabled** (required at creation, not
     retrofittable) but do **NOT** set a 30d COMPLIANCE default-retention yet.
  2. First smoke `put-object` with an explicit short retention
     `--object-lock-retain-until-date now+1day` (still COMPLIANCE, but only 1 day at
     risk if wrong).
  3. Verify the round-trip: download the object, gunzip, confirm it restores cleanly
     (format + integrity), and confirm `get-object-lock-configuration` /
     `head-object` report the lock as expected.
  4. ONLY after the 1-day smoke restore succeeds, switch the default-retention (and the
     real backup script's `retain-until`) to the full **30d COMPLIANCE**.
- This makes a misconfig cost ≤1 day, not 30.

### WARNING W-1 — `apt-get install awscli` is v1, plan requires v2 (Plan 03, Task 1 `03:138-139`)
C-07 / RESEARCH require **aws-cli v2** (`s3api put-object --object-lock-*` is reliable
only on v2). Debian/Ubuntu `apt-get install awscli` ships **v1**.
- **Action:** Replace the apt install with the official aws-cli **v2 zip installer**
  (`curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip
  && unzip awscliv2.zip && ./aws/install`), and assert `aws --version` reports
  `aws-cli/2.x`.

### WARNING W-2 — `--region de` vs endpoint `s3.eu-central-1.ionoscloud.com` inconsistent (Plan 03, Task 1 `03:143-144`)
The bucket-create uses `--region de` while the endpoint is `s3.eu-central-1.ionoscloud.com`.
These are likely mismatched.
- **Action:** Verify the correct IONOS endpoint/region pair against current IONOS S3
  docs (Context7 / IONOS docs) and make `--region` consistent with the endpoint host
  (e.g. `eu-central-1` ↔ `s3.eu-central-1.ionoscloud.com`). Use one canonical pair
  everywhere (bucket-create, put-object, restore-test, ionos-s3.env).

### WARNING W-3 — Versioning not separately verified, but Object-Lock requires it (Plan 03, Task 1 `03:154`)
S3 Object-Lock requires bucket Versioning to be enabled. Task 1 verifies the
object-lock-configuration but not versioning.
- **Action:** Add `aws s3api get-bucket-versioning --bucket nerve-training-backup
  --endpoint-url "$IONOS_ENDPOINT"` to the Task 1 verification and assert
  `Status: Enabled`.

### WARNING W-4 — rsync push precedes local rotation under `set -e` (Plan 02, Task 2 `02:131-160`)
The Schicht-2 rsync push block sits before the local Schicht-1 rotation, all under
`set -e`. A Storage-Box outage → rsync exits non-zero → script aborts → the local
30d rotation never runs (local disk slowly fills).
- **Action:** Wrap the rsync push so a Box failure is logged but non-fatal
  (`rsync ... || echo "[BACKUP] Schicht 2: Push FAILED (box unreachable) — continuing"`),
  so local rotation always runs. (Pairs with Gemini's MED grep-pipefail finding on the
  same script — harden both.)
