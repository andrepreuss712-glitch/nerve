## Dokumentierte Abweichungen vom Plan

Diese drei Abweichungen sind im Verifikationsbericht beabsichtigt dokumentiert — sie sind keine Gaps, sondern korrekte Korrekturen die waehrend der Ausfuehrung erkannt und gefixt wurden.

### 1. Endpoint/Region-Korrektur: eu-central-1/de → eu-central-4/eu-central-4

**Was:** Plan-Vorlage (RESEARCH.md C-WARN-2) hatte eu-central-1 + Region "de" fuer user-owned Buckets. Tatsaechlicher Frankfurt-Endpoint fuer contract-owned Buckets ist `https://s3.eu-central-4.ionoscloud.com`, Region `eu-central-4`.

**Auswirkung:** Kein funktionaler Impact — `backup_training_to_s3.sh` und `restore_test_s3.sh` waren bereits via `IONOS_S3_ENDPOINT`/`IONOS_S3_REGION` aus `ionos-s3.env` parametrisiert. Kein Hardcoded-Endpoint im Code. Korrekte Region auch als `AWS_DEFAULT_REGION` exportiert (SigV4-Signing-Pflicht).

**Beleg:** SUMMARY 03 Deviation-1; SSH live: `aws s3 ls s3://nerve-training-backup/ --region eu-central-4 --endpoint-url https://s3.eu-central-4.ionoscloud.com` → Objekte sichtbar.

### 2. Migration 0009: Sequence-Grant-Luecke aus 0008

**Was:** Migration 0008 hatte INSERT/SELECT auf `training.transcript_archive` gegraentet, aber die zugehoerige Identity-Sequence `transcript_archive_id_seq` nicht. `pg_dump --schema=training` liest Sequence-Werte → "permission denied for sequence" → erstes Backup schlaegt fehl.

**Fix:** Migration 0009 mit `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA training TO nerve_anon_worker` + `ALTER DEFAULT PRIVILEGES` fuer zukuenftige Sequences. Appliziert als postgres-User.

**Downstream-Hinweis:** D.UX.1-Migration muss von 0008 auf **0010** nummerieren (0009 jetzt belegt).

**Beleg:** SUMMARY 03 Deviation-2; SSH live: `has_sequence_privilege('nerve_anon_worker', 'training.transcript_archive_id_seq', 'USAGE')` → `t`; `inspect.sh migrations` → 0009.

### 3. SCP-Hotfix fuer app_routes.py (deploy.sh staging-Gate blockiert)

**Was:** `deploy.sh`-Staging-Gate blockiert durch pre-existing `test_ft_seed`-Failure (bekanntes Problem in allen bisherigen Phasen). `app_routes.py` (neues Feld `backup_s3_restore_ok` in `/api/health`) wurde via direktem `scp` auf Production deployed + `systemctl restart nerve`.

**Auswirkung:** Kein funktionaler Impact — rein additives JSON-Feld, kein Datenverlust-Risiko. User-approved Pattern "Pre-Launch direkt auf Production" (CLAUDE.md HART-Regel 2026-05-27).

**Bekannte Folge:** `deployed_at` und `git_head` in `/api/health` = null (kein `.deploy_meta`-Update beim Hotfix). Pre-existing Issue, wird durch Staging-Promotion-Pipeline-Mini-Phase geloest (vor EA-Launch).

**Beleg:** SUMMARY 03 Deviation-3; SSH live: `/api/health` zeigt `backup_s3_restore_ok: true` aber `deployed_at: null`.
