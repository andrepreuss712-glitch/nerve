<decisions>
## Implementation Decisions

### A) Test-User-Pattern

- **A-01:** `users.is_test_user BOOLEAN NOT NULL DEFAULT FALSE` — neue Spalte auf bestehender
  `users`-Tabelle (KEINE separate `test_users`-Tabelle). Reiht sich neben existierende
  Boolean-Flags `is_superadmin`, `is_trial`, `is_coach` (`database/models.py:64ff`).
- **A-02:** **Email-Send-Schutz = zentraler Guard in `_send(payload)`** (`services/email_service.py:17`).
  Resend (nicht SMTP) → `_send` ist der einzige Chokepoint für alle 6 Call-Sites
  (`auth.py`, `oauth.py`, `admin_views.py`). Check: wenn ein Empfänger in `payload['to']`
  auf `@nerve.local` endet (nicht-routbare Test-Domain) → kein Send, Log
  `[EMAIL] test-user recipient, skip`. Kein DB-Lookup nötig (Domain-Check reicht), kein
  globaler ENV-Schalter (würde echte Production-User-Mails blocken). Verworfen: ENV-Schalter
  (blockiert echte User), per-Call-Site-Check (fehleranfällig bei neuen Call-Sites).
- **A-03:** **Test-Call-Markierung via JOIN auf `users.is_test_user`** — KEINE dedizierte
  `calls.tag`-Spalte. Backup-Filter, DPO-Sammler (Phase E) und Analytics-Dashboard joinen
  `calls.user_id → users.is_test_user`. Single Source of Truth, kein Drift. Entspricht exakt
  dem Roadmap-Filter (`WHERE user_id IN (SELECT id FROM users WHERE is_test_user=TRUE)`).
  Hinweis: Roadmap nannte `tag='test'` wörtlich — bewusst NICHT umgesetzt zugunsten der
  JOIN-Wahrheit (vermeidet Redundanz/Drift).
- **A-04:** Test-User-Account `andre-test@nerve.local` mit `is_test_user=TRUE` via
  **idempotentes `scripts/seed_test_user.py`** (INSERT mit Check/ON CONFLICT). Trennt
  Daten-Seed von Schema-Migration. Einmal via SSH auf Production ausgeführt, jederzeit
  wiederholbar. Verworfen: Seed-in-Migration (vermischt DDL+Daten, Passwort-Hash hässlich),
  manuell (nicht reproduzierbar).
- **A-05:** Analytics-Dashboard-Filter + DPO-Korpus-Sammler-Filter nutzen denselben
  JOIN-Filter aus A-03 (Phase E konsumiert ihn — hier nur Foundation/Spalte + Filter-Hook,
  Sammler selbst ist Phase E).

### B) Backup-Schicht 2 (Hetzner Storage Box)

- **B-01:** Storage Box ist **noch nicht bestellt** → Plan enthält Setup-Task als
  Voraussetzung: Box bestellen (~3 EUR/Mon, 100 GB, **gleicher Hetzner-AVV** wie Hauptsystem,
  kein neuer AVV nötig), SSH-Key hinterlegen. Andre führt Bestellung aus, Skript-Verdrahtung
  durch Executor.
- **B-02:** Transport **Push via rsync über SSH-Key** aus `backup_postgres.sh` heraus
  (nach erfolgreichem lokalem `pg_dump` + Size-Check). Push (nicht Pull) — Server hat
  bereits den Dump, Pull bräuchte separates Box-seitiges Setup. Verworfen: BorgBackup
  (Overkill für gzip-Dumps), simpler scp (kein Resume/inkrementell).
- **B-03:** **90-Tage-Rotation** (länger als die lokalen 30d aus 08.23.2.A).
- **B-04:** Dedizierter SSH-Key `/root/.ssh/id_storagebox` (nur für die Box). Box-Host/User
  als Konstante oben in `backup_postgres.sh` (analog zur bestehenden Skript-Struktur).
  Key-Auth, kein Passwort. NICHT in `/etc/nerve/.env` (Skript läuft als postgres-User via
  systemd-Timer).
- **B-05:** **Test-Restore-Verifikation** nach Setup (Dump von der Box ziehen + Integrität
  prüfen).

### C) Backup-Schicht 3 (IONOS S3 Object Storage)

- **C-01:** **Noch kein IONOS-Account** → Plan enthält Setup-Tasks: IONOS-Account anlegen,
  S3-Bucket erstellen, **AVV abschließen** (deutscher Anbieter, DSGVO-eindeutig, kein
  Drittland-Transfer — Cross-AI-Gemini-Empfehlung über Backblaze B2). Andre führt
  Account+AVV aus.
- **C-02:** **Object-Lock Compliance-Mode, 30 Tage WORM** + Versioning aktiv (Object-Lock
  setzt Versioning voraus). Compliance (nicht Governance): NIEMAND kann vor Ablauf
  löschen/überschreiben — auch nicht mit Root/Master-Key. Genau der Ransomware-Schutz den
  Gemini meint. Governance-Bypass (`s3:BypassGovernanceRetention`) wäre exakt das Loch das
  ein kompromittierter Account ausnutzt → verworfen.
- **C-03:** **Test-User-Filter greift WRITE-TIME, nicht beim Backup.** Der Background-Job
  (gebaut in D.UX.1) prüft `is_test_user` BEVOR er in `training.transcript_archive` schreibt
  → Test-Calls landen nie in `training.*`. Folglich ist das IONOS-Backup ein voller
  `pg_dump --schema=training` OHNE Filter. **Dies korrigiert die Roadmap-Skizze** (dump-time
  `WHERE source_call_hash NOT IN (...)`), die eine Brücke `training.* → calls` gebraucht
  hätte — exakt die FK-Entkoppelung die der ADR „Internes Datenmodell" verbietet
  (Re-Identifizierungs-Risiko). **D.UX.0 dokumentiert diese Write-Time-Filter-Regel als
  Contract; D.UX.1 implementiert sie.**
- **C-04:** Eigenes **`scripts/backup_training_to_s3.sh`** + eigener systemd-Timer (NICHT
  `backup_postgres.sh` erweitern). Begründung: andere Kadenz (365d), andere DB-Rolle
  (`nerve_anon_worker`), nur `training.*`, andere Credentials (IONOS S3).
- **C-05:** **365-Tage-Rotation.**
- **C-06:** IONOS-S3-Credentials (Access-Key/Secret) in eigener Datei
  **`/etc/nerve/ionos-s3.env`, chmod 600, root-only**, vom Skript gesourct. Getrennt von
  App-`.env` (kleinerer Blast-Radius). `nerve_anon_worker`-DB-Passwort separat
  (DB-Connection-String, ebenfalls aus Secrets).
- **C-07:** Push-Tool **aws-cli**: `aws s3api put-object --endpoint-url <ionos>
  --object-lock-mode COMPLIANCE --object-lock-retain-until-date <now+30d>`. Object-Lock pro
  Objekt ist S3-API-Feature, aws-cli deckt es nativ ab (rclone/s3cmd schwächer).
- **C-08:** **Restore-Test initial + monatlich automatisch** (systemd-Timer): zieht ein
  Objekt, prüft Integrität, setzt `/api/health`-Metrik. Backup das nie getestet wird ist
  kein Backup.
- **C-09:** **Verschlüsselung-at-rest verifizieren** (IONOS server-side encryption) als
  Teil des Setups.

### D) PostgreSQL-Schema `training.*` + Rolle `nerve_anon_worker`

- **D-01:** **Hybrid Migrations-Vehikel:** Alembic-Migration macht `CREATE SCHEMA training`
  + `CREATE TABLE training.transcript_archive` + GRANTs (versioniert, idempotent).
  `CREATE ROLE nerve_anon_worker LOGIN PASSWORD '<aus Secrets>'` als **separater
  dokumentierter psql-Runbook-Step** auf Production — Passwort NICHT in Migration/VCS
  (CLAUDE.md-Secrets-Regel). Rolle ist Cluster-global, nicht schema-gebunden → gehört nicht
  in eine DB-Schema-Migration.
- **D-02:** **Migrations-Nummer = `0008`** (letzte existierende ist `0007_add_score_fields`).
  ⚠️ **Folge:** D.UX.1s `transcript_segments`-Migration (im D.UX.1-CONTEXT als `0008`
  geplant, bevor diese Foundation davor eingeschoben wurde) muss auf **`0009`**
  umnummeriert werden. Downstream-Agents von D.UX.1 müssen das beachten.
- **D-03:** **`training.transcript_archive`** — empfohlenes Schema (finale Spaltenliste in
  Research/Plan + Cross-AI bestätigen):
  ```sql
  CREATE SCHEMA training;
  CREATE TABLE training.transcript_archive (
    id               BIGSERIAL PRIMARY KEY,
    source_call_hash TEXT       NOT NULL,    -- HMAC-SHA-256(call_id, secret) — KEIN FK zu crm/public
    segment_index    INTEGER    NOT NULL,    -- Reihenfolge innerhalb des Calls
    speaker          TEXT       NOT NULL CHECK (speaker IN ('berater','kunde','system')),
    text             TEXT       NOT NULL,    -- anonymisierter Text (Pipeline B)
    ts_offset_ms     INTEGER    NOT NULL,    -- per-Call kryptographisch randomisierter Offset
    schema_version   SMALLINT   NOT NULL DEFAULT 1,  -- ADR-Pflicht für JSONB/Evolution
    archived_at      TIMESTAMPTZ DEFAULT now()
  );
  ```
  KEINE Foreign Keys zu `public.*`/`crm.*` (ADR-Pflicht — Anonymitäts-Entkoppelung).
- **D-04:** **`ts_offset_ms` = per-Call kryptographischer Salt** (`secrets.randbelow`). Jeder
  Call eigener Random-Offset → kein ableitbares Muster, verhindert Re-Korrelation via
  `ts_ms + calls.started_at` (Gemini-Befund 2026-05-28). D.UX.1 setzt den Offset beim
  Background-Insert; D.UX.0 stellt nur die Spalte bereit.
- **D-05:** **`source_call_hash` = HMAC-SHA-256(call_id, secret_key)**, Key aus Secrets. Ohne
  Key keine Rückrechnung/Brute-Force der (ratbaren) `call_id`. Erlaubt Dedup/Idempotenz ohne
  FK. Verworfen: plain SHA-256 (brute-forcebar → Re-ID-Brücke), UUID (kein Dedup möglich).
- **D-06:** **GRANTs jetzt:** `training.*` ausschließlich an `nerve_anon_worker`
  (`USAGE` on schema + `INSERT/SELECT` on `training.transcript_archive`). App-Rolle bekommt
  KEIN Grant auf `training.*` (Default bei neuem Schema). `nerve_anon_worker` braucht
  zusätzlich **`SELECT` auf die relevanten `public.*`-Tabellen** (`conversation_logs`,
  `transcript_segments`, `calls`, `users`) — damit D.UX.1s Background-Job als diese Rolle
  lesen (public) + schreiben (training) kann. (Aktuell `public.*`, da crm.*-Umzug erst
  G/MEET Wave 1.)
- **D-07:** **App-Rollen-Isolation verifizieren (Punkt 21):** Via `inspect.sh` prüfen als
  welche DB-Rolle die App connectet. Falls Superuser/Owner → GRANT-Isolation greift NICHT →
  als Finding im Plan dokumentieren (ggf. App auf Nicht-Owner-Rolle umstellen). Volle
  `nerve_app`-Restriktion auf `public.*`-only ist eigentlich G/MEET-Wave-1-Scope — hier nur
  verifizieren + Finding, nicht erzwingen.

## Specific Ideas

- **Andre-Quote 2026-05-28 (Motivation):** „wenn wir das backup jetzt schon bauen dann werden
  ständig tests gespeichert in der cloud, dann müssen wir alles vor launch nochmal löschen."
  → Test-User-Pattern + Write-Time-Filter lösen das Timing-Dilemma (kein Cloud-Müll, kein
  Pre-Launch-Purge).
- **Existenz-Risiko-Framing:** Hetzner-Account-Kompromittierung würde Server + Server-lokales
  Backup gleichzeitig vernichten → Schicht 3 (IONOS, anderer Anbieter, WORM) ist die
  Versicherung gegen Total-Verlust der Trainings-Daten-Foundation.
- **Roadmap-Korrektur (C-03):** Die Roadmap-Filter-Skizze (`WHERE source_call_hash NOT IN
  SELECT ... FROM calls`) wird NICHT umgesetzt — sie hätte die ADR-FK-Entkoppelung verletzt.
  Ersetzt durch Write-Time-Filter im Background-Job (D.UX.1).
- **Compliance- statt Governance-Object-Lock:** bewusste Härte — Fehlkonfig kostet 30d
  Speicher, aber genau das ist der Ransomware-Schutz.
