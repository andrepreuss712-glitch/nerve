## Summary

Phase D.UX.0 legt vier Foundation-Schichten an die alle vor D.UX.1 stehen müssen: (A) Test-User-Pattern mit Email-Guard, (B) rsync-Push-Backup auf Hetzner Storage Box, (C) WORM-Backup auf IONOS S3 mit Object-Lock COMPLIANCE, (D) PostgreSQL-Schema `training.*` mit isolierter `nerve_anon_worker`-Rolle und Tabelle `training.transcript_archive`. Keine UI-Änderungen.

Die kritischste technische Entscheidung ist das IONOS S3-Bucket-Setup: Object-Lock COMPLIANCE kann **nur bei Bucket-Erstellung** aktiviert werden, nicht nachträglich. Versioning wird automatisch mitaktiviert. Ein nachträglich erstelltes Bucket ohne Object-Lock-Flag bedeutet Neuanlage. Endpoint URL: `https://s3.eu-central-1.ionoscloud.com` (user-owned, Region `de`).

Für die Alembic-Migration 0008: `CREATE SCHEMA training` und GRANTs müssen via `op.execute()` in SQL eingebettet werden, da Alembic sie nicht autogeneriert. Die `CREATE ROLE nerve_anon_worker`-Anweisung gehört als Runbook-Step außerhalb der Migration (Passwort nicht in VCS; Rolle ist cluster-global). Per-Segment-Row-Design (nicht JSONB-Aggregat) ist die empfohlene Lösung für `transcript_archive` — maximale Abfrageflexibilität für D.UX.1-Background-Job und Phase-E-DPO-Sammler.

**Primary recommendation:** Alle vier Komponenten sequenziell in Waves planen: Wave 0 (Migration 0008 + seed_test_user.py + Email-Guard), Wave 1 (Hetzner Storage Box Schicht 2), Wave 2 (IONOS S3 Schicht 3 + Bucket-Setup), Wave 3 (DSGVO-Doku).

### Pattern 1: Alembic Migration mit CREATE SCHEMA + GRANT (op.execute)

**What:** Alembic autogeneriert kein `CREATE SCHEMA` und keine GRANTs. Beides via `op.execute()` mit raw SQL.
**When to use:** Immer wenn neue PostgreSQL-Schemas oder Rollen-Grants in Alembic gemanagt werden müssen.

```python
# Source: Alembic Cookbook + GitHub gist h4/fc9b6d350544ff66491308b535762fee [VERIFIED: WebSearch]
from alembic import op
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import JSONB as _JSONB

revision = '0008'
down_revision = '0007'
branch_labels = None
depends_on = None

_JSON_TYPE = sa.JSON().with_variant(_JSONB(), 'postgresql')

def upgrade() -> None:
    # 1. Schema anlegen (idempotent)
    op.execute("CREATE SCHEMA IF NOT EXISTS training")

    # 2. Tabelle anlegen
    op.execute("""
        CREATE TABLE IF NOT EXISTS training.transcript_archive (
            id              BIGSERIAL PRIMARY KEY,
            source_call_hash TEXT      NOT NULL,
            segment_index   INTEGER   NOT NULL,
            speaker         TEXT      NOT NULL
                CHECK (speaker IN ('berater', 'kunde', 'system')),
            text            TEXT      NOT NULL,
            ts_offset_ms    INTEGER   NOT NULL,
            schema_version  SMALLINT  NOT NULL DEFAULT 1,
            archived_at     TIMESTAMPTZ DEFAULT now()
        )
    """)

    # 3. GRANTs für nerve_anon_worker
    # Hinweis: CREATE ROLE nerve_anon_worker ist NICHT hier — Runbook-Step wegen Passwort
    op.execute("GRANT USAGE ON SCHEMA training TO nerve_anon_worker")
    op.execute("GRANT INSERT, SELECT ON training.transcript_archive TO nerve_anon_worker")
    # SELECT auf public.* (für D.UX.1-Background-Job: lesen+schreiben)
    op.execute("GRANT SELECT ON public.calls TO nerve_anon_worker")
    op.execute("GRANT SELECT ON public.users TO nerve_anon_worker")
    op.execute("GRANT SELECT ON public.conversation_logs TO nerve_anon_worker")
    op.execute("GRANT SELECT ON public.transcript_segments TO nerve_anon_worker")

    # 4. users.is_test_user Spalte
    with op.batch_alter_table('users') as batch_op:
        batch_op.add_column(
            sa.Column('is_test_user', sa.Boolean(), nullable=False,
                      server_default='false')
        )

def downgrade() -> None:
    # users.is_test_user entfernen
    with op.batch_alter_table('users') as batch_op:
        batch_op.drop_column('is_test_user')
    # GRANTs revoken
    op.execute("REVOKE SELECT ON public.transcript_segments FROM nerve_anon_worker")
    op.execute("REVOKE SELECT ON public.conversation_logs FROM nerve_anon_worker")
    op.execute("REVOKE SELECT ON public.users FROM nerve_anon_worker")
    op.execute("REVOKE SELECT ON public.calls FROM nerve_anon_worker")
    op.execute("REVOKE INSERT, SELECT ON training.transcript_archive FROM nerve_anon_worker")
    op.execute("REVOKE USAGE ON SCHEMA training FROM nerve_anon_worker")
    op.execute("DROP TABLE IF EXISTS training.transcript_archive")
    op.execute("DROP SCHEMA IF EXISTS training")
```

**Kritische Reihenfolge:** `CREATE SCHEMA` muss vor `CREATE TABLE training.*` kommen. GRANTs nach Tabellen-Erstellung.

**Achtung — Alembic `env.py` Search-Path:** Das bestehende `env.py` konfiguriert keinen `search_path`. Da `training.*`-Tabellen nicht im `target_metadata` von SQLAlchemy Models sind, ist `include_schemas=True` hier NICHT nötig und würde Probleme verursachen (Alembic würde die training-Tabellen als "zu entfernen" erkennen bei Autogenerate). Die Migration bleibt rein manuell via `op.execute()`.

### Pattern 2: Email-Guard in `_send()`

**What:** Domain-Check auf `@nerve.local` vor Resend-API-Call.
**When to use:** Jedes Mal wenn `_send()` aufgerufen wird — schützt alle 6 Call-Sites.

```python
# Source: CONTEXT.md A-02 + bestehende email_service.py Struktur [VERIFIED: Codebase read]
def _send(payload):
    if not resend.api_key:
        print('[EMAIL] RESEND_API_KEY missing — skip send')
        return False
    # Test-User-Guard: @nerve.local ist nicht-routbare Domain
    recipients = payload.get('to', [])
    if any(r.endswith('@nerve.local') for r in recipients):
        print(f'[EMAIL] test-user recipient {recipients!r}, skip')
        return False
    try:
        resend.Emails.send(payload)
        return True
    except Exception as e:
        print(f'[EMAIL] send failed: {e}')
        return False
```

**Soundness-Analyse:** `@nerve.local` ist eine nicht-routbare Domain die IANA für lokale Netzwerke reserviert hat (`.local` ist für mDNS/Bonjour). Resend würde eine Delivery-Failure zurückgeben. Der Domain-Check greift VOR dem API-Call — kein Netzwerk-Overhead, kein Resend-Billing. Kein DB-Lookup nötig. [VERIFIED: CONTEXT.md A-02]

### Pattern 3: IONOS S3 Bucket-Erstellung mit Object-Lock

**What:** Bucket mit COMPLIANCE Object-Lock muss bei ERSTELLUNG aktiviert werden — nicht nachträglich.
**When to use:** Einmalig bei IONOS-Account-Setup (manueller Schritt via André).

```bash
# Source: IONOS Cloud Docs (docs.ionos.com) [VERIFIED: WebFetch]
# Endpoint für user-owned Bucket, Region de (Frankfurt):
export AWS_ACCESS_KEY_ID="<aus IONOS Console>"
export AWS_SECRET_ACCESS_KEY="<aus IONOS Console>"
IONOS_ENDPOINT="https://s3.eu-central-1.ionoscloud.com"

# Schritt 1: Bucket mit Object-Lock erstellen (Versioning wird auto-aktiviert)
aws s3 mb s3://nerve-training-backup \
    --object-lock-enabled-for-bucket \
    --region de \
    --endpoint-url "$IONOS_ENDPOINT"

# Schritt 2: Default-Retention auf 30 Tage COMPLIANCE setzen
aws s3api put-object-lock-configuration \
    --bucket nerve-training-backup \
    --object-lock-configuration '{
        "ObjectLockEnabled": "Enabled",
        "Rule": {
            "DefaultRetention": {
                "Mode": "COMPLIANCE",
                "Days": 30
            }
        }
    }' \
    --endpoint-url "$IONOS_ENDPOINT"

# Verification: Object-Lock-Konfiguration prüfen
aws s3api get-object-lock-configuration \
    --bucket nerve-training-backup \
    --endpoint-url "$IONOS_ENDPOINT"

# Encryption-at-rest: IONOS S3 aktiviert SSE-S3 (AES256) standardmäßig im Web-Interface.
# Via CLI verifizieren:
aws s3api get-bucket-encryption \
    --bucket nerve-training-backup \
    --endpoint-url "$IONOS_ENDPOINT"
```

### Pattern 4: Object-Upload mit per-Objekt COMPLIANCE Retention

**What:** Beim Upload eines Dump-Files wird die Retention-Date per Objekt gesetzt (überschreibt / ergänzt den Bucket-Default).
**When to use:** In `backup_training_to_s3.sh` bei jedem Upload.

```bash
# Source: IONOS Cloud Docs awscli-object-lock [VERIFIED: WebFetch]
RETAIN_UNTIL=$(date -u -d '+30 days' +%Y-%m-%dT%H:%M:%SZ)
TIMESTAMP=$(date +%Y-%m-%d_%H%M%S)
BACKUP_KEY="training-${TIMESTAMP}.sql.gz"
IONOS_ENDPOINT="https://s3.eu-central-1.ionoscloud.com"
BUCKET="nerve-training-backup"

# Upload mit expliziter per-Objekt Retention (Dual-Guard: Bucket-Default + per-Object)
aws s3api put-object \
    --bucket "$BUCKET" \
    --key "$BACKUP_KEY" \
    --body "/tmp/$BACKUP_KEY" \
    --object-lock-mode COMPLIANCE \
    --object-lock-retain-until-date "$RETAIN_UNTIL" \
    --endpoint-url "$IONOS_ENDPOINT"
```

**Wichtig:** `aws s3 cp` unterstützt kein `--object-lock-*`. Zwingend `aws s3api put-object` verwenden für Object-Lock-Attribute. [CITED: docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html]

### Pattern 5: Hetzner Storage Box rsync Push

**What:** Backup-Datei vom Server auf die Storage Box pushen via rsync über SSH Port 23.
**When to use:** In `backup_postgres.sh` nach erfolgreichem lokalem Dump + Size-Check.

```bash
# Source: Hetzner Docs docs.hetzner.com/storage/storage-box/ [VERIFIED: WebFetch]
BOX_USER="uXXXXX"   # Konstante oben im Skript (nach Bestellung befüllen)
BOX_HOST="${BOX_USER}.your-storagebox.de"
BOX_PATH="/backups/nerve"
BOX_KEY="/root/.ssh/id_storagebox"

# Push via rsync über Port 23
rsync \
    --archive \
    --compress \
    --progress \
    -e "ssh -p23 -i ${BOX_KEY} -o StrictHostKeyChecking=no -o BatchMode=yes" \
    "$BACKUP_FILE" \
    "${BOX_USER}@${BOX_HOST}:${BOX_PATH}/"

# 90-Tage-Rotation: remote Listings via SSH (Port 23 unterstützt ls + find-ähnliche Ops)
# WICHTIG: Storage Box hat KEINE volle Shell. Scripts können nicht auf Box ausgeführt werden.
# Rotation muss script-side implementiert werden via SSH-Einzelbefehle:
# Methode: ls -lt remote → filter nach Alter → SSH rm für alte Dateien
# Oder: rsync mit --delete gegen ein gefiltertes lokales Set (komplex)
# Empfehlung: SSH-Befehl "find" ist auf Storage Box NICHT verfügbar.
# Praktische Lösung: Datei-Listing via SSH, Parsing script-side:
ssh -p23 -i "${BOX_KEY}" "${BOX_USER}@${BOX_HOST}" ls -la "${BOX_PATH}/" \
    | awk '{print $9}' | sort \
    | head -n -90  # Behalte neueste 90; ältere löschen
# Dann für jede zu löschende Datei:
# ssh -p23 -i "${BOX_KEY}" "${BOX_USER}@${BOX_HOST}" rm "${BOX_PATH}/<datei>"
```

**Hinweis zur Rotation:** Da keine Shell auf der Box läuft und `find -mtime` remote nicht ausführbar ist, wird die 90-Tage-Logik über Datei-Listing + script-seitige Berechnung des Alters via Dateinamen-Timestamp (Format `nerve-YYYY-MM-DD_HHMMSS.sql.gz`) implementiert. Das ist robuster als mtime-basiertes remote-find. [VERIFIED: Hetzner Docs]

### Anti-Patterns to Avoid

- **Object-Lock nachträglich aktivieren:** IONOS S3 unterstützt das nicht. Wenn Bucket ohne `--object-lock-enabled-for-bucket` erstellt, muss er neu angelegt werden. [VERIFIED: IONOS Docs]
- **Versioning manuell aktivieren:** Nicht nötig — Object-Lock aktiviert Versioning automatisch. Manueller Versioning-Befehl vor Object-Lock ist überflüssig. [VERIFIED: IONOS Docs / WebSearch]
- **`aws s3 cp` für Object-Lock-Uploads:** Unterstützt keine `--object-lock-*`-Flags; muss `aws s3api put-object` sein. [CITED: AWS CLI Docs]
- **GRANTs in Runbook statt Migration:** GRANTs gehören in die Migration (versioniert, reproduzierbar). Nur `CREATE ROLE` mit Passwort gehört als Runbook-Step außerhalb. [VERIFIED: CONTEXT.md D-01]
- **`CREATE ROLE` ohne `IF NOT EXISTS`:** Läuft der Runbook-Step zweimal, gibt es einen Fehler. Besser: `CREATE ROLE IF NOT EXISTS nerve_anon_worker; ALTER ROLE nerve_anon_worker WITH LOGIN PASSWORD '...'`
- **rsync --delete für Rotation:** Würde alle nicht-gematchten Dateien auf der Box löschen. Falsch für zeitgesteuerte Rotation; korrekt ist dateinamenbasiertes Filtern. [VERIFIED: Hetzner Docs research]
- **Schema `training` in SQLAlchemy `target_metadata` registrieren:** Würde Alembic autogenerate dazu bringen, `training.*`-Tabellen als "zu migrieren" zu erkennen und gegenzuschreiben. Training-Modelle sollen NICHT in models.py registriert sein (ADR: Trennung). [ASSUMED — basierend auf Alembic-Autogenerate-Verhalten]
- **Email-Guard via globalen ENV-Schalter:** Würde echte Production-User-Mails blockieren. Domain-Check ist selektiver. [VERIFIED: CONTEXT.md A-02]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| S3-Object-Lock-Upload | Eigene HTTP-Requests gegen S3-API | `aws s3api put-object` | S3-Signierung (SigV4) ist komplex; aws-cli übernimmt Auth, Multipart, Retry |
| PostgreSQL-GRANT-Isolation | App-Layer-Zugriffscheck | Native DB-GRANTs + role isolation | DB erzwingt es at-the-wire; App-Layer-Check kann umgangen werden |
| Backup-Rotation | Cron-Skript mit komplexem Datum-Parsing | Dateinamen-Timestamp-Parsing (YYYY-MM-DD im Namen) | Bereits durch `backup_postgres.sh`-Namensschema etabliert; datetime-Parsing in Bash via `date -d` |
| Idempotenter DB-Seed | Prüf-IF-Exist + INSERT-Logik | `ON CONFLICT DO NOTHING` | PostgreSQL UPSERT ist atomar, kein Race-Condition-Risiko |
| HMAC-SHA-256 | Custom Hash-Funktion | Python `hmac.new(key, msg, hashlib.sha256)` | stdlib, kein extra Dependency — aber erst in D.UX.1 gebraucht |

**Key insight:** Object-Lock COMPLIANCE ist eine sehr enge S3-API-Integration — rclone und s3cmd haben sie nicht vollständig implementiert. aws-cli ist hier die einzige sichere Wahl.

## Common Pitfalls

### Pitfall 1: IONOS S3 Object-Lock nur bei Bucket-Erstellung aktivierbar

**What goes wrong:** Bucket wird ohne `--object-lock-enabled-for-bucket` erstellt. Später stellt man fest, dass Object-Lock nicht nachträglich aktiviert werden kann. Bucket muss gelöscht und neu angelegt werden.
**Why it happens:** AWS-Dokumentation sagt das auch — es ist ein S3-Standard-Constraint, keine IONOS-Besonderheit.
**How to avoid:** `--object-lock-enabled-for-bucket` immer beim `aws s3 mb` oder `aws s3api create-bucket`. IONOS-Docs bestätigen das für user-owned Buckets.
**Warning signs:** `get-object-lock-configuration` gibt `ObjectLockEnabled: Disabled` zurück.

[VERIFIED: IONOS Cloud Docs, WebSearch multiple sources]

### Pitfall 2: `aws s3 cp` vs `aws s3api put-object` für Object-Lock

**What goes wrong:** `aws s3 cp` kennt keine `--object-lock-mode`- oder `--object-lock-retain-until-date`-Flags. Wird es trotzdem benutzt, werden Objekte ohne per-Objekt-Retention hochgeladen (nur Bucket-Default greift wenn konfiguriert).
**Why it happens:** `aws s3 cp` ist der verbreitete Upload-Befehl; die Object-Lock-Flags existieren nur auf `s3api put-object`.
**How to avoid:** Für alle Uploads in `backup_training_to_s3.sh` zwingend `aws s3api put-object --body <file>` verwenden.
**Warning signs:** Upload schlägt nicht fehl, aber `s3api get-object` zeigt kein `ObjectLockMode` Feld.

[CITED: docs.aws.amazon.com/cli/latest/reference/s3api/put-object.html]

### Pitfall 3: nerve_anon_worker-Passwort in Migration / VCS

**What goes wrong:** `CREATE ROLE nerve_anon_worker PASSWORD 'hardcoded'` in einer Alembic-Migrationsdatei, die in git eingecheckt ist.
**Why it happens:** Bequemlichkeit — alles in der Migration zu haben scheint einfacher.
**How to avoid:** `CREATE ROLE` ist ein manueller Runbook-Step. Passwort wird live generiert und nur in `/etc/nerve/ionos-s3.env` oder als Env-Variable gespeichert.
**Warning signs:** `git log --all --full-history -- alembic/versions/0008*` zeigt Passwort-String in Diff.

[VERIFIED: CLAUDE.md Secrets-Regel + CONTEXT.md D-01]

### Pitfall 4: Alembic autogenerate erkennt training.* als "fehlende" Tabellen

**What goes wrong:** Wenn `alembic revision --autogenerate` nach Migration 0008 ausgeführt wird, und `training.transcript_archive` ist nicht in SQLAlchemy `Base.metadata` registriert, ignoriert Alembic sie korrekt. ABER wenn jemand die Tabelle fälschlicherweise in `models.py` registriert (mit `schema='training'`), wird Alembic bei zukünftigen autogenerate-Runs versuchen, sie zu verwalten.
**Why it happens:** Verwechslung zwischen "Tabelle existiert" und "Tabelle soll von ORM verwaltet werden".
**How to avoid:** `training.transcript_archive` NICHT in `database/models.py` einführen. Sie gehört zum `training`-Schema das vom `nerve_anon_worker` owned wird. [ASSUMED: basierend auf Alembic-Autogenerate-Verhalten und ADR-Trennung]
**Warning signs:** `alembic revision --autogenerate` generiert ein leeres oder DROP-TABLE-Migration für training-Tabellen.

### Pitfall 5: Hetzner Storage Box — Kein Shell-Scripting auf Box-Seite

**What goes wrong:** Rotation-Logik die `find -mtime +90 -delete` remote ausführen will. Storage Box hat keine volle Shell; `find` ist nicht verfügbar.
**Why it happens:** Server-Admins erwarten eine normale SSH-Shell.
**How to avoid:** Alle Rotation-Logik script-side implementieren. Dateinamen enthalten Timestamp → Alter aus Dateiname berechnen → remote `rm` via SSH-Einzelbefehl.
**Warning signs:** `ssh -p23 uXXXXX@...your-storagebox.de find /backups -mtime +90` gibt Fehler zurück.

[VERIFIED: Hetzner Docs — "It is not possible to run rsync on a Storage Box itself"; no full shell]

### Pitfall 6: inspect.sh `schema`-Befehl unterstützt keinen Schema-Prefix

**What goes wrong:** `inspect.sh schema transcript_archive` schlägt fehl oder zeigt nichts — `\d transcript_archive` sucht im Default search_path (public), nicht in `training`.
**Why it happens:** `inspect.sh` nutzt `\d $2` ohne Schema-Qualifier.
**How to avoid:** Direkt via psql mit Schema-Qualifier verifizieren: `sudo -u nerve_app psql -d nerve -c "\d training.transcript_archive"`. Alternativ inspect.sh um schema-Argument erweitern — aber das ist eine inspect.sh-Erweiterung die im Plan dokumentiert werden muss.
**Warning signs:** `inspect.sh schema transcript_archive` gibt "Did not find any relation named transcript_archive."

[VERIFIED: Codebase read inspect.sh + PostgreSQL search_path-Verhalten]

### Pitfall 7: GRANTs auf public.* Tabellen — Reihenfolge + IF EXISTS

**What goes wrong:** `GRANT SELECT ON public.transcript_segments TO nerve_anon_worker` in Migration 0008 schlägt fehl wenn `transcript_segments`-Tabelle noch nicht existiert (sie wird erst in 0009/D.UX.1 angelegt).
**Why it happens:** GRANT auf nicht-existierende Tabelle = PostgreSQL-Fehler.
**How to avoid:** Für `transcript_segments` den GRANT entweder (a) in Migration 0009 verschieben, oder (b) nur auf existierende public.*-Tabellen (calls, users, conversation_logs) in 0008 GRANT setzen. Option (b) = safer, Option (a) = logisch korrekter Reihenfolge.
**Warning signs:** `alembic upgrade head` bricht bei GRANT-Statement mit "relation does not exist" ab.

[VERIFIED: PostgreSQL GRANT Semantik + CONTEXT.md D-06 + Alembic-Versionsreihenfolge]

**Empfehlung:** In Migration 0008 nur auf die Tabellen GRANT setzen die definitiv schon existieren: `calls`, `users`, `conversation_logs`. Das GRANT auf `transcript_segments` kommt in Migration 0009 (D.UX.1).

### transcript_archive — Finale Spaltenempfehlung (per-Segment-Row)

Die per-Segment-Row-Variante ist empfohlen gegenüber per-Call-JSONB weil:
1. Phase-E-DPO-Sammler braucht `WHERE speaker = 'berater'` und `segment_index BETWEEN` — keine JSON-Extraktion
2. D.UX.1-Background-Job insertet Segmente einzeln im Streaming-Modus
3. Schema-Versionierung via `schema_version`-Spalte ist bei Row-Format trivialer als bei JSONB-Array

```sql
-- Source: CONTEXT.md D-03 + Research-Empfehlung [VERIFIED: CONTEXT.md]
CREATE SCHEMA IF NOT EXISTS training;

CREATE TABLE IF NOT EXISTS training.transcript_archive (
    id               BIGSERIAL   PRIMARY KEY,
    source_call_hash TEXT        NOT NULL,
        -- HMAC-SHA-256(call_id, NERVE_TRAINING_HASH_KEY)
        -- Kein FK zu public.calls — ADR-Pflicht (Re-ID-Schutz)
    segment_index    INTEGER     NOT NULL,
        -- 0-basiert, Reihenfolge innerhalb des Calls
    speaker          TEXT        NOT NULL
        CHECK (speaker IN ('berater', 'kunde', 'system')),
    text             TEXT        NOT NULL,
        -- Anonymisierter Segment-Text (Pipeline B, implementiert in D.UX.1)
    ts_offset_ms     INTEGER     NOT NULL,
        -- Per-Call kryptographischer Salt (secrets.randbelow, gesetzt in D.UX.1)
        -- Verhindert Re-Korrelation via ts_ms + calls.started_at
    schema_version   SMALLINT    NOT NULL DEFAULT 1,
        -- ADR-Pflicht für Forward-Compatible-Evolution
    archived_at      TIMESTAMPTZ DEFAULT now()
);

-- Kein Index in dieser Phase (D.UX.1 entscheidet nach erstem Insert-Pattern)
```

### backup_training_to_s3.sh Skelett

```bash
#!/bin/bash
# scripts/backup_training_to_s3.sh — NERVE Training Schema Backup (Schicht 3)
# Runs via systemd nerve-backup-training.timer
# User: root (lädt ionos-s3.env, verbindet als nerve_anon_worker)
set -euo pipefail

SECRETS_FILE="/etc/nerve/ionos-s3.env"
if [ ! -f "$SECRETS_FILE" ]; then
    echo "[BACKUP-S3] FEHLER: $SECRETS_FILE nicht gefunden" >&2
    exit 1
fi
source "$SECRETS_FILE"

TIMESTAMP=$(date +%Y-%m-%d_%H%M%S)
BACKUP_KEY="training-${TIMESTAMP}.sql.gz"
TMP_FILE="/tmp/${BACKUP_KEY}"
MIN_SIZE_BYTES=512  # training-Schema kann anfangs leer sein — niedrigere Schwelle

echo "[BACKUP-S3] Start: $TIMESTAMP"

# pg_dump als nerve_anon_worker (hat SELECT auf training.*)
PGPASSWORD="$NERVE_ANON_WORKER_DB_PASSWORD" \
    pg_dump -U nerve_anon_worker -d nerve \
    --schema=training --no-owner --no-acl \
    | gzip > "$TMP_FILE"

ACTUAL_SIZE=$(stat -c%s "$TMP_FILE" 2>/dev/null || echo 0)
if [ "$ACTUAL_SIZE" -lt "$MIN_SIZE_BYTES" ]; then
    echo "[BACKUP-S3] FEHLER: Dump zu klein ($ACTUAL_SIZE bytes)" >&2
    rm -f "$TMP_FILE"
    exit 1
fi

# Retain-Until: jetzt + 30 Tage (UTC)
RETAIN_UNTIL=$(date -u -d '+30 days' +%Y-%m-%dT%H:%M:%SZ)

# Upload mit Object-Lock COMPLIANCE
aws s3api put-object \
    --bucket "$IONOS_S3_BUCKET" \
    --key "$BACKUP_KEY" \
    --body "$TMP_FILE" \
    --object-lock-mode COMPLIANCE \
    --object-lock-retain-until-date "$RETAIN_UNTIL" \
    --endpoint-url "$IONOS_S3_ENDPOINT"

echo "[BACKUP-S3] OK: s3://$IONOS_S3_BUCKET/$BACKUP_KEY"
rm -f "$TMP_FILE"

# 365-Tage-Rotation: Objekte nach Ablauf der WORM-Retention löschen
# (Ablauf-Datum schon vorbei → delete-object ist erlaubt)
# Implementierung in separatem Timer oder als nächster Block

echo "[BACKUP-S3] Abgeschlossen: $(date)"
```
