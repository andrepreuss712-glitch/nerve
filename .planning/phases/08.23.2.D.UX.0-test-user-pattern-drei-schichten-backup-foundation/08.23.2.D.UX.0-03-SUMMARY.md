# Phase 08.23.2.D.UX.0 Plan 03: Backup-Schicht 3 IONOS S3 WORM — Summary

**One-liner:** WORM-Backup des training-Schemas auf IONOS S3 (eu-central-4, COMPLIANCE 30d, aws-cli v2, SSE AES256, staged bring-up) mit systemd-Timer, monatlichem Restore-Test und `/api/health`-Metrik `backup_s3_restore_ok`.

---

## Was wurde gebaut

Backup-Schicht 3 der Drei-Schichten-Backup-Strategie (C-01 bis C-09) ist vollstaendig auf Production in Betrieb:

**scripts/backup_training_to_s3.sh** — woechentlicher systemd-Timer, dumpt training-Schema als nerve_anon_worker ueber TCP (`-h 127.0.0.1`, G-2), laedt per `aws s3api put-object --object-lock-mode COMPLIANCE +30d` auf IONOS S3 hoch (Pitfall 2: kein `aws s3 cp`). 365d-Rotation mit grep-Guard (G-3). Write-Time-Filter-Contract dokumentiert als Kommentar (C-03: voller Dump, kein WHERE).

**scripts/restore_test_s3.sh** — monatlicher systemd-Timer, zieht neuestes training-*.sql.gz, prueft Integritaet (`gunzip -t`), schreibt `/opt/nerve/.s3_restore_status` (key=value, analog .deploy_meta). grep-Guard G-3.

**4 systemd-Units** (deploy/): `nerve-backup-training.service/.timer` (weekly Sun 02:00) + `nerve-restore-test.service/.timer` (monthly). User=root, EnvironmentFile=/etc/nerve/ionos-s3.env.

**routes/app_routes.py** — api_health() liest /opt/nerve/.s3_restore_status und gibt `backup_s3_restore_ok` (bool|null) + `backup_s3_restore_checked_at` (ISO-8601|null) zurueck.

**alembic/versions/0009_grant_anon_worker_training_sequences.py** — GRANT USAGE,SELECT ON ALL SEQUENCES IN SCHEMA training + ALTER DEFAULT PRIVILEGES (Deviation-Fix, siehe unten).

## Deviations vom Plan

### Auto-fix Issues

**1. [Rule 1 — Korrektur] Endpoint/Region eu-central-1/de → eu-central-4/eu-central-4**

- **Gefunden bei:** Task 1 Provisioning (IONOS-Endpoint-Verifikation)
- **Problem:** Plan-Vorlage (RESEARCH.md C-WARN-2, Stand Pre-Provisioning) hatte eu-central-1 + Region "de" fuer user-owned Buckets. Tatsaechlicher Frankfurt-Endpoint fuer contract-owned Buckets ist https://s3.eu-central-4.ionoscloud.com, Region eu-central-4.
- **Fix:** ionos-s3.env mit korrektem Paar geschrieben; backup_training_to_s3.sh + restore_test_s3.sh bereits korrekt via IONOS_S3_ENDPOINT/IONOS_S3_REGION parametrisiert (keine Hardcodierung) → kein Code-Change noetig. Korrekte Region auch als AWS_DEFAULT_REGION exportiert (SigV4).
- **Commits:** 8edfcb9 (AWS_DEFAULT_REGION-Fix), d3bcd1a (STATE.md-Notiz)

**2. [Rule 2 — Sequenz-Grant-Luecke 0008] Migration 0009 hinzugefuegt**

- **Gefunden bei:** Erstem echten Backup-Lauf (nerve_anon_worker: "permission denied for sequence transcript_archive_id_seq")
- **Problem:** Migration 0008 (Plan 01) hatte INSERT/SELECT auf training.transcript_archive gegraentet, aber die zugehoerige Identity-Sequence nicht. pg_dump liest Sequence-Werte fuer alle Tabellen im Schema → Permission Denied → Backup fehlgeschlagen.
- **Fix:** Migration 0009 (`GRANT USAGE,SELECT ON ALL SEQUENCES IN SCHEMA training TO nerve_anon_worker` + `ALTER DEFAULT PRIVILEGES` fuer kuenftige Sequences). Appliziert als postgres-User (nerve_app hat kein GRANT-Recht auf postgres-owned training-Objekte — identisches Pattern wie Plan 01 Migration-Deployment-Workaround).
- **Dateien:** alembic/versions/0009_grant_anon_worker_training_sequences.py
- **Commit:** 55bfae3
- **Downstream-Hinweis:** D.UX.1-Migration muss von 0008 auf 0010 nummerieren (0009 jetzt belegt).

**3. [User-approved — hotfix] app_routes.py via surgical scp deployed (kein deploy.sh)**

- **Kontext:** deploy.sh staging-gate blockiert durch pre-existing test_ft_seed failure (bekanntes Problem, alle vorherigen Phasen). Statt Staging-Gate zu fixen (eigene Mini-Phase geplant fuer Pre-Launch) wurde app_routes.py direkt via `scp` auf Production kopiert + `systemctl restart nerve`.
- **Begruendung:** Explizit user-approved Pattern "Pre-Launch direkt auf Production" (CLAUDE.md HART-Regel 2026-05-27). Kein Datenverlust-Risiko (rein additives JSON-Feld in /api/health).
