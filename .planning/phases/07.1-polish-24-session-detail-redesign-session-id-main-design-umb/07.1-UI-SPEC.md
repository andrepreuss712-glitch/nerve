## Typ-Diskriminierendes Rendering (NEU Revision 3)

**Architektur-Fakt:** `ConversationLog.typ = 'live' | 'training'` — beide Session-Typen teilen eine Tabelle und landen heute auf `/session/<id>`. Training-Sessions werden im aktuellen Design falsch als Cold-Call-Sessions gerendert. Revision 3 behebt das.

Das Template kennt drei Varianten:

### Variante A: `typ='live', session_mode='cold_call'`

Wie in Revision 2 beschrieben. Alle 11 Sektionen wie gespect. Standard-Rendering-Pfad.

### Variante B: `typ='live', session_mode='meeting'`

Fast identisch zu Variante A. Sektion 1 zeigt `Meeting`-Badge statt `Cold Call`. Sektion 10 (Gesprächs-Analyse) koennte nach Phase 4.19 Meeting-Transkripte mit beiden Sprechern zeigen — bis dahin identisch zu Cold Call rendern.

### Variante C: `typ='training'`

Abweichendes Layout in mehreren Sektionen:

**Sektion 1 (Header):**
- Kein Modus-Badge `Cold Call` / `Meeting`
- Stattdessen drei Badges nebeneinander: `Training` + `{pt_name}` (Persoenlichkeitstyp) + `{schwierigkeit_label}` (Einsteiger/Fortgeschritten/Experte)
- Container-Klasse: `.n-session-detail-header--training` (ergaenzt `.n-session-detail-header`)
- Meta-Row: Datum + Dauer bleiben, `Result`-Feld zeigt Sterne-Rating statt kb_end-Wert

**Sektion 2 (Score-Hero):**
- Score-Aufbau identisch (grosse Zahl, Breakdown, Trend-Badge)
- Breakdown-Komponenten Training-spezifisch (4 Zeilen, gleiche Gewichtung ~40/30/20/10):
  - `Sterne-Rating` 40% (aus `conv.sterne_rating`, 1-5 Sterne → normalisiert auf 0-100)
  - `Einwände behandelt` 30% (identisch zu Live — Einwands-Behandlungs-Rate)
  - `Stimmung Ende` 20% (aus `stimmung_history` letzter Wert, -5…+5 → normalisiert 0-100)
  - `Skript-Abdeckung` 10% (meist 0 bei Training — Empty-State-Wert)
- Mini-Bars und Label-Styling unveraendert

**Sektion 3 (Chart):**
- Zeigt Stimmungs-Verlauf statt Kaufbereitschafts-Verlauf
- Y-Achse: -5 bis +5 (stimmung_history-Werte), ODER 0-100 wenn stimmung als normalisierter Wert vorliegt
- Datenquelle: `conv.stimmung_history` (JSON-Array, analog zu `kb_verlauf`)
- Chart-Typ bleibt `line`, Farbe bleibt Teal `#00D4AA`, Fill bleibt
- Canvas-ID: `sd-stimmung-chart` (ASCII)
- Headline: `Stimmungs-Verlauf`
- Empty-State: eigene Training-spezifische Copy (siehe Copywriting-Table oben)

**Sektion 5 (Phasen-Strip):**
- Identisch zu Live — Phasen existieren in Training genauso (Opener → Discovery → Argument → Close)
- Keine Aenderung noetig

**Sektion 6 (Skript-Abdeckung):**
- Training hat in der Regel kein Skript → Empty-State mit Training-spezifischer Copy
- Jinja-Condition: `{% if conv.typ == 'training' %}` → zeige `.n-session-detail-empty` mit Training-Skript-Copy statt Progress-Bar

**Sektionen 4, 7, 8, 9, 10, 11:** Unveraendert — identisches Rendering fuer beide `typ`-Werte.

**Jinja-Template-Strategie:** Einfaches `{% if conv.typ == 'training' %}` an den betroffenen Stellen. Kein Sub-Template, keine Vererbungshierarchie — die Unterschiede sind zu klein fuer Complexity-Overhead.

## Layout & Komponenten-Inventar

### Page-Struktur (vertikal, Mobile-first — 11 Sektionen)

```
.n-page
  .n-session-detail-header [.n-session-detail-header--training wenn typ='training']
                             ← Section 1: Zurueck-Link + Title + Meta-Row (Typ-diskriminierend)
  .n-session-detail-hero     ← Section 2: Score + Breakdown (typ-diskriminierend) + Trend-Badge
  .n-session-detail-card     ← Section 3: Chart (kb_verlauf ODER stimmung_history, typ-diskriminierend)
  .n-session-detail-card     ← Section 4: Einwand-Timeline
  .n-session-detail-card     ← Section 5: Phasen-Visualisierung (identisch fuer beide typen)
  .n-session-detail-card     ← Section 6: Skript-Abdeckung (Training: immer Empty-State)
  .n-session-detail-card     ← Section 9: "Was du üben solltest" (AKTIV, typ-aware Helper)
    .n-session-detail-recommendation-list
      .n-session-detail-recommendation (max 3 Cards, je mit left-Border 3px teal)
        .n-session-detail-recommendation-cross-context (NEU R3 — zwischen Explanation und CTA)
  .n-session-detail-card     ← Section 7: Painpoints-Liste
  .n-session-detail-card     ← Section 8: PreCall-Briefing (collapsible)
```

## Cross-Context-Badge Spezifikation (NEU Revision 3)

### Zweck

Jede Recommendation-Card in Sektion 9 zeigt einen kleinen Badge zwischen Explanation und CTA, der anzeigt ob der User das Problem schon im jeweils anderen Kontext (Training ↔ Live) geubt/erlebt hat.

### Badge fuer Live-Sessions (`typ='live'`)

Wenn `training_focus` ein `objections:`-Prefix hat, queried der Helper:

```sql
-- Vereinfachte Darstellung — exakte Implementierung im Plan
SELECT COUNT(*) as n, AVG(sterne) as avg_sterne
FROM conversation_logs cl
JOIN objection_events oe ON oe.conv_id = cl.id
WHERE cl.user_id = ?
AND cl.typ = 'training'
AND cl.created_at > NOW() - INTERVAL '14 days'
AND oe.einwand_typ = ?
```

Ergebnis → `cross_context`:
- `{'sessions': 3, 'avg_sterne': 4.2, 'focus_match': 'kein_bedarf'}` → Badge-Text `Zuletzt im Training: Ø 4.2★ aus 3 Sessions`, Modifier `--success` (≥3 + avg≥4)
- `{'sessions': 1, 'avg_sterne': 2.1, ...}` → Badge-Text `Zuletzt im Training: Ø 2.1★ aus 1 Sessions`, kein Modifier (neutral)
- `{'sessions': 0}` → Badge-Text `Noch nie im Training geübt`, Modifier `--danger`

### Badge fuer Training-Sessions (`typ='training'`)

Spiegel-Funktion — queried gegen `typ='live'`-Sessions:

```sql
-- Vereinfachte Darstellung
SELECT COUNT(*) as n_total,
       SUM(CASE WHEN oe.success THEN 1 ELSE 0 END) as n_success
FROM conversation_logs cl
JOIN objection_events oe ON oe.conv_id = cl.id
WHERE cl.user_id = ?
AND cl.typ = 'live'
AND cl.created_at > NOW() - INTERVAL '14 days'
AND oe.einwand_typ = ?
```

Ergebnis → `cross_context`:
- `{'sessions': 2, 'n_success': 0, ...}` → Badge-Text `Im echten Call: 2× versucht, 0× behandelt`, Modifier `--danger`
- `{'sessions': 2, 'n_success': 2, ...}` → Badge-Text `Im echten Call: 2× versucht, 2× behandelt`, Modifier `--success`
- `{'sessions': 0}` → Badge-Text `Noch nie im echten Call begegnet`, kein Modifier (neutral — unbekannt, nicht alarmierend)

### Kein Cross-Context (wenn `cross_context=None`)

- Kein Badge rendern — Element einfach weglassen
- CTA rueckt direkt unter Explanation

### Architektur-Grenze

Diese SQL-Queries greifen nur auf bestehende Tabellen zu: `conversation_logs` + `objection_events`. Keine neue Tabelle, kein Event-Stream, kein Muster-Erkenner. Die Abfrage ist einfach und kostet <1ms pro Recommendation. Max 3 Queries pro Page-Load.
