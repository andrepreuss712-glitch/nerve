**KRITISCH für UI-SPEC Rev 3 Variante C (Training Score-Hero):**

Die UI-SPEC Rev 3 annimmt, dass Training-Sessions einen `sterne_rating` haben. **Das stimmt so
nicht.** Die Realität:

1. Training generiert bei Call-Ende ein `scoring`-Dict mit `gesamt_score` (0-100, siehe

2. Training schreibt `gesamt_score` in **`conv.kb_end`**, nicht in `conv.sterne` —
   `routes/training.py:701`:
   ```python

   ```
3. Training sucht `wendepunkt_saetze` (wie viele Einwände behandelt) — wird in
   `einwaende_gesamt`/`einwaende_behandelt` persistiert (line 702-703)
4. `conv.sterne` für Training-Sessions ist **immer NULL** aktuell (außer ein User bewertet die
   Training-Session über ein anderes Endpoint — tut er nicht)

### Range + Normalisierungs-Formeln

**Range:** `sterne` ist 1-5 (Integer), NULL wenn unbewertet.

**Normalisierung 1-5 → 0-100:** `(sterne * 20)` — z.B. `3 ★ → 60`, `4 ★ → 80`, `5 ★ → 100`.

**ABER:** für Training ist `sterne` NULL. Deshalb muss die UI-SPEC Rev 3 Breakdown-Formel
**umgeschrieben** werden für Training:

### Spec-Korrektur Training Score-Breakdown

UI-SPEC Rev 3 Zeile 228-232 (Training Score-Hero) — wie angegeben **nicht lauffähig**. Korrektur:

| Komponente | UI-SPEC Rev 3 Annahme | Realität | Empfehlung Planner |
|------------|------------------------|----------|--------------------|
| Sterne-Rating 40% | `conv.sterne_rating * 20` | `conv.sterne` ist NULL für Training | **Ersetze durch `scoring.gesamt_score` aus `conv.kb_end`** — Training schreibt das dort hin |
| Einwände behandelt 30% | wie Live | `wendepunkt_saetze`-Pattern → `conv.einwaende_behandelt / conv.einwaende_gesamt` | OK wie in UI-SPEC |
| Stimmung Ende 20% | `stimmung_history[-1].wert → 0-100` | Range -5..+5 | Formel: `((wert + 5) / 10) * 100` — z.B. `-5 → 0`, `0 → 50`, `+5 → 100` |
| Skript-Abdeckung 10% | meist 0 | `conv.skript_abdeckung` ist NULL bei Training | OK — Empty-State |

**Normalisierungs-Formel Stimmung:**
```python

stimmung_normalized = round(((last_wert + 5) / 10) * 100)  # 0..100
```

**Empfehlung — pragmatischer Training Score-Aggregate:**

Training hat bereits einen `gesamt_score` (0-100) von Claude. Den einfach als Headline-Score
anzeigen, Mini-Bars für die vier Komponenten zusätzlich — jede Komponente auf 0-100 normalisiert.
Die Gewichtung ist rein visuell (Label "40% / 30% / 20% / 10%"), das ist UI-Decoration.

Oder: `_calc_training_score(conv)` Helper neu definieren parallel zu `_calc_call_score`:

```python
def _calc_training_score(conv, stimmung_history):
    """Training-Variante: spiegelt _calc_call_score, aber auf Training-Felder."""
    # Sterne-Komponente: Training nutzt gesamt_score, nicht conv.sterne (das ist NULL)
    score_comp = conv.kb_end or 0  # 0-100 (Claude's gesamt_score)
    einw_total = conv.einwaende_gesamt or 0
    einw_ok = conv.einwaende_behandelt or 0
    behandelt_rate = (einw_ok / einw_total * 100) if einw_total > 0 else 50
    # Stimmung-Komponente: letzter Wert normalisiert
    if stimmung_history:
        last_wert = stimmung_history[-1].get('wert', 0)
        stimmung_norm = round(((last_wert + 5) / 10) * 100)
    else:
        stimmung_norm = 50
    skript = conv.skript_abdeckung or 0
    return min(100, max(0, round(
        score_comp * 0.4 + behandelt_rate * 0.3 + stimmung_norm * 0.2 + skript * 0.1
    )))
```

Planner entscheidet: Helper oder Inline im Template. Helper ist sauberer.

### Pattern to mirror — `_calc_call_score`

`routes/app_routes.py:573-583`:
```python
def _calc_call_score(conv):
    """Server-seitige Spiegelung der client-seitigen _calcScore()-Formel in pip-launcher.js.
    Gewichtung: kb_end 40%, behandeltRate 30%, redeScore 20%, skript 10%."""
    kb = conv.kb_end if conv.kb_end is not None else 30
    einw_total = conv.einwaende_gesamt or 0
    einw_ok = conv.einwaende_behandelt or 0
    behandelt_rate = (einw_ok / einw_total) if einw_total > 0 else 0.5
    redeanteil = conv.redeanteil_avg if conv.redeanteil_avg is not None else 50
    rede_score = max(0, 100 - abs(redeanteil - 40) * 2)
    skript = conv.skript_abdeckung or 0
    return min(100, max(0, round(kb * 0.4 + behandelt_rate * 100 * 0.3 + rede_score * 0.2 + skript * 0.1)))
```

### Cross-Context-Query — SQLAlchemy-ORM (SQLite-safe)

**UI-SPEC Rev 3 nutzt PostgreSQL-Syntax (`INTERVAL '14 days'`) — das funktioniert in SQLite nicht.**

Korrekter Pattern für Live (Spiegel-Query gegen Training):

```python
from datetime import datetime, timedelta
from database.models import ConversationLog as CL, ObjectionEvent as OE
from sqlalchemy import func

def _cross_context_for_live(db, user_id, einwand_typ):
    cutoff = datetime.utcnow() - timedelta(days=14)
    rows = (db.query(
                func.count(OE.id).label('n'),
                func.avg(CL.sterne).label('avg_sterne'),  # kann None sein
            )
            .join(CL, CL.id == OE.conversation_log_id)
            .filter(CL.user_id == user_id)
            .filter(CL.typ == 'training')
            .filter(CL.created_at >= cutoff)
            .filter(OE.einwand_typ == einwand_typ)
            .first())
    n = int(rows.n or 0)
    avg_sterne = float(rows.avg_sterne) if rows.avg_sterne is not None else None
    return {'sessions': n, 'avg_sterne': avg_sterne, 'focus_match': einwand_typ}
```

**Cave:** `CL.sterne` für Training-Sessions ist **immer NULL** (siehe Q3). Das heißt
`avg_sterne` **wird immer None** sein bei Cross-Context von Live nach Training. Die UI-SPEC Rev 3
Copy `"Zuletzt im Training: Ø 4.2★ aus 3 Sessions"` ist semantisch unerreichbar bei aktuellem
Code. Planner-Empfehlung:

- Verwende stattdessen `CL.kb_end` (der `gesamt_score` vom Training) für avg-Berechnung
- Copy anpassen auf `"Zuletzt im Training: Ø {avg_score}/100 aus {n} Sessions"`
- Success-Modifier-Schwelle: `avg_score >= 75` (statt `avg_sterne >= 4`)

**Alternativ:** Cross-Context-Badge bei Training-Sessions für Live-Seite temporär nur "N Sessions
in letzten 14 Tagen" zeigen (ohne Qualitäts-Metrik). Planner entscheidet.

### Prioritäts-Reihenfolge `typ='live'` (4 Regeln) — Zugriffs-Felder

1. **Nicht behandelte Einwände:** `events` filtern auf `not e.success`, gruppieren nach
   `e.einwand_typ`, Top-Entry wählen. Wenn ≥3 vom gleichen Typ, höchste Prio.
2. **Kaufbereitschafts-Drop:** `conv.kb_start - conv.kb_end > 15` → kb:drop
3. **Redeanteil zu hoch/niedrig:** `abs(conv.redeanteil_avg - 40) > 25`
4. **Skript-Abdeckung niedrig:** `conv.skript_abdeckung < 50`

Nur erste 3 Matches → max 3 Cards. Empty-State wenn 0 Matches.

### Prioritäts-Reihenfolge `typ='training'` (4 Regeln)

1. **Score < 50:** `conv.kb_end < 50` (gesamt_score) → `training:generic_weakness`
2. **Kunde aufgelegt:** `stimmung_history[-1]['wert'] == -5` → `training:personality_{pt_id}`
3. **Nicht behandelte Einwände (Spiegel):** wie Regel 1 Live
4. **Stimmungs-Verschlechterung:** `stimmung_history[0]['wert'] > stimmung_history[-1]['wert'] + 3` → `training:mood_management`

## R3 — SQLite Migration Pattern

### Bestehender Pattern (duplicate-column-safe)

`app.py:72-134` — `_migrate()`-Funktion, läuft auf jeden App-Start. Pattern für
`conversation_logs` in `app.py:312-322`:

```python
# ── Phase 04.9: conversation_logs extensions ──────────────────────────
for col, typedef in [
    ('personality_type_id', 'INTEGER'),
    ('stimmung_history',    'TEXT'),
]:
    try:
        conn.execute(text(f'ALTER TABLE conversation_logs ADD COLUMN {col} {typedef}'))
        conn.commit()
        print(f"[DB] Migration: added conversation_logs.{col}")
    except Exception:
        pass
```

**`except Exception: pass` ist der idempotenz-Mechanismus** — SQLite wirft bei Duplicate-Column
einen `OperationalError`, der wird geswallowt. Code läuft bei jedem Start, no-op nach erster
Migration.

### Exakter Einfüge-Pattern für Phase 07.1

**`app.py` nach Zeile 322 einfügen (nach dem Phase-04.9-Block):**

```python
# ── Phase 07.1: kb_verlauf für Live-Session-Chart ─────────────────────
for col, typedef in [
    ('kb_verlauf', 'TEXT'),
]:
    try:
        conn.execute(text(f'ALTER TABLE conversation_logs ADD COLUMN {col} {typedef}'))
        conn.commit()
        print(f"[DB] Migration: added conversation_logs.{col}")
    except Exception:
        pass
```

Plus Spalte in `database/models.py` im `ConversationLog`-Block einfügen (z.B. nach Zeile 279
`stimmung_history`):

```python
kb_verlauf = Column(Text, nullable=True)  # Phase 07.1: JSON list [{ts, wert}]
```

**Cave — Alte Sessions:** Existierende `conversation_logs`-Rows bekommen `kb_verlauf = NULL` — das
ist gewünscht. UI-Template muss auf NULL checken → Empty-State "Noch keine Verlaufsdaten" (siehe
UI-SPEC Copy "Dieser Call wurde vor der Verlaufs-Erfassung geführt...").

### Migration ist Startup-Block, kein Script

- Liegt inline in `app.py` inside `_migrate()` definition
- Wird aufgerufen vom Haupt-App-Init (sucht nach `_migrate()`-Call)
- Kein separates `migrate.py`-Script nötig
- **Deploy-Trigger:** `deploy.sh` zieht Code rauf und restartet gunicorn → `_migrate()` läuft beim

# Smoke-Test Recipe (T2)

SQL-Query für 3 Test-Sessions (ein cold-call, ein meeting, ein training):

```sql
-- Cold Call Session (beste für Chart + Timeline)
SELECT id, user_id, session_mode, typ, kb_end, einwaende_gesamt,
       dauer_sekunden, created_at
FROM conversation_logs
WHERE typ = 'live' AND session_mode = 'cold_call'
  AND einwaende_gesamt >= 2
  AND kb_end IS NOT NULL
ORDER BY created_at DESC
LIMIT 1;

-- Meeting Session
SELECT id, user_id, session_mode, typ, kb_end, einwaende_gesamt, dauer_sekunden
FROM conversation_logs
WHERE typ = 'live' AND session_mode = 'meeting'
ORDER BY created_at DESC
LIMIT 1;

-- Training Session mit Personality + stimmung_history
SELECT id, user_id, typ, personality_type_id, kb_end, einwaende_gesamt,
       length(stimmung_history) as hist_len
FROM conversation_logs
WHERE typ = 'training'
  AND personality_type_id IS NOT NULL
  AND stimmung_history IS NOT NULL
ORDER BY created_at DESC
LIMIT 1;
```


Dann `/session/<id>` mit jeder der drei IDs öffnen → alle Varianten (A/B/C aus UI-SPEC Rev 3)
testen.

**Wichtig für Wave 3 Smoke:**

- **Neuer Call nach Deploy** muss `kb_verlauf` in DB haben (sonst ist die Migration nicht gegriffen):
  ```sql
  SELECT kb_verlauf FROM conversation_logs ORDER BY id DESC LIMIT 1;
  ```
  → sollte JSON-Array sein, nicht NULL
- **Alter Call** zeigt `kb_verlauf = NULL` → Chart rendert Empty-State (nicht crash)
- **Training-Session** zeigt `stimmung_history`-Chart korrekt auf `-5..+5`-Skala
