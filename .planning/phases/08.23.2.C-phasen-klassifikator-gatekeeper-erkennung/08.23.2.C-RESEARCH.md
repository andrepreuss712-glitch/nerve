## Summary

Phase 08.23.2.C ist eine komplexe (🔴) Cross-AI-Pflicht-Phase mit 14 Anforderungen, die sich über vier Hauptbereiche erstreckt: (1) GLiNER als zweite NER-Stufe in der bestehenden anonymization.py, (2) Umbau des modus-blinden Phasen-Klassifikators auf drei separate Listen mit Hysterese-Logik, (3) neues `services/gatekeeper.py`-Modul mit Drei-Kategorien-Klassifikation und Trigger-Phrasen, und (4) PiP-UI-Erweiterungen (Ctrl+G/Ctrl+E, Gatekeeper-Buttons, UWG-Banner).

Die Codebase ist klar strukturiert und alle Integrationspunkte sind identifiziert. Phase B hat saubere Abstraktionen hinterlassen (`anonymize()`, `AnrufAnonymisierer`, Fallback-Pattern), auf denen Phase C direkt aufbauen kann. Die kritischste technische Frage — GLiNER-Latenz <200ms P95 — ist als Acceptance-Gate definiert und muss in Wave 0 durch einen Latenz-Smoke-Test abgesichert werden, bevor die Anonymisierungs-Pipeline erweitert wird.

GLiNER `gliner_multi-v2.1` hat 209M Parameter, wird via `GLiNER.from_pretrained("urchade/gliner_multi-v2.1")` geladen und unterstützt `predict_entities(text, labels, threshold=0.5)`. Die App läuft auf CX32 (8 GB RAM); Speicher-Budget ist knapp aber rechnerisch ausreichend: spaCy ~600 MB + GLiNER ~800 MB + App ~300 MB ≈ 1.7 GB. Thread-Safety des GLiNER-Modells bei Concurrent Reads ist aus offizieller Dokumentation nicht explizit belegt — der Plan muss dasselbe `threading.Lock()`-Pattern wie für spaCy vorsehen.

**Primary recommendation:** Baue Phase C in fünf Waves: (0) GLiNER-Latenz-Smoke + Foundation, (1) anonymization.py + extract_entities(), (2) gatekeeper.py + classify_contact(), (3) classify_phase()-Umbau + Hysterese + call_events, (4) PiP-UI (Ctrl+G/E, Buttons, Banner), (5) Alembic 0003 + Seeds + Tests.

_gliner_model = None
_gliner_lock = threading.Lock()

def _get_gliner():
    """Thread-safe lazy load von GLiNER. Einmal pro Prozess geladen."""
    global _gliner_model, is_pipeline_healthy
    if _gliner_model is None:
        with _gliner_lock:
            if _gliner_model is None:
                try:
                    from gliner import GLiNER
                    _gliner_model = GLiNER.from_pretrained('urchade/gliner_multi-v2.1')
                    print('[ANON] GLiNER gliner_multi-v2.1 geladen')
                except Exception as e:
                    print(f'[ANON] KRITISCH: GLiNER nicht ladbar: {type(e).__name__}')
                    is_pipeline_healthy = False
    return _gliner_model

### Pattern 2: extract_entities() öffentliche Funktion

```python
# Source: D-02 aus CONTEXT.md — Design definiert
def extract_entities(text: str, cache=None) -> List[dict]:
    """Gibt rohe Entitäten mit Source-Tags zurück.
    Für gatekeeper.py-Konsens-Voting.
    Returns: [{'text': str, 'type': str, 'source': 'spacy'|'gliner'}, ...]
    """
    entities = []
    nlp = _get_nlp()
    if nlp:
        doc = nlp(text)
        for ent in doc.ents:
            if ent.label_ in ('PER', 'LOC', 'ORG'):
                entities.append({
                    'text': ent.text,
                    'type': 'PERSON' if ent.label_ == 'PER' else ent.label_,
                    'source': 'spacy',
                })
    gliner = _get_gliner()
    if gliner:
        try:
            results = gliner.predict_entities(text, ['person', 'organisation', 'location'],
                                               threshold=0.5)
            for ent in results:
                entities.append({
                    'text': ent['text'],
                    'type': ent['label'].upper().replace('ORGANISATION', 'ORG'),
                    'source': 'gliner',
                })
        except Exception as e:
            print(f'[ANON] GLiNER predict_entities Fehler: {type(e).__name__}')
    return entities
```

## Common Pitfalls

### Pitfall 1: GLiNER-Latenz überschreitet 200ms P95
**What goes wrong:** GLiNER-Inferenz auf CPU kann bei längeren Texten 100-300ms dauern; in Kombination mit spaCy könnten <200ms P95 aus Req-1 verletzt werden.
**Why it happens:** Beide Modelle laufen sequenziell auf CPU-Threads (kein GPU auf CX32).
**How to avoid:** Wave 0 MUSS einen Latenz-Smoke-Test enthalten: `timeit` über 100 Runs auf 200-Zeichen-Text BEVOR die Integration in anonymize() erfolgt. Falls >150ms Single-Run: nur auf PERSON-Labels begrenzen (kein ORG/LOC in extract_entities für gatekeeper.py), oder GLiNER nur für Namen aktivieren.
**Warning signs:** `pytest tests/test_anonymization_perf.py` schlägt nach GLiNER-Integration fehl.

### Pitfall 2: GLiNER Label-Case-Sensitivität
**What goes wrong:** GLiNER ist case-sensitiv für Labels. `"Person"` und `"person"` können unterschiedliche Ergebnisse liefern. Vergleich mit spaCy-Labels (`PER`) braucht explizites Mapping.
**Why it happens:** GLiNER akzeptiert beliebige Labels — Normalisierung liegt beim Caller.
**How to avoid:** In `extract_entities()` immer lowercase Labels an GLiNER übergeben: `['person', 'organisation', 'location']`. Rückgabe normalisieren: `ent['label'].upper()` → `'PERSON'`, `'ORG'`, `'LOC'`.
**Warning signs:** Konsens-Check in classify_contact() findet keine Übereinstimmung obwohl beide Modelle dieselbe Person erkennen.

### Pitfall 3: Hysterese-State im falschen Scope
**What goes wrong:** Hysterese-Zähler (`phase_hint_count`, `pending_phase`, `phase_entered_at`) in `live_session.state` (globaler Dict) statt in `_session_state[sid]` führt zu Cross-Session-Contamination.
**Why it happens:** `live_session.state` ist ein globaler Dict (Z.113), `_session_state[sid]` ist per-SID.
**How to avoid:** Alle neuen Phase-C-State-Keys (`contact_category`, `current_mode`, `context_notes`, `phase_hint_count`, `pending_phase`, `phase_entered_at`) MÜSSEN in `init_session_state()` unter `_session_state[sid]['state']` initialisiert werden — nie als neue Keys in `ls.state` (globaler Dict).
**Warning signs:** Phasen-Wechsel in Session A beeinflusst Session B.

### Pitfall 4: CallEvent-Insert fehlt `call_id`
**What goes wrong:** `CallEvent` erfordert `call_id` (UUID, FK zu `calls.id`, non-nullable). Im aktuellen Code ist `ft_session_id` in Session-State vorhanden, aber noch nicht mit `calls.id` verknüpft.
**Why it happens:** Write-Pfade in `calls` und `call_events` sind Phase 08.23.2.C/D laut Phase-A-Spec — Phase C ist der erste Write.
**How to avoid:** Plan muss explizit adressieren woher `call_id` kommt. Optionen: (a) `Call`-Record bei `start_live_session` anlegen und UUID in Session-State speichern, (b) `call_id=None` mit `nullable=True` als Workaround falls Schema erlaubt — ABER: `call_id` ist laut models.py `nullable=False`. Also MUSS Option (a) in Wave 0 oder Wave 1 als separater Task geplant werden.
**Warning signs:** `IntegrityError: NOT NULL constraint failed: call_events.call_id`

### Pitfall 5: GLiNER Thread-Safety unklar
**What goes wrong:** GLiNER-Dokumentation beschreibt Thread-Safety nicht explizit. Bei 4 Threads (Gunicorn gthread) könnten concurrent `predict_entities()`-Aufrufe zu Race-Conditions führen.
**Why it happens:** PyTorch-Inference-Objekte sind nicht immer thread-safe für concurrent Writes.
**How to avoid:** Dasselbe Pattern wie für spaCy verwenden: Modell einmal laden, dann für Read-only `predict_entities()`-Calls nutzen (kein State-Update während Inference). Falls Probleme auftreten: Inference unter `_gliner_lock` serialisieren (Latenz-Tradeoff gegen Safety).
**Warning signs:** Gelegentliche `RuntimeError` oder falsche Entity-Ergebnisse unter Last.

### Pitfall 6: `init_session_state()` hat zwei State-Dicts
**What goes wrong:** `live_session.py` hat ZWEI Zustand-Strukturen: den globalen `ls.state` (Z.113) UND `_session_state[sid]['state']` (Z.327). Bestehende Code schreibt in beide. Neue Phase-C-Keys müssen in BEIDE eingefügt werden wenn sie von bestehendem Code gelesen werden.
**Why it happens:** HIGH-2-Coexistence-Pattern aus Phase 08 — Migrations-Artifact.
**How to avoid:** `contact_category`, `current_mode`, `context_notes` zunächst nur in `_session_state[sid]['state']` und in `ls.state` — Plan-Author muss grep auf Read-Pfade prüfen. Kommentar im Code mit Verweis auf HIGH-2.
**Warning signs:** PiP-Frontend zeigt immer `unknown` obwohl Klassifikator etwas anderes zurückgibt.

### Pitfall 7: Gatekeeper-Buttons laden Phrases aus DB mit falscher Scope
**What goes wrong:** Phrases werden per `user_id` aus DB geladen. Gatekeeper-Phrases mit `mode='gatekeeper'` sind Seed-Daten die für alle User gelten — aber aktuell hat `phrases` `user_id` als NOT-NULL-FK.
**Why it happens:** Seed-Daten wurden nie für shared/system-level Phrases konzipiert.
**How to avoid:** Plan muss entscheiden: (a) Seed-Daten mit `user_id=NULL` + Schema-Anpassung, (b) Seed-Daten pro User beim ersten Login duplizieren, (c) Seed-Daten mit spezifischer `user_id=1` (Admin) + Fallback. Option (c) ist einfachste MVP-Lösung. Plan-Author soll grep auf `Phrase.user_id` NOT NULL constraint verifizieren.
**Warning signs:** `IntegrityError: NOT NULL constraint failed: phrases.user_id`

### Pitfall 8: Pre-Execute-Gate blockiert Execute wenn Korpora fehlen
**What goes wrong:** `scripts/verify_corpus_gate.py` bricht Execute ab wenn Korpora nicht existieren. Da André die Korpora async erstellt, kann Execute erst nach André's Bestätigung starten.
**Why it happens:** D-04-Entscheidung: Korpora sind Gate-Bedingung.
**How to avoid:** Plan muss Pre-Execute-Gate explizit als Wave-0-Schritt mit Andre-Gate kennzeichnen. Execute-Waves 1-5 dürfen erst nach Gate-OK starten.
**Warning signs:** Vergessen dass Korpora-Gate eine manuelle Pause im Workflow erfordert.
