## Warnings

### WR-01: Demo-Profile Migration Guard — Dual OR-Condition Can Miss Partially-Migrated Rows

**File:** `app.py:752`

**Issue:** The idempotency check uses two conditions joined with `and`:
```python
if 'basis' in _daten:
    continue                              # line 749 — correct early-out
...
if 'produkt' not in _daten and 'einwaende' not in _daten:
    continue                              # line 752-753 — skips if NEITHER key exists
```
A profile that already had `einwaende` moved into `basis` but still has a stale top-level `produkt` key would pass the `basis`-check (line 749) correctly and be skipped — that part is fine. However a profile row whose `daten` JSON is `{}` (empty object, not `null`) also passes line 749 (no `basis` key) and then fails line 752 (`produkt not in {} AND einwaende not in {}` = True), so it is silently skipped with no migration and no log output. This is the intended behaviour for rows that were never in flat-schema, but the condition masks any genuinely corrupt empty-daten row without a diagnostic print. Additionally, the condition `'produkt' not in _daten and 'einwaende' not in _daten` uses `and` meaning both keys must be absent to skip. A profile that has `einwaende` at top level but no `produkt` would NOT be skipped — it would be migrated — but `_basis['produktbeschreibung']` would be set to `''` (empty string from `_daten.pop('produkt', '')`). This is acceptable for demo data but could silently corrupt a real profile if the ID whitelist ever widens.

**Fix:** Add a log line for the empty-daten skip path, and tighten the comment to document the OR semantics explicitly:
```python
if 'produkt' not in _daten and 'einwaende' not in _daten:
    # No flat-schema keys found — skip (e.g. already-migrated or empty)
    print(f"[DB] Migration 08.9: Profil ID {_pid} hat keine Flat-Schema-Keys — uebersprungen")
    continue
```

### WR-02: `db.query(User).get()` — Deprecated SQLAlchemy 2.x API in onboarding.py

**File:** `routes/onboarding.py:192`

**Issue:** `db.query(User).get(g.user.id)` uses the legacy `Query.get()` method which was deprecated in SQLAlchemy 1.4 and removed in SQLAlchemy 2.0. The project's `requirements.txt` specifies `sqlalchemy >= 2.0.0` (per CLAUDE.md). Other route files in this phase (`routes/profiles.py`) correctly use `db.query(Model).filter_by(...)` or `db.get(Model, pk)`. If the runtime SQLAlchemy version is 2.x, `Query.get()` raises `AttributeError` at runtime whenever `complete()` is called — meaning `onboarding/complete` silently fails or 500s for every new user who completes onboarding.

**Fix:**
```python
# Before (line 192):
user = db.query(User).get(g.user.id)

# After:
user = db.get(User, g.user.id)
```
This matches the pattern used in `routes/auth.py` lines 50 and 55, and `routes/profiles.py` line 215.

### WR-03: `create_profile_from_template` — Silently Creates Incomplete Profile on Missing `basis` Key

**File:** `routes/onboarding.py:219-228`

**Issue:** `create_profile_from_template` stores `json.dumps(template, ...)` where `template` is the full branch template dict (which now always contains a `basis` sub-dict). Then immediately after, `_basis = template.get('basis', {})` is used for the response counts. If `BRANCHE_TEMPLATES` ever returns a value without a `basis` key (e.g. a future lookup fallback or a mis-keyed dict), the profile is written to the DB as `{"basis": ...}` from the constant but `_basis` falls back to `{}`, so the response reports `einwaende: 0` and `phasen: 0` even though data was stored. More critically: the profile `daten` column stores the full template object including the `basis` key — this is now correct for H-31 — but the code has no assertion that `basis` is present, meaning a future template without it would silently produce an unusable profile.

**Fix:** Add an explicit check after the template lookup:
```python
template = BRANCHE_TEMPLATES.get(branche, BRANCHE_TEMPLATES['Sonstiges'])
_basis = template.get('basis', {})
if not _basis:
    # Defensive: template structure broken — log and use empty basis
    print(f"[Onboarding] create_profile_from_template: no basis in template for branche={branche}")
```
Move `_basis` extraction before the DB write so the log/count is consistent with what is stored.

### IN-01: `_rolle()` Helper Reads From `flask_session` — Inconsistent with `g.user.rolle` Pattern

**File:** `routes/profiles.py:33-34`

**Issue:** `_rolle()` reads `flask_session.get('rolle', 'member')`. The session value is set at login time and is not re-read from the DB on each request, meaning a role change (e.g. demote a user from `owner` to `member`) only takes effect after re-login. This is a known architectural trade-off in the project (session-cached auth state), but it is worth documenting because `wizard_create()` now gates creation on `_rolle()`, and the four new `_rolle()` checks added in this phase all share the same stale-session caveat. No immediate bug — but the pattern diverges from `g.user.rolle` which comes from a live DB query in `login_required`.

**Fix:** No immediate code change required; document the caveat inline in `_rolle()`:
```python
def _rolle():
    # Session-cached at login — reflects role at last login, not current DB value.
    return flask_session.get('rolle', 'member')
```

### IN-02: `streame_manual_ewb_variante` — `stream` Variable Used After `with` Block

**File:** `services/claude_service.py:671-684`

**Issue:** The Cost-Hook block at lines 671-684 calls `stream.get_final_message()` where `stream` is the loop variable from the last successful `with claude_client.messages.stream(...) as stream:` block. After the `with` block exits, the stream context manager is closed. `get_final_message()` on a closed stream may raise or return stale data depending on the Anthropic SDK version. The variable `stream_ctx` is assigned at line 647 but never used — it was apparently intended for exactly this purpose. The same pattern works correctly in `streame_auto_variante` (line 569) because the cost-hook is inside the `with` block's `try` section.

**Fix:** Use `stream_ctx` which was assigned for this purpose, or move the cost-hook call into the `with` block before `break`:
```python
# Option A: use the already-assigned stream_ctx variable
final_msg = stream_ctx.get_final_message()

# Option B: move cost-hook inside the with-block (cleaner)
```
The `stream_ctx` assignment at line 647 can then be removed as dead code.

### IN-03: Test `test_match_hit_sets_kw_fired_for_line` — Conditional Assertion Weakens Coverage

**File:** `tests/test_08_5_03_integration.py:71-72`

**Issue:** The assertion is guarded by `if result is not None:`. If `match_with_dedup` does not match the input text `'Das ist viel zu teuer'` against the provided `profile_einwaende` (e.g. because the keyword dictionary changed), the test passes without asserting anything — a false-green. Per project CLAUDE.md test quality rules, tests must assert runtime behaviour, not conditionally skip.

**Fix:** Either use an input text guaranteed to hit a known keyword pattern, or assert that `result is not None` before checking the flag:
```python
result = matcher.match_with_dedup('Das ist viel zu teuer', profile_einwaende)
self.assertIsNotNone(result, "Expected keyword match for 'zu teuer' — check keyword dict")
self.assertEqual(mock_ls.state.get('kw_fired_for_line'), 'line-42')
```

### IN-04: `app.py` Demo-Migration — No Rollback on Partial Failure Within Loop

**File:** `app.py:762-765`

**Issue:** The migration loop commits after each individual profile update (`conn.commit()` inside the for-loop body). If an error occurs on the second profile after the first has been committed, the first profile is migrated and the second is not — with the outer `except` swallowing the error. On the next app restart, the first profile passes the idempotency check (`'basis' in _daten`) and is correctly skipped. The second profile would be retried. This is acceptable for demo-only data (IDs 2/3/4) and the idempotency design is sound, but documenting the intentional per-row-commit pattern would prevent future confusion.

**Fix:** No code change required; add a comment:
```python
conn.commit()  # Per-row commit — idempotent, retry-safe on next startup
```
