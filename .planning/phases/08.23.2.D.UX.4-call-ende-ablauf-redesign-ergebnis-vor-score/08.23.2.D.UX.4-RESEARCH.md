## Summary

Diese Phase baut die **Reihenfolge** des Call-Endes um, ohne die Score-Logik neu zu bauen. Heute: `endCall()` → `/api/beenden` → sofortiger vorläufiger Frontend-Score (`_calcScore()`) → `/api/postcall_analysis` (Haiku + Sonnet parallel) → `_renderOutcomeUx` → User-Confirm → `correct_outcome` rechnet den Score **nochmal** still nach (Doppelrechnung, L-01-Bug). Ziel: Beenden+Hold → Ladebalken-1 (Haiku) → Outcome-Screen → Confirm → Score+Basis-Analytics SOFORT → Ladebalken-2 (Sonnet).

**Der entscheidende Backend-Befund (S-02):** `_calc_coaching_score(conv, outcome)` (app_routes.py:720-764) liest **ausschließlich aus der `ConversationLog`-Row** (`conv.kb_end`, `conv.einwaende_gesamt`, `conv.einwaende_behandelt`, `conv.redeanteil_avg`, `conv.skript_abdeckung`). Die **einzige** outcome-abhängige Zeile ist `modifier = _OUTCOME_MODIFIERS.get(outcome, 1.00)` (Z.747). Alles andere — der `process_score` (Z.740-746) — ist bereits eine eigenständige, outcome-unabhängige Größe, die `breakdown['process_score']` schon ausweist. Der Split ist deshalb sauber und risikoarm: `process_score` ist **vollständig berechenbar in dem Moment, in dem die ConversationLog-Row existiert** (das ist am Ende von `/api/beenden`, VOR jeder Outcome-Schätzung). Keine neue Datenquelle, kein neuer Thread nötig.

**Primary recommendation:** `_calc_coaching_score` in zwei Funktionen splitten: `_calc_process_score(conv) → (process_score_float, base_breakdown_dict)` und `_apply_outcome_modifier(process_score, base_breakdown, outcome) → (coaching_score, final_score, full_breakdown)`. Den Prozess-Score-Teil **persistent in `calls.score_breakdown`** stashen — am Ende von `/api/beenden` ODER in `/api/postcall_analysis` (Haiku-Step) — damit er einen Page-Reload / Socket-Reconnect überlebt (HART-Regel: Production = Test-Env, kein in-RAM-Dict das verschwindet). `correct_outcome` liest den gestashten Prozess-Score, wendet nur den Modifier an, persistiert den finalen `coaching_score`. Frontend rendert `final_score` aus der synchronen `correct_outcome`-Response (S-01, schon heute der Fall). **Keine Schema-Änderung** — `score_breakdown` (jsonb) und `coaching_score` (double) existieren bereits.

|---|---|---|---|

| `behandelt_rate` (einwaende) | 732-734 | NEIN | `conv.einwaende_gesamt/behandelt` |

### Empfohlener Refactor (zwei Funktionen — sauberste Form)

```python
def _calc_process_score(conv):
    """Outcome-UNABHÄNGIGER Prozess-Score. Berechenbar sobald die ConversationLog-Row
    existiert (Ende /api/beenden). Returns (process_score_float, base_breakdown_dict)."""
    kb_norm = float(conv.kb_end if conv is not None and conv.kb_end is not None else 30)
    einw_total = (conv.einwaende_gesamt or 0) if conv is not None else 0
    einw_ok = (conv.einwaende_behandelt or 0) if conv is not None else 0
    behandelt_rate = (einw_ok / einw_total) if einw_total > 0 else 0.5
    redeanteil = float(conv.redeanteil_avg if conv is not None and conv.redeanteil_avg is not None else 50)
    redeanteil_score = float(max(0, 100 - abs(redeanteil - 40) * 2))
    skript = float((conv.skript_abdeckung or 0) if conv is not None else 0)
    frage_qualitaet = 0.0
    process_score = (kb_norm*0.30 + behandelt_rate*100*0.30
                     + redeanteil_score*0.20 + skript*0.10 + frage_qualitaet*0.10)
    base_breakdown = {
        'schema_version': 1, 'kb_end_norm': round(kb_norm,4),
        'behandelt_rate': round(behandelt_rate,4), 'redeanteil_score': round(redeanteil_score,4),
        'skript_norm': round(skript,4), 'frage_qualitaet': frage_qualitaet,
        'process_score': round(process_score,4),
    }
    return process_score, base_breakdown

def _apply_outcome_modifier(process_score, base_breakdown, outcome):
    """Modifier-Anwendung beim Confirm. Returns (coaching_score, final_score, full_breakdown)."""
    from datetime import datetime, timezone as _tz
    modifier = _OUTCOME_MODIFIERS.get(outcome, 1.00)
    raw = process_score * modifier
    final_score = int(min(100, max(0, round(raw))))
    full = dict(base_breakdown)
    full.update({'outcome_modifier': modifier, 'final_score': final_score,
                 'computed_at_iso': datetime.now(_tz.utc).isoformat()})
    return round(raw, 4), final_score, full
```

`_calc_coaching_score(conv, outcome)` bleibt als **Thin-Wrapper** für Rückwärtskompatibilität (ruft beide auf) — so brechen keine anderen Caller. (Pflicht-grep nach weiteren Callern: nur `correct_outcome` Z.1923 + Tests gefunden in dieser Recherche; Planner verifiziert via `inspect.sh grep '_calc_coaching_score'`.)

### Wo den Prozess-Score stashen? — robusteste Production-Variante

Die HART-Regel sagt: Production ist die Test-Env, also muss der gestashte Wert **Page-Reload / Socket-Reconnect überleben**. Ein in-RAM-Dict (`ls.last_postcall` o.ä.) verschwindet bei `reset_session()` (app_routes.py:678) und bei Worker-Restart. → **Persistent in `calls.score_breakdown` (jsonb)** stashen.

**Empfohlener Stash-Punkt: am Ende von `/api/beenden`**, im bestehenden `calls`-UPDATE-Block (app_routes.py:603-621), wo `_call_row` ohnehin schon geladen + committed wird. Dort `conv_for_score` laden (analog `correct_outcome` Z.1919-1921 über `saved_conv_id`), `_calc_process_score(conv)` aufrufen, `_call_row.score_breakdown = base_breakdown` setzen. Vorteil: läuft genau einmal, deterministisch, kein neuer Thread, kein Race mit Haiku (der Prozess-Score braucht Haiku nicht). `coaching_score` bleibt hier NULL (noch kein Outcome).

**Alternative (auch valide):** im `calls`-UPDATE-Block von `/api/postcall_analysis` (learning.py:122-143), wo schon `_call_row` für `outcome` geladen wird. Nachteil: dieser Block läuft nur wenn `_outcome_val is not None or _outcome_conf > 0` (Z.123) — bei echtem Haiku-Ausfall mit conf=0 würde der Prozess-Score-Stash übersprungen. → **`/api/beenden` ist robuster**, weil es immer läuft.

**Beim Confirm (`correct_outcome`, app_routes.py:1922-1929):**
```python
# statt _calc_coaching_score(conv_for_score, new_outcome):
base_bd = (row.score_breakdown or {})
if 'process_score' in base_bd:
    process_score = base_bd['process_score']
else:
    process_score, base_bd = _calc_process_score(conv_for_score)  # Fallback: neu berechnen
coaching_score_val, final_score_val, breakdown_data = _apply_outcome_modifier(process_score, base_bd, new_outcome)
```
Der Fallback (`_calc_process_score` falls kein Stash da) hält den Pfad robust gegen alte Calls / fehlenden Stash → **kein Hard-Fail, kein neuer Race**. Prozess-Teil wird genau einmal gerechnet (im Normalfall in `/api/beenden`), Modifier genau einmal (im Confirm). Erfüllt S-02.

## Landmines (Races, Doppelrechnung, Guards)

1. **Doppel-Render des Outcome-Screens:** Drei Pfade können `_renderOutcomeUx` triggern — `outcome_ready`-Socket (2444), `postcall_analysis`-`.then` (2960), neuer 9s-Timeout. 3. **Doppelrechnung des Scores (L-01):** Heute rechnet FE (`_calcScore`) UND BE (`correct_outcome`). Nach dem Split: Prozess-Teil genau einmal (in `/api/beenden`), Modifier genau einmal (in `correct_outcome`). **`_calcScore` (2982) DARF NICHT mehr in den angezeigten Score fließen** (L-01) — Aufruf in `_showPostcall` Z.3047-3049 aus dem Render-Pfad entfernen. (`_calc_call_score` BE-Spiegelung Z.695 ist Dead-Code-Kandidat — prüfen ob noch Caller.)
4. **Prozess-Stash-Miss bei alten Calls / conf=0:** Falls Stash nur in `postcall_analysis` läge, würde der conf=0-Pfad (Haiku-Ausfall) ihn überspringen (learning.py:123-Guard). → Stash in `/api/beenden` (läuft immer) + Fallback `_calc_process_score` in `correct_outcome`. Beides verhindert Hard-Fail.
5. **`correct_outcome` hat heute KEINEN Stale-Guard** (3816). Bei terminalem Forced-Choice (B-03) geringeres Risiko, aber für Konsistenz `endCallGen`-Check ergänzen.
6. **Sonnet-Reihenfolge:** Wird Sonnet erst NACH Confirm getriggert (Ladebalken-2), darf der Sonnet-Fetch den Score/Analytics-Render NICHT blockieren oder überschreiben (S-03: Score bleibt sichtbar während Ladebalken-2 läuft).
