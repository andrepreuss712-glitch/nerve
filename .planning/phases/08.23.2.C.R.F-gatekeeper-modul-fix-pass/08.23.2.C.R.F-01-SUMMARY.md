## What Was Built

### Task 1: Atomare Idempotenz-Sicherung in `create_call_for_sid()`

In `services/live_session.py` wurde am Funktionsanfang von `create_call_for_sid()` ein atomarer Sentinel-Guard eingefuegt:

- **Check + Sentinel-Write unter demselben `_session_state_lock`-Eintritt**: Kein paralleler Thread kann zwischen Check und Write eine None-call_id lesen
- **Drei Guard-Pfade:**
  1. `call_id` bereits eine echte UUID → sofort zurueckgeben (Duplicate Protection)
  2. `call_id == '__call_pending__'` → sofort `None` zurueckgeben (Concurrent-Call Protection)
  3. `call_id is None` → `'__call_pending__'` setzen, dann DB-Insert fortsetzen
- **Sentinel-Cleanup im except-Block**: DB-Fehler setzt `call_id` von `'__call_pending__'` zurueck auf `None` — naechster Reconnect kann es erneut versuchen (T-RF-10)

### Task 2: Wiring in `handle_start_live_session()`

In `services/deepgram_service.py` wurde nach dem `_load_profile_cache`-Block eingefuegt:

- **`ls.create_call_for_sid()` Aufruf**: REQ-6 Production-Pfad — Call-Record existiert jetzt bei jedem normalen Session-Start
- **Return-Wert Protokollierung**: `None`-Return loggt explizit (Finding 1.3 — kein stilles Fehlschlagen)
- **Fast-Path-Check**: Externer `_existing_cid_f is None`-Check als Performance-Optimierung dokumentiert (NICHT Korrektheit-Garantie)
- **`contact_category_update` Session-Init-Emit**: Liest `contact_category` und `current_mode` aus `_session_state` (nicht hardcoded) — Meeting-Sessions sehen korrekten Anfangszustand (Finding 1.1)
