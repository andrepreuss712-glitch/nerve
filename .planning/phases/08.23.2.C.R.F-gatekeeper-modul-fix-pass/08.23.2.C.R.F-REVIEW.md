## Warnings

### WR-01: Rollback called after close on `_db_mi` — SQLAlchemy session already closed

**File:** `services/live_session.py:499-501`

**Issue:** In `create_call_for_sid()`, the `mode_initial` event is written via `_db_mi`. The inner `try/finally` block calls `_db_mi.close()` in `finally` (line 498). If `_db_mi.add()` or `_db_mi.commit()` raises, the `finally` runs `_db_mi.close()` first — and then the outer `except` (line 499-501) tries `_db_mi.rollback()` on an already-closed session. With SQLAlchemy, calling `rollback()` on a closed session raises `InvalidRequestError: Can't reconnect until invalid transaction is rolled back`. Since the outer handler catches `Exception`, this second error is silently swallowed, but it means the rollback never actually executes (the session is closed, not rolled back).

Since this is non-fatal code the practical impact is low, but it's a logic error that leaks a potential transaction on some DB drivers.

**Fix:** Move rollback before close, or restructure so both happen in the same finally:

```python
# Option A: rollback in the inner finally, before close
try:
    _db_mi.add(_CE_mi(...))
    _db_mi.commit()
    print(...)
except Exception:
    try:
        _db_mi.rollback()
    except Exception:
        pass
    raise
finally:
    _db_mi.close()
```

Or, equivalently, remove the `_db_mi.rollback()` from the outer except entirely — the session is closed anyway, and the `mode_initial` INSERT failure is already non-fatal.

### WR-02: `state.contactCategory` uninitialized — first toggle click always emits `'gatekeeper'`

**File:** `static/pip-launcher.js:3479`

**Issue:** The `pip-mode-indicator` click handler computes the new category as:

```javascript
var newCategory = (state.contactCategory === 'gatekeeper') ? 'target' : 'gatekeeper';
```

`state.contactCategory` is **not declared** in the initial `state` object (lines 27–73). It is only set by `_updateContactCategory()`, which fires on the `contact_category_update` socket event. Before that event arrives, `state.contactCategory` is `undefined`. `undefined === 'gatekeeper'` is `false`, so the ternary evaluates to `'gatekeeper'` — any button click before the first socket ack emits `'gatekeeper'` regardless of the actual server state.

In practice the server emits `contact_category_update` at session init (line 507-509 of `deepgram_service.py`), so the window is small. But it is a genuine logic error: if the user clicks the toggle before the init emit arrives (race on slow connections or reconnect), the click sends the wrong category.

**Fix:** Initialize `contactCategory` in the `state` object declaration with the same default as the server:

```javascript
var state = {
  // ... existing fields ...
  contactCategory: 'gatekeeper',  // mirrors server default (init_session_state)
  currentMode: 'gatekeeper',
  // ...
};
```

## Info

### IN-01: `monotonic()` timestamp in `mode_initial` DB payload — not serializable on all drivers

**File:** `services/live_session.py:492`

**Issue:** The `mode_initial` CallEvent payload includes `'timestamp': _t_mi.monotonic()`. `time.monotonic()` returns a float, which is fine for JSON. However, monotonic time is machine-local and meaningless to any consumer that reads the row from the DB (it can't be compared to wall-clock time or to monotonic values from another process restart). The `event_ts_ms` field (integer epoch ms) already captures when the event occurred. The `'timestamp': monotonic()` field adds no actionable information and could confuse future analytics.

**Fix:** Remove the `'timestamp': _t_mi.monotonic()` key from the payload, or replace with a wall-clock ISO string if a human-readable timestamp is desired alongside `event_ts_ms`.

### IN-02: Double `import time as _t` block inside lock in `handle_manual_mode_toggle`

**File:** `services/deepgram_service.py:708-709`

**Issue:** `import time as _t` is executed inside the `with ls._session_state_lock:` block (line 709). Python imports are safe to call inside locks (the import system has its own lock), but holding a user-level lock while doing an import is an unusual pattern that could theoretically cause a brief priority inversion if another thread is waiting on `_session_state_lock`. The import is cached after the first call so the overhead is negligible, but the style is non-idiomatic.

**Fix:** Move `import time as _t` to the top of `handle_manual_mode_toggle` (or to the module-level import block).

### IN-03: Test helper `_extract_handler` calls `register_audio_handlers` on every invocation — re-registers all handlers each call

**File:** `tests/test_mode_switch_event.py:17-33`

**Issue:** Each test calls `_extract_handler(event_name)`, which calls `register_audio_handlers(mock_sio)`. This is a fresh `mock_sio` each time, so the closures are correct and there is no shared-state risk. However, if a third test were added that calls `_extract_handler` twice for different events, two separate `register_audio_handlers` calls create two independent handler sets — the `sio` in one handler's closure is not the same object as in the other. This is fine for current tests but would be a subtle bug if a future test needed to verify cross-handler interaction (e.g., checking that `handle_manual_mode_toggle` emits via the same `sio` that received `connect`).

**Fix:** (Low priority.) Extract a shared fixture or module-level setup that calls `register_audio_handlers` once and returns all registered handlers. For the current two-test suite this is not actionable.
