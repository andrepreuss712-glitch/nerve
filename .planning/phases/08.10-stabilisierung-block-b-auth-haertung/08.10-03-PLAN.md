<objective>
Wave 3: CSRF-Schutz vollständig implementieren — Backend CSRFProtect(app) + Webhook-Exempts + Meta-Tag in base.html + CSRF-Token in allen JS POST-Calls.

Purpose: Ohne CSRF-Schutz kann ein Angreifer einen eingeloggten User dazu bringen, ungewollte Aktionen auszuführen (z.B. Profil-Änderungen, Session-Start). Flask-WTF CSRFProtect schützt alle State-ändernden Endpunkte. Stripe-Webhook und OAuth-Callbacks müssen explizit exempt sein (keine Browser-Sessions).

Output: CSRFProtect(app) in app.py, 3 csrf.exempt(), Meta-Tag in base.html, getCsrfToken()-Helper in allen 5 JS-Files.

CSRF-Exempt-Begründung (für Cross-AI-Review):
- payments.stripe_webhook: Externe Stripe-Server senden POST, kein Browser-Cookie vorhanden. Stripe signiert via STRIPE_WEBHOOK_SECRET — das ist der korrekte Auth-Mechanismus.
- oauth.google_callback: OAuth-Flow = GET-Callback von Google. Kein Browser-POST, kein CSRF-Risiko.
- oauth.microsoft_callback: OAuth-Flow = GET-Callback von Microsoft. Identisch zu Google.

Backwards-Compatibility: Bestehende Browser-Sessions verlieren ihre CSRF-Token-Referenz erst beim nächsten Page-Load. Beim nächsten Page-Load wird der neue Meta-Tag gerendert, alle folgenden POST-Requests funktionieren. Kein User-Logout erforderlich.
</objective>

**Pattern für alle 5 Files:**

Hilfsfunktion oben in jedes File einfügen (als globale Funktion oder im jeweiligen Scope):
```javascript
function getCsrfToken() {
  var m = document.querySelector('meta[name="csrf-token"]');
  return m ? m.getAttribute('content') : '';
}
```

Dann bei JEDEM `fetch(url, { method: 'POST', ... })` Call den Header hinzufügen:

**Für JSON-Calls (Content-Type: application/json):**
```javascript
headers: {
  'Content-Type': 'application/json',
  'X-CSRFToken': getCsrfToken()
}
```

**Für FormData-Calls (feedback.js — kein Content-Type Header, da FormData auto-setzt):**
```javascript
// Bestehend: fetch('/api/feedback', {method:'POST', body:fd, credentials:'same-origin'})
// Nach Fix:
fetch('/api/feedback', {
  method: 'POST',
  body: fd,
  credentials: 'same-origin',
  headers: { 'X-CSRFToken': getCsrfToken() }
})
```

**Spezifische Stellen:**

app.js: Beim Lesen alle `method: 'POST'` Calls finden. Bestehende `headers:`-Objekte um `'X-CSRFToken': getCsrfToken()` ergänzen. Falls kein `headers:` vorhanden, hinzufügen.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → API (POST) | Ohne CSRF-Schutz können cross-origin Seiten POST-Requests im Namen eingeloggter User auslösen |
| Stripe-Server → /payments/webhook | Externe Server, kein Browser-Origin, kein Cookie — CSRF-Exempt korrekt |
| Google/Microsoft-Server → /auth/*/callback | OAuth GET-Callback, kein Browser-POST — CSRF-Exempt korrekt |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08.10-03-A | Spoofing + Tampering | Alle POST-Endpunkte | mitigate | CSRFProtect(app) + X-CSRFToken Header in JS |
| T-08.10-03-B | Spoofing | payments.stripe_webhook | accept (by design) | csrf.exempt() korrekt — Stripe-Auth via HMAC-Signature (STRIPE_WEBHOOK_SECRET) |
| T-08.10-03-C | Spoofing | oauth.google_callback | accept (by design) | csrf.exempt() korrekt — OAuth state-Parameter ist CSRF-Mitigation für OAuth-Flow |
| T-08.10-03-D | Spoofing | oauth.microsoft_callback | accept (by design) | csrf.exempt() korrekt — OAuth state-Parameter ist CSRF-Mitigation für OAuth-Flow |
| T-08.10-03-E | Information Disclosure | CSRF-Token im Meta-Tag | accept | Token ist session-scoped, kein Geheimnis per se — nur für eingeloggte User sichtbar |

Residual-Risk: CSRF-Token im Meta-Tag ist für XSS-Angreifer lesbar. XSS-Prävention (bleach in markdown_filter bereits vorhanden) ist primäre Gegenmassnahme. HttpOnly auf Session-Cookie (Wave 2) verhindert direkten Cookie-Diebstahl.

Backwards-Compatibility: Bestehende Sessions: Beim nächsten Page-Load erhält Browser den neuen Meta-Tag. Alle folgenden POST-Requests haben Token. Sessions mid-flight verlieren nichts (CSRF-Token ist stateless per Session).
</threat_model>
