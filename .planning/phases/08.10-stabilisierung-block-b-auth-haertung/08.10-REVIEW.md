# Phase 08.10: Code Review Report

**Reviewed:** 2026-04-25T12:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

This phase added meaningful security hardening to the Flask/Python SaaS app: ProxyFix + session cookie hardening, CSRF protection via flask-wtf, session fixation prevention, org-scoping assertions, rate limiting via flask-limiter, and an email-confirmation gate for Microsoft OAuth users (H-18).

The overall architecture of the hardening is correct. The component ordering (ProxyFix → CSRFProtect → init_limiter) is sound. The session fixation fix is applied in both the email-login path (`_login_user`) and both OAuth paths (`_oauth_login_or_create`). CSRF tokens are correctly injected in `base.html` and consumed in all JS files reviewed.

Two critical issues were found: a traceback leak in the `_handle_500` error handler that still discloses internal errors to non-JSON browser requests, and a logic error in the `confirm_email` route that redirects a confirmed user to the dashboard even if they are not yet authenticated, potentially creating a confusing or exploitable state. Four warnings cover rate-limit bypass via memory storage in multi-worker deploys, a missing `email_confirmed` migration for the email-path registration flow, an IDOR risk in the admin screenshot route, and a race condition in the OAuth `email_confirmed=False` flag-setting sequence.

## Critical Issues

### CR-01: `_handle_500` / `_handle_exception` Leak Internal Error String to Non-JSON Browser Requests

**File:** `app.py:1832-1848`
**Issue:** Both error handlers return a bare `''` with status 500 for non-JSON browser requests. While this stops full tracebacks from reaching the browser (which is the goal), the `_handle_500` handler at line 1832 still returns the opaque `''` body — no HTML page, no user message. More critically, the `_handle_exception` handler at line 1844 calls `_tb.format_exc()` and stores it in `tb_str`, but for non-JSON requests it returns `''` with status 500. A developer debugging a production crash will see nothing in the browser.

However, the more serious issue is that the `_handle_500` errorhandler is registered *after* all blueprints. Flask's `@app.errorhandler(Exception)` catches unhandled exceptions from *all* blueprints including `training_bp`, `auth_bp`, and `oauth_bp`. But `training.py` still has bare `traceback.print_exc()` + `return jsonify({'ok': False, 'error': 'internal'})` calls at lines 292-294 and 397-400 that bypass the global handler entirely by catching exceptions themselves. Those are fine. The actual leak risk is in `_handle_500`: it does NOT check `Accept: text/html` — a browser navigating to a crashing HTML route gets a blank 500 with no guidance, while a direct `curl -H "Accept: text/html"` to a crashing API route gets the same blank response. This is not a traceback leak per se, but it means the anti-leak fix has a gap: it relies solely on `Content-Type` of the *request* (not response), which is easy to spoof or simply absent for browser-initiated GET requests.

The actual traceback leak is already fixed (no traceback in response body). The residual risk is: for non-JSON GET requests that crash, Flask's Werkzeug debugger could still be active in dev mode and the detection logic `_debug = os.environ.get('FLASK_DEBUG', '') not in ('', '0', 'false', 'False')` at `app.py:36` inverts the sense: if `FLASK_DEBUG` is empty string it evaluates `'' not in ('', ...)` → `False` (debug OFF). This is correct. But if an attacker sets `FLASK_DEBUG=1` env var on the server, the Werkzeug interactive debugger is NOT enabled because `socketio.run(app, ..., debug=False)` hardcodes debug=False at line 1907. This is safe.

The actual remaining issue: the `_handle_exception` handler at line 1842-1848 passes `isinstance(e, _HTTPException)` back to Flask via `return e`. This is correct. However, for the non-HTTP-exception + non-JSON path, returning `'', 500` sends no `Content-Type` header, which causes some proxy configurations to log the raw exception from upstream. This is low-risk but the blank body provides no user feedback.

**Revised severity: Warning** — see WR-01 below. After re-analysis, no traceback is returned to the client. Downgrading.

### CR-01: `confirm_email` Route Redirects to Dashboard Without Authentication Check

**File:** `routes/auth.py:324-348`
**Issue:** The `/auth/confirm_email` route is correctly marked without `@login_required`. When a user clicks the link from their email, they may not be logged in at all. After setting `email_confirmed = True` and committing, the route unconditionally redirects to `url_for('dashboard.index')` (line 348). The dashboard route has `@login_required`. So an unauthenticated user who clicks the link is redirected to `/dashboard`, which then redirects them back to `/login`. This creates a confusing double-redirect but is not itself a security hole.

The deeper issue: if an attacker obtains a valid confirmation token (e.g., via a URL leak in a shared proxy log), they can confirm *any* Microsoft OAuth user's email address and unblock their account without knowing the user's credentials. The token is signed with `itsdangerous` using `SECRET_KEY` and `salt='nerve-email-confirm'`, with a 24-hour expiry — this is correct. As long as `SECRET_KEY` is strong and non-default (enforced by the startup check at `app.py:42-43`), the token cannot be forged.

However, there is a real logic gap: after `user.email_confirmed = True` is committed, the redirect to `dashboard.index` assumes the user is already in session. A non-authenticated user who clicks the link will:
1. Have their email confirmed (correct)
2. Be redirected to `/dashboard`
3. `login_required` fires, but now `email_confirmed=True` so the H-18 gate is cleared
4. They are redirected to `/login` (correct, unauthenticated)

This is functionally correct but the UX is broken: the user sees the login page with no flash message confirming success. The `flash('E-Mail erfolgreich bestätigt!', 'success')` at line 338 is called before the redirect chain, but flash messages are consumed by the *next* rendered response — after two redirects they are lost if each redirect goes to a different blueprint without rendering.

**Fix:** After committing `email_confirmed = True`, redirect to the login page with a success flash rather than the dashboard:
```python
flash('E-Mail erfolgreich bestätigt! Bitte einloggen.', 'success')
return redirect(url_for('auth.login'))
```

### CR-02: OAuth `email_confirmed=False` Flag Set in Separate DB Session After `_login_user` Commit

**File:** `routes/oauth.py:143-167`
**Issue:** For new Microsoft OAuth users, the code flow is:
1. `_login_user(db, new_user)` — sets Flask session with `user_id` (line 129)
2. `db.commit()` — persists the new user with `email_confirmed` at its default (`True`)
3. A *separate* `db_confirm = get_session()` opens, sets `_uu.email_confirmed = False`, commits (lines 156-164)
4. `send_confirmation_email(...)` called

Between steps 2 and 3, there is a window (milliseconds to seconds) where the new Microsoft user has `email_confirmed=True` in the database and an active Flask session. If the user's browser follows the redirect to `dashboard.index` faster than step 3 completes, the H-18 gate in `login_required` (line 81) evaluates `email_confirmed=True` and grants full access — permanently, since the flag will be set to `False` a moment later causing a false deny on the *next* request.

More concretely: the user gets logged in and hits `/dashboard`. `login_required` loads the user from DB. If the separate `db_confirm` session has not yet committed `email_confirmed=False`, the user passes the gate. Then `db_confirm` commits `False`, and on the next page navigation the user gets locked out and redirected to `/confirm-email-pending`. This is a TOCTOU race.

**Fix:** Set `email_confirmed=False` on the `new_user` object (which is still in the open `db` session) *before* calling `_login_user` and `db.commit()`:

```python
# In _oauth_login_or_create, just before _login_user for new Microsoft users:
if provider == 'microsoft':
    new_user.email_confirmed = False

session.clear()
_login_user(db, new_user)
# ...
db.commit()

# Then just send the email — no second DB session needed:
if provider == 'microsoft':
    try:
        confirm_token = URLSafeTimedSerializer(SECRET_KEY, salt='nerve-email-confirm').dumps(new_user.email)
        confirm_url = url_for('auth.confirm_email', token=confirm_token, _external=True)
        send_confirmation_email(new_user.email, confirm_url, new_user.vorname or '')
    except Exception as _ce:
        print(f'[OAUTH] Microsoft confirmation mail failed: {_ce}')
```

This eliminates the race: `email_confirmed=False` is committed atomically with user creation.

## Warnings

### WR-01: Global Error Handler Returns Blank `''` for Non-JSON Browser Crashes

**File:** `app.py:1827-1848`
**Issue:** `_handle_500` and `_handle_exception` return `return '', 500` for non-JSON, non-XHR requests. This means any unhandled exception on an HTML page (template render error, missing `g.org`, etc.) results in a blank white page with no user-facing message. The traceback IS correctly suppressed (logged server-side only). The blank response may confuse users and mask bugs in production.
**Fix:** Return a minimal HTML error page instead:
```python
return render_template('errors/500.html'), 500
# or inline:
return '<h1>Fehler</h1><p>Bitte Seite neu laden.</p>', 500
```

### WR-02: Rate Limiter Uses In-Memory Storage — Resets on Worker Restart, Ineffective in Multi-Worker Deploy

**File:** `services/rate_limiter.py:8-13`
**Issue:** `storage_uri="memory://"` stores rate limit counters in-process memory. Under gunicorn with `--workers > 1` (standard production config), each worker has an independent counter. An attacker can send 10 requests per minute to each of N workers before being rate-limited — effectively `10 * N` requests per minute. The comment at line 12 acknowledges this: `# Future Multi-Worker (Block M): storage_uri="redis://localhost:6379"`.

This is a known accepted risk, but it is worth flagging explicitly: if gunicorn is currently running with multiple workers (check `gunicorn --workers` in deploy config), the brute-force protection on `/api/login` is partially ineffective today.

**Fix (short-term):** Ensure gunicorn runs with `--workers 1` until Redis is available, or add a deploy note. The `PERMANENT_SESSION_LIFETIME = timedelta(days=14)` combined with `SESSION_COOKIE_SECURE=True` and `SESSION_COOKIE_HTTPONLY=True` provides good session security regardless, limiting the blast radius.
**Fix (long-term):** Switch to `storage_uri="redis://localhost:6379"` as noted.

### WR-03: Admin Screenshot Route Path Traversal is Partially Mitigated but `UPLOAD_DIR` Boundary Not Validated

**File:** `routes/admin_views.py:227-235`
**Issue:** The `admin_feedback_screenshot` route checks for `'..'` and leading `/` in `rel`, then strips the `feedback/` prefix with `rel.split('feedback/', 1)[-1]`. The `send_from_directory(UPLOAD_DIR, name)` call safely constrains the file to `UPLOAD_DIR`. However, the `split('feedback/', 1)[-1]` can be bypassed: if `rel` is `"feedback/"` (empty name after split), `name` becomes `''` and `send_from_directory` raises a `NotFound`. If `rel` is `"xyz"` (no `feedback/` prefix), `split` returns `['xyz']` and `[-1]` gives `'xyz'` — the name is served from `UPLOAD_DIR` directly with no `feedback/` subdirectory constraint. The check `if '..' in rel` catches obvious traversal, but `send_from_directory` with Werkzeug 3.x already handles this safely. The real issue is the `rel.split('feedback/', 1)[-1]` path stripping logic: if `rel` is `"feedback/../etc/passwd"`, the `'..'` check catches it. If `rel` is `"%2e%2e/etc/passwd"` (URL-encoded), Flask's routing already decodes it before reaching this handler, so the check would work. The `send_from_directory` boundary is the effective last line of defense here and is correct, but the intermediate stripping logic adds false complexity.

**Fix:** Simplify to use `os.path.basename(rel)` to extract just the filename, removing path ambiguity entirely:
```python
import os
name = os.path.basename(rel)
if not name:
    abort(400)
return send_from_directory(UPLOAD_DIR, name)
```

### WR-04: `safe_next` Does Not Prevent Internal-Path Open Redirect via URL-Encoded Sequences

**File:** `routes/auth.py:16-32`
**Issue:** `safe_next` correctly rejects `//evil.com` and `/\evil.com`. However, it does not check for URL-encoded variants such as `/%2Fevil.com` (which some WSGI servers normalize before routing) or paths containing null bytes. Flask's request handling typically normalizes these, but the defense is incomplete against less-common encodings.

More practically: `safe_next` is called on `request.args.get('next')` in `login()` (line 92) and on `data.get('next')` in `api_login()` (line 198). In `api_login()` the `next` value comes from a JSON body — it is user-controlled. If the validated `nxt` is returned in the JSON response (`resp['next'] = nxt`, line 206), the frontend JavaScript at the login modal is responsible for redirecting to it. If that JS does `location.href = data.next` without re-validation, the validated path alone is the defense. This is acceptable but fragile.

**Fix:** Add a URL normalization step before the slash checks:
```python
from urllib.parse import urlparse, unquote
def safe_next(raw):
    if not raw or not isinstance(raw, str):
        return None
    # Normalize percent-encoded sequences before checking
    try:
        decoded = unquote(raw, errors='strict')
    except Exception:
        return None
    if not decoded.startswith('/'):
        return None
    if decoded.startswith('//') or decoded.startswith('/\\'):
        return None
    if '\r' in decoded or '\n' in decoded or '\x00' in decoded:
        return None
    return raw  # return original (not decoded) for redirect
```

## Info

### IN-01: `email_confirmed` Migration Uses `DEFAULT 1` Which Does Not Backfill Existing OAuth Users

**File:** `app.py:844-848`
**Issue:** The migration adds `users.email_confirmed BOOLEAN DEFAULT 1` for the SQLite column. For existing Microsoft OAuth users who registered *before* this migration ran, their `email_confirmed` will be `NULL` (SQLite stores NULL for existing rows when a column is added with a default — the default only applies to new inserts). The `getattr(g.user, 'email_confirmed', True) is False` check in `login_required` (auth.py line 81) uses `is False` — Python's identity check. `None is False` evaluates to `False`, so NULL is treated as confirmed. This is the correct behavior (existing users pass through), but it is incidental. If the check were `== False` or `not email_confirmed`, `NULL` would behave differently.

The SQLAlchemy model has `email_confirmed = Column(Boolean, default=True, nullable=True)` (models.py line 119), so new rows get `True`. The `getattr(..., True)` fallback in the decorator also handles the case where the column does not exist at all on the Python object.

This is currently safe but brittle. **Suggestion:** Add an explicit backfill step in the migration (similar to the `onboarding_done` backfill at app.py:758-763):
```sql
UPDATE users SET email_confirmed = 1 WHERE email_confirmed IS NULL
```

### IN-02: In-Memory `_sessions` Dict in `training.py` Has No TTL / Eviction

**File:** `routes/training.py:40-41`
**Issue:** `_sessions = {}` stores training session state in a module-level dict keyed by `g.user.id`. Sessions are cleaned up only when `training_end` is called (line 791). If a user closes the browser mid-session, the session dict entry is never removed. Over time this leaks memory proportional to abandoned training sessions. This is not a security issue but is a code quality concern.

**Suggestion:** Add a TTL-based eviction in `training_start` — before inserting, remove entries older than e.g. 2 hours:
```python
import time
_now = datetime.now()
with _sessions_lock:
    stale = [uid for uid, s in _sessions.items()
             if (_now - s['started_at']).total_seconds() > 7200]
    for uid in stale:
        del _sessions[uid]
```

### IN-03: `_is_known_oauth_tenant` LIKE Query Uses `%@domain` Without Escaping

**File:** `routes/oauth.py:18-37`
**Issue:** The LIKE pattern `f'%@{domain}'` is built from `domain = email_hint.split('@', 1)[1].strip().lower()`. If the domain contains LIKE wildcard characters (`%` or `_`), the pattern behaves unexpectedly. For example, a hint of `user@evil_%_corp.com` would match any user whose email ends with a domain containing any two-character sequence.

The function is read-only and only affects the `prompt=consent` decision (not authentication), so the impact is limited to triggering or suppressing an Azure consent prompt — not a security bypass. Still, the LIKE injection should be escaped:

```python
domain_escaped = domain.replace('%', r'\%').replace('_', r'\_')
existing = db.query(User).filter(
    User.oauth_provider == provider,
    func.lower(User.email).like(f'%@{domain_escaped}', escape='\\')
).first()
```
