### Plan 02: Session-Cookie-Hardening

**Summary**
This plan implements foundational security improvements for Flask session cookies, protecting against XSS (HttpOnly) and cross-origin attacks (SameSite) while dynamically enforcing secure cookies in production.

**Strengths**
- Smart use of `os.environ.get('FLASK_DEBUG')` instead of `app.debug` to accommodate Gunicorn's execution environment.
- `SameSite='Lax'` is the correct choice for an application utilizing OAuth (which relies on top-level GET redirects).

**Concerns**
- **MEDIUM:** Proxy / SSL Termination. If the Hetzner VPS uses a reverse proxy (like Nginx) for SSL termination, Flask will see incoming requests as HTTP, not HTTPS. Setting `SESSION_COOKIE_SECURE = True` in this environment will cause Flask to silently drop/refuse to set cookies unless the application is wrapped in `Werkzeug.middleware.proxy_fix.ProxyFix`.

**Suggestions**
- Verify the reverse proxy configuration. If SSL is terminated before hitting Gunicorn, ensure `ProxyFix` is applied in `app.py`.

**Risk Assessment: LOW**
Straightforward implementation, provided the proxy setup is accounted for.

### Plan 05: Brute-Force-Schutz via flask-limiter

**Summary**
Introduces rate limiting for authentication endpoints to prevent brute-force and credential stuffing attacks, using a clean singleton pattern to avoid circular dependencies.

**Strengths**
- Excellent architectural foresight regarding the singleton `rate_limiter.py` to prevent Flask circular import headaches.
- Acknowledges the single-worker memory limitation and documents the Redis upgrade path.

**Concerns**
- **HIGH:** Reverse Proxy IP Masking. `get_remote_address` defaults to the immediate connecting IP. If Gunicorn is behind Nginx, all requests will appear to come from `127.0.0.1`. This will put all users in the same rate-limit bucket, causing a Denial of Service after 10 global login attempts.

**Suggestions**
- Ensure `X-Forwarded-For` headers are respected. Requires configuring `ProxyFix` in `app.py` before initializing the rate limiter, so `get_remote_address` pulls the actual client IP.

**Risk Assessment: HIGH**
High risk of accidentally rate-limiting the entire application if the proxy headers are not correctly parsed.

### Plan 06: oauth_id UNIQUE-Constraint + Microsoft Email-Hijacking-Mitigation

**Summary**
This plan hardens the database against duplicate OAuth IDs and attempts to mitigate a specific OAuth hijacking vector by enforcing an email confirmation step for new Microsoft logins.

**Strengths**
- Using a partial `UNIQUE` index (`WHERE oauth_id IS NOT NULL`) is the correct SQLite approach for nullable columns.
- Fails gracefully (silent catch) if the confirmation email fails to send, preventing broken onboarding flows.

**Concerns**
- **MEDIUM:** Incomplete Mitigation. "No redirect-block for unconfirmed emails in this phase — user can use app fully." If unconfirmed users can use the app fully, this is not a mitigation; it is merely telemetry. An attacker who hijacks an account via Microsoft OAuth can still access the victim's data immediately.
- **MEDIUM:** SQLite `ALTER TABLE` migrations can be brittle. Ensuring idempotency via `PRAGMA table_info` check is safer than bare try/except.

**Suggestions**
- To actually mitigate hijacking, block access to sensitive data until `email_confirmed == True`.
- Write a robust helper that checks `PRAGMA table_info(users)` before attempting `ALTER TABLE`.

**Risk Assessment: MEDIUM**
The database changes are solid, but the Microsoft hijacking "mitigation" as planned does not actually close the security loophole.

### Plan 05 — Brute-Force-Schutz via flask-limiter

**Summary:** Good architecture decision (singleton module avoids circular imports). The critical gap is X-Forwarded-For trust: on Hetzner behind Nginx, `get_remote_address` will return `127.0.0.1` for all requests.

**Strengths:**
- Singleton `services/rate_limiter.py` with `init_limiter(app)` is the correct pattern
- `default_limits=[]` (no global limit, only explicit decorators) is correct
- Residual acknowledged honestly: memory resets on restart, Redis required for multi-worker

**Concerns:**
- **HIGH:** `key_func=get_remote_address` returns `127.0.0.1` for all requests on reverse-proxied deployment (Nginx → Gunicorn). Rate limiter becomes completely ineffective in production. Fix: use `X-Forwarded-For` or `X-Real-IP` from Nginx, or configure `ProxyFix`.
- **MEDIUM:** Memory storage resets on gunicorn restart. An attacker triggering a restart resets the counter. Plan should note this restart-reset vector explicitly.
- **LOW:** No custom 429 handler — flask-limiter's default may include rate limit metadata. Consistent with Plan 01's error normalization: add `@app.errorhandler(429)` returning `{'error': 'rate limit exceeded'}`.
- **LOW:** No integration test specified for the 11th-request-returns-429 case.

**Suggestions:**
- **Critical fix before implementation:** Verify `get_remote_address` behavior behind Nginx. Add `RATELIMIT_FORWARDED_FOR = True` in limiter config or replace key_func with X-Forwarded-For extraction.
- Add `@app.errorhandler(429)` returning `{'error': 'rate limit exceeded'}` consistent with Plan 01
- Add integration test: POST /api/login 11 times in loop, assert 11th returns 429

**Risk: HIGH** (rate limiting silently fails in production — security goal not met)

### Agreed Concerns

**1. Dead Code References — Plans 01 + 03 [CRITICAL BEFORE EXECUTION]**
Both reviewers independently flagged that `app.js` (deleted in Phase 08.11) appears in the files lists and task descriptions of Plans 01 and 03. The success criteria for Plan 01 requires `sanitizeErrorMsg()` in app.js — if executed literally, the executor will either fail or recreate a deleted file.
- **Fix required:** Remove app.js from Plans 01 and 03 (files list, task actions, success criteria). Note deletion in 08.11.

**2. Reverse Proxy IP Issue — Plan 05 [CRITICAL BEFORE EXECUTION]**
Both reviewers independently raised that `get_remote_address` returns `127.0.0.1` on a reverse-proxied Nginx → Gunicorn deployment. The rate limiter becomes a global bucket for all users, effectively locking out the entire app after 10 login attempts.
- **Fix required:** Configure `ProxyFix` or use `X-Forwarded-For` / `X-Real-IP` in key_func before deploying Plan 05.

**3. Incomplete Email Hijacking Mitigation — Plan 06 [MEDIUM]**
Both reviewers noted that `email_confirmed=False` without a redirect-block is observational only — an attacker still has full app access. Decision required: either accept this as v1 telemetry (document explicitly) or add the redirect-block.
