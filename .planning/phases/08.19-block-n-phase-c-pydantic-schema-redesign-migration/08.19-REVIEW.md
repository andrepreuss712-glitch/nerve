# Phase 08.19: Code Review Report

**Reviewed:** 2026-04-27
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The Pydantic v2 schema redesign (`profile_schema.py`) is well-structured. The dual-schema pattern (Write `extra='forbid'` / Read `extra='ignore'`) is correct and the migration function is clean and idempotent. Tests are solid runtime-behaviour tests, not source-presence tests — compliant with CLAUDE.md test quality rules.

One critical finding: the `_showSaveToProfileDialog` PUT request in `pip-launcher.js` is missing the `X-CSRFToken` header. The app has CSRF protection enabled via Flask-WTF and all other mutating fetches in the same file include the token — this one does not, causing the request to be silently rejected (or if Flask-WTF exempts AJAX, leaving a CSRF gap).

Four warnings cover: a wizard validation gap that allows `unternehmensgroesse` values outside `UnternehmensgroesseEnum` to reach the DB without Pydantic validation; a client-side input-length mismatch on the precall form; a missing `db.rollback()` after `json.loads` failure in `bearbeiten()`; and an unhandled `None` path in `_showConsentModal` when `_showConsentModal` is called but all overlay elements are missing (silent no-op with no user feedback).

## Critical Issues

### CR-01: Missing CSRF token on Skript/Opener PUT in `_showSaveToProfileDialog`

**File:** `static/pip-launcher.js:652-656`
**Issue:** The `fetch` call that saves an edited Skript or Opener back to the profile sends a `PUT` request without the `X-CSRFToken` header. Every other mutating fetch in `pip-launcher.js` (lines 327, 887) includes `'X-CSRFToken': getCsrfToken()`. Flask-WTF's CSRF protection applies to all state-changing requests from the browser; this PUT will either be rejected with a 400 CSRF error (silently swallowed by `.catch(function () {})`) or — if Flask-WTF's AJAX exemption is active — represents an unfixed CSRF gap for authenticated sessions.

**Fix:**
```javascript
document.getElementById('lnr-save-yes').onclick = function () {
  fetch(endpoint, {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRFToken': getCsrfToken()   // ADD THIS
    },
    body: JSON.stringify({ inhalt: newText })
  }).catch(function () {});
  // ...
};
```

## Warnings

### WR-01: `wizard_create()` writes `unternehmensgroesse` to DB without Pydantic validation

**File:** `routes/profiles.py:126-148`
**Issue:** `wizard_create()` constructs the `daten` JSON dict directly and passes it to `json.dumps()` without running it through `ProfileSchema.model_validate()` first. The `unternehmensgroesse` value comes from `request.form.get('unternehmensgroesse', '').strip() or None` (line 126) and is written verbatim into `daten['zielkunde']['unternehmensgroesse']`. If a malformed POST contains a value outside `UnternehmensgroesseEnum` (e.g., via a crafted form submission), it bypasses the enum constraint and persists to the DB. The `bearbeiten()` POST (line 210) correctly runs `ProfileSchema.model_validate(_daten_neue)` — wizard_create should do the same.

**Fix:** After building the `daten` dict on line 128, validate it:
```python
from pydantic import ValidationError
_daten_obj = json.loads(daten)
try:
    ProfileSchema.model_validate(_daten_obj)
except ValidationError as _ve:
    flash(f"Profil-Daten ungültig — bitte Eingabe prüfen.", 'error')
    return redirect(url_for('profiles.wizard_page'))
```

### WR-02: Client-side `runPrecall()` accepts 2-char firmenname; backend rejects <3 chars — user sees silent error

**File:** `static/pip-launcher.js:300-303`
**Issue:** The JS validation in `runPrecall()` checks `firma.trim().length < 2` (rejects only 0-1 chars), but `precall_service.py:57` rejects `len(firmenname) < 3`. A user who types exactly 2 characters passes the client validation, the request is sent, and the backend returns an error string `"Firmenname muss zwischen 3 und 200 Zeichen lang sein"`. The error is shown via `sanitizeErrorMsg`, so the UX is not broken — but the off-by-one creates unnecessary server round-trips and a confusing user experience (passes client, rejected by server).

**Fix:**
```javascript
// line 300 — change < 2 to < 3
if (!firma || firma.trim().length < 3) {
```

### WR-03: Missing `db.rollback()` in `bearbeiten()` when `json.loads(daten_json)` fails silently on line 200

**File:** `routes/profiles.py:199-202`
**Issue:** In the POST path of `bearbeiten()`, if `json.loads(daten_json)` raises an exception on line 200, `_daten_neue` is set to `{}` and execution continues. However, at line 213, a `db.rollback()` is called only in the `ValidationError` branch. If `json.loads` fails, we continue with an empty dict, run migration on it, validate the (now-empty) schema, and then overwrite `p.daten` with `'{}'` on line 222. This silently destroys the user's existing profile data with no error shown. The fallback should abort, not silently zero out the profile.

**Fix:**
```python
try:
    _daten_neue = json.loads(daten_json) if daten_json else {}
except Exception:
    flash("Profil-Daten konnten nicht gelesen werden — bitte erneut versuchen.", 'error')
    db.rollback()
    return redirect(url_for('profiles.bearbeiten', pid=p.id))
```

### WR-04: `_showConsentModal` silently no-ops when DOM elements are missing

**File:** `static/pip-launcher.js:675`
**Issue:** `_showConsentModal` returns `undefined` without calling `callback` if any of the five DOM elements (`consent-overlay`, `consent-script`, `consent-btn-accept`, `consent-btn-reject`, `consent-btn-cancel`) is missing. The caller `startCall()` at line 867 relies on `callback('accepted')` to proceed. If the modal silently does nothing, the call never starts and there is no error shown to the user — the "Call starten" button appears to be broken. This is a real risk if the consent overlay markup is conditionally rendered or not included in a template.

**Fix:** Add a fallback when elements are missing:
```javascript
if (!overlay || !scriptEl || !acceptBtn || !rejectBtn || !cancelBtn) {
  console.error('[NerveLauncher] Consent modal DOM elements missing');
  // Fallback: treat as accepted or show an alert
  callback('cancelled');
  return;
}
```

## Info

### IN-01: `_migrate_profile_data` mutates its input dict in-place (undocumented aliasing risk)

**File:** `services/profile_schema.py:237`
**Issue:** The docstring says "Modifiziert daten in-place und gibt es zurueck (analog migrate_tabu_begriffe)". The in-place mutation is intentional and documented, but callers that pass a dict they expect to remain unchanged (e.g., a dict loaded from DB and cached) will find their cached value mutated. The `test_idempotent_zweiter_aufruf` test uses `.copy()` which shows the team is aware, but callers in `routes/profiles.py` (line 206, 240) do not `.copy()` before calling — they pass the dict directly, which is fine because they immediately write back, but it is a subtle contract. Consider adding `-> dict` return type annotation and noting the aliasing behaviour in the public docstring.

### IN-02: `precall_service.py` uses a bare global dict `_briefing_cache` — no thread-safety

**File:** `services/precall_service.py:18`
**Issue:** `_briefing_cache` is a plain `dict`. `recherche_firma` reads, writes, and deletes from it (lines 61-87) without any lock. The Flask app runs with `async_mode='threading'` (app.py line 45), meaning multiple threads can call `recherche_firma` concurrently. `dict` operations in CPython are individually GIL-protected, but the pattern of `stale_keys = [...]; for k in stale_keys: del _briefing_cache[k]` followed by a read and write is not atomic — a concurrent thread could delete a key between the staleness check and the `_briefing_cache[cache_key] = ...` write. The risk is low (worst case: a fresh briefing is lost or stale_keys delete races a concurrent insert) but worth noting for a future threading review.

### IN-03: Wizard branche values don't map to `VALID_BRANCHE` — all normalize to `'sonstiges'`

**File:** `templates/profile_wizard.html:268-318` / `routes/profiles.py:17-32`
**Issue:** The wizard branche chips use display values like `'Software/IT'`, `'Maschinenbau'`, `'Beratung'`, `'Finanzen/Versicherung'` etc. (template lines 268-317). The backend `VALID_BRANCHE` whitelist contains `'saas_b2b'`, `'maschinenbau'`, `'versicherung'`, `'finanzprodukte'`, `'immobilien'`, `'coaching'`, `'beratung'`, `'sonstiges'`. Every wizard-submitted branche value that doesn't exactly match (case-sensitive) falls through to `'sonstiges'`. For example `'Beratung'` (capital B) would map to `'sonstiges'` because the set check is case-sensitive and `'Beratung' not in VALID_BRANCHE`. `_normalize_branche` does `.strip()` but not `.lower()`. Functionally harmless (branche is still stored), but the wizard makes a selection that is silently overridden. The `bearbeiten()` editor presumably uses a proper enum-aligned select, so this is a wizard-only inconsistency.
