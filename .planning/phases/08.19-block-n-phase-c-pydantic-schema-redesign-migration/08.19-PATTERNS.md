```python
"""
services/profile_schema.py
────────────────────────────────────────────────────────────────────
Phase 08.19: Pydantic v2 ProfileSchema + idempotente Migration.

Exports:
  - ProfileSchema — Pydantic BaseModel fuer profil.daten JSON
  - _migrate_profile_data(daten: dict) -> dict
      Idempotent: v1 -> v2 upgrade. Prueft schema_version, loescht
      eliminierte Felder, setzt neue Defaults.
"""
from __future__ import annotations
from pydantic import BaseModel, ConfigDict
from typing import Optional, List, Literal

class BasisSchema(BaseModel):
    model_config = ConfigDict(extra='ignore')
    unternehmen: str = ''
    produktbeschreibung: str = ''
    branche: str = ''
    usps: List[str] = []
    # ... weitere Felder ...

class ProfileSchema(BaseModel):
    model_config = ConfigDict(extra='forbid')   # Write-Pfad: strict
    schema_version: int = 2
    basis: BasisSchema = BasisSchema()
    # ... weitere Sub-Schemas ...

def _migrate_profile_data(daten: dict) -> dict:
    """Idempotent: upgrade schema_version 1 -> 2."""
    if not isinstance(daten, dict):
        daten = {}
    version = daten.get('schema_version', 1)
    if version >= 2:
        return daten     # already migrated
    # v1 -> v2: remove eliminated fields, sync opener/pitch to ProfileOpener
    for key in ('opener', 'pitch'):
        daten.pop(key, None)
    zg = daten.get('zielgruppe', {})
    for b2c_key in ('alter', 'einkommensniveau', 'lebenssituation'):
        zg.pop(b2c_key, None)
    # ... further cleanup ...
    daten['schema_version'] = 2
    return daten
```

### idempotente DB-Column-Migration
**Source:** `app.py` lines 122-184 (the `_migrate()` function)
**Apply to:** `_migrate()` extension for any new `profiles` columns in 08.19 (none planned — `consent_text` column stays)

```python
# ── Migrate existing DB (add new columns if missing) ──────────────────────────
def _migrate():
    from sqlalchemy import text
    with engine.connect() as conn:
        for col, typedef in [
            ('some_new_col', 'TEXT'),
        ]:
            try:
                conn.execute(text(f'ALTER TABLE profiles ADD COLUMN {col} {typedef}'))
                conn.commit()
                print(f"[DB] Migration: added profiles.{col}")
            except Exception:
                pass

_migrate()   # called unconditionally at app startup (line 894)
```

**Key properties:**
- `try/except Exception: pass` swallows "column already exists" from SQLite
- `conn.commit()` inside the try block
- `print(f"[DB] Migration: ...")` log prefix convention
- `_migrate()` called at module level (line 894), after `init_db(engine)` (line 120)

## Key Observations for Planner

1. **`daten` dict structure is deeply nested** — existing code accesses `pdata.get('basis', {})`, `pdata.get('zielgruppe', {})`, `pdata.get('schmerzen', {})`, `pdata.get('ki', {})`, `pdata.get('kaufsignale', [])`, `pdata.get('uebergaenge', [])`, `pdata.get('wettbewerber', [])`. The Pydantic schema must cover all these namespaces.

2. **`zielgruppe.vorwissen` and `zielgruppe.entscheidungsverhalten`** are actively read in `services/claude_service.py` lines 229-230 — must survive in schema (whether as `zielgruppe.*` or renamed `zielkunde.*`). Do not eliminate.

3. **`opener`/`pitch` as top-level keys** in `profil_daten` are read at `services/precall_service.py` lines 150-151 — this is the exact read path to migrate to `ProfileOpener` table query.

4. **`profile_migration.py`** is the closest structural analog for `profile_schema.py` — same idempotent-migration-helper pattern, same module structure.

5. **`_migrate()` in `app.py`** runs at module load (line 894 = unconditional call after function definition). Any new data-level migration (`_migrate_profile_data`) for JSON fields should also be called at app startup — either inside `_migrate()` or as a separate `_data_migrate()` (pattern exists at line 1219).

6. **`wizard_create()` currently writes only `basis.*`, `ki.*`, `meta.*`** — no `zielkunde.*`, no `schema_version`. The new wizard must add `zielkunde.unternehmensgroesse` and `schema_version: 2`.

7. **`consent_text` dual-write** — `bearbeiten()` at line 178 already writes to `p.consent_text` (DB column). The 08.19 change adds a parallel write into `daten['meta']['consent_text']`. Read path gets a fallback: `daten.get('meta', {}).get('consent_text') or p.consent_text`.
