# Cross-AI Plan Review — Phase 08.19

---

## Gemini Review — Round 1 (2026-04-27T11:07:03Z)

Hier ist das Review der Pläne für Phase 08.19 (Pydantic Schema Redesign) basierend auf den NERVE-Architekturvorgaben.

### Plan 01: services/profile_schema.py

**Summary**
Definiert Pydantic-Modelle (v2) mit striktem Write- und tolerantem Read-Schema sowie eine idempotente Migrations-Funktion zur Bereinigung veralteter B2C-Felder.

**Strengths**
- `extra=forbid` (Write) vs `extra=ignore` (Read) ist ein exzellentes Pattern für Schema-Evolution ohne sofortige Crashes bei alten Daten.
- Idempotenz-Guard (`schema_version >= 2`) schützt sauber vor versehentlichen Mehrfach-Ausführungen.
- Beibehaltung von `ZielgruppeSchema` für den Training-Pfad sichert die Backwards-Compatibility für bestehende Prompts im `claude_service.py`.

**Concerns**
- **HIGH:** Wenn `extra=forbid` beim Schreiben greift, wirft Pydantic einen `ValidationError`. Wenn das Frontend unsaubere Daten schickt und dieser Fehler nicht sauber abgefangen wird, crasht die Route mit einem 500er-Fehler statt eines sauberen 400er für den User.
- **LOW:** Schwach typisierte Felder (`tabu_begriffe`, `phasen` als `List[dict]`) bleiben bestehen. Akzeptabel für diesen Block, aber lässt Typsicherheit ungenutzt.

**Suggestions**
- Sicherstellen, dass die Route (in Plan 03) `ValidationError` von Pydantic explizit abfängt und als HTTP 400 zurückgibt.

**Risk Assessment:** LOW

---

### Plan 02: app.py DB-Level Migration

**Summary**
Führt beim App-Start eine DB-Migration über alle Profile aus, lagert `opener`/`pitch` in die `ProfileOpener`-Tabelle aus und schreibt `consent_text` in das JSON (Dual-Write).

**Strengths**
- Per-Profile `try/except` verhindert, dass ein defektes Profil die gesamte Startup-Migration blockiert.
- Idempotenz auf Row-Level (`SELECT-before-INSERT` bei Opener).

**Concerns**
- **HIGH:** Multi-Worker Race-Condition. Wenn `app.py` von systemd/Gunicorn mit mehreren Workern gestartet wird, laufen die Migrationen parallel an. `SELECT-before-INSERT` ist nicht atomar. Das führt potenziell zu doppelten `ProfileOpener`-Einträgen für dasselbe Profil.
- **MEDIUM:** Der `consent_text` in der DB kann `NULL` sein. Wenn `NULL` in `daten.meta.consent_text` geschrieben wird, muss das Schema `None` zulassen.

**Suggestions**
- Die Migration im App-Startup mit einem einfachen File-Lock (`filelock`) absichern oder idealerweise als separates CLI-Kommando (`flask db-migrate-v2`) definieren, das im `deploy.sh` *vor* dem Restart der systemd-Worker ausgeführt wird.
- Explizites Handling für `consent_text IS NULL` ergänzen (Fallback auf leeren String oder Schema-Anpassung).

**Risk Assessment:** HIGH

### Plan 03: Read/Write Path Updates

**Summary**
Passt die Routen und das JS-Frontend an, um die neuen Schemata zu nutzen, Opener aus der DB zu lesen und den Dual-Write für `consent_text` umzusetzen.

**Strengths**
- Graceful Degradation im `precall_service.py` (sauberer Fallback wenn `profile_id=None`).
- Robuste Fallback-Kette im `pip-launcher.js` für den Consent-Text.

**Concerns**
- **HIGH:** In der `bearbeiten()` POST-Route wird `daten_json` aus dem Request als Dict geparst und gespeichert. Wenn das alte JS-Frontend beim Speichern noch Altlasten (`opener`, `pitch`) mitschickt, werden diese wieder in die DB geschrieben. Das Pydantic-Schema (`extra=forbid`) wirft dann sofort einen Fehler und das Speichern schlägt fehl.
- **MEDIUM:** Der Dual-Write im POST-Handler muss absolut konsistent sein (sowohl `p.consent_text` als auch das Feld im JSON müssen identisch geupdatet werden).

**Suggestions**
- `_migrate_profile_data()` MUSS zwingend auch im `bearbeiten()` POST-Handler aufgerufen werden, *bevor* das eingehende JSON validiert oder in die DB geschrieben wird. So werden Frontend-Altlasten on-the-fly weggeschnitten und das Schema bleibt sauber.

**Risk Assessment:** HIGH

### Plan 04: templates/profile_wizard.html UI Update

**Summary**
Erweitert den Profil-Wizard in Schritt 2 um eine Chip-Select-Komponente für die Unternehmensgröße inklusive Validierung.

**Strengths**
- Wiederverwendung bestehender UI-Patterns (`.einwand-chip` CSS).
- Clientseitige Validierung (Outline-Flash) verhindert fehlerhafte Step-Transitions.

**Concerns**
- **LOW:** Pre-filling bei Page Reload oder Zurück-Navigieren. Der Plan beschreibt, wie das hidden-Input gesetzt wird, aber nicht, wie der Zustand beim Laden aus dem hidden-Input in die UI (welcher Chip ist aktiv?) wiederhergestellt wird.

**Suggestions**
- Im JS einen Initialisierungs-Check einbauen: Beim Laden des DOMs prüfen, ob das hidden-Input einen Wert hat, und dem entsprechenden Chip initial die `active`-Klasse zuweisen.

**Risk Assessment:** LOW

## Gemini Review — Round 2 (2026-04-27)

### 1. Summary
The proposed implementation plans provide a solid, well-sequenced roadmap for migrating NERVE from a B2C-leaning data model to a strict B2B focus. The separation of concerns across the four plans—schema definition (Plan 01), database migration (Plan 02), application logic updates (Plan 03), and frontend UI (Plan 04)—is logical and handles the tricky requirements of dual-writing and idempotency well. However, there are significant risks regarding where the database migration is executed and a critical missing step in the new profile creation flow that could lead to data loss for new users.

### 2. Strengths
* **Safe Validation Strategy (Plan 01/03):** Using `extra='forbid'` for writes ensures no legacy B2C data sneaks back into the DB, while `extra='ignore'` on reads prevents application crashes if old data exists. Catching `ValidationError` to return a 400 instead of a 500 is excellent for UX.
* **Idempotency & Granularity (Plan 02):** Wrapping the DB migration in a per-profile `try/except` block prevents a single malformed profile from cascading and breaking the entire migration process. Checking `schema_version >= 2` ensures the script can be rerun safely.
* **Data Preservation Order (Plan 02):** Extracting `opener` and `pitch` *before* passing the JSON to `_migrate_profile_data()` correctly prevents the migration utility from deleting the data before it can be synced to the new `ProfileOpener` table.
* **UI Consistency (Plan 04):** Reusing the existing `.einwand-chip` CSS pattern for the new `unternehmensgroesse` field saves time, keeps the prototype lean, and adheres to the bootstrap budget constraint (no new libraries/frameworks).

### 3. Concerns
* **[HIGH] Missing `ProfileOpener` Insert in Wizard (Plan 03):** The plan states that `wizard_create()` will remove `opener/pitch` from the JSON. However, it does *not* explicitly state that `wizard_create()` will insert this generated data into the new `ProfileOpener` table. If omitted, new profiles created via the wizard will silently lose their opener/pitch.
* **[HIGH] Migration Execution Context (Plan 02):** Running heavy database migrations with advisory locks inside `app.py` (presumably on application startup) is a major anti-pattern. In a multi-worker WSGI setup (e.g., Gunicorn), this can cause worker boot timeouts, race conditions, or DB connection exhaustion before the app even starts serving traffic.
* **[MEDIUM] Cross-Database Locking Logic (Plan 02):** Branching code to handle both SQLite (`EXCLUSIVE`) and PostgreSQL (`pg_advisory_xact_lock`) dynamically is complex and brittle. If this is a solo-founder project pre-launch, this level of custom dual-database lock management introduces unnecessary maintenance overhead.
* **[LOW] Enum Syncing (Plan 01 & 04):** The UI chips in Plan 04 ("<10", "10-50", etc.) must perfectly match the string values of the Pydantic Enum in Plan 01. A mismatch here will cause silent validation failures (HTTP 400) during the Step 2→3 transition in the wizard.

### 4. Suggestions
* **Decouple the Data Migration:** Move `_migrate_profile_json()` out of `app.py` startup. Instead, create a Flask CLI command (e.g., `flask migrate-profiles-v2`). This allows you to run the migration manually during deployment without blocking app startup or requiring complex advisory locks.
* **Update `wizard_create()` Logic:** Explicitly add a step in Plan 03 for `wizard_create()` to instantiate a SQLAlchemy `ProfileOpener` model and commit it to the database alongside the new `Profile` record in the same transaction.
* **Transaction Safety for Dual-Writes:** In `bearbeiten()` POST (Plan 03), ensure that updating the `consent_text` JSON field and the DB column happens within a single `db.session.commit()`. If one fails, both should roll back.
* **Shared Constants for Enums:** Define the `unternehmensgroesse` values in a central Python constants file and inject them into `profile_wizard.html` via Jinja2 rather than hardcoding them in the HTML/JS.

### 5. Risk Assessment
**MEDIUM RISK.** 
The architectural thinking is very sound, but the execution details contain a few hazardous traps. The highest risks stem from attempting to run a locking database data-migration inside the app initialization (`app.py`), and the gap in the `wizard_create()` flow that could cause data loss. If the migration logic is moved to a CLI command and the `ProfileOpener` creation is properly handled in the wizard, the risk profile of this phase drops to LOW.

## Consensus Summary (Round 1 + Round 2)

### Agreed Strengths
- `extra=forbid` (Write) / `extra=ignore` (Read) Pydantic-Pattern — beide Rounds loben dieses Design.
- Idempotenz-Guards (`schema_version >= 2`, `SELECT-before-INSERT`) auf allen Ebenen.
- Per-Profile `try/except` im Startup verhindert Cascade-Failures.
- Beibehaltung von `ZielgruppeSchema` für Training-Pfad sichert Backwards-Compatibility.
- Graceful Degradation in `precall_service.py` (profile_id=None Fallback).
- UI: Wiederverwendung bestehender `.einwand-chip` CSS-Pattern.

### Agreed Concerns (beide Rounds einig)

**HIGH — bereits in Plans adressiert (Reviews v2):**
1. **ValidationError als 500er (Plan 01/03):** Pydantic `ValidationError` muss in der Route als HTTP 400 gefangen werden. → **Plan 03 Finding 3 adressiert das bereits explizit.**
2. **Frontend-Altlasten im POST-Handler (Plan 03):** `_migrate_profile_data()` vor Validation im bearbeiten() POST. → **Plan 03 Finding 2 adressiert das bereits explizit.**
3. **NULL consent_text (Plan 02):** NULL → leerer String beim Dual-Write. → **Plan 02 Finding 4 (`_db_consent or ''`) adressiert das bereits.**

**HIGH — NEU aus Round 2 (noch nicht in Plans):**
4. **Missing ProfileOpener Insert in wizard_create() (Plan 03):** Wizard entfernt opener/pitch aus JSON — aber fügt es NICHT in ProfileOpener-Tabelle ein für *neue* Profile. Plan 02 migriert nur *bestehende* Profile. Neue Profile über Wizard haben keinen Opener in ProfileOpener → precall_service.py findet nichts.
5. **Advisory-Lock Komplexität (Plan 02):** SQLite/PostgreSQL dual-lock-Logik ist Overkill für Pre-Launch mit 4 Profilen. Risiko: Bugs in Lock-Code blockieren App-Start.

**MEDIUM:**
6. **Enum-Sync UI↔Backend (Plan 01/04):** Chip-Werte in HTML müssen exakt den Pydantic Literal-Werten entsprechen. Kein Jinja2-Inject geplant — manuelle Sync-Pflicht.
