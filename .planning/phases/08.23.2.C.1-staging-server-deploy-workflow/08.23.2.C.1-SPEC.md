# Phase 08.23.2.C.1: Staging-Server + Deploy-Workflow — Specification

**Created:** 2026-05-19
**Ambiguity score:** 0.10 (gate: ≤ 0.20)
**Requirements:** 11 locked

## Goal

`staging.getnerve.app` (Hetzner CX32) wird als 1:1-Spiegel von Production aufgesetzt; `deploy.sh` bekommt einen TARGET-Parameter (`staging`/`production`) wobei `production` automatisch blockt wenn Staging rot, alt (>24h) oder auf falschem Commit steht.

## Background

Heute existiert ein einzelner Hetzner-VPS (`178.104.82.166`, CX32 seit 14.05.2026) der `getnerve.app` bedient. `deploy.sh` deployt direkt auf Production via tar-over-SSH ohne Staging-Zwischenstufe. Bugs in Phase 08.23.2.C Plan 07 (PiP Ctrl+G/Ctrl+E/UWG-Banner) konnten nicht lokal getestet werden da lokales Windows-SQLite-Setup nie 1:1-Production-Linux-Postgres-Spiegel ist — Anti-Drift-Entscheidung 2026-05-19. Staging ist die strukturelle Lösung, nicht Lokal-Fix.

**Was fehlt heute:**
- Zweiter Hetzner-Server für Staging
- `deploy.sh staging` Target
- `deploy.sh production` Pre-Deploy-Gate (Staging muss grün sein)
- `/api/health` kennt keine `git_head`/`deployed_at` Felder
- Kein `scripts/refresh_staging_from_production.sh`
- Kein `scripts/reset_sequences.py`
- Alembic-Auto-Hook in `app.py` für lokale SQLite-Entwicklung fehlt
- Phase 08.23.2.C Plan 07 Task 4 (PiP Live-Test) noch nicht durchgeführt

## Requirements

1. **Staging-Server erreichbar mit SSL**: `staging.getnerve.app` antwortet auf HTTPS mit gültigem Let's Encrypt-Zertifikat.
   - Current: Zweiter Server existiert nicht
   - Target: Hetzner CX32, Debian/Ubuntu, nginx + gunicorn (gthread, 1 Worker, gleiche Konfiguration wie Production), SSL via Certbot/Let's Encrypt für `staging.getnerve.app`
   - Acceptance: `curl -fsS https://staging.getnerve.app/api/health` gibt HTTP 200 zurück mit `{"status": "ok"}` (plus neue Felder)

2. **deploy.sh TARGET-Parameter**: `deploy.sh` akzeptiert `staging` oder `production` als erstes Argument.
   - Current: `deploy.sh` deployt hardcoded auf `root@178.104.82.166` (Production)
   - Target: `deploy.sh staging` deployt auf Staging-VPS mit SSH-Key `~/.ssh/nerve_staging`; `deploy.sh production` deployt auf Production mit `~/.ssh/nerve_vps`; kein Default-Argument (Fehler wenn keines gesetzt)
   - Acceptance: `./deploy.sh staging` deployt auf Staging-IP; `./deploy.sh production` deployt auf Production-IP; `./deploy.sh` ohne Argument bricht mit Fehlermeldung ab

3. **Staging-Meta nach Deploy schreiben**: `deploy.sh staging` schreibt nach erfolgreichem Deploy eine Meta-Datei auf dem Staging-Server.
   - Current: Kein Deploy-Meta existiert
   - Target: `deploy.sh staging` schreibt nach Restart `/opt/nerve/.deploy_meta` auf Staging mit `GIT_HEAD=$(git rev-parse HEAD)` und `DEPLOYED_AT=$(date -u +%Y-%m-%dT%H:%M:%SZ)`
   - Acceptance: Nach `deploy.sh staging` existiert `/opt/nerve/.deploy_meta` auf Staging mit aktuellem Commit-SHA und Timestamp (via SSH prüfbar)

4. **/api/health-Extension**: Der `/api/health`-Endpoint gibt `git_head` und `deployed_at` zurück.
   - Current: `/api/health` gibt `{"status": "ok", ...}` ohne Deploy-Meta
   - Target: App liest `.deploy_meta` beim Start (falls vorhanden) und exponiert `git_head` und `deployed_at` in der Health-Response; fehlt die Datei → beide Felder sind `null`
   - Acceptance: Nach `deploy.sh staging` gibt `https://staging.getnerve.app/api/health` ein JSON zurück das `git_head` (40-stelliger SHA) und `deployed_at` (ISO-8601-String) enthält

5. **Production Pre-Deploy-Gate**: `deploy.sh production` blockt automatisch wenn Staging nicht bereit ist.
   - Current: Production-Deploy läuft ohne Staging-Prüfung durch
   - Target: `deploy.sh production` macht vor dem Deploy einen `curl`-Call auf `https://staging.getnerve.app/api/health` und prüft drei Bedingungen: (a) `status == "ok"`, (b) `deployed_at` Alter < 24h, (c) `git_head == $(git rev-parse HEAD)`; schlägt eine Bedingung fehl → Exit mit erklärender Fehlermeldung
   - Acceptance: Test-Szenarien: (a) Staging-Health gibt `status: "error"` → Production-Deploy bricht ab mit "[deploy] BLOCKER: Staging not healthy"; (b) `deployed_at` ist 25h alt → Abbruch mit "[deploy] BLOCKER: Staging deploy older than 24h"; (c) `git_head` weicht ab → Abbruch mit "[deploy] BLOCKER: Local HEAD != Staging HEAD"

6. **DB-Refresh-Skript**: `scripts/refresh_staging_from_production.sh` synchronisiert Production-DB auf Staging in < 10 Minuten.
   - Current: Kein Skript existiert
   - Target: Skript (a) zeigt Bestätigungs-Prompt `[y/N]`, (b) erstellt Pre-Refresh-Backup auf Staging (`/opt/nerve/backups/pre-refresh-TIMESTAMP.sql.gz`), (c) streamt `pg_dump` von Production direkt nach Staging via SSH-Pipe (kein temporäres Dump auf lokalem Rechner), (d) ruft anschließend `reset_sequences.py` auf
   - Acceptance: Skript läuft durch ohne Fehler; nach Abschluss lässt sich auf Staging per `psql -U nerve -c "SELECT COUNT(*) FROM users"` die gleiche User-Anzahl wie auf Production abfragen; Laufzeit < 10 Minuten bei aktuellem DB-Größe

7. **reset_sequences.py**: Neues Skript setzt alle Postgres-Sequences auf `MAX(id)+1`.
   - Current: Logik existiert nur eingebettet in `scripts/migrate_to_postgres.py` (Phase A)
   - Target: `scripts/reset_sequences.py` ist eigenständiges ~20-30-Zeilen-Python-Skript das alle Sequences in der konfigurierten DB auf `SELECT MAX(id)+1` setzt; idempotent
   - Acceptance: `python scripts/reset_sequences.py` läuft ohne Fehler durch; nach einem DB-Insert auf Staging gibt es keinen "duplicate key violates unique constraint"-Fehler auf der `users`-Sequence

8. **Staging-Schutz**: Staging ist nicht öffentlich indexierbar und hinter HTTP-Basic-Auth.
   - Current: Kein Schutz für Staging-Server geplant
   - Target: (a) nginx auf Staging serviert `/robots.txt` mit `Disallow: /`; (b) nginx auf Staging hat HTTP-Basic-Auth vor allen Routen (Credentials dokumentiert in `.env.staging.example`)
   - Acceptance: `curl -fsS https://staging.getnerve.app/robots.txt` enthält `Disallow: /`; `curl -fsS https://staging.getnerve.app/` gibt HTTP 401 zurück ohne Basic-Auth-Header

9. **Deferred PiP Live-Test (AC4)**: Phase 08.23.2.C Plan 07 Task 4 wird auf Staging abgenommen.
   - Current: Live-PiP-Test auf Production deferred (Phase 08.23.2.C Plan 07 Kommentar)
   - Target: André führt manuellen Browser-Test auf `staging.getnerve.app/live` durch
   - Acceptance: (1) Ctrl+G zeigt Gatekeeper-Buttons + Vorzimmer-Indikator; (2) Ctrl+E wechselt zurück zu Standard-EWB-Buttons; (3) `_showUwgBanner('Test-UWG-Phrase')` in Browser-Console triggert rotes UWG-Banner; (4) keine JS-Fehler in Browser-Console während aller drei Schritte

10. **Alembic-Auto-Hook lokal (SQLite)**: `app.py` führt beim Start automatisch `alembic upgrade head` aus wenn DATABASE_URL auf SQLite zeigt.
    - Current: Kein Auto-Hook; lokale SQLite-DB muss manuell auf Stand gebracht werden
    - Target: Hook in `app.py` prüft beim Start ob `DATABASE_URL` mit `sqlite://` beginnt; falls ja → `alembic upgrade head` ausführen (idempotent durch Alembic's `alembic_version`-Tabelle); Postgres wird übersprungen (Production-Alembic läuft via `deploy.sh`)
    - Acceptance: Nach `python app.py` auf lokaler SQLite-Umgebung läuft `SELECT mode FROM phrases LIMIT 1` ohne SQL-Error; `app.py` startet 30 Sekunden ohne Crash

11. **CSRF-Workaround unverändert**: Der bestehende CSRF-Patch in `app.py` (Z.54-58, Commit aae9aa8) bleibt unberührt.
    - Current: `WTF_CSRF_ENABLED=False` in `.env` schaltet CSRF lokal ab; Patch in `app.py` Z.54-58
    - Target: C.1 macht keine Änderungen an diesem Patch; keine Refaktorierung auf `FLASK_ENV`-basierte Lösung
    - Acceptance: `git diff aae9aa8 -- app.py` zeigt keine Änderungen an Z.54-58 (CSRF-Block)

## Boundaries

**In scope:**
- Hetzner CX32-Server-Provisionierung für `staging.getnerve.app` (OS-Setup, Postgres, nginx, gunicorn, Certbot)
- SSH-Key `~/.ssh/nerve_staging` (neuer separater Key, Anleitung in Plan)
- `deploy.sh` Refactor: TARGET-Parameter (`staging`/`production`) mit getrennten SSH-Keys und VPS-IPs
- `deploy.sh staging`: schreibt `.deploy_meta` nach erfolgreichem Deploy
- `/api/health`-Extension: `git_head` + `deployed_at` Felder (liest `.deploy_meta`)
- `deploy.sh production`: Pre-Deploy-Gate mit 3 Staging-Checks via curl+jq
- `scripts/refresh_staging_from_production.sh` (neues Skript)
- `scripts/reset_sequences.py` (neues Skript, extrahiert aus `migrate_to_postgres.py`)
- nginx-Konfiguration Staging: HTTP-Basic-Auth + robots.txt noindex
- Alembic-Auto-Hook in `app.py` (SQLite-only, Postgres-skip)
- Manueller PiP-Live-Test (AC4) auf Staging nach Deploy

**Out of scope:**
- GitHub Actions CI/CD — Setup-Aufwand unverhältnismäßig bei Pre-Launch-Deploy-Frequenz; deferred als Mini-Phase 08.23.2.C.1.1 mit Trigger "Push-Frequenz >5/Woche"
- Nightly Cron-Refresh der Staging-DB — deferred bis Early-Access aktiv und Production-Daten täglich wachsen
- DSGVO-konformer Anonymisierungs-Umbau beim DB-Refresh — wird Pflicht beim ersten externen User; dokumentiert in Vault DSGVO Analyse.md Sektion 8
- Backup-Cron für Staging-Server — Staging-Daten sind expendable, kein Backup-Bedarf
- Automatisierte Playwright/Selenium-Tests für PiP — One-Off-Test, manuelle Abnahme reicht Pre-Launch
- CSRF-Refaktorierung (FLASK_ENV-basierte Lösung) — separate Folge-Phase falls je benötigt
- Monitoring/Alerting auf Staging — deferred (SCALE-03 in REQUIREMENTS.md)
- GLiNER-Corpus-Erstellung (gatekeeper_classifier_corpus.json) — separates Thema aus Phase 08.23.2.C

## Constraints

- **Server-Parität**: Staging-Server muss immer gleichen Hetzner-Plan wie Production haben (aktuell CX32, 8GB RAM). GLiNER + spaCy erfordern ≥6GB RAM. Wenn Production auf CX42 upgraded → Staging ebenfalls.
- **SSH-Key-Trennung**: Staging nutzt `~/.ssh/nerve_staging`, Production `~/.ssh/nerve_vps`. Kein Key-Sharing — Kompromittierung eines Servers darf anderen nicht gefährden.
- **jq-Dependency**: `deploy.sh production` Pre-Deploy-Gate benötigt `jq` im Deploy-Environment (Git Bash auf Windows). Pflicht-Constraint: `which jq || { echo "[deploy] ERROR: jq not installed"; exit 1; }` als erstes im production-Block.
- **Stream-Pipe ohne lokale Dump-Datei**: `refresh_staging_from_production.sh` darf keine Postgres-Dump-Datei auf André's lokaler Maschine erstellen (DSGVO-Hygiene + Bandbreite). Nur SSH-Pipe.
- **DSGVO-Trigger**: Solange kein externer Early-Access-User registriert ist, ist 1:1-Kopie der Production-DB auf Staging DSGVO-konform (beide Server EU-Frankfurt, Daten sind André-Test-Daten + post-Phase-B-anonymisierte Anrufe). Sobald erster externer User registriert → `refresh_staging_from_production.sh` muss anonymisieren. Trigger dokumentieren in `Nerve-Vault/04 Entscheidungen/NERVE DSGVO Analyse.md` Sektion 8.
- **Alembic-Auto-Hook SQLite-only**: Hook in `app.py` darf `alembic upgrade head` NUR ausführen wenn `DATABASE_URL` mit `sqlite://` beginnt. Postgres-DBs werden von `deploy.sh` verwaltet, nie von `app.py`.
- **CSRF-Patch unberührt**: `app.py` Z.54-58 (Commit aae9aa8) wird in C.1 nicht angefasst.
