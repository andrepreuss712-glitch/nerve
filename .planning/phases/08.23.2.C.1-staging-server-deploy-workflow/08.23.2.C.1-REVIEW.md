## Warnings

### WR-01: deploy.sh — `.deploy_meta` line 183 writes literal `$(date ...)` string instead of executing it

**File:** `deploy.sh:183`

**Issue:** The `.deploy_meta` file is written inside a `<< ENDHEREDOC` block (unquoted heredoc), which means the local shell expands `$TARGET`, `$GIT_HEAD_LOCAL`, and `$SERVICE_NAME` before sending the script to the remote. However, `\$(date -u +%Y-%m-%dT%H:%M:%SZ)` has the `$` escaped with a backslash to prevent local expansion. On the remote side the backslash is consumed by the heredoc send, so the remote bash sees:

```bash
echo "DEPLOYED_AT=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> /opt/nerve/.deploy_meta
```

This is actually correct — the remote shell executes `date`. BUT the preceding line:

```bash
echo "GIT_HEAD=$GIT_HEAD_LOCAL" > /opt/nerve/.deploy_meta
```

uses `>` (overwrite), and the DEPLOYED_AT line uses `>>` (append). If the first `echo` fails for any reason the second still runs (both are separate commands, not connected with `&&`). More importantly, `set -e` is active inside the heredoc, so a failure of the first echo does abort — this part is actually fine. **The real bug**: `\$(date ...)` is correct escaping for heredoc, but the comment on line 183 says "DEPLOYED_AT=\$(date ...)" which makes readers think it writes a literal string. Verify behaviour to avoid confusion. Run a smoke test: after deploy, check that `/opt/nerve/.deploy_meta` contains an actual ISO timestamp, not the literal string `$(date -u +%Y-%m-%dT%H:%M:%SZ)`.

**Fix:** Add a verification step after deploy, or use an explicit intermediate variable before the heredoc to make intent unambiguous:

```bash
# Before the heredoc:
DEPLOYED_AT_VAL=$(date -u +%Y-%m-%dT%H:%M:%SZ)

# Inside the heredoc (both lines use >):
echo "GIT_HEAD=$GIT_HEAD_LOCAL" > /opt/nerve/.deploy_meta
echo "DEPLOYED_AT=$DEPLOYED_AT_VAL" >> /opt/nerve/.deploy_meta
```

This eliminates ambiguity entirely and makes the escaping strategy obvious.

### WR-02: deploy.sh — `$SERVICE_NAME` inside unquoted heredoc expands locally but is used remote

**File:** `deploy.sh:187`

**Issue:** Line 187 inside the `<< ENDHEREDOC` block is:

```bash
sudo systemctl restart $SERVICE_NAME
```

Because the heredoc delimiter `ENDHEREDOC` is **unquoted**, `$SERVICE_NAME` is expanded by the **local** shell before the script is sent to SSH. This works correctly as long as `SERVICE_NAME` is set in the local shell at that point — and it is (set on line 64 or 69). However, the same heredoc block escapes remote variables with `\$` (e.g., `\$PYTEST_EXIT`, `\$?`) but leaves `$SERVICE_NAME` and `$TARGET` unescaped intentionally. This inconsistency is a latent readability/maintenance trap: a future editor adding a new local variable inside the heredoc without the `\$` prefix would silently pass an empty string to remote.

**Fix:** Document the escaping convention explicitly above the heredoc, or switch the heredoc to a quoted form (`<< 'ENDHEREDOC'`) for the remote-only parts and pass local values as environment variables via `ssh ... VAR=val bash -s`:

```bash
ssh -i "$SSH_KEY" "$VPS_HOST" TARGET="$TARGET" SERVICE_NAME="$SERVICE_NAME" GIT_HEAD_LOCAL="$GIT_HEAD_LOCAL" bash -s << 'ENDHEREDOC'
  # All $ references now always refer to remote-side variables
  sudo systemctl restart $SERVICE_NAME
ENDHEREDOC
```

This is the safer pattern — no mixed escaping, no risk of silent empty-variable expansion.

### WR-03: `refresh_staging_from_production.sh` — Large DB dumps stored in a shell variable risk silent truncation or OOM

**File:** `scripts/refresh_staging_from_production.sh:67-68`

**Issue:** The entire `pg_dump` output is captured into a bash variable `DUMP`:

```bash
DUMP=$(ssh -i "$PROD_SSH_KEY" ... "pg_dump -U nerve_app --no-owner --no-acl $DB_NAME 2>/dev/null")
```

Bash variables have no built-in size limit but storing multiple megabytes of SQL in a variable is fragile:
1. On some systems the subshell command substitution can fail silently for very large outputs (limits vary by OS and ulimit settings).
2. The `2>/dev/null` suppresses all pg_dump stderr output including actual errors (connection failures, permission errors). If pg_dump exits non-zero the variable will be empty or partial, but the `DUMP_SIZE` check only catches the empty-variable case — a partial dump larger than 1 KB passes the guard.
3. Passing a large variable via `echo "$DUMP" | ssh ... psql` re-invokes the shell, which may add a trailing newline or silently truncate depending on the shell version.

The size guard (line 72-77) catches the extreme case but not a corrupt partial dump.

**Fix:** Use a true SSH pipe without intermediate variable storage — this is both safer and more memory-efficient. Remove the `2>/dev/null` so pg_dump errors are visible:

```bash
ssh -i "$PROD_SSH_KEY" -o StrictHostKeyChecking=accept-new "$PROD_HOST" \
  "pg_dump -U nerve_app --no-owner --no-acl $DB_NAME" \
  | ssh -i "$STAGING_SSH_KEY" -o StrictHostKeyChecking=accept-new "$STAGING_HOST" \
    "psql -U nerve_app $DB_NAME"
```

If the DSGVO constraint requires the data never to leave both SSH tunnels simultaneously, the current in-memory approach is acceptable — but then remove `2>/dev/null` and add `|| { echo "pg_dump failed"; exit 1; }` after the command substitution.

### WR-04: `api_health` — deploy_meta path is hardcoded to `/opt/nerve/.deploy_meta` with no fallback for production

**File:** `routes/app_routes.py:1394`

**Issue:** The health endpoint reads:

```python
deploy_meta_path = '/opt/nerve/.deploy_meta'
```

The deploy script only writes this file for staging (`if [[ "$TARGET" == "staging" ]]`, line 181). For production the file is never written, so `git_head` and `deployed_at` are always `null` in the production health response. This is intentional by design, but the production deploy gate (deploy.sh line 54-58) checks `STAGING_HEAD != LOCAL_HEAD` — relying entirely on staging returning a non-null `git_head`. If the staging `.deploy_meta` write ever fails silently (e.g., permission error caught by `set -e` abort before that line), the production gate will block with `BLOCKER: Staging hat kein deployed_at` rather than a meaningful message.

Additionally, the OSError catch on line 1403 is correct, but a malformed `.deploy_meta` (e.g., a line without `=`) silently yields `git_head=None` with no log message. This makes debugging a failed production gate much harder.

**Fix:** Add a log line when the file exists but parsing yields no values:

```python
try:
    with open(deploy_meta_path, 'r') as _f:
        for _line in _f:
            _line = _line.strip()
            if _line.startswith('GIT_HEAD='):
                git_head = _line[len('GIT_HEAD='):]
            elif _line.startswith('DEPLOYED_AT='):
                deployed_at = _line[len('DEPLOYED_AT='):]
    if git_head is None and deployed_at is None:
        print(f'[Health] .deploy_meta exists but contained no parseable values')
except (OSError, IOError):
    pass  # local dev — expected
```

Also consider writing `.deploy_meta` for production deploys too (with different key names if needed), so production health responses are symmetrically useful for monitoring.

### IN-01: `setup_staging.sh` — missing `set -o pipefail`

**File:** `scripts/setup_staging.sh:6`

**Issue:** The script uses `set -e` but not `set -o pipefail`. Several commands pipe through `grep` (lines 46-50). If `psql` succeeds but `grep -q 1` fails (e.g., role already exists but output format differs), the overall pipe exits non-zero and `set -e` aborts the idempotent check. Conversely, if `psql` returns an error but `grep` exits 0, the error is hidden. `pipefail` would make the failure detection consistent.

**Fix:** Change line 6 from `set -e` to `set -eo pipefail`.

### IN-02: `nginx-production.conf` — `/api/health` endpoint not present, no unauthenticated health check possible on production

**File:** `deploy/nginx-production.conf`

**Issue:** The staging nginx config has an explicit `location = /api/health { auth_basic off; ... }` block. Production has no equivalent. While production does not use Basic-Auth, production does not expose a dedicated health location block at all. This is not a security issue, but means the health endpoint on production has no nginx-level caching or independent routing — it goes through the generic `location /` block. For symmetry and future monitoring (e.g., an external uptime checker hitting `/api/health`), a dedicated location block is advisable.

**Fix:** Add to `nginx-production.conf`:

```nginx
location = /api/health {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### IN-03: `alembic/env.py` — `render_as_batch=True` applied globally including Postgres

**File:** `alembic/env.py:30,47`

**Issue:** `render_as_batch=True` is set in both `run_migrations_offline()` and `run_migrations_online()` unconditionally. This flag is designed for SQLite which does not support `ALTER TABLE`. For Postgres, it causes Alembic to use a CREATE+COPY+DROP pattern even for simple column additions where native `ALTER TABLE ADD COLUMN` would be faster and safer (no table lock during copy). On a production Postgres DB with large tables this could cause avoidable lock contention.

**Fix:** Conditionally set `render_as_batch` based on the database dialect:

```python
_use_batch = db_url.startswith('sqlite')

# In run_migrations_offline():
context.configure(
    ...
    render_as_batch=_use_batch,
)

# In run_migrations_online():
context.configure(
    ...
    render_as_batch=_use_batch,
)
```

### IN-04: `deploy.sh` — hardcoded production IP address in source

**File:** `deploy.sh:62`

**Issue:** Production server IP `178.104.82.166` is hardcoded on line 62, and staging IP `178.104.245.8` on line 68. Similarly, `refresh_staging_from_production.sh` hardcodes both IPs on lines 29-31. These IPs are not secrets, but hardcoded infrastructure values are a maintenance liability if the server is migrated. The staging IP is partially mitigated in `refresh_staging_from_production.sh` via `STAGING_IP` env-var override (line 31), but `deploy.sh` has no such override.

**Fix:** For `deploy.sh`, accept optional env-var overrides:

```bash
VPS_HOST="${PROD_HOST_OVERRIDE:-root@178.104.82.166}"
# ... and for staging:
VPS_HOST="${STAGING_HOST_OVERRIDE:-root@178.104.245.8}"
```

This is a low-priority improvement but prevents hard changes across two files on server migration.
