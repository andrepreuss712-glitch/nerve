### refresh_staging_from_production.sh

```bash

# Nach Hetzner-Provisionierung (STAGING_IP in Skript ersetzen):
```

Das Skript fuehrt 3 Schritte aus:
1. **Pre-Refresh-Backup auf Staging** — `pg_dump | gzip > /opt/nerve/backups/pre-refresh/pre-refresh-<TIMESTAMP>.sql.gz`
2. **SSH-Pipe Production→Staging** — Dump in RAM-Variable, DUMP_SIZE-Check, dann `echo "$DUMP" | ssh staging psql`
3. **Sequence-Reset auf Staging** — `DATABASE_URL=... /opt/nerve/venv/bin/python .../reset_sequences.py`

### reset_sequences.py (direkt auf Staging-Server)

```bash
DATABASE_URL=postgresql://nerve_app@/nerve /opt/nerve/venv/bin/python /opt/nerve/app/scripts/reset_sequences.py
```

## REVIEW-HIGH-3 Fix — Bestaetigung

**Problem:** Die urspruengliche SSH-Pipe `ssh prod 'pg_dump' | ssh staging 'psql'` gibt Exit-Code von psql (letztem Befehl) zurueck — psql kann mit exit 0 enden obwohl pg_dump mid-stream abgebrochen hat. Ergebnis: leere oder korrupte Staging-DB ohne Fehlermeldung.

**Implementierte Loesungen:**

| Massnahme | Implementierung | Schutz |
|---|---|---|
| `set -eo pipefail` | Zeile 22 (erste ausfuehrbare Zeile) | Pipe schlaegt fehl wenn irgendein Segment fehlschlaegt |
| DUMP_SIZE-Check | `DUMP_SIZE=${#DUMP}; if [[ $DUMP_SIZE -lt 1024 ]]; then ABORT` | Exit 1 bei leerem/korruptem Dump vor psql-Import |
