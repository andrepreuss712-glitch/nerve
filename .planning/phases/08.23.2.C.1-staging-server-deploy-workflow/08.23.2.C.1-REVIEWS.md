# Cross-AI Plan Review — Phase 08.23.2.C.1: Staging-Server + Deploy-Workflow

---

## Gemini Review

### 1. Summary

The implementation plans provide a solid and pragmatic foundation for a staging environment and safe deployment pipeline, well-suited for a solo-founder setup. The strategic use of a "deployment gate" requiring a fresh, matching staging environment before touching production is excellent. However, there are critical logical conflicts regarding HTTP Basic Auth, sequencing issues with the metadata file, and data corruption risks in the SSH pipe that must be resolved prior to execution to prevent immediate pipeline failures.

### 2. Strengths

- **Production Safeguards:** The deployment gate (24h freshness, git HEAD match) is a highly effective, low-overhead mechanism to enforce staging validation before production rollouts.
- **Idempotency:** Using `psql -tAc` patterns in `setup_staging.sh` ensures the setup script can be run multiple times safely without failing or duplicating data.
- **Security Posture:** Strict separation of SSH keys (`nerve_staging` vs `nerve_vps`) and the avoidance of local SQL dump files maintain good security and DSGVO hygiene.
- **Automated Verification:** Including a specific verification step (Plan 05) to ensure the CSRF patch remains untouched prevents accidental regressions during refactoring.

### 3. Concerns

- **[HIGH] Staging Gate Auth Failure:** Plan 01 puts HTTP Basic Auth on *all* routes on staging. Plan 02 has `deploy.sh` using `curl` to hit Staging's `/api/health`. Without passing credentials (`curl -u user:pass`), the production deployment gate will perpetually fail with a `401 Unauthorized` error.
- **[HIGH] Race Condition in Metadata Load:** Plan 02 states `.deploy_meta` is written *after* the staging restart. If `/api/health` reads this file exactly at startup, it will either load the outdated previous deploy data or crash on the very first deploy if the file doesn't exist yet.
- **[HIGH] Silent Database Corruption:** Plan 03 uses an SSH pipe (`ssh prod pg_dump | ssh staging psql`). In bash, pipes return the exit code of the *last* command by default. If `pg_dump` fails (e.g., connection drop), `psql` might receive an empty or partial file and succeed, wiping the staging database without throwing a top-level script error.
- **[MEDIUM] WebSocket Basic Auth Compatibility:** Browsers often fail to pass HTTP Basic Auth credentials when upgrading connections to WebSockets. This might cause the SocketIO connections in the PiP Live-Test to fail on staging.
- **[MEDIUM] Alembic Subprocess & SQLite Limitations:** Plan 04 uses `subprocess.run` for Alembic, which is brittle if systemd alters the CWD. Alembic also requires `render_as_batch=True` in `env.py` to safely handle `ALTER TABLE` statements in SQLite — not mentioned in the spec.
- **[LOW] DSGVO Enforcement:** Documenting the DSGVO trigger in the Vault (Plan 05) is good, but lacks technical enforcement. It relies entirely on human memory to implement anonymization once the first external user registers.

### 4. Suggestions

- **Fix Health Check Auth:** Modify `deploy.sh` (Plan 02) to source `.env.staging` (or pass vars) and include credentials in the curl command: `curl -s -u "$STAGING_BASIC_AUTH_USER:$STAGING_BASIC_AUTH_PASS" https://staging...`
- **Fix Metadata Sequencing:** In `deploy.sh` (Plan 02), generate and write `.deploy_meta` *before* `systemctl restart nerve`, ensuring the app loads fresh data immediately.
- **Enforce Pipe Safety:** Add `set -eo pipefail` at the top of `refresh_staging_from_production.sh` (Plan 03) to ensure any failure in the `pg_dump` stream aborts the entire script.
- **Use Alembic Python API:** In `app.py` (Plan 04), use Alembic's programmatic API (`alembic.config.Config` + `alembic.command.upgrade`) instead of subprocess. Verify `render_as_batch=True` is set in `alembic/env.py`.
- **WebSocket Auth Bypass:** If PiP test fails to connect Socket.IO, add `auth_basic off;` inside the `/socket.io/` location block in `nginx-staging.conf` (Plan 01).

### 5. Risk Assessment

**MEDIUM.** The core architecture is sound, but the execution details contain conflicting requirements (Basic Auth vs unauthenticated cURL gate) and unsafe bash practices (unprotected SSH pipes) that guarantee the initial implementation will fail. Applying the specific suggestions above will resolve these friction points and reduce the overall execution risk to **LOW**.

## Claude Review (inline — running as Claude Code)

### 1. Summary

The 5-plan wave structure is well-organized and the phase goal is strategically correct: staging as structural solution beats local-dev parity. The production-blocking gate (Req 5) is the most valuable feature in this phase. The plans are detailed and artifacts are precisely specified. Three structural issues need fixing before execution: the Basic Auth / curl conflict (independently caught by Gemini), the SSH pipe safety gap, and the Alembic subprocess CWD assumption. These are all fixable with small amendments to the plan tasks — they don't change the architecture.

### 2. Strengths

- **Wave 1 → Wave 2 → Wave 3 sequencing is correct:** Server artifacts must exist (Plan 01) before `deploy.sh staging` can be tested (Plan 02). Plans 02+03+04 are correctly independent within Wave 2 (no shared file edits). Plan 05 correctly waits for a running staging server.
- **`.deploy_meta` approach is elegant:** Writing a simple key=value file after deploy and reading it in `/api/health` is zero-dependency, survives reboots, and gives the gate everything it needs.
- **Req 11 (CSRF untouched) enforced by grep in Plan 05:** Preventing accidental regressions via automated check is better than documentation alone.
- **`psql -tAc` idempotency pattern:** Correctly avoids false positives from row-count footers like `(1 row)` that would break a naive `grep -q 1` check.
- **SSH key separation:** Separate key per environment prevents lateral movement. Good for a solo-founder who might share keys across tools.
- **`.env.staging.example` as committed artifact:** Makes staging setup reproducible for future André or any collaborator without tribal knowledge.

### 3. Concerns

- **[HIGH] curl vs. Basic Auth conflict (same as Gemini):** `deploy.sh production` gate calls `curl https://staging.getnerve.app/api/health` but nginx-staging.conf applies `auth_basic` on all routes → gate always returns 401. Fix: pass credentials in curl OR exempt `/api/health` from auth at nginx level.
- **[HIGH] SSH pipe lacks pipefail (same as Gemini):** `ssh prod 'pg_dump nerve' | ssh staging 'psql -U nerve_app nerve'` — if pg_dump fails after psql has started consuming stdin, psql drops the partial input and may partially restore or silently succeed. `set -eo pipefail` is required.
- **[HIGH] `.deploy_meta` written after restart — timing issue:** Plan 02 restarts the service first, then writes `.deploy_meta`. If health check is called immediately after restart (e.g., pre-deploy gate verifying staging), the file may be the previous deploy's. Fix: write meta before restart.
- **[MEDIUM] Alembic subprocess CWD:** `subprocess.run(['alembic', 'upgrade', 'head'], check=True)` in `app.py` assumes `alembic.ini` is in the CWD at runtime. On a development machine this usually works. Under systemd (if production ever runs app.py directly), the CWD may differ. Plan 04 should either use `cwd=os.path.dirname(__file__)` or use the Alembic Python API.
- **[MEDIUM] `render_as_batch` not verified:** Alembic migrations adding columns to SQLite tables require `render_as_batch=True` in `alembic/env.py`. Migrations 0002 and 0003 add `quality_tier` and `mode` to `phrases` — likely use `ALTER TABLE`. If `render_as_batch` is not set, the auto-hook will raise `NotImplementedError` at startup despite the rest of the code being correct.
- **[MEDIUM] Production nginx-conf duplication risk:** Plan 01 creates `deploy/nginx-production.conf` extracted from the inline heredoc in `deploy.sh`. Plan 02 modifies `deploy.sh`. If Plan 02 doesn't also remove the inline heredoc, the production nginx config will have two sources that can drift. The plan should explicitly state "remove inline heredoc from deploy.sh, use `scp deploy/nginx-production.conf`."
- **[LOW] PiP manual test as AC without a fallback:** Req 9 (Plan 05) is a `checkpoint:human-verify`. If the PiP test fails on staging, there's no defined resolution path in the plan. The plan should specify: on test failure → open debug task before proceeding.
- **[LOW] 24h gate may be too tight for solo-founder:** If André deploys to staging on Friday afternoon, the gate blocks production deploy Saturday evening without re-deploying staging. Consider extending to 48h or making it configurable via env var.

### 4. Suggestions

- **Plan 02:** Choose one of two approaches for the curl auth conflict: (a) Add nginx `location /api/health { auth_basic off; ... }` to `nginx-staging.conf` (cleaner), or (b) source credentials into `deploy.sh` and add `-u` flag to curl. Option (a) is simpler and keeps health endpoint accessible for monitoring.
- **Plan 03:** Add `set -eo pipefail` as first executable line in `refresh_staging_from_production.sh`. Also add a size check: if pg_dump output is < 1KB, abort before piping to psql.
- **Plan 02:** Swap order — write `.deploy_meta` SSH heredoc BEFORE `systemctl restart nerve-staging`.
- **Plan 04:** Add a pre-check: `grep -q "render_as_batch" alembic/env.py || echo "[DB] WARNING: render_as_batch not set, SQLite ALTER TABLE may fail"`. Or better: verify `render_as_batch=True` is in env.py and add to Plan 04's must_haves.
- **Plan 01+02:** Add explicit task to Plan 02: "remove inline nginx heredoc from deploy.sh after `scp deploy/nginx-production.conf` is wired in" to prevent config drift.
- **Plan 05:** Add failure path: "if PiP test fails → create debug task, do NOT mark Req-9 complete."

### 5. Risk Assessment

**MEDIUM.** Three HIGH-severity structural bugs (all fixable before execution with small plan amendments) prevent the pipeline from working out of the box. Architecture is correct. Fix the curl/auth conflict, pipe safety, and meta timing — then execution risk is LOW.

## Consensus Summary

Both reviewers converged on the same 3 HIGH-severity findings and 2 MEDIUM findings.

### Agreed Strengths

- Production deployment gate (Req 5: 3-check staging pre-condition) is the standout design decision of this phase
- `psql -tAc` idempotency pattern in setup_staging.sh is correct and robust
- SSH key separation (`nerve_staging` vs `nerve_vps`) is the right security posture
- Automated CSRF patch verification (Plan 05 grep check) prevents regression without manual overhead
- `.deploy_meta` approach is elegant and zero-dependency

### Agreed Concerns (fix before execution)

1. **[HIGH] HTTP Basic Auth vs. unauthenticated curl gate:** nginx-staging puts auth on all routes; `deploy.sh` production gate curl hits `/api/health` without credentials → always 401. Fix: exempt `/api/health` from auth in nginx-staging.conf OR pass credentials in curl.
2. **[HIGH] SSH pipe without pipefail:** `ssh prod pg_dump | ssh staging psql` — pg_dump failure is silently swallowed, potentially wiping staging DB. Fix: `set -eo pipefail` in refresh script + size check before psql.
3. **[HIGH] `.deploy_meta` written after restart:** Gate reads stale data on first-deploy or immediate health check. Fix: write `.deploy_meta` before `systemctl restart`.
4. **[MEDIUM] Alembic subprocess CWD brittleness:** `subprocess.run(['alembic', 'upgrade', 'head'])` assumes `alembic.ini` in CWD. Use Python API with explicit config path or add `cwd=` kwarg.
5. **[MEDIUM] `render_as_batch` not verified:** SQLite ALTER TABLE requires this in `alembic/env.py`. If missing, auto-hook crashes instead of upgrading.

### Divergent Views

- **WebSocket + Basic Auth:** Gemini raised WebSocket auth as a concern for the PiP test. Claude noted this is solvable with `auth_basic off` inside the `/socket.io/` location — not a blocker if addressed in nginx config.
- **24h gate duration:** Claude flagged solo-founder timing pressure (weekend scenarios). Gemini did not raise this. Worth making configurable.
- **Production nginx config duplication:** Only Claude flagged the deploy.sh heredoc + `deploy/nginx-production.conf` dual-source drift risk.
