### Server-Provisionierung — Plan 01 Lieferumfang (D-02)

Plan 01 liefert:
1. **`scripts/setup_staging.sh`** — idempotentes Shell-Skript für Ausführung auf dem frischen Server. Scope: `apt install` (nginx, postgres, certbot, python3-venv), `useradd nerve_app`, `mkdir -p /opt/nerve/{app,venv,backups/postgres,backups/pre-refresh}`, Postgres-User + DB anlegen (`nerve` + `nerve_test`), Verzeichnis-Permissions. Scope NICHT: Hetzner-Console-Klicks, DNS-Eintrag, SSL-Cert — die bleiben Runbook-Schritte.
2. **Runbook** (Markdown-Checkliste) — manuelle Schritte für André: Hetzner CX32 erstellen, SSH-Key `~/.ssh/nerve_staging` generieren, DNS `staging.getnerve.app` setzen, Certbot ausführen, `setup_staging.sh` ausführen.
3. **`deploy/nerve-staging.service`** — neue systemd-Service-Datei analog `deploy/nerve.service`, mit Staging-spezifischem EnvironmentFile-Pfad.
4. **nginx-Config-Template** — `deploy/nginx-staging.conf` mit Platzhaltern für SSL-Cert-Pfad + htpasswd-Datei-Pfad.

`setup_staging.sh` ist idempotent: zweiter Lauf bricht nicht ab, prüft ob Schritte schon erledigt (z.B. `id nerve_app || useradd nerve_app`).

### deploy.sh Architektur — Chirurgisch (D-03)

**Minimale Struktur-Änderungen:**
- TARGET-Parameter-Block ganz oben: `TARGET="${1:?Usage: ./deploy.sh staging|production}"` — kein Default, kein leerer Aufruf möglich
- If/else-Block setzt `VPS_HOST` + `SSH_KEY` je nach TARGET:
  - `staging`: `VPS_HOST="root@<STAGING_IP>"`, `SSH_KEY="$HOME/.ssh/nerve_staging"`
  - `production`: `VPS_HOST="root@178.104.82.166"`, `SSH_KEY="$HOME/.ssh/nerve_vps"` + Production-Gate-Checks davor
- Inline-SSH-Heredoc bleibt wie er ist — beide Targets teilen denselben Server-Setup-Code (spaCy + GLiNER laden bei erstem Staging-Deploy einmalig, danach pip-gecacht)
- TARGET-spezifische Heredoc-Teile: nginx-Config-Datei (`nginx-staging.conf` vs. bestehende Production-Config), systemd-Service-Datei (`nerve-staging.service` vs. `nerve.service`)
- Nach erfolgreichem Restart bei `staging`-Target: schreibt `/opt/nerve/.deploy_meta` auf Staging-Server

**Notiz für Plan-Phase:** Refactor in Funktionen wird als eigene Mini-Phase vermerkt. CLAUDE.md-Trigger: ≥3 Pflaster in deploy.sh ODER drittes Target wird hinzugefügt.

### deploy.sh — Production-Gate Ablauf (D-04)

`deploy.sh production` führt vor dem Deploy folgende Checks durch:
1. `which jq || { echo "[deploy] ERROR: jq not installed"; exit 1 }` — jq-Pflicht-Check
2. `curl`-Call auf `https://staging.getnerve.app/api/health`, prüft: `status == "ok"`, `deployed_at` Alter <24h, `git_head == $(git rev-parse HEAD)`
3. `.env`-Check auf Production-Server (wie auf Staging): `ssh ... 'test -f /etc/nerve/.env'`
4. Erst danach: tar-Upload + Server-Setup-Heredoc

### Staging .env — Strategie (D-05)

**Manuell von André erstellt, nie im Repo:**
- `deploy.sh` prüft vor jedem Deploy (beide Targets): `ssh root@$VPS_HOST 'test -f /etc/nerve/.env'`. Fehlt die Datei: Abbruch mit `"[deploy] BLOCKER: /etc/nerve/.env fehlt auf $TARGET — erstelle die Datei mit .env.staging.example als Template"`
- André erstellt `/etc/nerve/.env` auf Staging-Server manuell via SSH (einmalig)
- **`.env.staging.example`** — neue Datei im Repo (committed mit Dummy-Werten, NICHT in .gitignore). Enthält alle Pflicht-Variablen mit Kommentaren:
  - `ANTHROPIC_API_KEY=sk-ant-...` (Staging-Sandbox-Key, separat von Production)
  - `DEEPGRAM_API_KEY=...` (Staging-Sandbox-Key)
  - `STRIPE_SECRET_KEY=sk_test_...` (Stripe Test-Mode)
  - `STAGING_BASIC_AUTH_USER=staging`
  - `STAGING_BASIC_AUTH_PASS=<generate with openssl rand -hex 12>`
  - `DATABASE_URL=postgresql://nerve_app@/nerve`
  - `FLASK_ENV=production`
  - Alle weiteren Vars analog `.env.example`

### /api/health Extension — Lese-Strategie (D-06)

`/api/health` liest `.deploy_meta`-Datei beim **Request** (nicht beim App-Start). Datei-Pfad: `/opt/nerve/.deploy_meta`. Enthält zwei Zeilen: `GIT_HEAD=<SHA>` und `DEPLOYED_AT=<ISO-8601>`. Fehlt die Datei (lokale Dev-Umgebung) → `git_head: null`, `deployed_at: null`. Bestehende Felder (`backup_status`, `pipeline_status`) bleiben unverändert.

<specifics>
## Specific Ideas

- **deploy.sh TARGET ohne Default:** `TARGET="${1:?Usage: ./deploy.sh staging|production}"` — leerer Aufruf gibt sofort Fehlermeldung, kein versehentliches Production-Deploy
- **`.deploy_meta`-Format:** Zwei KEY=VALUE-Zeilen (shell-parsbar): `GIT_HEAD=$(git rev-parse HEAD)` und `DEPLOYED_AT=$(date -u +%Y-%m-%dT%H:%M:%SZ)` — einfach via `grep`/`cut` parsbar in Production-Gate-Check
- **Pre-Refresh-Backup in `refresh_staging_from_production.sh`:** `pg_dump nerve | gzip > /opt/nerve/backups/pre-refresh/pre-refresh-$(date +%Y%m%dT%H%M%S).sql.gz` direkt auf Staging (kein Transfer nach lokal)
- **`reset_sequences.py` idempotent:** `SELECT setval(seq, MAX(id)+1, true) WHERE MAX(id) IS NOT NULL` — läuft bei leerer Tabelle ohne Fehler
- **CLAUDE.md Trigger-Notiz für deploy.sh-Refactor:** ≥3 Pflaster in deploy.sh ODER drittes Deploy-Target → separater Mini-Refactor als eigene Phase

</specifics>
