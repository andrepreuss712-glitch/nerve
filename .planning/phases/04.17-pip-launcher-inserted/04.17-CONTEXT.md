# Phase 04.17: PiP Launcher - Context

**Gathered:** 2026-04-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Upgrade des bestehenden PiP-Fensters von einem "Live-Coaching Viewer" zu einem "Call-Launcher". User kann aus dem PiP heraus einen kompletten Call starten (Modus wählen, Kundendaten eingeben, Skript auswählen), Live-Coaching empfangen, und nach dem Call Score + Highlights sehen — ohne je zum Haupt-Tab wechseln zu müssen. Der Vertriebler bleibt im PiP für 30-40 Calls am Tag.

</domain>

<decisions>
## Implementation Decisions

### Pre-Call Setup Flow
- **D-01:** Minimierter Zustand = kleiner NERVE-Button (120x44px, Teal-Border, immer sichtbar über anderen Fenstern)
- **D-02:** Klick auf Button → Panel klappt auf mit geradlinigem Setup-Flow: Modus → Kundendaten → Skript → Start
- **D-03:** Kein Zurück-Button nötig — Flow muss schnell sein (30-40 Calls/Tag)
- **D-04:** Modus-Auswahl: Cold Call / Meeting (identisch zum bestehenden Live-Modus, Phase 4.2)
- **D-05:** Kundendaten-Felder: Firma, Name, Position. Starten leer, aber kleines Dropdown zeigt die letzten 3-5 Eingaben zum Schnellauswählen (localStorage-basiert)
- **D-06:** Skript-Auswahl: Liste aus den Verkaufsprofilen des Users (bestehende Profile-Daten). Default = aktives Profil
- **D-07:** PreCall-Recherche-Button im Setup: Ruft bestehenden PreCall-Service (Phase 4.13) auf, zeigt kompaktes Briefing im PiP

### Call-Start & Audio
- **D-08:** Mikrofon-Berechtigung wird beim ersten PiP-Start einmalig angefragt (Browser-Dialog)
- **D-09:** WebSocket shared mit Haupt-Tab via shared reference (same origin) — NICHT postMessage
- **D-10:** Session-Initialisierung identisch zum bestehenden Live-Modus, nur Frontend anders
- **D-11:** Haupt-Tab muss im Hintergrund offen bleiben (Browser-Einschränkung)

### Live-Coaching im PiP
- **D-12:** Bestehende PiP-Tabs bleiben (Opener, Einwand, Coaching, EWB) — bereits implementiert
- **D-13:** Keine Änderungen am Live-Coaching Rendering nötig — bestehende `updatePipFromErgebnis()` / `updatePipFromCoaching()` Funktionen reichen

### Post-Call im PiP
- **D-14:** Nach Call-Ende zeigt PiP: großer Score-Wert (z.B. 72%) + 2-3 farbige Highlight-Tags aus Metriken (z.B. "Preis-Einwand gemeistert", "Redeanteil zu hoch"). Kein LLM-Call nötig — rein aus bestehenden Metriken berechnet
- **D-15:** Zwei Buttons darunter: "Nächster Call" (zurück zu Kundendaten-Eingabe) und "Details" (öffnet Post-Call Analyse im Haupt-Tab)
- **D-16:** Vertriebler bleibt im PiP für den nächsten Call — soll nicht nach jedem Call zum Haupt-Tab wechseln müssen

### Scope MVP für EA
- **D-17:** MVP-Kern: PiP öffnen → Modus wählen → Kundendaten → Call starten → Live-Coaching → Post-Call Score/Tags → Nächster Call
- **D-18:** PreCall-Recherche-Button: ja (Phase 4.13 schon gebaut, nur Button der bestehenden Service aufruft)
- **D-19:** Auto-Start und Einstellungen (pip_auto_start, pip_default_mode): nice-to-have, kann in Polish (Phase 4.16)
- **D-20:** Keine neuen DB-Tabellen nötig — PiP ist nur ein Frontend für bestehende Backend-Logik

### Claude's Discretion
- Kundendaten-History Implementierung (localStorage key format, max entries)
- Highlight-Tag Auswahl-Logik (welche Metriken → welche Tags)
- Animationen beim Auf-/Zuklappen des Panels
- Exact sizing des Post-Call Score Bereichs

</decisions>

## Existing Code Insights

### Reusable Assets
- `openPipWindow()` in app.js:1425 — Document PiP API Wrapper, already handles CSS loading, Lucide icons, pagehide cleanup
- `initPipContent()` in app.js:1566 — PiP content initialization (mode badge, opener text, EWB buttons)
- Tab-State-Machine (app.js:1517-1565) — `handlePipTabClick()`, `setPipTabFromKI()`, `activatePipTab()`
- `updatePipFromErgebnis()` / `updatePipFromCoaching()` — AI result rendering in PiP
- `renderPipEwbButtons()` — EWB button rendering with AI-selected highlighting
- `syncPipTimer()` — Timer synchronization between main tab and PiP

### Established Patterns
- PiP content lives in `#pip-window` div in app.html, moved into PiP document via `appendChild`
- CSS für PiP inline in app.html (`.pip-header`, `.pip-tabs`, `.pip-content`, etc.)
- `getPipElement(id)` helper checks PiP window first, falls back to main document
- `window._pipWindow` / `window._pipTabLocked` for state management
- Shared reference pattern: `pipWindow.nerveApp = { socket, startCall, ... }`

### Integration Points
- PiP Setup Flow muss bestehenden `/api/start_session` oder Socket.IO Events nutzen
- Kundendaten werden an `live_session.set_session_meta()` übergeben
- Profil-Auswahl nutzt bestehende Profile-API (`/profiles/api/list` oder ähnlich)
- PreCall-Button ruft bestehenden Service auf (Phase 4.13 endpoints)
- Post-Call Score kommt aus `ConversationLog` Metriken (kb_end, einwaende_behandelt, etc.)

</code_context>
