## Summary

Phase 04.17 upgrades the existing PiP window from a passive coaching viewer to a self-contained call launcher. The existing PiP infrastructure in `static/app.js` (lines 1414-1692) and `templates/app.html` (lines 909-956) is complete and working. The phase is entirely a frontend concern: new HTML panels inside `#pip-window` for pre-call setup and post-call summary, plus JS wiring to the already-complete backend APIs.

The key architectural insight is that the PiP content (`#pip-window` div) is a single DOM node that gets `.appendChild()`-ed into the PiP browser window. All new setup panels go inside that same div, toggled by a new JS state machine. The Socket.IO connection, the Deepgram audio stream, and all API calls already live in the main tab's JS scope — the PiP JS merely calls these functions directly via shared reference (`window._pipWindow` pattern is already in use for `closePipToVollbild()`).

The session start protocol is: (1) emit `start_live_session` Socket.IO event with `{ mode: 'cold_call'|'meeting' }` → (2) `startMicStream()` which calls `getUserMedia` and starts audio streaming. Kundendaten (Firma/Name/Position) do not currently flow through any backend API during session start — `session_meta` only gets updated by `reset_session()`. The correct approach is to store Kundendaten in a JS module variable alongside `precallBriefingText`, and pass Firma/Name as additional fields in the `api_beenden` payload (same pattern as `precall_briefing`).

**Primary recommendation:** Implement PiP launcher as a multi-panel state machine inside `#pip-window` with 4 states: `setup` (pre-call), `live` (existing tabs), `postcall`, and `minimized`. All transitions happen in JS; no new backend routes needed.

## Architecture Patterns

### PiP State Machine (new pattern for this phase)

The current PiP has no state concept — it always shows the 4 live-coaching tabs. The upgrade adds a wrapping state machine:

```
pip_state: 'minimized' | 'setup' | 'live' | 'postcall'
```

**State transitions:**
- `minimized` → `setup`: user clicks the NERVE mini button (opens PiP panel, shows setup flow)
- `setup` → `live`: user clicks "Call starten" after completing Modus + Kundendaten + Skript selection
- `live` → `postcall`: `api_beenden` response received, postcall data available in JS
- `postcall` → `setup`: user clicks "Nächster Call"
- Any state → `minimized`: user minimizes PiP (resize handle already exists via Document PiP API)

**Implementation approach:** A global `window._pipState` variable + `setPipState(newState)` function that shows/hides panels. Follows existing pattern of `window._pipWindow` and `window._pipTabLocked`.

### Setup Flow Panels (inside #pip-window)

Four new `<div>` panels added to `#pip-window`:

```html
#pip-panel-setup-modus       — Step 1: Cold Call / Meeting buttons
#pip-panel-setup-kundendaten — Step 2: Firma + Name + Position inputs
#pip-panel-setup-skript      — Step 3: Profile dropdown + Start button
#pip-panel-postcall          — Post-call: Score + Tags + Next/Details buttons
```

The existing 4 live-coaching panels (`#pip-panel-opener`, `#pip-panel-einwand`, `#pip-panel-coaching`, `#pip-panel-ewb`) remain unchanged per D-12/D-13.

The setup flow is a single-direction wizard (no back button, per D-03). Each step shows one panel, advancing on button click.

### Post-Call Score Calculation (D-14)

Available metrics from `api_beenden` response (`postcall` object): [VERIFIED: app_routes.py:319-329]

```javascript
postcall = {
  kb_end,              // 0-100, Kaufbereitschaft at session end
  kb_start,            // 0-100, Kaufbereitschaft at session start
  berater_words,       // int
  kunde_words,         // int
  einwaende: [],       // list of recognized objections
  dauer_sek,           // session duration in seconds
  skript_abdeckung: { gesamt_prozent }
}
```

Additional from `ConversationLog` fields saved: `einwaende_behandelt`, `redeanteil_avg`.

**Recommended score formula (Claude's Discretion):**

```javascript
function calcPipScore(postcall) {
  // Weighted composite, 0-100
  var kb = postcall.kb_end || 30;
  var total = postcall.berater_words + postcall.kunde_words;
  var redeanteil = total > 0 ? Math.round(postcall.berater_words / total * 100) : 50;
  var einwaende_ok = postcall.einwaende_behandelt || 0;
  var einwaende_total = (postcall.einwaende || []).length;
  var behandelt_rate = einwaende_total > 0 ? einwaende_ok / einwaende_total : 0.5;
  var skript = (postcall.skript_abdeckung || {}).gesamt_prozent || 0;

  // 40% KB + 30% Einwand-Behandlung + 20% Redeanteil (target ~40%) + 10% Skript
  var redeanteil_score = 100 - Math.abs(redeanteil - 40) * 2;  // best at 40%
  return Math.round(kb * 0.4 + behandelt_rate * 100 * 0.3 + redeanteil_score * 0.2 + skript * 0.1);
}
```

## Integration Points — Verified

### 1. Socket.IO — shared reference (D-09)

`const socket` is initialized at module scope in `app.js` line 4. Since all PiP JS runs in the same document (the `#pip-window` div is moved into the PiP document, but event handlers referencing `socket` close over the module scope), the Socket.IO connection is automatically shared. [VERIFIED: app.js:1-8, openPipWindow() DOM move pattern]

**Implication:** `socket.emit('start_live_session', ...)` called from PiP setup flow works identically to calling it from the main tab flow.

### 2. getUserMedia in PiP context

`getUserMedia` is called in `startMicStream()` which runs in the main document's JS scope (not inside the PiP window document). The PiP window is a separate browsing context but shares the JS scope through closure. `getUserMedia` requires a secure context (HTTPS) and a user gesture. The call button inside the PiP IS a user gesture in this context because the handler runs in the opener's scope. [ASSUMED — Document PiP API spec says PiP window shares opener's browsing context; microphone permission inherited from opener origin]

### 3. Profile API — `/api/set_profile` (existing)

`POST /api/set_profile` with `{ profile_id }` updates the server-side active profile AND the `ls.active_profile_data` global that drives Claude context. After calling this from PiP, the PiP Opener tab must refresh its text by calling `initPipContent()`. [VERIFIED: app_routes.py:568-592]

### 4. PreCall Research — `/api/precall/research` (existing)

Takes `firmenname` (required, 3-200 chars), optional `ansprechpartner`, optional `branche`. Returns `{ briefing: { text, firmenname, quellen_count } }`. Store `briefing.text` in `precallBriefingText` variable (already declared at module scope in app.js:17). The `api_beenden` call already reads this variable and sends it as `precall_briefing` field. [VERIFIED: app.js:17, 646; app_routes.py:256-261]

### 5. Session End — `api_beenden` (existing)

`POST /api/beenden` with `{ session_mode, precall_briefing }`. The PiP should add Kundendaten to this payload:

```javascript
body: JSON.stringify({
  session_mode: sessionMode || 'meeting',
  precall_briefing: precallBriefingText,
  kundendaten: window._pipKundendaten || null  // NEW — needs server-side handling
})
```

The server currently ignores unknown fields, so this is safe to add without breaking existing code. The `kundendaten` field would need a small addition in `api_beenden` to save it in `ConversationLog` if desired — but D-20 says no new DB tables/columns. Decision: pass Kundendaten through but do not persist for MVP (store in `ls.last_postcall` for the Post-Call overlay display only).

**Alternative (simpler):** Store Kundendaten only in `window._pipKundendaten` for display in the PiP post-call panel. Do not send to backend. Sufficient for MVP per D-20.

### 6. `api_beenden` postcall response

The response includes the `postcall` object needed for PiP post-call display:

```javascript
// [VERIFIED: app_routes.py:319-329, 559]
{ ok: true, filename, conv_id, postcall: {
  einwaende, kaufsignale, painpoints,
  berater_words, kunde_words,
  kb_start, kb_end, kb_verlauf,
  skript_abdeckung: { gesamt_prozent, phasen },
  dauer_sek,
  crm_notiz, followup_email, naechste_schritte

```

The existing `showPostcall(data)` JS function renders the full post-call modal. The PiP needs only a subset: `kb_end`, `berater_words`, `kunde_words`, `einwaende.length`, plus `einwaende_behandelt` (not in postcall object — needs to be added or calculated from `ga_details`).

**Finding:** `einwaende_behandelt` is saved to DB but NOT returned in the `postcall` JSON response currently. The PiP score formula needs this. Options:
1. Add `einwaende_behandelt` to the `postcall` dict in `api_beenden` (small backend change, clean)
2. Calculate it from `postcall.ga_details` (already in response) — `ga_details.filter(x => x.erfolgreich === true).length`

Option 2 requires no backend change. [VERIFIED: app_routes.py:400, 541]

## Common Pitfalls

### Pitfall 1: PiP Content DOM Node Moves Out of Main Document

**What goes wrong:** `document.getElementById()` calls fail after `openPipWindow()` moves `#pip-window` into the PiP document.
**Why it happens:** `appendChild()` physically moves the DOM node — it no longer exists in the main document.
**How to avoid:** Always use `getPipElement(id)` helper (already exists, app.js:1417-1422). New PiP panels use the same helper.
**Warning signs:** `getPipElement()` returns `null` for new IDs → ID typo or panel not inside `#pip-window`.

### Pitfall 2: `getUserMedia` User Gesture Requirement

**What goes wrong:** `getUserMedia` throws `NotAllowedError` when called outside a user gesture.
**Why it happens:** Browser security policy requires getUserMedia to be triggered by click/keydown.
**How to avoid:** The "Call starten" button's click handler MUST directly call `startMicStream()` without setTimeout or async indirection. If called inside a `.then()` chain from another fetch, the user gesture context is lost.
**Warning signs:** Console error `NotAllowedError: Permission denied` or `Must be handling a user gesture`.

### Pitfall 3: CSS Variables Missing in PiP Window

**What goes wrong:** PiP window shows wrong colors (white backgrounds instead of dark theme).
**Why it happens:** `openPipWindow()` copies CSS rules from all stylesheets, but cross-origin sheets (CDN fonts, Lucide) fail with CORS error and are added as `<link>` tags. CSS variable definitions may not transfer if they're in a CORS-blocked sheet.
**How to avoid:** NERVE's own CSS (nerve.css, inline styles) is same-origin and copies correctly. Verify `--page-bg`, `--glass-border`, `--color-teal` etc. are in `nerve.css` or `app.html` inline styles, not CDN-loaded.
**Warning signs:** PiP shows white/default colors while main tab is dark.

### Pitfall 4: Setup Panels Visible in Live State

**What goes wrong:** After starting a call, the Modus/Kundendaten setup panels are still visible alongside the live coaching tabs.
**Why it happens:** The state machine didn't hide setup panels or the CSS display toggle was missed.
**How to avoid:** `setPipState(newState)` must toggle display of all panels, not just show the new one. Use a single `data-pip-state` attribute on `#pip-window` + CSS selectors, or explicit JS `display = 'none'`/`'block'` for each section.

### Pitfall 5: `api_beenden` called before PiP postcall panel

**What goes wrong:** The existing `api_beenden` call in `app.js` fires on the main tab "Beenden" button, but the PiP needs to trigger it too and capture the response.
**Why it happens:** PiP's "Call beenden" button needs its own handler that calls `api_beenden`, switches PiP to `postcall` state with the returned data.
**How to avoid:** Extract the `api_beenden` fetch into a shared function `endCallAndShowPostcall()` that both the main tab button and the PiP button call.
**Warning signs:** PiP stays in `live` state after call ends, or post-call shows no data.

## Code Examples

### PiP State Machine Skeleton

```javascript
// [PATTERN: follows existing window._pipWindow / window._pipTabLocked pattern]
window._pipState = 'minimized';  // 'minimized' | 'setup' | 'live' | 'postcall'
var _pipSetupStep = 1;  // 1: modus, 2: kundendaten, 3: skript
var _pipSelectedMode = null;
var _pipKundendaten = null;  // { firma, name, position }

function setPipState(newState) {
  window._pipState = newState;
  var sections = {
    'setup':    getPipElement('pip-section-setup'),
    'live':     getPipElement('pip-section-live'),
    'postcall': getPipElement('pip-section-postcall'),
  };
  Object.keys(sections).forEach(function(k) {
    if (sections[k]) sections[k].style.display = (k === newState) ? 'flex' : 'none';
  });
}

function pipStartSetup() {
  _pipSetupStep = 1;
  setPipState('setup');
  showPipSetupStep(1);
}

function showPipSetupStep(step) {
  [1, 2, 3].forEach(function(s) {
    var el = getPipElement('pip-setup-step-' + s);
    if (el) el.style.display = (s === step) ? 'block' : 'none';
  });
  _pipSetupStep = step;
}
```

### Kundendaten History (localStorage)

```javascript
// [PATTERN: follows existing try/catch localStorage pattern in openPipWindow()]
var _KUNDENDATEN_HISTORY_KEY = 'nerve_pip_kundendaten';
var _KUNDENDATEN_MAX = 5;

function loadKundendatenHistory() {
  try {
    return JSON.parse(localStorage.getItem(_KUNDENDATEN_HISTORY_KEY) || '[]');
  } catch(e) { return []; }
}

function saveKundendaten(eintrag) {
  // eintrag: { firma, name, position }
  try {
    var history = loadKundendatenHistory().filter(function(h) {
      return !(h.firma === eintrag.firma && h.name === eintrag.name);
    });
    history.unshift(eintrag);
    localStorage.setItem(_KUNDENDATEN_HISTORY_KEY, JSON.stringify(history.slice(0, _KUNDENDATEN_MAX)));
  } catch(e) {}
}
```
