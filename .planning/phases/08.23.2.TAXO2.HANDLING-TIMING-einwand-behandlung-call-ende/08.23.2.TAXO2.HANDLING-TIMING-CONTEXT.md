<problem>
## Verifizierter Befund (Prod-Datenbestand + Code, Live-Test 2026-06-26)

**Symptom:** Die Einwand-Behandlung wird NIE benotet → jeder Call landet auf `insufficient_data`.

**Belege (Test-Call `9b224830…`):**
- `intent_event.handling_status='abstained'` für **alle 3 Einwände**; `abstain_log.next_advisor_sentence` LEER bei allen.
- Benotungs-Zeit (`abstain_log.created_at`) = ~30ms NACH dem Einwand-Emit (15:50:16/31/49) → Benotung passiert **LIVE beim Knopfdruck/Emit**.
- `transcript_segments` des Calls: 15 Stück, ALLE `created_at=15:51:14` → **gebündelt am Call-Ende geschrieben** (25–58s NACH der Benotung). `speaker`-Werte korrekt (`berater`/`kunde`), `text` vorhanden.
- `_find_next_advisor_utterance` (`services/slow_lane.py:189-213`) filtert/ordnet auf `transcript_segments.created_at >= ev.timestamp` — aber `created_at` ist die **Batch-SCHREIBZEIT** (bei allen identisch `now()`), NICHT die Sprech-Zeit (`ts_ms`). Zum Benotungs-Zeitpunkt existieren die Segmente **noch gar nicht** → Lookup findet nichts → `grade_handling` abstainiert (D-07) → Event terminal `'abstained'` → `_persist_event_ref`-Idempotenz (nur `'pending'` wird re-prozessiert) verhindert späteres Re-Scoring.

**Systemisch, nicht test-spezifisch:** live benoten + Batch-Transkript-am-Ende → der Antwort-Satz ist beim Benoten nie da.

## Persistenz-Schicht-Beleg (Punkt 21 — Prod-Schema, inspect.sh 2026-06-26)

**`transcript_segments`** (public):
- `id` bigint PK; `conversation_log_id` integer NOT NULL → FK `conversation_logs(id)` ON DELETE CASCADE; `ts_ms` integer NOT NULL (**ms-in-call = Sprech-Zeit**); `speaker` text CHECK in ('berater','kunde','system'); `text` text NOT NULL; `created_at` timestamptz DEFAULT `now()` (**Batch-Schreibzeit**).
- Index `idx_transcript_segments_conv_ts` btree (conversation_log_id, ts_ms).

**`intent_event`** (public):
- `event_id` bigint PK; `call_id` uuid NOT NULL → FK `calls(id)`; `timestamp` timestamptz NOT NULL (**Wall-Clock Event-Zeit**); `handling_status` varchar(16) DEFAULT 'pending'; Index auf `timestamp` + `handling_status`.
- `abstain_log.event_id` → FK `intent_event(event_id)` ON DELETE CASCADE.

**`calls`** (public, relevant für die Brücke):
- `started_at` timestamptz (**Call-Start = Referenz für die ts_ms-Brücke**); `ended_at` timestamptz (F-02-Signal); `conversation_log_id` integer NULLABLE → FK `conversation_logs(id)` (**Join-Schlüssel zu transcript_segments, gesetzt am Call-Ende in `api_beenden` app_routes.py:697**); `audio_health_resolved` boolean (Fan-In-Flag aus TAXO2-04-Fix).

**Zwei harte Konsequenzen aus dem Schema:**
1. **Zeit-Bezug:** `intent_event.timestamp` (Wall-Clock) und `transcript_segments.ts_ms` (ms-in-call) haben KEINEN gemeinsamen Bezug außer `calls.started_at`. Eine korrekte Verankerung rechnet `ev_ms_in_call = (intent_event.timestamp − calls.started_at)` in ms und vergleicht gegen `transcript_segments.ts_ms`. **In RESEARCH bestätigen, dass `ts_ms` wirklich relativ zu `started_at` ist** (nicht zu einem anderen Nullpunkt) — am Real-Daten-Sample.
2. **Join-Schlüssel existiert live nicht:** `transcript_segments` hängen an `conversation_log_id`; `intent_event` an `call_id` (uuid). Die Brücke läuft über `calls.conversation_log_id` — die wird ERST am Call-Ende gesetzt. Zum Live-Benotungs-Zeitpunkt gibt es weder die Segmente noch den Join-Schlüssel. → starkes Argument für Deferred-Scoring.
</problem>

<decisions>
## Implementation Decisions (locked, soweit nicht als Fork markiert)

### FIX-RICHTUNG (Empfehlung — als explizite Entscheidung im Plan, Cross-AI/Gemini bewertet den Fork)
- **Deferred Handling-Scoring (empfohlen):** Die Handling-Benotung der Einwand-Events wird NICHT mehr live beim Emit gefahren, sondern **DEFERRED bis nach dem `transcript_segments`-Write (Call-Ende)**. Die Events bleiben `'pending'` bis dahin. Ein **Fan-In-Signal** (analog zum gerade gebauten `calls.audio_health_resolved`) stößt die Handling-Benotung an, sobald das Transkript persistiert ist. Passt zur Plan-04-Merge-Vorbedingung (`pending_events==0` → der Merge wartet ohnehin, bis Handling fertig ist).
- **PLUS Zeit-Verankerung:** `_find_next_advisor_utterance` auf die **Sprech-Zeit (`ts_ms`)** ankern, NICHT `created_at`. Gemeinsamer Bezug = `calls.started_at` (siehe Persistenz-Beleg oben).
- **Zu bewertende Alternative (Fork — Cross-AI):** `transcript_segments` real-time statt Batch schreiben. Vermutlich teurer/riskanter (die Anonymisierungs-Pipeline B läuft am Call-Ende). Im Plan als verworfene/abzuwägende Option dokumentieren, Gemini entscheidet mit.

### Trigger / Fan-In (Punkt 14 — Race sauber definieren)
- Das Fan-In-Signal für die Deferred-Handling-Benotung am Call-Ende sauber definieren: **was, wenn der Transkript-Write scheitert/fehlt → kein Hang** (analog zur „resolved-als-absent"-Logik im audio_health-Fix: wenn keine Segmente kommen, das Signal trotzdem setzen, damit nichts ewig pending bleibt); **Idempotenz**; **Doppel-Trigger** (mehrfaches put → idempotenter Re-Run, Single-Consumer bestätigt = `app.py` startet genau einen `slow_lane_consumer`).
- **Interaktion mit Plan-04-Merge:** `pending` bleibt bis Handling benotet → der Merge wartet korrekt (F-02 `pending_events==0`). Mit `audio_health_resolved` zusammen ergibt sich ein **Mehrfach-Fan-In am Call-Ende** (Transkript-fertig + Audio-fertig + 0 pending → erst dann Merge). Das Zusammenspiel beider Signale im Plan explizit modellieren (keine gegenseitige Verklemmung).

### Idempotenz-Falle (Re-Scoring)
- Heute verhindert `_persist_event_ref` (re-prozessiert nur `'pending'`) ein späteres Re-Scoring bereits terminaler `'abstained'`-Events. Bei Deferred-Scoring bleiben die Events `'pending'`, bis das Transkript da ist → das Problem entfällt strukturell. **Sicherstellen, dass die neue Reihenfolge keine Events vorzeitig auf einen Terminal-Status setzt.**

### Latenz (Punkt 25)
- **KEIN Block des Call-Endes.** Die Benotung bleibt async (Slow Lane). Der Call-Ende-Pfad (`api_beenden`) darf nur leichte Queue-puts machen, kein synchrones Grading/LLM.
</decisions>
