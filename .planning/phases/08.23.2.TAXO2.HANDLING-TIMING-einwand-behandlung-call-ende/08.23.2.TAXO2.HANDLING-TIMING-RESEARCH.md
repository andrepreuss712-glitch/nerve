**Researched:** 2026-06-26
**Domain:** Slow-Lane-Timing / async Benotungs-Race / Zeit-Verankerung (intent_event ↔ transcript_segments)
**Confidence:** HIGH (Code + Prod-`inspect.sh`-Belege für alle 6 Pflicht-Fragen)

## Summary

Die Einwand-Behandlungs-Note (`handling_status`/`handling_score_numeric`) landet **systemisch** auf
`abstained`, weil die Benotung **live beim Emit** läuft (`emit_intent_event` → sofortiges
`slow_lane.put({'event_id'})`, intent_event_writer.py:159), während das Transkript
(`transcript_segments`) erst **am Call-Ende gebündelt** geschrieben wird (`api_beenden`,
app_routes.py:454-470). Zum Benotungs-Zeitpunkt existieren weder die Segmente noch der Join-Schlüssel
`calls.conversation_log_id` (der wird erst app_routes.py:697 gesetzt). `_find_next_advisor_utterance`
findet nichts → `grade_handling` abstainiert (D-07) → Event terminal `abstained` → die
`_persist_event_ref`-Idempotenz (nur `pending` wird re-prozessiert) zementiert es. Prod-Beleg:
**12/12 gesampelte intent_event-Zeilen `handling_status='abstained'`** (inspect.sh 2026-06-26).

Hinzu kommt ein **zweiter, unabhängiger Defekt im Lookup selbst**: `_find_next_advisor_utterance`
filtert/ordnet auf `transcript_segments.created_at` (= Batch-**Schreib**zeit, bei allen Segmenten
identisch `now()`), nicht auf `ts_ms` (= **Sprech**zeit). Selbst MIT Deferred-Scoring würde die
Ordering kollabieren, wenn nicht zugleich auf `ts_ms` verankert wird. Beide Fixes (defer + ts_ms)
gehören in dieselbe Phase.

**Primary recommendation:** Deferred Handling-Scoring (Events bleiben `pending` bis Transkript-Write)
+ ts_ms-Verankerung des Lookups, angestoßen durch ein **drittes Fan-In-Signal am Call-Ende**, exakt
nach dem Muster des `audio_health_resolved`-Fixes (TAXO2-04 Gap-Fix). Der Fork (Realtime-Transcript-
Write) ist teurer/riskanter (Anonymisierungs-Pipeline B läuft am Call-Ende) — als verworfene Option
dokumentieren, Gemini bewertet ihn.

## Architecture Patterns

### System-Datenfluss (Ist vs. Soll)

**IST (defekt):**
```
emit_intent_event (Live-Loop, intent_event_writer.py:128-159)
  → INSERT intent_event (timestamp = now() wall-clock, handling_status='pending')
  → slow_lane.put({'event_id'})        ← LIVE-TRIGGER (zu früh!)
        ↓ (Slow-Lane-Consumer, sofort)
  _persist_event_ref → _find_next_advisor_utterance
        → calls.conversation_log_id  ← NULL (wird erst am Call-Ende gesetzt!)
        → 0 Segmente (noch nicht geschrieben)
        → None → grade_handling abstainiert → handling_status='abstained' (TERMINAL)

... 25-58s später ...
api_beenden (app_routes.py)
  → INSERT transcript_segments (Batch, alle created_at=now())   ← zu spät
  → calls.conversation_log_id = saved_conv_id (app_routes.py:697)
  → calls.ended_at = now()
  → slow_lane.put({'call_id'})  → Merge (Events sind aber schon terminal-abstained)
```

**SOLL (Deferred + ts_ms-anchored):**
```
emit_intent_event (Live-Loop)
  → INSERT intent_event (handling_status='pending')
  → KEIN live-Grade-put mehr (oder put bleibt no-op, weil Lookup fehlschlägt-und-NICHT-terminalisiert)
        ↓ (Events bleiben 'pending')
api_beenden (Call-Ende):
  1. INSERT transcript_segments (Batch)          [bestehend]
  2. calls.conversation_log_id = saved_conv_id   [bestehend, app_routes.py:697]
  3. calls.ended_at = now()                       [bestehend, app_routes.py:696]
  4. calls.transcript_resolved = True (NEU)        ← Fan-In-Setpoint, im selben commit
  5. slow_lane.put({'call_id': ...}) / re-queue der pending events des Calls
        ↓ (Slow-Lane-Consumer, async)
  Grade-Step (am Call-Ende, transcript ist DA):
     pro pending Event → _find_next_advisor_utterance (ts_ms-anchored) → grade → scored/abstained/failed
  → erst wenn alle pending gegraded (pending==0) UND audio_health_resolved UND transcript_resolved
     → Merge (rubric_score)
```

### Pattern 1: Fan-In-Resolved-Flag (mirror audio_health_resolved)
**What:** Eine `calls.<x>_resolved` BOOLEAN-Spalte (NOT NULL DEFAULT FALSE), die TRUE wird, sobald
ein async Teilzustand endgültig festgeschrieben ist; das Merge-Gate wartet darauf, und der Setpoint
re-putet `{'call_id'}` in die Slow Lane. **Beweis (TAXO2-04 Gap-Fix, live, Migration 0027):**
`calls.audio_health_resolved` (models.py:703-711) wird gesetzt (a) in `_audio_health_bg`-`finally`
auf JEDEM Pfad (app_routes.py:792-823) ODER (b) in `api_beenden` resolved-als-absent, wenn kein
Buffer existiert (app_routes.py:723-724). Merge-Gate liest es (slow_lane.py:566).

**When to use:** Für die Transcript-Bereitschafts-Naht (`transcript_resolved`) — exakt dieselbe Form.

**Example (resolved-als-absent + idempotenter Set, aus dem Live-Fix):**
```python
# routes/app_routes.py:723-724 (Vorbild — kein Buffer → sofort resolved, sonst Thread-finally)
if not _phase_d_word_confidences:
    _call_row.audio_health_resolved = True
# ... im selben _db_calls.commit() wie ended_at/conversation_log_id
```

### Pattern 2: Deferred-Grade-Step als Call-Ende-Schritt
**What:** Statt live beim Emit zu graden, wird das Grading der `pending`-Events eines Calls **am
Call-Ende** ausgelöst (transcript ist dann da). Zwei valide Bauformen (Claude's Discretion):
- (a) Re-queue aller `{'event_id'}` des Calls aus `api_beenden`/Consumer, nachdem `transcript_resolved`
  gesetzt ist — `_persist_event_ref` bleibt unverändert die Grade-Funktion, nur der Trigger-Zeitpunkt
  verschiebt sich. **Vorteil:** minimaler Eingriff, H-3-Bootstrap (`_requeue_pending`) re-graded
  ohnehin alle `pending` aus der DB.
- (b) Ein registrierter `_grade_pending_step(ctx)` via `register_call_end_step`, der VOR `_pending_events`
  läuft. **Nachteil:** der Merge zählt `pending` als Gate — ein Step, der erst pending→terminal macht
  und im selben Merge-Pass den Merge freigibt, ist Reihenfolge-empfindlich. (a) ist robuster.

**When to use:** Empfehlung (a) — der H-3-Pfad existiert schon und ist idempotent.

### Anti-Patterns to Avoid
- **`created_at` als Zeit-Achse für intra-Call-Ordering:** ist die Batch-Schreibzeit (alle identisch).
  Immer `ts_ms` für Sprech-Reihenfolge.
- **Live-Grade beim Emit:** strukturell unmöglich korrekt (Transkript + Join-Key existieren noch nicht).
- **Event vorzeitig auf Terminal setzen, wenn Lookup leer:** bei Deferred darf ein leerer Lookup VOR
  dem transcript-Write NICHT terminalisieren (sonst zurück zum Bug). Nur NACH `transcript_resolved`
  ist `None`/leer eine valide Abstention.

## Common Pitfalls

### Pitfall 1: ts_ms-Nullpunkt ≠ calls.started_at (HAUPT-LANDMINE)
**What goes wrong:** Die CONTEXT (und der models.py:927-Kommentar „ms ab Call-Start") suggerieren
`ts_ms` sei relativ zu `calls.started_at`. **Das stimmt NICHT.** Der einzige Writer
`_transcript_entries_to_segments` (app_routes.py:45-72) rechnet:
`ts_ms = wall_clock_of_day_ms(entry) − wall_clock_of_day_ms(ERSTER transcript-entry)`
(app_routes.py:48, 60-66). Der Nullpunkt ist also **die erste Transkript-Aussage**, nicht `started_at`.
Prod-Beleg: jeder conversation_log beginnt bei `ts_ms=0` (inspect.sh sample: conv 200→0, conv 240→0,
conv 243→0, …). `calls.started_at` (live_session.py:601, gesetzt bei Session-Start) liegt VOR der
ersten Aussage (Begrüßung/Stille). Eine naive Formel `ev_ms = (ev.timestamp − started_at)·1000`
ist um die „Vorlauf-Lücke" verschoben → Lookup trifft das falsche Segment.
**Why it happens:** Zwei unabhängige Zeit-Achsen ohne gemeinsamen geschriebenen Bezug:
`intent_event.timestamp` (wall-clock UTC) und `transcript_segments.ts_ms` (relativ zur 1. Aussage).
**How to avoid:** Zwei valide Strategien (Plan muss eine wählen, Cross-AI bewerten):
- **(A) Anker an die erste Segment-Sprechzeit:** `ev_offset_ms = (ev.timestamp − started_at)·1000`
  UND `base_offset_ms = (erste_segment_wall_clock − started_at)·1000`. Da `base` nicht gespeichert
  ist, ist (A) nicht direkt rechenbar — **deshalb riskant**.
- **(B) Robuste Relativ-Ordnung statt absoluter Verankerung:** Nutze die **Reihenfolge der
  intent_event-timestamps** und die **ts_ms-Reihenfolge** als zwei monotone Sequenzen; ordne die
  Berater-Segmente nach `ts_ms` und nimm das erste Berater-Segment, dessen relative Position NACH
  dem Einwand liegt. Praktisch: weil EWB-Button-Einwände als `kunde`-Segment MIT eigenem ts_ms in
  transcript_segments landen (Prod-Beleg: „Kein Bedarf \*ewb button\*", speaker=kunde, conv 243
  ts_ms=75000/95000), kann der Einwand SELBST über `interaction_id`/Text im Transkript verortet
  werden → das nächste `berater`-Segment mit größerem `ts_ms` ist die Antwort. Das umgeht die
  wall-clock↔ts_ms-Brücke komplett.
**Warning signs:** Nach Fix immer noch `abstained` bei Calls mit klarer Label-Antwort; oder Antwort-
Sätze, die zeitlich VOR dem Einwand liegen.

### Pitfall 2: Vorzeitige Terminalisierung bei Deferred (Idempotenz-Falle)
**What goes wrong:** Wenn der Live-Emit-put (intent_event_writer.py:159) bestehen bleibt UND
`_persist_event_ref` bei leerem Lookup weiter `abstained` setzt, sind die Events VOR dem
transcript-Write wieder terminal → Bug reproduziert.
**Why it happens:** `_persist_event_ref` (slow_lane.py:259-284) setzt bei `score None` →
`handling_status='abstained'` (terminal). Idempotenz skippt danach (slow_lane.py:230).
**How to avoid:** Defer den GRADE-Trigger (kein live-put-grade), ODER lass `_persist_event_ref` bei
fehlendem Transkript (`transcript_resolved==False` ODER 0 Segmente) das Event auf `pending` LASSEN
(früher return ohne Terminalisierung). Empfehlung: beides — primär den Trigger verschieben (Pattern 2a),
sekundär ein Guard in `_persist_event_ref` als Sicherheitsnetz.
**Warning signs:** abstain_log-Zeilen mit `next_advisor_sentence` LEER (= Lookup fand nichts) trotz
existierendem Transkript.

### Pitfall 3: speaker='system'-Fallback bricht den Lookup
**What goes wrong:** `_find_next_advisor_utterance` filtert `speaker == 'berater'` (slow_lane.py:207).
Ältere Calls haben `speaker='system'` (126/400 Segmente, prod) — der int→role-Map (`_sp_map`,
app_routes.py:33) mappt unbekannte/None-Sprecher auf `'system'` (app_routes.py:69). Für solche
Segmente findet der Lookup NIE eine Berater-Aussage.
**Why it happens:** Deepgram-Diarization liefert nicht immer einen Sprecher-Int; cold_call ohne
Dual-Speaker fällt auf 'system'. Aktuelle Calls (conv 240+) haben korrekte 'berater'/'kunde'-Labels
(247 berater / 27 kunde im Sample) — der Fix greift also für NEUE Calls; Altdaten bleiben teils
'system'.
**How to avoid:** Akzeptieren, dass 'system'-Segmente nicht benotbar sind (D-07-Abstention ist dann
korrekt). Den Plan NICHT auf Altdaten-Reparatur ausrichten. ggf. im Lookup `speaker IN ('berater')`
beibehalten; eine Lockerung auf 'system' würde Kunden-Sätze fälschlich als Berater-Antwort werten.

### Pitfall 4: ts_ms-Ausreißer / Clock-Skew
**What goes wrong:** Prod-Beleg conv 242: `ts_ms=29812000` (~8h) neben sonst kleinen Werten —
Clock-Skew oder Mitternachts-Wrap. Der monotone Klemm in `_transcript_entries_to_segments`
(app_routes.py:64-66) verhindert Rückwärts-Sprünge, aber nicht Vorwärts-Ausreißer.
**How to avoid:** Beim Anchoring keine harte Absolut-Schwelle; „nächstes Berater-Segment NACH dem
Einwand per ts_ms-Ordnung" ist gegen Vorwärts-Ausreißer robust (es nimmt das nächste, nicht ein
zeitfenster-gefiltertes).

### Pitfall 5: ts_ms-Kollisionen (gleiche ts_ms für Einwand + Antwort)
**What goes wrong:** EWB-Button-Einwand und Berater-Antwort teilen oft dieselbe `ts_ms` (Prod: conv
241 id 348/349 beide ts_ms=14000; conv 243 id 373/374 beide 75000). Ein striktes `ts_ms > ev_ms`
verfehlt die Antwort; `>=` nimmt evtl. den Einwand selbst.
**How to avoid:** Bei Gleichstand nach `speaker='berater'` filtern (der Einwand ist `kunde`) und
sekundär nach `id ASC` (Insert-Reihenfolge = Sprech-Reihenfolge, BIGSERIAL) ordnen.

### Q4 — Interaktion mit Plan-04-Merge + audio_health_resolved (Mehrfach-Fan-In)
**Modell:** Das Merge-Gate (`_call_end_merge`, slow_lane.py:549-567) prüft HEUTE drei Bedingungen:
`ended_at IS NOT NULL` (557) AND `_pending_events==0` (558) AND `audio_health_resolved==True` (566).
Mit Deferred-Handling ergänzt sich das natürlich:
```
Merge feuert ⇔  ended_at gesetzt
             ∧  pending_events(call_id) == 0     ← jetzt NUR nach dem Call-Ende-Grading 0
             ∧  audio_health_resolved == True     ← Audio-Thread / resolved-als-absent
             ∧  transcript_resolved == True (NEU)  ← Transkript geschrieben / resolved-als-absent
```
- **Kein Deadlock:** alle drei resolved-Flags werden GARANTIERT True (jeweils resolved-als-absent-
  Pfad). `pending_events` draint sicher auf 0, weil das Grading nach `transcript_resolved` läuft und
  jedes Event terminal (scored/abstained/failed) wird — `_persist_event_ref` setzt IMMER einen
  Terminal-Status, sobald Transkript da ist (slow_lane.py:255-284). Kein Event bleibt nach dem
  Call-Ende-Grade ewig pending.
- **Reihenfolge-Garantie:** `transcript_resolved` muss VOR/zugleich mit dem ersten grade-`{'event_id'}`-
  put gesetzt sein, sonst gradet der Consumer gegen ein leeres Transkript. Lösung: api_beenden setzt
  `transcript_resolved` im calls-commit (nach transcript-commit) und putet ERST DANN die
  `{'event_id'}`-Re-Queue / `{'call_id'}`. Bzw. der Grade-Step prüft selbst `transcript_resolved`
  und no-opt sonst (Event bleibt pending, kein Terminal).
- **Idempotenz-Interaktion (heute):** `_persist_event_ref` re-prozessiert nur `pending` (F-01). Bei
  Deferred bleiben die Events `pending` bis das Transkript da ist → **kein vorzeitiger Terminal-Status**
  → kein Re-Scoring-Block. Genau das Verhalten, das die CONTEXT fordert. Die Idempotenz-Falle entfällt
  strukturell, SOLANGE der Live-Emit-put nicht mehr terminalisiert (s. Pitfall 2).
- **Nichts setzt Events terminal-früh:** verifiziert — der einzige Terminal-Setzer ist
  `_persist_event_ref` (slow_lane.py:239/251/257/270/277), getriggert durch `{'event_id'}`-Puts. Wenn
  diese Puts erst am Call-Ende kommen, gibt es keine vorzeitige Terminalisierung.

### Q6 — Zeit-Brücke konkret + Empfehlung vs. Fork
**Konvertierungs-Problem:** Die naive Formel `ev_ms_in_call = (intent_event.timestamp − calls.started_at)·1000`
ist NICHT direkt gegen `ts_ms` vergleichbar, weil `ts_ms`-Nullpunkt = erste Aussage ≠ `started_at`.
Die fehlende Größe ist `gap = erste_segment_wall_clock − started_at`, die NICHT gespeichert ist.

**Edge-Fälle:**
- **NULL `started_at`:** `calls.started_at` ist nullable (models.py:695). Bei NULL → keine Brücke
  rechenbar → Fallback auf reine ts_ms-Ordnung (Strategie B) ODER Abstention.
- **Zeitzonen:** `intent_event.timestamp` und `calls.started_at` sind beide `timestamptz` (UTC) →
  konsistent. `ts_ms` ist tz-frei (ms). Kein tz-Mismatch, SOLANGE nur Differenzen gerechnet werden.
- **Clock-Skew Emit↔DB:** `emit_intent_event` stempelt mit App-Server-Wall-Clock; transcript-ts kommt
  aus den RAM-Entries (`entry.get('ts')` als 'HH:MM:SS', app_routes.py:36-42) → potenziell andere
  Uhr/Quelle (Deepgram-Stream-Zeit vs. Server-now). **Das macht die absolute Brücke unzuverlässig.**
- **Mitternachts-Wrap:** `_ts_to_ms_of_day` (app_routes.py:36) ist ms-seit-Mitternacht → ein Call über
  Mitternacht wrappt; der Monoton-Klemm fängt's nur teilweise. (Selten, aber real bei
  meeting_consented-Calls über Tage — Prod-Beleg: call 35050386 started 06-03, ended 06-05.)

**Empfohlener Ansatz (für den Plan, Cross-AI bewertet):**
> **Strategie B — Relativ-Ordnung statt absoluter Verankerung.** Verorte den Einwand IM Transkript
> (nicht über die wall-clock-Brücke), dann nimm das nächste `berater`-Segment per `ts_ms`-Ordnung:
> 1. EWB-/UI-Einwände erscheinen SELBST als `kunde`-Segment in transcript_segments (Prod-Beleg:
>    „Kein Bedarf \*ewb button\*", „Zu teuer \*ewb button\*", speaker=kunde). Über `interaction_id`
>    (intent_event.interaction_id ↔ … ) oder `triggering_text`-Match lässt sich das Einwand-Segment
>    finden → dessen `ts_ms` ist der Anker.
> 2. LLM-inferred Einwände (advisor_paraphrase) haben evtl. kein eigenes kunde-Segment — Fallback:
>    grobe Wall-Clock-Brücke NUR zur Reihenfolge-Schätzung (nicht zur exakten Schwelle), dann
>    nächstes berater-Segment.
> 3. Lookup: `transcript_segments WHERE conversation_log_id=X AND speaker='berater' AND ts_ms >= anchor_ts_ms
>    ORDER BY ts_ms ASC, id ASC LIMIT 1`. (`>=` + id-Tiebreak gegen ts_ms-Kollisionen, Pitfall 5.)

**Der Fork (crisp für Cross-AI/Gemini):**

| | Option A — Deferred + ts_ms-Anchor (EMPFOHLEN) | Option B — Realtime transcript_segments-Write |
|---|---|---|
| Kern | Grading auf Call-Ende verschieben, Lookup ts_ms-anchored, Fan-In-Flag `transcript_resolved` | Segmente live/inkrementell schreiben, damit der live-grade-Lookup sie sofort findet |
| Eingriffstiefe | mittel: 1 neue Spalte + Trigger-Verschiebung + Lookup-Fix | hoch: Live-Write-Pfad + Anonymisierungs-Timing umbauen |
| Anonymisierung | unberührt (läuft am Call-Ende wie heute, Pipeline B) | **Pipeline B müsste live laufen** → Latenz/Kosten im Live-Loop (Bau-Regel 1 / Punkt 25 Risiko) |
| Join-Key | `conversation_log_id` erst am Call-Ende — passt zu Deferred | conversation_log_id existiert live noch nicht → braucht zusätzlichen Umbau |
| DSGVO | unverändert | live geschriebene Roh-Segmente = neues PII-Timing-Risiko |
| Latenz Live | null (nur post-call) | nicht-null (Write + Anon pro Segment) |
| Risiko | niedrig (spiegelt erprobtes audio_health_resolved-Muster) | hoch (neue Live-DB-Writes, neue Race-Surface) |

**Research-Empfehlung:** Option A. **Entscheidung NICHT getroffen** — Cross-AI/Gemini bewertet den Fork
(CONTEXT-Auftrag).
