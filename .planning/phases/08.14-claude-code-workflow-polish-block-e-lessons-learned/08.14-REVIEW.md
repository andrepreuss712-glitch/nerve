## Critical Issues

### CR-01: Wrong Table Name in ApiRate Seed — Silent No-Op on Every Startup

**File:** `app.py:881,886`
**Issue:** The SQLAlchemy model `ApiRate` maps to table `api_rates` (plural, confirmed in `database/models.py:581`). The raw SQL seed inside `_migrate()` queries `api_rate` (singular) in both the SELECT check and the INSERT. On SQLite this raises `OperationalError: no such table: api_rate`, which is silently swallowed by the `except Exception as _e` handler at line 891. The seed never runs, the 8 new rate rows are never inserted, and cost tracking for the new model IDs is broken from day one.

**Evidence:**
```python
# models.py line 581
__tablename__ = 'api_rates'   # ← plural

# app.py line 881 — wrong
text("SELECT 1 FROM api_rate WHERE ...")  # ← singular

# app.py line 886 — wrong
text("INSERT INTO api_rate (...)...")     # ← singular
```

**Fix:** Change both raw SQL strings to `api_rates`:
```python
text("SELECT 1 FROM api_rates WHERE provider=:p AND model=:m AND unit_type=:u"),
# ...
text("INSERT INTO api_rates (provider, model, unit_type, price_per_unit, currency, active, source_url) "
     "VALUES (:p,:m,:u,:price,:cur,1,'seed:2026-04-27')"),
```

## Warnings

### WR-01: Idempotency Gap — SELECT Check Ignores `active` Column

**File:** `app.py:880-883`
**Issue:** The `api_rates` table has a `UniqueConstraint('provider', 'model', 'unit_type', 'active', ...)`. The SELECT check at line 880 only filters on `provider`, `model`, `unit_type` — it ignores `active`. If an existing row for the same (provider, model, unit_type) has `active=False` (deactivated rate), the SELECT finds it, skips the INSERT, and leaves no active row for that rate. The seed is not truly idempotent: a soft-deleted rate blocks re-seeding an active replacement.

**Fix:** Add `AND active=1` to the existence check so it only skips when an active rate already exists:
```python
text("SELECT 1 FROM api_rates WHERE provider=:p AND model=:m AND unit_type=:u AND active=1"),
```

### WR-02: Nested `engine.connect()` Inside Outer `engine.connect()` Block

**File:** `app.py:878`
**Issue:** `_migrate()` already holds an open connection via `with engine.connect() as conn:` (line 125). The ApiRate seed block opens a second connection via `with engine.connect() as _conn:` (line 878) while the first is still open. For SQLite this can trigger `database is locked` on write-heavy startup if WAL mode is not enabled, because SQLite allows only one writer at a time. It also wastes a connection from the pool.

**Fix:** Reuse the outer `conn` and commit after the seed loop, consistent with how the rest of `_migrate()` operates:
```python
# Replace: with engine.connect() as _conn:
# Use the outer conn directly:
for _provider, _model, _unit, _price, _currency in _needed:
    _exists = conn.execute(
        text("SELECT 1 FROM api_rates WHERE provider=:p AND model=:m AND unit_type=:u AND active=1"),
        {'p': _provider, 'm': _model, 'u': _unit}
    ).fetchone()
    if not _exists:
        conn.execute(
            text("INSERT INTO api_rates ..."),
            {'p': _provider, ...}
        )
        print(f"[DB] ApiRate seeded: {_model} {_unit}")
conn.commit()
```

### WR-03: Unresolved Blueprint Names for admin_dashboard and admin_ewb

**File:** `routes/CLAUDE.md:56-57`
**Issue:** The Blueprint table lists `admin_dashboard.py` and `admin_ewb.py` with `(pruefen)` in the Blueprint-Name column. Both names are now resolvable from the source: `admin_dashboard_bp = Blueprint('admin_dashboard', ...)` and `admin_ewb_bp = Blueprint('admin_ewb', ...)`. Leaving `(pruefen)` in the table invites incorrect `url_for()` calls — exactly the failure mode the table is meant to prevent.

**Fix:** Update the table rows:
```markdown
| admin_dashboard.py | admin_dashboard_bp   | 'admin_dashboard' |
| admin_ewb.py       | admin_ewb_bp         | 'admin_ewb'       |
```

## Info

### IN-01: ruff Hook — `$CLAUDE_TOOL_INPUT` Passed Through python3, Not Directly to Shell

**File:** `.claude/settings.local.json:64`
**Issue:** The PostToolUse hook pipes `$CLAUDE_TOOL_INPUT` through `python3 -c "import sys,json; ..."` to extract the file path, and only the extracted `$FILE` value reaches `ruff format`. This means arbitrary content in `CLAUDE_TOOL_INPUT` (e.g., a file_path containing shell metacharacters like `;rm -rf`) would only be injected via `$FILE` into the `ruff format "$FILE"` call — which is double-quoted, preventing word splitting. The design is functionally safe against the most common injection vectors. No immediate action required, but note that `ruff format` on a path with newlines embedded would silently fail (the `2>/dev/null` suppresses the error).

**No fix required.** The current design is safe for its use case.

### IN-02: `_seed_founder_dashboard_defaults` Uses Different Guard Condition than `_migrate` Seed

**File:** `app.py:921`
**Issue:** `_seed_founder_dashboard_defaults()` guards ApiRate seeding with `if db.query(ApiRate).count() == 0` — meaning it only seeds when the table is completely empty. The newer `_migrate()` seed (08.14) uses per-row existence checks. These two seed paths target different model names (`haiku-4-5` vs `claude-haiku-4-5-20251001`) and serve different purposes, but if `_seed_founder_dashboard_defaults()` runs first on a fresh DB, it inserts rows with old model names and then the count-check guard prevents any future seeding for the table. The cost dashboard would then show only old model names with no rates for the new versioned IDs. This is a pre-existing design inconsistency, not introduced by 08.14.

**Suggestion:** Document the two seed paths explicitly, or unify the guard logic so both use per-row checks.
