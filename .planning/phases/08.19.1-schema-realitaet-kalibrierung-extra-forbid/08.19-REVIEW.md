## Warnings

### WR-01: `ProfileSchema.schema_version` default is `2`, should be `3`

**File:** `services/profile_schema.py:135`

**Issue:** `ProfileSchema` sets `schema_version: int = 2` as its default. After Phase 08.19.1 all production profiles are on v3 and the Write-Schema exclusively produces v3 documents. A bare `ProfileSchema()` or any write path that does not explicitly pass `schema_version=3` will silently stamp new documents as v2, causing them to be re-migrated on every subsequent startup run. `ProfileReadSchema` has the same default on line 230, which is less critical (read-only) but inconsistent.

**Fix:**
```python
# services/profile_schema.py line 135
schema_version: int = 3   # v3 is canonical after Phase 08.19.1

# services/profile_schema.py line 230
schema_version: int = 3   # Read-Schema — keep consistent with Write-Schema
```

Note: `test_08_19_01_profile_schema.py::test_profile_schema_default_instanziierung` currently asserts `schema_version == 2` (line 32) and will need updating.

### WR-02: `_migration_profile_id` helper key leaks into DB if `_mpd()` raises an unhandled exception

**File:** `app.py` (batch migration block, around line 938-941)

**Issue:** The batch migration injects `_daten['_migration_profile_id'] = _p.id` before calling `_mpd(_daten)`. If `_mpd` raises (e.g. due to an unexpected dict structure that bypasses the `isinstance` guards), the outer `try/except` on line 951 catches the exception and continues, but by that point `_p.daten` has not been written — however the in-memory `_daten` dict already carries the extra key. The bigger risk is the `_daten_migrated.pop('_migration_profile_id', None)` on line 941: if `_mpd` returns early (e.g. `version >= 3` path), the key was already injected into the dict that was **passed by reference** from `_p.daten`, but the early-return path in `_migrate_profile_data` (line 269) returns the original `daten` object unchanged with the extra key still in it. In that case `_version >= 3` check on line 934 prevents writing, so there is no DB corruption — but if a v3 profile somehow reaches `_mpd`, the returned dict will contain `_migration_profile_id`.

More concretely: inject the key **after** the version check or pop it before calling `_mpd`:

**Fix:**
```python
# app.py — batch migration block
_daten['_migration_profile_id'] = _p.id
_daten_migrated = _mpd(_daten)
_daten_migrated.pop('_migration_profile_id', None)  # already present
_p.daten = _json.dumps(_daten_migrated, ensure_ascii=False)
```
This is already the pattern used — the only hardening needed is to set the key *inside* the `if _version < 3` branch so it is never injected on already-migrated profiles:

```python
if _version >= 3:
    _skipped_count += 1
    continue
# Only inject for profiles that actually need migration
_daten['_migration_profile_id'] = _p.id
_daten_migrated = _mpd(_daten)
_daten_migrated.pop('_migration_profile_id', None)
```
The current code already does `continue` before the inject (line 934-936), so this is actually safe. **The real gap** is that `_migrate_profile_data()` itself does not strip the `_migration_profile_id` key before returning, so callers that do not pop it explicitly would persist it. Since `_migrate_profile_data` is a public export used in tests, a stray caller that forgets the pop will write the helper key to the DB.

**Fix (defensive):** Strip the key at the end of `_migrate_profile_data`:
```python
# services/profile_schema.py — end of _migrate_profile_data(), before return daten
daten.pop('_migration_profile_id', None)
return daten
```

### WR-03: `basis`-reference writeback logic has a dead branch that silently drops `basis` when it is an empty dict

**File:** `services/profile_schema.py:374-377`

**Issue:**
```python
if basis:
    daten['basis'] = basis
elif 'basis' in daten and isinstance(daten['basis'], dict):
    daten['basis'] = basis  # leeres dict behalten (sub-schema Default greift)
```
The `elif` branch writes back `basis = {}` only when `basis` was originally present in `daten`. However when `basis` was obtained via the fallback `basis = daten.get('basis') if isinstance(daten.get('basis'), dict) else {}` (line 352), and `daten` had no `basis` key at all (it fell to the `else {}` arm), the `elif` condition `'basis' in daten` is `False`. In that case neither branch fires and `daten['basis']` is never set — which is correct because there was nothing to preserve. This is fine.

The actual dead branch is the `elif` itself: if `basis` is falsy (empty dict) **and** `'basis' in daten`, it writes `daten['basis'] = {}`. This is the intended behaviour per the comment. The logic is correct but the comment "leeres dict behalten" is misleading because it also fires when `basis` was non-empty but all keys were popped (e.g. both `einwaende` and `phasen` removed, leaving an empty dict). In that scenario `daten['basis'] = {}` is written back, which is the right thing to do (prevents KeyError in sub-schema). No bug, but verify the intent:

**Reduced risk — downgrade to INFO if intentional.** Flagged as Warning because the fallthrough of the `if basis:` arm silently loses the write-back when `basis` becomes `{}` due to popping (which is the normal case after v3 migration when `basis` had only `einwaende`/`phasen`). The `elif` recovers it, but only because `'basis' in daten` happens to be `True` at that point. Refactoring to always write back is safer:

```python
# Replace lines 374-377 with:
daten['basis'] = basis   # always write back (empty dict is valid; sub-schema defaults apply)
```

### WR-04: `_BasisReadSchema` still includes `einwaende` and `phasen` fields (stale after v3 promotion)

**File:** `services/profile_schema.py:200-201`

**Issue:** `_BasisReadSchema` defines `einwaende: Any = []` and `phasen: Any = []` on lines 200-201. After Phase 08.19.1 these fields live exclusively at top-level in `ProfileReadSchema` (lines 245-246). The fields in `_BasisReadSchema` are dead — they were kept for `extra='ignore'` drift tolerance during the transition, but they now create a risk: code that reads `profile.basis.einwaende` instead of `profile.einwaende` will silently get an empty list instead of an error, hiding a logic bug.

Since the migration is confirmed complete (all profiles on v3), these dead fields should be removed from `_BasisReadSchema`:

**Fix:**
```python
class _BasisReadSchema(BaseModel):
    model_config = ConfigDict(extra='ignore')
    unternehmen: str = ''
    produktbeschreibung: str = ''
    branche: str = ''
    branche_kontext: str = ''
    usps: Any = []
    preismodell: str = ''
    konsequenz: str = ''
    eigene_formulierungen: Any = []
    beweise: Any = []
    tabu_begriffe: Any = []
    zielkunden: str = ''
    # einwaende and phasen removed — now top-level in ProfileReadSchema (v3)
```

### IN-01: Audit-log write inside `_migrate_profile_data()` silently swallows all errors — failures are invisible

**File:** `services/profile_schema.py:388-406`

**Issue:** The D-03 audit block catches `Exception as _audit_e` and does `pass` (line 405-406). The variable `_audit_e` is bound but never logged. Any DB failure (missing table, constraint violation, connection error) is completely invisible — no print, no log. Per project convention `[Schema]` prefix prints are used for migration events. This is within the established error-handling pattern (`except Exception: pass`) but because this is an explicit D-03 requirement ("Pflicht-Audit-Event"), silent failure is especially misleading.

**Fix:**
```python
except Exception as _audit_e:
    print(f"[Schema] Profile {_profile_id}: audit_log write failed (non-fatal): {_audit_e}")
```

### IN-04: `test_08_19_01_profile_schema.py::test_erlaubnis_transitional` tests nothing useful

**File:** `tests/test_08_19_01_profile_schema.py:82-88`

**Issue:** The test passes `{'erlaubnis': True}` to `_migrate_profile_data()` and only asserts `schema_version == 3`. It does not assert anything about `erlaubnis` — neither that it is preserved nor dropped. The comment says "wird NICHT entfernt" but the test does not verify this. If `erlaubnis` handling changes, the test stays green regardless.

Per project test-quality rules (CLAUDE.md), a test should assert the actual state mutation. Either add `assert result.get('erlaubnis') == True` (if keeping is intentional) or remove the test if the behaviour is intentionally untested until Phase 08.20.

**Fix (minimal):**
```python
def test_erlaubnis_transitional(self):
    result = _migrate_profile_data({'erlaubnis': True})
    assert result.get('schema_version') == 3
    assert result.get('erlaubnis') == True  # transitional: preserved until Phase 08.20
```
