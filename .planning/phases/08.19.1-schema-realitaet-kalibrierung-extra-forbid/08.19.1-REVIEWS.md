## Gemini Review

Here's a structured review of your 5-plan wave structure:

### Overall Risk Assessment: LOW-MEDIUM

The plan is exceptionally detailed and addresses many potential pitfalls. The main risks lie in the
complexity of data migration edge cases and ensuring all local profiles are fully representative of
production. However, the meticulous planning, clear checkpoints, and incremental approach
significantly mitigate these.

---

### Plan-01: Production-DB-Analyse

**Summary:** This plan aims to gather real-world data from the production database to inform
subsequent schema adjustments. It includes steps for secure data extraction and analysis,
culminating in a structured `KEY-FINDINGS.md` document.

**Strengths:**
- **Data-driven approach:** Basing schema changes on actual production data minimizes assumptions and potential errors.
- **Security conscious:** Explicitly mentions `.gitignore` for the dump and SSH-Key-Auth, along with sanitizing the `KEY-FINDINGS.md` from sensitive free text.
- **Clear output:** The `KEY-FINDINGS.md` with specific sections ensures the analysis is focused and actionable.

**Concerns:**
- MEDIUM — Python Analysis Script Robustness: The plan assumes the Python script for analysis will correctly identify all keys and their types, especially handling nested structures or varying data types across profiles. Any error here could propagate to later stages.
- LOW — Data Volume Impact: For very large databases, the analysis script's performance could be a factor, though not explicitly mentioned.

**Suggestions:**
- Consider adding a step to validate the Python analysis script against a small, known subset of production data or a synthetic dataset that covers expected variations.
- Specify if the analysis script will handle JSON data types robustly (e.g., distinguishing between `null`, `[]`, and `absent` if `get()` returns `None`).

**Risk Assessment:** LOW. The plan is solid, and the minor concerns are about the implementation details of the analysis script rather than the strategy itself.

### Plan-02: Schema-Kalibrierung

**Summary:** This plan focuses on updating `services/profile_schema.py` to align with the real
production data discovered in Plan-01, specifically handling the `einwaende` and `phasen` fields
and removing `fragen`. It emphasizes maintaining read compatibility for older profiles.

**Strengths:**
- **Targeted changes:** Clearly identifies which schemas to modify and how (`BasisSchema`, `ProfileSchema`, `ProfileReadSchema`).
- **Backward compatibility:** Explicitly states that `_BasisReadSchema` will not be changed to maintain compatibility with older profiles, which is crucial.
- **Incremental strictness:** Keeping sub-schemas at `extra='ignore'` until Plan-05 is a good safety measure, preventing premature validation errors.
- **Key Decision D-01:** Clearly documents the type change for `einwaende` to `List[dict]`, indicating a deep understanding of the data evolution.

**Concerns:**
- MEDIUM — Scope of "Ungemappte Keys": While `Ungemappte Keys` are checked, the plan doesn't explicitly detail the action to take if significant unmapped keys are found that are *not* `einwaende`/`phasen`. This could lead to difficult decisions at this stage.
- LOW — Smoke Test Coverage: "Smoke-Test against all local profiles" is good, but if local profiles don't perfectly reflect the diversity of production profiles, some edge cases might be missed.

**Suggestions:**
- Define a clear process for handling `Ungemappte Keys` from `KEY-FINDINGS.md` that are not `einwaende`/`phasen`. Options include adding them to the schema, deciding they are truly dead fields, or flagging them for further investigation.
- Consider creating a representative set of local test profiles that cover the identified variations from `KEY-FINDINGS.md` for more robust smoke testing.

**Risk Assessment:** LOW. The plan is well-defined, and the concerns are about the thoroughness of edge case handling, which can be addressed with minor additions.

### Plan-03: `_migrate_profile_data()` v2→v3

**Summary:** This plan details the implementation of the `v2→v3` migration logic within
`_migrate_profile_data()`, focusing on specific merge semantics for `einwaende` and `phasen`,
removal of dead fields, and a `schema_version` bump. It includes robust testing with specific
assertions and the use of a `__MISSING__` sentinel.

**Strengths:**
- **Precise Merge Semantics (D-02):** The explicit definition of how `absent`, `[]`, `null`, and `existing` keys are handled is excellent and crucial for a reliable migration. This foresight prevents common data loss or corruption issues.
- **`__MISSING__` Sentinel:** Elegant solution to disambiguate `None` from `absent`, significantly enhancing migration logic robustness.
- **Detailed Test Assertions:** 8 specific test cases cover critical scenarios and ensure the migration logic behaves as expected.
- **Idempotency:** Designing the migration to be idempotent (Test 7) is a best practice, making re-runs safe.
- **Guard Change:** The `if version >= 3: return daten` guard ensures that profiles already migrated to v3 are skipped.

**Concerns:**
- LOW — Test Count Discrepancy: The plan mentions "8 Test-Assertions inline" but "Acceptance: All 7 Test-Assertions". This should be clarified to ensure all planned tests are implemented.
- LOW — `basis.pop()` behavior: While `basis.pop()` is mentioned as safe (T-08191-09), ensuring `basis` itself doesn't remain as `basis: {}` in migrated profiles (if it becomes empty) may be worth verifying — or explicitly accepting.

**Suggestions:**
- Confirm the exact number of test assertions (7 or 8) and ensure they are all implemented.
- Verify behavior when the `basis` dictionary becomes empty after fields are moved: should `basis: {}` remain (Sub-Schema defaults greifen) or be omitted? Plan-03 body says "leeres dict behalten" — this should be explicit in acceptance criteria.

**Risk Assessment:** LOW. Exceptionally well-thought-out, addressing complex data migration with a high degree of precision and testability.

### Plan-04: DB-Level Batch-Migration

**Summary:** This plan outlines the process for performing a batch migration of all production
profiles to v3 at app startup, leveraging the idempotent `_migrate_profile_data()` from Plan-03.
Prioritizes app startup stability and includes a human checkpoint.

**Strengths:**
- **Idempotency:** Leveraging the idempotent migration logic from Plan-03 ensures safety during re-runs.
- **Error Handling:** The outer `try/except` to prevent app startup blocking is a critical safety measure.
- **Auditability:** The `_migration_profile_id` mechanism provides clear per-profile tracking in logs.
- **Human Checkpoint:** Explicit human verification step before proceeding to Plan-05 is excellent.

**Concerns:**
- MEDIUM — Performance Impact at Startup: Migrating all profiles at app startup could cause a delay or resource spike. While `try/except` prevents blocking, the duration of migration could impact initial availability.
- LOW — Human Checkpoint Ambiguity: "Alle Profile auf v3 verifizieren" is general. A specific query method should be specified (e.g., Python script querying schema_version).

**Suggestions:**
- For larger datasets: consider noting whether this is acceptable at startup or if a background thread would be more appropriate. For NERVE's current scale (6 Production profiles), startup migration is fine — document this assumption.
- Specify the method for "Alle Profile auf v3 verifizieren" — the Python DB-check script already in the plan body is good; link to it explicitly in the checkpoint.

**Risk Assessment:** MEDIUM (at scale); LOW for NERVE's current profile count. Robust approach, with clear startup safety.
