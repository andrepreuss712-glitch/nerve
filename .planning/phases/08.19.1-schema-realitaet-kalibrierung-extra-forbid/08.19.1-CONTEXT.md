<decisions>
## Implementation Decisions

### D-01: Drift-Keys-Strategie — Top-Level legalisieren

Editor-Realität schlägt Schema-Theorie (CLAUDE.md Nudelcode-Regel 1):
- `einwaende: List[dict] = []` und `phasen: List[dict] = []` in `ProfileSchema` top-level aufnehmen
- `BasisSchema.einwaende` und `BasisSchema.phasen` entfernen (Dead Schema Fields — Editor schreibt nie dort hin)
- `branche` top-level in `_migrate_profile_data()` v2→v3 entfernen (`Profile.branche` DB-Column ist die neue Quelle seit Phase 08)

**Verifikationsbefund (lokal):**
- Profile 1 (NERVE Vertrieb): `einwaende` + `phasen` NUR top-level (basis.* = NOT_PRESENT)
- Profile 2/3/4 (Demo): `einwaende` + `phasen` NUR in `basis.*` (top-level fehlt) + top-level `branche`
- Bestätigt: Beide Formate existieren in Production → Merge-Migration zwingend

### D-02: Merge-Strategie einwaende + phasen (v2→v3)

**"Top-Level gewinnt, basis.* als Fallback"** — Editor ist kanonische Schreib-Quelle.

Exakte Semantik für "top-level fehlt" (kein Ambiguität erlaubt):
- Key **existiert nicht** → `basis.*` nach top-level hochziehen, dann `basis.*` droppen
- Key **existiert mit `[]`** (leeres Array) → `basis.*` NICHT hochziehen (User-Intent "alles gelöscht" respektieren)
- Key **existiert mit `null`** → wie "nicht vorhanden" → `basis.*` hochziehen

Gilt für `einwaende` und `phasen` jeweils unabhängig.

### D-03: Schema-Version v3-Bump

`_migrate_profile_data()` bekommt eine zweite Stufe:
```python
# Stufe 1: v1 → v2  (Phase 08.19 — unverändert)
# Stufe 2: v2 → v3  (Phase 08.19.1 — Kalibrierung)
if version < 3:
    # ... alle v3-Migrations-Steps
    daten['schema_version'] = 3
```

Idempotenz: `if schema_version >= 3: return daten` (analog zu v2-Check).

**Pflicht-Audit-Event pro Profil** (als `print`-Log analog zu bestehenden `[DB]`-Events):
```
[Schema] Profile {id}: v2→v3 applied — dropped fragen, upward-merged basis.einwaende→einwaende, upward-merged basis.phasen→phasen, dropped branche top-level
```

### D-04: Sub-Schema Scope — ALLE Sub-Schemas strict

ALLE Sub-Schemas erhalten `extra='forbid'` (nicht nur Top-Level):
- `BasisSchema`, `ZielgruppeSchema`, `ZielkundeSchema`, `ValueSchema`, `EinwandDetailSchema`, `KiSchema`, `SchmerzenSchema`, `MetaSchema`
- Verhindert Drift "unter dem Radar" in Sub-Schemas
- Production-Profile müssen nach Kalibrierung alle Sub-Schemas strict durchlaufen

### D-05: fragen-Key-Removal in v2→v3

Standard idempotente Migration:
```python
daten.pop('fragen', None)  # war gesetzt auf [] in 08.19.3, jetzt komplett raus
```

Schema: `fragen`-Feld aus `ProfileReadSchema` entfernen (falls vorhanden).

### D-06: Production DB als Plan-01 Spec-Input

**Reihenfolge:** Hetzner-Pull ZUERST, dann Schema-Änderungen — nicht umgekehrt.
