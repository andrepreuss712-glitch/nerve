### 5. Legacy opener Situation

**Why Block I deferred it:** The `opener` vs. `openerItems` dual-schema in `pip-launcher.js` is a backward-compatibility fallback, not a Classic-view artifact.

**What it is:**
- `openerItems` = new schema: separate `ProfileOpener` DB records, loaded via `/api/launcher/init` → `opener_items` array
- `profileDaten.opener` = legacy schema: opener text stored directly in `Profile.daten` JSON as a flat `'opener'` key

**Where the fallback lives:**
```javascript
// pip-launcher.js lines 460, 486, 488, 988-989, 1703-1704
var legacyOpener = (state.profileDaten && state.profileDaten.opener) ? state.profileDaten.opener : '';
// ...used as fallback in 3 places when openerItems array is empty
```

**Why Block I didn't remove it:** The `profileDaten.opener` key could still exist in real production profiles that were created before the `ProfileOpener` table existed (i.e., profiles created before Phase 04.17). Removing the fallback would silently break those users' opener display.

**Why Block F should include it:** The audit (MASTER-AUDIT-v2 MEDIUM section) lists `opener vs. openerItems Doppel-Schema` as a frontend legacy item to clean up. Block I explicitly deferred to Block F.

**What the cleanup looks like:**
- In `pip-launcher.js`: remove the 3 `legacyOpener` / `profileDaten.opener` fallback branches (lines ~460, 486, 488, 988-989, 1703-1704)
- No backend change needed: `/api/launcher/init` already returns `opener_items` from the `ProfileOpener` table
- Risk: if any production profile still uses the flat `opener` key in JSON, their opener disappears silently. Mitigation: run a one-time DB check or accept that Block C's BRANCHE_TEMPLATES migration already normalizes profiles — new profiles use the correct schema.

**Planner note:** This is low-blast-radius since all profiles created since Phase 04.17 use `openerItems`. The fallback is a legacy-compatibility dead branch for the current EA cohort (0 users yet).

#### Risk: /live Redirect Breaks Things?

The `/live` route currently does significant setup work:
- Fair-Use check and monthly reset (lines 42-80)
- Profile loading into `ls.set_active_profile()` (line 116)
- Learning cards loading (line 118)

After Classic deletion: these will NOT run when user visits `/live` (they just get redirected). However, PiP launcher already handles all of this via `/api/launcher/init` and the `start_live_session` socket event. No regression.

#### Risk: api_beenden still uses quick_action_log

`api_beenden()` at line 362-363 reads `len(ls.quick_action_log)` and stores it as `quick_actions` in `ConversationLog`. The `quick_action_log` is populated by `/api/frage` and `/api/ewb_trigger`. After deletion, it will always be empty (0) for PiP sessions.

**Assessment:** `quick_actions=0` for all PiP sessions is correct and acceptable. PiP does not use the Classic "Frage stellen" or HTTP EWB flow. The `quick_action_log` field in `ConversationLog` becomes unused but harmless.

**Do NOT remove quick_action_log from live_session.py** — the `_build_log_content()` function uses it for the session log text file. This is a minor cosmetic thing (will always show 0).

#### Risk: OBJECTION_TRIGGER_PROMPT_BASE deletion

Do NOT delete `OBJECTION_TRIGGER_PROMPT_BASE` from `app_routes.py` until verifying whether `app.py:_seed_prompt_versions()` imports it. If the import is removed from app.py, the constant becomes unused and can be deleted. If the seed entry for `'objection_trigger'` is kept (it should be — the EWB pipeline uses this PromptVersion), then the import stays, meaning `OBJECTION_TRIGGER_PROMPT_BASE` stays as a module-level constant even without the HTTP route that used it.

**Recommendation:** Keep `OBJECTION_TRIGGER_PROMPT_BASE` constant. Remove the import of `API_FRAGE_PROMPT_BASE` from app.py and remove the `'api_frage'` tuple from the `modules` list.

#### Risk: _SuppressPolling in app.py

After `/api/ergebnis` deletion: `_SuppressPolling.filter()` still references `'/api/ergebnis'`. The filter class is harmless (it just filters log messages for routes that no longer exist — meaning no messages ever match). But it's misleading dead code. Block F should remove the entire `_SuppressPolling` class and the `logging.getLogger('werkzeug').addFilter(...)` call (lines 14-19 of app.py). `/api/status` was already deleted in Block I.
