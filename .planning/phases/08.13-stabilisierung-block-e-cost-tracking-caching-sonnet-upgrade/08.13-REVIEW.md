# Phase 08.13: Code Review Report

**Reviewed:** 2026-04-26T12:00:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

This phase introduced model-string migration to `config.MODEL_*` constants, prompt-caching hooks with a 16 000-character threshold, per-call latency/call_site fields on `ApiCostLog`, and a user_id threading helper for background threads. The changes are structurally sound and follow the "MUST NOT raise" contract for cost hooks. However, several correctness issues stand out: the cache threshold is set at 16 000 chars but Anthropic requires a minimum of **1 024 tokens (~4 000 characters)** not 16 000, so the cache is permanently disabled in practice for every current system prompt, wasting the feature entirely. Additionally, several cost hooks log cache tokens against the wrong model string (`sonnet-4-5` instead of `haiku-4-5`), and `precall_service` references `MODEL_PRECALL` in config but logs cost against a hardcoded `'sonnet-4-5'` string rather than the config constant — a model-migration miss. `coaching_service` and `coaching_service`'s weekly report hook similarly use hardcoded `'sonnet-4-5'` strings instead of the relevant config constants. These are not crashes but silently poison cost-tracking accuracy.

## Critical Issues

### CR-01: Cache threshold 16 000 chars never triggers — prompt caching permanently disabled

**File:** `services/claude_service.py:482`, `services/claude_service.py:571`, `services/claude_service.py:671`, `services/qa_pipeline.py:412`

**Issue:** All four caching branches gate on `len(system_prompt) >= 16000`. The Anthropic minimum cache threshold is **1 024 tokens**, not 16 000 characters (roughly 4 000 chars). The longest system prompt in this codebase (`SYSTEM_PROMPT_BASE` + profile context) rarely exceeds ~4 000–6 000 characters. The `_ewb_autovar_system` and `_ewb_manual_system` strings are ~85 chars each — they will never reach 16 000. The QA system prompt (`_SYSTEM_PROMPT_QA` formatted with profile data) is typically under 500 chars. Result: `CACHE_EWB=true` and `CACHE_QA=true` are set in config but the cache branch is dead code for every current prompt. Zero cache hits, zero cache writes, feature silently disabled.

**Fix:** Lower threshold to the Anthropic minimum of ~4 096 chars (safe margin above the 1 024-token hard minimum). Example correction for all four sites:

```python
# Before
if config.CACHE_EWB and len(_ewb_autovar_system) >= 16000:

# After
_CACHE_MIN_CHARS = 4096  # Anthropic minimum: 1024 tokens ≈ 4096 chars
if config.CACHE_EWB and len(_ewb_autovar_system) >= _CACHE_MIN_CHARS:
```

Apply the same change in `claude_service.py:571` (autovar), `claude_service.py:671` (manual EWB), `claude_service.py:482` (analyse), and `qa_pipeline.py:412` (QA response). Note: `_ewb_autovar_system` (85 chars) and `_ewb_manual_system` (~95 chars) will still not reach 4 096 chars — those two call sites will correctly remain uncached unless the system prompt is enriched with profile context.

## Warnings

### WR-01: Cache token cost logged against wrong model string (`sonnet-4-5` instead of `haiku-4-5`)

**File:** `services/claude_service.py:612-618`, `services/claude_service.py:735-742`

**Issue:** In `streame_auto_variante` and `streame_manual_ewb_variante`, the cache-read and cache-write cost rows are logged with `model='sonnet-4-5'` even though both functions call `config.MODEL_PIP_AUTOVAR` / `config.MODEL_PIP_VARIANTE` which map to `claude-haiku-4-5-20251001`. The regular input/output token rows on lines 601-607 and 726-731 correctly use `'haiku-4-5'`, but the cache rows flip to `'sonnet-4-5'`. This causes incorrect rate lookups in `ApiRate` and inflated cost calculations.

```python
# Wrong (lines 612–618 and 735–742)
log_api_cost('anthropic', 'sonnet-4-5', user_id=None,
             units=_cache_hits/1000.0, unit_type='per_1k_cache_read_tokens',
             context_tag='ewb', call_site='ewb')

# Correct — match the model actually used
log_api_cost('anthropic', 'haiku-4-5', user_id=None,
             units=_cache_hits/1000.0, unit_type='per_1k_cache_read_tokens',
             context_tag='ewb', call_site='ewb')
```

Same fix for the `cache_creation_input_tokens` rows immediately below.

### WR-02: Same wrong-model bug in `qa_pipeline.py` cache token logging

**File:** `services/qa_pipeline.py:466-472`

**Issue:** `generate_qa_response` calls `config.MODEL_QA` (= `claude-sonnet-4-5`), which is Sonnet. The regular token rows on lines 454-461 use `'haiku-4-5'` — this is wrong for this call site itself (QA response uses MODEL_QA which is Sonnet, not Haiku). The cache rows on lines 466-472 then also use `'sonnet-4-5'` which is at least a consistent model name, but the regular rows should also say `'sonnet-4-5'` since MODEL_QA is Sonnet. Either the MODEL_QA assignment in config is intentional (Sonnet for QA responses) and both cost rows should log `'sonnet-4-5'`, or MODEL_QA should be Haiku. Currently the regular rows say `haiku-4-5` but the model called is `claude-sonnet-4-5` — a model mismatch that produces wrong rates.

**Fix:** Use the config constant directly in cost logging instead of a hardcoded string:

```python
_model_short = 'sonnet-4-5' if 'sonnet' in config.MODEL_QA else 'haiku-4-5'
log_api_cost('anthropic', _model_short, user_id=None, ...)
```

Or simpler — store the short name as a local variable once per function:

```python
_cost_model = 'haiku-4-5'   # in classify_utterance (MODEL_ANALYSE = haiku)
_cost_model = 'sonnet-4-5'  # in generate_qa_response (MODEL_QA = sonnet)
```

### WR-03: `precall_service` logs cost against hardcoded `'sonnet-4-5'` — model migration miss

**File:** `services/precall_service.py:176-182`

**Issue:** `_generiere_briefing` calls `config.MODEL_PRECALL` (which is `claude-sonnet-4-5`), so the Sonnet string is technically correct here. However, the cost logging uses the hardcoded literal `'sonnet-4-5'` instead of a derived string. More importantly, the config comment on line 53 says `MODEL_PRECALL` is Sonnet, but the module's own header comment (line 4) says "Kein Sonnet (CLAUDE.md Constraint: nur Haiku fuer alles Live)". This is a contradiction: `MODEL_PRECALL` resolves to Sonnet which violates the CLAUDE.md "Haiku only for live" constraint. PreCall is triggered by the live interface, so this may be an intentional policy change from the phase, but it is undocumented and inconsistent with the module header.

**Fix:** Either update the module header to reflect the Sonnet decision, or change `MODEL_PRECALL` to a Haiku variant. Separately, replace the hardcoded string with a derived reference:

```python
# Instead of hardcoded 'sonnet-4-5', derive from config:
_cost_model = 'sonnet-4-5' if 'sonnet' in config.MODEL_PRECALL else 'haiku-4-5'
log_api_cost('anthropic', _cost_model, user_id=user_id, ...)
```

### WR-04: `coaching_service` cost hooks use hardcoded `'sonnet-4-5'` — should reference config constants

**File:** `services/coaching_service.py:94-101`, `services/coaching_service.py:327-334`

**Issue:** `generate_postcall_analysis` (line 94) and `get_or_generate_weekly_report` (line 327) both call the respective `config.MODEL_POSTCALL_ANALYSIS` and `config.MODEL_WEEKLY_SUMMARY` constants to select the model, then hardcode `'sonnet-4-5'` in the cost-tracking calls. If either config constant is overridden via env var to a Haiku model, the cost rows will log the wrong model string and hit the wrong `ApiRate` row.

```python
# Current (line 94-98)
log_api_cost('anthropic', 'sonnet-4-5', user_id=user_id,
             units=..., unit_type='per_1k_input_tokens',
             context_tag='postcall_coach')

# Fix — derive from the actual model used:
_cost_model = 'sonnet-4-5' if 'sonnet' in config.MODEL_POSTCALL_ANALYSIS else 'haiku-4-5'
log_api_cost('anthropic', _cost_model, user_id=user_id, ...)
```

Same pattern applies to the weekly report cost hook at lines 327-334 (reference `config.MODEL_WEEKLY_SUMMARY`).

### WR-05: `training_service.generate_help_suggestion` cost hook logs `'sonnet-4-5'` but model is `MODEL_TRAINING_HELP`

**File:** `services/training_service.py:1032-1038`

**Issue:** `generate_help_suggestion` calls `config.MODEL_TRAINING_HELP` (= `claude-sonnet-4-5` by default). The cost hook at lines 1032-1038 hardcodes `'sonnet-4-5'`, which happens to be correct for the default. However, `_generate_live_preview` (line 1320-1326) uses `config.MODEL_TRAINING_PREVIEW` (= `claude-haiku-4-5-20251001`) but logs cost as `'haiku-4-5'` — correctly. Both are inconsistently using hardcoded strings. The `generate_scoring` hook (line 1234-1240) also hardcodes `'sonnet-4-5'` against `MODEL_TRAINING_SCORING`. The pattern should be uniform: derive from config.

**Fix:** For each cost hook in training_service, replace the hardcoded model string with a derived expression, or define a local `_cost_model` variable bound to the actual config constant before the API call.

### WR-06: `crm_service` logs `latency_ms` only on the input-token row, not on the output-token row

**File:** `services/crm_service.py:73-76`

**Issue:** The CRM cost hook (lines 71-76) passes `latency_ms=_latency_ms` and `call_site='crm'` to the input-token `log_api_cost` call, but the output-token call on line 74-76 omits `latency_ms`. This is not a data-loss bug (latency is captured once per API call on the input row), but it creates an asymmetry with other call sites that omit latency on the output row too — and the inconsistency makes cost analysis queries that join on `latency_ms IS NOT NULL` produce confusing results. Minor but worth standardising.

**Fix:** Either pass `latency_ms=_latency_ms` to both calls, or pass it to neither (and only use the input row for latency). The existing pattern in other services (e.g., `precall_service.py:176-182`) omits latency on the output row as well, so the CRM input-row passing of `latency_ms` is the outlier.

### WR-07: `deepgram_service` STT accumulation dict `_stt_seconds_accumulated` is read and written without `_sessions_lock` in the hot path

**File:** `services/deepgram_service.py:81`

**Issue:** `_stt_seconds_accumulated[sid]` is incremented inside `on_message` at line 81 (called from Deepgram's background thread), while `_close_deepgram_connection` pops from the same dict at line 251 inside `_sessions_lock`. The increment at line 81 is NOT inside `_sessions_lock`, creating a race: if `_close_deepgram_connection` fires concurrently while `on_message` is incrementing, `pop` could complete and return `0.0`, and the subsequent increment creates a new orphaned key — the STT seconds are lost. This is a data-correctness issue (not a crash) because the read in `_close_deepgram_connection` happens inside the lock but the write does not.

```python
# Current (line 79-81) — unguarded write
_dur = getattr(getattr(result, 'metadata', None), 'duration', 0.0) or 0.0
if _dur > 0:
    _stt_seconds_accumulated[sid] = _stt_seconds_accumulated.get(sid, 0.0) + _dur

# Fix — guard with _sessions_lock
_dur = getattr(getattr(result, 'metadata', None), 'duration', 0.0) or 0.0
if _dur > 0:
    with _sessions_lock:
        _stt_seconds_accumulated[sid] = _stt_seconds_accumulated.get(sid, 0.0) + _dur
```

Note: CPython's GIL makes dict operations atomically safe for single-key read-modify-write at the bytecode level, so a crash is unlikely — but the race between pop-in-close and increment-in-message can still cause the pop to win and subsequently lose the accumulated seconds for the last few packets. The fix eliminates the ambiguity.

## Info

### IN-01: `config.MODEL_*` constants use non-canonical model strings

**File:** `config.py:48-68`

**Issue:** The MODEL_* constants use strings like `"claude-sonnet-4-5"` and `"claude-haiku-4-5-20251001"`. The Sonnet models lack the date suffix while the Haiku models have one. Anthropic's API accepts both, but for consistency and auditability all model IDs should use the same format. If Anthropic deprecates the un-versioned alias, only Sonnet calls will break silently.

**Fix:** Use the fully versioned string for all models, e.g., `"claude-sonnet-4-5-20251001"` for Sonnet, matching the pattern already used for Haiku. Verify the exact version string in Anthropic's model list.

### IN-02: `_resolve_user_id_from_live_session` and `_resolve_org_id_from_live_session` duplicated, no unit for background-thread user_id

**File:** `services/cost_tracker.py:31-48`

**Issue:** The two helper functions are nearly identical (both read a single key from `ls.state` under `state_lock`). They could be merged into `_resolve_from_live_session(key)`. More importantly, all cost hooks that call `log_api_cost(..., user_id=None, ...)` from background threads (analyse_loop, coaching_loop, PiP stream threads) rely on these fallbacks. But several hooks — specifically `analysiere_mit_claude` (line 502-507), `analysiere_coaching` (line 783-788), `classify_phase` (line 342-347), `infer_customer_state` (line 413-419), and all QA pipeline calls — still pass `user_id=None` without threading any user context through the call signature. The fallback correctly reads from `ls.state['user_id']`, so this works in practice — but it creates an invisible dependency: if `cost_tracker.py` is called from a context where `live_session` is not imported or `ls.state` has no `user_id` (e.g., unit tests, training context), the cost row will have `user_id=NULL` silently.

**Fix:** No immediate action required for production. For clarity, consider adding a comment at each `user_id=None` call site in background thread contexts to document that user_id is resolved via `_resolve_user_id_from_live_session`.

### IN-03: `learning.py` H-22 exception handling pattern is correct but swallows stacktrace

**File:** `routes/learning.py:47-49`

**Issue:** `api_postcall_analysis` catches `Exception as _e` and returns a generic `{'ok': False, 'error': 'internal error'}` without logging the full traceback. The `print(f"[Learning] api_postcall_analysis Fehler: {_e}")` only logs the exception message, not the traceback. For background analysis failures this makes debugging non-obvious. The existing pattern in the codebase uses `import traceback; traceback.print_exc()` in some places, but not here.

**Fix:** Add `import traceback; traceback.print_exc()` inside the except block, or log `repr(_e)` to capture exception type.

### IN-04: `CACHE_ANALYSE` default is `false` in config but `print` always fires regardless of cache state

**File:** `services/claude_service.py:486-487`

**Issue:** The `[Cache-Check]` print lines fire on every analyse_loop call (line 486-487 and line 575-576, 675-676), even when `CACHE_ANALYSE=false`. In production with 4-second intervals this generates verbose log noise. Same applies to the three EWB and QA cache-check prints.

**Fix:** Guard the print behind the cache flag or a debug-level check:

```python
if config.CACHE_ANALYSE:
    print(f"[Cache-Check] analyse system_prompt: {len(_system_prompt)} chars ...")
```
