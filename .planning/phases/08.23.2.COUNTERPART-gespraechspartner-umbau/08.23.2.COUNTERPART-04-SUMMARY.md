## Rollback-Betrachtung (Auftrag: wörtlich ins SUMMARY)

> Zwischen Migration und Code-Deploy läuft für einen kurzen Moment **alter Code gegen den neuen Constraint**. Der alte Code schreibt `event_type='mode_initial'` → der Constraint lehnt ab. Das ist **gutartig**, weil **beide Event-Writer non-fatal** sind:
>
> | Writer | Stelle | Verhalten im Fehlerfall |
> |---|---|---|
> | Initial-Event | `services/live_session.py:747` | `except` → `print(...)`, die Call-Anlage läuft weiter |
> | Umschalt-Event | `services/deepgram_service.py:1194` | `except` → `print(...)`, der Toggle wirkt trotzdem |
>
> Folge: im Zwischenfenster geht höchstens **ein Protokoll-Eintrag** verloren — kein Anruf bricht ab, kein Nutzer merkt etwas. Dasselbe gilt für einen Rollback des Code-Deploys: der alte Code kann gegen den neuen Constraint weiterlaufen, er verliert nur die zwei Events. **Deshalb braucht diese Umbenennung keinen Expand/Contract-Zweischritt** — die Kosten des Halb-Zustands wären höher als sein Nutzen.

Verifiziert, dass die Fehler-Toleranz beider Writer **unverändert** ist: `live_session.py` `try/except` + `finally: _db_mi.close()` + `print(...)`; `deepgram_service.py` `except` → `rollback()` → `print(...)` (DB-Regel: kein stiller `except` auf einer Session ohne `rollback`). Nur der String-Literal-Wert und die Log-Texte wurden ersetzt.
