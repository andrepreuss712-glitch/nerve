### Warum die Reihenfolge Migration → Code gefahrlos ist (Rollback-Betrachtung)

Zwischen Migration und Code-Deploy läuft für einen kurzen Moment **alter Code gegen den neuen
Constraint**. Der alte Code schreibt `event_type='mode_initial'` → der Constraint lehnt ab. Das
ist **gutartig**, weil **beide Event-Writer non-fatal** sind:

| Writer | Stelle | Verhalten im Fehlerfall |
|---|---|---|
| Initial-Event | `services/live_session.py:747` | `except` → `print(...)`, die Call-Anlage läuft weiter |
| Umschalt-Event | `services/deepgram_service.py:1194` | `except` → `print(...)`, der Toggle wirkt trotzdem |

Folge: im Zwischenfenster geht höchstens **ein Protokoll-Eintrag** verloren — kein Anruf bricht ab,
kein Nutzer merkt etwas. Dasselbe gilt für einen Rollback des Code-Deploys: der alte Code kann
gegen den neuen Constraint weiterlaufen, er verliert nur die zwei Events. **Deshalb braucht diese
Umbenennung keinen Expand/Contract-Zweischritt** — die Kosten des Halb-Zustands wären höher als
sein Nutzen.

⚠ Diese Rollback-Betrachtung ist Teil des Auftrags und gehört **wörtlich ins SUMMARY**.
