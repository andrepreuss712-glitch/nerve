## ⚠ KRITISCHE KORREKTUR DER ROADMAP-HYPOTHESE (vor allem anderen lesen)

Die Roadmap (Task 1) vermutet die Wortteil-Bug-Root-Cause in einem **nackten `str.replace(token, tag)` in der NER-Replace-Mechanik** (`_apply_ner`). **Das ist FALSCH.** Code-Beweis:

- `_apply_ner()` (anonymization.py:293-301) ersetzt **bereits korrekt span-/offset-basiert** und **rückwärts** (`for start, end, ... in reversed(unique_spans): result = result[:start] + token + result[end:]`). Das ist exakt der "richtige" Algorithmus, den die Roadmap als Fix vorschlägt — er ist im INPUT-Pfad schon implementiert.
- Der Wortteil-Bug (`ausführl[PERSON_C]e`, `wirkl[PERSON_C]`) entsteht im **OUTPUT-Pfad**: `anonymize_output()` (anonymization.py:485-488) macht ein **nacktes `text.replace(original, token)`** über den ganzen Claude-Text. Wenn `cache.mapping` einen Eintrag `'ich' → '[PERSON_C]'` enthält (Pronomen das im Input-Pfad fälschlich als PERSON getaggt wurde), ersetzt `'ich'` als **Substring** mitten in `wirklich`/`ausführliche`.

**Konsequenz für den Plan:** Der Fix ist zweigeteilt und greift an ZWEI Stellen:
1. **Task 2 (Pronomen-Whitelist) ist die eigentliche Root-Cause-Behebung** — verhindert dass `'ich'/'Sie'/...` überhaupt in `cache.mapping` landen. Damit verschwindet der Wortteil-Bug + die Über-Schwärzung gleichzeitig.
2. **Task 1 (Wortteil-Bug) muss in `anonymize_output()` gefixt werden** (Wortgrenzen-Replace via Regex `\b...\b`), NICHT in `_apply_ner()`. `_apply_ner` ist schon korrekt — dort ist KEINE Änderung nötig (und wäre schädlich).

Diese Korrektur ist Punkt-22-konform belegt: jeder Code-Pfad unten mit `file:line` + Real-Daten-Beleg.

## Task-für-Task Implementierungs-Hinweise

### Task 1 — Wortteil-Bug fixen (Ziel: `anonymize_output`, NICHT `_apply_ner`)

**Datei/Zeilen:** `services/anonymization.py:466-488` (`anonymize_output`).
**Heutiger Code (Bug):**
```python
for original, token in items:
    if original in text:
        text = text.replace(original, token)   # ← Substring-Replace, Wortteil-Bug
```
**Fix (Wortgrenzen-Replace):** Pro Mapping-Key wortgrenzen-gebunden ersetzen. Für deutsche Tokens mit Umlauten ist `\b` brauchbar, aber `re.UNICODE` (Default in py3) + `re.escape(original)`:
```python
import re
for original, token in items:               # items bereits nach len absteigend sortiert (Partial-Match-Schutz bleibt)
    pattern = r'\b' + re.escape(original) + r'\b'
    text = re.sub(pattern, lambda _m: token, text, flags=re.UNICODE)
```
**Vorsicht:** `\b` greift NICHT sauber wenn `original` mit Nicht-Wortzeichen beginnt/endet (z.B. "Dr. Mueller", IBAN-Tokens mit Leerzeichen). Für mehrteilige Keys (`Dr. Mueller`, `Commerzbank AG`) ist `\b...\b` weiterhin korrekt an den äußeren Grenzen. Edge-Case dokumentieren: Keys die auf `.`/Ziffer enden → `\b` sitzt nach dem letzten Wortzeichen. Lieber konservativ: `(?<!\w)` … `(?!\w)` Lookarounds statt `\b` (robuster bei Umlaut-Grenzen):
```python
pattern = r'(?<!\w)' + re.escape(original) + r'(?!\w)'
```
**Real-Daten-Validation (Punkt 13, Production-only):** Nach Deploy 1× Cold-Call mit identischem NERVE-Skript fahren, `inspect.sh logs` / Log-Pull → prüfen dass `ausführliche`/`wirklich` **unversehrt** im PAINPOINT stehen.

**Längere-Keys-zuerst bleibt:** `items = sorted(cache.mapping.items(), key=lambda x: len(x[0]), reverse=True)` (Zeile 484) NICHT entfernen — schützt `Dr. Mueller` vor `Mueller`.

### Task 3 — GLiNER-Konfidenz-Schwelle erhöhen

**Heute:** `threshold=0.5` an DREI Stellen: anonymization.py:261 (`_apply_ner`), :331 (`_apply_ner_parallel`), :567 (`extract_entities`). Default-Wert laut context7 [CITED: github.com/urchade/gliner/docs/usage.md] = 0.5.
**Empfehlung:** Als **Modul-Konstante** zentralisieren (`GLINER_THRESHOLD = float(os.environ.get('GLINER_THRESHOLD', '0.6'))`) und an allen drei Stellen verwenden. Wert **0.6** als Startpunkt:
- context7: "Higher thresholds increase precision, lower thresholds increase recall." [CITED]
- 0.5→0.7 ist der dokumentierte Precision-Schwenk. Für DSGVO gilt: Recall-Verlust = durchgelassene PII = NICHT akzeptabel (D-01 0%-False-Negative-Geist). Deshalb **moderat 0.6**, nicht 0.7. [ASSUMED: exakter Wert — muss gegen Real-Daten getunt werden, Task 6].
- Fehlalarme wie `nach dem Anruf`→LOC sind typische Low-Confidence-Treffer; 0.6 sollte sie filtern ohne echte Namen (meist score >0.85, siehe context7-Beispiele) zu verlieren.
**Pflicht-Tuning (Task 6):** Schwelle gegen heutigen Korpus iterieren — `[PERSON_A]` (echter Name "…") muss bleiben, `[LOC_A]` (Satzfragment) muss weg. **ENV-Override macht Live-Tuning ohne Redeploy möglich** (empfohlen, da Production-only).

## Common Pitfalls

### Pitfall 1: Fix an der falschen Funktion (`_apply_ner` statt `anonymize_output`)
Roadmap-Hypothese verleitet dazu, `_apply_ner` umzubauen — der ist aber korrekt. Eine Änderung dort bringt nichts gegen den Wortteil-Bug und riskiert Regression im INPUT-Pfad. **Fix gehört in `anonymize_output` (Zeile 485-488).**

### Pitfall 2: Pronomen-Filter nur in `_apply_ner`, nicht in `_apply_ner_parallel`/`extract_entities`
Drei Stellen tokenisieren (anon.py:241-283, 306-372, 533-588). Whitelist + Threshold an ALLEN drei spiegeln, sonst Gatekeeper-Inkonsistenz (`extract_entities` füttert `gatekeeper.classify_contact`, anon.py:536).

### Pitfall 3: `\b` an Umlaut-Grenzen
`\b` ist in py3-`re` unicode-aware, aber für Tokens die mit `.`/Ziffer enden unzuverlässig. Lookarounds `(?<!\w)…(?!\w)` sind robuster. Mehrteilige Keys (`Dr. Mueller`) weiter zuerst (len-Sort behalten).

### Pitfall 4: Threshold zu hoch → PII durchgelassen (DSGVO-Verstoß)
0.6 ist konservativ. NICHT auf 0.8 springen ohne Real-Daten-Gegencheck dass echte Namen (`score` typ. >0.85) bleiben. ENV-Override für Live-Tuning nutzen.

### Pitfall 5: Production-only Verifikation vergessen (Punkt 13 + HART)
Kein lokaler GLiNER-Lauf möglich/erlaubt. Acceptance = Deploy + Test-Call + Log-Diff gegen Erwartungstabelle. Plan-`<verify>` muss Production-Pfad formulieren.
