# Cross-AI Plan Review — Phase 08.23.2.G-MEET (SQL-Layer Focus)

## Gemini Review

### Q1 — Dual-Write trigger & SECURITY DEFINER
**Verdict: WRONG (Unnecessary Privilege Escalation).** 🔴 HIGH — actionable

`public.tenant_orgs` is `OWNER TO nerve_app`. The trigger fires on an INSERT performed by `nerve_app`, and a plain `SECURITY INVOKER` function would run as `nerve_app` — which, as the **owner** of `tenant_orgs`, already has INSERT. So `SECURITY DEFINER` is not needed for the insert to succeed. Worse: the function is created by the migration runner (**postgres superuser**), so `SECURITY DEFINER` makes the trigger body run **as superuser on every org INSERT** — gratuitous privilege escalation and attack surface.

**Fix:** Drop `SECURITY DEFINER SET search_path = public` from `mk_tenant_org()`; let it default to `SECURITY INVOKER` (runs as `nerve_app`, which owns the target).

### Q2 — 0013 worker policies (anon_worker_read / anon_worker_stamp), PERMISSIVE-OR
**Verdict: CORRECT.** ✅

PG 16: multiple PERMISSIVE policies for the same command+role combine with **OR**.
- `nerve_app`: role-specific `anon_worker_*` policies do not apply; only `tenant_isolation` (TO PUBLIC) governs it → stays strictly tenant-scoped. **No leak.**
- `nerve_anon_worker`: `tenant_isolation` (FALSE, no tenant set) OR `anon_worker_*` (TRUE) → full cross-tenant access.
- UPDATE path: a row must pass a SELECT/USING check to be found AND the UPDATE USING/WITH CHECK to be modified. Because `anon_worker_read` (FOR SELECT USING true) + `anon_worker_stamp` (FOR UPDATE USING true + WITH CHECK true) are both present, the worker can see and stamp without `tenant_isolation` blocking it. Semantics are sound.

### Q3 — calls.tenant_id backfill UPDATE-join
**Verdict: CORRECT-WITH-CAVEAT (trusting without verification).** 🟡 MEDIUM — actionable

Gemini checked `database/models.py`: `users.org_id` is `nullable=False`. Seed runs immediately before the backfill in the same `upgrade()` with `ON CONFLICT DO NOTHING` over all `organisations`, so the INNER JOIN `calls→users→organisations→tenant_orgs` is mathematically guaranteed to map every call → a tenant_orgs.id. **But** the migration blindly assumes 100% success; a corrupted legacy row would leave `calls.tenant_id` silently NULL.

**Fix (recommended):** Append a post-backfill assertion so a deploy fails loudly instead of leaving silent orphans:
```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM public.calls WHERE tenant_id IS NULL) THEN
    RAISE EXCEPTION 'Backfill failed: orphaned calls with NULL tenant_id';
  END IF;
END $$;
```
> ⚠ Claude note for André: confirm there are no legitimately-NULL-tenant calls expected (e.g. test-user calls, or a user whose org was hard-deleted). If some NULLs are legitimate, make the assertion a logged COUNT rather than a hard `RAISE EXCEPTION`, else the migration will refuse to deploy. The plan currently *intends* nullable-tolerated; the assertion would tighten that — decide which you want.

### Q4 — FORCE RLS reach
**Verdict: CORRECT-WITH-CAVEAT (functionally inert for postgres, defensively sound).** 🟡 MEDIUM — verify

`FORCE` only bites the table **owner** when that owner lacks BYPASSRLS. crm.* are **postgres-owned** and postgres is superuser → bypasses RLS regardless of FORCE, so migrations/maintenance as postgres still see everything (understood, not a gap). nerve_app is a non-owner, so plain `ENABLE` already constrains it; `FORCE` is belt-and-suspenders.

**Caveat (the real risk):** any **non-superuser** role that connects without setting `app.tenant_id` gets **0 rows** silently. Named risks to confirm:
- **Founder-analytics / dashboards** that read crm.* as `nerve_app` with no tenant context → 0 rows.
- Any BI/backup/reporting role, or `pg_dump` as a non-superuser.
- Any **out-of-request** code path reading crm.* as nerve_app (startup task, a different cron, a migration data-step) where the `after_begin` hook never set the GUC → silent 0 rows. **This is a functional-bug surface, not just security.**

**Action:** grep for any crm.* read outside the request path / outside the worker, and confirm founder-analytics either sets a tenant or doesn't touch crm.* yet.

### Q5 — set_config(...,true) / after_begin firing
**Verdict: CORRECT.** ✅

`after_begin` fires reliably at the start of **every** transaction on the connection (lazy-begun on first query, or explicit begin), gives the right connection, and the transaction-local `set_config(...,true)` lives for exactly that transaction's queries. On ROLLBACK the GUC clears; the **next** transaction on the same session re-fires `after_begin` and re-sets it — so per-transaction re-set is correct.

Fail-closed for worker threads is the **correct design**: a thread that never calls `set_current_tenant()` → `if not tid: return` → GUC unset → `current_setting('app.tenant_id', true)` = NULL → 0 rows. Gemini explicitly warns: do **NOT** raise inside `after_begin` — that would break every generic background job touching non-RLS public tables (`calls`, `users`). The current early-return is right.

> ⚠ Claude note: the security side is fine. The open *functional* question (overlaps Q4) — does any **live-session worker thread actually need to read/write crm.\*** and might forget to call `set_current_tenant()` → silently 0 rows? Plan 02 Task 3.5 mandates this worker-thread audit; make sure it is actually executed and its result recorded in 02-SUMMARY.
