### CRITICAL TOOL LIMITATION (read first — affects every training.* node)

`inspect.sh` connects to Postgres as **`nerve_app`** (verbatim from script: `DB_USER="${DB_USER:-nerve_app}"` + `sudo -u "$DB_USER" psql`). Two consequences that the orchestrator's "verify with `columns`" instruction did NOT account for:

1. **`columns <name>`** queries `information_schema.columns`. Postgres `information_schema` only shows objects the **connecting role has privileges on**. Migration `0008` granted `training.transcript_archive` ONLY to `nerve_anon_worker`, NOT to `nerve_app`. Therefore `columns transcript_archive` returns 0 rows **even if the table exists** — this is a privilege-visibility false-negative, NOT proof of absence.
2. **`tables`** runs `\dt` which respects `nerve_app`'s search_path (public). It does NOT list `training.*` even if present.

**Control test proving the limitation (run this session):**
```
$ bash scripts/inspect.sh columns transcript_segments   # nerve_app OWNS this (0010) → VISIBLE
     column_name     |        data_type         | is_nullable
---------------------+--------------------------+-------------
 id                  | bigint                   | NO
 conversation_log_id | integer                  | NO
 ... (6 rows)                                              ← visible because nerve_app owns it

$ bash scripts/inspect.sh columns transcript_archive    # nerve_app has NO grant → INVISIBLE
 column_name | data_type | is_nullable
-------------+-----------+-------------
(0 rows)                                                  ← NOT proof of absence
```

**Indirect proof that training.* DOES exist:** alembic head = `0010`. Migration `0010` (verbatim line 43) executes `GRANT SELECT ON public.transcript_segments TO nerve_anon_worker`. A GRANT to a non-existent role raises and aborts the migration. Since `0010` is the recorded head and `transcript_segments` IS present (control above), the role `nerve_anon_worker` exists and migrations `0008`→`0009`→`0010` all ran in sequence. Therefore `CREATE SCHEMA training` + `CREATE TABLE training.transcript_archive` + grants from `0008`/`0009` were applied. **This is inference from the migration chain, not a direct read** — see "Residual verification need" below.

**Residual verification need (one command, must run as postgres, NOT in inspect.sh whitelist):** to turn inference into proof, the plan's runbook should run ONCE as the migration user:
```
sudo -u postgres psql -d nerve -c "\dn training"          # schema exists?
sudo -u postgres psql -d nerve -c "\dt training.*"        # transcript_archive present?
sudo -u postgres psql -d nerve -c "\du nerve_anon_worker" # role + attributes (BYPASSRLS?)
sudo -u postgres psql -d nerve -c "\du nerve_app"         # role + attributes (BYPASSRLS? CREATE on public?)
```

## Open-Question Recommendations

### 1. Session-tenant-UUID enrichment (D-11, D-12.1/.3) — RECOMMEND: login-token + per-request SET via SQLAlchemy checkout event, RESET on checkin

**Recommendation:** Resolve the tenant UUID ONCE at login (join organisations→tenant_orgs by legacy_org_id) and store it in the Flask session alongside the existing `org_id`. Per request, set the GUC; on connection return, reset it.

- **Why login-token over `get_current_tenant_uuid()` PG function:** the caching-function approach still needs a per-request input (which org?), and the app already establishes identity at login. Storing the UUID in session avoids a per-request DB round-trip AND avoids a SECURITY DEFINER function whose search_path is itself an attack surface. D-11 explicitly forbids per-query bridge reloads — session storage satisfies that.
- **Where to SET/RESET (D-12.3 — the leakage killer):** use SQLAlchemy pool events, NOT just `teardown_request`. `teardown_request` runs in Flask app context but a pooled connection can be checked in/out outside a clean request boundary (background threads, socket handlers — and this app has live-session worker threads per memory). Pattern:
  ```python
  from sqlalchemy import event
  @event.listens_for(engine, "checkout")
  def _set_tenant(dbapi_conn, conn_record, conn_proxy):
      # only if a request/session context has a tenant_uuid
      ...
  @event.listens_for(engine, "checkin")
  def _reset_tenant(dbapi_conn, conn_record):
      cur = dbapi_conn.cursor(); cur.execute("RESET app.tenant_id"); cur.close()
  ```
  Belt-and-suspenders: also `RESET` in `teardown_request`. The `checkin` reset is the one that survives the thread-pool reality.
- **GUC choice:** use `SET app.tenant_id = ...` (custom GUC, allowed without prior config in Postgres because it has a dot). Use `set_config('app.tenant_id', :uuid, false)` parameterized to avoid SQL injection (NEVER string-interpolate the UUID).
- **Race note (Punkt 14):** the live-session worker threads run outside the request that opened them. They must set the GUC on their own connection or they will read 0 rows from RLS tables. Plan must audit whether any worker touches the NEW tables; if not, no action; if yes, set the GUC in the worker.

### 2. RLS correctness kit (D-12) — RECOMMEND: FORCE ROW LEVEL SECURITY per new table AND restricted role; USING + WITH CHECK; tenant_id index; empirical isolation test

- **D-12.4 owner-bypass:** Do BOTH for defense-in-depth, but the *load-bearing* control is `ALTER TABLE crm.accounts FORCE ROW LEVEL SECURITY` (and each new RLS table). Reason: even if a future migration accidentally re-grants nerve_app ownership or BYPASSRLS, FORCE keeps the policy active for the owner. Restricting nerve_app's BYPASSRLS (D-16) is correct too but has app-wide blast-radius (Punkt 4) — FORCE scopes the guarantee to exactly the new tables (D-10's intent). Verify `nerve_app` lacks BYPASSRLS via `\du` (KNOWN GAP) and, if it has it, the first migration does `ALTER ROLE nerve_app NOBYPASSRLS`.
- **D-12.5 USING + WITH CHECK:** every policy needs both. USING gates SELECT/UPDATE/DELETE visibility; WITH CHECK gates INSERT/UPDATE row values so tenant A cannot write a row tagged tenant B. Pattern per table:
  ```sql
  CREATE POLICY tenant_isolation ON crm.accounts
    USING (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
  ```
- **D-12.6 index:** `CREATE INDEX ON crm.accounts(tenant_id)` (or composite as the sketch shows: `(tenant_id, contact_id)` etc.). Without it every RLS-filtered query is a seq scan.
- **D-12.2 isolation test:** mandatory pytest (run on Production server post-deploy, per no-local-dev rule). Create tenant A + tenant B rows, SET app.tenant_id=A, assert SELECT returns only A's rows and INSERT with B's tenant_id raises. This test is the proof the karte demands; without it RLS "exists" only on paper.
- **D-12.1 atomicity:** the migration that adds policies AND the app code that sets the GUC ship in the SAME wave/deploy. If policies go live before the SET hook, `current_setting('app.tenant_id')` is empty → `::uuid` cast on empty string raises OR returns 0 rows → app broken. Use `current_setting('app.tenant_id', true)` (missing_ok=true) defensively so an unset GUC yields NULL (→ 0 rows, fail-closed) rather than an error.

### 3. Dual-Write at registration (D-09) — RECOMMEND: DB trigger on `organisations` AFTER INSERT

- **Why trigger over app-code:** three creation sites exist today (auth `_create_org_and_user`, waitlist, coach — verified Punkt 3). App-code dual-write must touch all three and any future site; a trigger fires for ALL INSERTs atomically in the same transaction. This is the anti-Abrieb choice (CLAUDE.md "lieber einmal richtig").
- **Trigger shape:**
  ```sql
  CREATE OR REPLACE FUNCTION public.mk_tenant_org() RETURNS trigger AS $$
  BEGIN
    INSERT INTO public.tenant_orgs (id, legacy_org_id, name, created_at)
    VALUES (gen_random_uuid(), NEW.id, NEW.name, now())
    ON CONFLICT (legacy_org_id) DO NOTHING;
    RETURN NEW;
  END; $$ LANGUAGE plpgsql;
  CREATE TRIGGER trg_mk_tenant_org AFTER INSERT ON public.organisations
    FOR EACH ROW EXECUTE FUNCTION public.mk_tenant_org();
  ```
- **`ON CONFLICT (legacy_org_id) DO NOTHING`** makes it idempotent and safe alongside the Wave-1 backfill (which seeds existing orgs). `legacy_org_id` needs a UNIQUE constraint.
- **gen_random_uuid()** requires pgcrypto (or use uuid-ossp `uuid_generate_v4()`); check which extension is enabled — `gen_random_uuid()` is built-in from Postgres 13+, verify server version. **[ASSUMED: Postgres >= 13 — verify on Production]**
- **Caveat:** the trigger function is owned by postgres (migration runs as postgres); ensure it can INSERT into tenant_orgs regardless of the calling role. SECURITY DEFINER may be needed since nerve_app (the inserting role) must be allowed to fire an insert into tenant_orgs it may not directly own. Flag for Cross-AI.

### 4. Anonymizer state-tracking (D-18.4) — RECOMMEND: Variante A (`anonymized_at` stamp in crm)

- **Confirm Variante A.** It mirrors the EXISTING `nerve_anon_worker` grant model (worker already has read on public.calls; extend with read on crm + a targeted UPDATE right on the specific `anonymized_at` column). No crm IDs cross into training → no re-identification surface (satisfies D-17 spirit + DSGVO).
- **Mechanism:** worker reads crm rows WHERE `anonymized_at IS NULL`, writes anonymized output to `training.preference_pairs` (+ existing `training.transcript_archive`), then `UPDATE crm.<table> SET anonymized_at = now()`. The worker needs `GRANT UPDATE (anonymized_at) ON crm.<table>` — column-level grant keeps the wall minimal.
- **Variante B rejected** (processed-list in training spiegelt crm-IDs over the wall) — matches CONTEXT's stated lean.

### 5. crm-role grant details (D-18) — MIRROR the proven training pattern (0008/0009)

The plan's FIRST crm migration (Wave 2) must, as postgres:
```sql
CREATE SCHEMA IF NOT EXISTS crm;
GRANT USAGE ON SCHEMA crm TO nerve_app;
ALTER ROLE nerve_app SET search_path = crm, public;   -- D-18.1 (role-level)
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA crm
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO nerve_app;   -- D-18.2
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA crm
  GRANT USAGE, SELECT ON SEQUENCES TO nerve_app;
-- worker sees crm for read:
GRANT USAGE ON SCHEMA crm TO nerve_anon_worker;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA crm
  GRANT SELECT ON TABLES TO nerve_anon_worker;
```
- **search_path caveat (D-18.1):** if PgBouncer is ever added it can override role search_path in transaction-pooling mode. `env-keys` should be checked for a pooler; document that crm.* references in app code should be schema-qualified OR rely on search_path being set. Safer: schema-qualify in ORM (`__table_args__ = {'schema': 'crm'}`).
- **Owner reality:** new crm tables created by postgres are postgres-owned. With `ALTER DEFAULT PRIVILEGES` nerve_app gets DML but NOT ownership → nerve_app does NOT bypass RLS on crm tables (this is exactly what makes D-16 work). This is the inverse of the public-table situation where nerve_app owns everything. Document the ownership split clearly.

Flag this ordering tension for the plan/Cross-AI — the literal "RLS ab Welle 1" only makes sense if a tenant-scoped table exists in Wave 1.
