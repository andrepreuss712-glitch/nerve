> This contract covers ONLY the UI. The data layer (`crm.meetings`) is live; the save endpoint is execute-phase backend work.
> Generated by gsd-ui-researcher 2026-06-02, verified by gsd-ui-checker.

> **HART (CLAUDE.md Punkt 8 + Vault-HART):** Light-Mode, current app design. The dark HTML mockup

## Interaction & State Contract

### Field set → `crm.meetings` mapping (VERIFIED ground truth)
| UI field | Type | Prefill | Maps to (server-side, execute phase) |
|----------|------|---------|--------------------------------------|
| Ansprechpartner | text | from call (where known) | resolves/creates `crm.contacts` row → `contact_id` |
| Firma | text | from call (where known) | resolves/creates `crm.accounts` row → `account_id` |
| Datum & Uhrzeit | `datetime-local` | default = next business day 10:00 (Sa→Mo, So→Mo) | `scheduled_at` |
| Worum geht's? | text | topic from call (where known) | `notes` |

`call_id` + `tenant_id` are set server-side from the live call context. There is no title/name column on `meetings` itself — name/firm live on the linked contact/account rows.

### datetime-local in Light-Mode (explicit — the dark mockup used `color-scheme:dark`; do NOT)
- Style the native `input[type="datetime-local"]` with the `.n-input` token family: `var(--input-bg)` fill, `var(--input-border)` 1.5px border, `var(--input-radius)` 12px, `var(--input-text)` #1a1a1a, `var(--page-font-mono)` for the value, focus → `--input-border-focus` + `--input-focus-glow`.
- Do NOT set `color-scheme: dark`. Either omit `color-scheme` or set `color-scheme: light` so the native calendar/spinner picker renders in light mode and the typed value stays dark-on-white (legible). This is a hard requirement — the dark mockup's white-on-dark native control would be invisible in Light-Mode.

### Checkbox "automatisch merken" — DSGVO HART
- **UNCHECKED by default. Always. Never pre-checked** (Privacy by Default, Art. 25 Abs. 2 DSGVO). The executor must not add a `checked` attribute or JS that defaults it on.
- Storage target: writes `auto_save_meeting` (boolean) to `crm.user_preferences` (table to be created in the execute phase — `tenant + user + auto_save_meeting`). The SPEC defines the interaction (opt-in toggle, off by default); the storage table is backend work.
- Visual: unchecked = neutral box on `var(--input-bg)` with `var(--glass-border)` border. Checked = teal fill (`--btn-primary-bg-from`) + white check icon. Whole row (box + label + hint) is the click target.

### Confirmation transition
- On successful save, the form view is replaced in place by the confirmation view (same PiP panel, no reload). Success ring + check (teal, or `--success-green` token if a distinct success hue is chosen), heading "Termin gemerkt", body referencing {Firma}, briefing-preview card (sparkles icon, {Thema} · {Datum}), and "Weiter".
- "Weiter" closes the meeting flow and returns to / advances the existing post-call sequence.

## Placement & Integration Contract (Variante A — locked)

- **Variante A: the EXISTING Picture-in-Picture window (bottom-right) EXPANDS to show this form.** NO centered overlay, NO scrim/dim backdrop. It is part of the post-call flow.
- **Render host:** the post-call host `#nlp-section-postcall` inside the PiP document. It slots into the existing D.UX.4 post-call sequence, appearing after outcome = "Termin" / `meeting_booked` at call end.
- **PiP DOM gotcha (note for executor):** PiP content lives in `state.pipWindow.document`, NOT the main document. All element lookups MUST use the `pipEl(id)` helper (`static/pip-launcher.js:99`; post-call host referenced at `:1824`). Do NOT target `document.getElementById` on the main window — the form would render into the invisible main DOM.
- Entry animation: a subtle grow/fade is acceptable (the PiP "expand" feel), but no modal scrim. Reuse existing PiP transition conventions rather than the mockup's dark drop-shadow.
