## Phase Boundary

Diese Phase baut den **datenseitigen Unterbau** für NERVEs Conversational-Memory-Pattern
(Industrie-Standard Gong/Chorus/Salesloft/Apollo/Outreach): internes Mini-CRM-Skelett
(accounts/contacts/meetings) + JSONB-`account_memory` (MEDDPICC + context_hooks) als Pre-Call-
Briefing-USP, Multi-Tenancy auf der UUID-Achse (`tenant_id` → `tenant_orgs`), Row-Level-Security
auf den neuen Tabellen, sowie die DSGVO-Schema-Trennung `crm`/`training` mit zwei DB-Rollen +
Training-Foundation (`training.preference_pairs`) + Anonymizer-Worker.

**Architektur-Entscheidung ist gelockt (Option C Hybrid).** Diese Discuss-Phase hat NICHT den
Scope neu erfunden, sondern die offenen Implementierungs-/Reihenfolge-Entscheidungen geklärt,
die der Architektur-Plan offen ließ — insbesondere die Versöhnung des bestehenden Integer-
`org_id`-Mandantenmodells mit der geplanten UUID-`tenant_id`-Achse.

**Out of scope (verschoben):** Voll-Umstellung `users.id`/`calls.user_id` auf UUID; Ablösung des
alten `organisations`/`org_id`-Modells; Verschieben der 32 Alttabellen nach `crm`; bidirektionaler
CRM-Sync; Pipeline-Stages/Deal-Werte/Forecasts; Inbound-Telefonie-Implementation.

## Implementation Decisions

### Phasen-Zuschnitt (Plan-vs-Execute-Strategie)
- **D-01:** Plan deckt **alle 3 Wellen als EIN zusammenhängendes Fundament-Design** ab — die
  Architektur-Stücke hängen voneinander ab, Andre will sie gemeinsam sehen und beurteilen.
- **D-02:** Ausführung erfolgt **Welle für Welle mit Stopp-Punkten**. **HARTE Anforderung:**
  jede Welle muss für sich abgeschlossen UND lauffähig deploybar sein, damit ein Stopp nach
  Welle 1 (oder Welle 2) ein sauberer, produktionsfähiger Zustand ist. Kein halb-fertiger
  Zwischenzustand zwischen Wellen.
- **D-03:** Wellen-Schnitt (aus ROADMAP):
  - **Welle 1** — Multi-Tenancy-Unterbau (UUID-Achse + RLS, kein Design, parallel zum Dark-Redesign).
  - **Welle 2** — CRM-Tabellen + Meeting-Merk-Fenster (Frontend) + Pre-Call-Briefing um
    `account_memory` erweitern + CSV-Export.
  - **Welle 3** — `training`-Schema + `training.preference_pairs` + Anonymizer-Worker.

### Mandanten-Achse (org_id vs tenant_id vs workspace_id)
- **D-04:** **`org_id` (Integer → `organisations`) lebt** — 144 aktive Treffer im Production-
  Code-Pfad (routes/services/static). Bleibt auf allen 32 Alttabellen unangetastet.
- **D-05:** **`tenant_id` (UUID) ist bewusst gelegte Deferred-FK-Foundation** (Phase 08.23.2.A,
  Migration `0005`, ORM-definiert) — NICHT tot, NICHT entfernen. 0 Leser/Schreiber im laufenden
  Code, aber per Bauplan der Ziel-Mandantenschlüssel.
- **D-06:** **`workspace_id` wird NICHT eingeführt** (0 Treffer, reiner Research-Doc-Wunsch).
  Kein viertes Namensschild.
- **D-07:** **Neue Tabellen (accounts/contacts/account_memory/meetings) werden auf der UUID-Achse
  geboren: `tenant_id` (UUID) → `tenant_orgs`.** KEIN `org_id` auf neuen Tabellen (sonst
  Split-Brain: calls/accounts=UUID-tenant vs. Rest=Integer-org).
- **D-08:** **Reichweite dieser Phase = Variante 1 (staged consolidation):** Welle 1 legt
  `tenant_orgs` (UUID) an, **eine Zeile pro bestehender `organisations`-Firma**, mit Brücke
  `legacy_org_id` (Integer) zurück zur alten Tabelle. `calls.tenant_id` wird befüllt. Neue
  Tabellen hängen per FK an `tenant_orgs`. Der Voll-Umbau (Nutzer-ID → UUID, Ablösung `org_id`)
  bleibt **draußen** (spätere Phase / koordiniert mit TEAM).
- **D-09 (Risiko 4 — Dual-Write Pflicht):** Solange beide Register koexistieren, MUSS jede neue
  Firmen-Registrierung automatisch BEIDE Zeilen anlegen (`organisations` + `tenant_orgs` inkl.
  `legacy_org_id`-Brücke). Sonst fallen Neukunden in eine UUID-Lücke und können neue Features
  nicht nutzen. **Plan muss festlegen:** Registrierungs-Code anpassen ODER DB-Trigger auf
  `organisations`.

### Datenbank-Schließanlage (Row-Level Security / RLS)
- **D-10:** **RLS ab Welle 1, NUR auf den neuen UUID-Tabellen** (accounts, contacts,
  account_memory, meetings). Die 32 Alttabellen behalten die App-Level-Code-Wache (`org_id`-
  Filter) bis zur späteren Voll-Umstellung.
- **D-11 (Risiko 5 — Session trägt UUID):** RLS filtert auf `tenant_id` (UUID), aber Session/Auth
  trägt heute nur Integer `org_id`. RLS darf die UUID NICHT pro Query aus der Brücke nachladen
  (Performance). **Lösung:** beim Login die `tenant_orgs`-UUID in die Session/das Token legen,
  ODER cachende Postgres-Funktion `get_current_tenant_uuid()`. Plan + Cross-AI entscheiden den
  exakten Weg.
- **D-12 (6 RLS-Pflichten — alle im Plan abdecken):**
  1. **Atomar:** Session-Var-Setup (`SET app.tenant_id` pro Request) geht in DERSELBEN Welle
     live wie die RLS-Policies — sonst `current_setting` leer → 0 Rows → App kaputt.
  2. **Isolations-Test (Pflicht):** Test beweist empirisch, dass Mandant A `account_memory` von
     Mandant B NICHT lesen kann. RLS ohne Beweis-Test existiert faktisch nicht.
  3. **Connection-Pooling-Leakage:** SQLAlchemy poolt Connections — `SET app.tenant_id` MUSS bei
     Connection-Rückgabe via `teardown_request`/checkout-Event RESET werden, sonst erbt der
     nächste Request die Mandanten-ID des vorherigen.
  4. **Owner-Bypass:** Postgres ignoriert RLS wenn die App als Tabellen-Owner/Superuser
     verbindet (heute besitzt `nerve_app` alle Tabellen!). Lösung via D-16 (eingeschränkter
     App-User ohne `BYPASSRLS`) ODER `ALTER TABLE ... FORCE ROW LEVEL SECURITY` je RLS-Tabelle.
  5. **`WITH CHECK`:** Policy braucht `USING` (SELECT/UPDATE/DELETE) UND `WITH CHECK`
     (INSERT/UPDATE), sonst kann Mandant A einen Datensatz FÜR Mandant B anlegen.
  6. **Index auf `tenant_id`** auf JEDER RLS-Tabelle, sonst Full-Table-Scan je Abfrage.

### DSGVO-Schema-Trennung (crm/training) + zwei DB-Rollen
- **D-13:** **Volle Architektur — echte Postgres-Schema-Mauern.** Neue Klartext-Kundendaten in
  Schema `crm`, anonymisierter Lern-Stoff in Schema `training`. Das ist der DSGVO-Grundpfeiler,
  der die "echte Anonymisierung"-Aussage rechtlich trägt.
- **D-14 (Klarstellung):** Die **32 Alttabellen bleiben in `public`** — werden NICHT jetzt nach
  `crm` verschoben. NUR neue Tabellen werden in `crm` geboren.
- **D-15:** **Welle 3** baut `training`-Schema + `training.preference_pairs` (TRL-kompatibel:
  prompt/chosen/rejected JSONB, `schema_version`) + Anonymizer-Worker (separater Cron).
- **D-16:** Zwei DB-Rollen: **`nerve_app`** eingeschränkt auf `crm` + `public`, OHNE `BYPASSRLS`
  (macht die Schließanlage erst wirksam — löst D-12 Punkt 4). **`nerve_anon_worker`**:
  read-`crm` / write-`training`, einziger der beide Mauern sieht.
- **D-17:** **KEINE Foreign Keys über die crm/training-Mauer** (verhindert Re-Identifizierung +
  ungewollte Cascades).
- **D-18 (5 Rollen/Grant-Details — penibel in die ERSTE Migration):**
  1. **search_path:** `ALTER ROLE nerve_app SET search_path = crm, public` (auf der Rolle, nicht
     pro Session). Falls später PgBouncer: prüfen ob Pooler den Path überschreibt.
  2. **`ALTER DEFAULT PRIVILEGES` (kritisch):** Migrationen laufen als `postgres`-Owner — sonst
     hat `nerve_app` NULL Rechte auf zukünftige `crm`-Tabellen. Pflicht:
     `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA crm GRANT SELECT,INSERT,UPDATE,DELETE ON TABLES TO nerve_app;`
     + dito `GRANT USAGE,SELECT ON SEQUENCES`.
  3. **`GRANT USAGE ON SCHEMA crm TO nerve_app`** (Tabellenrechte nutzlos ohne Schema-Zugang).
     Worker: `USAGE` auf `crm` + `training`.
  4. **Anonymizer-State-Tracking — Entwurfs-Entscheidung:** Wie merkt sich der Worker
     verarbeitete Records? **Default-Empfehlung Variante A:** `anonymized_at`-Stempel in `crm`
     (Worker braucht gezieltes UPDATE-Recht auf `crm`, Mauer bleibt sauber, KEIN ID-Spiegeln).
     Variante B (processed-Liste in `training`) verworfen-tendenz: spiegelt crm-IDs über die
     Mauer = Re-Identifizierungs-Risiko. Plan muss eine wählen + begründen.
  5. **Keine FK** crm↔training (= D-17).

### Anti-Patterns (explizit verboten — aus Architektur-Doc)
- **D-19:** Pipeline-Stages / Deal-Werte / Forecasts (Pipedrive-Territorium); FKs crm↔training;
  Token-Cache-Persistierung; JSONB ohne `schema_version`; Custom-Fields-Mechanismus für User;
  Lead/Contact-Trennung; bidirektionaler CRM-Sync v1 (push-only reicht); volle Event-Sourcing-
  Implementierung.

### PFLICHT-VORBEDINGUNG: Verbindungs-Karte (Andre-Direktive)
- **D-20:** **Bevor IRGENDEINE Namens- oder Schema-Entscheidung im Plan festgeklopft wird, MUSS
  eine bewiesene "Verbindungs-Karte" vorliegen — keine Annahmen, alles gegen echten Code +
  Production verifiziert.** Plan OHNE vollständige Verbindungs-Karte = NICHT approve-bar. Die
  Karte geht zusätzlich an Gemini im Cross-AI-Review. Vier Pflicht-Punkte:
  1. **NAMEN** (`org_id`/`tenant_id`/`workspace_id`): `grep -rn` jeweils in models, services/,
     routes/, static/, migrations/. Pro Name dokumentieren: wo definiert, wo GESCHRIEBEN, wo
     GELESEN, wie viele aktive Treffer im Production-Pfad (Tests/Migrationen GETRENNT zählen).
     Entscheidung wird mit der Treffer-Liste begründet — **was LEBT gewinnt, nicht was der Plan
     wünscht.** Kein vierter Name, keine neue Parallel-Spalte ohne Beweis dass die alte tot ist
     (0 Leser/Schreiber im Production-Pfad).
  2. **TABELLEN/SPALTEN:** jede angefasste Tabelle gegen Production via `inspect.sh schema <table>`
     (NICHT lokal, NICHT geraten). Existiert die Spalte? Typ? CHECK-Constraints? Befüllt oder brach?
  3. **WER SCHREIBT / WER LIEST** pro neuer Verknüpfung: tatsächlichen Code-Pfad nachzeichnen
     (welche Funktion, welche Datei, welcher Thread/Worker). Plus Schicht-Check (CLAUDE.md Punkt

     D.UX-Bug (`log_entries` als DB-Spalte angenommen, war RAM) darf sich nicht wiederholen.
  4. **REICHWEITE:** bei jeder Verknüpfung 30 Zeilen Kontext lesen + benennen, was die
     Entscheidung sonst noch berührt (andere Calls, andere Worker, Migrationen, RLS-Policies).
