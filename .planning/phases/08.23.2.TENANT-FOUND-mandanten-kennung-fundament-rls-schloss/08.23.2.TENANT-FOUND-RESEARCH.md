Fix: `set_current_tenant(str(call.tenant_id))` (db.py:54) vor jedem RLS-geschützten Daemon-Write.

**Gute Nachricht für den Backfill (DSGVO-kritisch):** Alle 37 NULL-Tenant-Calls lösen **sauber** auf (`user_id → org → tenant_orgs`): 37/37 user_exists, 37/37 org_exists, 37/37 tenant_resolvable. **0** Users ohne Org, **0** Orgs ohne tenant_org-Zeile (4 Orgs = 4 tenant_orgs). ## 3. Der `create_call_for_sid`-Write-Path

**Datei:** `services/live_session.py:529-619`. Aktueller Insert (Z.566-571):

→ **`tenant_id` wird NICHT gesetzt** → DB-Default NULL. Genau hier ist der Anlage-Punkt.

**Ist `user_id` immer da?** Ja. Aufrufer `deepgram_service.py:712` `ls.create_call_for_sid(_sid, user_id=user_id, ...)`. Kommentar Z.696: „Punkt 14 Control-Flow-Audit: user_id ist gesetzt (handle_connect() rejectet unauthenticated)". ✓

**Transaktions-/Kontext-Kontext (KRITISCH):** Aufrufer ist ein **Deepgram-Callback-Thread**, KEIN Flask-Request. `g.tenant_id` existiert dort NICHT. `_db = SessionLocal()` (Z.564) trägt zwar den `after_begin`-GUC-Hook, aber der contextvar `_current_tenant_id` ist im Callback-Thread leer → GUC bliebe NULL. **Konsequenz:** Der Tenant MUSS per DB-Query aus `user_id` aufgelöst werden, BEVOR `Call(...)` gebaut wird. Da `calls` selbst KEINE RLS hat (psg_class §1.3), braucht dieser INSERT keinen GUC — nur den aufgelösten Wert.

**Saubererster Punkt + Mechanismus (Empfehlung):**
```python

from database.db import resolve_tenant_uuid_for_user   # neuer Helper (§1.1)
_tid = resolve_tenant_uuid_for_user(user_id, _db)      # user→org→tenant_orgs.id, None bei Edge
call = Call(user_id=user_id, tenant_id=_tid, call_mode=_db_mode, ...)
```
Der Helper joint in EINER Query (kein N+1):
```python
def resolve_tenant_uuid_for_user(user_id, db):
    row = (db.query(TenantOrg.id)
             .join(User, User.org_id == TenantOrg.legacy_org_id)
             .filter(User.id == user_id).first())
    return str(row[0]) if row else None
```
→ Bei einem (heute nicht existenten) Edge ohne tenant_org: `None` → calls.tenant_id NULL → später durch periodischen Backfill-Sweep oder Re-Resolution gefangen. **Latenz:** ein indizierter Join im Callback-Thread bei Call-Anlage (1×/Call), NICHT im Live-Antwort-Pfad. (§8.)

→ Heute schreibt der Daemon `abstain_log` **ohne** je `set_current_tenant` zu rufen. `_current_tenant_id`-contextvar ist im Daemon-Thread leer (kein before_request). Solange `abstain_log` KEINE RLS hat, geht das. **Sobald RLS forciert wird, schlägt der INSERT fail-closed fehl** (WITH CHECK gegen leeren GUC) → `db.rollback()` (Z.376) → Event bleibt 'pending' → H-3 re-queued endlos → **abstain_log nie geschrieben, lautlos**. Das ist M-4.

**GUC-Transaktions-Mechanik (db.py:54-89) — wo genau `set_current_tenant` ruft:**
- `set_current_tenant(tid)` setzt den contextvar (db.py:54-60).
- Der `after_begin`-Hook (db.py:73-89) liest den contextvar **bei Transaktions-Begin** und issued `SELECT set_config('app.tenant_id', %s, true)` (SET LOCAL, auto-clear bei commit/rollback).
- **Die SET feuert, wenn die TX beginnt (vor ihren Queries)** → GUC und tenant-gescopte Queries teilen sich EINE TX (db.py:45-47).

**Konsequenz für den per-Item-Commit-Bau:** `set_current_tenant` MUSS gerufen werden **BEVOR die TX beginnt, in der der abstain_log-Write committet** — d.h. VOR dem ersten Statement von `_persist_event_ref` auf der frischen Session. Da der Tenant pro Event variiert (verschiedene Calls in der Queue), ist der Wert **pro Item** zu setzen.

**Empfohlenes Muster (Wave 3):** in `_persist_event_ref`, sobald `ev` geladen und der Tenant ermittelt ist, ABER bevor der RLS-Write passiert:
```python
tid = _tenant_id_for(ev, db)        # calls.tenant_id (DB), jetzt dank Wave 1 nicht-NULL
if tid is not None:
    set_current_tenant(str(tid))    # contextvar setzen
# WICHTIG TX-Timing: der after_begin-Hook hat ggf. schon bei der ev-Query (oben) gefeuert
# mit leerem contextvar. Damit der GUC für den abstain_log-Write greift, MUSS die TX, in der
# der INSERT committet, NACH dem set_current_tenant beginnen.
```
**TX-Timing-Falle (vom M-4-Test verbatim belegt, test_rubric_score_schema.py:217-225):**
> „der app.tenant_id-GUC wird vom after_begin-Hook bei TRANSAKTIONS-BEGINN aus dem contextvar gesetzt … clear_current_tenant() leert nur den contextvar für KÜNFTIGE TX, NICHT die schon laufende … Daher: nach dem Clear die laufende TX per rollback() beenden → der nächste Statement-Block öffnet eine FRISCHE TX."

→ **Planungs-Entscheidung (Grau-Zone, für Plan-Author):** Zwei saubere Optionen:
- **(A) Set VOR der ersten Query der Item-TX.** Im Consumer-Loop, NACHDEM das `item` (event_id) gezogen ist und der Tenant aus einer eigenen kurzen Lookup-Session ermittelt wurde, `set_current_tenant(...)` rufen, DANN `db = get_session()` öffnen → after_begin liest den gesetzten contextvar. Erfordert Tenant-Lookup VOR der Haupt-Session (oder eine separate read-Session ohne RLS-Bedarf, da calls/intent_event keine RLS haben).
- **(B) Innerhalb `_persist_event_ref`: nach dem Tenant-Lookup `set_current_tenant` + `db.commit()`/Neustart der TX** (wie der Test es mit rollback macht), sodass der abstain_log-INSERT in einer frischen, GUC-tragenden TX läuft. Folgt exakt dem getesteten Muster.

**Empfehlung: Variante A** (Tenant zuerst ermitteln, GUC setzen, dann die Schreib-TX öffnen) — sauberer als Mid-TX-Reset, weil intent_event/calls keine RLS haben und der Lookup GUC-frei laufen darf. **Plus Hygiene:** `clear_current_tenant()` im `finally` nach jedem Item (Thread wird wiederverwendet), analog app.py:2134-2138.

**M-4-Negativ/Positiv-Test-Muster (verbatim aus `tests/test_rubric_score_schema.py:195-269`, pro neu-geRLS-ter Tabelle replizieren):**

## 6. Backfill-Design (DSGVO)

**Ist-Stand (psql als postgres, prod 2026-06-25):**
```
 total_calls | with_tenant | null_tenant
-------------+-------------+-------------
          52 |          15 |          37
```
→ **37 NULL-Tenant-Calls** (ROADMAP sagte 36/51; Drift bestätigt, meine Zahlen sind autoritativ: 37/52).

**Lösen alle NULL-Calls sauber auf?** (psql, LEFT JOINs):
```
 null_calls | user_exists | org_exists | tenant_resolvable
------------+-------------+------------+-------------------
         37 |          37 |         37 |                37
```
→ **37/37 vollständig auflösbar.** Jeder NULL-Call hat einen existierenden User, dessen Org existiert, deren tenant_org existiert.

**Globale Integrität:**
```
 users_no_org | orgs_no_tenant | total_orgs | total_tenant_orgs
--------------+----------------+------------+-------------------
            0 |              0 |          4 |                 4
```
→ **0** Users ohne Org, **0** Orgs ohne tenant_org. 4 Orgs ↔ 4 tenant_orgs (1:1, UNIQUE).

**fail-closed vs Default-Tenant — Entscheidung:**
- **Es gibt heute KEINEN Edge** (kein User ohne Org, keine Org ohne Tenant). Der Backfill-UPDATE (§5) setzt für ALLE 37 NULL-Calls den korrekten Tenant.
- **Empfehlung (DSGVO, kein Cross-Tenant-Leck):** **fail-closed by construction** — der Backfill setzt NUR, was eindeutig per Join auflöst. Sollte (künftig) ein Call NICHT auflösen, bleibt `tenant_id NULL` (KEIN Default-Tenant! Ein Default-Tenant würde fremde Daten unter einen falschen Mandanten ziehen → DSGVO-Leck). Ein NULL-Tenant-Call ist für die RLS-Kinder unsichtbar (fail-closed), was korrekt ist: lieber keine Note als eine im falschen Mandanten.
- **`calls.tenant_id` selbst bleibt NULLABLE** (KEIN NOT NULL auf calls diese Runde) — sonst bräche ein künftiger unauflösbarer Edge die Call-Anlage (Live-Pfad!). Die NOT-NULL-Härte gehört auf die **Bewertungs-Kinder** (rubric_score/abstain_log), nicht auf calls. (calls.tenant_id NOT NULL + FK = Phase F.)
- **Verifikations-Runbook (wie G-MEET-01 „Residual-Verification"):** nach dem Backfill `SELECT count(*) FROM calls WHERE tenant_id IS NULL` == erwartete Rest-Zahl (idealerweise 0 für auflösbare). Im SUMMARY belegen.
