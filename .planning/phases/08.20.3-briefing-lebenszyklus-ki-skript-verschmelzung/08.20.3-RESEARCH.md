### mdToHtml() (Z.78-87)

```js
function mdToHtml(md) {
  return String(md || '')
    .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
    .replace(/^## (.+)$/gm, '<h2>$1</h2>')
    .replace(/\*\*(.+?)\*\*/g, '<strong>$1</strong>')
    .replace(/^- (.+)$/gm, '<li>$1</li>')
    .replace(/(<li>.*<\/li>\n?)+/g, '<ul>$&</ul>')
    .replace(/\n{2,}/g, '<br>')
    .replace(/\n/g, ' ');
}
```

XSS-sicher: Escaped `&`, `<`, `>` VOR der Markdown-Konvertierung. Fuer Modus-B-Tab sicher verwendbar.

### _migrate()-Pattern (app.py Z.123-185)

```python
def _migrate():
    from sqlalchemy import text
    with engine.connect() as conn:
        for col, typedef in [
            ('col_name', 'TYPEDEF DEFAULT value'),
            ...
        ]:
            try:
                conn.execute(text(f'ALTER TABLE table ADD COLUMN {col} {typedef}'))
                conn.commit()
                print(f"[DB] Migration: added table.{col}")
            except Exception:
                pass  # Idempotent: doppeltes ALTER TABLE schlaegt still fehl
```

**Fuer profile_opener Migration:**
```python
# ── Phase 08.20.3: parent_id + is_personalized fuer ProfileOpener ────────────
for col, typedef in [
    ('parent_id',       'INTEGER'),          # Self-Ref FK, nullable
    ('is_personalized', 'BOOLEAN DEFAULT 0'), # False fuer alle bestehenden Items
]:
    try:
        conn.execute(text(f'ALTER TABLE profile_opener ADD COLUMN {col} {typedef}'))
        conn.commit()
        print(f"[DB] Migration: added profile_opener.{col}")
    except Exception:
        pass
```

**Wichtig:** SQLite erlaubt keine FK-Constraints via ALTER TABLE ADD COLUMN — der FK-Constraint `REFERENCES profile_opener(id)` muss nur im SQLAlchemy-Model deklariert sein, NICHT im ALTER TABLE Statement. Der bestehende Code macht das ueberall so (z.B. `'coach_id', 'INTEGER'` in organisations — kein FK im ALTER TABLE).

### LATEST_SCHEMA_VERSION (app.py Z.923-955)

`LATEST_SCHEMA_VERSION` ist in `services/profile_schema.py` definiert (Referenz Z.931). **Fuer 08.20.3 keine Aenderung noetig** — die Migration betrifft `profile_opener`-Tabelle, NICHT das Profile-JSON-Schema (`daten`-Spalte). `LATEST_SCHEMA_VERSION` betrifft nur den Profile-JSON-Schema-Versionierungs-Mechanismus in `profile_schema.py`.

### Idempotenz-Verhalten

`except Exception: pass` schlaegt IMMER bei doppeltem Ausfuehren still fehl. Kein Log bei zweitem Aufruf — nur `print(f"[DB] Migration: added ...")` beim ersten Mal. Testet-Pattern: Migration einmal laufen lassen, dann nochmal — kein Crash, kein Fehler.

## Landmines

### L1: renderStep() String-Step-Values

`renderStep()` nutzt `switch(state.step)` mit Zahl-Cases. Pseudo-Steps `'4b'` und `'4c'` sind Strings — `switch` matcht sie NICHT gegen `case 4` oder `case 5`. Die neuen Steps muessen **vor dem switch** abgefangen werden:

```js
function renderStep() {
  if (state.step === '4b') { renderStep4b(); return; }  // NEU
  if (state.step === '4c') { renderStep4c(); return; }  // NEU
  switch (state.step) { ... }
}
```

Alternativ String-Cases im switch — aber Pre-Check ist sauberer und konsistenter mit "Pseudo-Step"-Semantik.

### L2: Cross-Window DOM fuer Briefing-Tab

Wie V2 oben: Der Briefing-Tab ist nach `_setupPipWindow()` im `pipWindow.document`. Template in `base.html` definiert das DOM-Element (initial `display:none`). In `_initPipLive()` conditional einblenden. ALLE Zugriffe via `pipEl()`.

### L3: window.mdToHtml Timing (Script-Reihenfolge)

D-04: `window.mdToHtml` wird am Ende der pip-launcher.js IIFE gesetzt. app.js liest `window.mdToHtml`. Die Script-Reihenfolge in `templates/base.html` muss `pip-launcher.js` VOR anderen Skripten laden.

**Verifikationsschritt fuer Plan 4:** `grep -n 'pip-launcher\|app\.js' templates/base.html` — prueft ob pip-launcher.js korrekt vor anderen Skripten steht. Aktuell gibt es keine separate `app.js` — der Gesamte Frontend-Code ist in pip-launcher.js. Fuer Modus-B wird kein separates Laden noetig; `window.mdToHtml` ist innerhalb der IIFE verfuegbar und muss nur fuer Cross-File-Zugriff exposed werden (falls base.html Inline-Script den Tab rendert). Planerhin: Klaeren ob der Briefing-Tab-Render-Code in der IIFE bleibt (empfohlen) oder in einem Inline-Script — ersteres ist einfacher und sicherer.

### L4: Cap-Modal Timing-Constraint

SPEC Req 9, CONTEXT.md Constraints: "Cap-Sub-Modal erscheint NACH KI-Call (im Vorher/Nachher-Modal-Flow), NICHT davor." Das bedeutet: Backend darf Cap-Check NICHT beim Fetch von `/api/precall/personalize` als Pre-Check zurueckgeben — nur NACH dem KI-Call. Frontend zeigt renderStep4c() zuerst (Vorher/Nachher), und erst wenn User auf "Personalisiert nutzen + Call ▶" klickt, wird der Save-Request mit Cap-Check gemacht. Die Flask-Route hat zwei moegliche Antworten: `{'personalized_text': ...}` (KI-Ergebnis, kein Save) ODER `{'item_id': ..., 'ok': true}` (Save-Ergebnis). Das erfordert ZWEI getrennte Endpoints oder einen mit Action-Parameter.

**Empfehlung:** Zwei Endpoints:
1. `POST /api/precall/personalize` — nur KI-Call, gibt `personalized_text` zurueck, kein DB-Write
2. `POST /api/precall/personalize/save` — DB-Write mit Cap-Check, gibt `item_id` oder `cap_exceeded` zurueck

### L5: parent_id FK in SQLite

SQLite unterstuetzt keine FK-Constraints in ALTER TABLE. Die FK-Referenz (`profile_opener.id`) muss im SQLAlchemy-Model per `ForeignKey('profile_opener.id')` deklariert sein, ABER das ALTER TABLE Statement darf NUR `'parent_id', 'INTEGER'` enthalten (ohne REFERENCES-Klausel). Andernfalls wirft SQLite einen Syntax-Fehler. Das bestehende Migrationsmuster handhabt das bereits so (Z.186-227 organisations-Block: `'coach_id', 'INTEGER'` ohne FK im ALTER TABLE).

### L6: PERSONALIZED_SCRIPTS_CAP ENV-Variable

Cap-Wert aus ENV lesen:
```python
import os
PERSONALIZED_SCRIPTS_CAP = int(os.environ.get('PERSONALIZED_SCRIPTS_CAP', '20'))
```

In `config.py` oder direkt in `precall_service.py` definieren — konsistent mit `BRAVE_SEARCH_API_KEY` (Z.14 in precall_service.py: `from config import BRAVE_SEARCH_API_KEY`). Empfehlung: in `config.py` als `PERSONALIZED_SCRIPTS_CAP = int(os.environ.get('PERSONALIZED_SCRIPTS_CAP', 20))` und Import in precall_service.py.

### L7: is_personalized Boolean DEFAULT in SQLite

SQLite speichert Booleans als 0/1 Integer. `ALTER TABLE profile_opener ADD COLUMN is_personalized BOOLEAN DEFAULT 0` ist korrekt. SQLAlchemy-Model deklariert `Boolean` — das ist kompatibel. Bestehende Rows erhalten `is_personalized = 0 = False` — korrekt per SPEC Req 8.
