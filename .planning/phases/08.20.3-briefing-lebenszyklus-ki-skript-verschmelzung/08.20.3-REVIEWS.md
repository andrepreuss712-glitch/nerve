# Cross-AI Plan Review -- Phase 08.20.3

## Gemini Review

### Summary
Der Plan ist architektonisch fundiert (gute Backend-Routen, Security-Awareness, pragmatische DB-Migration), weist aber einen gravierenden chronologischen Logik-Bruch im UX-Flow auf (Step 4 vs. Step 5). Zudem fehlt eine Strategie, wie die neuen personalisierten Opener im bestehenden Profil-Editor und Dropdown dargestellt werden, was zu massivem UI-Clutter fuehren wird.

### Strengths
- **Security:** Konsequente Nutzung von `@login_required`, CSRF-Tokens und IDOR-Checks beim Loeschen via `delete_ids`.
- **Datenbank:** Pragmatische und sichere SQLite-Migration in `app.py` (idempotentes `ALTER TABLE` ohne riskante `REFERENCES`).
- **Resilienz:** Einsatz von `AbortController` fuer den KI-Request verhindert haengende UI-States bei Abbruechen.
- **Kostenkontrolle:** Implementierung von `log_api_cost` direkt mit bedacht.
- **DSGVO-Compliance:** Audit-Logs beim Loeschen von Inhalten beruecksichtigt.

### Concerns
- **[HIGH] UX-Sequenz-Bruch (Step 4 vs. Step 5):** Plan 01 platziert die Pseudo-Steps `4b` (Loading) und `4c` (Vorher/Nachher). Der Opener wird aber laut Plan und aktuellem Flow erst in Step 5 im Dropdown ausgewaehlt. Es ist unmoeglich, in Step 4 bereits das Skript zu personalisieren.
- **[HIGH] Schema-Drift / UI-Clutter:** Neue `ProfileOpener`-Eintraege mit `is_personalized=True` werden im Profil-Editor (`profiles.py`) und im regulaeren Step-5-Dropdown auftauchen. Wenn ein User das Feature oft nutzt, wird das Dropdown unbrauchbar. Es fehlt ein Plan zum Filtern oder Gruppieren dieser Eintraege.
- **[MEDIUM] Transaktionssicherheit beim Save:** In Plan 02 (`/api/precall/personalize/save`) muss das Loeschen der `delete_ids` und das Speichern des neuen Openers zwingend in einer Datenbank-Transaktion (db.session.commit() erst ganz am Ende) passieren. Sonst droht bei einem Insert-Fehler Datenverlust der geloeschten Skripte.
- **[MEDIUM] Orphaned `parent_id` (Rollback-Risiko):** Da SQLite den Foreign Key beim `ALTER TABLE` nicht erzwingt, kann der Ursprungs-Opener geloescht werden, waehrend die `parent_id` bestehen bleibt. Der Rollback-Mechanismus (Req11) muss `None`-States robust abfangen.
- **[LOW] Modellauswahl:** Plan 02 nennt `config.MODEL_PRECALL`. Sicherstellen, dass dies auf Claude 3.5 Sonnet mappt, da Haiku laut Architektur-Pflock nur fuer den Live-Call-Loop reserviert ist.

### Suggestions
- **Flow-Korrektur (Step 5b/5c statt 4b/4c):** Step 4 setzt lediglich den internen Status `briefingModus = 'C'` und navigiert zu Step 5. In Step 5 waehlt der User den Opener und klickt auf den neuen "Personalisieren + Call"-Button. Erst dieser Klick triggert den Loading-Screen (`5b`) und danach die Vorher/Nachher-Ansicht (`5c`).
- **UI-Clutter verhindern:** Step-5-Dropdown anpassen, um personalisierte Skripte optisch abzugrenzen (z.B. `<optgroup>`). Den Profil-Editor (`routes/profiles.py`) so anpassen, dass personalisierte Opener entweder nicht editierbar sind, ausgeblendet oder in einem separaten Tab "Personalisierte Skripte" landen.
- **DB-Transaktion:** In `app_routes.py` explizit `db.rollback()` bei Exceptions waehrend des Save/Delete-Vorgangs implementieren.
- **Orphan-Guard:** Vor dem Rendern der Vorher/Nachher-Ansicht serverseitig pruefen, ob der Opener der `parent_id` noch existiert. Falls nicht: Fallback auf einen sauberen State ohne Rollback-Option.

### Risk Assessment
**HIGH** -- Der Plan kann so nicht implementiert werden, da der Frontend-Flow (Step 4 vs. Step 5) logisch inkompatibel ist und die Nicht-Beachtung bestehender DB-Abfragen (Dropdown/Profil-Editor) die Usability fuer Core-User zerstoeren wird. Die Backend-Fundamente sind jedoch stark; mit einem Re-Routing der UI-Steps auf `5b/5c` und Filter-Logik fuer `is_personalized` ist der Plan startklar.

## Consensus Summary

Reviewed by: 1 external AI (Gemini). Claude Code CLI skipped per independence rule.

### Reviewer Note on Finding #1 (HIGH: UX-Sequenz-Bruch)

**This is a FALSE POSITIVE / misread.** The actual designed flow is:
- Step 4 (Modus C click) → sets `state.briefingModus='C'` → navigates to **Step 5**
- Step 5 → user sees opener dropdown (unchanged) + new "Personalisieren + Call" button
- Clicking "Personalisieren" in Step 5 → `state.step = '4b'` → renderStep4b() loading
- After KI call → `state.step = '4c'` → renderStep4c() Vorher/Nachher

The naming "4b/4c" caused confusion because steps are accessed FROM Step 5, but the naming reflects that they are sub-steps of the Modus C / Briefing path. The CONTEXT.md D-01 and Plan 01 task spec both confirm this flow explicitly. This concern does NOT require plan changes.

### Actionable Findings (Substantive)

#### Finding A -- [HIGH actionable] Step-5 Dropdown Clutter (Schema-Drift)
**Description:** Plans add `is_personalized=True` items to `profile_opener` table, but NO filter is applied in the Step-5 opener dropdown loading code. A user who runs Modus C 10 times will see 10+ personalized variants cluttering the dropdown alongside the originals.

**Impact:** Core UX for every call flow is degraded. Opener dropdown becomes unusable.

**Fix needed in Plan 01 or Plan 02:** When loading openerItems for the Step-5 dropdown (wherever the JS array `state.openerItems` is populated from the API), filter to `is_personalized=False` OR visually group with `<optgroup>` label "Personalisiert". The profile editor (routes/profiles.py) also needs to handle `is_personalized=True` items differently (read-only or separate section).

#### Finding B -- [MEDIUM actionable] Non-Atomic Delete+Save Transaction
**Description:** Plan 02 `/api/precall/personalize/save` does:
1. `_db.delete(item)` + `_db.commit()` (for each delete_id)
2. `_db.add(new_opener)` + `_db.commit()`

If step 2 fails (e.g. DB constraint or network timeout), step 1 items are already permanently deleted. This creates a data loss window.

**Fix needed in Plan 02:** Batch all deletes + the new INSERT into a single transaction. Only call `_db.commit()` once after both operations succeed. Add `_db.rollback()` in the except handler.

#### Finding C -- [MEDIUM actionable] Orphaned parent_id on Original Delete
**Description:** SQLite does not enforce FK constraints unless `PRAGMA foreign_keys = ON` is set per connection. If a user later deletes the original opener from the profile editor, the personalized item's `parent_id` becomes a dangling reference. The Vorher/Nachher panel in renderStep4c() reads from `state.openerItems` (JS state, not live DB), so during the immediate session this is safe -- but any future UI that reads `parent_id` for display must guard against `None`.

**Fix needed:** In Plan 02 save route, this is already mitigated because `parent_id` is only written at save time. In renderStep4c() the original text comes from `state.openerItems` (loaded before the personalize call), so no live DB lookup. **Risk is LOW for Phase 08.20.3 scope** but should be documented for Block D.

### Agreed Strengths
- Strong CSRF + IDOR security pattern (consistent with existing codebase)
- Idempotent ALTER TABLE migration (correct SQLite approach, no REFERENCES clause)
- AbortController cancel prevents UI hang on 5-10s KI call
- Two-endpoint architecture (KI-only vs. save) is correct per L4 landmine
- DSGVO audit log on delete addressed

### Divergent Views
None (single reviewer). Finding #1 (UX flow) is a confirmed false positive based on plan re-reading.
