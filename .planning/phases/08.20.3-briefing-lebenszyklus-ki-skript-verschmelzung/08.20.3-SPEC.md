# Phase 08.20.3: Briefing-Lebenszyklus + KI-Skript-Personalisierung — Specification

**Created:** 2026-04-30
**Ambiguity score:** 0.136 (gate: ≤ 0.20)
**Requirements:** 14 locked

## Goal

Nach "Ergebnis übernehmen" in Step 4 (PreCall-Briefing) entscheidet der User aktiv in einem 3-Button-Footer was mit dem Briefing passiert — Modus A (Nur EWB, default), Modus B (Briefing als ausklappbarer PiP-Reiter), Modus C (KI personalisiert gewählten Opener/Skript mit Lead-Daten und speichert Ergebnis dauerhaft in ProfileOpener-Liste).

## Background

Phase 08.20.2 lieferte den Trust-Layer für PreCall-Briefings: 3-Schichten-Output (Pflichtfeld-Karte mit Confidence, Fließtext, Empfehlungen), Anti-Halluzinations-Pipeline, `precall_fields`-Spalte in DB. **Gap:** Nach "Ergebnis übernehmen" verschwindet das Briefing aus dem User-Workflow — `state.precallBriefing` lebt nur im JS-State, fließt via `set_briefing_for_sid()` in EWB-Section 8, ist aber für den User danach nicht mehr sichtbar oder aktionierbar.

Codebase-Status 2026-04-30:
- `static/pip-launcher.js`: Step 4 → "Ergebnis übernehmen" → direkt `state.step = 5`. Kein Modus-Selector.
- `database/models.py ProfileOpener`: Felder `id, profile_id, name, inhalt, sortierung, type, created_at`. **Kein `is_active`-Flag, kein `parent_id`, kein `is_personalized`-Flag.**
- `services/precall_service.py`: `recherche_firma()` + `_generiere_briefing()` + `_generiere_empfehlungen()`, Modell via `config.MODEL_PRECALL`.
- Modus D (manuelle Skript-Bearbeitung neben Briefing) → **explizit out-of-scope** (Andre-Decision 2026-04-30).

## Requirements

1. **Modus-Selector im Briefing-Footer**: Step 4 zeigt nach Briefing-Inhalt einen 3-Button-Footer statt des einzelnen "Ergebnis übernehmen"-Buttons.
   - Current: `renderStep4()` hat 1 Button "Ergebnis übernehmen →" der direkt zu `state.step = 5` springt.
   - Target: 3 Buttons mit Icon + Verb-Text + Subtext-Zeile: (A) ▶ "Briefing übernehmen — Call starten" / "Briefing fließt automatisch in die EWB-Hilfe ein", (B) 📋 "Briefing während Call sichtbar lassen" / "Ausklappbarer Tab im PiP zum Nachschauen", (C) ✨ "Skript auf diesen Lead personalisieren" / "KI passt einen Opener/Skript an die Lead-Daten an". Modus A ist visuell als Primary hervorgehoben.
   - Acceptance: Alle 3 Buttons in renderStep4() gerendert; Modus-A-Button hat primary-CSS-Klasse; Klick auf A/B/C triggert korrekte State-Transition.

2. **Modus C ausgegraut wenn kein Opener**: Wenn das aktive Profil keine ProfileOpener-Items hat, ist der C-Button disabled.
   - Current: Kein solcher Zustand — Modus C existiert noch nicht.
   - Target: Button C hat `disabled`-Attribut + Tooltip "Erst einen Opener im Profil anlegen" wenn `profileOpeners.length === 0`.
   - Acceptance: Bei leerem Opener-Array ist Button C nicht klickbar; Tooltip erscheint on-hover; Bei ≥1 Opener ist Button C aktiv.

3. **Modus A Flow**: Klick auf A speichert Modus-Wahl im State und navigiert zu Step 5 (Skript-Auswahl) — identisch zum bisherigen Verhalten.
   - Current: Einziges Verhalten (direkter Step-5-Sprung ohne Modus-Konzept).
   - Target: `state.briefingModus = 'A'` gesetzt; `state.step = 5`; Briefing fließt weiterhin via `set_briefing_for_sid()` in EWB-Section 8.
   - Acceptance: Nach Klick A ist `state.briefingModus === 'A'` und Step 5 wird gerendert; EWB-Briefing-Injection bleibt funktional.

4. **Modus B Flow — PiP-Reiter**: Klick auf B setzt Modus und navigiert zu Step 5. Während Live-Call ist ein ausklappbarer "Briefing"-Tab im PiP sichtbar.
   - Current: PiP zeigt Anrede + Vorwissen + EWB-Buttons + KI-Slots. Kein Briefing-Tab.
   - Target: `state.briefingModus = 'B'`; PiP erhält einen collapsible "Briefing"-Tab der `state.precallBriefing.text` im Lese-Modus rendert (Markdown → HTML); Tab ist nicht editierbar; initial collapsed.
   - Acceptance: Nach Klick B und Call-Start: Briefing-Tab im PiP vorhanden; Klick auf Tab-Header klappt Inhalt auf/zu; Briefing-Text korrekt gerendert; kein Edit-Modus.

5. **Modus C Flow — Opener-Auswahl**: Klick auf C öffnet ein Auswahl-Modal (oder Inline-Dropdown) über dem Footer, das alle ProfileOpener-Items des aktiven Profils als Dropdown zeigt.
   - Current: Kein Modus C.
   - Target: Dropdown mit allen `profile_opener`-Items des aktiven Profils (Name + type als Subtext); Default-Auswahl = zuletzt in Step 5 gewähltes Item (`state.selectedOpenerId`); "Personalisieren starten →"-Button startet KI-Call.
   - Acceptance: Dropdown listet korrekte Items für aktives Profil; Default-Selektion entspricht Step-5-Auswahl; Klick startet Personalisierungs-Call.

6. **KI-Personalisierungs-Call**: `generate_personalized_skript()` in `precall_service.py` (oder neuer Service) ruft `config.MODEL_PRECALL` auf mit Briefing-Inhalt + Original-Opener-Inhalt + Profil-Kontext.
   - Current: Keine solche Funktion existiert.
   - Target: Funktion nimmt `(briefing_dict, opener_inhalt, profil_daten, user_id)` → gibt `(personalisierter_text, error_msg)` zurück; Prompt-Input: Briefing-fields + text + empfehlungen + Original-Opener + Profil-ki-Felder; Output: personalisierte Version im selben Format (Markdown/Plaintext) wie Original-Opener; Modell: `config.MODEL_PRECALL`.
   - Acceptance: Funktion-Signatur korrekt; Unit-Test mit gemocktem Anthropic-Call gibt `(str, None)` zurück; API-Cost via `log_api_cost()` geloggt.

7. **Vorher/Nachher-Modal**: Nach KI-Call zeigt ein Modal Original-Opener (links/oben) vs. personalisierter Text (rechts/unten) mit 2 Aktions-Buttons.
   - Current: Kein solches Modal.
   - Target: Modal mit 2 Panels; "Original nutzen" Button → schließt Modal, `state.briefingModus = 'A'`, navigiert zu Step 5 mit Original-Opener vorselektiert; "Personalisiert nutzen + Call ▶" Button → triggert Save-Flow (Req 8–10) dann Call-Start.
   - Acceptance: Modal erscheint nach Personalisierungs-Call; beide Texte korrekt angezeigt; "Original nutzen" verworft Personalisierung und landet in Step 5.

8. **Dauerhafter DB-Save personalisierter Skripte**: Nach User-Bestätigung ("Personalisiert nutzen") wird das Ergebnis als neues `ProfileOpener`-Item gespeichert.
   - Current: ProfileOpener hat kein `parent_id`- und kein `is_personalized`-Flag.
   - Target: DB-Migration: `profile_opener` bekommt Spalten `parent_id` (Integer, nullable, FK→profile_opener.id) und `is_personalized` (Boolean, default=False); `generate_personalized_skript()` schreibt neues Item mit `name = "{Firmenname} — {original name} (personalisiert, YYYY-MM-DD)"`, `type = original.type`, `parent_id = original.id`, `is_personalized = True`.
   - Acceptance: Migration läuft fehlerfrei auf bestehender DB; neues Item erscheint in `profile_opener`-Tabelle nach Bestätigung; `parent_id` zeigt auf Original-ID; `is_personalized = True`.

9. **Cap-Enforcement (PERSONALIZED_SCRIPTS_CAP=20)**: Wenn User beim Bestätigen bereits 20 personalisierte Items hat, erscheint ein Inline-Sub-Modal zur Auswahl welche zu löschen.
   - Current: Kein Cap-Mechanismus.
   - Target: Backend prüft `COUNT(profile_opener WHERE profile_id=X AND is_personalized=True)` vor Save; wenn ≥ Cap: Inline-Sub-Modal (KEIN Redirect) mit Multi-Select-Checkboxen aller personalisierten Items (sortiert: älteste oben), Format "{Firmenname} — {Original} (Datum, N Wochen alt)"; Buttons: "Abbrechen" (→ kein Delete, kein Save, zurück zu Vorher/Nachher-Modal) / "Auswahl löschen + Personalisieren →" (→ löscht markierte Items, speichert neues, startet Call); `PERSONALIZED_SCRIPTS_CAP=20` als ENV-Variable konfigurierbar.
   - Acceptance: Bei 20 Items erscheint Sub-Modal statt direktem Save; "Abbrechen" hinterlässt alle 20 Items unverändert; "Auswahl löschen + Personalisieren" löscht exakt die markierten Items und speichert neues Item; Cap-Wert aus ENV-Variable gelesen.

10. **DSGVO-Audit-Log bei User-Delete**: Jedes vom User bestätigte Löschen eines personalisierten Items (via Cap-Sub-Modal) erzeugt einen Audit-Log-Eintrag.
    - Current: Kein Audit-Log für ProfileOpener-Deletes.
    - Target: Audit-Log-Eintrag bei jedem User-bestätigten Delete: `"User-Aktion: personalisiertes Skript gelöscht zur Cap-Befreiung (item_id={}, firmenname={}, erstellt={})"`; Implementierung als `print()` mit `[DSGVO-Audit]`-Prefix (Block D verifiziert vollständige Implementierung).
    - Acceptance: Nach Delete via Cap-Sub-Modal erscheint Audit-Log-Eintrag in Stdout; Eintrag enthält item_id, Firmenname-Hint (erster 20 Chars des Namens), Erstelldatum.

11. **Rollback via parent_id**: Im Vorher/Nachher-Modal (und optional in ProfileOpener-Liste) kann der User zum Original zurück.
    - Current: Kein parent_id, kein Rollback-UI.
    - Target: "Original anzeigen"-Komponente im Vorher/Nachher-Modal zeigt Original-Opener via `parent_id`-Lookup; Original-Opener bleibt immer erhalten (personalisiertes Item wird zusätzlich gespeichert, Original nie überschrieben).
    - Acceptance: Original-Opener existiert nach Personalisierung unverändert in DB; Vorher-Panel im Modal zeigt Original via parent_id; Original-Opener kann in Step 5 weiterhin ausgewählt werden.

12. **Modus B — Naming-Konsistenz**: Alle Code-Bezeichner verwenden "personalisieren" statt "verschmelzen".
    - Current: Kein Code existiert (neue Funktion).
    - Target: Funktionsname `generate_personalized_skript()`, DB-Spalte `is_personalized`, JS-State `state.briefingModus`, keine "merge"-/"-merged"-Bezeichner in neuen Files.
    - Acceptance: `grep -r "merge_skript\|is_merged\|briefing_merged" services/ static/` gibt 0 Treffer für neue Files; `grep "personalized\|is_personalized\|briefingModus" services/ static/` gibt ≥ 3 Treffer.

13. **Skript-Auswahl in Modus C**: Dropdown-Default ist die aktuelle Step-5-Auswahl.
    - Current: Kein Modus C.
    - Target: Dropdown für Opener-Wahl in Modus C liest `state.selectedOpenerId` (wird in Step 5 gesetzt); wenn `state.selectedOpenerId` gesetzt: entsprechendes Item ist default-selektiert; wenn nicht gesetzt: erstes Item in Liste.
    - Acceptance: Bei gesetztem `state.selectedOpenerId` ist das entsprechende Item im Dropdown vorausgewählt; Dropdown listet alle Items des aktiven Profils.

14. **Modus B — Kein Edit während Call**: Briefing-Tab im PiP ist read-only.
    - Current: Kein Briefing-Tab.
    - Target: Briefing-Tab rendert HTML (via `mdToHtml()`), kein `<textarea>`, kein `contenteditable`; kein "Anpassen"-Button im PiP-Kontext.
    - Acceptance: PiP-HTML enthält kein `textarea` und kein `contenteditable` innerhalb des Briefing-Tab-Elements.

## Boundaries

**In scope:**
- 3-Button-Modus-Selector Footer in Step 4 (renderStep4) — A/B/C
- Modus A: State-Flag setzen, Verhalten bleibt identisch zu 08.20.2
- Modus B: Ausklappbarer Lese-Modus Briefing-Tab im PiP während Live-Call
- Modus C: Opener-Auswahl-Dropdown → KI-Personalisierungs-Call (`generate_personalized_skript()`) → Vorher/Nachher-Modal → dauerhafter DB-Save
- DB-Migration: `parent_id` + `is_personalized` Spalten zu `profile_opener`
- Cap-Enforcement (ENV `PERSONALIZED_SCRIPTS_CAP=20`) mit Inline-Delete-Sub-Modal
- DSGVO-Audit-Log (print-basiert) bei User-bestätigtem Delete
- parent_id-Rollback: Original immer erhalten, "Original anzeigen" im Vorher/Nachher-Modal

**Out of scope:**
- Modus D (manuelle Skript-Bearbeitung neben Briefing) — Andre-Decision 2026-04-30, KI-Personalisierung (Modus C) deckt Use-Case ab
- `is_active`-Flag für ProfileOpener — kein neues DB-Feld in 08.20.3; Modal-Auswahl reicht
- DSGVO-Vollimplementierung (Art. 17 Delete, Art. 20 Export für personalisierte Skripte) — Block D zuständig; 08.20.3 liefert nur Audit-Log-Grundlage
- Cross-User-Firmen-DB / User-Korrekturen während Call (Block J Mini-Add, separate Phase)
- Visual-Polish / Design-Overhaul (Block O)
- EWB-Briefing-Gewichtung im Prompt verstärken (Phase 08.21 Sales-Wisdom-Layer)
- Echtzeit-Briefing-Updates während Live-Call (Briefing ist pre-call, nicht live)

## Constraints

- Modell für `generate_personalized_skript()`: `config.MODEL_PRECALL` (ENV-konfigurierbar, aktuell Sonnet)
- `PERSONALIZED_SCRIPTS_CAP=20` als ENV-Variable (kein Hardcode)
- Cap-Sub-Modal erscheint NACH KI-Call (im Vorher/Nachher-Modal-Flow), NICHT davor — User entscheidet erst ob Personalisierung gut genug ist
- Personalisierte Skripte werden im Klartext gespeichert (inkl. Lead-Daten) — DSGVO-Compliance via Block D
- Original-Opener wird NIEMALS überschrieben — personalisiertes Skript ist immer ein zusätzliches Item
- Naming-Konvention: "personalisieren"/"personalized" (nicht "verschmelzen"/"merge") in allen neuen Bezeichnern
- Kein neuer `is_active`-Flag in `profile_opener` — kein Migrations-Overhead
- Modus B Briefing-Tab: Lese-Modus only, kein Edit, initial collapsed
