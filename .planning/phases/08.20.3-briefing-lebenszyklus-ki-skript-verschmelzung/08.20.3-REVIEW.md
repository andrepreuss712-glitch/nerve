**Reviewed:** 2026-05-01T12:00:00Z

## Summary

This phase introduces KI personalization of Verkaufsskripte via `generate_personalized_skript()` and two new Flask routes (`/api/precall/personalize`, `/api/precall/personalize/save`). Three new columns are added to `ProfileOpener` via idempotent migration. The frontend adds a 3-button Modus-Selector (A/B/C), renderStep4b/4c with AbortController, optgroup opener dropdown, and a collapsible Briefing Tab in PiP.

The implementation is architecturally sound. The atomic delete+insert transaction in the save endpoint is correctly implemented, and the AbortController pattern for cancellable KI calls is clean. The three new DB columns are properly nullable/defaulted and the migration is idempotent.

One **critical** issue exists: the `/api/precall/personalize` endpoint reads `profile_id` from the Flask session cookie but does not verify `profile.org_id == g.org.id`. This means a user who manually crafts a session with `active_profile_id` pointing to another org's profile can read that profile's opener text and profile data.

Four **warnings** cover a double-rollback pattern in the save endpoint, a cap-check race condition under concurrent saves, a missing `opener_id` type validation, and the `precall_service.py` cache-hit path returning a stale (pre-empfehlungen) dict when empfehlungen were set during the original call.

## Critical Issues

### CR-01: Missing org_id isolation in `/api/precall/personalize` — Cross-Org Profile Read

**File:** `routes/app_routes.py:1070`
**Issue:** `profile_id` is taken from `flask_session.get('active_profile_id')` but the subsequent `Profile` lookup does not verify `org_id`. An attacker who sets `active_profile_id` to a profile belonging to a different org can read that profile's `daten` (including `basis`, `ki` keys, USPs, Tabu-Begriffe) and any opener text belonging to that profile.

The opener query at line 1064 does filter `profile_id=profile_id`, so it protects opener isolation only as far as the session value is trusted. But `Profile.daten` (line 1070) is fetched without an org check.

The same gap exists in the session-cookie path of `/api/precall/personalize/save` (line 1139): `original = _db.query(ProfileOpener).filter_by(id=opener_id, profile_id=profile_id).first()` — again, `profile_id` is trusted without verifying that the profile belongs to `g.org`.

**Fix:**
```python
# In api_personalize_skript(), after fetching profile:
profile = _db.query(Profile).filter_by(id=profile_id).first()
if not profile or profile.org_id != g.org.id:
    return jsonify({'error': 'Profil nicht gefunden oder kein Zugriff'}), 403

# Same pattern in api_personalize_skript_save(), after fetching original:
original = _db.query(ProfileOpener).filter_by(
    id=opener_id, profile_id=profile_id
).first()
if not original:
    return jsonify({'error': 'Opener nicht gefunden'}), 400
# Add org check:
_prof_check = _db.query(Profile).filter_by(id=profile_id, org_id=g.org.id).first()
if not _prof_check:
    return jsonify({'error': 'Zugriff verweigert'}), 403
```

All other profile-access endpoints in `routes/profiles.py` correctly use `filter_by(id=pid, org_id=g.org.id)`. This endpoint is the only one that does not.

## Warnings

### WR-01: Double-rollback anti-pattern in `api_personalize_skript_save` — potential session state corruption

**File:** `routes/app_routes.py:1219-1221`
**Issue:** The `with _db.begin():` block automatically rolls back on exception. The bare `except Exception as e: _db.rollback(); raise` on lines 1219-1221 then calls `_db.rollback()` a second time on an already-rolled-back transaction. In SQLAlchemy 2.x the session's internal state machine tracks transaction state; calling `.rollback()` on a session that already rolled back via `with begin()` is a no-op in practice, but it can confuse the session state in edge cases and is misleading to future readers.

**Fix:** Remove the defensive bare rollback — the `with _db.begin()` context manager handles both commit and rollback atomically:
```python
# Remove lines 1219-1221:
# except Exception as e:
#     _db.rollback()  # <- redundant, already rolled back by with-block
#     raise

# Replace with:
try:
    with _db.begin():
        # ... deletes + insert ...
        _db.flush()
        new_item_id = new_opener.id
except Exception as e:
    raise  # let finally: _db.close() run; with-block already rolled back
```

### WR-02: Cap-check race condition — two concurrent saves can both pass cap < N

**File:** `routes/app_routes.py:1147-1152`
**Issue:** The cap-check reads `personalized_count` and then the insert happens in a separate `with _db.begin()` block. Between the count query and the insert, a concurrent request from the same user/profile can also read count < cap and proceed. Both will then insert, ending up with `cap + 1` rows.

This is low-risk for a solo-founder product with single-user orgs, but worth documenting. For safety, the cap check should be inside the same `with _db.begin()` block as the insert, or a row-level lock (`SELECT ... FOR UPDATE`) should be used.

**Fix (pragmatic — avoids full redesign):** Move the cap check inside the atomic transaction block:
```python
try:
    with _db.begin():
        if not delete_ids:
            personalized_count = _db.query(ProfileOpener).filter_by(
                profile_id=profile_id, is_personalized=True
            ).with_for_update().count()   # acquires lock in Postgres; no-op on SQLite
            if personalized_count >= cap:
                # return cap_exceeded before insert
                ...
        # deletes + insert
```
On SQLite (current stack) this is equivalent to the current behaviour, but the pattern is correct and future-proof when migrating to Postgres.

### WR-03: `opener_id` not validated as integer before DB query — potential type error

**File:** `routes/app_routes.py:1051,1118`
**Issue:** `opener_id = data.get('opener_id')` accepts whatever the client sends (string `"abc"`, float, `null` after the early check). The early check `if not opener_id` passes for `0` (falsy), and a non-integer value would cause SQLAlchemy to raise a `TypeError`/`DataError` on the `filter_by(id=opener_id)` query, returning an unhandled 500 instead of a 400.

```python
# Current:
opener_id = data.get('opener_id')
if not opener_id:
    return jsonify({'error': 'opener_id ist Pflicht'}), 400
```

A string like `"1; DROP TABLE profile_opener"` will be passed directly into SQLAlchemy, which parameterises the query safely, but a non-numeric string would still cause an exception that leaks into the 502 error path.

**Fix:**
```python
opener_id_raw = data.get('opener_id')
try:
    opener_id = int(opener_id_raw)
    if opener_id <= 0:
        raise ValueError
except (TypeError, ValueError):
    return jsonify({'error': 'opener_id muss eine positive Ganzzahl sein'}), 400
```

Apply the same pattern to both `/api/precall/personalize` and `/api/precall/personalize/save`.

### WR-04: `precall_service` cache returns pre-empfehlungen dict for first caller, stale empfehlungen for cache-hit callers

**File:** `services/precall_service.py:180-222`
**Issue:** The cache stores the fully-constructed `briefing` dict (including `empfehlungen`) after `_generiere_empfehlungen()` is called (line 221). However, on a cache miss the flow is:

1. `_generiere_briefing()` → returns dict without `empfehlungen`
2. `set_briefing_for_sid()` is called with Schicht-1+2 text (correct)
3. `_generiere_empfehlungen()` called with `sid` → correct
4. `briefing['empfehlungen'] = empfehlungen` set
5. Cache stored with `empfehlungen`

On a **cache hit** (line 180), the cached dict already has `empfehlungen` from the previous call. These empfehlungen were generated for the *previous* `sid` and its `build_profile_context()` — which may be a different session or even a different user profile if the cache key collides (key is `{firmenname.lower()}_{profile_id}`). The empfehlungen are session-specific (Section 8 of profile context depends on the session's live briefing), so serving a different session's empfehlungen on a cache hit is semantically incorrect.

This is not data loss, but the empfehlungen shown to the user on a cache hit reflect a stale session context rather than the current one.

**Fix:** On cache hit, regenerate empfehlungen (the cheap Schicht-3 call) using the current `sid`:
```python
if cached and (time.time() - cached[1]) < _CACHE_TTL_S:
    print(f"[PreCall] Cache hit: {firmenname}")
    cached_briefing = dict(cached[0])  # shallow copy
    # Re-run Schicht-3 for current sid (cheap, uses cached Schicht-1+2)
    if sid:
        try:
            from services.live_session import set_briefing_for_sid
            _sid_text = schicht1_summary_from_cache + "\n\n" + cached_briefing.get('text', '')
            set_briefing_for_sid(sid, _sid_text)
        except Exception:
            pass
    cached_briefing['empfehlungen'] = _generiere_empfehlungen(
        sid, firmenname, cached_briefing['fields'], user_id=user_id
    )
    return (cached_briefing, None)
```

Alternatively (simpler), store only `fields + text` in the cache and always regenerate `empfehlungen`.

### IN-02: `generate_personalized_skript` — `empfehlungen` field treated as both `list` and `str`

**File:** `services/precall_service.py:519-529`
**Issue:** The function handles `empfehlungen` being a `list` of dicts (line 524: `isinstance(empfehlungen, list)`) but `recherche_firma()` returns `empfehlungen` as a `str` (the raw text from `_generiere_empfehlungen()` which returns `msg.content[0].text.strip()`). So when the frontend passes `state.precallBriefing` (which is the JSON from the `/api/precall/research` route), `empfehlungen` is a string, not a list.

The `isinstance(empfehlungen, list)` guard at line 524 will be `False`, and `emp_text` will remain empty string — the empfehlungen will not be included in the personalization prompt.

**Fix:** Handle both types:
```python
emp_text = ''
if empfehlungen:
    if isinstance(empfehlungen, list):
        emp_text = '\n'.join(
            '- ' + (e.get('text') or e if isinstance(e, str) else str(e))
            for e in empfehlungen[:5]
        )
    elif isinstance(empfehlungen, str) and empfehlungen.strip():
        emp_text = empfehlungen.strip()
```

### IN-03: `pip-launcher.js` step `'4c'` — `renderStep4c()` does not guard missing `opener` gracefully

**File:** `static/pip-launcher.js:594-597`
**Issue:** `renderStep4c()` looks up the opener via `state.openerItems.find(...)` using `state.selectedOpenerId`. If `state.selectedOpenerId` is `null` (user navigated directly to step 4c without selecting an opener, e.g., from the Modus-C button in Step 5 when `lnr-opener-select` has no selection), `opener` will be `undefined` and `originalText` will be `''`. The comparison displayed to the user will show empty "Original" — potentially confusing, but not a crash.

More importantly, `_savePersonalizedAndStartCall()` will send `opener_id: null` to `/api/precall/personalize/save` which returns 400. The error is handled by the `.catch` block. No data loss, but UX is broken.

**Fix:** Add a guard in `renderStep4c()` and before triggering `_savePersonalizedAndStartCall`:
```javascript
// At the top of renderStep4c():
if (!state.selectedOpenerId) {
  // Fall back to step 5 with error message
  state.step = 5;
  renderStep();
  return;
}
```

And in the Modus-C personalize button handler in `renderStep5()` (line 999-1007), verify that `state.selectedOpenerId` is non-null before proceeding to `'4b'`.
