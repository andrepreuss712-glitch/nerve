<decisions>
## Implementation Decisions

### D-01: Modus C Flow — Kein Dropdown in Step 4, Action-Button in Step 5

**Entscheidung:** KEIN eigenes Opener-Dropdown im Step-4-Footer für Modus C. Stattdessen:

1. C-Button in Step 4 setzt `state.briefingModus = 'C'` und navigiert direkt zu Step 5
2. Step 5 bekommt einen zweiten Action-Button neben "Call starten ▶":
   - "Call starten ▶" → normaler Call (Modus A oder B)
   - "✨ Personalisieren + Call ▶" → Modus-C-Trigger, startet KI-Call mit `state.selectedOpenerId`

**Begründung:** User hat in Step 5 bereits seinen Opener gewählt (`state.selectedOpenerId`). Separates Dropdown in Step 4 wäre Duplikat mit Drift-Risk. User kann Step-5-Dropdown vor "Personalisieren"-Klick noch ändern.

**Modus-C-Disabled-Regel:** Wenn `state.openerItems.length === 0` → C-Button in Step 4 disabled + Tooltip "Erst einen Opener im Profil anlegen". Der "✨ Personalisieren + Call ▶"-Button in Step 5 erscheint nur wenn `state.openerItems.length > 0`. (SPEC Req 2 gilt für C-Button in Step 4.)

**Skript vs. Opener:** `generate_personalized_skript()` arbeitet mit `state.selectedOpenerId` (Opener) ODER `state.selectedSkriptId` (Skript) — welches der User in Step 5 zuletzt aktiv hat. Plan-Phase-Detail: State-Priorität festlegen.

### D-02: Lade-State während Sonnet-Call — renderStep4b() Pseudo-Step

**Entscheidung:** Eigener Pseudo-Step `renderStep4b()` für 5-10s Sonnet-Wartezeit.

**Konsistenz:** Identisches Pattern wie Step 3 (Briefing-Recherche-Ladescreen). "Zurück"-Button bricht Fetch-Request via AbortController ab, setzt `state.step = 5`.

**Flow:**
- Step 5: "✨ Personalisieren + Call ▶" geklickt → `state.step = '4b'` → `renderStep4b()`
- Step 4b: Ladeanimation + Cancel-Button → nach KI-Antwort → `renderStep4c()` (Vergleich)
- Cancel-Pfad: AbortController, kein DB-Save, zurück zu Step 5

### D-03: Vorher/Nachher-Vergleich — renderStep4c() Pseudo-Step

**Entscheidung:** Als `renderStep4c()` Pseudo-Step im pip-launcher Step-Management implementiert (nicht als DOM-Overlay).

**Begründung:** Konsistent mit Step-Architektur (R7-Lesson: Step-State-Mgmt verhindert Zurück-Workflow-Bugs). DOM-Overlay würde Step-Stack-Pattern brechen.

**Layout:**
- 2 Panels (Side-by-Side bei breitem Viewport, gestackt bei schmalem PiP-Window)
- "Original nutzen" → `state.briefingModus = 'A'`, `state.step = 5`, Original-Opener vorselektiert
- "Personalisiert nutzen + Call ▶" → Save-Flow (Req 8-10) dann Call-Start

### D-04: mdToHtml() Cross-File-Sharing — window.mdToHtml expose

**Entscheidung:** Am Ende der pip-launcher.js IIFE:
```js
window.mdToHtml = mdToHtml;
```

**Konsistenz mit bestehendem Pattern:** `window.pipSetAnrede`, `window.pipVorwissenEdit`, `window.pipSetVorwissen` sind bereits genauso exponiert (Commit f1916e2, 2026-04-30).

**Script-Reihenfolge (PFLICHT für Plan):** In `templates/base.html` sicherstellen dass `pip-launcher.js` VOR `app.js` geladen wird — sonst `window.mdToHtml` undefined bei PiP-Tab-Render.

**XSS-Sanitization (Test-Pflicht):** `mdToHtml()` wurde in 08.20.2 Code-Review behandelt. Bei Modus-B fließt KI-generiertes Markdown durch `mdToHtml()` im PiP. Test-Pflicht: Mock-Briefing mit `<script>`-Tag → muss escaped werden.

**Dokumentation:** Comment-Block am Ende der IIFE:
```js
// Window-exposed for cross-file usage:
//   window.mdToHtml — used by app.js PiP briefing tab (Phase 08.20.3 Modus B)
//   window.pipSetAnrede / pipVorwissenEdit / pipSetVorwissen — PiP onclick handlers
```

**Anti-Drift:** Verhindert versehentliches Entfernen bei späteren Refactorings.

### D-05: PiP-Briefing-Tab — Position, Verhalten, Auto-Collapse

**Tab-Position:** Oben im PiP-Window, unter dem Header, VOR der bestehenden Anrede-Row (`pip-anrede-row`). Collapsible, initial collapsed (32px Höhe sichtbar als "Briefing: {Firmenname} ▼").

**Nicht-Render-Bedingung:** Wenn `state.precallBriefing === null` oder `state.precallBriefing.firmenname` fehlt/leer → Tab gar nicht rendern. Verhindert leeren "Briefing: " Tab.

**Markdown-Renderer:** `window.mdToHtml()` (aus D-04). Kein neuer Renderer, kein Drift-Risk.

**Auto-Collapse bei EWB-Antwort:**
- Trigger: `pip_token_done`-Event (oder analoger EWB-Stream-Complete-Event)
- Guard: `state.briefingTabExpandedAtStreamStart` — wird beim Stream-Start gespeichert
- Nur auto-collapse wenn Tab beim Stream-Start expanded war
- Manuelle Mid-Stream-Öffnungen des Users bleiben erhalten
- Animation: 200ms smooth collapse, nicht abrupt

**Education-Hint beim ersten Modus-B-Call:**
- Marker: `localStorage.getItem('nerve.seen_briefing_tab_intro')`
- Trigger: erster Call-Start mit `state.briefingModus === 'B'`
- Timing: 500ms delay → Tab aufklappen (300ms transition) → 3000ms sichtbar → auto-close (300ms)
- localStorage-Key: `nerve.seen_briefing_tab_intro = '1'` (nach Hint gesetzt)
- Cancel-Pfade:
  - User klickt Tab innerhalb 3s → Timer canceln, Tab bleibt offen, Marker setzen
  - User klickt EWB-Button innerhalb 3s → Timer canceln, Tab schließt sofort, Marker setzen
  - Call-Ende / Modus-Wechsel innerhalb 3s → Timer canceln, kein Marker

**localStorage-Namespace:** `nerve.*` Prefix (konsistent mit anderen App-Settings — Plan-Phase grep auf bestehende Keys).

### D-06: Plan-Splitting — 4 Plans + Wave-Struktur

**Plan 1:** Step-4-Footer (3-Button-Modus-Selector A/B/C) + Step-4b-Ladescreen + Step-4c-Vergleich-Modal + "✨ Personalisieren + Call ▶" Button in Step 5

**Plan 4:** PiP-Briefing-Tab in `app.js` (Modus-B-Implementation) + `window.mdToHtml` expose in pip-launcher.js + Script-Reihenfolge-Verifikation

**Wave-Struktur (Dependency-Reihenfolge):**
- **Wave 1 (parallel):** Plan 3 (DB-Foundation) + Plan 4 (PiP-Tab, standalone)
- **Wave 2 (nach Wave 1):** Plan 1 (Step-4-UI, baut auf DB-Strukturen auf)
