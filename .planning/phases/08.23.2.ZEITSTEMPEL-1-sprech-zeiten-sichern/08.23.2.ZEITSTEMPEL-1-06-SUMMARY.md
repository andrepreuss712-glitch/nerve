## 3. Ausrollen — und die Bedingung, an der die Reihenfolge haengt

**Reihenfolge, wie gefahren:** Migration auf Production **zuerst**, Deploy **danach**.

1. `scp` der Revision nach `/opt/nerve/app/alembic/versions/` — md5 lokal = md5 auf dem Server
   (`4de35929afb011ddf269b7c3b8e6e8b2`)
2. `alembic upgrade head` als OS-User `postgres` **mit gesetztem `DATABASE_URL`** →
   `Running upgrade 0038 -> 0039`
3. Gegenprobe **vor** dem Deploy: `migrations` = `0039`, drei Spalten nullable, `ts_ms`
   unveraendert `not null`, Index intakt, `count` = 627
4. Vorwaerts-Vertraeglichkeit **gemessen, nicht behauptet:** im Fenster zwischen Migration und
   Deploy lief der **alte** Code gegen das **neue** Schema — `/api/health` = HTTP 200,
   `journalctl -p err` = keine Eintraege
5. `bash deploy.sh production` → Tor gruen, Neustart

### ⚠ Die Bedingung, ohne die diese Reihenfolge falsch waere

**„Migration vor Deploy" gilt hier NUR, weil alle drei Spalten `nullable=True` sind** — null
Vorkommen von `nullable=False` in der Revision. Der Alt-Code kann dadurch weiterschreiben, ohne
die Spalten zu kennen; die neuen Spalten bleiben schlicht `NULL`. **Es gibt gar kein Fenster.**

**Waere auch nur eine Spalte `NOT NULL` ohne Default gewesen, waere „Migration zuerst" FALSCH
gewesen** — jeder `INSERT` des Alt-Codes waere sofort gebrochen. Dann haette man erst mit
Default migrieren, dann deployen, dann den Default ziehen muessen.

**Die Regel lautet also nicht „Migration vor Deploy", sondern: „Migration vor Deploy, wenn die
neuen Spalten nullable sind — sonst umgekehrt oder dreistufig."** Wer nur den halben Satz
mitnimmt, uebertraegt ihn beim naechsten Mal blind auf eine `NOT NULL`-Spalte und legt
Production lahm.

Umgekehrt gilt weiter: gegen Schema `0038` mit neuem ORM braechen **alle fuenf** Entity-Leser
mit `UndefinedColumn`, und `slow_lane_consumer` liefe ueber `_requeue_pending()` beim Neustart
von allein hinein. Deshalb ist „erst Deploy, dann Migration" hier definitiv die falsche
Reihenfolge gewesen — sie war zwischenzeitlich vorgeschlagen und wurde verworfen.

### Ein Bug, den das Wegwerf-`nerve_test` gefangen hat

Der erste Migrations-Versuch starb mit
`InvalidRequestError: A value is required for bind parameter '113'`. Ursache:
`op.execute(str)` dreht den String durch `sa.text()`, und das liest **jeden Doppelpunkt ohne
vorangehendes Wortzeichen** als Bind-Parameter. Im Tabellen-Schild stand die Zeilenangabe frei
(`in :113-118`) → `%(113)s`. Die Nachbar-Referenz `deepgram_service.py:490` im selben Satz
ueberlebte, weil dort ein Buchstabe vor dem Doppelpunkt steht.

Gefixt auf **zwei** Ebenen (`229edac`), weil die Text-Haelfte allein die Falle nur verschiebt:
- **Text:** volle Datei-Referenz statt nackter Zeilenzahl, in `models.py` und Migration —
  beide bleiben zeichengleich, alle vier Schilder md5-identisch
- **Mechanismus:** `_comment()` nutzt `exec_driver_sql`, damit Schild-Prosa Doppelpunkte und
  Prozentzeichen tragen darf. Das Warum steht als Warnung im Docstring der Funktion, damit die
  naechste Person sie nicht „aufraeumt".

Gegenprobe: keine weitere Migration mit `COMMENT ON` ist betroffen (`0021` hat echte, gewollte
Bind-Parameter). **Production war zu keinem Zeitpunkt halb migriert** — Kopf blieb `0038`,
627 Zeilen, Dienst lief unveraendert seit dem 07.08.

## 4. Pflicht-Notizen

### D-01 (b) — warum keine Wort-Tabelle

*Eine Wort-Tabelle waere faktisch eine zweite Kopie des Transkripts und braeuchte einen eigenen
Schwaerzungs-Pfad — Verstoss gegen „genau EINE Schwaerzungs-Pipeline". Das wiegt schwerer als

**Speicher-Vorbehalt:** die Prod-Stichprobe (627 Zeilen / 77 `conversation_logs` ≈ 8 Segmente je
Anruf) ist von kurzen Test-Anrufen dominiert und **nicht** repraesentativ fuer einen
15-Minuten-Realanruf. Das Verhaeltnis A:B bleibt bei ~100x; die absoluten MB-Zahlen brauchen
diesen Vorbehalt.

die Zeit ergaebe still Unsinn, ohne dass irgendetwas rot wird. Zwei getrennte Achsen sind
ehrlicher als eine Spalte mit zwei Bedeutungen.*

### D-05 / D-06 / D-06a — die Streichung als BENANNTE Grenze

*Naht-Luecken (Reconnect/Pause) sind an der Divergenz zwischen `ts_ms` und der Deepgram-Uhr
erkennbar bzw. an einer negativen Differenz; es gibt bewusst KEINEN Naht-Marker. Beide

**Terminierung:** die Aufnahme des Markers gehoert in **die** Phase, die eine Naht-Quelle real
erreichbar macht — nicht hierher.

*Gegen B: die Sprech-Zeit fehlte sonst in Zaehler UND Nenner des Redeanteils, und die Luecke

## 7. Tueroeffner-Validierung (Bau-Regel 2) — korrigierte Fassung

⚠ Die erste Fassung sicherte zu, dass sich aus diesen Spalten in **jedem** Modus vier
Kenngroessen ergeben. Das ist fuer den dominanten Modus unwahr, und eine Validierung, die etwas
Falsches zusichert, ist schlimmer als keine.

- **Im Meeting-Modus sind alle vier Groessen bestimmbar:** Redeanteil = Summe
  (`end_ms`−`start_ms`) je `speaker` durch Gesamt · Sprechtempo = `word_count` durch
  (`end_ms`−`start_ms`) · Redeblock-Laenge = zusammenhaengende Abschnitte desselben `speaker` ·
  Pausenlaenge = `naechster.start_ms` − `voriger.end_ms`.
- **Im Cold-Call sind Redeanteil und Redeblock-Laenge strukturell nicht berechenbar**
  (Single-Speaker, `diarize=False`, `log_sp` hart 0). **Sprechtempo und Pausenlaenge bleiben
  gueltig** — an `conv=268` gemessen: 205 W/Min, 14 Pausen.

**Zwei Auflagen fuer METRIK-1, hier verankert:**
1. Pausen ueber eine Naht sind `NULL`, erkennbar an negativer Differenz bzw.
   Zwei-Uhren-Divergenz — **nicht `0`**.
2. „Redebloecke nicht kuenstlich kuerzen" muss ueber **zusammengehoerige** Abschnitte gerechnet
   werden, nicht je `is_final`-Abschnitt — sonst ist jeder Block ein Erkennungs-Stueck von fuenf
   Woertern und die Regel schlaegt immer an.
