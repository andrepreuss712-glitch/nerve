## Summary

Die Phase haengt drei neue, nullable Integer-Spalten (`start_ms`, `end_ms`, `word_count`) an
`public.transcript_segments` und fuehrt die dazu noetigen Deepgram-Wortzeiten durch die bestehende
RAM-Kette (`services/deepgram_service.py` on_message -> `ls._session_state[sid]['conversation_log']`
-> `routes/app_routes.py:_transcript_entries_to_segments` -> INSERT). Migration und Schema sind der
kleine, risikoarme Teil; das ist durch Prod-Daten und Code bestaetigt. Der schwierige Teil ist die
Naht selbst UND — das ist der wichtigste Fund dieser Recherche — **ein echter Widerspruch zwischen
der gesperrten CONTEXT.md-Entscheidung D-06 (Naht-Pause = 0) und Claudians spaeterer Korrektur im
Fragen-Kanal (Naht-Pause = NULL, nicht 0)**. CONTEXT.md wurde laut eigenem Kopftext ungelesen aus
den *urspruenglichen* Forscher-Empfehlungen gesetzt, bevor Claudian die Korrektur einbrachte — die
Korrektur ist im selben Dialog-Dokument spaeter dokumentiert, aber nie in CONTEXT.md nachgezogen
worden. Der Plan-Author MUSS das vor dem Bauen mit Andre klaeren (siehe Abschnitt "KONFLIKT").

Zweiter wichtiger Fund: Der einzige Code-Pfad, der `_open_deepgram_connection` fuer eine bereits
laufende `sid` ein zweites Mal aufruft (`services/deepgram_service.py:764-870`), loescht dabei via
`pop_session_state`+`init_session_state` das GESAMTE `_session_state[sid]` inklusive
`conversation_log` — bevor er ueberhaupt prueft, ob eine `call_id` schon existiert. Der
"Reconnect-Fast-Path" (Idempotenz-Check `_existing_cid_f`, Zeilen ~832-847) liest folglich IMMER
`None`, weil der Wert eine Codezeile vorher frisch auf `None` gesetzt wurde. Und clientseitig gibt es
in `static/pip-launcher.js` **keinerlei** Code, der `start_live_session` nach einem `dg_error`/
`dg_close` erneut emittiert — das Frontend loggt den Fehler nur (`console.error`) und tut sonst
nichts. D-05s Versatz-Mechanismus ist fachlich richtig (deckt sich mit Deepgrams eigener
Empfehlung), aber der konkrete "Reconnect-auf-derselben-`call_id`"-Pfad, den CONTEXT.md als Beleg
zitiert, ist im heutigen Code entweder tot oder wuerde ohnehin einen neuen `call_id` samt leerem
Transkript erzeugen. Der Plan muss diesen Punkt entweder als bewusste Vorsorge (Deepgram-Doku sagt:
Reconnects setzen `word.start`/`word.end` auf 0 zurueck — das *kann* durch andere, hier nicht
gefundene Pfade passieren) einordnen, oder den D-05-Aufwand entsprechend re-skalieren.

**Primaerempfehlung:** D-02/D-03/D-04/D-07/D-08/D-09/D-10 wie in CONTEXT.md gesperrt bauen (durch
diese Recherche bestaetigt, keine Aenderung noetig). D-05/D-06 vor Planungs-Start explizit mit Andre

### Pattern 1: Wortzeiten-Extraktion im on_message-Callback

**Was:** `result.channel.alternatives[0].words` ist bereits im `is_final`-Zweig verfuegbar
(`services/deepgram_service.py:188-191`, dort schon fuer den Confidence-Buffer genutzt — derselbe
`words`-Zugriff, nur eine andere Verwendung). Fuer die neue Naht:
`start_ms = round(words[0].start * 1000)`, `end_ms = round(words[-1].end * 1000)`,
`word_count = len(words)` — **plus der per-SID-Versatz aus D-05 addiert.**

**Wann:** im selben `is_final`-Block, VOR dem `anonymize()`-Aufruf (D-07: Wortanzahl aus den
Roh-Wortobjekten, nicht aus dem anonymisierten Text).

```python
# Quelle: services/deepgram_service.py:58-70 (_get_speaker, bestehende Nutzung von
# result.channel.alternatives[0].words) + Context7 developers.deepgram.com/docs/diarization
# (word.start/word.end sind Sekunden seit Verbindungs-Oeffnung, floats)
words = result.channel.alternatives[0].words
if words:
    _start_ms = int(round(words[0].start * 1000)) + versatz
    _end_ms   = int(round(words[-1].end   * 1000)) + versatz
    _word_count = len(words)
else:
    _start_ms = _end_ms = _word_count = None
```

**Edge-Case (nicht in CONTEXT.md explizit adressiert, PLAN MUSS ihn behandeln):** `is_final=True`
Resultate koennen laut Deepgram-Doku theoretisch `words=[]` liefern (leere Transkription mit
Interpunktion o.ae.) — heute fangt `_get_speaker()` das per `if not words: return None` ab
(Zeile 61-62), aber der neue Code-Pfad muss denselben Leer-Fall separat behandeln (NULL statt
Crash/IndexError bei `words[0]`).

### Pattern 2: Per-SID-Reconnect-Versatz (D-05)

**Was:** ein Integer/Float in `ls._session_state[sid]` (z.B. `'_dg_ms_offset'`), gelesen beim
Verbindungsaufbau, geschrieben nach jedem verarbeiteten `is_final`-Resultat mit dem hoechsten
gesehenen `end_ms` (VOR Offset-Addition oder NACH — Plan muss das eindeutig festlegen, sonst
Doppel-Addition).

**Kritischer Fund (siehe Abschnitt "Reconnect-Realitaet" unten):** der einzige Aufrufer von
`_open_deepgram_connection` fuer eine bereits belegte `sid` (`services/deepgram_service.py:764-870`,
Handler `handle_start_live_session`) ruft VORHER `ls.pop_session_state(sid)` +
`ls.init_session_state(sid, ...)` — **beide loeschen `_session_state[sid]` komplett**, inklusive
eines dort gehaltenen Offsets. **Der Offset muss also aus dem alten State AUSGELESEN werden, BEVOR
`pop_session_state` laeuft, und NACH `init_session_state` wieder hineingeschrieben werden** — sonst
resettet exakt der Mechanismus, den D-05 verhindern soll, bei jedem "Reconnect" wieder auf 0. Das
ist eine Pre-Insert-Control-Flow-Notwendigkeit (Punkt 14), die CONTEXT.md nicht erwaehnt.

### Anti-Patterns to Avoid

- **`ts_ms` fuer irgendeine der vier Kennzahlen verwenden** — Sekunden-Aufloesung macht
  Sprechtempo/Pausenlaenge unbrauchbar (CONTEXT.md D-02, mehrfach belegt).
- **`word_count = 0` fuer Zeilen ohne Deepgram-Zeiten** — verwaesst Redeanteil/Sprechtempo
  (D-04, EWB-Knopf-Zeile).
- **Wortanzahl aus dem anonymisierten Text zaehlen** (`len(anon_text.split())`) — zaehlt
  Platzhalter-Tokens (`[PERSON_A]` etc.), nicht gesprochene Woerter (D-07 explizit verworfen).
- **Ein zweiter RAM-Kanal/eine neue Datenstruktur fuer die Zeiten** — D-08 verwirft das explizit
  zugunsten der bestehenden `conversation_log`-Dicts.
- **`_migrate()`-Pattern statt Alembic** — auf Postgres wirkungslos (`app.py:140` returnt frueh bei
  Postgres, `[VERIFIED: alembic/versions/0036 Kommentar zitiert dieselbe Zeile]`).

## Reconnect-Realitaet — Forschungs-Frage 2 (ausfuehrlich)

**Frage:** Prove from the code whether a reconnect on the same call really opens a fresh Deepgram
connection (and therefore resets the word clock to 0), and whether audio is withheld during pause.

### Deepgram-Vertrag (offiziell, `[CITED]`)

- `[CITED: developers.deepgram.com/docs/recovering-from-connection-errors-and-timeouts-when-live-streaming-audio]`
  — *"When reconnecting to the Deepgram API, new streaming sessions reset timestamps to 00:00:00.
  [...] your application should maintain a starting timestamp [...] added to all returned
  timestamps."* — das ist GENAU D-05s Versatz-Pattern, Deepgram empfiehlt es selbst.
- `[CITED: developers.deepgram.com/docs/audio-keep-alive]` — *"Word timings [...] are based on the
  audio stream itself, not the lifetime of the WebSocket connection. If you send KeepAlive messages
  without any audio payloads [...] the timestamps will continue from where the audio left off — not
  from when the KeepAlive messages were sent."* Bestaetigt D-06: waehrend Pause (kein Audio, aber
  SDK-eigene KeepAlives laufen im Hintergrund, `services/deepgram_service.py:460-465`,
  `[VERIFIED]`) steht die Deepgram-Uhr still, kein Zeit-Vorlauf.
- `[CITED: developers.deepgram.com/docs/diarization]` — `word.start`/`word.end` sind Floats in
  **Sekunden**, Beispiel `"start":15.259043` — Millisekunden-Umrechnung ist `* 1000`, KEINE weitere
  Einheiten-Unklarheit.

   (`pip-launcher.js:1622-1629`). `[VERIFIED: grep "start_live_session" static/ -> genau 1 Emit-Stelle]`
4. **Der einzige (theoretische) Weg, wie `_open_deepgram_connection` fuer eine schon aktive `sid`
   ein zweites Mal laeuft**, ist ein zweites Client-seitiges `start_live_session`-Event auf DEMSELBEN
   Socket (Doppelklick, doppelte Navigation etc. — laut Code-Kommentar "SID reconnects before
   disconnect fires", `deepgram_service.py:742/761`). In diesem Pfad:
   - `if _sid in ls._session_state: ls.pop_session_state(_sid)` (Zeile 764-765) — **loescht
     `conversation_log` und alle anderen per-SID-Daten komplett.**
   - `ls.init_session_state(_sid, ...)` (766-774) — legt `_session_state[sid]` FRISCH an,
     `state.call_id = None` (`live_session.py:719`).
   - **Erst danach** (Zeile ~835-841) wird `_existing_cid_f = ls._session_state.get(_sid, {}).get(
     'state', {}).get('call_id')` gelesen — das liest den Wert, der eine Codezeile vorher gerade auf
     `None` gesetzt wurde. **`_existing_cid_f` kann in diesem Ablauf nicht `!= None` sein** —
     `create_call_for_sid` wird also bei jedem erneuten `start_live_session` IMMER erneut aufgerufen,
     legt einen neuen `call_id` an, und das gesamte bisherige Transkript (`conversation_log`) ist zu
     diesem Zeitpunkt bereits weg.
   - `_open_deepgram_connection(_sid, ...)` (Zeile 870) oeffnet danach die neue Verbindung —
     `word.start`/`word.end` beginnen bei 0.

**Schlussfolgerung (HIGH confidence, code-belegt):** Der von CONTEXT.md zitierte
"Reconnect-Pfad auf dieselbe `call_id`" (`deepgram_service.py:833-846`) ist im heutigen Code so
gebaut, dass er **niemals** eine bestehende `call_id` wiederverwendet — jeder erneute
`start_live_session`-Aufruf auf derselben `sid` erzeugt einen frischen Call MIT leerem Transkript.
Das bedeutet: **der eigentliche Kontinuitaets-Bruch, den D-05s Versatz reparieren soll (alte
Segmente + neue Segmente im selben `conversation_log` mit zurueckspringender Zeitachse), tritt im
heutigen Code so nicht ein** — weil die alten Segmente beim "Reconnect" ohnehin schon geloescht
sind, bevor die neue Verbindung oeffnet. Der Versatz-Mechanismus wuerde in diesem konkreten Pfad auf
ein leeres `conversation_log` angewendet und waere folgenlos richtig, aber auch folgenlos nutzlos.

**Was das fuer den Plan bedeutet — drei Optionen, keine davon vorentschieden von dieser Recherche:**
1. **D-05 trotzdem bauen** als Vorsorge fuer einen Reconnect-Pfad, der heute nicht sauber
   nachvollzogen werden konnte (z. B. wenn `_session_state_lock`-Contention den Pop/Init-Ablauf
   zeitlich anders interleaved, oder ein zukuenftiger Retry-Mechanismus im Frontend nachgezogen
   wird) — konsistent mit Deepgrams eigener Empfehlung, geringes Bau-Risiko (ein paar Zeilen).

## Common Pitfalls

### Pitfall 1: Doppel-Addition des Reconnect-Versatzes
**Was schiefgeht:** Wenn der Versatz sowohl beim Lesen als auch beim Schreiben addiert wird, oder
wenn er bei jedem `is_final`-Resultat statt nur beim Verbindungsaufbau aktualisiert wird, driften die
Zeiten.
**Warum:** die Versatz-Logik lebt an zwei Stellen (Connection-Open + laufende Aktualisierung des
"zuletzt gesehenes end_ms").
**Vermeidung:** genau EIN Ort schreibt den Versatz (beim Open), genau EIN Ort addiert ihn (beim
Verarbeiten jedes `words`-Arrays). Unit-Test mit zwei simulierten Verbindungen deckt das ab.
**Warnzeichen:** `end_ms` eines spaeteren Segments kleiner als `start_ms` eines frueheren.

### Pitfall 2: `pop_session_state` loescht den Versatz mit
**Was schiefgeht:** siehe Abschnitt "Reconnect-Realitaet" — der Versatz wird bei jedem
Session-Reset auf 0 zurueckgesetzt, wenn er nicht explizit ueber den Reset hinweg transportiert wird.
**Vermeidung:** Versatz-Wert VOR `pop_session_state` auslesen, NACH `init_session_state` wieder
hineinschreiben (Punkt 14 Control-Flow-Pflicht).
**Warnzeichen:** Test, der zwei aufeinanderfolgende `start_live_session`-Events auf derselben `sid`
simuliert, zeigt Versatz=0 beim zweiten Mal.

### Pitfall 3: `words[0]`/`words[-1]` bei leerer Liste
**Was schiefgeht:** `IndexError`, wenn `result.channel.alternatives[0].words` leer ist, obwohl
`is_final=True` und `text` nicht-leer war (moeglich bei reinen Interpunktions-/Formatierungs-Resultaten
laut Deepgram-Verhalten).
**Vermeidung:** expliziter `if not words: start_ms = end_ms = word_count = None`-Zweig, analog zu
`_get_speaker()` (`deepgram_service.py:61-62`).
**Warnzeichen:** Crash-Log im Live-Loop-Thread, Call haengt.

### Pitfall 4: Wortanzahl nach statt vor Anonymisierung gezaehlt
**Was schiefgeht:** `[PERSON_A]`/`[ORG_B]`-Platzhalter zaehlen als je EIN Wort, unabhaengig davon
wie viele Woerter im Original standen ("Herr Mueller" = 2 Woerter -> `[PERSON_A]` = 1 Token) —
verzerrt Sprechtempo systematisch nach unten.
**Vermeidung:** `word_count = len(words)` explizit VOR dem `anonymize()`-Aufruf berechnen (D-07),
nicht aus `_anon_text.split()`.
**Warnzeichen:** Sprechtempo-Werte, die bei Namen-/Firmen-lastigen Gespraechen systematisch
niedriger sind als bei neutralen.

### Pitfall 5: `slow_lane.py` liest weiterhin `created_at` — durch neue Spalten NICHT automatisch
besser
**Was schiefgeht:** ein spaeterer Leser koennte annehmen, `start_ms`/`end_ms` loesen die in Punkt 26
dokumentierte Batch-Write-Falle in `slow_lane.py:205-209` automatisch — tun sie nicht, weil
`_find_next_advisor_utterance` weiterhin explizit auf `TranscriptSegment.created_at >= ev.timestamp`
filtert (`[VERIFIED: services/slow_lane.py:205-209]`), nicht auf `start_ms`.
**Vermeidung:** im Plan/SUMMARY explizit festhalten, dass diese Phase `slow_lane.py` NICHT anfasst
(schon in CONTEXT.md "Deferred" so vermerkt) — nur sicherstellen, dass die neuen NULL-Spalten den
bestehenden `created_at`-Filter nicht stoeren (tun sie nicht, ORM-Query selektiert nicht auf sie).

def _transcript_entries_to_segments(log_entries):
    out = []
    base = None
    running = 0
    for _entry in (log_entries or []):
        if not isinstance(_entry, dict) or _entry.get('type') != 'transcript':
            continue
        _txt = _entry.get('text') or ''
        if not _txt:
            continue
        _raw_ts = _entry.get('ts')
        _abs = _ts_to_ms_of_day(_raw_ts)
        if base is None:
            base = _abs
        _rel = _abs - base
        if _rel < running:
            _rel = running
        running = _rel
        out.append({
            'ts_ms': _rel,
            'speaker': _sp_map.get(_entry.get('speaker'), 'system'),
            'text': _txt,
            # NEU (D-08): einfaches Durchreichen, kein Rechnen noetig — die RAM-Eintraege tragen
            # start_ms/end_ms/word_count bereits fertig berechnet (oder None fuer den Knopf-Schreiber)
            'start_ms': _entry.get('start_ms'),
            'end_ms': _entry.get('end_ms'),
            'word_count': _entry.get('word_count'),
        })
    return out
