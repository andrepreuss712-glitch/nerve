<decisions>
## Implementation Decisions

### D-01: Einwand-Schubladen — Kern-Taxonomie FEST im Code, nicht user-editierbar (André-Entscheidung)
Die Kern-Taxonomie (`echter_einwand`, `vorwand`, `reflexeinwand`, `kaufsignal`, `aufschub`,
`info_frage` + Gemini-Ergänzungen `gatekeeper`, `wettbewerber_referenz`, `hard_opt_out`,
`commitment`, `meta_kommunikation`) bleibt **fest im Code als versioniertes Enum/Konstante**,
mit `taxonomy_version` an jedem Event. **Bewusst NICHT user-editierbar.**

**Begründung (André):** Die Kern-Taxonomie ist der geteilte Vertrag für Erkennung + Benotung
(TAXO2) + den späteren KI-Trainings-Korpus (DPO). Wäre sie user-editierbar, zerhaut ein
späterer Kategorie-Split Analytics + Trainings-Korpus. Single-Source-Vertrag schlägt
Flexibilität.

**User-Erweiterung läuft AUSSCHLIESSLICH über `custom_objection_*`** pro Profil (pro-Profil
überschreibbares Label, kein Schema-/Code-Umbau bei neuem Einwand). Damit ist Punkt 12
(Eingriffs-Möglichkeit / Marge-Mentalität) erfüllt, OHNE den Kern weichzumachen.

**Planungs-Folge (löst SPEC-Req 5 „D2 zwei Welten"):** Das alte `ist_vorwand`-String/Boolean
in `claude_service.py:966` UND der `einwand_typ`-Enum in `profile_schema` werden auf GENAU
DIESE EINE versionierte Quelle umgezogen. Der Live-Klassifikator schreibt nur noch daraus.
Alte parallele Pfade löschen (Single-Source-Direktive §0.1).

### D-02: Umbau-Risiko — Wellen-Schnitt wie SCHILD, KEIN Big-Bang (André-Entscheidung)
Inkrementeller Bau in Wellen (wie Phase 08.23.2.SCHILD), KEIN Big-Bang. Begründung:
Kernfeature-Umbau (Live-Assistent) + Pfad-Löschungen + kein Local-Dev = Inkrement de-riskt.
Jede riskante Welle wird einzeln auf Production verifiziert, bevor die nächste kommt.

### D-03: Test-Takt — Test-Anruf nur bei riskanten Wellen, mit 3 Auflagen (André-Entscheidung)
Test-Anruf auf Production nach jeder Welle, die einen laufenden Anruf kaputtmachen KÖNNTE.
Reine Schema-Addition ohne Live-Anbindung überspringt den Test-Anruf (nur Auto-Check).

**Auflage 1 — „Riskant" großzügig auslegen:** Alles was Live-Erkennung anfasst / einen alten
Pfad löscht / Modus-Routing ändert = Test-Anruf. NUR reine Schema-Addition (leere
`intent_event`-Tabelle anlegen, Klempnerei-Gerüst OHNE Live-Anbindung) darf überspringen.
**Im Zweifel: Test-Anruf.**

**Auflage 2 — Auto-Check ist schwach, deshalb verstärken:** Das `deploy.sh`-Test-Tor ist kaputt
bis Phase 08.23.2.STAGING. Für übersprungene Wellen heißt „Auto-Check" nur: Migration lief +
App startet. Deshalb bei JEDER Schema-Welle (`intent_event`, `ewb_ratings`-Zombie) zusätzlich
den **SCHILD-Wächter MANUELL server-seitig gegen die Prod-DSN laufen lassen** (Punkt 23 +
SPEC-Constraint).

**Auflage 3 — Test-Anruf muss DATEN-FLUSS verifizieren, nicht nur „Anruf ok":** Pflicht-Checks
pro Test-Anruf: (a) `intent_event`-Zeilen werden wirklich geschrieben (`inspect.sh count/sample
intent_event` steigt mit korrektem `intent_type`/`phase`/`mode`/`source`/`speaker_role`),
(b) Dashboard-Einwand-Zähler stimmt nach dem Anruf (objection_events-Spiegel befüllt),
(c) Phase/Readiness bewegen sich, `org_id` im Kosten-Log ≠ NULL, keine `user_id leer`-Warnung.
**Begründung (André):** K1/K8 waren deployed-aber-tot — kein Crash, der Wert kam nur nie an.
Genau diese Pfade bauen wir hier um, also wird der Daten-Fluss bewiesen, nicht angenommen.

### D-04: Wegwerf-Brücke (Dual-Write) — MINIMAL, klar als befristet markiert (empfohlener Default, #1 nicht einzeln besprochen)
Die `objection_events`-Dual-Write-Brücke wird so dünn wie möglich gebaut: `intent_event` ist
die primäre Single Source; derselbe Erkennungs-Schreibpfad spiegelt übergangsweise das Nötige
nach `objection_events`, damit Dashboard-Einwand-Zähler + `integration_engine` + `admin_views`
nicht brechen. KEIN Schnickschnack: kein Rück-Sync, kein Backfill alter Zeilen, keine
Zusatz-Features auf der Brücke.

- Als EIN gekapselter, klar kommentierter Expand-Contract-Shim bauen (eine Stelle, nicht
  über den Code verstreut), mit explizitem `# SUNSET: TAXO2`-Marker.
- **Begründung:** Anti-Abrieb (Punkt: „lieber einmal richtig"). Die Brücke fliegt in TAXO2 eh
  raus — nicht in Wegwerf-Code investieren. Gleichzeitig gekapselt genug, dass sie selbst keine
  Bugs in den Live-Pfad einschleppt.
- Die eigentliche Zombifizierung von `objection_events` + Umzug seiner Leser = TAXO2 (locked).

### D-05: Neuer Antwort-Baustein (EWB v2-modular) — Live-Test ist eine eigene riskante Welle (empfohlener Default, #4 nicht einzeln besprochen)
Die EWB-Umstellung (v2-modular als die EINE Variante, v1-legacy → Reserve/deaktiviert) ist
laut D-03 eine **riskante Welle** (ändert Live-Verhalten) → bekommt einen eigenen Test-Anruf.

- Dieser Test-Anruf enthält Pflicht den **Fachbegriff-Check**: prüfen, dass die Technik-Schritt-
  Labels (`ANKER`/`REFRAME` etc.) NICHT als Vokabular in den vorgelesenen Antworten landen
  (Gerüst §4.5: Technik unsichtbar). Plus Log-Beleg `[EWB] vv2-modular assembled`.
- ENV `PROMPT_EWB_VERSION_OVERRIDE` bleibt als <30s-Notbremse (Punkt 12, reversibel).
- **Caveat (aus SPEC):** v2-modular ist die bessere Brücke, NICHT das Ziel — TAXO3 ersetzt
  diesen hardcoded Prompt durch `build_answer_context()`. Nicht über-investieren.

### Claude's Discretion (Researcher/Planner entscheiden)
Rein technische Detail-Entscheidungen, die André bewusst delegiert hat:

- Konkreter Wellen-Schnitt (Reihenfolge + Grenzen der einzelnen Bau-Wellen) — Planner entwirft
