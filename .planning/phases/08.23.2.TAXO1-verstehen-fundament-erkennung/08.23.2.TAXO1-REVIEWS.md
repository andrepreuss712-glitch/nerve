## Gemini Review

### 1. Summary

This is an exceptionally well-structured and detailed set of implementation plans. It demonstrates a strong grasp of the existing system's complexities and risks, particularly given the "production-only" verification constraint. The phased, wave-based approach is a significant strength, systematically de-risking a complex migration by isolating schema changes, state refactoring, and live-path cutovers. The plans are grounded in thorough research, clearly define their scope and dependencies, and specify concrete verification steps. While the overall strategy is sound, there are a few notable risks, primarily concerning data durability in the proposed "Slow Lane" and the inherent limitations of "best-effort" shutdown procedures in a live environment.

### 2. Strengths

- **Risk-Aware Phased Rollout:** The breakdown of the complex migration into seven distinct, sequentially dependent plans ("waves") is the biggest strength. It correctly isolates high-risk changes (state refactoring, live cutover) from low-risk changes (additive schema changes) and applies appropriate verification (Test-Anruf vs. auto-check), directly implementing the user's decisions (D-02, D-03).
- **Grounded in Research:** The plans consistently and effectively translate findings from `RESEARCH.md` into concrete actions, addressing known bugs (K3, K4, K8), zombie table readers (`admin_ewb.py`), and state management flaws (§0.1 Putzliste) directly.
- **Clear Contracts & Boundaries:** The design rigorously enforces the boundaries between TAXO1, TAXO2, and TAXO3. Defining the complete `intent_event` schema upfront (Plan 01), including nullable columns for future scoring, is excellent foresight that ensures forward compatibility.
- **Centralized, Encapsulated Logic:** The creation of a single `emit_intent_event` function (Plan 04) as the sole writer to the new central table is a robust design pattern that enforces consistency and validation. Similarly, encapsulating the `objection_events` compatibility layer into a minimal, temporary Dual-Write Bridge (Plan 05) is pragmatic and prevents scope creep.
- **Attention to Detail:** The plans exhibit a high level of diligence, including small but critical details like the "Fachbegriff-Check" for the EWB v2 prompt (Plan 06), defense-in-depth type coercion for the K3 bug (Plan 03), and specifying the use of an adapter for the Slow Lane queue to facilitate future upgrades (Plan 02).

### 3. Concerns

- **[HIGH] Slow Lane Data Loss on Crash (Plan 02):** The proposed Slow Lane uses an in-memory `queue.Queue`. In the event of an unexpected process termination (e.g., `kill -9`, hardware failure, OOM killer), all `intent_event` references currently in the queue will be permanently lost. As this data is the foundation for the future scoring and training flywheel (TAXO2), and "Production IS the test environment," this represents a significant data integrity risk. The plan for a "graceful shutdown" only mitigates clean shutdowns.
- **[MEDIUM] `atexit` Graceful Shutdown Unreliability (Plan 02):** The reliance on `atexit` for the graceful shutdown flush is a "best-effort" solution. It is not guaranteed to run on all signal types (like SIGKILL) or in all failure modes. This is a lesser version of the data loss concern, as it specifically addresses the limitations of the chosen shutdown hook mechanism. While likely sufficient for Early Access, it's not a fully durable solution.
- **[LOW] Idempotency of Call Finalization (Plan 05):** The dual-write bridge in Plan 05 replaces the old write path for `objection_events`. The plan correctly identifies the risk of double-writes. While replacing the logic is the right approach, it's critical to ensure the entire call finalization process, including the `mirror_intent_events_to_objection_events` call, is fully idempotent. If the `/api/beenden` endpoint could be called twice for the same session, this could still result in duplicate `objection_events` rows unless the mirror function itself performs a check-then-insert/upsert.
- **[LOW] Manual Verification Steps (All Plans):** The entire workflow relies heavily on manual, disciplined execution of `inspect.sh` commands and the `SCHILD-Guard` against the production environment. While the plans are explicit about this, it remains a process risk. A forgotten check or a misinterpretation of the output could allow a bug to slip through, which would have been caught by an automated CI/test gate.

### 4. Suggestions

- **Plan 02 (Slow Lane):** To mitigate the data loss risk before a full Redis implementation, consider a simple file-based persistence mechanism for the queue. The `SlowLaneQueue` adapter could be modified to periodically (e.g., on a timer or after N items) and during the `atexit` flush, dump the queue's content to a file on disk. On startup, the queue would be repopulated from this file. This would offer a significant durability improvement over a pure in-memory queue with minimal added complexity.
- **Plan 05 (Dual-Write Bridge):** To guarantee idempotency, the `mirror_intent_events_to_objection_events` function should first check if `objection_events` for the given `conversation_log_id` already exist. If they do, it should either skip the operation or, more robustly, `DELETE` the existing entries for that `conversation_log_id` before `INSERT`ing the new ones. This ensures a clean, repeatable state even if the finalization logic is triggered more than once.
- **Plan 03/04 (K3/K4 Fixes):** Add optional, simple regression tests for the K3 (`detect_phase` with string input) and K4 (`classify_utterance` with low confidence) bug fixes. While the project has no local dev environment, these pure-logic functions could be tested server-side with `pytest` to prevent future regressions.

### 5. Cross-Plan Interlock Check

The seven plans are exceptionally well-interlocked. The dependency ordering is logical and correct, minimizing risk at each step.

- **Schema Foundation (Plan 01):** The `intent_event` schema is the central contract. Plan 01 defines it comprehensively, correctly anticipating the needs of all subsequent plans. The inclusion of nullable fields for future phases (`handling_score_numeric`) and context fields for current needs (`mode`, `speaker_role`, `confidence`) is a key enabler for the other plans.
- **Data Flow:** The data flow is clean. Plan 03 first cleans up the state sources. Plan 04 then re-routes the live detection to write to the new table using this clean state. Plan 07 further refines the data being written by introducing mode-specific strategies. Plan 05 acts as a consumer of the new table, reading from `intent_event` to feed a legacy table. Plan 02 provides the asynchronous infrastructure to consume these events later.
- **Dependencies:** The `depends_on` metadata in each plan appears correct. A critical dependency is Plan 03 (state cleanup) running before Plan 04 (live cutover), which the plan correctly identifies. This ensures the new `intent_event` records are populated with correct `user_id`, `phase`, etc., from day one.
- **No Mismatches:** There are no apparent mismatches between what one plan produces and another consumes. For example, the `mode`/`speaker_role`/`speaker_id` fields required by the `intent_event` schema in Plan 01 are provided by the ModeStrategy in Plan 07 and written during the cutover in Plan 04. The interlock is solid.

### 6. Risk Assessment

**MEDIUM**

The overall plan set is of very high quality, demonstrating a sophisticated approach to risk management. The "HIGH" rating is avoided because the detailed research, wave-based rollout, and specific verification steps significantly mitigate the inherent risks of modifying a live system without a dedicated testing environment.

However, the risk cannot be classified as "LOW" due to two primary factors:
1. The acknowledged risk of data loss from the in-memory "Slow Lane" queue in a production environment where crashes can occur.
2. The heavy reliance on disciplined, manual verification instead of automated testing, which introduces potential for human error.

The plan is as safe as it can be within the project's stringent constraints, but the "Production is the test environment" paradigm coupled with the identified data durability gap elevates the residual risk to a medium level.

## Consensus Summary

Single external reviewer (Gemini). Findings ranked by actionability for a replan decision.

### Actionable Concerns (priority order)

1. **[HIGH] Slow Lane in-memory queue loses data on hard crash (Plan 02).** `queue.Queue` events vanish on `kill -9` / OOM / hardware failure. This data is the TAXO2 scoring + training-flywheel foundation. **→ Decision needed:** accept the gap for EA (queue holds only short-lived references, live lanes are unaffected since intent_event is already persisted by Plan 04's `emit_intent_event`), OR add the suggested file-spill durability to the `SlowLaneQueue` adapter now. *Note: verify whether the Slow Lane actually carries un-persisted state or only references to already-written `intent_event` rows — that distinction decides whether this is HIGH or LOW in practice.*
2. **[MEDIUM] `atexit` flush is best-effort (Plan 02).** Won't fire on SIGKILL. Same root as #1. Consider SIGTERM handler (gunicorn/systemd sends SIGTERM first) in addition to `atexit` for graceful restarts/deploys — that covers the common case (`deploy.sh` restart) even if not the crash case.
3. **[LOW] Dual-Write bridge idempotency (Plan 05).** Make `mirror_intent_events_to_objection_events` idempotent (check-then-skip or DELETE-by-`conversation_log_id`-then-INSERT) so a double `/api/beenden` can't double-count the Dashboard objection counter.
4. **[LOW] Manual verification reliance (all plans).** Inherent to the pre-launch "Production is the test env" constraint — not fixable in this phase, but the K3/K4 pure-logic regression tests (Gemini's suggestion) would add cheap automated coverage server-side.

### Strengths Affirmed
Wave-based de-risking, single `emit_intent_event` writer, complete forward-compatible `intent_event` schema, encapsulated Dual-Write bridge, and **solid cross-plan interlock** (Plan 03 → 04 ordering correct; 01's schema satisfies 02/04/05/07 and downstream TAXO2/TAXO3 with no field mismatches).
