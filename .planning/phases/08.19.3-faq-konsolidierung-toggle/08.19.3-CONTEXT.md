# Phase 08.19.3: FAQ-Konsolidierung mit Toggle — Context

**Gathered:** 2026-04-28
**Status:** Ready for planning

<domain>
## Phase Boundary

FAQ-Konsolidierung: Zwei überlappende UI-Sektionen ("Häufige Fragen" aus `daten.fragen` JSON + "FAQ-Datenbank" aus `profile_faqs` DB-Tabelle) zu EINER Sektion mit Toggle-Modus pro Eintrag konsolidieren. Toggle steuert: `literal` (Embedding-Match → wortwörtlicher Auswurf, kein LLM-Call) vs. `ki_generated` (KI generiert Antwort aus Kontext-Wissen).

**In scope:**
- Schema-Migration: `mode`-Spalte zu `profile_faqs` + Backfill + `daten.fragen` → `profile_faqs` Migration
- Backend: `match_faq()` mode-aware (nur `literal`-FAQs für direkten Auswurf)
- Backend: `build_profile_context()` inkludiert ALLE FAQs als Q+A-Block (Foundation für 08.20)
- Frontend: "Häufige Fragen"-Sektion (`fragen-list` DOM) entfernen
- Frontend: Toggle-Switch pro FAQ-Card in der bestehenden FAQ-Datenbank-Sektion

**Out of scope:**
- `build_profile_context()` Reihenfolge-Refactor (08.20)
- Schema-Realität-Kalibrierung + tote Felder säubern (08.19.1 — kommt nach dieser Phase)
- Pipeline-Re-Wire: System/User-Message-Split, PreCall-Inject, Manual-EWB (08.20)

</domain>

<decisions>
## Implementation Decisions

### Schema-Migration

- **D-01:** `profile_faqs`-Tabelle: neue Spalte `mode VARCHAR(20) NOT NULL DEFAULT 'ki_generated'` via idempotenter `ALTER TABLE` in `app.py _migrate()` mit Advisory-Lock-Pattern (analog Block E + 08.13).
- **D-02:** Backfill: bestehende `profile_faqs`-Rows erhalten `mode='literal'` — Bestandsverhalten (Embedding-Match-Pfad) bleibt erhalten bis User explizit umschaltet.
- **D-03:** Migration `daten.fragen → profile_faqs`: Pro Profil alle `daten.fragen`-Einträge als `profile_faqs`-Rows inserten mit `mode='ki_generated'`. Idempotenz-Check: **Exact Match + TRIM** — `SELECT EXISTS WHERE frage_muster = trim(f) AND profile_id = p.id`. Kein Case-insensitive-Matching nötig.
- **D-04:** `daten.fragen`-Key nach Migration auf **leeres Array `[]`** setzen (nicht entfernen). Grund: profile_schema.py und alle `.get('fragen', [])` Aufrufe bleiben crash-safe. Saubere Entfernung kommt in 08.19.1 (Schema-Kalibrierung).
- **D-05:** Test gegen Production-Profile: Andre's Profil 6 + System-Profil 7 — alle bestehenden Einträge verlustfrei migriert, strict-Mode-Test gemäß CLAUDE.md Regel 13 (Real-Daten-Validation).

### Backend-Logik

- **D-06:** `match_faq()` in `qa_pipeline.py` selbst bleibt unverändert — sie filtert nicht intern nach `mode`. Der **Caller** (qa_pipeline-Dispatcher in `claude_service.py`) filtert die FAQ-Liste vor dem `match_faq()`-Aufruf: nur `mode='literal'`-FAQs werden übergeben.
- **D-07:** `mode='ki_generated'`-FAQs werden für den Embedding-Match übersprungen (nicht in die `match_faq()`-Liste aufgenommen).
- **D-08:** Wenn nach `mode='literal'`-Filter eine leere Liste übrig bleibt — `match_faq()` returnt `None` (bestehender Pfad), Standard-EWB-Pipeline greift natürlich. Kein expliziter Fallback nötig.
- **D-09:** `build_profile_context()` in `prompt_pipeline.py`: **ALLE `profile_faqs`** (beide Modi) kommen als Q+A-Block rein. Position: nach `beweise`-Block, vor Anrede-Lock.
- **D-10:** Q+A-Block-Format in `build_profile_context()`:
  ```
  Häufig gestellte Fragen + Muster-Antworten:
  - F: [frage_muster]
    A: [antwort]
  ```
  Block nur wenn mindestens 1 FAQ existiert. DB-Query in `build_profile_context()` via `profile_id` aus `live_session.get_active_profile()`.
- **D-11:** PUT `/profiles/api/profile/faqs/<id>` in `routes/profiles.py` erweitern: `mode`-Feld aus Request-Body auslesen + validieren (`literal` oder `ki_generated`), in DB schreiben. Bestehende Felder (frage_muster, antwort, kategorie) bleiben updatebar.
- **D-12:** GET `/profiles/api/profile/<id>/faqs` Response erweitern: `mode`-Feld in jedem FAQ-Objekt mitliefern.

### Frontend

- **D-13:** "Häufige Fragen"-Sektion (HTML: `<!-- ehemals sec-fragen -->`, DOM-ID `fragen-list`, JS-Funktionen `addFrage()`/`getFragen()`) komplett entfernen — HTML, JS-Render, JS-Save-Pfad.
- **D-14:** `fragen: getFragen()` im Speicher-Payload (Zeile ~1163 in profile_editor.html) entfernen.
- **D-15:** Per FAQ-Card: **Custom CSS Toggle Switch** (Two-State, `<label>` + `<input type="checkbox">`). Links "Wortwörtlich" (`literal`) — grau/neutral. Rechts "KI generiert" (`ki_generated`) — teal (#00D4AA) aktiv als Default-Hervorhebung. Analog zum bestehenden Toggle-Pattern (`toggleBlock`, `toggleEW`) in Stil.
- **D-16:** Toggle persistiert direkt via `fetch` (PUT auf `/profiles/api/profile/faqs/<id>`) mit `X-CSRFToken`-Header (Polish-Cycle 5 Lesson). Kein globaler Speichern-Klick nötig.
- **D-17:** Inline-Hilfetext pro Toggle (als `title` oder `.field-desc`-Span):
  - "Wortwörtlich = KI spielt deine Antwort exakt so aus wenn die Frage erkannt wird."
  - "KI generiert = KI nutzt deine Antwort als Wissen und formuliert situationsabhängig."
- **D-18:** FAQ-Datenbank-Sektion bleibt in Sektion ④ "Einwände & Antworten" wo sie heute ist.

### Claude's Discretion

- Genaues CSS für den Toggle-Switch (Breite, Animationsgeschwindigkeit, Übergänge) — solange teal/#00D4AA für aktiven Zustand und grau für inaktiven Zustand.
- Exakte Position des Toggle-Switches innerhalb der FAQ-Card (z.B. oben rechts oder unter dem Antwort-Text).
- Ob der mode-Label ("Wortwörtlich" / "KI generiert") neben dem Toggle als Text-Label angezeigt wird oder nur als Tooltip/title.
- Advisory-Lock-Implementierungsdetail (SQLite-compatible Pattern wie in Block E).

</decisions>

<specifics>
## Specific Ideas

- André's Position: KI-Antworten > wortwörtlich für die meisten Fälle. Wortwörtlich nur für Compliance-kritische Fragen (DSGVO, Preisgarantien, technische Spezifikationen).
- Default für neue FAQs = `ki_generated` (aus `mode VARCHAR(20) NOT NULL DEFAULT 'ki_generated'`)
- Migrations-Default für bestehende `profile_faqs` = `literal` (Backwards-Compat, Verhalten bleibt bis User umschaltet)
- Migrations-Default für aus `daten.fragen` migrierte Einträge = `ki_generated`

</specifics>
