# Phase 08.19.3: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Reviewed 7 files covering the FAQ-Konsolidierung-Toggle feature (Phase 08.19.3). This phase adds a `mode` toggle (literal vs. ki_generated) to FAQ entries, consolidates FAQ sections in the profile editor, and injects the FAQ Q+A block into the prompt pipeline.

The overall code quality is good. The new FAQ mode toggle has solid optimistic-revert error handling in the JS. The prompt pipeline FAQ injection is correctly capped at 20 entries and sorted by `used_count`. No critical security or data-loss issues were found.

Four warnings are raised: one for a missing `role_check` ordering issue in `api_faqs_create`, one for a silent `_pitch_dual_write` re-commit hazard after session close, one for an unguarded `resp.content[0]` access in `claude_service.py`, and one for a logic gap where the mode-toggle DOM state is set before the POST resolves. Four informational findings cover dead code, a redundant double-serialization pattern, duplicate `window.PROFILE_DATEN` assignments, and inconsistent `used_count` reset behavior.

## Warnings

### WR-01: Role check happens AFTER DB open in `api_faqs_create`

**File:** `routes/profiles.py:751-754`
**Issue:** The `_rolle()` permission check on line 751 occurs *after* parsing and validating the request body, but *before* `_require_own_profile()` opens a DB session. However, unlike `api_tabu_update` (line 862) which also does this, the real hazard here is ordering: if `_require_own_profile` is called first (line 753) and returns early due to `p is None`, the DB session is still opened and must be closed. Currently this is fine because the role check precedes the DB open, but the pattern is fragile — any future reordering puts the DB open before the role check, leaking the session if `403` exits before `finally`. The actual current order is safe but warrants a note for maintainers: keep the role check as the first non-trivial guard, before any `get_session()` / `_require_own_profile()` call.

No immediate bug, but `api_tabu_update` at line 862 already has the same pattern but its role check (line 862) comes **after** `_require_own_profile` opens a session at line 864. If `_rolle()` returns 403, the code exits without going through the `finally` block that closes `db`.

**Fix:**
```python
# api_tabu_update — move role check before _require_own_profile:
@profiles_bp.route('/api/profile/<int:profile_id>/tabu', methods=['POST'])
@login_required
def api_tabu_update(profile_id):
    ...
    if _rolle() not in ('owner', 'admin'):          # ← MOVE HERE (before DB open)
        return jsonify({'error': 'Keine Berechtigung'}), 403
    p, db = _require_own_profile(profile_id)         # ← DB opened AFTER role check
    try:
        ...
    finally:
        db.close()
```

### WR-02: `_pitch_dual_write` calls `db.commit()` on a session that may already be closed

**File:** `routes/profiles.py:472-484`
**Issue:** `_pitch_dual_write(db, pid)` is called from `pitch_erstellen` and `pitch_bearbeiten` after the initial `db.commit()` (lines 519, 549). The outer `try/finally` block closes `db` after the handler returns. If `_pitch_dual_write` raises *during* its own internal `db.commit()`, the exception is swallowed by the surrounding `except Exception as _e` catch. However if `_pitch_dual_write` *succeeds* but then the outer `finally` runs `db.close()`, a second commit attempt in the dual-write function after session close would silently fail or raise. The actual risk depends on SQLAlchemy session state — after `db.commit()` the session is still open but `db.close()` is deferred to `finally`. The `_pitch_dual_write` function issues its own `db.commit()` on the **same** session object, which is fine. The dual-write is guarded by `try/except`, so any failure is swallowed. This pattern is accepted project-wide but the dual-write could leave `Profile.daten['pitch']` stale if the outer commit succeeds and the dual-write commit fails.

**Fix:** Log the stale-state explicitly when dual-write fails, so it is detectable:
```python
except Exception as _e:
    print(f"[Profile] pitch dual-write FAILED (stale daten.pitch possible) pid={pid}: {_e}")
```

### WR-03: `resp.content[0]` access without length guard in `claude_service.py`

**File:** `services/claude_service.py:354` (and similarly lines 426, 499)
**Issue:** After each `claude_client.messages.create(...)` call the code immediately accesses `resp.content[0].text`. If the API returns an empty content list (e.g., a stop-reason of `end_turn` with zero blocks, or a network truncation), this raises `IndexError` which propagates up to the calling loop and could crash `analyse_loop`. The broader `except Exception` at the top level catches it, but the error path loses context and may cause the live session to stop emitting results until the next trigger.

**Fix:**
```python
if not resp.content:
    print(f"[claude] empty content from API (module={module})")
    return {}
text = resp.content[0].text.strip()
```

### WR-04: Mode-toggle optimistic update applied before DB confirmation — revert race in `profile_editor.js`

**File:** `static/profile_editor.js:121-124`
**Issue:** The toggle change handler at line 121 applies `_setModeVisual(modeChk.checked)` as an optimistic update immediately, then disables the toggle during the fetch. If the user rapidly opens the editor in two browser tabs and toggles in both simultaneously, the second tab's load via `loadFaqs()` will re-render the row from the DB state and the first tab's optimistic state is already diverged. This is an inherent race in multi-tab scenarios, but more concretely: if the network request fails and `_revertAndNotify()` is called but the page is already partially re-rendered (e.g., another `loadFaqs()` was triggered), the revert may be applied to a stale `modeChk` reference that no longer exists in the DOM.

The current guard `modeChk.disabled = false` in both `.then()` and `.catch()` is correct. The risk is limited to multi-tab use, which is uncommon for a solo-founder tool.

**Fix:** Add a stale-DOM guard before reverting:
```javascript
function _revertAndNotify() {
  if (!document.body.contains(row)) return;  // DOM guard: row may have been removed
  modeChk.checked = prevChecked;
  _setModeVisual(prevChecked);
  ...
}
```

### IN-01: Duplicate `window.PROFILE_DATEN` assignment in `profile_editor.html`

**File:** `templates/profile_editor.html:716,723`
**Issue:** `daten` is serialized to JSON and assigned twice in the same script block:
- Line 716: `const DATEN = {{ daten | tojson | safe }};`
- Line 723: `window.PROFILE_DATEN = {{ daten | tojson | safe }};`

Both contain the same Jinja expression and will produce identical values. The constant `DATEN` appears to be used by the inline script while `window.PROFILE_DATEN` is used by `profile_editor.js`. They could be unified to avoid double serialization and keep them in sync.

**Fix:**
```javascript
const DATEN = {{ daten | tojson | safe }};
window.PROFILE_DATEN = DATEN;  // share one reference
```

### IN-02: `_ACTIVE_PROMPT_CACHE` in `claude_service.py` is never invalidated

**File:** `services/claude_service.py:108-126`
**Issue:** `get_active_prompt_version()` populates `_ACTIVE_PROMPT_CACHE` once per module and never clears it. `prompt_pipeline.py` has `invalidate_resolver_cache()` for its own caches but that does NOT clear `_ACTIVE_PROMPT_CACHE` in `claude_service.py`. If a `PromptVersion` is changed in the DB during a running session, `get_active_prompt_version()` returns the stale cached version for all subsequent calls. This is low-risk if the server is restarted after schema changes, but could cause silent stale-version logging in `ft_assistant_events`.

**Fix:** Either hook `invalidate_resolver_cache()` to also clear `_ACTIVE_PROMPT_CACHE`, or document in a comment that a server restart is required for `PromptVersion` changes to take effect.

### IN-03: `mode` column added to `ProfileFaq` but no migration in `app.py`

**File:** `database/models.py:159` and `app.py` (migration section)
**Issue:** The `ProfileFaq` model (line 159 of `models.py`) defines `mode = Column(String(20), nullable=False, default='ki_generated')`. The `_migrate()` function in `app.py` adds columns for `users`, `organisations`, `billing_events`, `conversation_logs`, etc., but there is no migration entry for `profile_faqs.mode`. On a fresh DB `init_db()` creates the column via `create_all()`. On an existing DB that already has `profile_faqs` but was created before `mode` was added, the column is absent and every FAQ read/write will raise a DB error.

**Fix:** Add a migration entry in `app.py`'s `_migrate()` loop:
```python
# ── profile_faqs ──────────────────────────────────────────────────────
for col, typedef in [
    ('mode', "VARCHAR(20) NOT NULL DEFAULT 'ki_generated'"),
    ('used_count', 'INTEGER DEFAULT 0'),
]:
    try:
        conn.execute(text(f'ALTER TABLE profile_faqs ADD COLUMN {col} {typedef}'))
        conn.commit()
        print(f"[DB] Migration: added profile_faqs.{col}")
    except Exception:
        pass
```

### IN-04: FAQ `used_count` is read in `build_profile_context` for sorting but never incremented by the service

**File:** `services/prompt_pipeline.py:194` and `routes/profiles.py:716-730`
**Issue:** The FAQ injection in `build_profile_context` sorts by `_PF.used_count.desc()` (line 194) to prioritize most-relevant FAQs when the 20-cap is hit. However, searching the reviewed files for any increment of `used_count` finds nothing — the API routes expose it as read-only and no service layer increments it when a FAQ match occurs in the live pipeline. The sort by `used_count` will always produce the same order as insertion order (`id` ASC) for all FAQs with `used_count == 0` (the default), making the ordering logic a no-op until the increment path is implemented.

This is not a crash risk, but the feature intent (hot-FAQ prioritization) is silently non-functional.

**Fix:** When the QA pipeline matches a FAQ (in `qa_pipeline.py`, not reviewed here), increment `used_count` via a separate update query, or document in a comment that the increment path is deferred to a future phase.
