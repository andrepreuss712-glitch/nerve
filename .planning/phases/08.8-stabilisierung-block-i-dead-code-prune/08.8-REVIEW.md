## Summary

This review covers the Block I dead-code pruning phase. The primary concerns are:

1. A **wrong-argument-order bug** in `tests/test_qa_pipeline.py` — tests call `generate_qa_response` with `confidence` and `version` positional args swapped. The function silently accepts `'v1'` as `confidence` and `0` as `version`, bypassing the confidence branch it was meant to exercise.
2. A **stale import** in `routes/training.py` — `build_sekretaerin_prompt` is imported at line 11 but has been superseded by `build_sekretaerin_type_prompt` in all actual call sites. The old function is still live code but the import creates a misleading dependency signal.
3. `services/training_service.py` still defines `SEKRETAERIN_PROMPT` and the old `build_sekretaerin_prompt` wrapper. These are referenced only in `_TRAINING_FALLBACKS` (as the `training_sek` fallback value) and in `routes/training.py`'s import. No functional route calls `build_sekretaerin_prompt` — only the test fixture in `test_08_5_05_training_pipeline_t2.py` (line 59) does, making this code marginal.

No accidental live-code removals were detected. Import cleanup in all other files is correct. Tests in `test_08_5_05_training_pipeline_t1.py` and `test_prompt_pipeline.py` are well-structured and avoid source-presence patterns per CLAUDE.md rules.

## Warnings

### WR-01: Wrong argument order in `test_qa_pipeline.py` — confidence/version swapped

**File:** `tests/test_qa_pipeline.py:183`
**Issue:** The calls to `generate_qa_response` pass positional arguments in the wrong order. The actual signature is:
```python
def generate_qa_response(utterance, category, profile_data, anrede,
                         confidence=1.0, version='', user_id=0)
```
The test calls use:
```python
generate_qa_response('', 'einwand_unknown', {}, 'Sie', 'v1', 0)
generate_qa_response('x', 'smalltalk_none', {}, 'Sie', 'v1', 0)
```
Here `'v1'` is passed as `confidence` (float expected) and `0` as `version` (str expected). Python silently accepts this because the early-exit checks (`if not utterance` or `if category not in (...)`) fire before `float(confidence)` is evaluated. The tests therefore never actually validate the confidence-branch logic — the tests pass for the wrong reason. This is a test reliability issue.

**Fix:**
```python
# Use keyword arguments to make the call unambiguous:
generate_qa_response('', 'einwand_unknown', {}, 'Sie', confidence=1.0, version='v1', user_id=0)
generate_qa_response('x', 'smalltalk_none', {}, 'Sie', confidence=1.0, version='v1', user_id=0)
# Line 192:
result = generate_qa_response('wie teuer?', 'frage', {}, 'Sie', confidence=1.0, version='v1', user_id=0)
# Line 207:
result = generate_qa_response(
    'Wie lange dauert die Implementierung?', 'frage', {}, 'Sie',
    confidence=1.0, version='v1', user_id=0
)
```

### WR-03: `generate_qa_response` called with empty string `''` as `confidence` argument in `_qa_pipeline_dispatch`

**File:** `services/claude_service.py:1180` and `services/claude_service.py:1220`
**Issue:** The call sites in `_qa_pipeline_dispatch` pass `''` (empty string) as the `confidence` argument:
```python
_antwort = generate_qa_response(
    neuer_text, 'einwand_unknown', {}, _anrede, '', _user_id
)
```
The actual signature has `confidence: float = 1.0`. When `''` is passed, `generate_qa_response` evaluates `float(confidence) < CONFIDENCE_THRESHOLD` which calls `float('')` and raises `ValueError` — this is swallowed by the `except Exception` at the bottom, causing a silent `_FALLBACK_RUECKFRAGE` return on every call. The confidence-branch logic is therefore never reached from this call path in production.

**Fix:**
```python
# Pass the actual _conf value from classify_utterance, or 1.0 explicitly:
_antwort = generate_qa_response(
    neuer_text, 'einwand_unknown', {}, _anrede, _conf, _user_id
)
# For the frage fallback path (line 1220), similarly:
_antwort = generate_qa_response(
    neuer_text, 'frage', {}, _anrede, _conf, _user_id
)
```

### IN-03: `_SCORING_FALLBACK_TEMPLATE` in `training_service.py` is only a partial fallback

**File:** `services/training_service.py:681`
**Issue:** The constant `_SCORING_FALLBACK_TEMPLATE` is a short generic preamble string (`"Du bist ein Bewertungs-Experte..."`) stored in `_TRAINING_FALLBACKS['training_scoring']`. At runtime, `generate_scoring()` calls `_load_training_prompt_template('training_scoring', version)` and stores the result in `_scoring_preamble`, but this preamble is **never used** — the full scoring prompt is built from an inline f-string (lines 1129–1164) that does not incorporate `_scoring_preamble`. This means the DB prompt-version lookup for `training_scoring` is wasted work (DB query on every scoring call with no effect). Not a bug — scoring works correctly via the inline prompt — but the preamble machinery is dead from an output perspective.

**Fix:** Either wire `_scoring_preamble` into the scoring prompt (e.g. as a system-prompt prefix) or drop the `_load_training_prompt_template` call in `generate_scoring()` until it is intentionally implemented. The fallback constant and the DB call currently do nothing.
