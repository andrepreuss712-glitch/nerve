## Gemini Review

Cross-AI Plan-Review als Gegenleser für die Phase-1-Pläne (P1-01 + P1-02). Der ruhende Bestandscode
(`services/prompt_pipeline.py`, `services/claude_service.py` etc.) wurde geprüft.

### 1. `build_answer_context` Block-Split (stabil vs. volatil)
**Verdikt: BLOCKER**
Der Ansatz ist konzeptionell richtig, scheitert aber an der Realität des aktuellen Codes in
`prompt_pipeline.py`. Zwei gravierende Cache-Miss/Poisoning-Fallen:
1. **Sektionen-Nummerierung (Index-Falle):** Der Plan spricht von "Sektion 1–9 = stabil; 10–11 =
   volatil". Im aktuellen Code (`build_profile_context`) sind `PreCall-Briefing` jedoch als Sektion 8
   und `Lead-Kontext` als Sektion 9 dokumentiert. Ein stumpfer Array-Split "nach Sektion 9" zieht das
   volatile Lead-Kontext zwingend in den stabilen Block.
2. **`anrede` ist eine Cache-Poisoning-Falle:** In Sektion 7 (KI-Verhalten, Z. 402) wird die Variable
   `anrede` fest in den String eingebacken (`lines.append(f'Anrede: {anrede}...')`). Diese `anrede`
   wird über `_resolve_anrede(ls, ki, sid)` berechnet und priorisiert die **`session_anrede`** (also
   eine flüchtige, per-SID Variable). Bleibt das im stabilen Block, sprengt jede Call-Session mit
   abweichender Anrede den Cache-Prefix für den gesamten User.

**Fix-Vorschlag:** `build_profile_context` (bzw. die neue `_profile_blocks`-Funktion) MUSS so umgebaut
werden, dass `anrede` **komplett** aus Sektion 7 (KI-Verhalten) entfernt und ausschließlich im volatilen
`Lead-Kontext`-Block gerendert wird. Der Split muss über ein Text-Trennmerkmal (z.B. Index von
`## PreCall-Briefing`) erfolgen, nicht über hartcodierte Sektions-Nummern, da die Kommentare im Code
von der Plan-Annahme abweichen.

### 2. EIN-Intent-Durchreichung deterministisch + Punkt-26-Async-Naht
**Verdikt: OK**
Die Async-Naht ist deterministisch und wasserdicht. In `analyse_loop` (`claude_service.py`) wird direkt
nach `ergebnis = analysiere_mit_claude(...)` der Intent in `_med_st['primary_intent']` und die Confidence
in `_med_st['confidence']` geschrieben (unter `ls._session_state_lock`), streng sequenziell im selben
Thread **bevor** nachgelagerte Funktionen wie `_qa_pipeline_dispatch` getriggert werden. Der Leser
(`build_answer_context`) läuft dem Schreiber also niemals voraus. Ein fail-open Default (None →
Default-Intent) ist sicher, da der Fast-Lane-Keyword-Pfad ohnehin seinen Match direkt übergibt und die
Medium-Lane den Wert immer rechtzeitig setzt.

### 3. Paradigma/Rollen-Text (P1-01 Task 1 DRAFT)
**Verdikt: OK**
Der Draft-Text ist exzellent getroffen. Keine Beispielsätze, keine toxischen Technik-Vokabeln
("Reframe", "Anker"). Die Regeln formulieren präzise die gewünschte Haltung ("Benenne die wahrscheinliche
Sorge des Kunden vorsichtig", "Bevorzuge eine kurze, offene Frage"). Klingt menschlich; setzt Gong/Voss-
Prinzipien sauber in Verhaltensanweisungen um, inkl. der harten Tabus (Druck, Mini-Romane, Lügen).

### 4. Latenz (Punkt 25 — Dealbreaker)
**Verdikt: BEDENKEN** (akzeptabel, Latenz-Risiko im Auge behalten)
Voller Profil-Kontext auf dem Auto-Pfad ohne aktives Caching (erst Phase 2) verschlechtert die TTFT
deutlich. Vertretbar für Phase 1, weil (1) der Auto-Pfad im Cold-Call dank PIP deaktiviert ist und nur
im Meeting triggert (geringerer Reaktionsdruck) und (2) Slot A als lokales <1s-Sofortnetz das UI stabil
hält. Phase 2 (Caching) muss aber zwingend der nächste Schritt sein; ein langes Liegenlassen dieses
Stands ist ein Risiko für das Meeting-Feeling.

### 5. Weg-3-Andockstelle wirklich umbaufrei erweiterbar?
**Verdikt: OK**
Die Signatur `load_answer_config(user_id, sid)` ist passgenau. `user_id` (bzw. abgeleitet die
Workspace-ID) ist der exakte FK, um später in `pack_assignments` nach einer Zuweisung zu suchen. Das
Rückgabe-Dict (mit `paradigm`, `roles`, `intent_hints`) ermöglicht der künftigen Coach-Tabelle, das
Paket-Overlay auf den NERVE-Default zu mergen. Da `build_answer_context` nur dieses Dict konsumiert, muss
der Code dort nicht angefasst werden, wenn die DB-Auflösung später in `load_answer_config` injiziert wird.

### Severity-Liste (Gemini)
- **HIGH:** Cache-Poisoning durch `anrede` in Sektion 7 (`KI-Verhalten`). Volatile per-SID-Daten leaken
  in den angeblich stabilen Block.
- **HIGH:** Sektions-Nummerierungs-Drift zwischen Plan-Mentalmodell und echtem Code. Ein Split nach der
  Annahme "Sektion 1-9 = stabil" verlegt Lead-Kontext (im Code Sektion 9) in den stabilen Cache-Block.

### Gesamt-Risiko (Gemini)
**HIGH** — Plan fachlich/konzeptionell stark, importiert aber durch leichte Unschärfe am Bestandscode
(`anrede` + Kommentar-Nummern in `prompt_pipeline.py`) unbemerkt Cache-Miss-Fallen, die das
Architekturziel von Phase 2 torpedieren und im Execute zwingend korrigiert werden müssen.

## Claudian-Gegenprüfung der Befunde (Punkt 24: gegen realen Code verifiziert)

Beide HIGH-Findings **gegen `services/prompt_pipeline.py` (Ruhezustand) bestätigt** — nicht nur Prosa:

**Finding 1 (Sektions-Drift) — BESTÄTIGT, sogar schärfer als Gemini formuliert.**
Der echte Code hat **nur 9 Sektionen**, nicht 11:
- `:243–399` Sektion **1–7** = STABIL (Branche, Basis, Zielkunde, Schmerzen, Einwände, Phasen,
  KI-Verhalten)
- `:433` Sektion **8 = PreCall-Briefing** — `## PreCall-Briefing (volatile — per-SID)`
- `:442` Sektion **9 = Lead-Kontext** — `## Lead-Kontext (volatile — per-SID)`
- Modul-Docstring `:8` sagt explizit "**9-Sektionen** Voll-Profil-Kontext".

Die Plan-Interface-Map (P1-01 Z. 104–109) behauptet dagegen "1 Branche … 7 KI-Verhalten, **8 FAQ, 9
Tabu** = STABIL. **10 PreCall-Briefing + 11 Lead-Kontext** = VOLATIL". → Die Sektionen "8 FAQ / 9 Tabu"
**existieren im Code nicht** als eigene nummerierte Sektionen; die volatilen Blöcke sind **8+9**, nicht
10+11. Ein Split "an der 9/10-Grenze" (wie im Plan, P1-01 Z. 254–258) fasst damit das **gesamte
Profil inkl. volatilem Briefing+Lead als stabil** → Cache-Poisoning zur Phase-2-Aktivierung. Verstößt
gegen SPEC Req 9 ("flüchtige Daten NICHT in den gecachten Prefix").

**Finding 2 (anrede-Poisoning) — BESTÄTIGT.**
`:241 anrede = _resolve_anrede(ls, ki, sid)  # used in Sektionen 7 + 9`;
`:402 lines.append(f'Anrede: {anrede}. WICHTIG: Nutze konsequent {anrede}-Form...')` in der STABILEN
Sektion 7; `_resolve_anrede` (`:465–496`) priorisiert `session_anrede` (per-SID, `:495–496`). Die
`anrede` steht damit **doppelt**: einmal stabil (Sek. 7) + einmal volatil (Sek. 9, `:452`). Der stabile
Treffer ist die Leak-Quelle.

**Findings 2–5 (Gemini) — geteilt/bestätigt:** Async-Naht, Paradigma-Text, Latenz-Abwägung,
Weg-3-Andockstelle sind wie von Gemini beschrieben tragfähig.
