## 1. Lokaler Kontext (Punkt 14 — _persist_event_ref-Insert)
`_persist_event_ref(event_ref, db)` ist in TAXO1 ein No-Op (Marker `# SLOW LANE: No-Op in TAXO1`). TAXO2 ersetzt den Body. Kein early-return-Problem (eigene Funktion). Aufgerufen aus `slow_lane_consumer`-Loop (eigene DB-Session) + `flush_to_db` (drain-Session).

## 2. Funktions-Skelett
`_persist_event_ref(event_ref, db)`: hole intent_event per event_id → wenn `handling_status != 'pending'` return (idempotent, F-01: NICHT mehr "handling_score_numeric not None" — sonst würde abstained/failed neu verarbeitet) → Tor-1-Konfidenz prüfen → "nächste Berater-Aussage" finden → grade_handling() in try/except:
- Erfolg + score 1-3 → handling_score_numeric=score, handling_status='scored'
- Erfolg + None (Abstention, Tor 2 D-07) → handling_score_numeric NULL, handling_status='abstained', abstain_log-INSERT
- Exception/dauerhaft nicht bewertbar (F-05 Poison-Pill) → handling_status='failed' (handling_score_numeric NULL), optional retry_count++ → blockiert den Merge NICHT
→ commit (vom Consumer/flush gesteuert).

## 4. Edge-Case-Analyse + Race-Condition-Audit (Punkt 14)
1. **Gleichzeitiges Feuern:** Mehrere Consumer? TAXO1 = 1 Consumer-Thread → keine parallele Schreibung auf dieselbe Zeile. Fast/Medium schreiben handling_score_numeric/handling_status NIE (Bau-Regel 1). → keine Race auf der Spalte. (F-06 Multi-Worker: erst Block M, dann FOR UPDATE SKIP LOCKED — jetzt nur vorbereitet.)
2. **Verbindungsabbruch mid-Operation:** Consumer-Crash vor commit → Zeile bleibt handling_status='pending' → bei Restart neu in Arbeitsliste (re-derivierbar via 'pending'). Kein halb-fertiger Zustand persistiert.
3. **Wiederverbinden mit altem Zustand:** Idempotenz — _persist_event_ref skippt Zeilen `WHERE handling_status != 'pending'` (F-01: scored/abstained/failed werden NICHT neu verarbeitet → KEIN doppelter abstain_log bei Consumer-Restart).
4. **Tab im Hintergrund:** n/a (Server-seitiger Daemon, kein Browser-Timer).
5. **Race-Beweis-Gate (Task 0, F-04 ORM-aware):** kein Live-Leser von intent_event → das In-Place-Update kann mit keiner Live-Lese-Query kollidieren.
6. **Poison-Pill (F-05):** dauerhaft scheiternde Einzelbewertung → 'failed', blockiert Merge nicht (Plan 04 zählt 'failed' nicht als offen). Call wird mit Marker "N Events nicht bewertbar" trotzdem benotet (D-09-not_gradable-Philosophie konsistent).
7. **DSGVO-Cascade-Bruch (F-08, REVIEWS):** wenn TAXO1s `intent_event.call_id` LOSE FK ist → Call-Löschung räumt intent_event NICHT → abstain_log-Wortlaut-Zeilen überleben → DSGVO-Orphan zurück. Mitigation: Task 0 verifiziert die Naht (inspect.sh); bei LOSE → INTERLOCK-Flag (TAXO1 ergänzt CASCADE additiv ODER Anonymizer räumt intent_event mit). Test (Task 3): End-to-End-Lösch-Assertion über BEIDE Tabellen.
