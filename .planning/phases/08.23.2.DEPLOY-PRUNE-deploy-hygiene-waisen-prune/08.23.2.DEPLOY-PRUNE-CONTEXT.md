## Phase Boundary

**Problem (live-verifiziert):** `deploy.sh:78-79` deployt via `tar -cf - ./ | ssh … tar -xf -`. tar-extract **mergt** — es löscht nie server-seitige Dateien, die nicht im tar sind. Im Repo gelöschte Dateien bleiben als toter Cruft in `/opt/nerve/app` liegen (AUTH-1: 2× Gate-D-Fehlalarm durch Ghost-Templates app/landing/onboarding.html, manuell per ssh rm bereinigt). Tote importierbare `.py`-Leichen sind gefährlicher als Templates.

**Ziel:** deploy.sh räumt im Repo gelöschte Code-Dateien AUCH server-seitig ab (Server == Repo für Code) — via **Manifest-Diff**, mit hartem Selbst-Aussperr- und Kundendaten-Schutz. Plus einmaliger Server-vs-Repo-Ghost-Abgleich.

**Rahmen:** NUR `deploy.sh` + neues `scripts/prune_orphans.sh` + ein Deploy-Gate-Guard-Test. **KEIN NERVE-App-Code-Change.**

**NICHT in Scope:** rsync (deploy.sh ist tar-basiert, Windows-Git-Bash, `deploy.sh:5`). `logs/` + `database/` werden strukturell NICHT angefasst (Kundendaten).

<decisions>
## Implementation Decisions (LOCKED — André 2026-07-07)

### D-01 — Prune-Mechanik: Manifest-Diff (Weg 1), scope-beschränkt
- Server vergleicht **git-Manifest** (was getrackt SEIN soll) gegen `find` im App-Verzeichnis → löscht Waisen, die nicht im Manifest UND nicht ausgeschlossen sind.
- **NUL-delimitiert durchgehend:** `git ls-files -z` vs `find … -print0` (Pfade mit Leerzeichen, z.B. `03 Planung/`).
- **Suchbereich = Include-Whitelist der Code-Verzeichnisse** (nicht das ganze App-Dir): `templates static routes services scripts tests alembic config tools nerve_rt docs` + Top-Level `*.py` (verifiziert: `app.py config.py extensions.py`). → `logs/` + `database/` liegen **strukturell außerhalb** des Prune-Scopes (Verteidigung in der Tiefe, zusätzlich zur Exclude-Liste).
- Alle 11 Whitelist-Dirs existieren + sind git-getrackt (live-verifiziert 2026-07-07).

### D-02 — Selbst-Aussperr-Schutz (Grauzone A): isolierte Funktion NACH Restart + Cap
- Prune = **separat testbare Funktion** in `scripts/prune_orphans.sh`, aufgerufen am **ENDE** von deploy.sh, **NACH** erfolgreichem `systemctl restart` + Status. Ein Prune-Bug kann so **nie** Deploy/Restart blockieren.
- **Fail-closed Cap:** bricht ab und löscht/quarantänt NICHTS, wenn Manifest leer ODER > **N=30** Kandidaten (übersteuerbar per `PRUNE_MAX`-Env).

### D-03 — Erst-Rollout: erzwungener Dry-Run
- Der **allererste** scharfe Prod-Lauf läuft hart als **Dry-Run** (nur Liste + Report, keine Bewegung). André verifiziert die Kandidaten manuell, DANN wird scharfgeschaltet (`PRUNE_APPLY=1`).

### D-04 — Quarantäne statt `rm`
- Kandidaten werden nicht gelöscht, sondern **verschoben**: `mv` nach `/opt/nerve/trash/<timestamp>/` (relativer Pfad erhalten). Nur die **letzten 2** Deploy-Quarantänen aufbewahren (ältere trash-Dirs entfernen). Reversibel bei Fehl-Prune.

### D-05 — Zweiter Guard: harter logs/database-Abbruch
- Zusätzlich zur strukturellen Scope-Beschränkung (D-01): **harter Abbruch** (exit, keine Bewegung), wenn IRGENDEIN Lösch-Kandidat mit `logs/` oder `database/` beginnt. Belt-and-suspenders gegen Kundendaten-Verlust.

### D-06 — Harte Exclude-Liste (gemeinsam)
- Zusätzlich zur Whitelist ausgeschlossen (nie Kandidat): alles was tar schon excluded — `__pycache__`, `*.pyc`, `*.db*`, `.env`, `logs/`, `database/*.db`. Der Manifest-Diff + Whitelist deckt das großteils schon strukturell ab; die Exclude-Liste ist der explizite fail-safe.

### D-07 — Wächter C: Deploy-Gate-Guard-Test
- Ein `tests/test_deploy_prune_*.py` läuft im bestehenden pytest-Gate mit (`deploy.sh:186-194`, `pytest tests/ -m "not live and not perf"`). Testet die Prune-**Logik** deterministisch (tmp-Fixture-Baum + Fake-Manifest, Dry-Run): korrekte Orphan-Erkennung, Whitelist/Exclude-Filter, Cap-Guard, logs/database-Hard-Abort. Test-Netz-Ratsche.

### Manifest-Transport
- Manifest wird **lokal** erzeugt (`git ls-files -z`, Server hat kein `.git` — tar-excluded `:52`) und **per scp** zum Server geschoben (Muster wie nginx/service-Dateien `deploy.sh:85-96`) → `scripts/prune_orphans.sh` liest es. Frisch pro Deploy, kein getracktes Waisen-Risiko.

## Claude's Discretion

## Bewusster Scope-Gap (dokumentiert)
- `database/*.py` (models.py, db.py) liegen NICHT in der Whitelist → deren Waisen werden NICHT auto-gepruned. Bewusster Safety-First-Tradeoff (D-01/D-05): `database/` bleibt tabu, weil dort die Kundendaten-`.db` wohnen. Seltener Fall, manueller Eingriff akzeptiert.
