## Ziel

Die Datenbank wechselt von SQLite auf Postgres (gleicher Hetzner-Server, Nürnberg). Alle 32
bestehenden Tabellen wandern 1:1. Die Tabellen `ft_call_sessions` und `ft_assistant_events`
werden ersatzlos gelöscht und durch neue Tabellen `calls` / `call_events` mit dem Schema aus
der Architektur-Konsolidierung (Sektion 1.2) ersetzt. Alle Code-Stellen die die alten Klassen
nutzen werden umgeschrieben.

## Hintergrund

- **Datenbank heute:** SQLite unter `sqlite:///database/nerve.db` (konfiguriert in `config.py:32`)
- **Kein Alembic heute:** Kein Migrations-Tool in `requirements.txt`, Schema-Änderungen laufen über
  manuelle `_migrate()`-Funktionen in `app.py`
- **34 Tabellen total:** Definiert in `database/models.py`. Davon sind 32 in 1:1-Migration.
- **FtCallSession** (`ft_call_sessions`): Integer-PK, `conversation_log_id`, `talk_ratio`, `hints_shown` etc.
  — komplett anderes Schema als das neue `calls`-Ziel-Schema. Enthält nur André's eigene
  Bau-Test-Anrufe, keine Kunden-Daten.
- **FtAssistantEvent** (`ft_assistant_events`): Integer-PK, `hint_type`, `context_window` etc.
  — komplett anderes Schema als das neue `call_events`-Ziel-Schema. Ebenfalls nur Test-Daten.
- **Direkte Imports ohne Service-Layer:** FtCallSession und FtAssistantEvent werden direkt
  importiert in 10 Dateien (keine Abstraktions-Schicht davor):
  - `database/models.py` (Definition)
  - `routes/app_routes.py` (liest FtCallSession via DB-Query)
  - `services/deepgram_service.py` (erstellt FtCallSession-Instanzen)
  - `services/claude_service.py` (erstellt FtAssistantEvent-Instanzen)
  - `scripts/export_ft_jsonl.py` (liest beide Modelle)
  - `tests/test_ab_stats.py`, `tests/test_ft_lifecycle.py`, `tests/test_ft_models.py`,
    `tests/test_ft_write_hooks.py`, `tests/test_per_sid_migration.py` (alle vier Test-Dateien)

**Was diese Phase NICHT ist:**
Die Architektur-Konsolidierung definiert 11 neue Tabellen. Diese Phase legt nur `calls` und
`call_events` davon an. Die restlichen 9 neuen Tabellen (`tenant_orgs`, `accounts`, `contacts`,
`account_memory`, `suggestions`, `suggestion_reactions`, `dpo_pairs`, `data_subject_requests`)

## Requirements

### 1. Engine-Migration: SQLite → Postgres (32 Tabellen 1:1)

Alle 32 bestehenden SQLAlchemy-Modelle (ohne FtCallSession, ohne FtAssistantEvent) werden
auf dem Hetzner-Server in Postgres angelegt und mit den bestehenden Daten aus SQLite befüllt.

- **Aktuell:** 34 Tabellen in SQLite; kein Postgres auf dem Server
- **Ziel:** Postgres läuft auf demselben Hetzner-Server; alle 32 Tabellen existieren mit
  identischer Struktur und identischer Datensatz-Anzahl wie in SQLite
- **Akzeptanz:** SELECT COUNT(*) für jede der 32 Tabellen in Postgres ergibt dieselbe Zahl
  wie in SQLite (automatisierter Vergleichs-Check im Migrations-Skript)

---

### 2. Neues calls-Schema (Rebuild statt Rename)

Die alte `ft_call_sessions`-Tabelle wird ersatzlos gelöscht. Eine neue `calls`-Tabelle mit dem
Schema aus der Architektur-Konsolidierung Sektion 1.2 wird angelegt. Die FK-Spalten
(`tenant_id`, `account_id`, `contact_id`) bleiben vorerst NULLABLE — Foreign-Key-Constraints
werden in Phase 08.23.2.F geschärft wenn die Ziel-Tabellen existieren. `user_id` bleibt
Integer-kompatibel mit dem aktuellen `users`-Schema (wird gemeinsam mit `users` in 08.23.2.F
auf UUID umgestellt).

- **Aktuell:** `ft_call_sessions` mit Integer-PK, `conversation_log_id`, `talk_ratio`,
  `hints_shown` etc. (kein UUID, keine `call_mode`-Spalte, kein JSONB)
- **Ziel:** `calls` mit UUID-PK, `tenant_id` (NULLABLE), `account_id` (NULLABLE),
  `contact_id` (NULLABLE), `user_id` (Integer, NOT NULL, FK→users), `call_mode` TEXT NOT NULL
  CHECK ('cold_call', 'meeting_consented'), `call_type`, `started_at`, `ended_at`,
  `duration_seconds` (generated), `transcript_storage`, `transcript_expires_at`, `call_summary`,
  `outcome`, `audio_health_score`, `coaching_score`, `meddpicc_extracted` (JSONB), `created_at`.
  Indizes aus Architektur-Konsolidierung Sektion 1.2 vorhanden.
- **Akzeptanz:** `SELECT * FROM calls LIMIT 0` gibt 0 Zeilen zurück (Tabelle leer, kein
  Migrationsfehler). `\d calls` in psql zeigt UUID-PK + alle Spalten aus Sektion 1.2.
  Schreib-Test: eine Call-Instanz wird programmiert gespeichert und wieder gelesen ohne Fehler.

---

### 3. Neues call_events-Schema (Rebuild statt Rename)

Die alte `ft_assistant_events`-Tabelle wird ersatzlos gelöscht. Eine neue `call_events`-Tabelle
mit dem Schema aus der Architektur-Konsolidierung Sektion 1.2 wird angelegt.

- **Aktuell:** `ft_assistant_events` mit Integer-PK, `ft_session_id` FK, `hint_type`,
  `context_window` (Text/JSON) etc.
- **Ziel:** `call_events` mit BIGSERIAL-PK, `call_id` (UUID, FK→calls ON DELETE CASCADE),
  `tenant_id` (NULLABLE vorerst), `event_type` TEXT NOT NULL CHECK ('transcript_chunk',
  'suggestion_shown', 'reaction', 'phase_change', 'audio_health', 'objection_detected',
  'consent_optin'), `event_ts_ms` BIGINT NOT NULL, `payload` JSONB NOT NULL, `created_at`.
  GIN-Index auf `payload` vorhanden.
- **Akzeptanz:** `\d call_events` zeigt BIGSERIAL-PK, UUID `call_id`, CHECK-Constraint auf
  `event_type`, GIN-Index auf `payload`. Schreib-Test: ein CallEvent-Eintrag mit
  `event_type='transcript_chunk'` wird gespeichert und gelesen ohne Fehler.

### 4. Code-Refactoring: Alte Klassen-Namen aus Code entfernen

Alle 10 Dateien die FtCallSession oder FtAssistantEvent referenzieren werden auf die neuen
Klassen-Namen umgestellt. Die neuen SQLAlchemy-Klassen heißen `Call` (Tabelle: `calls`) und
`CallEvent` (Tabelle: `call_events`) gemäß der PascalCase-Konvention des Projekts.

- **Aktuell:** `FtCallSession` und `FtAssistantEvent` referenziert in `routes/app_routes.py`,
  `services/deepgram_service.py`, `services/claude_service.py`, `scripts/export_ft_jsonl.py`,
  4 Test-Dateien, und `database/models.py`
- **Ziel:** `grep -rn "FtCallSession\|FtAssistantEvent" routes/ services/ scripts/ tests/`
  ergibt 0 Treffer. Code nutzt neue Klassen `Call` und `CallEvent`
- **Akzeptanz:** `grep -rn "FtCallSession\|FtAssistantEvent" routes/ services/ scripts/ tests/`
  liefert keine Ausgabe. Import-Fehler beim App-Start = 0.

### 5. Alembic-Setup: Migrations-Tool einrichten

Alembic wird neu eingerichtet. Die erste Migration erfasst den vollständigen Postgres-Schema-Stand
nach der Migration als Baseline-Snapshot. Alle zukünftigen Schema-Änderungen laufen über Alembic.

- **Aktuell:** Alembic nicht in `requirements.txt`. Schema-Änderungen über manuelle
  `_migrate()`-Funktionen in `app.py`
- **Ziel:** `alembic` und `psycopg2-binary` in `requirements.txt`. `alembic.ini` konfiguriert
  mit `DATABASE_URL` aus Umgebungsvariable. Verzeichnis `alembic/versions/` enthält eine
  Migrations-Datei `0001_initial_postgres_schema.py` als Baseline (autogenerate + review)
- **Akzeptanz:** `alembic current` zeigt die Baseline-Migration als aktuelle Version.
  `alembic upgrade head` läuft ohne Fehler (idempotent — Schema existiert bereits).

### 6. Daten-Validierungs-Skript (CLAUDE.md Punkt 13)

Ein Validierungs-Skript prüft vor und nach der Migration ob alle 32 Tabellen korrekt in Postgres
angekommen sind. Das ist der Pflicht-Check aus CLAUDE.md Punkt 13 (Schema-Real-Daten-Validierung).

- **Aktuell:** Kein Validierungs-Skript vorhanden
- **Ziel:** Skript `scripts/validate_postgres_migration.py` zählt für jede der 32 Tabellen
  die Datensätze in SQLite und in Postgres und vergleicht. Bei Abweichung: Abbruch mit Fehlermeldung.
  Führt außerdem Stichproben-Vergleich (5 Zeilen pro Tabelle) durch.
- **Akzeptanz:** Skript läuft nach Migration durch ohne Abbruch. Output: "32/32 Tabellen validiert,
  0 Abweichungen". Stichproben-Vergleich zeigt identische Daten in beiden Datenbanken.

### 7. Rollback-Vorbereitung: SQLite lokal sichern

Vor dem Production-Cutover wird die SQLite-Datei auf den lokalen Rechner gesichert. Sie bleibt
auf dem Server bis zur 14-tage-Stabilitäts-Bestätigung. Rollback-Zeit: unter 5 Minuten via
ENV-Wechsel.

- **Aktuell:** SQLite läuft live auf dem Server, kein lokales Backup
- **Ziel:** SQLite-Datei `nerve.db` per `scp` lokal gesichert VOR dem ersten Stopp der App.
  Die Datei bleibt auf dem Server bis nach 14-tage-Stabilität. Rollback-Prozedur dokumentiert:
  (1) `DATABASE_URL` in `.env` zurück auf sqlite-Pfad, (2) `systemctl restart nerve` — unter 5 Min.
- **Akzeptanz:** Lokale Kopie von `nerve.db` auf dem Laptop vorhanden mit korrektem Timestamp
  (vor Cutover). Auf dem Server existiert die Datei noch (nicht gelöscht).

### 8. Production-Cutover + Smoke-Test

Big-Bang-Cutover im Wartungsfenster (Sonntag 23:00). App läuft anschließend ausschließlich auf
Postgres. Drei kritische Funktionen werden im Smoke-Test verifiziert.

- **Aktuell:** App läuft auf SQLite
- **Ziel:** Nach Cutover läuft die App auf Postgres. Smoke-Test auf getnerve.app besteht:
  (a) Login mit bestehendem Account funktioniert, (b) Dashboard lädt ohne Fehler,
  (c) `/api/health`-Adresse antwortet HTTP 200 mit DB-Status `'ok'` (verifiziert Postgres-Verbindung)
- **Akzeptanz:**
  - `journalctl -u nerve | grep -i error` nach Cutover: keine kritischen Fehler
  - Login auf getnerve.app gelingt ohne 500-Fehler
  - Dashboard-Seite lädt vollständig (HTTP 200)
  - `/api/health` gibt HTTP 200 mit JSON-Feld `db_status='ok'`. Schreib-Verifikation in `calls`/`call_events` ist deferred bis Phase 08.23.2.D (wenn Outcome-Modal + Phasen-Klassifikator Schreib-Pfade aktivieren). Begründung: In Phase 08.23.2.A werden alle FtCallSession/FtAssistantEvent-Schreiber ersatzlos gelöscht (Discuss-Phase-Entscheidung), neue Schreib-Pfade kommen erst in 08.23.2.C/D/H. `calls` und `call_events` bleiben nach 08.23.2.A leer bis 08.23.2.D.

### 9. Postgres-Backup-Cronjob ab Tag 1

Ab dem ersten Tag nach dem Cutover läuft ein automatisches tägliches Backup von Postgres.
Die SQLite-Sicherung (Requirement 7) gilt nur am Cutover-Tag — danach veraltet sie täglich.
Ein laufender Cronjob schließt diesen blinden Fleck.

- **Aktuell:** Kein automatisches Postgres-Backup (Postgres ist noch nicht eingerichtet)
- **Ziel:** Tägliches `pg_dump` läuft via systemd-Timer oder cron. Ausgabe nach
  `/opt/nerve/backups/postgres-YYYY-MM-DD.sql`. Rolling-Retention: 30 Tage (ältere Sicherungen
  werden automatisch gelöscht). Der Cronjob hat mindestens einmal erfolgreich gelaufen und ein
  Wiederherstellungs-Test (pg_restore auf separate Test-DB, Zeilen-Anzahl stimmt) wurde einmal
  durchgespielt.
- **Akzeptanz:**
  - (a) `systemctl list-timers | grep nerve-backup` ODER `crontab -l` zeigt einen aktiven Eintrag
  - (b) Mindestens eine Datei unter `/opt/nerve/backups/postgres-YYYY-MM-DD.sql` mit aktuellem Datum
  - (c) Wiederherstellungs-Test einmal durchgespielt und Ergebnis dokumentiert: `pg_restore` auf
    Test-DB, `SELECT COUNT(*)` auf 5 zufälligen Tabellen stimmt mit Postgres-Original überein

### 10. Alt-Tabellen ft_call_sessions / ft_assistant_events existieren NICHT in Postgres

Die alten Tabellen dürfen in Postgres nicht existieren — weder als leere Hülle noch als
Geister-Tabelle. Der explizite Check verhindert dass das Migrations-Skript versehentlich beide
Welten parallel anlegt (calls + ft_call_sessions nebeneinander).

- **Aktuell:** `ft_call_sessions` (250 Einträge) und `ft_assistant_events` (556 Einträge)
  existieren in SQLite
- **Ziel:** Nach Migration existieren in Postgres weder `ft_call_sessions` noch
  `ft_assistant_events`. Nur `calls` und `call_events` mit dem neuen Schema sind vorhanden.
- **Akzeptanz:**
  - (a) `psql -c "\dt ft_call_sessions"` → "Did not find any relation named 'ft_call_sessions'"
  - (b) `psql -c "\dt ft_assistant_events"` → "Did not find any relation named 'ft_assistant_events'"
  - (c) `psql -c "\dt calls"` → zeigt Tabelle mit UUID-PK
  - (d) `psql -c "\dt call_events"` → zeigt Tabelle mit BIGSERIAL-PK

## Constraints

1. **Datenbank-Treiber:** `psycopg2-binary` — bewährt, stabil mit Flask + SQLAlchemy 2.0.
   Psycopg3 wird nicht verwendet (kein asyncio-Vorteil bei Flask-Synchron-Architektur).

2. **Cutover-Strategie:** Big-Bang Wartungsfenster Sonntag 23:00. Erwartete Dauer: 10-15 Minuten.
   Wartungsseite wird vor App-Stop hochgezogen.

3. **Rollback-Weg:** SQLite-Datei bleibt 14 Tage auf dem Server nach Cutover.
   Rollback-Zeit: < 5 Minuten via `DATABASE_URL` ENV-Wechsel + `systemctl restart nerve`.

4. **Idempotente Migration:** Alembic-Migrationen sind idempotent. Wenn Migration erneut läuft,
   gibt es keinen Fehler (CHECK ob Tabelle already exists).

5. **FK-Strategie:** `calls.tenant_id`, `calls.account_id`, `calls.contact_id` starten NULLABLE
   ohne FK-Constraint. FK-Constraints werden in 08.23.2.F geschärft. `calls.user_id` bleibt
   Integer kompatibel mit `users.id` bis UUID-Migration in 08.23.2.F.

6. **CLAUDE.md Punkt 13 (Schema-Real-Daten-Validierung):** Validierungs-Skript ist Pflicht
   VOR Plan-Approval. Das Skript muss alle bestehenden SQLite-Records gegen das neue Postgres-Schema
   prüfen und bestätigen bevor Plan approved wird.

7. **CLAUDE.md Punkt 11 (Fix-vs-Rebuild):** calls und call_events sind Rebuilds (kein Patch),
   da die Schemas komplett unterschiedlich sind. Die anderen 32 Tabellen sind 1:1-Migrations
   (kein Rebuild nötig).

8. **CLAUDE.md Punkt 10 (Migration-Vollständigkeit):** Das Daten-Migrations-Skript ist idempotent
   und prüft Datensatz-Anzahlen bevor es als erfolgreich gilt.
