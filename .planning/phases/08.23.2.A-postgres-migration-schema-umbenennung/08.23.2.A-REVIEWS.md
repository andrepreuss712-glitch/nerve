# Cross-AI Plan Review — Phase 08.23.2.A

## Gemini Review

### 1. Summary
The plan set provides a well-structured foundation for migrating NERVE from SQLite to PostgreSQL, thoroughly addressing the migration of 32 tables, circular foreign keys, and rollback procedures. However, critical contradictions across the plans—most notably the deletion of application write paths coupled with a cutover smoke test that expects them to function—make this plan set highly risky to execute as written. Targeted revisions to testing expectations, schema sequencing, and database permissions are required before proceeding.

### 2. Strengths
- **Robust Migration Strategy:** The two-pass update approach to handle circular FKs (`organisations.coach_id` and `users.active_profile_id`) is excellent and prevents deadlocks.
- **Validation & Safety:** `validate_postgres_migration.py` with explicit row-count and sample validation, plus `DRY_RUN` mode, significantly de-risks the data transfer.
- **Clear Rollback Path:** Maintaining SQLite on the server for 14 days with a simple ENV variable switch ensures a sub-5-minute rollback window.
- **Thorough Cleanup:** Surgically removing old FT tables, references, and tests ensures the codebase doesn't carry legacy baggage into the Postgres era.

### 3. Concerns

- **HIGH: Guaranteed Smoke Test Failure (Plans 03/04 vs Plan 09)**
  - *Issue:* Plans 03 and 04 delete all code paths writing to ft_call_sessions/ft_assistant_events but do NOT replace them with new writes to `calls`/`call_events` (scheduled for Phase 08.23.2.C/D). However, Plan 09 smoke test explicitly checks `SELECT COUNT(*) FROM calls > 0` and `SELECT COUNT(*) FROM call_events > 0` after a live test call.
  - *Impact:* The smoke test will fail. This would trigger an unnecessary rollback on Sunday night, or cause confusion about whether the cutover succeeded.

- **HIGH: Alembic Sequencing Ambiguity (Plan 06 vs Plan 09)**
  - *Issue:* It is unclear if Alembic autogenerates against an *empty* or *populated* Postgres DB. If dry-run data is populated before Alembic is initialized, Alembic will generate an empty migration file (seeing the schema as already matching). The verification step (`grep -c op.create_table` expects 34) will fail, and `upgrade head` during cutover won't create the schema.

- **MEDIUM: TRUNCATE Permissions (Plan 07)**
  - *Issue:* The dry-run cleanup instructs running a TRUNCATE command via a DO block as the `nerve_app` user. But `nerve_app` is only granted SELECT/INSERT/UPDATE/DELETE — no TRUNCATE right.
  - *Impact:* The dry-run cleanup step will throw "permission denied".

- **MEDIUM: Schema Data Type Discrepancy (Plan 01)**
  - *Issue:* SPEC requires `call_events.event_ts_ms` to be BIGINT. Plan 01 codes it as `Integer` in models.py.
  - *Impact:* Potential integer overflow. Unix timestamps in milliseconds require BIGINT (> 2^31 for dates beyond 2038).

- **LOW: .env Update Breaking Live App (Plan 07 vs Plan 09)**
  - *Issue:* Plan 07 instructs setting `DATABASE_URL=postgresql://...` in .env during the *setup* phase. If the production app dynamically reads this, it will attempt to connect to the empty Postgres DB before the Sunday cutover.

- **LOW: Backup Script Privileges & Dev Warnings (Plan 08)**
  - *Issue:* backup systemd unit runs as `postgres` superuser rather than a restricted backup user. Local dev environments will persistently show yellow dashboard warnings (backup dir `/opt/nerve/backups/postgres` doesn't exist locally). `PIPESTATUS[0]` in deploy.sh will fail if run with `/bin/sh` instead of `/bin/bash`.

### 4. Suggestions

1. **Revise Cutover Smoke Test (Plan 09):** Update the cutover runbook and REQ-8 Acceptance Criteria. Smoke test for this phase should only verify: app boots, connects to Postgres, can read existing users, no 500 errors on page loads. Defer `calls`/`call_events` write validations to Phase 08.23.2.C/D.

2. **Explicit Alembic Sequencing (Plans 06/09):** Update Plan 06 to strictly enforce that `alembic revision --autogenerate` is run against a completely **empty** Postgres DB to ensure correct DDL generation.

3. **Fix event_ts_ms Type (Plan 01):** Change `event_ts_ms = Column(Integer, ...)` to `Column(BigInteger, ...)` in the CallEvent model.

4. **Fix TRUNCATE Permissions (Plan 07):** Update runbook so dry-run TRUNCATE is executed as `postgres` superuser (not nerve_app).

5. **Relocate .env Instructions (Plan 07):** Move the `DATABASE_URL` change instruction out of the setup runbook and place it strictly within the cutover maintenance window (Plan 09 Step 7).

6. **QoL Improvements (Plan 08):**
   - Change `PIPESTATUS[0]` to standard POSIX `$?` in deploy.sh, or ensure shebang is `#!/bin/bash`.
   - Wrap backup directory check in `/api/health` with an environment check (e.g., only on production) to suppress the yellow warning in local dev.

### 5. Risk Assessment
**Overall Risk Level: HIGH**

**Justification:** While the migration scripts and database schemas are well thought out, executing these plans exactly as written will result in a failed deployment. The fundamental contradiction between deleting write paths (Plans 03/04) and mandating a smoke test that expects those write paths to exist (Plan 09 REQ-8) guarantees a perceived failure during the critical cutover window. The Alembic sequencing ambiguity threatens schema creation itself. Plans must be revised based on the suggestions above before execution is safe.
