**CRITICAL CONSTRAINT (C-2): Autogenerate MUST run against a completely EMPTY Postgres DB.**

If autogenerate runs against a DB that already has tables (e.g. from a prior dry-run in Plan 07 Section 9), Alembic sees the schema already matches models.py and generates an empty migration file. An empty migration file means `grep -c op.create_table` returns 0 instead of 34, and schema creation will fail at cutover.

**Step 0 — Enforce empty DB before autogenerate:**

Use the `nerve_test` DB (which starts empty) for autogenerate. This avoids polluting the production `nerve` DB and guarantees Alembic sees a schema-free DB:

```bash
# Confirm nerve_test DB has no tables:
sudo -u nerve_app psql -d nerve_test -c "SELECT COUNT(*) FROM pg_tables WHERE schemaname='public';"
# Expected: 0

# If nerve_test has leftover tables from earlier runs, drop and recreate:
sudo -u postgres psql -c "DROP DATABASE nerve_test;"
sudo -u postgres psql -c "CREATE DATABASE nerve_test WITH ENCODING 'UTF8' LC_COLLATE='de_DE.UTF-8' LC_CTYPE='de_DE.UTF-8' TEMPLATE template0;"
sudo -u postgres psql -d nerve_test -c "GRANT CONNECT ON DATABASE nerve_test TO nerve_test_user; GRANT USAGE ON SCHEMA public TO nerve_test_user;"
```

**DO NOT run autogenerate against the `nerve` DB if it already has tables** — this will produce an empty migration file.

**Step 1 — Run autogenerate against the empty nerve_test DB:**

```bash
DATABASE_URL=postgresql://nerve_test_user@/nerve_test \
alembic revision --autogenerate -m "initial_postgres_schema"
```

This generates a migration file under `alembic/versions/` with a UUID prefix. Rename it to `0001_initial_postgres_schema.py` for clarity:

```bash
# Find the generated file
ls alembic/versions/
# Rename (replace <hash> with actual generated hash prefix)
mv alembic/versions/<hash>_initial_postgres_schema.py alembic/versions/0001_initial_postgres_schema.py
```

Update the `Revision ID` and `down_revision` in the file header after renaming:
- `revision = '0001'`
- `down_revision = None` (this is the first migration, no parent)
- `branch_labels = None`
- `depends_on = None`

**Step 2 — Review the generated file for these common issues:**
1. SQLite-specific constructs (PRAGMA, etc.) — remove any
2. Missing CHECK constraints on `calls` and `call_events` — verify they appear in `op.create_table('calls', ...)` as `sa.CheckConstraint(...)`
3. GIN index on `call_events.payload` — verify `op.create_index('idx_call_events_payload_gin', 'call_events', ['payload'], postgresql_using='gin')` is present
4. Conditional index on calls `idx_calls_mode_outcome` with `postgresql_where` — verify it is present
5. Tables `ft_call_sessions` and `ft_assistant_events` — must NOT appear in the upgrade() function (they don't exist in models.py anymore)

If Alembic autogenerate MISSES the CHECK constraints (common if dialect-specific features aren't detected): add them manually to the generated migration's `upgrade()` function:

```python
# In upgrade():
op.execute("ALTER TABLE calls ADD CONSTRAINT ck_calls_call_mode CHECK (call_mode IN ('cold_call', 'meeting_consented'))")
op.execute("ALTER TABLE calls ADD CONSTRAINT ck_calls_transcript_storage CHECK (transcript_storage IN ('none', 'ephemeral', 'consented_full'))")
op.execute("ALTER TABLE calls ADD CONSTRAINT ck_calls_outcome CHECK (outcome IN ('meeting_booked', 'callback', 'no_interest', 'wrong_person', 'contract_signed', 'unknown') OR outcome IS NULL)")
op.execute("ALTER TABLE call_events ADD CONSTRAINT ck_call_events_event_type CHECK (event_type IN ('transcript_chunk', 'suggestion_shown', 'reaction', 'phase_change', 'audio_health', 'objection_detected', 'consent_optin'))")
```
