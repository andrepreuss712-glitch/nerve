## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] SQLite batch_alter_table Downgrade-Konflikt mit ORM-CHECK-Constraint**

- **Found during:** Task 1.1 Roundtrip-Test (alembic downgrade -1)
- **Issue:** `batch_alter_table` nutzt das ORM-Modell als Basis fuer die temporaere Tabelle. Da Task 1.2 `ck_calls_outcome_source` zum ORM hinzufuegt, versuchte der Downgrade eine temp-Tabelle MIT dem CHECK aber OHNE die `outcome_source`-Spalte zu erstellen -> `sqlite3.OperationalError: no such column: outcome_source`.
- **Fix:** Downgrade als Raw-SQL-Sequenz implementiert: `CREATE TABLE _calls_pre0005` (exakte DDL ohne outcome_source-Spalten), `INSERT SELECT` der Pre-0005-Spalten, `DROP TABLE calls`, `ALTER TABLE _calls_pre0005 RENAME TO calls`. Entspricht dem was batch_alter_table intern tut, aber ohne ORM-Modell-Interpolation.
- **Warum nicht Rule 4:** Kein Architektur-Wechsel -- gleiche CREATE+COPY+DROP-Semantik, nur manuell statt ueber batch_alter_table. SQLite-spezifisch; PostgreSQL-Migration (Phase F) wuerde native ALTER TABLE nutzen.
- **Files modified:** alembic/versions/0005_add_outcome_fields_to_calls.py
- **Commits:** f81e61c (initial), dann Write-Update in gleicher Task

**2. [Rule 1 - Bug] Alembic-Version-Tracking-Desync**

- **Found during:** Erste Migration-Ausfuehrung
- **Issue:** DB zeigte `alembic_version = 0005` obwohl die 4 Spalten fehlten -- erste `upgrade head` war kein-op weil version_num bereits 0005 war (aus vorherigem Session-State).
- **Fix:** `UPDATE alembic_version SET version_num = '0004'` via Python, dann sauberes `alembic upgrade head`. Ursache: Phase-Vorbereitung hatte Alembic-State gesetzt ohne tatsaechliche Migration.
- **Files modified:** DB-State (nicht code-relevant)
