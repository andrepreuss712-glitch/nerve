<decisions>
## Implementation Decisions

### D-01: Outcome-Classifier Service-Datei

- **D-01a:** Neues `services/outcome_service.py` — separate Datei, nicht in `coaching_service.py`. Begründung: saubere Trennung (coaching_service.py = Lernkarten, outcome_service.py = Outcome + Audio-Health). Folgt Phase-B-Pattern (anonymization.py als eigene Service-Datei).
- **D-01b:** `outcome_service.classify(conv_data) -> dict` gibt `{outcome, confidence}` zurück. Pure Logik-Funktion, kein Emit, kein DB-Write im Service.
- **D-01c:** `outcome_service.calculate_audio_health(word_confidences_buffer) -> dict` berechnet die 5 Metriken aus dem Word-Confidence-Buffer.

### D-02: Haiku-Classifier-Input

Strukturierte Felder aus ConversationLog + anonymisierte Top-3-Snippets:

**Strukturiert (immer verfügbar):**
- `dauer_sekunden` (Integer)
- `erreichte_phase` (Top-Phase: opener/pitch/einwand/closing — aus phasen_details)
- `einwaende_liste` (typ + intensitaet, strukturiert, max 10 Einträge)
- `ewb_clicks` (gedrückte EWB-Buttons + success-Flag)
- `kb_endwert` (Final KB-Score 0–100)

**Klartext-Snippets (anonymisiert):**
- Top-3 längere Aussagen vor Call-Ende aus log_entries, bereits anonymisiert via services/anonymization.py (läuft in Phase B vor DB-Insert).
- Snippet-Auswahl bei langen Calls (>15 Min): erste 30s + letzte 60s als wichtigste Marker.
- Snippets laufen durch `services/anonymization.py` vor Weiterleitung (auch wenn bereits anonymisiert in DB — Defense-in-depth).

**Edge-Cases — Plan-Phase muss abdecken:**
- Call <30s, keine Phase erreicht, keine Einwände → Classifier muss trotzdem laufen; bei unzureichenden Daten `outcome=NULL` mit `confidence=0` (kein Crash).
- CLAUDE.md Punkt 13: Summary-Schema gegen echte bestehende ConversationLog-Records validieren vor Plan-Phase.

**Token-Budget-Schätzung:** ~500–1000 Tokens pro Klassifikation (Haiku $0.0003/Call × 50 EA-User × 20 Calls/Tag ≈ $0.30/Tag).

### D-03: Post-Call-Flow-Koordination

**Korrigierter Flow (SPEC-Drift behoben — run_postcall_engine() ist SQL-only, keine Claude-Calls):**

```
api_beenden():
  1. ConvLog-INSERT (wie heute)
  2. calls-INSERT mit conversation_log_id FK (outcome/health NULL)
  3. Background-Thread für Audio-Health-Berechnung starten
  4. run_postcall_engine() für SQL-Pattern-Erkennung (wie heute, SQL-only)
  5. Return {ok, conv_id, postcall}

Frontend ruft /api/postcall_analysis (wie heute):
  generate_postcall_analysis() in coaching_service.py:
    - Sonnet-Call für Lernkarten (wie heute)
    - outcome_service.classify() für Outcome (Haiku, NEU)
    - UPDATE calls.outcome + outcome_confidence + outcome_source
    - Emit SocketIO 'outcome_ready' {outcome, confidence, source, call_id}

Audio-Health-Thread (parallel zu postcall_analysis):
  - outcome_service.calculate_audio_health(word_confidences_buffer)
  - UPDATE calls.audio_health_score
  - INSERT CallEvent(event_type='audio_health', payload={5 Metriken})
```

**Wichtig:** `run_postcall_engine()` macht KEINE Claude-Calls — reine SQL-Aggregation. Claude-Calls nur in `generate_postcall_analysis()` via `/api/postcall_analysis`.

**Race-Conditions (CLAUDE.md Punkt 14 Schicht 4):**
- Schreib-Pfade auf calls-Row separiert: Outcome-Block (outcome, outcome_confidence, outcome_source) vs. Audio-Block (audio_health_score) — kein Spalten-Konflikt.
- `/api/postcall_analysis` darf erst laufen NACHDEM calls-INSERT durch ist — durch Sequenz in api_beenden garantiert.
- Frontend ruft `/api/postcall_analysis` nie → outcome bleibt NULL → Dashboard-Reminder zeigt "unbestätigter Call" → User kann später korrigieren.
- Audio-Health-Thread crasht → audio_health_score bleibt NULL → Phase-E-DPO-Gate filtert diesen Call raus (war ohnehin Pflicht-Gate).

### D-04: Emit-Ort für 'outcome_ready'

- **D-04a:** Emit aus Route (nicht aus Service). `outcome_service.classify()` gibt nur `{outcome, confidence}` zurück. Route (`/api/postcall_analysis` in `coaching_service.py` oder aufrufende Route in `routes/learning.py`) macht: UPDATE calls + `emit('outcome_ready', ...)`
- **D-04b:** Event-Payload: `{outcome, confidence, source, call_id}`
- **D-04c:** Subscribers: `pip-launcher.js` + `dashboard.js` (für Live-Yellow-Dot-Update wenn User auf Dashboard während Call endet)
- **D-04e:** Plan-Phase Pflicht: Fallback-Pull-Endpoint (`/api/calls/latest_outcome` oder ähnlich) für Reconnect-Case wenn SocketIO-Connection zwischen Call-Ende und `outcome_ready` abreißt.

### D-05: calls-INSERT Feld-Quellen

- **D-05a:** `call_mode` aus `req_data.get('session_mode', 'meeting')` in `api_beenden` Z.42 — **NICHT** aus Session-State. SPEC-Drift-Korrektur: SPEC.md Z.28 sagt "aus Session-State", aber kein `ls.state.get('current_mode')` existiert (grep-verifiziert). Code-Realität ist req_data.
- **D-05b:** `conversation_log_id`: Integer-FK. Plan-Phase prüft D-04-Pattern aus Phase A (nullable=True Konvention für ALLE NERVE-FKs oder nur für unsichere Pfade). Wenn Pattern-Konsistenz → nullable=True; wenn saubere Architektur erlaubt → nullable=False (Sequenz garantiert ConvLog-Save vor calls-INSERT per SPEC Constraint).
- **D-05c:** `contact_category` (Gatekeeper-Modus) wird NICHT in `calls.call_mode` gespeichert — mode_switch-Events gehen in call_events (bereits Migration 0004 aus Phase C.R).

### D-06: Word-Confidence-Buffer

- **D-06a:** Storage: `ls._session_state[sid]['word_confidences']` = Liste von `(ts_ms: int, confidence: float)` Tuples.
- **D-06b:** Schreib-Pfad: `_make_on_message()` in `deepgram_service.py` bei `is_final=True` — für jedes Wort in `result.channel.alternatives[0].words` ein Tuple `(int(time.time() * 1000), w.confidence)` anhängen.
- **D-06c:** Rolling-10s-Score (Live-Warnung):
  ```python
  def rolling_10s_score(buffer, now_ms):
      cutoff = now_ms - 10_000
      recent = [c for ts, c in buffer if ts >= cutoff]
      return statistics.mean(recent) if recent else 1.0
  ```
- **D-06d:** PostCall-Score: `api_beenden` liest komplette Liste vor `reset_session()`. Hintergrund-Thread berechnet 5 Metriken.
- **D-06e:** Cleanup: `reset_session()` + `pop_session_state(sid)` bei Reconnect löschen `word_confidences` automatisch mit (kein Sonderfall nötig).
- **D-06f:** Memory: ~60KB bei 60-Min-Call — vernachlässigbar. Optimierung deferred.

### D-07: Dashboard-UX (Brand-konform)

- **D-07a:** Reminder als Stripe-Pattern (analog bestehende DSGVO/Backup-Warning-Stripes). Plan-Phase nutzt existing Stripe-CSS-Klassen/Token.
- **D-07b:** Inline-Korrektur als 5-Button-Auswahl im Calls-Listen-Row (kein Vollbild-Modal). Analog EWB-Quick-Action-Pattern.

KEIN neuer Hex-Wert ohne Brand-Cross-Check.
- **D-07d:** Reminder-Stripe-Farbe: vermutlich existing Warning-Stripe-Token wiederverwenden (Plan-Phase prüft nerve.css).

### D-08: outcome_note Render-Ort
