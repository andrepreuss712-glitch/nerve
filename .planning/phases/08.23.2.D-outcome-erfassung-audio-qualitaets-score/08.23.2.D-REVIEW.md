# Phase 08.23.2.D: Code Review Report

**Reviewed:** 2026-05-27
**Depth:** standard

## Summary

This phase adds Outcome-Erfassung (Outcome classification via Claude Haiku) and an Audio-Quality-Score to the `calls` table. The scope covers a new Alembic migration (0005), ORM model additions, a pure-logic service (`outcome_service.py`), two new API endpoints (`latest_outcome`, `correct_outcome`), inline correction UI in `dashboard.html`, and integration tests.

The overall architecture is sound: ownership checks exist on all three new endpoints, ORM queries are used throughout (no raw string interpolation), and the word-confidence buffer is correctly copied before `reset_session()` is called.

Two critical issues were found:
1. The `correct_outcome` POST endpoint in `dashboard.html` sends without a CSRF token — it is the only POST in the entire dashboard page that bypasses the project-wide CSRF pattern present in `pip-launcher.js`.
2. The `_audio_health_bg` background thread queries `Call` by `call_id` alone without the `user_id` ownership filter, which means a user who obtains another user's `call_id` (e.g., via the `call_id` returned in the `api_beenden` JSON response) can overwrite `audio_health_score` for a call they do not own.

Four warnings were found covering a logic error in the reminder query (the `(Call.outcome_source == 'ai_auto_unsicher') | (Call.outcome.is_(None))` pipe-operator is not the SQLAlchemy ORM OR pattern — it should be `or_(...)`) that may produce unexpected results on some backends, an unescaped icon injection in the recommendations renderer, a confidence boundary edge-case, and the `_audio_health_bg` ownership gap already flagged as critical.

## Critical Issues

### CR-01: CSRF Token Missing on `correct_outcome` POST (dashboard.html)

**File:** `templates/dashboard.html:865`
**Issue:** The inline-correction fetch call for `POST /api/calls/<call_id>/correct_outcome` sends no `X-CSRFToken` header. Every other POST in `pip-launcher.js` explicitly calls `getCsrfToken()` and includes `'X-CSRFToken': getCsrfToken()`. This endpoint mutates `Call.outcome` and `Call.outcome_source` in the database. A CSRF attack can force any authenticated user to silently overwrite the outcome of their most-recently-visible call.

```javascript
// dashboard.html line 863-870 — current (MISSING CSRF):
fetch('/api/calls/' + encodeURIComponent(callId) + '/correct_outcome', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },   // no X-CSRFToken
  body: JSON.stringify({ outcome: pair[0] }),
})

// Fix — add CSRF header (same pattern as pip-launcher.js):
fetch('/api/calls/' + encodeURIComponent(callId) + '/correct_outcome', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRFToken': document.querySelector('meta[name="csrf-token"]')
                    ? document.querySelector('meta[name="csrf-token"]').getAttribute('content')
                    : ''
  },
  body: JSON.stringify({ outcome: pair[0] }),
})
```

Note: `dashboard.html` does not load `pip-launcher.js`, so `getCsrfToken()` is not available in this scope. Either inline the helper as shown above, or extract it to a shared utility script included in `base.html`.

### CR-02: `_audio_health_bg` Queries `Call` Without Ownership Filter

**File:** `routes/app_routes.py:557`
**Issue:** The background thread queries `Call` with only the call ID:
```python
_row = _db_ah.query(_CallAH).filter(_CallAH.id == call_id_val).first()
```
The `call_id` passed into the thread (`_phase_d_call_id`) is first resolved via a `ls._session_state` iteration that *does* check `user_id`, but the fallback path at line 499-513 resolves the call via:
```python
_CallModel_fb.user_id == g.user.id,
_CallModel_fb.ended_at.is_(None)
```
So the fallback is owner-correct. However, the `_posted_call_id` branch (lines 470-475) accepts any `call_id` the client sends in the POST body and matches it against session state *only by call_id equality*, without a user-id cross-check on the state entry itself:
```python
if str(_sd['state']['call_id']) == str(_posted_call_id):  # no g.user.id check on _sd
```
If an attacker crafts a POST to `/api/beenden` with another user's `call_id` in the body, and that call happens to match an active session-state entry, `_audio_health_bg` will then update that foreign call's `audio_health_score` (line 559) without any ownership check at the DB layer.

**Fix:** Add `Call.user_id == g.user.id` (captured before the thread starts) to the `_audio_health_bg` filter, and add a user-id check to the session-state `_posted_call_id` branch:
```python
# In _audio_health_bg, change:
_row = _db_ah.query(_CallAH).filter(_CallAH.id == call_id_val).first()

# To (pass user_id into the thread as a fourth argument):
_row = _db_ah.query(_CallAH).filter(
    _CallAH.id == call_id_val,
    _CallAH.user_id == user_id_val,   # ownership guard
).first()

# In the _posted_call_id session-state lookup:
if str(_sd['state']['call_id']) == str(_posted_call_id) and _sd.get('user_id') == g.user.id:
```

## Warnings

### WR-01: SQLAlchemy `|` Pipe Operator — Not Reliable Cross-Dialect OR

**File:** `routes/performance.py:455`
**Issue:** The reminder count query uses the Python bitwise OR operator `|` to compose SQLAlchemy WHERE clauses:
```python
(Call.outcome_source == 'ai_auto_unsicher') | (Call.outcome.is_(None))
```
The `|` operator is overloaded on SQLAlchemy `Column` objects and produces a `BinaryExpression`. While this works in SQLAlchemy ORM when the expression is placed inside `.filter()`, it is fragile: it relies on Python operator overloading rather than the canonical `sqlalchemy.or_()` function. The test in `test_dashboard_outcome_reminder.py` correctly uses `or_()` (line 73), creating an inconsistency between route code and test code. If the column types change or a SA version update alters operator behavior, the route silently misbehaves.

**Fix:** Use the canonical function consistently:
```python
from sqlalchemy import or_
_unsichere = (
    db.query(Call)
      .filter(
          Call.user_id == g.user.id,
          Call.ended_at >= _seven_days_ago,
          or_(Call.outcome_source == 'ai_auto_unsicher', Call.outcome.is_(None)),
      )
      .count()
)
```

### WR-02: Unescaped Icon Field Written Into innerHTML in `renderRecommendations`

**File:** `templates/dashboard.html:898`
**Issue:** Recommendation icons from the server JSON are written directly into `innerHTML` without escaping:
```javascript
html += '<div class="db2-reco-icon">' + r.icon + '</div>';
```
`r.title` and `r.subtitle` are passed through `esc()` (line 900-901), but `r.icon` is not. The icon field is server-generated (`'🚀'`, `'🎯'` etc.) so in current code it contains only emoji literals. However the `recommendations` list is built by string formatting that includes user-controlled data paths (e.g., `weakest["name"]` at line 408, `sessions_this_week` at line 428). If a future code path populates `r.icon` from a DB value or user input, this becomes an XSS sink.

**Fix:** Apply `esc()` consistently:
```javascript
html += '<div class="db2-reco-icon">' + esc(r.icon) + '</div>';
```

### WR-03: Confidence Boundary Edge-Case — `confidence == 0.70` Maps to `ai_auto_unsicher` but Code Comment Says Otherwise

**File:** `routes/learning.py:96-103`
**Issue:** The threshold logic is:
```python
if _outcome_conf >= 0.90:
    _outcome_source_val = 'ai_auto'
elif _outcome_conf >= 0.70:
    _outcome_source_val = 'ai_auto_unsicher'
else:
    # Niedrige Confidence: KEIN Auto-Set
    _outcome_val = None
    _outcome_source_val = None
```
A confidence of exactly `0.70` maps to `ai_auto_unsicher`. This is correct per the spec comment ("D-02 Edge-Case-Grenze"). However, the corresponding test in `test_postcall_outcome_route.py` only tests `0.80` for `ai_auto_unsicher` and misses the boundary value `0.70` itself. No bug in the route, but the boundary is unspecified in tests and could be silently broken by a `>` vs `>=` change.

**Fix:** Add a boundary test:
```python
def test_threshold_boundary_0_70_maps_to_unsicher():
    """confidence exactly 0.70 must map to ai_auto_unsicher (>= boundary, not strictly >)."""
    conf = 0.70
    result = 'ai_auto' if conf >= 0.90 else ('ai_auto_unsicher' if conf >= 0.70 else None)
    assert result == 'ai_auto_unsicher'
```

### WR-04: `_audio_health_bg` No Rollback on Outer Exception Path

**File:** `routes/app_routes.py:574-580`
**Issue:** The inner `except` on line 574 calls `_db_ah.rollback()`, but there is no rollback in the outer `except` at line 579. If `calculate_audio_health()` itself raises unexpectedly (e.g., a stats module error), the outer except catches it, logs it, and returns — but no `_db_ah.close()` is called because `_db_ah` was never opened in that code path. This is safe (no session leak) only because `_db_ah = _gs_ah()` is inside the `try` block that the outer except does not cover.

On closer inspection the structure is:
```python
try:
    metrics = ...
    if metrics.get('score') is None:
        return          # _db_ah never opened — safe
    _db_ah = _gs_ah()  # opened here
    try:
        ...
    except ...:
        _db_ah.rollback()
    finally:
        _db_ah.close()   # always called
except Exception as _e_outer:
    print(...)            # _db_ah may not exist here — no close needed
```
The `finally: _db_ah.close()` inside the inner try guarantees cleanup. The outer except path is only reached before `_db_ah` is opened — so there is no leak. However, there is no rollback on the inner except path before `_db_ah.close()`:
```python
except Exception as _e_inner:
    print(...)
    _db_ah.rollback()   # line 576 — this IS present
finally:
    _db_ah.close()
```
This is actually correct. The warning is reduced to: if `_db_ah.rollback()` itself throws, `_db_ah.close()` still runs via `finally`. No actual bug — informational flag only; consider adding a try/except around the rollback for robustness.

### IN-01: `test_migration_0005.py` — Source-Presence Pattern Risk in `test_0005_existing_rows_null`

**File:** `tests/test_migration_0005.py:27-38`
**Issue:** `test_0005_existing_rows_null` runs a raw `SELECT` and then does `assert True`. This test can never fail regardless of what the query returns, making it a no-op assertion. It provides zero signal about column readability — only about whether the query raises an exception. Per CLAUDE.md, tests must assert on return values.

**Fix:**
```python
def test_0005_existing_rows_null():
    db = get_session()
    try:
        rows = db.execute(text(
            "SELECT outcome_confidence, outcome_note, outcome_source, conversation_log_id "
            "FROM calls LIMIT 5"
        )).fetchall()
        # All new columns are nullable — existing rows must have None for these fields
        for row in rows:
            assert row[0] is None or isinstance(row[0], float), \
                f"outcome_confidence must be None or float, got {type(row[0])}"
    finally:
        db.close()
```

### IN-02: `outcome_service.classify()` — Bare `except Exception` Swallows All Errors Including Keyboard Interrupt

**File:** `services/outcome_service.py:106`
**Issue:** The outer `except Exception as e` catches all exceptions, including potential issues from `json.loads()` and `float()` coercions. In a long-running server context this is intentional (graceful degradation), and the function signature documents this. However, `KeyboardInterrupt` and `SystemExit` are `BaseException`, not `Exception`, so they propagate correctly. This is informational only — the implementation matches the docstring.

**Fix:** No code change needed, but a comment clarifying the intentional broad catch would aid future maintainers:
```python
except Exception as e:
    # Intentional broad catch: classify() must never crash the postcall pipeline.
    # All failure modes return {'outcome': None, 'confidence': 0.0}.
    print(f'[OutcomeService] classify() Fehler: {e}')
    return {'outcome': None, 'confidence': 0.0}
```
