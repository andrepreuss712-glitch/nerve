## Haiku-Classifier-Integration

### Q1: Wo lebt der neue Outcome-Classifier-Code?

| Option | Description | Selected |
|--------|-------------|----------|
| Eigene services/outcome_service.py | Saubere Trennung, coaching_service.py bleibt Lernkarten-only. Folgt Phase-B-Pattern (anonymization.py) | ✓ |

**User's choice:** Eigene services/outcome_service.py

---

### Q2: Was bekommt der Haiku-Outcome-Classifier als Input?

| Option | Description | Selected |
|--------|-------------|----------|
| Anonymisiertes Transkript-Summary + Metadaten | Strukturierte Felder + Top-3 anonymisierte Snippets | ✓ |
| Rohe Einwands-Liste + KB-Verlauf only | Nur strukturiert, keine Gesprächs-Dynamik | |
| Vollständige log_entries | Maximum Kontext, hohes Token-Budget bei langen Calls | |

**User's choice:** Option 1 mit konkretem Schema-Vorschlag (via "Other"):
- Strukturierte Felder: dauer_sekunden, erreichte_phase, einwaende_liste, ewb_clicks, kb_endwert
- Top-3 anonymisierte Snippets (erste 30s + letzte 60s bei langen Calls)
- Token-Budget: ~500–1000 Tokens/Call, Haiku ~$0.30/Tag bei 50 EA-User
- Edge-Cases: Call <30s → outcome=NULL mit confidence=0; Calls >15 Min → intelligente Snippet-Auswahl

---

### Q3: Wann läuft der Haiku-Classifier im Post-Call-Flow?

| Option | Description | Selected |
|--------|-------------|----------|
| In run_postcall_engine() nach Sonnet-Call | Sequenziell im Background-Thread | |
| Eigener paralleler Background-Thread | Schneller, aber potenzielle Race Conditions | |
| Als separater /api/postcall_analysis Endpoint | Frontend-getriggert, mehr FE-Komplexität | |

**User's choice:** Korrektur via "Other" — run_postcall_engine() ist SQL-only (keine Claude-Calls). Korrekter koordinierter Flow:
1. api_beenden: ConvLog-INSERT → calls-INSERT → Audio-Health-Thread → run_postcall_engine() → Return
2. Frontend ruft /api/postcall_analysis
3. coaching_service.py: Sonnet (Lernkarten) → outcome_service.classify() (Haiku) → UPDATE calls → emit 'outcome_ready'
4. Audio-Health-Thread parallel: 5-Metriken-Berechnung → UPDATE calls.audio_health_score + CallEvent

## Audio-Health-Buffer

### Q6: Word-Confidence-Speicherung

| Option | Description | Selected |
|--------|-------------|----------|
| ls._session_state[sid]['word_confidences'] (Empfohlen) | Liste von (ts_ms, confidence) Tuples, zentrales State-Management | ✓ |
| In CallEvent-Payload per transcript_chunk | Persistiert, aber Extra-DB-Writes ohne Vorteil | |
| Eigener Deque-Buffer in deepgram_service | Dezentral, State-Cleanup muss separat verwaltet werden | |

**User's choice:** Option 1 mit Schema-Präzisierung (via "Other"):
- `[(ts_ms: int, confidence: float), ...]` — Tuple spart Memory
- Schreib-Pfad: _make_on_message() bei is_final=True für jedes w in words
- Rolling-10s: `statistics.mean([c for ts, c in buffer if ts >= now_ms - 10_000])`
- Cleanup: reset_session() + pop_session_state(sid) — automatisch, kein Sonderfall
