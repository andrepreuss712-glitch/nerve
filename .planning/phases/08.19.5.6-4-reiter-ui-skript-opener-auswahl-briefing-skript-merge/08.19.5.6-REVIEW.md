## Summary

This phase added a 4-tab UI (`renderStep5`) to `pip-launcher.js` for Opener / Erlaubnisfrage / Pitch / Skript selection and updated the backend personalization endpoints (`api_personalize_skript`, `api_personalize_skript_save`) to support `call_mode` routing. `ProfileSkript` received 3 new columns (`parent_id`, `is_personalized`, `briefing_source_firma`) with a matching `_migrate()` block.

The logic is mostly sound. One critical bug was found: the `type` field is missing from the opener-items JSON returned by both API endpoints, which causes the 4-tab filter logic in the frontend to silently show empty tabs for every profile. Three warnings address a missing CSRF token on a profile-change fetch, silent cap-modal call without null-check, and inconsistent inline-edit wiring for Erlaubnisfrage/Pitch tabs. Three info items cover minor quality points.

## Critical Issues

### CR-01: `type` field missing from opener-items API responses — all 4-tab filters silently empty

**File:** `routes/app_routes.py:840-850` and `routes/app_routes.py:884-894`

**Issue:** Both `api_launcher_init` and `api_launcher_profile` serialize `ProfileOpener` rows without including the `type` column. The frontend in `renderStep5` filters `state.openerItems` by `o.type === 'opener'`, `o.type === 'erlaubnis'`, `o.type === 'pitch'`. Because every item has `type: undefined`, all three filters return empty arrays, so all three tabs show "Noch kein X hinterlegt" regardless of the actual data. The Opener-Tab, Erlaubnisfrage-Tab and Pitch-Tab are all broken for any profile that actually has these items.

**Fix:**

```python
# In api_launcher_init (line ~840) and api_launcher_profile (line ~884):
opener_items = [
    {
        'id': o.id,
        'name': o.name,
        'inhalt': o.inhalt or '',
        'type': o.type or 'opener',          # ← ADD THIS FIELD
        'is_personalized': bool(o.is_personalized),
        'briefing_source_firma': o.briefing_source_firma or '',
    }
    for o in db.query(ProfileOpener).filter_by(profile_id=active_profile_id)
    .order_by(ProfileOpener.sortierung, ProfileOpener.id).all()
]
```

Apply the same fix in both `api_launcher_init` (line ~840) and `api_launcher_profile` (line ~884).

## Warnings

### WR-01: Profile-change fetch in `renderStep5` has no CSRF token

**File:** `static/pip-launcher.js:966`

**Issue:** The profile-change `fetch('/api/launcher/profile/' + pid)` call uses a GET request and sends no `X-CSRFToken` header. GET requests are not mutating, so CSRF is not a concern here — but the fetch also lacks error handling for non-200 responses. The `.catch(function () {})` swallows the error silently. If the server returns a 404 (profile not found or org-mismatch), the UI silently fails without resetting — leaving stale opener/skript data from the previous profile in `state.openerItems` and `state.skripte` while the display shows the new profile name.

**Fix:**
```javascript
profileSel5.onchange = function () {
  var pid = parseInt(profileSel5.value);
  if (!pid) return;
  fetch('/api/launcher/profile/' + pid, {
    headers: { 'X-CSRFToken': getCsrfToken() }
  })
    .then(function (r) {
      if (!r.ok) throw new Error('profile load failed: ' + r.status);
      return r.json();
    })
    .then(function (data) {
      state.activeProfileId     = data.id;
      state.profileDaten        = data.daten || {};
      state.skripte             = data.skripte || [];
      state.openerItems         = data.opener || [];
      state.selectedSkriptId    = null;
      state.selectedOpenerId    = null;
      state.selectedErlaubnisId = null;
      state.selectedPitchId     = null;
      state.activeTab           = null;
      renderStep5();
    })
    .catch(function (err) {
      console.warn('[Launcher] Profile load failed:', err);
      // Optionally show an error in the UI
    });
};
```

### WR-02: `_showCapSubModal` second save call does not null-check `_personalizedSkriptText` before `startCall`

**File:** `static/pip-launcher.js:776-784`

**Issue:** In the cap sub-modal delete+save path, after a successful save the code sets `state._editedOpenerText = state._personalizedSkriptText || ""` and then calls `_collectEditedTexts(); startCall(true)`. There is no check for `data.cap_exceeded` in this second response path (the delete-ids path). If the server somehow returns `cap_exceeded: true` again (e.g., race condition where another tab created a new item between the first cap-check and the delete+insert), the code falls through to `startCall(true)` without aborting. The cap-exceeded UI disappears and the call starts with the un-saved personalized text loaded into `_editedOpenerText`.

**Fix:**
```javascript
.then(function (data) {
  if (data && data.cap_exceeded) {
    // Race: re-show cap modal with fresh list
    _showCapSubModal(data.items || []);
    if (delBtn) { delBtn.disabled = false; delBtn.textContent = 'Auswahl löschen + Personalisieren →'; }
    return;
  }
  if (data && data.error) { /* ... existing error handling ... */ return; }
  // proceed to startCall
  if (state.mode === 'meeting') {
    state._editedSkriptText = state._personalizedSkriptText || "";
  } else {
    state._editedOpenerText = state._personalizedSkriptText || "";
  }
  state._personalizedSkriptText = null;
  _collectEditedTexts();
  startCall(true);
})
```

### WR-03: Inline-edit wiring always uses `'opener'` type for Erlaubnisfrage and Pitch tabs

**File:** `static/pip-launcher.js:1022-1027`

**Issue:** After rendering the tab content, `_wireInlineEdit` is called with either `'skript'` or `'opener'` as the type parameter:
```javascript
if (state.activeTab === 'skript') {
  _wireInlineEdit('lnr-skript-edit-btn', 'lnr-skript-preview', 'lnr-skript-textarea', 'skript');
} else {
  _wireInlineEdit('lnr-opener-edit-btn', 'lnr-opener-preview', 'lnr-opener-textarea', 'opener');
}
```
When the active tab is `'erlaubnis'` or `'pitch'`, the wiring uses type `'opener'`. Inside `_wireInlineEdit`, the "save to profile" path calls `_showSaveToProfileDialog(type, itemId, newText)` which constructs the endpoint as `/profiles/{id}/opener/{itemId}` for both Erlaubnisfrage and Pitch tabs. If Erlaubnisfrage/Pitch items are stored under a different endpoint path (e.g., `/profiles/{id}/opener/{itemId}` is generic for all `ProfileOpener` items), this may work correctly — but the intent is ambiguous. More importantly, `_wireInlineEdit` reads `itemId` as `state.selectedOpenerId` when `type !== 'skript'`, but for the Erlaubnisfrage tab the correct state variable is `state.selectedErlaubnisId` and for Pitch it is `state.selectedPitchId`. This means the "Bearbeiten" / "Im Profil speichern" path will PUT to the wrong item ID when a user edits in the Erlaubnisfrage or Pitch tab while `state.selectedOpenerId` differs from `state.selectedErlaubnisId` / `state.selectedPitchId`.

**Fix:** Pass the correct `itemId` from the calling context rather than deriving it inside `_wireInlineEdit`:
```javascript
if (state.activeTab === 'skript') {
  _wireInlineEdit('lnr-skript-edit-btn', 'lnr-skript-preview', 'lnr-skript-textarea', 'skript');
} else if (state.activeTab === 'erlaubnis') {
  _wireInlineEdit('lnr-opener-edit-btn', 'lnr-opener-preview', 'lnr-opener-textarea', 'opener', state.selectedErlaubnisId);
} else if (state.activeTab === 'pitch') {
  _wireInlineEdit('lnr-opener-edit-btn', 'lnr-opener-preview', 'lnr-opener-textarea', 'opener', state.selectedPitchId);
} else {
  _wireInlineEdit('lnr-opener-edit-btn', 'lnr-opener-preview', 'lnr-opener-textarea', 'opener', state.selectedOpenerId);
}
```
And update `_wireInlineEdit` to accept an optional `overrideItemId` parameter.

### IN-01: `_migrate()` for `profile_skripte` inconsistently handles duplicate-column errors vs. `profile_opener` migration

**File:** `app.py:417-431`

**Issue:** The `profile_opener` migration block (lines 405-416) uses a bare `except Exception: pass` to swallow all errors. The `profile_skripte` migration block (lines 417-431) is more precise: it only swallows `duplicate column name` errors and re-raises others. This is the correct and safer pattern. No action required on the `profile_skripte` block — but the `profile_opener` block (from Phase 08.20.3) should be updated to match for consistency and to expose unexpected migration failures.

**Fix:** Update the `profile_opener` migration block from `except Exception: pass` to:
```python
except Exception as e:
    if 'duplicate column name' in str(e).lower():
        pass
    else:
        raise
```

### IN-02: `renderStep4b` personalizes only `selectedOpenerId` for cold-call mode, even if user lands on Skript tab

**File:** `static/pip-launcher.js:553-555`

**Issue:** When `state.mode` is `'cold_call'` (or falsy), `renderStep4b` sends `opener_id: state.selectedOpenerId` to the backend. But in `renderStep5` the Personalisieren-Button in the Opener tab (cold-call mode) correctly reads `state.selectedOpenerId` from the select element before setting `state.step = '4b'`. This is correct. However, if the user navigates from the Opener tab to the Skript tab in cold-call mode, clicks "Call starten", then opens the launcher again mid-call (which is prevented by `state.micStarted` guard), or if a future change allows cold-call personalization from the Skript tab, `selectedSkriptId` would be set but `renderStep4b` would still send `opener_id`. This is a latent issue — no functional bug today because the Personalisieren-Button is only rendered in the Opener tab for cold-call mode.

**Fix:** No immediate action needed. Document the constraint in a comment at the top of `renderStep4b` to prevent future regressions:
```javascript
// NOTE: cold_call path always uses state.selectedOpenerId.
// Personalisieren-Button is only rendered in Opener-Tab for cold_call — this is enforced in renderStep5.
// Do not add cold_call personalization to Skript-Tab without updating this routing.
```
