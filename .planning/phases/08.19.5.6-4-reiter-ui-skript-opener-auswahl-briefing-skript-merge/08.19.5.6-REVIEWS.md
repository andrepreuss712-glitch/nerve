# Cross-AI Plan Review — Phase 08.19.5.6

## Gemini Review

Here is the structured review of the proposed implementation plans for Phase 08.19.5.6:

### 1. Summary
The plan successfully introduces the requested 4-tab UI architecture while strictly adhering to the vanilla JS `innerHTML` constraints and respecting the `nerve.css` design system. The backend database migration for `ProfileSkript` is safe and idempotent. However, there are critical logical flaws regarding how state is shared across the new tabs, incomplete coverage of the text collection functions, and a false assumption that the frontend and backend plans can be executed independently.

### 2. Strengths
- **Architecture Compliance:** Fully respects the single-file frontend `innerHTML` rendering pattern with inline `onclick` handlers, avoiding messy event listener memory leaks.
- **Design System Integrity:** Successfully avoids hardcoded hex colors by utilizing `var(--btn-primary-bg-from)` for the empty state links, fulfilling the CSS token constraint.
- **Safe Database Migration:** The use of `ALTER TABLE` inside a `try/except` block is an excellent, idempotent approach for SQLite that prevents crashes on subsequent startup.
- **Constraint Adherence:** Leaves `/api/launcher/init`, `/api/launcher/profile/<pid>`, and `generate_personalized_skript()` untouched as requested.

### 3. Concerns

- **HIGH — False Independence (Deployment Risk):** Plan 01 and Plan 02 are **NOT** independent. Plan 01 modifies the frontend to send `skript_id` to the personalization endpoints, while Plan 02 updates the backend to expect `skript_id`. If deployed asynchronously in Wave 1, the personalization feature will break instantly (400 Bad Request). They must be deployed in the same transaction/wave.
- **HIGH — State Clobbering (`selectedOpenerId`):** The plan states that the Opener, Erlaubnis, and Pitch tabs all share the `state.selectedOpenerId` variable. If the user is meant to select *one of each* for their call, navigating between tabs and selecting items will overwrite the previous selections. *(Note: If the system only allows selecting ONE item total across all three categories because the backend only accepts one `opener_id`, this behavior is technically correct but creates a highly confusing UX).*
- **HIGH — `_collectEditedTexts()` Omission:** The plan updates `renderStep4c` and `_savePersonalizedAndStartCall`, but fails to mention `_collectEditedTexts()`. If this function is responsible for scraping the `textarea` before saving or starting a call, it will likely fail if it's still looking for the old Opener DOM elements instead of the new Skript elements.
- **MEDIUM — DOM Element ID Reuse:** Reusing the ID `lnr-opener-select` across different tabs is functionally safe *only* because `innerHTML` completely destroys and rebuilds the DOM. However, it is a poor practice that makes `getElementById` brittle and creates confusion for future maintenance.
- **MEDIUM — Missing Empty State Edge Case:** The plan filters `state.openerItems` by `type` to check for empty states, but does not explicitly guard against `state.openerItems` or `state.skripte` being completely `null` or `undefined` (e.g., on initial load before the profile is fully fetched).

### 4. Suggestions

- **Synchronize Deployment:** Explicitly link Plan 01 and Plan 02 as codependent. They must be merged and deployed simultaneously.
- **Clarify/Separate Selection State:**
  - *If the user selects 1 of each:* Create separate state variables (`state.selectedOpenerId`, `state.selectedErlaubnisId`, `state.selectedPitchId`). *Warning: This would require backend changes violating R7.*
  - *If the user selects 1 total:* Keep a single state variable but rename it to `state.selectedPrecallItemId` to clarify intent, and add a visual indicator to show which tab holds the currently active selection.
- **Dynamic DOM IDs:** Instead of reusing `lnr-opener-select`, dynamically generate IDs based on the active tab (e.g., `id="lnr-${state.activeTab}-select"`) and update the corresponding `onchange` wiring in the JS.
- **Update Text Collection:** Explicitly add instructions to review and update `_collectEditedTexts()` to ensure it correctly pulls the `.value` from the `skript` textareas.
- **Robust Empty State Checks:** Ensure the empty state logic includes a safeguard like `const items = state.openerItems || []; const filtered = items.filter(...)`.

### 5. Risk Assessment
**Overall Risk Level: HIGH**

**Justification:** While the styling and basic DOM manipulation are safe, the data-layer changes carry significant risk. The API payload mismatch between frontend and backend will cause immediate breakage if treated as independent waves. Furthermore, the ambiguity surrounding `state.selectedOpenerId` sharing across three distinct tabs will likely result in data loss during the user flow (selections clobbering each other) or an incomplete payload being sent to the backend. These logical gaps must be patched before execution.

## Consensus Summary

Only one external reviewer was available (Claude skipped — running inside Claude Code). Gemini's findings stand as the sole review.

### Key Findings (all from Gemini)

**HIGH — Plan 01 + Plan 02 Codependency**
Plans are marked as independent waves but are NOT: Plan 01 sends `skript_id` to the personalization endpoint while Plan 02 adds `skript_id` support in the backend. Executing them truly independently would break the personalization feature with 400 errors. Both must ship in the same git commit / deploy.

**HIGH — `_collectEditedTexts()` Not Addressed**
Plan 01 updates `renderStep4c`, `_savePersonalizedAndStartCall`, and `_showCapSubModal` — but does NOT mention `_collectEditedTexts()`. This function likely still looks for the old Opener textarea DOM element. It needs explicit review and update to handle the Skript textarea IDs.

**HIGH — `selectedOpenerId` Shared Across 3 Tabs**
Opener, Erlaubnisfrage, and Pitch tabs all write to `state.selectedOpenerId`. This is documented by the plan but the UX implication is unaddressed: selecting an item in Pitch overwrites what was selected in Opener. If the intent is "one opener-type item total for the call", this is acceptable (and the plan correctly routes them all to `selectedOpenerId`). But the plan should explicitly state this is intentional, not an oversight.

**MEDIUM — DOM ID Reuse (`lnr-opener-select`)**
Functionally safe due to innerHTML rebuild pattern, but fragile for future maintenance. Low priority but worth noting.

**MEDIUM — Null Guards on State Arrays**
`state.openerItems || []` pattern should be explicit in the filter calls. Already included in Plan 01 via `(state.openerItems || []).filter(...)` per the plan text — but the plan should confirm this pattern is applied consistently.

3. **Clarify selectedOpenerId intent** in Plan 01 — add a comment in the plan that sharing selectedOpenerId across Opener/Erlaubnisfrage/Pitch is intentional (one item total).
