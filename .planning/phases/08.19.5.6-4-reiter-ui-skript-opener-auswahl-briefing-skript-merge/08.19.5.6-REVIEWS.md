## Plan 01: Frontend renderStep5() 4-Tab-UI (v3)

### 1. Summary
Plan 01 orchestrates the transition of Step 5 from a flat list to a 4-tab interface, separating content by type (Opener, Erlaubnisfrage, Pitch, Skript). It introduces robust state management for selections (4 independent variables), ties the "Personalisieren" button to the current `state.mode`, and fixes the textarea overwrite bug. It also introduces `_resolvedTeleprompterSkript` to handle the priority cascade for what gets displayed in the PiP window.

### 2. Strengths
- **State Separation:** Isolating the selected IDs into four distinct variables prevents cross-tab contamination.
- **Mode-Aware UI:** Tying the "Personalisieren" button to `state.mode` (Cold-Call vs. Meeting) correctly aligns the UI with the user's workflow intent.
- **Robust Teleprompter Resolution:** The 3-level resolution in `_openPipAndMic` (`_resolvedTeleprompterSkript` -> `_editedSkriptText` -> `selectedSkriptId`) elegantly solves the Pitch-Fallback requirement (OD-01).
- **Strict CSS Enforcement:** Explicitly banning hex literals ensures the UI remains theme-compliant.

### 3. Concerns
- **MEDIUM — State Reset Scope:** The plan mentions that a `profile-change` resets all 4 selection variables. However, if the user changes `state.mode` (e.g., from Cold-Call to Meeting), the selection states should likely be reset as well to prevent invalid combinations from persisting across modes.
- **LOW — PiP Text Mapping:** When a Cold-Call (Opener) is personalized and saved (which Plan 02 dictates is saved as a `ProfileSkript`), the frontend must ensure it knows to look in the correct place upon reload. Plan 01 seems to handle this via `renderStep4c` reading `originalText` appropriately, but edge cases during rapid navigation might exist.

### 4. Suggestions
- Update Task 2 to ensure that both `profile-change` **and** `mode-change` trigger the reset of the 4 selection variables.
- Ensure the `fcd-tab` classes are thoroughly tested for active/inactive visual states, as the removal of inline hex codes means it relies entirely on the existing CSS cascade.

### 5. Risk Assessment
**LOW to MEDIUM.** The architectural risks from v2 have been effectively mitigated. The state management is now sound, and the atomic deployment requirement safeguards the integration. The remaining risks are standard UI state edge-cases.

## Plan 02: Backend Mode-dependent Routing (v3)

### 1. Summary
Plan 02 updates the data model and API endpoints to support the new frontend logic. It adds three new columns to `ProfileSkript` (`parent_id`, `is_personalized`, `briefing_source_firma`) using an idempotent SQLite migration. It rewrites the personalization and save endpoints to intelligently route based on `call_mode`, ensuring all generated content is saved uniformly into the `ProfileSkript` table, regardless of whether the source was an Opener or a Meeting Skript.

### 2. Strengths
- **Unified Storage:** Forcing all personalized outputs into `ProfileSkript` simplifies the data model. An AI-personalized opener is functionally a script for a specific prospect.
- **Safe Migrations:** Using `try/except` for the `ALTER TABLE` statements in `app.py` is the correct, safe way to handle SQLite migrations without a heavier tool.
- **Constraint Avoidance:** Dropping the Foreign Key requirement for `parent_id` (D-04) avoids SQLite's notoriously difficult `ALTER TABLE` constraints while still maintaining logical relations.
- **Backwards Compatibility:** Keeping a fallback mechanism (checking for ID presence without `call_mode`) ensures older frontend clients/sessions won't crash immediately.

### 3. Concerns
- **MEDIUM — Migration Error Masking:** The idempotent `try/except` in `app.py` uses broad `except Exception: pass`, which might silently swallow syntax errors or database locks — not just the expected "duplicate column name" error.
- **LOW — Orphaned Records:** Because `parent_id` lacks a Foreign Key constraint, deleting an original Opener won't cascade to its personalized `ProfileSkript`. Likely acceptable for an AI history use case, but worth noting.

### 4. Suggestions
- In Task 2, explicitly catch `sqlite3.OperationalError` and check the error string for "duplicate column name" rather than broad `except Exception: pass`.
- Ensure `api_personalize_skript_save()` correctly maps `parent_id` to the source `opener_id` or `skript_id` so lineage of generated text can be tracked.

### 5. Risk Assessment
**LOW.** The backend changes are isolated, non-destructive, and safely implemented via idempotent migrations. The unified storage approach is a smart architectural decision that simplifies future development.

### New Findings from v3 Review

**MEDIUM — Mode-change should also reset selection state**
Profile-change correctly resets all 4 selection variables, but mode-change (Cold-Call → Meeting) does not. A user who selected an Opener in Cold-Call mode, then switches to Meeting mode, will have a stale `selectedOpenerId` in state while in the Skript-Tab flow. This could send an incorrect payload if `selectedOpenerId` is referenced in a fallback.

**MEDIUM — Migration error masking too broad**
`except Exception: pass` in the DB migration block swallows non-idempotency errors (syntax errors, locks). Should catch specifically for "duplicate column name".

**LOW — Orphaned ProfileSkript records**
No cascading delete on `parent_id`. Acceptable given the use case but should be documented.
