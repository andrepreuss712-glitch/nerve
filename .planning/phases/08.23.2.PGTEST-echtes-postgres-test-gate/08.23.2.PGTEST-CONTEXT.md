<decisions>
## Implementation Decisions

### Test-DB-Provisionierung
- **D-01:** Wegwerf-DB = **eigene DB auf der bestehenden Prod-Postgres-Instanz** (`CREATE DATABASE nerve_test` als `postgres` im deploy.sh → `alembic upgrade head` → `DROP DATABASE` am Ende). KEIN Docker-Container, KEIN ephemerer Temp-Cluster.
  - Begründung: `nerve_app` + `nerve_anon_worker` existieren cluster-global (peer-auth) → Req-4 (RLS/Anon-Tests laufen) wird OHNE Rollen-Nachbau erfüllt; kein Docker-Dependency auf dem Hetzner-Host; schnellster Deploy. Isolation per dediziertem DB-Namen + DROP-Teardown (SPEC erlaubt „eigener DB-Name").
  - Research-Pflicht-Bestätigung: peer-auth-Verbindbarkeit von `nerve_app`/`nerve_anon_worker` gegen eine SEPARATE DB `nerve_test` auf derselben Instanz (Rollen sind cluster-global, sollten greifen — verifizieren).
- **D-02 (HARTE SICHERHEITS-SCHRANKE, André-Direktive):** CREATE DATABASE + DROP DATABASE + alle Test-DSNs zielen **AUSSCHLIESSLICH** auf den dedizierten Namen `nerve_test` — NIEMALS auf die Produktions-DB `nerve`.
  - Harter Guard: das Provision-/Teardown-Skript verweigert CREATE/DROP, wenn der Ziel-DB-Name nicht **EXAKT** `nerve_test` ist (Whitelist), und **bricht ab statt zu raten**.
  - Begründung: ein Tippfehler bei `DROP DATABASE` auf der Prod-Instanz = Totalverlust der Produktions-DB. Dieser Guard ist nicht optional.

### Test-Isolation
- **D-03:** DB wird **1× pro Deploy-Lauf** gebaut (1× `alembic upgrade head`); **per-Test-Isolation via Transaktions-Rollback** im Fixture (`autocommit=False`, `rollback()` im `finally`) — das bestehende Muster von `nerve_app_pg_conn` (conftest.py:111ff). KEIN Schema-Drop-Recreate pro Test (zu langsam), KEINE shared-DB-ohne-Reset (Leakage).
- **D-04 (HARTE AUSNAHME für Security-Tests, André-Direktive):** Die **RLS-Isolations- + Anonymizer-Worker-Tests dürfen NICHT auf dem Rollback-pro-Test-Pfad laufen.**
  - Grund: Cross-Tenant-Sichtbarkeit prüft man über ECHTE Commits über getrennte Connections (Tenant A committet → Connection als Tenant B prüft, dass er es NICHT sieht). Bei rollback-only ist nichts committet → die zweite Connection sieht ohnehin nichts → Test wäre TRIVIAL grün, OHNE RLS je zu prüfen = **False-Green**.
  - Lösung: Security-Tests nutzen das **dedizierte Real-Commit-Fixture MIT deterministischem Teardown** (Daten nach dem Test gezielt löschen, da kein Rollback aufräumt). Generische Tests bleiben auf dem schnellen Rollback-Pfad.

### RLS-Mandanten-Kontext in generischen Tests
- **D-05:** Generische Fixtures (`db_session`, `client`) verbinden als `nerve_app` und **setzen einen Default-Test-Mandanten** via `set_current_tenant(TEST_TENANT_UUID)` am Fixture-Start → tenant-scoped Reads auf `crm.*` funktionieren, **spiegelt den echten Prod-Pfad** (nerve_app + GUC `app.tenant_id`).
  - KEINE BYPASSRLS-/Superuser-Rolle für generische Tests (das wäre False-Green: ein RLS-Defekt der Prod träfe, bliebe in generischen Tests unsichtbar).
  - Tests die nur `public.*` anfassen sind ohnehin unberührt (RLS FORCE nur auf `crm.*`).
  - Security-/Isolations-Tests setzen weiterhin explizit ihre eigenen Mandanten (tun sie schon, kombiniert mit D-04 Real-Commit).
  - Randbedingung: der `after_begin`-Hook (db.py:86) feuert ab jetzt gegen echtes PG → ohne D-05 sähen generische Tests RLS-fail-closed 0 Zeilen.

### Gate-Robustheit & Deploy-Tempo
- **D-06:** Teardown via **`trap cleanup EXIT`** im deploy.sh-Test-Block → `DROP DATABASE nerve_test` läuft garantiert auch bei Test-Fehler / SIGTERM / Skript-Abbruch. PLUS **Pre-Run-Cleanup**: vor dem Lauf eine evtl. verwaiste `nerve_test`-DB defensiv droppen (Gürtel-und-Hosenträger, falls ein früherer Lauf hart starb). Beides nur auf dem Whitelist-Namen `nerve_test` (D-02).
- **D-07:** Fail-closed **pro Schritt einzeln** mit eigenem Klartext-Grund: Provisionierung, Connect, `alembic upgrade head`, pytest — jeder Schritt prüft Exit-Code und bricht mit eigenem Log ab (z.B. `[deploy] FEHLER: Test-DB-Provisionierung fehlgeschlagen`). KEIN Code-Zweig weicht je auf SQLite/Prod aus (Req 7). Erfüllt Req-7-Acceptance (expliziter Grund) direkt.
- **D-08:** Deploy-Tempo: **Korrektheit vor Tempo, ~+30s Mehrzeit OK.** Das Gate läuft pro Deploy, ein ehrliches Postgres-Gate ist den Aufpreis wert; Deploy ist kein Live-Pfad (Punkt 25 gilt der Antwort-Latenz, nicht dem Deploy). Tempo-Optimierung (z.B. Template-DB) erst wenn spürbar störend — kein Vorab-Engineering.

### Abgeleitete Implikation (kein Re-Ask, Plan-Stoff)
- **D-09:** **Alle vier Test-DSNs zeigen im Gate auf `nerve_test`** (Req 5, kein Prod-Kontakt): die 3 bestehenden Fixtures lesen heute `NERVE_APP_TEST_DSN` / `ANON_WORKER_TEST_DSN` / `NERVE_SCHILD_TEST_DSN` (→ Live-`nerve`); die generischen brauchen `TEST_DATABASE_URL`. Im deploy.sh-Gate werden alle vier auf `nerve_test` gesetzt. Genaue Env-Var-Verdrahtung = Plan-Stoff.

### Claude's Discretion
- Genaue Mechanik des Provision-/Teardown-Skripts (inline in deploy.sh vs. ausgelagertes Helper-Skript) — Planner entscheidet.
- Exaktes Fixture-Design für den Real-Commit-Security-Pfad (D-04) + deterministischer Teardown-Mechanismus.
- `TEST_TENANT_UUID`-Quelle/Konstante für D-05 (fester Test-UUID vs. seed-erzeugt).
- Migrations-Revision-Pinning: `alembic upgrade head` liest die Live-HEAD-Revision zur Execute-Zeit (NICHT hardcoden — PGTEST kann vor/nach TAXO1-Migrationen laufen).

## Existing Code Insights

### Reusable Assets
- **Real-PG-Fixture-Muster** (conftest.py:111-190): DSN-aus-Env + SKIP-wenn-fehlt + explizite Transaktion. Vorbild für das D-04-Real-Commit-Security-Fixture. `nerve_app_pg_conn` nutzt bereits `autocommit=False` + `rollback()` im finally (D-03-Muster).
- **RLS-GUC-Plumbing** (db.py:56-103): `set_current_tenant(tid)` publiziert den Mandanten in eine contextvar; `after_begin`-Hook setzt transaktions-lokal `set_config('app.tenant_id', …, true)`. D-05 ruft `set_current_tenant(TEST_TENANT_UUID)` im generischen Fixture.
- **Peer-Auth-Deploy-Muster** (deploy.sh:151): `sudo -u nerve_app bash -c '… NERVE_SCHILD_TEST_DSN=postgresql://nerve_app@/nerve …'` — etablierter Weg, Tests als echte DB-Rolle server-seitig zu fahren (Vorbild für nerve_app/nerve_anon_worker gegen `nerve_test`).

### Established Patterns
- **Postgres-Schemas** (public/crm/training): RLS FORCE nur auf `crm.*` (G-MEET 0012/0013); `training.*` ist DPO-Tresor (nerve_app hat KEINEN Zugriff — DPO-Wand). Generische Tests fassen primär `public.*` an → RLS-unkritisch außer bei crm-Tests.
- **Migrations als `postgres`/OWNER `nerve_app`**: Prod-Schema via deploy.sh, NICHT app.py (app.py-Hook ist SQLite-only). PGTEST baut das Test-Schema via `alembic upgrade head` gegen `nerve_test`.

### Integration Points
- `deploy.sh`-Test-Stufe (Z.130-143) = der zentrale Umbau-Ort: Provision → upgrade → pytest → Teardown.

- Schild-Guard-Stufe (deploy.sh:145-156) darf nicht brechen (Req 9) — ggf. auch auf `nerve_test` umlenken (Req 5), ohne Aussagekraft zu verlieren.

## Specific Ideas

- **Whitelist-Guard `nerve_test`** (D-02): André bestand explizit auf Abbruch-statt-Raten bei jedem CREATE/DROP DATABASE, dessen Ziel-Name nicht exakt `nerve_test` ist. Prod-`nerve`-Totalverlust-Schutz ist nicht verhandelbar.
- **False-Green-Bewusstsein** durchgängig: rollback-only für RLS-Tests (D-04) UND BYPASSRLS für generische Tests (D-05 abgelehnt) wurden beide als False-Green-Fallen erkannt und vermieden. Der Geist von Req 7 (fail-closed, kein still-grün) zieht sich durch alle Isolations-Entscheidungen.
