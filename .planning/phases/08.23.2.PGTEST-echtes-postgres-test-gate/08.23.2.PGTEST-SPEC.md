## Goal

Das `deploy.sh`-Test-Gate (volle pytest-Suite) läuft gegen eine echte, wegwerfbare Postgres-Datenbank statt gegen SQLite-in-memory — das Schema dieser Wegwerf-DB wird per `alembic upgrade head` gebaut (echte Schemas/Rollen/RLS/Grants), und das Gate ist fail-closed: kann die Wegwerf-DB nicht stehen, bricht der Deploy ab statt still zu skippen oder auf SQLite/Produktion auszuweichen.

## Background

Das Gate ist seit ~29.05.2026 unbemerkt kaputt (kein ehrlicher Deploy seither). Diagnose 2026-06-15, drei Schichten — alle pre-existing, NICHT durch TAXO1 verursacht:

1. **`deploy.sh:135`** fährt `pytest /opt/nerve/app/tests/` ohne Test-DSN → läuft gegen SQLite. Der begleitende Kommentar (`deploy.sh:130-134`) nennt den conftest-Refactor bereits explizit als „eigene Folge-Phase".
2. **`tests/conftest.py`** — die generischen Fixtures `db_session` (Z.43) und `client` (Z.66) sind hart auf `create_engine("sqlite:///:memory:")` verdrahtet und ignorieren jede `TEST_DATABASE_URL`. Drei Spezial-Fixtures existieren bereits mit echtem-PG-DSN + SKIP-wenn-fehlt (kein SQLite-Fallback, bewusst gegen False-Green): `nerve_app_pg_conn` (`NERVE_APP_TEST_DSN`, RLS-Isolation), `anon_worker_pg_engine` (`ANON_WORKER_TEST_DSN`, Anonymizer-Worker-RLS), `schild_guard_pg_conn` (`NERVE_SCHILD_TEST_DSN`, Schild-Guard). Diese drei zeigen heute auf die **LIVE `nerve`-Produktions-DB**.
3. **`app.py:1115`** — Alembic-Auto-Hook läuft `alembic upgrade head` NUR im SQLite-Pfad (`if _db_url_str.startswith('sqlite')`). Migrationen 0008–0016 enthalten ~57 nur-Postgres-Befehle (CREATE SCHEMA, GRANT, RLS, OWNER) → gegen SQLite Syntaxfehler → harter `raise`.
4. **Schicht-1-Pflaster `cf5de6d`** (`database/db.py:41-49`) registriert global einen `connect`-Listener, der pro SQLite-Verbindung `:memory:` als Schema `crm`/`training` ATTACHt, damit `Base.metadata.create_all()` durchläuft. Cross-AI Gemini (`.planning/_testgate_gemini_OUT.md`): statisch korrekt + isoliert (PASS), aber bestätigt — es bleibt ein **SQLite-Pflaster auf `create_all`**; die alembic-Kette bleibt SQLite-inkompatibel.

**Vierter Befund (Scout 2026-06-15, im Brief nicht genannt):** `database/db.py:86-103` registriert für nicht-SQLite-Engines einen `after_begin`-Hook, der den Mandanten-Zeilen-Schutz (RLS GUC `app.tenant_id`) transaktions-lokal scharfschaltet. Sobald die generischen Tests gegen echtes Postgres laufen, feuert dieser Hook → Tests ohne gesetzten Mandanten-Kontext sehen `current_setting('app.tenant_id', true) = NULL` → RLS fail-closed → 0 Zeilen. SQLite hat diesen Pfad nie ausgelöst. Genau diese Drift soll die Phase ehrlich machen — wird hier als Randbedingung verankert, die Mechanik (Mandanten-Kontext in generischen Tests vs. Test-DB-Strategie) ist Plan-Stoff.

**Primäres Deliverable (existiert heute NICHT):** ein Deploy-Gate, das die pytest-Suite gegen eine per `alembic upgrade head` gebaute, wegwerfbare, von Produktion isolierte Postgres-DB fährt und fail-closed abbricht statt zu skippen.

**Herkunft:** herausgelöst aus Slot `08.23.2.STAGING` Task (1) („deploy.sh-Test-Gate fixen") und vorgezogen, weil das Gate jeden `deploy.sh production` blockiert — inkl. der TAXO1-Migrations-Deploys. STAGING behält Rest-Tasks (2)–(5).

## Requirements

1. **Echtes-Postgres-Gate**: Die deploy.sh-pytest-Suite läuft gegen eine echte Postgres-DB, nicht SQLite-in-memory.
   - Current: `deploy.sh:135` fährt pytest ohne Test-DSN → SQLite-in-memory.
   - Target: Das Gate fährt die Suite gegen eine echte, per `alembic upgrade head` aufgebaute Wegwerf-Postgres-DB.
   - Acceptance: Im Deploy-Lauf ist nachweisbar (Log/DSN), dass pytest gegen eine `postgresql://`-DB lief; ein bewusst eingebauter Postgres-spezifischer Schema-Defekt (z.B. fehlende RLS-Policy) lässt mindestens einen Test rot werden — auf SQLite wäre er grün geblieben.

2. **conftest honoriert Test-DSN**: Die generischen Fixtures bauen gegen die echte Test-DB, nicht hardcoded SQLite.
   - Current: `db_session` (conftest:43) + `client` (conftest:66) sind hart auf `sqlite:///:memory:`.
   - Target: Beide Fixtures verbinden gegen die echte Postgres-Test-DB (DSN aus Umgebung, z.B. `TEST_DATABASE_URL`); keine hardcoded SQLite-URL mehr im aktiven Pfad.
   - Acceptance: `grep "sqlite:///:memory:" tests/conftest.py` liefert keinen Treffer im aktiven Fixture-Code; beide Fixtures liefern eine Session gegen die Postgres-Test-DB.

3. **Schema via alembic upgrade head**: Das Test-Schema wird durch die volle Migrations-Kette gebaut, nicht durch `create_all`.
   - Current: Test-Schema entsteht über `Base.metadata.create_all()` (+ SQLite-ATTACH-Pflaster); die alembic-Kette läuft nie gegen die Test-DB.
   - Target: Die Wegwerf-Test-DB wird per `alembic upgrade head` aufgebaut → echte Schemas (public/crm/training), Rollen, RLS-Policies, Grants, Constraints sind vorhanden.
   - Acceptance: Nach Aufbau enthält die Test-DB `alembic_version` = head-Revision; die schema-qualifizierten Tabellen (crm.*, training.*) + die 0013/0015-RLS-Policies existieren (per Katalog-Query belegbar).

4. **Sicherheits-Tests laufen WIRKLICH (kein Skip)**: RLS-Isolation + Anonymizer-Worker werden im Gate ausgeführt, nicht übersprungen.
   - Current: `test_rls_isolation.py` + `test_anonymizer_worker.py` SKIPpen im Deploy-Gate, weil `NERVE_APP_TEST_DSN`/`ANON_WORKER_TEST_DSN` dort nicht gesetzt sind.
   - Target: Die Test-Rollen `nerve_app` + `nerve_anon_worker` verbinden gegen die Wegwerf-DB (mit den per alembic gebauten Policies) → beide Test-Gruppen LAUFEN und sind grün. **Guardrail:** Fallback auf „nur generische Tests" NUR wenn Research belegt, dass das unverhältnismäßig ist; dann wird die RLS-Test-Lücke EXPLIZIT als `SEC-USERDATA`-Folgepunkt in Plan + Roadmap getrackt — niemals still für immer skippend. Die getroffene Wahl (Ziel-Option vs. Fallback) wird in CONTEXT/PLAN dokumentiert.
   - Acceptance: Im Deploy-Log erscheinen `test_rls_isolation.py` + `test_anonymizer_worker.py` als PASSED (nicht SKIPPED) — ODER, falls Guardrail-Fallback, existiert ein verlinkter `SEC-USERDATA`-Tracking-Eintrag in ROADMAP + Plan und das SKIP ist begründet protokolliert.

5. **Alle Fixtures → Wegwerf-DB (keine Prod-DB-Berührung)**: Die 3 bestehenden Live-`nerve`-Fixtures werden auf die Wegwerf-Test-DB umgelenkt.
   - Current: `nerve_app_pg_conn`, `anon_worker_pg_engine`, `schild_guard_pg_conn` verbinden gegen die LIVE `nerve`-Produktions-DB.
   - Target: Alle drei verbinden gegen die Wegwerf-Test-DB; kein Test (auch nicht der Schild-Guard im Gate-Kontext dieser Phase) liest/schreibt je die Produktions-`nerve`-DB. (Falls Req-4-Guardrail-Fallback greift, wird diese Umlenkung mit-revidiert.)
   - Acceptance: Statische Prüfung + DSN-Beleg: keiner der drei Fixture-DSNs zeigt im Test-Lauf auf die Produktions-`nerve`-DB; der Ziel-DSN ist die Wegwerf-DB.

6. **SQLite-Emulation entfernt (kein toter Pfad)**: Die SQLite-Pflaster werden entfernt, nicht erweitert.
   - Current: `cf5de6d`-ATTACH-Listener (`db.py:41-49`) + `app.py:1115` SQLite-Alembic-Hook halten den SQLite-Test-/Start-Pfad künstlich am Leben.
   - Target: Beide werden entfernt (Postgres-only für Tests, André-Entscheidung). Kein verbleibender aktiver Code-Pfad hängt von SQLite-Schema-Emulation oder SQLite-Auto-Alembic ab; falls Reste bleiben müssen, sind sie explizit begründet (Foundation-Register).
   - Acceptance: `grep` zeigt den ATTACH-Listener + den SQLite-Alembic-Hook entfernt (oder begründet im Foundation-Register); die Suite läuft grün OHNE diese Pflaster.

7. **FAIL-CLOSED (keine stille Hintertür)**: Steht die Test-DB nicht, bricht der Deploy ab.
   - Current: Bei DSN-Abwesenheit skippen die PG-Tests still; die generische Suite läuft auf SQLite weiter → False-Green möglich.
   - Target: Kann die Wegwerf-Test-DB nicht provisioniert werden ODER ist Postgres nicht erreichbar ODER lässt sich das Schema nicht per `alembic upgrade head` bauen → `deploy.sh` bricht mit non-zero Exit ab (kein Restart, kein Deploy). NIEMALS still die Suite überspringen, auf SQLite zurückfallen oder gegen Produktion ausweichen.
   - Acceptance: Simulierter Provisionierungs-/Verbindungsfehler führt zu `deploy.sh`-Abbruch (Exit ≠ 0, kein Service-Restart); im Log steht ein expliziter Fehlergrund; es gibt keinen Code-Zweig, der bei fehlender Test-DB auf SQLite oder Produktion ausweicht.

8. **Sauberer Teardown**: Die Wegwerf-DB wird pro Lauf erzeugt und rückstandsfrei entfernt.
   - Current: Keine Test-DB-Provisionierung/-Teardown existiert.
   - Target: `deploy.sh` provisioniert die Test-DB vor dem Lauf und räumt sie danach ab (auch bei Test-Fehlschlag — kein Müll-Rest auf der Instanz).
   - Acceptance: Nach einem Deploy-Lauf (grün wie rot) existiert keine verwaiste Test-DB/-Rolle/-Container-Artefakt auf der Instanz (per Katalog-/Liste-Check belegbar).

9. **Produktion + Schild-Guard unverändert grün**: Der bestehende Postgres-Produktions- und Schild-Guard-Pfad bricht nicht.
   - Current: `deploy.sh:151` Schild-Guard läuft als `nerve_app` gegen Postgres-`pg_description` der Live-`nerve`; Produktion läuft auf echtem Postgres (Schema via deploy.sh, app.py-Hook übersprungen).
   - Target: Der Produktions-Deploy-Pfad + der Schild-Guard funktionieren nach dem Umbau weiter (Schild-Guard ggf. auf Wegwerf-DB umgelenkt gemäß Req-5, ohne seine Aussagekraft zu verlieren).
   - Acceptance: Ein vollständiger `deploy.sh production`-Lauf endet grün (Tests + Schild-Guard + Restart); die Produktions-`nerve`-DB ist unverändert (keine Schema-/Daten-Mutation durch den Test-Pfad).

## Boundaries

**In scope:**
- Umbau `deploy.sh`-Test-Stufe: Wegwerf-Postgres-Test-DB provisionieren → `alembic upgrade head` → pytest dagegen → Teardown.
- `tests/conftest.py`-Refactor: generische Fixtures (`db_session`, `client`) auf echten Test-DSN; die 3 Spezial-Fixtures auf Wegwerf-DB umlenken.
- Entfernen der SQLite-Emulation: `cf5de6d`-ATTACH-Listener (`db.py`) + `app.py:1115` SQLite-Alembic-Hook.
- Fail-closed-Verhalten im Gate (Provisionierung/Verbindung/Schema-Aufbau scheitert → Deploy-Abbruch).
- RLS-Isolation + Anonymizer-Worker-Tests im Gate zum Laufen bringen (Ziel), inkl. Verbindbarkeit der Test-Rollen gegen die Wegwerf-DB.
- Reparatur von Test-Inhalten, die durch den Backend-Wechsel rot werden, SOWEIT es Test-Infrastruktur betrifft (z.B. Mandanten-Kontext setzen, damit RLS-fail-closed nicht fälschlich 0 Zeilen liefert).

**Out of scope:**
- Rest-Tasks von `08.23.2.STAGING`: Auto-Alembic im Deploy-Workflow, Auto-`deploy_meta`-Write, atomarer `staging→production`-Promote, Drift-Audit — bleiben in STAGING (eigene Phase, ans Ende).
- Dedicated-Staging-Cloud (`08.23.2.MIRROR`) — Post-Launch.
- Die TAXO1-Migration selbst (intent_event) — eigene Phase; PGTEST gatet sie nur.
- Aufdecken/Beheben echter App-Logik-Bugs, die der Postgres-Lauf zutage fördert — werden als Fund eskaliert (eigener Bugfix/Mini-Phase), nicht still in dieser Phase mitgepatcht (Anti-Abrieb, ein Thema pro Phase). Stilllegen/Skippen eines real-roten Tests ist verboten (Req-7-Geist).
- Container-vs-eigene-DB, frische-DB-pro-Lauf-vs-Transaktions-Rollback, genaue DSN-/Auth-Mechanik — bewusst WIE-Fragen für Research/Plan, hier nicht festgelegt.

## Constraints

- **Production-Host, kein Local-Dev** (CLAUDE.md HART): pytest + Provisionierung laufen serverseitig im `deploy.sh`-Pfad; Verify = `deploy.sh production`. Kein lokaler Postgres-Lauf als Acceptance.
- **Isolation von Produktion ist hart**: Die Test-DB ist von der Live-`nerve`-DB getrennt (eigener DB-Name / eigene Instanz / Container) und darf deren Daten NIE lesen/schreiben.
- **Test-Rollen-Feasibility (Research-Pflicht-Check):** `nerve_app` + `nerve_anon_worker` müssen gegen die Wegwerf-DB verbindbar sein (Peer-Auth / Rollen-Existenz auf der Instanz). Bestätigt Research; falls nicht verhältnismäßig → Req-4-Guardrail.
- **RLS-`after_begin`-Hook feuert gegen echtes Postgres** (`db.py:86`): generische Tests brauchen ggf. Mandanten-Kontext, sonst RLS-fail-closed → 0 Zeilen. Behandlung = Plan-Stoff, aber Randbedingung ist gesetzt.
- **Deploy-Dauer:** das Gate läuft bei JEDEM `deploy.sh production` → Provisionierung + Teardown sollen den Deploy nicht unverhältnismäßig verlangsamen (kein hartes Budget, Research-Erwägung).
- **Migrations-Stil unverändert:** keine Migration wird umgeschrieben, um SQLite-kompatibel zu werden (das ist genau das Hau-den-Maulwurf-Anti-Pattern, das diese Phase beseitigt).
