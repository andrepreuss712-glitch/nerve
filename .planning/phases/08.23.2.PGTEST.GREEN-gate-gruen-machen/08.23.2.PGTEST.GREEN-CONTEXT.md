## Implementation Decisions

### Teil a — Isolations-Mechanismus (Req-2/3/4) — 3-Sichten-validiert

- **D-G01 (Kern):** **Auto-Reset-Wächter, GESPALTEN.** Der Wächter HEILT nach jedem Test die test-erzeugten EXTRA-Rows selbst (reverse-FK-DELETE) + emittiert eine LAUTE Warnung (nodeid + Tabelle + PKs) → 0 Baseline-Errors, Leaks sichtbar (Req-3/Req-7-Ehrlichkeit), nächster Test sauber (Isolation).
- **D-G02 (STRICT SPLIT, Gemini-Wachpunkt 1):** `_diff_baseline` gibt `leaked` zum Löschen zurück; `missing` + `mutated` der geschützten Baseline (id=1-Seed, prompt_versions etc.) werfen sofort **harten `pytest.fail`** mit nodeid (BLOCK — echter Bug → Teil-b-Triage). KEIN Heilen von missing/mutated: Re-Insert würde `trg_mk_tenant_org` feuern → neue UUID → bricht Folge-Tests (technisch kaputt, nicht nur Req-7). Fängt die 7 base-seed-Delete-Bugs (Tests die id=1 löschen).
- **D-G03 (Attribution, Req-3, Gemini-Wachpunkt 2):** Auto-Delete NIE stumm — `logging.warning("[BASELINE-AUTO-FIX] {nodeid} leaked rows in {tbl}: {ids}")`.
- **D-G04 (Scope-Klarstellung, André):** Der Auto-Reset-Wächter heilt/blockt **NUR public.*** (wie der heutige in-pytest-Guard). **crm.* bleibt UNVERÄNDERT POST-SUITE-Check in deploy.sh = HARTER BLOCK bei crm != 0** (KEIN Auto-Clean — nerve_app sieht crm nur tenant-gefiltert). Die wenigen crm-Writer (test_rls_isolation/test_anonymizer_worker/...) räumen ihre crm-Rows weiter selbst auf (`cleanup_rows`). Auto-Reset löst die PUBLIC-Leak-Dimension (die ~600-Test-Wurzel), NICHT crm.
- **D-G05 (Wächter-TX-Hygiene, Gemini-Wachpunkt 5):** explizit `begin()`/`commit()` auf der `_baseline_guard_engine`, damit gelöschte Rows für den nächsten Test wirklich weg sind.
- **D-G06 (UUID-Cast, Gemini-Wachpunkt 4):** das Auto-Delete repliziert den 10e5d0a-Fix (`WHERE id::text = ANY(...)`) — public-Tabellen haben gemischt UUID- und INT-PKs.
- **D-G07 (Multi-Conn-Race, niedrig bei 1 Worker, Gemini-Wachpunkt 6):** Wächter-Snapshot/Cleanup vs. async Worker-Connection-Locks für Block M (Multi-Worker) vormerken — kein Handlungsbedarf jetzt.

### Teil b — Empirische Triage (Req-5/6)

- **D-G08 (Triage-Mechanismus):** **Server-Triage-Harness, kein Restart.** Bau `scripts/triage.sh` (ODER deploy.sh-Subkommando), das den Gate-Provisioning-Block 1:1 wiederverwendet (pg_dump-Restore + `alembic upgrade head` + 4 nerve_test-DSNs + DATABASE_URL + Whitelist-Guard + trap-Drop), aber NUR gezielte Tests läuft (`pytest <file::test> -v / -k`) und NIE `systemctl restart`/Deploy auslöst. nerve_test-only → Prod-nerve nie berührt (Req-5/10). Erlaubt iteratives Instrumentieren + Re-Run am echten PG (Diagnose-Prints temporär im Harness, NICHT ins git committen). **Bleibendes Werkzeug (Ratchet, André-Direktive 15.06.)**, kein Wegwerf-Skript.
- **D-G09 (Empirie-Workflow, deckt die "2×-daneben"-Lektion):** (1) Erst EIN voller Lauf via Harness `-v --tb=long` → alle ~51 Fail-Tracebacks einsammeln (grobe Klassifikation). (2) DANN jeden mehrdeutigen Fail (echter App-Bug vs. veralteter Test?) gezielt instrumentieren + einzeln re-runnen bis Ursache empirisch belegt — NICHT aus dem Code-Lesen raten. (3) Klassifikation pro Test in die Triage-Tabelle (Req-5) mit empirischem Beleg.
- **D-G10 (xfail-Ticket-Ziel):** Jeder bestätigte echte NICHT-kritische Bug, der ge-xfailed wird, bekommt einen **Backlog-999.x-Eintrag** (gsd-add-backlog-Muster): Test-nodeid + reason + "xfail(strict) in GREEN, Fix in eigener Phase". Der `xfail`-Marker `reason=` verlinkt die 999.x-ID. KEIN dedizierter BUGS-Phasen-Eintrag jetzt (Scope vor Triage unbekannt = verfrüht). Anti-Versickern 2-schichtig: (1) `xfail(strict=True)` selbst-aufdeckend (XPASS → Suite rot → Marker-Zwang), (2) 999.x getrackt. NACH der Triage: Backlog-Review der 999.x → opportunistisch fixen ODER (bei mehreren) in dedizierte Fix-Phase promoten (`gsd-review-backlog`).

### Teil c — Marker-Registrierung (Req-7/8)

- **D-G11 (Marker-Set):** Nur **`live` + `perf`** (kein preemptiver `reid`, YAGNI). `live` = braucht real-API (real-Haiku-Integration, Re-ID-Rate-Messung am echten Modell). `perf` = p95/Latenz/Timing. Deckt die ~29 env-abhängigen. Falls später Anonymisierungs-Threshold-Tuning häufig EINEN gezielten Re-ID-Lauf braucht: via `pytest -m live -k reid` sub-selektieren (trivial nachrüstbar). pytest.ini hat heute nur `security` — `live`/`perf` werden dort registriert (keine unknown-marker-Warnung).
- **D-G12 (Gate-Exklusion):** der deploy.sh-pytest-Aufruf (heute `pytest tests/ --tb=short -q`, kein `-m`) bekommt `-m "not live and not perf"`. Security-Tests laufen heute schon im Tor (kein `-m`) und BLEIBEN drin — `not live and not perf` schließt sie NICHT aus.
- **D-G13 (Re-ID-Rate-Bedingung, Req-8-Brücke):** Re-ID-Rate per `live` aus dem Tor zu nehmen ist NUR zulässig, weil die SICHERHEIT/LOGIK der Anonymisierung DETERMINISTISCH im Tor bleibt (test_anonymizer_worker mit `_fake_anonymize`-Stub). Nur die STATISTISCHE Echt-Modell-QUALITÄT (re-id rate) ist der env-abhängige, exkludierte Teil.
- **D-G14 (Determinismus-Strategie, Req-8):** Via Triage-Harness (D-G08) EMPIRISCH feststellen, welche Security/DSGVO/RLS/Anon-Tests heute nur wegen fehlendem API-Key skippen/roten. Die werden via `monkeypatch` des anthropic-Clients (Canned-Response) deterministisch gemacht und BLEIBEN im Tor (PASSED). KEIN live/perf-Marker auf Security-Tests — `grep` belegt das (Req-8-Acceptance). KEIN separater statischer Inventur-Schritt (Harness trifft die per-Test-Entscheidung schon mit; statisches Raten vermeiden).
  - **PRÄZISIERUNG 1 (kritisch, false-green-Guard):** der Mock macht NUR die nicht-deterministische EXTERNE Abhängigkeit (Modell-/API-Aufruf) deterministisch — er darf die SICHERHEITS-LOGIK NICHT umgehen. Die Canned-Response muss realistisch genug sein, dass der echte Security-Pfad (RLS/Filter/Gating/Anon-Merge) WIRKLICH läuft + asserted wird. Ein Mock der die zu testende Eigenschaft wegmockt = false-green.
  - **PRÄZISIERUNG 2 (Edge-Case):** lässt sich ein Security-Test NICHT mocken ohne seinen Zweck zu zerstören → NICHT still per Marker raus. Stattdessen deterministische Variante ODER explizit dokumentierte Tor-Deckungs-Lücke mit kompensierenden Kontrollen (deterministische Logik-Tests + on-demand live-Lauf). Sichtbar, nicht versteckt.
- **D-G15 (Doku-Ort):** **`tests/MARKERS.md`** (NICHT Phasen-Dir — lebende Betriebs-Doku, überlebt `gsd-cleanup`-Archivierung, liegt neben Suite + Marker-Registrierung). Inhalt: Tabelle Test→Marker(live/perf)→Grund + separater Lauf-Befehl (`pytest -m "live or perf"`) + Voraussetzungen (API-Key, erwartbare Flakiness). Die Phasen-Triage-Tabelle (Req-5, einmaliges Arbeits-Protokoll, bleibt im Phasen-Dir) VERLINKT `tests/MARKERS.md`.

### Teil d — Schema-Ableitung (Req-9), Naht zu Teil a

- **D-G16 (Katalog-Quelle + FK-Order):** **pg_catalog topo-Sort aus `pg_constraint`** (contype='f') — FK-Kanten lesen → topologischer Sort (Kind-vor-Eltern) EINMAL bei Session-Start, wiederverwendet. Liefert Tabellen-Liste UND reverse-FK-Lösch-Order aus EINER Wahrheit. (information_schema + kuratierte Order verworfen — verfehlt Req-9 für den Order-Teil.)
  - **Bau-Wachpunkt 1 (Zyklen):** self-ref FK (parent_id auf eigene Tabelle) + mutual FK → topo-Sort würde hängen. Lösung: DELETE-in-Schleife bis Row-Count stabil ODER bekannte Zyklus-Kanten ignorieren. Im Plan via pg_constraint benennen, welche NERVE-Tabellen self-ref/mutual sind.
  - **Bau-Wachpunkt 2 (CASCADE):** `ON DELETE CASCADE` nutzen wo vorhanden (intent_event→calls, transcript_segments→conversation_logs) → Löschen der Eltern-Leak-Row räumt CASCADE-Kinder automatisch → reduziert topo-Sort-Aufwand auf RESTRICT/NO-ACTION-FKs. Der id::text-uuid-Cast (10e5d0a) gilt auch hier.
- **D-G17 (Tabellen-Set + Foundation-Register):** **Alle public base-Tabellen minus begründete Denylist.** Default = "watch everything"; jede Exklusion dokumentiert + bewusst (Req-7: nichts still ausgeschlossen) = Foundation-Register. Denylist winzig: `alembic_version` (Migrations-Stand, kein Test-Datum), Views/Matviews. crm.* dynamisch via `pg_tables WHERE schemaname='crm'`. (Implizit-via-id-Spalte verworfen — droppt still, Audit-Schwäche.)
  - **REFINEMENT (Plan + Gemini abwägen):** PK-Spaltenname pro Tabelle AUS DEM KATALOG ableiten, NICHT `id` hardcoden (früherer PGTEST-Befund "SELECT id nimmt id-PK an"; heute alle id-PK, künftige TAXO/Junction-Tabelle evtl. nicht). Falls eine public base-Tabelle keinen bewachbaren PK hat → LOGGEN + in Denylist mit Grund, NIE still droppen.
- **D-G18 (DRY-Quelle):** **Geteiltes, parametrisiertes Python-Ableitungs-Modul** (z.B. `tests/_schema_introspect.py`), parametrisiert auf (DSN/Connection, Schema), liefert (Baseline-Tabellen-Liste, reverse-FK-Order). conftest importiert ihn (nerve_app, schema='public'); deploy.sh ruft ihn via `python -c`/kleines Wrapper-Skript (postgres-peer, schema='crm') für den POST-SUITE-Check. Katalog-Lesen ist rollen-agnostisch. EINE Wahrheit (keine Multi-Source-Drift), UNIT-TESTBAR, bleibender Ratchet.
