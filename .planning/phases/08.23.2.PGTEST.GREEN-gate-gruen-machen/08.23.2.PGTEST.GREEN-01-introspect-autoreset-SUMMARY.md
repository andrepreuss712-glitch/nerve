# Phase 08.23.2.PGTEST.GREEN Plan 01: Schema-Introspect-Modul + Auto-Reset-Waechter Summary

Liefert das geteilte Katalog-Ableitungsmodul (`tests/_schema_introspect.py`) aus pg_constraint topo-Sort (Kahn, CROSS-SCHEMA) und den Auto-Reset gespaltenen Baseline-Waechter in conftest.py, der test-erzeugte Extra-Rows automatisch loescht (laut, attribuiert) und Baseline-Verletzungen hart blockt — ohne Hardcode-Listen.

## Was gebaut wurde

### Task 1: `tests/_schema_introspect.py` (NEU)

Geteiltes, parametrisiertes Python-Modul (D-G18). Oeffentliche API:

- `derive_baseline_tables(conn_or_dsn, schemas=('public',))` — liefert `(baseline_table_list, reverse_fk_delete_order, foundation_register)` aus pg_constraint CROSS-SCHEMA-topo-Sort.
- `primary_key_column(conn_or_cur, table, schema='public')` — PK-Spaltenname aus Katalog (pg_index indisprimary), NICHT 'id' hardcoden.

Kern-Eigenschaften:
- **ALLE FK-Kanten im Sort** (auch CASCADE/confdeltype='c') — kein DoS bei CASCADE->RESTRICT-Ketten (Gemini-Fund #1)
- **CROSS-SCHEMA** via `n.nspname IN %s` Tuple — analog SCHILD-Guard (Fund #8)
- **Kahn-Algorithmus** auf umgekehrtem Graphen, dann umdrehen -> Leaves-vor-Roots (Kind-vor-Eltern)
- **Naming-konsistent schema.table** (kein unqualifizierter `::regclass::text`-Output)
- **Composite-PK-Guard** (Fund #6/#9): `len(pk_cols) != 1` -> foundation_register mit ehrlichem Grund `"composite PK: not auto-delete-eligible AND not snapshot-monitored (known gate gap)"` + `logging.warning`; KEINE falsche Snapshot-sichtbar-Behauptung
- **Denylist** (`alembic_version`, no-PK-Tabellen, composite-PK-Tabellen) — nie still, immer begruendet
- **PROD-FAKT 2026-06-16**: 0 composite-PK-Tabellen in public/crm/training -> Luecke heute leer; Tuple-Key-Umbau deferred (Backlog-999.x)

NERVE-konkrete Cross-Schema-FK-Kante (aus Prod-Katalog 2026-06-16, psql gegen 178.104.82.166): `crm.accounts -> public.tenant_orgs` — diese Kante geht in den Sort -> `crm.accounts` steht VOR `public.tenant_orgs` in der globalen `reverse_fk_delete_order` -> `cleanup_rows` (crm+public) loescht crm zuerst -> keine FK-Violation.

### Task 2: `tests/conftest.py` (MODIFY)

**Neue Imports:** `logging`, `derive_baseline_tables`, `primary_key_column` aus `tests._schema_introspect`.

**Neue Modul-Level-Globals** (einmal bei Session-Start via `_baseline_schema` gefuellt):
- `_DERIVED_FK_ORDER`: globale cross-schema reverse-FK-Loeschorder (crm vor public, Fund #8)
- `_DERIVED_PK_COLS`: `{qualified_table: pk_col_name}` fuer single-PK-Tabellen

**Neue Fixture `_baseline_schema`** (session-scoped):
- Ruft `derive_baseline_tables(conn, schemas=('public','crm','training'))` EINMAL auf
- Fuellt `_DERIVED_FK_ORDER` + `_DERIVED_PK_COLS` als Modul-Level-Cache
- Liefert die katalog-abgeleitete `table_list`

**`_baseline_snapshot` erweitert** (Fund #7 Cache-Fill-Garantie):
- Signatur: `def _baseline_snapshot(_pgtest_base_seed, _baseline_guard_engine, _baseline_schema):`
- `_baseline_schema` als Dependency -> Cache ist garantiert gefuellt VOR erstem cleanup_rows-Aufruf

**`_snapshot_public_tables` ersetzt** (Req-9/D-G17):
- Parametrisiert auf `public_table_list` (katalog-abgeleitet)
- Filtert lokal auf `startswith('public.')` (D-G04/Fund #8 public-only erhalten)
- PK-Spalte aus `_DERIVED_PK_COLS` (kein hardcoded `id`)

**`_baseline_cleanup_guard` AUTO-RESET-SPLIT** (D-G01/D-G02/D-G03):
- `leaked` -> `[BASELINE-AUTO-FIX]` Warnung + DELETE in `engine.begin()` (D-G05 TX-Hygiene)
  Auto-Delete via `{pk_col}::text = ANY(:ids)` (Fund #2 + D-G06 uuid-Cast)
- `missing/mutated` -> sofortiger `pytest.fail` mit nodeid (D-G02 hard-block, kein Re-Insert)
- Loeschorder aus `_DERIVED_FK_ORDER` (Fallback: `_CLEANUP_FK_ORDER` bleibt erhalten)
- Scope: nur public.* (D-G04 erhalten, crm bleibt POST-SUITE in deploy.sh Plan 02)

**`cleanup_rows`** (Signatur unveraendert):
- Liest `_DERIVED_FK_ORDER` als primaere Loeschorder, Fallback `_CLEANUP_FK_ORDER`
- Keine Signatur-Aenderung, keine per-call DB-Query
