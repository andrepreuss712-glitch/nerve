## Funde

- **🔴 #1 BLOCKER (Plan 01 Task 1, topo-Sort) — CASCADE-Kanten weggelassen → Wächter-Crash bei CASCADE-Ketten:** Plan Z.158 fordert „CASCADE-Kinder (confdeltype='c') als Kanten WEGLASSEN". Bei einer Kette A→(CASCADE)→B→(RESTRICT)→C fehlt dem Sortierer die A→B-Kante → A wird evtl. vor C sortiert → Löschen von A cascadet auf B, scheitert weil C noch auf B zeigt (FK-Violation) → Wächter crasht → Tor dauerhaft blockiert (DoS). **FIX:** ALLE FK-Kanten (unabhängig von confdeltype) in den topo-Sort aufnehmen → garantiert Leaves-vor-Roots auch bei CASCADE. CASCADE-Deletes werden dann redundant (Kind schon explizit gelöscht), aber nie fehlerhaft. (Claudian-verifiziert: Plan sagt das wörtlich; Bug latent heute, aktiviert bei künftiger CASCADE-RESTRICT-Kette = TAXO-Risiko.)

- **🟠 #2 HOCH (Plan 01 Task 2, Auto-Delete) — hardcoded `id::text` ignoriert die abgeleitete PK-Spalte:** Task 1 leitet die PK-Spalte aus dem Katalog ab (D-G17 `primary_key_column`), aber das Auto-Delete (Z.34/81) hardcodet `WHERE id::text = ANY(:ids)`. `intent_event` hat PK `event_id` (nicht `id`) — sobald TAXO1 live + ein Test leakt eine intent_event-Zeile → DELETE crasht an „column id does not exist". **FIX:** Auto-Delete nutzt zwingend die in Task 1 abgeleitete PK-Spalte: `DELETE FROM {tbl} WHERE {pk_col}::text = ANY(:ids)`. (Claudian-verifiziert: models.py — intent_event.event_id ist PK; untergräbt Req-9-Zukunftssicherheit.)

- **🟠 #3 HOCH (Plan 01 Task 2, cleanup_rows-Kopplung):** Der Plan stellt das bestehende `cleanup_rows` (von 20+ Tests aufgerufen) auf die dynamische `reverse_fk_order` um. `cleanup_rows` ist aber eine normale Funktion ohne Zugriff auf die session-scoped Fixture → Executor müsste entweder die Signatur ändern (bricht 20+ Aufrufer) ODER `derive_baseline_tables` pro Aufruf gegen die DB laufen lassen (Suite extrem langsam). **FIX:** dynamische `reverse_fk_order` auf Modul-Ebene cachen (globales Dict in conftest, einmal bei Session-Start), ODER `cleanup_rows` behält die hardcoded `_CLEANUP_FK_ORDER` als best-effort-Fallback.
