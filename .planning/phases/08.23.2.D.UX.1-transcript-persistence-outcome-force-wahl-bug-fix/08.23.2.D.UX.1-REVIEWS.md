### Overall Assessment (Across the Set)

**Summary:** A highly structured, well-researched phase plan that correctly identifies the root causes of the 0.65-confidence blind-guessing bug across all layers (DB, Backend, Frontend). The decomposition into database foundation (01), write-path (02), read-path (03), UI rendering (04), and GDPR compliance (05) is logically sound and minimizes blast radius.

**Strengths:**
- **Rigorous GDPR Implementation:** The dual-table architecture (ephemeral user-bound table vs. permanently anonymized training archive with randomized timestamp offsets) is an excellent privacy pattern.
- **Zero-Dependency Testing:** Using Node.js's built-in `node:test` for frontend logic prevents `package.json`/Jest friction in a vanilla JS repo.
- **Pre-Insert Control Flow Audits:** The plan enforces manual cross-layer verification using `inspect.sh` instead of relying on local assumptions, which actively prevents the exact class of bug it aims to fix.
- **Graceful Degradation:** The UI `_decideModalState` and background thread exception handlers (e.g., loud `MISSING-table` markers) are highly defensive.

**Concerns:**
- **[HIGH] Plan 05 crashes on account deletion (Column Assumption):** Plan 05's code attempts to query `ConversationLog.user_id`. However, the plan's own text explicitly states that the deletion path must traverse `calls.conversation_log_id -> conversation_logs.id`. This strongly implies `conversation_logs` does not have a `user_id` column. If true, the `delete_account` endpoint will crash with an `AttributeError`.
- **[HIGH] Plan 04 ignores the `user_corrected` state:** If a user reconnects to a call they have *already* corrected, the payload will likely carry `source: 'user_corrected'`. `_decideModalState` drops this into the `unsicher` fallback state, which will incorrectly prompt the user to re-choose an outcome they already finalized.
- **[MEDIUM] Plan 03 arbitrary sorting on ties:** `learning.py` orders by `ts_ms`. If `ts_ms` resolution is too coarse (e.g., falls back to `0` or multiple segments share the exact same ms), Postgres does not guarantee stable sorting. This could scramble the chronological order of the transcript.

**Suggestions:**
- Replace `ConversationLog.user_id` queries in Plan 05 with a traverse starting from `Call.user_id`.
- Add explicit handling for `data.source === 'user_corrected'` in Plan 04's `_decideModalState`.
- Append `.order_by(TranscriptSegment.id)` as a secondary sort key in Plan 03 to guarantee stable chronology.

**Risk Assessment:** **MEDIUM-HIGH.** The core fix is robust, but the edge cases in account deletion (Plan 05) and reconnect UI state (Plan 04) risk introducing regressions in production workflows if not corrected prior to execution.

### Plan 01 Review
- **Summary:** Creates the `transcript_segments` table and ORM model, securely migrating the database and applying necessary grants for the worker role.
- **Strengths:** Uses raw `op.execute` matching the established codebase DDL style; correctly implements `ON DELETE CASCADE` for future-proof GDPR purges.
- **Concerns:** **[LOW]** Grants `USAGE` on the sequence to `nerve_anon_worker`. If the worker only ever `SELECT`s (as stated in the plan), it does not need sequence usage (which is for `INSERT`/`nextval`).
- **Suggestions:** Remove the `GRANT USAGE` on the sequence from the migration unless `nerve_anon_worker` explicitly writes to `public.transcript_segments`.
- **Risk Assessment: LOW.** The schema is well-defined and matches existing patterns perfectly.

### Plan 02 Review
- **Summary:** Implements the synchronous call-end write-path for transcripts, alongside an asynchronous, anonymized double-write to the training schema.
- **Strengths:** Idempotency guard correctly prevents duplicated rows on re-finalization; `secrets.randbelow(86_400_000)` efficiently neutralizes timestamp correlation attacks.
- **Concerns:** **[MEDIUM]** `_ts_to_ms` falls back to `0` on parse failure. If multiple segments fall back to `0`, their temporal order depends entirely on DB insertion order, which requires Plan 03 to query them safely (see Plan 03 suggestion).
- **Suggestions:** No direct code change needed here, provided the downstream reader (Plan 03) ensures stable sorting via the PK.
- **Risk Assessment: LOW.** The separation of the main request path and the daemon thread is safe and standard Flask practice.

### Plan 03 Review
- **Summary:** Rewires the backend classification read-path to use the database instead of a RAM object, fixes the confidence thresholding, and ensures UI events emit reliably.
- **Strengths:** Properly handles `confidence == 0` (bypasses DB update but still emits to frontend, unblocking the UI); ensures `ai_auto_unsicher` outcomes are persisted for future DPO training.
- **Concerns:**
  - **[MEDIUM]** `.order_by(TranscriptSegment.ts_ms)` lacks a tie-breaker. Postgres sort stability is not guaranteed for identical values.
  - **[LOW]** If `confidence` is exactly `0.0` (float), `if _outcome_conf == 0:` evaluates correctly, but an explicit `0.0` check or `math.isclose` is generally safer for floating-point bounds.
- **Suggestions:** Change the query to `.order_by(TranscriptSegment.ts_ms, TranscriptSegment.id)` to guarantee insertion-order chronological stability.
- **Risk Assessment: MEDIUM.** Logic is sound, but sorting instability could degrade the quality of the transcript passed to Claude.

### Plan 04 Review
- **Summary:** Fixes the frontend modal by centralizing the 4-state logic and enforcing rendering for all confidence levels, validated with built-in Node tests.
- **Strengths:** Extracts logic into a pure function `_decideModalState`, drastically improving testability without Jest; removes the flawed `(outcome || source)` null-guard at all 3 call sites.
- **Concerns:** **[HIGH]** Missing state handling. The `ck_calls_outcome_source` constraint allows `'user_corrected'`. If a user reconnects to a call they already corrected, the UI falls through to `return 'unsicher'` and mistakenly shows the "KI unsicher — bitte wählen" badge again.
- **Suggestions:** Update `_decideModalState` to handle the already-corrected state:
  ```javascript
  if (data.source === 'user_corrected') return 'sicher'; // Or a new state that disables edits
  ```
- **Risk Assessment: HIGH.** Ignoring the `user_corrected` state will cause a poor UX loop on page reloads/reconnects.

### Plan 05 Review
- **Summary:** Resolves the soft-delete GDPR loophole, adding proper audit logging and ensuring cascading deletes work via explicit confirmation.
- **Strengths:** Forces an explicit architectural decision on soft vs. hard deletes rather than silently assuming cascade works; audit-log insertion accurately avoids non-existent schema columns (`event_type`/`payload`).
- **Concerns:** **[HIGH]** Count-retrieval logic assumes `ConversationLog` has a `user_id` column (`db.query(ConversationLog.id).filter(ConversationLog.user_id == g.user.id)`). This appears to contradict the plan's own `calls.conversation_log_id -> conversation_logs.id` traversal language. If `user_id` does not exist on `ConversationLog`, this crashes the settings page.
- **Suggestions:** Traverse from the `Call` model instead:
  ```python
  _conv_ids = [r[0] for r in db.query(Call.conversation_log_id).filter(Call.user_id == g.user.id).all() if r[0] is not None]
  ```
- **Risk Assessment: HIGH.** A crash on the account-deletion endpoint is a critical failure and a potential GDPR-compliance violation if users cannot delete their accounts.
