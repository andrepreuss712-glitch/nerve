## Phase Boundary

Drei Bugs — eine Wurzel fixen damit das D.UX-Outcome-Modal tatsächlich funktioniert.

- **Bug A (Wurzel):** Transcript landet als TXT-Datei in `/opt/nerve/app/logs/`. `conversation_logs`-DB-Tabelle hat KEINE `log_entries`-Spalte. `routes/learning.py` liest `getattr(_conv, 'log_entries', None)` → `None` → `classify()` bekommt leere Liste → Haiku rät blind → 0.65 confidence.
- **Bug B:** `routes/learning.py` Z.97-103: Bei confidence < 0.70 setzt aktueller Code `_outcome_val = None`, `_outcome_source_val = None` — falsch. Haiku-Best-Guess soll gespeichert werden.
- **Bug C:** `static/pip-launcher.js` Z.2955: Defensive-Check `paResult.outcome || paResult.source` rendert kein Modal wenn beide null. Falsche Bedingung für alle Low-Confidence-Fälle.

**Depends on:** Phase 08.23.2.D.UX.0 (Foundation-Phase muss VOR D.UX.1 abgeschlossen sein — enthält training.*-Schema, nerve_anon_worker-Rolle, training.transcript_archive-Tabelle, Test-User-Flag, Backup-Infrastruktur).

### Bug A — Transcript-DB-Persistierung

- **DA-01:** DB-Layout: **Variante 2 — Separate `public.transcript_segments`-Tabelle** (NICHT JSONB-Spalte). Begründung: G/MEET-Architektur-Entscheidung (Architektur-Entscheidung Internes Datenmodell.md): "JSONB für semi-strukturiert und evolutionär, relational für stabil und gequeryt." Transcript-Segments sind stabil + werden gequeryt → relational.

- **DA-02:** Schema für Migration `0008_add_transcript_segments.py`:
  ```sql
  CREATE TABLE public.transcript_segments (
    id               BIGSERIAL PRIMARY KEY,
    conversation_log_id  INTEGER NOT NULL
                         REFERENCES conversation_logs(id) ON DELETE CASCADE,
    ts_ms            INTEGER NOT NULL,         -- ms ab Call-Start, für Reihenfolge
    speaker          TEXT NOT NULL CHECK (speaker IN ('berater','kunde','system')),
    text             TEXT NOT NULL,            -- anonymisierter Text (Pipeline B)
    created_at       TIMESTAMPTZ DEFAULT now()
  );
  CREATE INDEX idx_transcript_segments_conv_ts
    ON public.transcript_segments (conversation_log_id, ts_ms);
  ```
  `ON DELETE CASCADE` erledigt DSGVO-Cascade-Delete auf DB-Ebene.

- **DA-03:** Namespace: `public.*` jetzt. G/MEET Wave 1 zieht `transcript_segments` + alle User-Daten-Tabellen (`calls`, `conversation_logs`, `users`, `profiles`) gemeinsam nach `crm.*` um — single Migration-Step, kein Drift-Risiko.

- **DA-04:** Schreib-Pfad in `services/live_session.py`: Beim Call-Ende — alle gepufferten Segments aus RAM-Variable `ls.conversation_log` in `transcript_segments` INSERT. **Idempotent:** Vor Insert prüfen ob schon Segments für diese `conversation_log_id` existieren (Reentrance-Guard). Anonymisierungs-Pipeline (Phase B) läuft vor Insert — gleicher Stand wie TXT-Datei-Schreibung.

- **DA-05:** Lese-Pfad in `routes/learning.py`: `classify()` ruft jetzt DB statt `getattr(_conv, 'log_entries', ...)`:
  ```python
  segments = db.query(TranscriptSegment).filter(
      TranscriptSegment.conversation_log_id == conv.id
  ).order_by(TranscriptSegment.ts_ms).all()
  _conv_data['log_entries'] = [
      {'ts_ms': s.ts_ms, 'speaker': s.speaker, 'text': s.text}
      for s in segments
  ]
  ```

- **DA-06:** Doppel-Speicherung (Cross-AI Gemini 2026-05-28 Empfehlung — Variante A): Beim Call-Ende wird AUCH in `training.transcript_archive` (in `training.*`-Schema, erstellt durch D.UX.0) geschrieben — **Background-Job**, nicht im Request-Pfad. DPO-Sammler (Phase E) liest ausschließlich aus `training.*`. Keine FK-Referenz in `training.*` zu `calls`/`conversation_logs` (Entkoppelung für Anonymität). `ts_offset_ms` wird per-Call kryptographisch randomisiert (Timestamp-Korrelations-Angriff-Schutz).

### Bug B — Backend Confidence-Logik Fix

- **DB-01:** Neue Schwellenlogik in `routes/learning.py` (Z.94-103 ersetzen):
  ```python
  # Neue Logik (D.UX.1 Bug B Fix):
  if _outcome_conf == 0:
      # Kein Klassifizierungs-Versuch (leeres Transcript / API-Timeout / Exception)
      _outcome_val = None
      _outcome_source_val = None
      print(f'[D.UX.1] classify() confidence=0, reason: check logs')
  elif _outcome_conf < 0.70:
      # Haiku unsicher, trotzdem Best-Guess in DB speichern (für DPO-Training Phase E)
      # outcome_val = Haiku-Best-Guess, NICHT überschreiben mit None
      _outcome_source_val = 'ai_auto_unsicher'
  elif _outcome_conf < 0.90:
      _outcome_source_val = 'ai_auto_unsicher'  # bestehende D.UX-Logik
  else:
      _outcome_source_val = 'ai_auto'           # bestehende D.UX-Logik
  ```
  **Kritische Änderung:** Bei `confidence > 0 and < 0.70` bleibt `_outcome_val = Haiku-Best-Guess` (wird NICHT auf `None` gesetzt). Backend speichert immer den Best-Guess wenn vorhanden — für Trainings-Daten-Qualität in Phase E.

- **DB-02:** Trennung Backend-Speicherung vs. Frontend-Render: Backend speichert Haiku-Best-Guess auch bei niedriger Confidence. Frontend entscheidet via `source`-Wert ob und wie es ihn zeigt (kein Haiku-Highlight bei `ai_auto_unsicher` — Variante B aus D.UX-Discuss).

- **DB-03:** Schwellen-Werte **unverändert beibehalten** (0.90 / 0.70 / <0.70). Empirische Kalibrierung nach 50-100 EA-Calls via SQL-Auswertung von `calls.outcome_confidence`. Trigger für spätere Anpassungs-Phase: >40% aller Calls in `ai_auto_unsicher` → Schwellen zu eng; <5% → zu locker.

- **DB-04:** Telemetrie-Pflicht: Bei `confidence=0` Log-Marker mit Fehler-Typ (`empty_transcript` / `api_timeout` / `parse_error` / `exception`). Founder-Cost-Dashboard bekommt Metrik "Haiku-Failure-Rate" mit Alarm-Schwelle >5%.

### Bug C — Frontend Force-Wahl-Render

- **DC-01:** Neue zentrale Funktion `_decideModalState(data)` in `pip-launcher.js` (statt zwei separate Code-Pfade für Socket + Response-Handler). Beide Handler (Socket `outcome_ready` + `postcall_analysis`-Response) rufen diese Funktion auf.

- **DC-02:** 4-Zustände-Render-Logik:

  | Zustand | Bedingung | Modal-Verhalten |
  |---------|-----------|-----------------|
  | **1 — Kein Versuch** | `confidence === 0` | Modal MIT 7 Knöpfen, kein Badge, Text "Automatische Erkennung nicht verfügbar", Confirm ausgegraut |
  | **2 — Sicher** | `source === 'ai_auto'` | Modal mit Vorauswahl (teal), Confirm-Button direkt klickbar |
  | **3 — Unsicher** | `source === 'ai_auto_unsicher'` | Modal OHNE Haiku-Highlight, Badge "KI unsicher — bitte wählen", 7 Knöpfe gleichwertig, Confirm ausgegraut |
  | **4 — Defensiv** | `outcome === null && confidence > 0` | Wie Zustand 3 + `console.warn('[D.UX.1] Inconsistent state', ...)` (kein UI-Element) |

  **Wichtig:** Zustand 1 zeigt jetzt auch Modal (Selbst-Korrektur während Discuss: D.UX-Direktive "Outcome-Pflicht-Schritt vor Score" gilt auch bei confidence=0). Kein "kein Modal"-Fall mehr.

- **DC-03:** Zustand 4 wird explizit als "should not happen — defensive guard" kommentiert im Code. Kein Toast/UI-Element — nur Backend-Bug-Logger via `console.warn`.

- **DC-04:** Unit-Tests für alle 4 Zustände (Jest oder vergleichbar).

### DSGVO + Cascade-Delete

- **DD-01:** ON DELETE CASCADE auf `transcript_segments.conversation_log_id` FK (bereits in DA-02 Schicht 1 — DB-Level-Schutz auch wenn App-Code Audit-Log vergisst).

- **DD-02:** App-Level-Audit-Log (Schicht 2): Lösch-Endpoint (`routes/profile.py` oder `routes/settings.py` "Account löschen"-Funktion) schreibt VOR Cascade-Delete:
  ```sql
  INSERT INTO audit_log (user_id, event_type, payload, created_at)
  VALUES (<user_id>, 'user_deletion_request',
          json_build_object(
            'transcript_segments_count', <count>,
            'calls_count', <count>,
            'profiles_count', <count>,
            'conversation_logs_count', <count>,
            'initiator', 'user_self_request'
          ), NOW());
  ```
  Audit-Log enthält KEINE Klartext-User-Daten (nur Counts + IDs). `audit_log`-Tabelle existiert bereits in Production.

- **DD-03:** Aufbewahrungsfrist `public.transcript_segments`: 90 Tage Frist ('ephemeral'), User-Opt-in zu 'consented_full' möglich (analog bestehende DSGVO-Architektur). `training.transcript_archive` (D.UX.0): dauerhaft (Entkoppelt von User-Identität, kein FK, kryptographisch anonymisiert).

- **DD-04:** `04 Entscheidungen/NERVE DSGVO Analyse.md` Sektion 7 (Anonymisierungs-Pipeline) erweitern um DB-Persistenz, Zwei-Tabellen-Architektur, Cascade-Delete-Pfad, Aufbewahrungsfristen und Art. 17 + Art. 5 Abs. 2 Rechenschaftspflicht.

<specifics>
## Specific Ideas

- **Trennung Backend-Speicherung vs. Frontend-Render:** Backend speichert IMMER Haiku-Best-Guess (auch bei niedriger Confidence) — für DPO-Trainings-Daten. Frontend entscheidet unabhängig davon wie es rendert (Variante B aus D.UX: kein Haiku-Highlight bei `ai_auto_unsicher`).
- **Doppel-Speicherung (Cross-AI Gemini 2026-05-28 Variante A):** `public.transcript_segments` mit FK (90 Tage, User-gebunden) + `training.transcript_archive` (kein FK, kryptographisch anonymisiert, dauerhaft, ts_offset_ms randomisiert).
- **Timestamp-Korrelations-Angriff-Schutz:** `training.transcript_archive` bekommt `ts_offset_ms` mit per-Call kryptographischem Random-Offset — verhindert Rückkorrelation via `ts_ms + calls.started_at` (Gemini-Cross-AI-Befund 2026-05-28).
- **Telemetrie "Haiku-Failure-Rate":** Metrik im Founder-Cost-Dashboard, Alarm >5%, Aufschlüsselung nach Typ (empty/timeout/parse/exception).
- **Zukünftige Schwellen-Kalibrierung:** Nach 50-100 EA-Calls SQL-Auswertung von `calls.outcome_confidence`-Verteilung. Trigger: >40% in `ai_auto_unsicher` → zu eng; <5% → zu locker.

</specifics>
