## Was gebaut wurde (CI-4)

Zwei Teile in `services/slow_lane.py`:

1. **Defensiver Backstop in `_persist_event_ref`** (Abstain-Zweig): vor `db.add(AbstainLog(...))` wird
   der Tenant via `_tenant_id_for(ev, db)` ermittelt. Ist er `None` (kein call_id / kein calls.tenant_id) →
   **`ev.handling_status = 'failed'`** (TERMINAL, aus der pending-Arbeitsliste raus; F-01: H-3 re-queued nur
   `'pending'`) + **LAUTER `[CALLID-ALARM]`-Log** + `return` — **KEIN abstain_log-INSERT** (der würde gegen
   FORCE RLS fail-closed scheitern → rollback → `'pending'` → H-3-Endlos). Nur der Abstain-Zweig betroffen;
   scored/Tor-1-failed/Poison-failed unverändert. Der Tenant wird einmal ermittelt und im erfolgreichen
   Abstain-Pfad als `tenant_id=_bk_tenant` wiederverwendet.
2. **`flush_to_db` A1-`set_current_tenant`-Klammer** (PRO ITEM, symmetrisch zum Consumer-Loop): statt
   einem Sammel-Commit ohne GUC jetzt pro gedraintem Item → separate Read-Session →
   `_tenant_id_for_item(it, _read_db)` → close → `set_current_tenant(str(_tid))` (falls nicht None) →
   Schreib-Session → `_persist_event_ref` + commit → `clear_current_tenant()` im finally + close.
   **Per-Item-TX** (kein Sammel-Commit über Tenant-Grenzen) + **Per-Item-Fehler-Isolierung mit
   EXPLIZITEM Log** (`[SLOW] flush_to_db item-Fehler ... — übersprungen, Flush läuft weiter`,
   Gemini-Review-Fund 3 — kein stilles `except: pass`). Damit ist `flush_to_db` symmetrisch zum
   Consumer-Loop → kein fail-closed-Verlust beim SIGTERM/atexit-Flush bei gültiger call_id.
