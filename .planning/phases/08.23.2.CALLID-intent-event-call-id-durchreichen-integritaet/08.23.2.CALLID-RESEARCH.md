## 2. call_id IST verfügbar — per-SID-Zustand

`create_call_for_sid` (`services/live_session.py:529`) legt die UUID in `_session_state[sid]['state']['call_id']` ab:

- `:580-583` DB-INSERT calls + commit → `cid = str(call.id)`.

**KEIN Getter existiert.** Alle Leser inlinen `_session_state.get(sid,{}).get('state',{}).get('call_id')` (live_session.py:546, deepgram_service.py:707/:1017). → **Neuer Helfer `resolve_call_id_for_sid(sid)` nötig**, der die durable UUID liefert und `None`/`'__call_pending__'` als „nicht durable" behandelt (NIEMALS den Sentinel-String durchreichen — sonst landet `'__call_pending__'` in einer UUID-Spalte → Writer-try/except → -1).

## 3. Die Race (CI-2-Kern) — am echten Code belegt

**Start-Sequenz `handle_start_live_session` (`services/deepgram_service.py:519`):**
1. `:539` `mode` per-SID gesetzt.
2. `:570` `_keyterms` (Mini-Profil-Load).
3. **`:572` `_open_deepgram_connection(_sid, ...)` ← ab hier kann on_message (Transkript→Detection→emit) feuern.**
4. `:646` `init_session_state` (seedet `state['call_id']=None`).
5. `:662-694` anonymizer / profile / cache.
6. **`:712` `create_call_for_sid` ← call_id erst HIER durable (nach DB-INSERT+commit, :584-586).**

Detection-Pfad: `@sio.on('audio_chunk')` (`:747`) → Deepgram → `on_message` (`:49`, **eigener Callback-Thread**). Quell-Kommentar `:51-52` dokumentiert die Race explizit: „SID may not be in `_per_sid_profile` yet if Deepgram fires before handle_start_live_session completes DB load (race window)."

**Befund:** Die Verbindung (= Detection-Freischaltung) öffnet bei `:572`, die call_id wird erst ~`:712`+ durable. Das Fenster umspannt den GESAMTEN per-SID-Init-Block (mehrere DB-Queries). **Detection KANN vor durable call_id feuern** → der defensive Backstop allein genügt nicht (würde den ersten Einwand verlieren), das Ordering-Gate (CI-2) ist nötig.

**Mechanik-Optionen für den Plan (research_first in Plan 02 entscheidet):**
- **(bevorzugt, schlank) Reorder:** `init_session_state` + `create_call_for_sid` VOR `_open_deepgram_connection` ziehen → call_id durable BEVOR die Verbindung steht → harte sequenzielle Garantie, kein Puffer. Risiko: Vorwärts-Abhängigkeiten im Init-Block (research_first muss belegen, dass `_open_deepgram_connection`/keyterms nichts brauchen, was init_session_state erst danach setzt — `mode` ist bei :539 schon gesetzt, keyterms bei :570 eigenständig geladen).
- **(Fallback) Per-SID-Puffer:** frühe Emits pro sid puffern (RAM-Queue im emit-Pfad), flushen sobald `resolve_call_id_for_sid` durable liefert. Call-Anlage bleibt Single-Owner in start_live_session. Mehr Mechanik (Buffer + Flush-Trigger), nur falls Reorder unsicher.

Beide Varianten: Call-Anlage NIE aus dem Detection-Thread. Latenz: Start-Pfad, nicht Live-Antwort-Bahn (Punkt 25 ✓).

## 5. flush_to_db — zweiter ungesicherter Schreibpfad (CI-4)

`flush_to_db` (`services/slow_lane.py:328`) drained die Queue + ruft `_persist_event_ref` (kann `abstain_log` INSERT) + EIN `db.commit()` — **OHNE `set_current_tenant`**. Asymmetrie zum Consumer-Loop (`:399` setzt GUC). → Beim SIGTERM/atexit-Flush wird ein abstain_log-INSERT auch bei gültiger call_id fail-closed abgewiesen. **Dieselbe A1-`set_current_tenant`-Klammer wie der Consumer-Loop nachrüsten** (Per-Item-Tenant ermitteln → set → write → clear im finally). Da flush_to_db mehrere Items in EINER TX committet: entweder per-Item-TX (wie Consumer) ODER pro-Item gruppiert. Plan 03 entscheidet die saubere Form (bevorzugt: pro-Item dieselbe Klammer wie der Consumer, kein Sammel-Commit über Tenant-Grenzen).
