# Phase 08.23.2.B: Code Review Report

**Reviewed:** 2026-05-13
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

This phase introduces the DSGVO anonymization pipeline (Art-9 filter → Regex PII → spaCy NER) and wires it into the Deepgram transcript path (INPUT) and Claude/EWB output path (OUTPUT). The pipeline architecture is sound — the ordering guarantee (Art-9 first), the token-cache lifecycle, the ghost-SID guard, and the D-08 health/error-rate design are all correctly implemented.

Two critical issues stand out: (1) a double-counting bug that makes the error-rate circuit breaker trip at half the configured threshold, and (2) `NameError` crashes for undefined variables `market` and `language` in `deepgram_service.py` that will prevent any session from initializing. Five warnings cover DSGVO-relevant concerns (ART9_REDACTED sentinel persisting to `ObjectionEvent.antwort_text`, `_apply_regex_filter` iterator/mutation bug silently losing matches, `_register_error` and `_record_snippet_error` both modifying the same list, missing `init_anonymisierer()` call in session-start path, and a thread-safety gap in `anonymize_output`). Four info items cover test and code quality concerns.

## Critical Issues

### CR-01: `NameError` — `market` and `language` are undefined in `handle_start_live_session`

**File:** `services/deepgram_service.py:443-444`

**Issue:** `init_session_state()` is called with `market=market` and `language=language`, but neither variable is defined anywhere in `handle_start_live_session`. They are not extracted from `data` and not defined as module-level constants. Every `start_live_session` socket event will crash with `NameError: name 'market' is not defined`, aborting the per-SID state init inside the bare `except Exception as _pe` handler. The session continues (Deepgram connection already opened before this block) but no `_session_state` entry is created — meaning `get_anonymisierer()` returns `None` for all subsequent transcripts, the anonymizer never runs, and raw PII flows into `conversation_log`.

**Fix:**
```python
# Extract from data payload, with safe defaults
market   = (data or {}).get('market', 'dach') if isinstance(data, dict) else 'dach'
language = (data or {}).get('language', 'de')  if isinstance(data, dict) else 'de'
# Then call init_session_state(..., market=market, language=language, ...)
```
Add these two lines before the DB-load try-block (e.g. after line 412 `user_id = flask_session.get('user_id')`).

### CR-02: Double-counting in error-rate — `_register_error()` and `_record_snippet_error()` both append to `_error_timestamps`

**File:** `services/anonymization.py:291-316`

**Issue:** In each `except` block inside `anonymize()` (lines 291-292, 300-301, 315-316), BOTH `_register_error()` AND `_record_snippet_error()` are called sequentially. Both functions append to the same `_error_timestamps` list under `_error_lock`. The net effect is that every single anonymization error records **two** timestamps, so the rolling-error circuit breaker (threshold 5 by default) trips after only **3** actual errors instead of 5. For production this means the pipeline will be declared "degraded" or "unavailable" at half the intended tolerance.

`_register_error()` (line 242) also sets `is_pipeline_healthy = False` when threshold is exceeded; `_record_snippet_error()` (line 369) does the same append-and-prune but does NOT set `is_pipeline_healthy`. Since both are called together, the double-append is the only observable difference — the `is_pipeline_healthy` mutation only happens in `_register_error()`.

**Fix:** Remove the duplicate calls. Keep only `_register_error()` in every `except` block — it already does the full append-prune-threshold-check. Delete the three `_record_snippet_error()` calls in the `anonymize()` body entirely, and consider deprecating or deleting `_record_snippet_error()` as it is now unreachable dead code.

```python
# BEFORE (lines 291-292, 300-301, 315-316):
        _register_error()
        _record_snippet_error()   # D-08 Kat. C: Rolling-Error-Counter

# AFTER: one call only
        _register_error()
```

### WR-01: DSGVO — `anonymize_output()` not called on `ObjectionEvent.antwort_text` in all code paths; EWB manual path is correct but the analyse-loop path is not wired

**File:** `services/deepgram_service.py:591-601` / `routes/app_routes.py:277-280`

The concern is the analyse-loop path: if Claude's analyse result produces `einwand_zitat` or `gegenargument_1/2` text that gets written to `ObjectionEvent.antwort_text` via a different code path, those are not yet anonymized. Looking at the current wiring: the analyse-loop path does NOT currently write `ObjectionEvent` rows directly (only the EWB click path does). The keyword-match auto-variant path (lines 167-179 in deepgram_service.py via `streame_auto_variante`) does NOT call `anonymize_output()` on the streamed result before it is displayed and potentially logged. This is an incomplete output-path wiring.

**Fix:** Ensure `anonymize_output()` is called on any AI-generated text that flows into client-visible output or persistent storage, including the auto-variant streamed result in `streame_auto_variante`. Audit `claude_service.py` for all emission points.

### WR-02: `_apply_regex_filter` mutates `text` while iterating over the original — partial-match overlap bug

**File:** `services/anonymization.py:136-193`

**Issue:** The regex filter pattern is:
```python
for m in _RE_IBAN.finditer(text):
    iban_val = m.group()
    ...
    text = text.replace(iban_val, token)
```
`finditer(text)` is called once on the original string, capturing match objects with character offsets. Then `text = text.replace(...)` creates a new string. The iterator still references the old string via the pre-computed match objects, so if the same IBAN appears twice, the second iteration replaces the remaining occurrence correctly — this part is fine.

However, the **phone number** path (line 155) calls `_parse_phone_de(text)` on the *already-mutated* `text` (potentially with IBAN/email tokens inserted). This is intentional. But for the **Steuernummer** regex `_RE_STEUERNR = re.compile(r'\b\d{2,3}[\s/]\d{3}[\s/]\d{4,5}\b')`, the pattern can match substrings of an **IBAN token character sequence** like `[IBAN_A]` — specifically the digits in `DE89 3704 0044 0532 013000`. After IBAN substitution this is gone, but consider a case where the token itself (e.g. `[IBAN_AA]` when counter > 26) happens to contain digit sequences. More concretely: the IBAN raw string `DE89370400440532013000` could match `_RE_STEUERNR` (e.g. `890 370 04405`) if the IBAN replacement hasn't happened yet — but it has since IBAN runs first. The real bug risk is that `_parse_phone_de` runs AFTER IBAN/email tokens are inserted, and its regex fallback `(?:\+49|0049|0)\s*\d{2,5}[\s/\-]?\d{3,}[\s\d]{0,10}` could produce overlapping matches in the token-replaced text. This is a low-probability correctness issue but worth documenting.

A larger practical concern: `text.replace(iban_val, token)` does a **global** replace — if the same IBAN string somehow appears in two different places in the text, both are replaced correctly. But if two different entities share a common substring, the later `replace()` call for the shorter one can clobber the already-placed longer token. For phone numbers, `_parse_phone_de` returns substrings that may overlap with already-tokenized text.

**Fix:** Either (a) switch to the same offset-based replacement approach used in `_apply_ner()` (collect all spans, sort descending, replace from end), or (b) add a post-pass check that no original PII string remains in the output. Minimum fix: call `_parse_phone_de` on the **original** `text` before any mutation, not on the evolving `text`.

### WR-03: `init_anonymisierer()` is never called in the session-start path — anonymizer is always `None`

**File:** `services/deepgram_service.py` / `services/live_session.py:276-287`

**Issue:** `init_session_state()` sets `_session_state[sid]['anonymisierer'] = None` (live_session.py line 386). `init_anonymisierer()` must be called explicitly after `init_session_state()` to create the `AnrufAnonymisierer` instance. Searching `deepgram_service.py` and `app_routes.py`: there is no call to `init_anonymisierer()` anywhere in `handle_start_live_session` or any other reachable session-start code path.

The test `test_cache_lifecycle_init_get_pop` (test_anonymization_wiring.py line 141-155) explicitly calls `init_anonymisierer(test_sid)` manually, correctly testing the lifecycle. But in production, `get_anonymisierer(sid)` will always return `None` because `init_anonymisierer()` is never called by the runtime. The `anonymize()` call in `deepgram_service.py` (line 83) passes `_anon_cache = ls.get_anonymisierer(sid)` which is always `None`, meaning: (a) no stable per-call token mapping, (b) NER results use anonymous `[PERSON_X]` tokens without mapping-persistence, (c) `register_briefing_pii()` is never populated into a real cache.

**Fix:** Add `ls.init_anonymisierer(_sid)` immediately after `ls.init_session_state(...)` in `handle_start_live_session` (after line 446 in deepgram_service.py). Also add `register_briefing_pii` call if briefing data is available.

```python
ls.init_session_state(_sid, user_id=user_id, ...)
ls.init_anonymisierer(_sid)   # D-06: create AnrufAnonymisierer for this SID
# If briefing is set, pre-populate cache with briefing PII:
if precall_briefing:
    _anon = ls.get_anonymisierer(_sid)
    if _anon:
        from services.anonymization import register_briefing_pii
        register_briefing_pii({'personen': [...], 'firmenname': ...}, _anon)
```

### WR-04: `anonymize_output()` accesses `cache._lock` and `cache.mapping` outside the lock — TOCTOU window

**File:** `services/anonymization.py:332-337`

**Issue:**
```python
def anonymize_output(text: str, cache: Optional[AnrufAnonymisierer]) -> str:
    ...
    with cache._lock:
        items = sorted(cache.mapping.items(), key=lambda x: len(x[0]), reverse=True)
    for original, token in items:
        if original in text:
            text = text.replace(original, token)
    return text
```
The lock is held only for the snapshot (`items = sorted(...)`). The replacement loop runs outside the lock. This is correct design — reading a snapshot and then operating on it is safe. However, the snapshot-under-lock is correct only if `cache.mapping` values (token strings) are stable after assignment. They are (tokens are write-once: once assigned in `get_or_assign_token`, the same key is never reassigned). This pattern is safe as written.

The actual issue: if `cache._lock` is acquired by another thread in `get_or_assign_token` while `anonymize_output` iterates over `items` (outside the lock), a new mapping entry added concurrently after the snapshot will be silently missed for this output pass. For a Deepgram `on_message` callback running in one thread while a briefing-load completes in another thread, this is a real race: a name registered via `register_briefing_pii` after the snapshot is taken will not be substituted in the current output. For the current single-session-single-SID use case this is low risk, but worth noting.

**Fix:** Document the known limitation explicitly. If strict consistency is required, take the snapshot and run the replacement within the same lock scope — but this trades a potential micro-deadlock (long string replacement under lock) for the TOCTOU risk. Acceptable as-is for the current scale.

### WR-05: `anon_text == '[ART9_REDACTED]'` sentinel check in `deepgram_service.py` does not also guard the `_merge_pending` queue

**File:** `services/deepgram_service.py:86-98`

**Issue:** When `anonymize()` returns `('[ART9_REDACTED]', 'C')`, the code correctly skips `conversation_log.append()`. However, the raw `text` (containing Art-9 content) has already been:
1. Printed to stdout: `print(f"[DG] [{sp_label}] {text}")` (line 71)
2. Emitted via SocketIO to the browser: `sio.emit('transcript', {'type': 'final', 'text': text, ...}, room=sid)` (line 72-74)
3. Queued into `_merge_pending` for flushing to the analysis buffers (lines 118-136)

The `_merge_pending` flush (via `_flush_segment`) writes to `_per_sid_transcript` (the analyse-loop input) and `_per_sid_coaching_buffer` (the coaching-loop input) using the raw `text` — **not the anonymized text**. This means Art-9 content flows into the Claude analysis context even though the conversation_log insert is blocked.

The SocketIO emit of raw `text` to the browser is a separate DSGVO concern (the browser tab displays the raw transcript for the advisor to see — this may be intentional by design for the live coaching UX, but should be a documented decision).

**Fix:** The anonymize call should happen **before** the SocketIO emit and the merge-queue insertion, or the Art-9-redacted text should be used in the merge queue. At minimum, `_flush_segment` should receive the anonymized text when available:

```python
# After anonymize() call, use anon_text for all downstream paths:
_text_for_analysis = _anon_text if (_anon_text not in ('[ART9_REDACTED]', '[ANON_FEHLER]')) else None

# In merge pending (use _text_for_analysis or skip):
if _text_for_analysis is not None:
    ls._merge_pending[key]['texts'].append(_text_for_analysis)
```

This requires refactoring the `on_message` handler to compute the anonymized text before the merge-queue insertion.

### IN-01: Art-9 keyword list missing common German dialectal/variant forms

**File:** `services/art9_keywords.py:11-76`

**Issue:** The keyword `'bipolaar'` (line 28) appears to be a typo — it should be `'bipolaar'` or `'bipolar'`. Both `'bipolar'` and `'bipolaar'` are listed (lines 28-29), suggesting a copy-paste error where the incorrect spelling was kept alongside the correct one. This is harmless (both will match) but visually confusing.

Also: the keyword `'tarif'` (line 43 under Gewerkschaft) is highly ambiguous — "Tarif" is commonly used in B2B sales contexts ("Das ist nicht im Tarif", "welchen Tarif haben Sie") without any union/labor connotation. This will produce false-positive Art-9 hits for normal pricing discussions, causing those snippets to be discarded as `[ART9_REDACTED]`. Consider requiring contextual co-occurrence (e.g. "Tarifrunde", "Tarifvertrag", "Tarifverhandlung") rather than the bare word "tarif".

**Fix:** Remove `'bipolaar'` (keep `'bipolar'`). Replace bare `'tarif'` with only the compound forms that are already listed (`'tarifvertrag'`, `'tarifverhandlung'`).

### IN-02: `_register_error` sets `is_pipeline_healthy = False` but there is no automatic recovery path

**File:** `services/anonymization.py:242-252`

**Issue:** Once `_register_error()` sets `is_pipeline_healthy = False` via the threshold check (line 252), there is no mechanism to restore it to `True`. The only write-back to `True` is implicit (reset test fixture) or via manual restart. In production, a transient NER error spike (e.g. spaCy hit a large text once, timed out) could permanently disable the pipeline until the process restarts. `get_pipeline_status()` correctly reports `'unavailable'` but has no auto-recovery.

**Fix:** Consider adding a recovery window: if `is_pipeline_healthy == False` but the last error was more than `ROLLING_ERROR_WINDOW_S` ago and `_nlp` is loaded, reset `is_pipeline_healthy = True`. Alternatively, expose a `/api/admin/reset_pipeline_health` endpoint for manual recovery without restart.

### IN-03: `test_anonymization_security.py` uses a shared `AnrufAnonymisierer` cache for all 50 snippets — tokens accumulate, Re-ID difficulty artificially increases

**File:** `tests/test_anonymization_security.py:95-99`

**Issue:**
```python
cache = AnrufAnonymisierer()  # single shared cache for all 50 snippets
for snippet in SNIPPETS:
    result = anonymize(snippet, cache)
```
A single cache means tokens are assigned sequentially across all 50 snippets. By snippet 50, `cache.mapping` has ~100+ entries and tokens like `[PERSON_AA]` instead of `[PERSON_A]`. This makes the anonymized output harder to re-identify than a fresh-cache-per-snippet scenario (which is what production uses via per-SID `AnrufAnonymisierer`). The test is therefore slightly optimistic about Re-ID resistance.

The performance test (`test_anonymization_perf.py:113`) correctly uses a fresh cache per run (`cache = AnrufAnonymisierer()` inside the loop).

**Fix:** Either use a fresh cache per snippet in the security test to match the production model, or document explicitly that the cross-snippet cache is intentional (simulating a full-call scenario). If cross-call re-ID is the threat model, the current approach is correct.

### IN-04: `delete_pretest_data.py` SQL uses raw f-strings in `count_rows()` — table name injection

**File:** `scripts/delete_pretest_data.py:66-73`

**Issue:**
```python
result = conn.execute(text(f'SELECT COUNT(*) FROM {table}'))
```
`table` is sourced from the hardcoded list `tables = ['conversation_logs', ...]` in the same function, so there is no external input path. This is not an exploitable injection in the current code. However, the pattern is unsafe by convention — if the `tables` list were ever refactored to accept external input, this would be injectable. For a one-shot admin script this is acceptable, but worth noting for anyone who extends it.

**Fix:** Use SQLAlchemy's `text()` with bind parameters for COUNT, or use the ORM `func.count()`. As a minimum: add a comment that `table` must always be a hardcoded literal, never user input.
