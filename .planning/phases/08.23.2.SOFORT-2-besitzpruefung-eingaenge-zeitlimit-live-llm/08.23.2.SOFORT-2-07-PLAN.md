## ⚠ DREI FALLEN, an denen dieser Plan haengt

### Falle 1 — Der breite `except Exception` verschluckt den Timeout-Zweig (P-1)

Beide Loops haben heute schon einen per-sid-`try` um **fast den ganzen** Schleifenrumpf, mit
genau einem Handler:
- `analyse_loop`: `except Exception as e: print(f"[Claude-1] SID={sid} Fehler: {e}")`
- `coaching_loop`: `except Exception as e: print(f"[Claude-2] SID={sid} Fehler: {e}")`

**Ein `APITimeoutError` landet dort heute schon** und wird als anonyme Fehlermeldung
ausgedruckt. Wer nur ein `timeout=` setzt (Plan 06) und sonst nichts, bekommt Stufe 1
**geschenkt** — und Stufe 2 **nie**, weil ein Timeout nicht von einem JSON-Parse-Fehler
unterscheidbar ist. **Es saehe funktionierend aus.**

→ Der Zweig gehoert in einen **inneren, engen** `try` **unmittelbar um den LLM-Aufruf**, nicht
in den aeusseren.

### Falle 2 — `APITimeoutError` ist eine UNTERKLASSE von `APIConnectionError` (P-2)

```
anthropic/_exceptions.py:
    class APIConnectionError(APIError): ...
    class APITimeoutError(APIConnectionError):   # ← Unterklasse
```

Steht `except APIConnectionError` **vor** `except APITimeoutError`, ist der Timeout-Zweig
**unerreichbar** und Stufe 1/2 feuern nie — waehrend der statische Waechter aus Plan 05 gruen
bleibt. **Genau die Klasse Fehler, die still gruen aussieht.**

→ `except anthropic.APITimeoutError` steht **immer zuerst**. Der Runtime-Test in Task 4
beweist die Erreichbarkeit.

### Falle 3 — „Runde" ist NICHT „Takt" (P-7)

Beide Loops steigen **vor** dem LLM-Aufruf aus, wenn nichts zu tun ist:
- `analyse_loop`: `if not buf: continue` (plus Pause- und Tot-SID-Ausstiege)
- `coaching_loop`: `if not _sid_cbuf: continue`

Ein Zaehler auf Schleifentakte wuerde Stufe 2 **in einer Gespraechspause** ausloesen — genau der
Alarm, den D-04 vermeiden will.

→ Gezaehlt werden ausschliesslich **LLM-Versuche, die stattfanden und mit einer
Zeitueberschreitung endeten**. Der Zaehler wird nur an zwei Stellen angefasst: `+1` im
`except APITimeoutError`, `= 0` unmittelbar nach einem erfolgreichen Aufruf.

## Drei Entscheidungen, die D-04 ausdruecklich verlangt — hier beantwortet

**(a) Pro `sid` oder global?** → **Pro `sid`.**
Die Loops iterieren sequentiell; ein haengender Fremd-Call blockiert zwar die Reihe, erzeugt aber
fuer die **eigene** `sid` keinen Fehlversuch. Ein globaler Zaehler wuerde dem Berater einen
Ausfall melden, den er nicht hat. Ausserdem: Punkt 28 — pro-Nutzer-Daten gehoeren per-`sid`.

⚠ **Wichtig zu wissen:** `tests/test_no_live_global_state.py` wuerde einen Modul-Global in
`services/claude_service.py` **NICHT** fangen — sein Regex zielt nur auf `ls.<attr> =` und
`ls.state['key'] =`. **Der Waechter waere gruen, und das Gruen waere wahr und wertlos zugleich**
(Punkt 31, wortwoertlich der LOCK-2-Fall). Der Zaehler liegt per-`sid`, **weil es richtig ist —
nicht weil ein Test es erzwingt.** Diese Luecke wird in Task 4 ausdruecklich benannt.

**(b) Setzt ein Erfolg den Zaehler zurueck?** → **Ja** — anders traegt „in Folge" nicht.
Vorbild im selben Code: `sid_state_ref['_bof_count'] = 0` bei einer Frage. Die Ruecksetzung steht
**unmittelbar hinter** dem erfolgreichen Aufruf und **vor** der SID-Lebendigkeitspruefung — sonst
bleibt sie bei einem Abbruch aus.

**(c) Zahlen `classify_phase` und `infer_customer_state` in denselben Zaehler ein?** → **Ja.**
Fuer den Berater ist „die Erkennung setzt aus" **eine** Aussage, nicht drei. Beide werden
innerhalb des `analyse_loop`-Rumpfes gerufen; ihre Timeouts zahlen in denselben per-sid-Zaehler
ein wie der Haupt-Analyse-Aufruf.

⚠ **Der Preis dieser Entscheidung, ausdruecklich benannt:** beide Funktionen **fangen ihre
Ausnahme heute selbst ab** (`try` `:422`/`:505` **vor** `messages.create` `:427`/`:510`, breiter
`except Exception` `:475`/`:558`). Ein Zweig im Loop allein waere deshalb **toter Code** —
gruene Abnahme, kein Verhalten. Entscheidung (c) ist nur eingeloest, wenn Task 1 (c1)
**zusaetzlich** den Durchreiche-Zweig in beiden Funktionen einzieht. Wer (c1) weglaesst, muss
(c) hier zuruecknehmen — nicht beides halb.

**(d) Die Stream-Pfade zaehlen NICHT in Stufe 2.** Sie liegen nicht in den Loops, sondern werden
durch eine Nutzer-Aktion ausgeloest, und sie haben mit `pip_stream_error` bereits einen eigenen
Fehlerkanal. Ihre Timeouts zahlen nur in den **Founder**-Zaehler ein. Begruendung: „die
Erkennung setzt gerade aus" ist eine andere Aussage als „diese eine Antwort ist gescheitert" —
sie zu vermischen macht beide unbrauchbar.

def _timeout_stufen(sid, funktion: str) -> None:
    """Stufe 1 immer, Stufe 2 ab der N-ten Ueberschreitung IN FOLGE fuer diese sid.

    Wird AUSSCHLIESSLICH aus einem Timeout-Ausnahmezweig gerufen — also nur, wenn ein
    LLM-Versuch stattgefunden hat und an der Zeit gescheitert ist.

    print(f"[SOFORT-2] Zeitueberschreitung in {funktion} (sid={sid}) — Runde uebersprungen, kein Retry")
    if not sid:
        return
    with ls._session_state_lock:
        _st = ls._session_state.get(sid)
        if not isinstance(_st, dict):
            return
        _streak = _st.get(_SID_TIMEOUT_KEY, 0) + 1
        _st[_SID_TIMEOUT_KEY] = _streak
    # Emit AUSSERHALB des Riegels (Muster audio_health_warning: SocketIO kann blockieren).
    # Genau BEIM Erreichen der Schwelle, nicht bei jeder weiteren — sonst blinkt es.

            sio.emit('live_llm_timeout_warning', {
                'text': config.LIVE_LLM_TIMEOUT_HINWEIS_TEXT,
                'tip': config.LIVE_LLM_TIMEOUT_HINWEIS_TIP,
            }, room=sid)
        except Exception as _e_emit:
            print(f"[SOFORT-2] Hinweis-Emit fehlgeschlagen (non-fatal): {_e_emit}")


def _timeout_streak_zuruecksetzen(sid) -> None:

        _st = ls._session_state.get(sid)
        if isinstance(_st, dict) and _st.get(_SID_TIMEOUT_KEY):
            _st[_SID_TIMEOUT_KEY] = 0
