<domain>
## Phase Boundary

**Was diese Phase liefert:** Jede DB-Tabelle und jede nicht-triviale Spalte bekommt ein "Schild" — einen Postgres-`COMMENT`, der in Klartext sagt: **Wozu ist die Tabelle da (Business-Logik), lebt sie / ist sie Reserve / ist sie Zombie, und wer liest/schreibt sie (Code-Pfade).** Das Schild lebt im Code (SQLAlchemy `models.py` via `comment=`), Alembic schiebt es per Migration in die DB. Ein pytest-Guard blockt künftig den Deploy, wenn eine Tabelle/Spalte kein Schild hat. Ein `inspect.sh schilder`-Befehl zeigt pro Tabelle Schild + Migrations-Historie. Die Regel §0.2 wird in `salesnerve/CLAUDE.md` verankert, damit jeder künftige Tabellen-Bau das Schild mitzieht.

**Warum (André):** (1) Überblick, (2) Drift reduzieren, (3) Code schneller verstehen. **Kern-Prinzip: Verbindungen müssen IMMER aus unseren Änderungen hervorgehen — kein Raten mehr ob etwas tot oder lebendig ist.** Wenn jede Tabelle selbst-erklärt ist, entfällt das "nicht löschen, weil wir die Verbindungen nicht kennen"; Cleanups gehen schneller, Tabellen-Zusammenlegungen werden sicher. Das ist die Doku-Grundlage **VOR dem TAXO-Bau** (der Zombie-Rename + Konsolidierung macht).

**Diese Phase LÖSCHT/REPARIERT NICHTS am Daten-Modell.** Sie dokumentiert nur. Write-only/Zombie-Funde werden NUR als `[ZOMBIE]`/Status im Schild markiert, NICHT entfernt. Foundation-Tabellen kommen ins `Nerve-Vault/04 Entscheidungen/Foundation-Code-Register.md`.

**Reichweite:** ~44 Tabellen über 3 DB-Schemas — `public` (App), `crm` (accounts/contacts/meetings/account_memory/user_preferences, RLS-isoliert), `training` (preference_pairs + transcript_archive, abgeschottet). 43 davon haben ein ORM-Model in `database/models.py`; **`training.transcript_archive` hat KEIN ORM-Model** (nur raw DDL in Migration 0008) → sein COMMENT muss direkt in die Migration/DDL.

<decisions>
## Implementation Decisions

### Gelockt aus §0.2 (verriegelt 2026-06-09, Gemini-reviewed) — NICHT neu verhandeln

- **L-01: Schild = Postgres-`COMMENT`** auf jeder Tabelle + jeder nicht-trivialen Spalte. Inhalt = NUR Jetzt-Zustand: Zweck (Business-Logik), Status (lebt/Reserve/Zombie), wer liest/schreibt (Code-Pfade). KEINE Historie im Text.
- **L-02: Schild lebt im Code** (`models.py` via `comment=` auf `Column(...)` bzw. `{'comment': ...}` in `__table_args__`), NICHT von Hand in Migrationen geschrieben → Alembic-autogenerate schiebt es in die DB. Code-Definition + DB-Schild = EIN Ort, kein Drift. **Ausnahme:** ORM-lose Tabellen (`training.transcript_archive`) → COMMENT direkt in der Migration via `op.execute("COMMENT ON TABLE ...")`.
- **L-03: KEINE Historie im Schild.** `COMMENT` lässt sich nur überschreiben — ein dateiertes Log darin würde selbst zur Drift-Quelle. Datum + Warum jeder Änderung leben da, wo sie eh datiert entstehen: **Alembic-Migration + Git-Commit.**
- **L-04: Trivial-Spalten per KONVENTION ausnehmen** (nicht per starrer Liste): `id`, `created_at`, `updated_at`, deutsche Varianten `erstellt_am`/`aktualisiert_am`, FK-Spalten (`*_id`), Status-Flags (`is_*` / `aktiv`), UUID-Primärschlüssel. Sonst "schreibt man sich tot".
- **L-05: Automatischer Guard (pytest, blockt Deploy):** scheitert, wenn eine Tabelle / nicht-triviale Spalte KEIN Schild hat ODER das Schild < 10 Zeichen ist (= "tbd"-Blocker). **KEIN FK-im-Text-Abgleich** (brüchig, False-Positives — die DB kennt ihre FKs selbst).
- **L-06: Zombie-Regel:** wird eine Tabelle später Reserve/Zombie → `zombie_`-Vorsilbe + `[ZOMBIE]` im Schild + Code liest sie nicht mehr. (In DIESER Phase wird NICHTS umbenannt — nur Status im Schild markiert.)

### Gelockt aus Gemini-Cross-Check (§G, 09.06.) — Plan-Verschärfungen, in Scope

- **L-07: Guard prüft direkt über `pg_description` auf der DB, ALLE Schemas (public/crm/training)** — NICHT über `models.py`. Grund: ORM-lose Tabellen (transcript_archive) haben kein Model; der Guard muss sie trotzdem fangen. Die DB ist die Wahrheit.
- **L-08: Multi-Schema-Zugriff:** Guard/Test-Connection braucht `search_path` + `USAGE`-Recht auf `crm` + `training`, sonst werden deren Tabellen still übersehen (falsche grüne Sicherheit). Test-Connection-Rolle muss das sehen können.
- **L-09: `Column(comment=)` wird heute NIRGENDS genutzt** (recon-bestätigt: 0 Treffer) → das ist eine **Erst-Einführung**, keine Vervollständigung. Pattern wird neu etabliert.

<specifics>
## Specific Ideas

- **Schild-Inhalt-Formel (aus §0.2):** `"<Zweck/Business-Logik>. Status: <lebt|Reserve|Zombie>. Schreibt <datei.py:zeile/funktion>; liest <datei.py>."` — knackig, aber alle drei Teile drin.
- **Status-Vokabular einheitlich halten:** "lebt", "lebt (TAXO-Umbau-Zone)", "Reserve/Foundation", "[ZOMBIE]" / "write-only". Damit der spätere TAXO-Bau und Audits maschinell + visuell danach filtern können.
- **transcript_archive ist der Sonderfall** — überall mitdenken: kein Model → COMMENT in Migration, und der Guard fängt es NUR weil er über `pg_description` (DB) statt `models.py` prüft (L-07). Das ist der Grund für die Guard-Architektur.
- **Guard ist die Versicherung gegen Drift:** ohne ihn verfällt die Schild-Disziplin beim ersten Termin-Druck. Mit ihm kann kein Deploy durch, der eine Tabelle/Spalte ohne Schild lässt. Das ist der eigentliche langfristige Wert (Anti-Abrieb).
- **inspect.sh schilder** zeigt pro Tabelle BEIDES: aktuelles Schild (`obj_description`/`col_description` aus pg_description) + datierte Änderungs-Historie (welche Migrationen die Tabelle berührt haben) → "wann + warum auf einen Blick" ohne zweites Tagebuch (§0.2 Punkt 4).

</specifics>
