# Cross-AI Plan Review — Phase 08.23.2.SCHILD

## Gemini Review

### 1. Zusammenfassung

Der 6-teilige Plan ist außergewöhnlich gründlich, sicherheitsbewusst und methodisch ausgereift. Discovery-First, ROT→GRÜN-Guard-Beweis, manuelle Migrations-Checkpoints = hohe Engineering-Disziplin. Risiken (DB-Rechte, Alembic-Verhalten, ORM-lose Tabellen) proaktiv adressiert. **Sehr hohes Erfolgspotenzial.**

### 2. Stärken
- **Discovery-First (Plan 01):** größte Unbekannte zuerst geklärt; `DISCOVERY-DECISIONS.md` als Single-Source-of-Truth = exzellent.
- **ROT→GRÜN (Plan 05→04):** Guard zuerst rot sehen, dann durch Migration grün = Goldstandard der Testvalidierung.
- **Robuste Sicherheits-Checkpoints:** manuelle Migrations-Prüfung, Punkt-20-grep-Verifikation, human-verify-Checkpoints.
- **Edge-Cases:** `training.transcript_archive` (ORM-los) + `__table_args__`-Heikligkeiten korrekt adressiert.
- **Logische Wave-Struktur:** entkoppelt, minimiert Risiko pro Welle.

### 3. Bedenken
- **(MEDIUM) Alembic-autogenerate-Workflow komplex** — Plan 04 Task 2. Der Server-Roundtrip (push → `alembic revision` auf Server → `scp` zurück → Server-Temp löschen) ist fehleranfällig (Split-Brain-Risiko). Der Plan nennt `op.execute` selbst den "einfacheren Pfad", und das Projekt nutzt ihn als etabliertes Muster (alle 14 bestehenden Migrationen). autogenerate bringt fürs reine COMMENT-Hinzufügen unnötige Komplexität.
- **(LOW) Migrations-Historie ungenau** — Plan 06 Task 1. `grep -l "$tbl" alembic/versions/*.py` kann False-Positives liefern (Tabellenname als Substring oder nur im Kommentar).
- **(LOW) Manueller Guard-ROT-Deploy** — Plan 05 Acceptance. Separater manueller Lauf erfordert Konzentration; automatisierbarer Ansatz reduziert Fehleranfälligkeit.

### 4. Vorschläge
1. **`op.execute`-Stil priorisieren (Plan 04):** klar als empfohlenen Weg setzen; autogenerate nur als dokumentierte, nicht-empfohlene Alternative.
2. **`grep` für Migrations-Historie präzisieren (Plan 06):** gezielt nach Alembic-Operationen suchen, z.B. `grep -l -E "op\.(create_table|alter_table|drop_table)\(['\"]$tbl['\"]"`.
3. **Optional `pytest.mark.xfail` für den Guard (Plan 05):** Guard mit `@pytest.mark.xfail(reason='Migration 0015 ausstehend')` einchecken → Deploy läuft durch (XFAIL), Plan 04 entfernt den Marker → Test wird PASS. Vermeidet den manuellen Separat-Lauf.

### 5. Risiko-Gesamteinschätzung
**LOW** — ohne Planung hochriskant, mit diesem Plan auf Minimum reduziert. Restrisiko = menschliche Ausführungsfehler, v.a. im komplexen autogenerate-Workflow. Mit Vorschlag 1 (op.execute priorisieren) verschwindend gering. "Vorbild für sichere weitreichende Schema-Änderungen."
