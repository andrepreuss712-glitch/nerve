## (a) DB-Rolle für pg_description-Sichtbarkeit — BEWIESEN

**Frage (L-08):** `nerve_app` hat leeren search_path (db.py) + ist NICHT Owner von crm/training
(models.py:748-754) → sieht es deren `pg_description`-Kommentare überhaupt?

**ANTWORT: JA — `nerve_app` liest die Kommentare aller 3 Schemas OHNE jeden GRANT.**
`obj_description()`/`col_description()` lesen den Catalog `pg_description`, der world-readable ist;
die Sichtbarkeit hängt NICHT an Ownership, USAGE-Grant oder search_path. **Kein Provisioning nötig.**

### Beleg 1 — Catalog-Sicht pro Rolle (verbatim)

TEST A (`sudo -u nerve_app psql -d nerve`, mit `SET search_path TO public, crm, training`):


TEST B (`sudo -u postgres psql -d nerve`):
```

----------+--------+--------------

(3 rows)
```

→ Beide Rollen sehen IDENTISCH alle 45 Tabellen (public 38 + crm 5 + training 2). `with_comment=0`
überall (noch keine Schilder gesetzt — das ist der Vor-Migrations-Zustand, den Plan 05 als ROT beobachtet).

das Catalog-Verhalten je ändert (unwahrscheinlich — Catalog-Read ist Postgres-Grundsemantik):

→ **GEWÄHLT: "nerve_app reicht ohne Grant"** (Beleg 1+2). Plan 05/06 übernehmen das 1:1.

```

  /opt/nerve/venv/bin/pytest /opt/nerve/app/tests/test_schild_guard.py -q
```

**Entscheidung für André am Checkpoint:**
- **(1) Manuell (wie geplant):** Guard läuft server-seitig manuell (RED vor Migration, GREEN danach) — exakt was Plan 04/05 als Acceptance beschreiben. Kein deploy.sh-Edit. **← Default, plan-konform.**

## (b) Migrations-Stil — FESTGELEGT

**`MIGRATION_STYLE: op.execute`** (EMPFOHLENER Default, Cross-AI-Finding 1).

Begründung: Alle 14 Bestands-Migrationen nutzen `op.execute` (etabliertes Hausmuster);
`op.execute("COMMENT ON TABLE/COLUMN ... IS '...'")` ist für reines COMMENT-Hinzufügen perfekt;
der autogenerate-Pfad bräuchte einen fehleranfälligen Server-Round-Trip (push → `alembic revision`
auf dem Server → scp zurück → Server-Temp löschen) mit Split-Brain-Risiko.

**autogenerate = NICHT-empfohlener Fallback** (nur dokumentiert, Split-Brain-Risiko). Plan 04 verzweigt
rein auf `MIGRATION_STYLE` → Default-Branch = op.execute. KEINE Stil-Entscheidung in Plan 04.

- **Migrations-Rolle:** `postgres` (Memory project_nerve_prod_deploy; nerve_app fehlt CREATE auf schema public).
  Relevant für `training.transcript_archive`-COMMENT-DDL + crm/training-Schreibrechte.
- **ALEMBIC_VERSION:** `1.18.4` (server-side `alembic --version`, informativ — op.execute braucht keine Mindest-Version).
- **ALEMBIC_HEAD:** `0014` (`SELECT version_num FROM alembic_version` → Plan 04: `down_revision = '0014'`).

### include_name-Filter (FALLBACK-relevant, NICHT kritisch für op.execute-Default)

`alembic/env.py` hat aktuell KEIN `include_schemas` (Z.36-50, nur `compare_type=True` + `render_as_batch=True`).
Für die op.execute-Migration ist das **irrelevant** (op.execute schreibt rohe COMMENT-DDL, kein metadata-Diff).
NUR falls jemand später autogenerate nutzt, additiv in `context.configure(...)` (Plan 04 darf es additiv setzen,
markiert als nicht-kritisch):

```python
def _include_name(name, type_, parent_names):
    if type_ == "schema":
        return name in {"public", "crm", "training"}  # kein pg_catalog/information_schema
    return True
```
