## 1. Technischer Ansatz pro Scope-Punkt

### (1) `comment=` in `database/models.py`

**Stack:** Flask-SQLAlchemy `db.Model`-Stil über `from database.db import Base`, alle Spalten inline `Column(Type, ..., comment='...')`. KEIN `mapped_column`. SQLAlchemy ≥ 2.0 → `comment=` voll unterstützt. **Heute 0× `comment=` in der ganzen Datei → Erst-Einführung.**

**Tabellen-Kommentar via `__table_args__` — Tuple-Ordnung ist kritisch:**

- **Public-Tabellen (kein Schema-Dict):** trailing Dict als LETZTES Tuple-Element anhängen:
  ```python
  __table_args__ = (
      UniqueConstraint(...),
      Index(...),
      {'comment': 'Schild: ...'},   # neu, muss letztes Element sein
  )
  ```
  Vorsicht bei Tabellen mit nur EINEM Constraint und trailing comma `(UniqueConstraint(...),)` — wird zu `(UniqueConstraint(...), {'comment': ...})`.

- **crm/training-Tabellen (haben schon `{'schema': 'crm'}` als letztes Element):** comment IN das bestehende Schema-Dict mergen (bleibt letztes Element):
  ```python
  __table_args__ = (
      CheckConstraint(...),
      Index(...),
      {'schema': 'crm', 'comment': 'Schild: ...'},
  )
  ```

- **Spalten-Kommentar:** `name = Column(String(200), nullable=False, comment='Schild: ...')` — einzelner Param, additiv, ungefährlich.

**Trivial-Spalten-Konvention (L-04, NICHT kommentieren):** `id`, `created_at`, `updated_at`, `erstellt_am`, `aktualisiert_am`, `*_id` (FK), `is_*`/`aktiv` (Status-Flags), UUID-PKs.

## 3. Risiken / Landminen

- **`__table_args__`-Bruch:** falsche Tuple-Ordnung (Dict nicht letztes Element) oder Überschreiben eines bestehenden Schema-Dicts → SQLAlchemy-Registrierungsfehler. Pro Tabelle das bestehende `__table_args__` lesen, dann additiv ergänzen (Punkt 14 Control-Flow gilt analog für Schema-Edits).
- **`include_schemas=True`-Nebenwirkung:** autogenerate könnte fremde Schemas/Objekte aufnehmen → unbeabsichtigte Drop/Create in der Migration. Migration nach autogenerate HÄNDISCH prüfen (nur COMMENTs, keine Struktur-Diffs). Gegen Production-Schema verifizieren.
- **SQLite-Test-Falle:** Wer den Guard versehentlich an die SQLite-Fixture hängt, bekommt einen False-Green oder Crash (kein pg_description). Guard MUSS Postgres-Fixture + Skip-ohne-DSN nutzen.
- **RLS/USAGE-Blindheit (L-08):** sieht die Guard-/inspect-Rolle crm+training-`pg_description` nicht, werden deren fehlende Schilder still übersehen (falsche grüne Sicherheit) — exakt der Fehler, vor dem Gemini warnt. Rolle/Rechte vor Festlegung gegen Production prüfen.
- **Status-Drift im Schild:** §G-Entwürfe sind vom 09.06.; Code kann sich geändert haben. Punkt 20 ist Pflicht, nicht Kür (Agent + Gemini lagen je 1× daneben).
