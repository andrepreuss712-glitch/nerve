# Cross-AI Plan Review — Phase 08.20

## Gemini Review

Hier ist das strukturierte Cross-AI-Review für Phase 08.20.

### 1. Summary

Der Plan für Phase 08.20 integriert das vollständige Profil-Kontext-Fenster in alle LLM-Pfade und liefert essenzielles PreCall-Steering sowie den Wechsel auf Sonnet für EWB. Die Caching-Struktur mit 9 fixen Sektionen ist strategisch richtig. Dennoch gibt es erhebliche Architektur-Risiken bei Memory Leaks (SID Lifecycle), Deadlocks durch verschachtelte Locks und N+1 DB-Queries im hochfrequenten Streaming-Pfad. Ohne Fixes vor der Umsetzung drohen im Live-Betrieb Server-Crashes und starke Performance-Einbrüche.

### 2. Strengths

- **Caching-Strategie:** Die Architektur mit 9 festen Sektionen (Sektion 1-7 stabil, Sektion 8-9 volatil am Ende) maximiert die Anthropic Prompt Caching Hit-Rate.
- **Schema-Migration:** Die abwärtskompatible v3->v4 Transition in `profile_schema.py` mit deterministischem Fallback ist defensiv und sicher.
- **Circuit-Breaker:** Gute Resilienz-Logik. Fallback auf Haiku bei Sonnet-Latenz-Spikes schützt die Live-Experience im Call.
- **Branchen-Steering:** Deterministische, I/O-freie Logik für Branchen-Hints bringt fachlichen Wert ohne Performance-Penalty.

### 3. Concerns

- **HIGH:** Memory Leak in `live_session.py`. Wenn die asynchrone `recherche_firma()` fertig wird *nachdem* der User disconnectet hat, schreibt `set_briefing_for_sid()` in ein leeres State-Dict. Diese Ghost SID wird nie wieder aufgeräumt.
- **HIGH:** Deadlock-Risiko bei `pop_session_state()`. Das sequenzielle Aquiring von `_per_sid_lock` und danach `_per_sid_briefing_lock` führt zwangsläufig zum Deadlock, wenn ein anderer Thread die Locks jemals umgekehrt anfordert.
- **HIGH:** N+1 Queries im Streaming-Pfad. `build_profile_context()` ruft DB-Queries (`ProfileOpener`, User, ProfileFAQ) bei *jedem* Claude Request auf. Das killt den Durchsatz.
- **MEDIUM:** Prompt Injection. Vom User erstellte Inputs (`eigene_formulierungen`) fließen ungefiltert in den System-Prompt. Breakout-Gefahr durch böswillige Orgs.
- **MEDIUM:** Du/Sie False Positives. "Ich sage meinem Chef, du hast recht" triggert das UI-Toast fälschlicherweise. Die reine Zählung von Wortformen hat keinen semantischen Kontext.
- **MEDIUM:** Circuit-Breaker Timer. Messung startet vor dem `.stream()`-Aufruf und inkludiert TCP-Overhead. Die 1500ms fliegen bei Netzschwankungen zu schnell.
- **MEDIUM:** Bootstrap-Kosten-Risiko. Sonnet ist ca. 5x teurer als Haiku. Bei Voll-Profil mit ~1300 Input-Tokens (auch gecached) + Output für jeden EWB-Call schnellen die Kosten in die Höhe.
- **LOW:** Cache-Determinismus gefährdet. DB-Query für `ProfileOpener` in Sektion 2 ohne explizites Sort/Limit kann Reihenfolge variieren und so den Claude-Cache nullifizieren.
- **LOW:** Unvollständige Migration. Wurden Jinja2-Template-Vererbungen und der `training_service.py` bei der Liste der 11 Callsites berücksichtigt?
- **LOW:** Absturz-Risiko im Socket-Handler. Event-Trigger für `vorwissen_level` bevor `_session_state[sid]` voll initialisiert ist, wirft einen KeyError.

### 4. Suggestions

- **Ghost SIDs abfangen:** In `set_briefing_for_sid()` vor dem Schreiben prüfen, ob die SID im aktiven State (z.B. in `_per_sid_profile`) noch existiert. Wenn nicht: Wert sofort droppen.
- **Lock-Komplexität reduzieren:** Kein separates `_per_sid_briefing_lock` einführen. Das Briefing einfach unter dem bestehenden `_per_sid_lock` mitverwalten.
- **In-Memory Profil-Cache:** `ProfileOpener` und alle anderen DB-Objekte *einmalig* bei Session-Start laden. `build_profile_context()` darf nur noch auf den In-Memory-State zugreifen.
- **Circuit-Breaker justieren:** Threshold auf 2000ms erhöhen oder TTFT rein aus dem ersten empfangenen Byte messen.
- **Du/Sie robuster machen:** UI-Toast erst nach deutlicher Aggregation oder durch explizite LLM-Klassifikation im Post-Call.
- **Socket-State sichern:** In allen drei neuen Socket-Handlern `_session_state.setdefault(sid, {})` nutzen oder per `if sid not in ...` sauber abbrechen.
- **Wave 2 Parallelität:** Plan 02 und 03 modifizieren unterschiedliche Dateien — auf Code-Ebene sicher parallelisierbar.
- **Query-Determinismus erzwingen:** Der `ProfileOpener` DB-Aufruf muss immer mit striktem `ORDER BY id LIMIT 1` versehen werden.

### 5. Risk Assessment

**Overall: HIGH**

**Begründung:** Die Pläne enthalten kritische Architekturlücken im Bereich Concurrency und State-Management. Das Memory-Leak durch abgebrochene PreCalls und das Deadlock-Risiko zweier verschachtelter Locks sind tickende Zeitbomben für den Live-Betrieb. Zudem torpedieren DB-Queries bei jedem Claude-Call die Streaming-Latenz (N+1 Problem). Diese Punkte (Ghost SID, Locks, DB-Queries) müssen strikt überarbeitet werden, bevor der Code implementiert wird.

## Consensus Summary

Reviewed by: 1 external AI (Gemini). Claude skipped as self (running inside Claude Code).

### Top Concerns (Action Required Before Execution)

**1. [HIGH] Ghost SID Memory Leak — `set_briefing_for_sid()` race condition**
If `recherche_firma()` completes asynchronously *after* the user disconnects, `set_briefing_for_sid()` writes to a key that was already popped by `pop_session_state()`. The ghost entry persists in `_per_sid_briefing` indefinitely.
→ **Fix in Plan 01:** Add guard in `set_briefing_for_sid()`: if SID not in `_per_sid_profile`, drop the write immediately (or use a write-then-check pattern). Alternatively, add an expiry/TTL.

**2. [HIGH] Deadlock Risk — dual lock acquisition ordering**
`pop_session_state()` acquires `_per_sid_lock` then `_per_sid_briefing_lock` sequentially. If any other code path acquires them in reverse order, deadlock occurs.
→ **Fix in Plan 01:** Either merge briefing storage under the existing `_per_sid_lock` (store briefing inside the same dict as `_per_sid_profile` value, e.g. as a third tuple element), or enforce strict canonical lock ordering everywhere and document it.

**3. [HIGH] N+1 DB Queries inside `build_profile_context()`**
Section 2 (Basis) does a ProfileOpener DB query + User query. Section FAQ does another ProfileFAQ query. This fires on every single Claude streaming call (every EWB request).
→ **Fix in Plan 02:** Cache ProfileOpener + ProfileFAQ at session start (similar to how profile daten is loaded once). Load into `_per_sid_profile` tuple or a separate `_per_sid_profile_extras` dict. `build_profile_context()` reads from memory only, no DB access.

**4. [MEDIUM] `ProfileOpener` ORDER BY missing — cache determinism at risk**
Without `ORDER BY id LIMIT 1`, the DB query could return different rows on different calls, breaking byte-equality of `build_profile_context()` output and invalidating Anthropic cache keys.
→ **Fix in Plan 02:** Add `order_by(ProfileOpener.id).limit(1)` to the ProfileOpener query.

**5. [MEDIUM] Sonnet cost impact — needs ENV rollback path documented**
Sonnet is ~5x Haiku per token. With ~1300 cached input tokens per call, cost per EWB increases substantially. Circuit-breaker helps but only triggers on TTFT SLA breach, not on cost threshold.
→ **Already mitigated:** ENV override `MODEL_PIP_AUTOVAR=claude-haiku-4-5-20251001` is the rollback path. Should be explicitly documented in Plan 04 config.py comment and in HANDOFF.

**6. [LOW] Socket handler `_session_state[sid]` initialization race**
`vorwissen_level` from session-start may arrive before `_session_state[sid]` is initialized.
→ **Fix in Plan 05:** Use `_session_state.setdefault(sid, {})` in all three new SocketIO handlers.

### Agreed Strengths

- 9-section fixed-order cache contract (stable 1-7, volatile 8-9 at end) — correct Anthropic cache pattern
- Schema v3→v4 idempotent migration with transition fallback — safe for existing data
- Circuit-Breaker design (deque maxlen=5, 3/5 threshold, 30s auto-reset) — sound approach
- `branchen_data.py` pure static module — zero runtime risk, immediate value

### Divergent / Open Items

- **Du/Sie detection threshold:** Gemini flags 2-trigger threshold as too low for false-positive safety. Context-window heuristic (checking speaker attribution) would help but adds complexity. Current plan has User-Confirmation Toast as safety net — may be sufficient for pre-launch.
- **Training service coverage:** Plan does not explicitly cover `training_service.py`. If training calls EWB with profile context, it may be a missing callsite. Worth a grep before execution.
- **Circuit-Breaker timer includes TCP:** 1500ms threshold calibrated for wall-clock-before-stream, not pure model TTFT. May need tuning after first production data. ENV-configurable, so acceptable.
