# Code Review — Phase 08.20

## Summary

Phase 08.20 introduces the full-profile EWB/QA pipeline re-wire: `build_profile_context()` now assembles a 9-section Markdown block (Branche, Basis, Zielkunde, Schmerzen, Einwände, Phasen, KI-Verhalten, PreCall-Briefing, Lead-Kontext) consumed by EWB and QA. Schema migration advances from v3 to v4 (`einwaende` → `einwaende_detail`). Branchen-spezifische PreCall-Hints (`services/branchen_data.py`) are injected into the PreCall system prompt. Per-SID Ghost-SID guard prevents async PreCall writes after disconnect.

The pipeline wiring, caching architecture, Ghost-SID guard, and test coverage are solid. One critical boot-migration bug was pre-identified (CR-0820-A): the on-boot batch migration still skips profiles with `schema_version >= 3` instead of `>= 4`, meaning on-demand is the only active v3→v4 path. Two additional warnings were found during code review: a dead `profile_id` parameter in the EWB-Preview API and schema-mismatched onboarding templates. Three info-level items (CSRF localhost gap, stale log strings, wizard `einwaende` path) round out the findings.

## Findings

### CR-0820-A — Schema-Migration Skip-Check Bug: Wrong Version Threshold in app.py

**Severity:** Critical
**File:** `app.py:934`
**Issue:** The on-boot batch migration loop skips profiles where `_version >= 3`, but the current migration target is v3→v4 (Phase 08.20). Profiles already on v3 are the exact profiles that need to be migrated to v4. The `_migrate_profile_data()` function in `services/profile_schema.py` correctly handles v3→v4 (lines 407–462), but it never gets called for these profiles because the skip-guard fires first. Additionally, the print strings at lines 946 and 948 still read `"v2->v3"` and `"bereits auf v3"` — these are misleading regardless of the threshold fix. Note: `LATEST_SCHEMA_VERSION` is NOT currently defined as an exportable constant in `services/profile_schema.py` — the current max version (4) only appears implicitly inside `_migrate_profile_data()`.

**Consequence:** On-boot migration for v3→v4 never fires. Existing v3 profiles are only migrated on demand (via `bearbeiten()` GET in `routes/profiles.py` line 256), meaning any profile that isn't opened in the editor stays on v3 until manually triggered. The v4 fields (`einwaende_detail`) will be empty/absent for these profiles in live and QA paths.

**Fix:**
```python
# app.py ~line 934 — change the skip threshold from 3 to 4:
if _version >= 4:   # was: _version >= 3
    _skipped_count += 1
    continue

# app.py ~lines 946, 948 — update log strings:
print(f"[Schema] Batch-Migration v3->v4: {_migrated_count} Profile migriert, {_skipped_count} uebersprungen")
# ...
print(f"[Schema] Batch-Migration v3->v4: alle {_skipped_count} Profile bereits auf v4")

# Recommended: also add a LATEST_SCHEMA_VERSION constant to services/profile_schema.py:
# LATEST_SCHEMA_VERSION = 4
# Then import it in app.py and use:
# if _version >= LATEST_SCHEMA_VERSION:
```

### WR-0820-D — Onboarding Templates: `einwaende_detail` Items Use `typ` Instead of Required Fields

**Severity:** Warning
**File:** `routes/onboarding.py:13–161`
**Issue:** All `BRANCHE_TEMPLATES` entries define `einwaende_detail` items with a `typ` key (e.g. `{'typ': 'Kosten/Preis', 'einwand': '...', 'gegenargument': '...'}`). The `EinwandDetailSchema` in `services/profile_schema.py` (lines 89–99) does NOT have a `typ` field — it requires `einwand`, `varianten`, `gegenargument`, `technik`, `intensitaet`, `kurzlabel`, `kategorie`, `einwand_typ`. Two consequences: (1) the `typ` key will silently pass through since Pydantic `extra='forbid'` is only on the `ProfileSchema` level (the `onboarding.create_profile_from_template` writes raw `template` JSON without Pydantic validation), (2) the `einwand_typ` field (required by schema, default `'unbekannt'`) is missing from all templates, and the live-path `einwand_typ` display in `build_profile_context()` will render `'unbekannt'` for all onboarding-created profiles. Note: because profiles created via onboarding have `schema_version` from the raw template (which doesn't set it), they will likely be migrated on next access anyway, but the stale `typ` key will remain as a dirty extra field.

**Fix:** Update all template entries in `BRANCHE_TEMPLATES` to match `EinwandDetailSchema`:
```python
# Replace 'typ' with 'kategorie' and add missing required fields:
{
    'einwand': 'Das ist zu teuer',
    'varianten': [],
    'gegenargument': 'Was waere es euch wert wenn ihr damit 10 Stunden pro Woche spart?',
    'technik': '',
    'intensitaet': 3,
    'kurzlabel': 'Preis',
    'kategorie': 'Kosten/Preis',
    'einwand_typ': 'unbekannt',
}
```

### IR-0820-D — `prompt_pipeline.py` KI-Verhalten Block: Reads Non-Existent `wisdom` and `stil` Fields

**Severity:** Info
**File:** `services/prompt_pipeline.py:348`
**Issue:** The `## KI-Verhalten` section iterates over `('ton', 'wisdom', 'stil')` when checking ki fields. `wisdom` and `stil` do not exist in `KiSchema` (which only defines `anrede`, `ansprache`, `ton`, `zusatz`, `antwortlaenge`). `stil` was explicitly migrated into `ton` in v1→v2 (`_migrate_profile_data()` line 289–291). These lookups always return `None` and add no content — they're effectively dead code that could mislead future readers into thinking `ki.wisdom` is a valid field.

```python

for _fld, _label in [('ton', 'Ton'), ('wisdom', 'Wisdom'), ('stil', 'Stil')]:
    _val = ki.get(_fld)

for _fld, _label in [('ton', 'Ton'), ('zusatz', 'Zusatz')]:
    _val = ki.get(_fld)
```

### IR-0820-E — `routes/profiles.py` Wizard: Writes `einwaende` Under `basis.*` (Pre-Migration Shape)

**Severity:** Info
**File:** `routes/profiles.py:138–139`
**Issue:** `wizard_create()` writes `schema_version: 2` with `einwaende` under `basis.einwaende` (line 138: `'basis': {'produktbeschreibung': ..., 'zielkunden': ..., 'einwaende': einwaende_list, 'phasen': []}`). This is the pre-v3 shape. The schema migration (`_migrate_profile_data()`) will eventually upward-merge these to top-level, and v3→v4 will convert to `einwaende_detail`. However, the Pydantic validation at line 157 (`ProfileSchema.model_validate(json.loads(daten))`) will fail because `BasisSchema` has `extra='forbid'` and `basis.einwaende` is no longer a valid field in the v3 schema — `basis` no longer has `einwaende`. This means new wizard-created profiles will consistently trigger a `ValidationError` flash and redirect to the wizard page without saving.

**Fix:** Either (a) write `einwaende_list` at top level and set `schema_version: 3`, or (b) run `_migrate_profile_data()` on the constructed dict before calling `ProfileSchema.model_validate()`:
```python
# Option A — preferred: write directly in v3/v4 shape
daten_dict = {
    'schema_version': 3,
    'basis': {'produktbeschreibung': produkt, 'zielkunden': zielkunden},
    'einwaende': einwaende_list,   # top-level, not under basis
    'phasen': [],
    # ... rest unchanged
}
daten_dict = _migrate_profile_data(daten_dict)   # advances to v4
ProfileSchema.model_validate(daten_dict)
```
