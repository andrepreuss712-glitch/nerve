Rationale: Der Launcher-Modal hat in Step 4 nach PreCall-Ergebnis-Akzeptierung genug Zeit. "Ergebnis übernehmen" führt jetzt zu Step 4b (Vorwissen) → Step 5 (Skript). Wer ohne PreCall startet (Step 1 → Step 5 direkt) bekommt Vorwissen-Picker eingebettet in Step 5 als optionaler Block. Der PiP-Override ist nur ein Read-only-Indicator mit Edit-Funktion für mid-call Korrekturen — kein vollständiger Zweig.

### Interaction Spec

**Launcher Step 4b flow:**
1. User akzeptiert PreCall-Ergebnis (Step 4) → `state.step = '4b'` → `renderStep4b()` wird aufgerufen
2. Default: "Weiß nicht" Pill ist `.active` (pre-selected). User muss nichts tun — direkt "Weiter" klicken ist valide.
3. Klick auf Pill → alle Pills: `.active` entfernen → geklickte Pill: `.active` setzen → `state.vorwissenLevel = val` (null | 'niedrig' | 'mittel' | 'hoch')
4. "Weiter" → `state.step = 5` → `renderStep5()`
5. "Zurück" → `state.step = 4` → `renderStep4()`

**Ohne PreCall (Step 1 → Step 5 direkt):**
- Vorwissen-Block ist in Step 5 eingebettet als optionaler Bereich unterhalb der Anrede-Auswahl, gleiche 4-Pill-Reihe, Label: "Vorwissen (optional)"
- Gleicher Default: "Weiß nicht" pre-selected

**PiP Override:**
- Indicator zeigt aktuellen Level als Text (Kurzform: "Wenig" / "Vertraut" / "Kennt uns" / "Weiß nicht")
- Klick auf Indicator → Indicator ausblenden → Edit-Flyout einblenden (inline replace, kein Modal)
- Pill-Klick in Edit-Flyout → Wert setzen → `socket.emit('set_vorwissen', {level: val, sid: sid})` → Indicator wieder einblenden mit neuem Wert
- Flyout schließt sich automatisch nach Auswahl (keine explizite Schließen-Aktion nötig)
- Backend emittiert kein Acknowledgement — optimistic update im Frontend reicht

**State Flow:**
- `state.vorwissenLevel` in pip-launcher.js state-dict (analog `state.mode`)
- Beim Call-Start (`startCall()`) wird `vorwissen_level: state.vorwissenLevel` mitgeschickt (analog `anrede`)
- Backend erwartet: `{vorwissen_level: "niedrig"|"mittel"|"hoch"|null}`

### Backend Contract

```
Session-Start Payload (ergänzt):
  vorwissen_level: "niedrig" | "mittel" | "hoch" | null

PiP Override SocketIO Event (client → server):
  event: "set_vorwissen"
  payload: { level: "niedrig" | "mittel" | "hoch" | null, sid: <str> }

Sektion in build_profile_context() output:
  ## Lead-Kontext
  Vorwissen-Level: {niedrig|mittel|hoch|nicht angegeben}
  Anrede: {Du|Sie}
```

## Component 2: Du/Sie-Toggle mit Live-Detection (D-06)

**Placement:** PiP-Sidebar als kompakte Toggle-Reihe (Du | Sie) — bereits partiell in Step 5 als Anrede-Vorauswahl vorhanden. Erweitert um Live-Detection-Badge und Toast-Notification.

**Live-Detection Feedback: Option B** — User-Bestätigungs-Toast ("Anrede-Wechsel erkannt — übernehmen?" mit Ja/Nein). Rationale: Stille Auto-Switch (Option A) würde Prompt mid-Stream ändern können, was den Berater mitte im Vorlesen überrascht. Toast = Kontrolle bleibt beim Berater.

### Interaction Spec

**Manual Toggle:**
1. Klick auf "Du"-Button → "Du" bekommt `.active`, "Sie" verliert `.active` → `state.anrede = 'du'` → `socket.emit('set_anrede', {anrede: 'du', sid: sid})` → Backend updated `## Lead-Kontext` Sektion in aktiver Session
2. Klick auf "Sie"-Button → inverse
3. Badge "Erkannt" bleibt ausgeblendet bei manuellem Toggle

**Live-Detection Flow (SocketIO event vom Server):**
1. Backend erkennt Du-Wechsel via `analyse_loop` keyword-heuristik → emittiert `anrede_switch_detected` Event an sid-room
2. Frontend empfängt `anrede_switch_detected` → Badge "Erkannt" wird sichtbar (`display:inline-block`)
3. Toast erscheint im PiP-Window (fixed position, oben mittig)
4. Toast Auto-Dismiss nach 15 Sekunden ohne User-Aktion → Dismiss-Verhalten (kein Switch)
5. "Ja, wechseln" → `pipSetAnrede('du')` aufrufen (selber Pfad wie manueller Toggle) → Toast ausblenden → Badge bleibt 3s sichtbar dann ausblenden
6. "Nein, behalten" → Toast ausblenden → Badge sofort ausblenden → `socket.emit('anrede_switch_rejected', {sid: sid})` (Backend loggt für Algorithmus-Tuning)
7. Nur ein Toast gleichzeitig — wenn während Toast läuft ein weiteres Event kommt: ignorieren (Debounce)

**Kein zweiter Toast innerhalb von 60 Sekunden** nach letztem akzeptierten oder abgelehnten Switch (Frontend-Timer).

**State:**
- `state.anrede` in pip-launcher.js: 'du' | 'sie'
- Toast-State: `_anredeToastActive` boolean
- `_anredeToastDebounceMs = 60000` Konstante

### Backend Contract

```
SocketIO Event (server → client):
  event: "anrede_switch_detected"
  payload: { detected_form: "du", confidence: 0.0-1.0, sid: <str> }

SocketIO Event (client → server, on manual toggle):
  event: "set_anrede"
  payload: { anrede: "du" | "sie", sid: <str> }

SocketIO Event (client → server, on toast dismiss):
  event: "anrede_switch_rejected"
  payload: { sid: <str> }

Sektion in build_profile_context() output:
  ## Lead-Kontext
  Anrede: {Du|Sie}
  Vorwissen-Level: {niedrig|mittel|hoch|nicht angegeben}
```

### Interaction Spec

**Load Flow:**
1. User klickt "Vorschau laden"
2. Button: `disabled=true`, Text ändert sich zu "Wird geladen…" → Loading-Span erscheint
3. Empty-State-Div ausblenden
4. `fetch('/api/profile/preview-context?profile_id=<current_profile_id>')` GET-Request
5. Response: `{ context: "<rendered build_profile_context() output as plain text>" }`
6. Bei Erfolg:
   - `ewb-preview-pre.textContent = data.context` (textContent, nicht innerHTML — XSS-safe)
   - Output-Div einblenden
   - Empty-State ausblenden
   - Button: `disabled=false`, Text zurück zu "Vorschau laden" (optional: Text "Neu laden")
   - Loading-Span ausblenden
7. Bei Fehler (non-2xx oder Netzwerkfehler):
   - Error-State-Div einblenden
   - Loading-Span ausblenden
   - Button re-aktivieren

**Kein auto-refresh, kein debounce, kein Cache-Invalidation-Badge.** User klickt erneut wenn gewünscht.

**Profile-ID-Quelle:** Das Profil ist beim Aufruf der `/profiles/edit/<profile_id>` Route bekannt. Jinja2 rendert `data-profile-id="{{ profile.id }}"` auf dem `editor-main`-Element (oder per JavaScript aus URL extrahiert: `window.location.pathname.split('/').pop()`).

**Scroll-Verhalten:** Nach erfolgreichem Load: kein auto-scroll. User scrollt selbst durch den `<pre>`-Block (max-height 480px mit overflow-y:auto).

### Backend Contract

```
New API Endpoint:
  GET /api/profile/preview-context?profile_id=<int>

Auth: @login_required (existierendes Decorator-Pattern)
Org-Scoping: verify profile belongs to g.user.org_id before returning

Response (success):
  HTTP 200
  { "context": "<full build_profile_context() output as plain string>" }

Response (error):
  HTTP 400: { "error": "Kein Profil angegeben" }
  HTTP 403: { "error": "Zugriff verweigert" }
```
