## Implementation Decisions

### D-01: Voll-Profil-Kontext Format — 9-Sektionen-Markdown-Blöcke

**Entscheidung:** Markdown `##`-Headings (nicht `Sektion:` Notation) für stabile Cache-Anker. Jede Sektion hat exakt einen `##`-Header. Format ist deterministisch → byte-gleicher Output für identischen Input ist Pflicht-Verifikation.

**Kanonische Sektions-Reihenfolge (unveränderlich für Cache-Stabilität):**
1. `## Branche` — `Profile.branche` DB-Column + `daten.basis.branche` + `basis.branche_kontext`
2. `## Basis` — `basis.unternehmen`, `basis.produktbeschreibung`, `basis.preismodell`, `basis.usps`, `basis.konsequenz`, `basis.eigene_formulierungen`, `basis.beweise`, **Opener aus ProfileOpener-Tabelle** (kanonische Quelle seit 08.19, NICHT aus `daten.JSON`)
3. `## Zielkunde` — `zielkunde.unternehmensgroesse`, `zielkunde.buying_committee`, `zielkunde.statusquo`, `zielkunde.zeithorizont` + erhaltene `zielgruppe.*`-Felder (vorwissen/entscheidungsverhalten für Training)
4. `## Schmerzen` — `schmerzen.*` Felder
5. `## Einwände` — `einwaende_detail` Liste als Markdown-Liste (nach D-04-Migration), Format: `- {einwand} ({einwand_typ}) | {gegenargument}`
6. `## Phasen` — `phasen` als nummerierte Liste (Markdown-Liste für Einwände, nummerierte Liste für Phasen — nie mischen)
7. `## KI-Verhalten` — `ki.ton`, `ki.ansprache`, `ki.wisdom`, `ki.stil`-Merge (falls noch vorhanden), Anrede-Resolution-Logik bleibt erhalten
8. `## PreCall-Briefing` — Session-volatile (per-SID aus `_per_sid_briefing`, D-03/D-09)
9. `## Lead-Kontext` — Session-volatile (Vorwissen-Level + aktuelle Anrede-Präferenz, D-05/D-06)

**Cache-Layering:**
- Sektionen 1-7: cache-stable (statisch per User-Profil, identisch über alle Calls im Session)
- Sektionen 8-9: cache-volatile (per-Call, am Ende des Strings → Anthropic-Pattern: stable zuerst, volatile am Ende)

**Leere Sektionen:** NIE skippen — immer mit Marker rendern:
- Felder nicht ausgefüllt: `(noch nicht ausgefüllt)`
- PreCall nicht gemacht: `(noch nicht erstellt)`
- PreCall gefailed: `(Recherche fehlgeschlagen — siehe Logs)`
- PreCall ohne Treffer: `(keine Treffer für [Lead-Name])`

Cache-Stabilität braucht stabile Sektions-Anzahl — variierende Sektions-Anzahl zerstört Cache-Keys.

**Pflicht-Verifikation (Test in Plan):** `build_profile_context()` mit identischem Profil + Lead-Context liefert exakt byte-gleichen Output. Deterministisch, kein Dict-Iteration-Order-Nichtdeterminismus.

### D-03: PreCall-Briefing Reinject — Sektion 8 in build_profile_context via _per_sid_briefing

**Entscheidung:** `## PreCall-Briefing` als Sektion 8. Single-Funktion-API — alle Pipelines die `build_profile_context()` nutzen bekommen es automatisch. Cache-Layering konsistent: stable User-Profil → volatile Briefing → volatile Lead-Kontext.

**Anti-Header-Constraint:** `_generiere_briefing()` System-Prompt bekommt explizite Einschränkung: "Verwende KEINE `##`-Markdown-Header in deiner Antwort — nur Fließtext und einfache Bullet-Listen (`-`)." Verhindert nested-`##`-Chaos im eingebetteten Briefing-Text.

**Failure/Empty-Marker (nie skippen — immer Status rendern):**
- Kein PreCall: `(noch nicht erstellt)`
- Generierung fehlgeschlagen: `(Recherche fehlgeschlagen — siehe Logs)`
- PreCall ohne Treffer: `(keine Treffer für [Lead-Name])`

### D-04: einwaende_detail als Target-Format — Schema-Version v3 → v4

**Entscheidung:** `einwaende_detail: List[EinwandDetailSchema]` wird Single-Source. Altes `einwaende: List[str]` wird migriert und dann gedroppt.

**Echte EinwandDetailSchema-Felder** (aus `services/profile_schema.py` — NICHT erfinden):
`einwand / varianten / gegenargument / technik / intensitaet / kurzlabel / kategorie / einwand_typ`

**Migration-Pattern (str → EinwandDetailSchema):**
- `einwand` = string aus alter Liste (1:1)
- Defaults: `varianten=[]`, `gegenargument=''`, `technik=''`, `intensitaet=3`, `kurzlabel=''`, `kategorie=''`, `einwand_typ='unbekannt'`
- User befüllt Detail-Felder nachträglich im Editor

**Schema-Version-Bump:** v3 → v4 in `_migrate_profile_data()`:
- Audit-Event: `[Schema] Profile {id}: v3→v4 applied — migrated einwaende→einwaende_detail, dropped einwaende top-level`
- Strict-Mode (`extra='forbid'`) bleibt aktiv auf allen Sub-Schemas

**Pipeline-Reads-Migration (Pflicht in Plan-01):**
- Grep `services/` + `routes/` + `templates/` für alle `daten.get('einwaende')` / `.einwaende`-Reads
- ALLE auf `daten.get('einwaende_detail')` + `.einwand` bzw. `.gegenargument` umstellen
- Editor-Verifikation: 08.19.2-einwaende_detail-Karte schreibt korrektes Schema (nicht `List[str]`)

### D-07: Markt-differenzierter Sonnet-Default + Circuit-Breaker — LOCKED (André 2026-04-29)

EWB liefert vollständig vorlesbare Sätze via Streaming — TTFT (Time-To-First-Token) ist die relevante Reaktionsfähigkeits-Metric, da Berater mid-stream anfängt vorzulesen.

**Markt-spezifische Defaults (via `config.MARKET`):**
- DACH: `MODEL_PIP_AUTOVAR=claude-sonnet-4-5` (deutsche Grammatik braucht Sonnet-Niveau)
- USA: `MODEL_PIP_AUTOVAR=claude-haiku-4-5-20251001` (englische Grammatik mit Haiku akzeptabel + Cost-Effizienz)
- Pro-User-Override-Setting für Premium-Tier: Foundation aus 08.15 Plan-Architektur

**Latency-Metriken + Schwellwerte (ENV-configurable, Plan-Phase darf Tuning):**
- **Primär — TTFT:** `EWB_SONNET_FALLBACK_TTFT_MS=1500` — Circuit-Breaker triggert bei 3 von 5 letzten Calls > 1500ms
- **Sekundär — ITL p95:** `EWB_SONNET_FALLBACK_ITL_P95_MS=300` — Stream darf zwischen Tokens nicht laggen (Berater stottert beim Vorlesen)
- **Total-Latency:** NICHT geschwellwertet — bei komplexen Fragen variabel akzeptabel solange Stream flüssig

**Circuit-Breaker-Fallback-Logik:**
- DACH: Sonnet → Haiku-Fallback für 30 Sek, dann Sonnet-Retry
- USA: Haiku → Haiku-Retry (kein weiterer Fallback)

**Pflicht-Check Plan-01 — Streaming-Verifikation:**
`services/claude_service.py` EWB-Pfad muss verifiziert werden ob heute `anthropic.messages.stream()` oder async-äquivalentes Pattern aktiv ist. Falls nicht: Streaming-Aktivierung als Pflicht-Schritt im Plan (sonst ist TTFT-Argumentation leer). Frontend-PiP WebSocket-Pattern für inkrementelle Token-Updates ebenfalls verifizieren.

**Cost-Tracking-Tags in `api_cost_log`:** `model_used` + `fallback_active` + `market` → Founder-Cost-Dashboard nach Markt aufschlüsselbar + Fallback-Rate sichtbar.
