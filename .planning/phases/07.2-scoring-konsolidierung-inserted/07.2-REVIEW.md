## Summary

Phase 07.2 reworks the post-Training flow — overlay removed, Session-Detail extended with 3 new Sektionen (Wendepunkt/Einzel-Bewertungen/Verbesserungen), Custom-Persona fallback and "Nochmal trainieren"-Action wired up. Code-quality is solid overall: defensive `isinstance`-Guards around JSON deserialization, whitelisted `schwierigkeit_raw` against tampering, Jinja autoescape relied on for user-rendered AI-Output, login_required konsistent angewendet auf alle neuen/angefassten Routen.

Security posture for the changes is clean — no XSS, no SQL-Injection, no Auth-Bypass, keine neuen Deserialization-Risiken. `_parse_kunden_meta` Regex ist non-backtracking-safe (non-greedy + anchored + Input auf 100 Zeichen begrenzt via DB-Schema). IDOR in `session_detail` korrekt durch `user_id=g.user.id`-Filter abgedeckt.

Zwei echte Bugs gefunden:
1. **WR-01:** "Nochmal trainieren"-Button bastelt URL-Params `?personality_type_id=...&schwierigkeit=...`, aber `templates/training.html` konsumiert diese nicht — Pre-Selection ist non-functional, User landet auf Training-Setup ohne voreingestellte Werte.
2. **WR-02:** Backend ruft `_generate_live_preview()` (Haiku-API-Call) bei jedem `training_end()`, das Resultat wird aber vom Frontend seit Wave 3 (Overlay-Removal) ignoriert — unnötige Kosten + Latenz pro Training-Abschluss.

Info-Items betreffen Dead-Code-Cleanup (orphaned response-keys), redundante JSON-Parses, einen pre-existing Umlaut-Violation-Bug in training.html (nicht 07.2-eingefuehrt, aber im reviewed file), und kleinere Robustheits-Hints.

## Warnings

### WR-01: "Nochmal trainieren"-Button-URL-Params werden nicht konsumiert

**File:** `templates/session_detail.html:14-18` + `templates/training.html:931,2176-2197`
**Issue:** Der neue Action-Button in Sektion 1 (Header) baut die URL `"/training?personality_type_id=X&schwierigkeit=Y"` zusammen (Wave 3, Plan 03). Das Training-Setup (`templates/training.html`) liest aber ausschließlich `quick=1` und `einwand_typ` aus `window.location.search`. `personality_type_id` und `schwierigkeit` werden weder von `startTraining()` noch von `checkQuickTraining()` ausgewertet. Der User klickt "Nochmal trainieren" und landet auf dem Setup-Screen mit Default-Werten (`selectedDiff='mittel'`, `selectedPersonalityTypeId=null`) — die URL-Params werden noch vor dem ersten Payload durch `window.history.replaceState` weggespült (Zeile 983-984).

**Fix:** In `templates/training.html` neben `checkQuickTraining()` einen Handler ergänzen, der `personality_type_id` (int-cast + Card-Pre-Select via `selectTyp()`) und `schwierigkeit` (Whitelist `leicht|mittel|schwer` + `selectDiff()`) aus den URL-Params liest, z.B.:
```javascript
// In initSetup (oder als neuer init-Block)
(function prefillFromRepeat() {
  const p = new URLSearchParams(window.location.search);
  const ptid = parseInt(p.get('personality_type_id'), 10);
  const sw = p.get('schwierigkeit');
  if (ptid && !isNaN(ptid)) {
    // Nach loadPersonalityTypes() — Card mit data-id anklicken
    const card = document.querySelector('.t-typ-card[data-id="' + ptid + '"]');
    if (card) card.click();
  }
  if (['leicht','mittel','schwer'].includes(sw)) {
    selectDiff(sw);
  }
})();
```
Einbinden muss man das nach `loadPersonalityTypes()`-Resolve (z.B. in der `.then()`-Kette oder mit einem kleinen `MutationObserver` auf `#t-typ-cards`), weil die Cards asynchron kommen. Alternativ: `/training?personality_type_id=X&schwierigkeit=Y` Server-seitig im `training_page()`-Handler auswerten und an Jinja übergeben.

### WR-02: `_generate_live_preview()` läuft bei jedem Training-Ende, Resultat ungenutzt

**File:** `routes/training.py:652-656` (+ 669 returned `live_preview`)
**Issue:** `confirmEndTraining()` redirected seit Wave 3 direkt auf `/session/<log_id>` (training.html:1436), die response-keys `live_preview` und `personality_revealed` werden nicht mehr gelesen. Backend ruft aber weiterhin `_generate_live_preview(session['history'], session['profile_data'])` auf (ein Haiku-API-Call mit Token-Kosten + 1-3s Latenz), siehe training.py:654. Das verzögert den Redirect und produziert pro Training-Abschluss unnötige API-Kosten (`claude-haiku-4-5-20251001`).

**Fix:** Entweder den Call entfernen, bis POLISH-36 (Re-Introduction) das Feature wieder einbaut:
```python
# routes/training.py training_end — ENTFERNEN Zeilen 652-656 (live_preview-Block)
# und result['live_preview'] = live_preview wegnehmen (Zeile 669).
# Alternativ: hinter if-Flag gaten, z.B. if session.get('include_live_preview') — Wave-3-Flow setzt das nicht.
```
personality_revealed (Zeile 673-679) ist in-memory ohne API-Call — kann bleiben oder gleich mit entfernt werden (ebenfalls POLISH-35). Dokumentation in training.html:630-634 ist da, Backend-Aufräumen fehlt.

### IN-01: Umlaut-Violation: `sekretärin_typ` als JSON-Key (pre-existing, nicht 07.2)

**File:** `templates/training.html:946`
**Issue:** `sekretärin_typ: selectedSekTyp` in `startPayload` verwendet Umlaut als JS-Object-Key. Der Key landet nach `JSON.stringify` als UTF-8-String im POST-Body. `routes/training.py:152` liest aber `data.get('sekretaerin_typ', 'blockerin')` (ASCII). Result: Die User-Auswahl (blockerin/helferin/abwimmlerin) wird verworfen, Backend defaultet immer auf `'blockerin'`. Bug eingeführt in Commit `568b1b0c` (Phase 07 Umlaut-Cleanup-Overshoot) — NICHT 07.2-Änderung, aber da `templates/training.html` im Review-Scope ist, hier dokumentiert. Verletzt CLAUDE.md-Regel "JS-Object-Keys die als JSON ans Backend gehen: ASCII (`sekretaerin_typ`)".

**Fix:** Zeile 946 ändern zu `sekretaerin_typ: selectedSekTyp,`. Parallel verifizieren, dass kein anderer Code-Pfad auf den Umlaut-Key referenziert.

### IN-02: Dead-Code im Backend: `personality_revealed` Response-Key ohne Konsument

**File:** `routes/training.py:673-679`

### IN-03: `phasen_details` wird in `session_detail()` 3-4x re-parsed

**File:** `routes/dashboard.py:807, 828, 844, 879`
**Issue:** `_json.loads(conv.phasen_details)` wird viermal hintereinander aufgerufen (schwierigkeit_label, schwierigkeit_raw, scoring_kategorien/wendepunkte/verbesserungen, custom_persona). Jeder Call macht einen vollständigen String→Dict-Decode. Für typische Payloads (~5-10 KB) unbedeutend, aber unnötig.

**Fix:** Einmal parsen, als lokale Variable wiederverwenden:
```python
_pd_cached = None
if conv.phasen_details:
    try:
        _pd_cached = _json.loads(conv.phasen_details)
    except Exception:
        _pd_cached = None

# Dann überall _pd_cached nutzen statt _json.loads(conv.phasen_details)
# und isinstance(..., dict)-Guards wie gehabt.
```
Bonus: Vermeidet die Duplikation der try/except-Blöcke.

### IN-04: `confirmEndTraining()` cleart `loadInterval` nicht im Success-Branch

**File:** `templates/training.html:1410-1442`
**Issue:** `loadInterval = setInterval(...)` (Zeile 1410) wird nur im Error-Branch (Zeilen 1423, 1444) über `clearInterval` aufgeräumt. Im Success-Branch (Zeile 1436) redirected der Browser via `window.location.href`, was den Interval implizit beendet. Kein Leak, aber asymmetrischer Code-Pfad.

**Fix:** `clearInterval(loadInterval)` vor dem Redirect einbauen (kurz vor `window.location.href = '/session/' + data.log_id;`). Dient der Lesbarkeit, kein Bugfix.

### IN-05: `_derive_practice_recommendations()` — Dedupe-Key kann `None` sein

**File:** `routes/app_routes.py:817-825`
**Issue:** `_key = r.get('explanation')` — falls eine zukünftige Rec-Regel vergisst `explanation` zu setzen, würde `None` als erster Key ins Set wandern und alle weiteren Recs ohne `explanation` blocken. Heute nicht triggerbar (alle 4 Live-Regeln + 4 Training-Regeln setzen `explanation` explizit).

**Fix:** Robustheits-Hint:
```python
_key = r.get('explanation') or id(r)  # fallback: object identity = never dedupes
```
Oder strikter: `if _key is None: _deduped.append(r); continue`. Nicht dringend.

### IN-06: `chart_data_json | safe` — XSS-Überlegung (pre-existing, nicht 07.2)

**File:** `templates/session_detail.html:116`
**Issue:** `<script type="application/json" id="sd-chart-data">{{ chart_data_json | safe }}</script>` bypasst Jinja-Autoescape. Heute ungefährlich, weil `chart_data_json` aus `conv.kb_verlauf` bzw `conv.stimmung_history` kommt — beide Server-seitig als JSON geschrieben (numeric `wert`, `HH:MM:SS`-Timestamps, hardcoded `grund`-Strings). Keine User-kontrollierte Eingabe. Aber: `</script>` im JSON-Value würde aus dem `<script>`-Tag ausbrechen (klassischer JSON-Island-XSS). Risiko heute 0, aber robuster wäre ein dedizierter Filter der `<` und `>` escaped.

**Fix:** Optional — in `app.py` einen `|tojson_safe` Filter definieren der `</` zu `<\\/` ersetzt, oder auf Flask's eingebautes `|tojson` umstellen (das macht genau das). Beispiel: `{{ chart_data_json | tojson_safe | safe }}` oder besser: Python-seitig `json.loads(chart_data_json)` und dann `{{ parsed | tojson }}` — dann greift Jinja's builtin Escape für JSON. Nicht 07.2-Scope, aber beim nächsten Touch des Templates mitnehmen.
