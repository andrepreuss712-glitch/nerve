# Phase 06.5: Meeting-Modus Flow-Umbau — Consent als Modal beim Call-Start - Context

**Gathered:** 2026-04-17
**Status:** Ready for planning
**Source:** User specification (POLISH-16 Folgearbeit) + Phase 06.4 Headset-Modal Pattern als Vorlage

<domain>
## Phase Boundary

Meeting-Modus bekommt denselben Launcher-Flow wie Cold Call (step 1 Mode -> 2 PreCall-Option -> 3/4 PreCall -> 5 Skript/Opener). Inline-Consent-Screen direkt nach Meeting-Card-Klick wird entfernt. Consent erscheint stattdessen als Modal (analog zum Headset-Modal aus Phase 06.4) beim Klick auf "Call starten" in Step 5.

Dreistufiges Ergebnis:
- "Stattgegeben" -> Call startet im Meeting-Modus (state.mode bleibt 'meeting', KEIN Headset-Check — Consent deckt beide Stimmen rechtlich ab)
- "Abgelehnt" -> state.mode wird auf 'cold_call' umgeschaltet, regulaerer Cold-Call-Fallback greift inkl. Headset-Gate
- "Abbrechen" -> Modal schliesst, User bleibt auf Step 5, kein Call-Start

state.consentDone einmal pro Session (analog sessionStorage.headsetConfirmed). Text aus state.profileDaten.consent_text ueberschreibbar; Default-Text und [Name]-Token-Ersetzung aus state.precallFormData.person. Alter PiP-Consent-Screen (pip-section-consent) komplett ausgebaut — Wave 4 Cleanup.

## Warum

Der aktuelle Meeting-Flow zeigt den Consent-Screen DIREKT nach Meeting-Card-Klick, BEVOR User Profil, Skript oder Opener waehlt. Das ergibt keinen Sinn — User kennt weder Kontext noch Gespraechspartner, soll aber schon den Einwilligungs-Text vorlesen. Consent muss am Ende des Launcher-Flows stehen, unmittelbar vor Call-Start, analog zum Headset-Gate.

</domain>

<decisions>
## Implementation Decisions

### Launcher-Flow (LOCKED)
- Cold Call bleibt unveraendert: step 1 (Mode) -> 2 (PreCall-Option) -> 3/4 (PreCall) -> 5 (Skript/Opener) -> Headset-Modal -> 6 (Live)
- Meeting neu: step 1 (Mode) -> 2 -> 3/4 -> 5 -> Consent-Modal -> 6 (Live)
- Meeting-Card-Klick setzt ausschliesslich state.mode = 'meeting' und geht direkt zu Step 2 (wie Cold-Card)

### Consent-Modal Text (LOCKED — nicht abaendern)
- Titel: "Einwilligung des Gespraechspartners"
- Pflicht-Label: "Bitte laut vorlesen"
- Default-Script: "Kurz vorab — ich lasse mich gerade von einem Assistenzsystem unterstuetzen, das unser Gespraech mitliest und mir hilft, keine Audioaufnahme. Passt das fuer Sie?"
- Button 1 (primary): "Stattgegeben"
- Button 2 (ghost/reject): "Abgelehnt"
- Button 3 (ghost/cancel): "Abbrechen"
- Keine Tipp-Zeile, kein Zweck-Satz, kein Widerrufs-Hinweis im Modal selbst

### Consent-Text Ueberschreibbarkeit (LOCKED)
- Wenn state.profileDaten.consent_text gesetzt ist, wird dieser statt des Defaults angezeigt
- [Name]-Platzhalter im Profil-Text durch state.precallFormData.person ersetzen (falls vorhanden)
- Fallback zur Default-Konstante, wenn profileDaten.consent_text leer/undefined

### Gate-Stack in startCall() (LOCKED)
Reihenfolge in startCall(setProfile):
1. Cold Call + kein Headset-Confirm -> Headset-Modal (bestehendes Verhalten aus Phase 06.4)
2. Meeting + !state.consentDone -> Consent-Modal (NEU)
3. Beide Checks bestanden -> Call startet

Consent-Modal-Callback-Logik:
- result === 'accepted'  -> state.consentDone = true; startCall(setProfile) re-call
- result === 'rejected'  -> state.mode = 'cold_call'; state.consentDone = true; startCall(setProfile) re-call (dann greift Headset-Gate ggf.)
- result === 'cancelled' -> nichts tun, User bleibt auf Step 5

### Session-Persistenz (LOCKED)
- state.consentDone als JS-State-Flag (nicht sessionStorage — lebt nur in der Launcher-Instanz)
- Einmal pro Session reicht; Reset nur bei vollstaendigem Launcher-Reset/Logout
- Bestehende state.consentDone-Variable aus aktueller Implementation wird BEHALTEN (Wave 1) und in Wave 3 vom neuen Modal gesetzt

### HTML / CSS Pattern (LOCKED)
- Neues Overlay in templates/base.html NEBEN dem bestehenden headset-overlay:
  `<div class="consent-overlay" id="consent-overlay">` mit Z-Index 10100 (gleiche Schicht wie Headset-Modal)
- Inhalt: Titel, Pflicht-Label, Platzhalter fuer Script-Text (dynamisch befuellt via JS), drei Buttons
- CSS-Klassen analog zu .headset-*: .consent-overlay, .consent-box, .consent-title, .consent-pflicht, .consent-script, .consent-actions, .consent-btn, .consent-btn-accept, .consent-btn-reject, .consent-btn-cancel
- Optik konsistent zu Headset-Modal

### JS-Funktion _showConsentModal (LOCKED)
Analog zu _showHeadsetModal aus Phase 06.4:
- Signatur: `_showConsentModal(callback)` mit callback(result), result in {'accepted', 'rejected', 'cancelled'}
- Text-Resolution: state.profileDaten.consent_text -> [Name]-Token-Replacement via state.precallFormData.person -> Fallback Default-Konstante
- Overlay-Show via .open Klasse (gleiches Pattern wie Headset-Modal)
- Close-Handler: alle drei Buttons schliessen das Modal, rufen callback mit entsprechendem Ergebnis

### Wave-Breakdown (LOCKED)

**Wave 1 — Inline-Consent-Screen aus Meeting-Mode-Wahl entfernen**
- static/pip-launcher.js Zeile ~174-179: onclick-Handler fuer lnr-card-meeting nimmt direkt den Cold-Call-Pfad (state.mode setzen, dann nextStep(2))
- Kompletten renderConsentStep()-Block und zugehoerige Handler entfernen (Zeile ~181 bis Ende der Funktion)
- State-Flag state.consentDone BEHALTEN — wird in Wave 3 vom neuen Modal gesetzt

**Wave 2 — Consent-Modal analog Headset-Modal bauen**
- HTML in templates/base.html neben dem headset-overlay div (siehe oben)
- CSS-Klassen im gleichen Stylesheet wie .headset-* (analog gestaltet)
- JS-Funktion _showConsentModal(callback) in pip-launcher.js analog zu _showHeadsetModal

**Wave 3 — Gate in startCall() einbauen**
- In startCall(setProfile) ZWISCHEN Headset-Gate und eigentlichem Call-Start:
  ```
  if (state.mode === 'meeting' && !state.consentDone) {
    _showConsentModal(function(result) {
      if (result === 'accepted')  { state.consentDone = true; startCall(setProfile); }
      if (result === 'rejected')  { state.mode = 'cold_call'; state.consentDone = true; startCall(setProfile); }
      if (result === 'cancelled') { /* nichts */ }
    });
    return;
  }
  ```

**Wave 4 — Alte Consent-Logik in der PiP loeschen**
- static/pip-launcher.js Zeile ~1128-1170: Block der nach Call-Start nochmal pip-section-consent anzeigt — komplett raus
- static/pip-launcher.js Zeile ~1185-1194: consentSection-Referenzen im Reset-Flow raus
- HTML-Element `<div id="pip-section-consent">` suchen und entfernen (base.html oder dashboard.html)
- Alle Referenzen auf pip-section-consent im Code raeumen
- state.consentDone bleibt (wird jetzt ausschliesslich vom Launcher-Modal aus Wave 3 gesetzt)

### Encoding-Regel (LOCKED — POLISH-12 Bug vermeiden)
- Keine nativen Umlaute in Code/Text verwenden
- "ae", "oe", "ue", "ss" in allen Strings (genau wie im Headset-Modal aus Phase 06.4)

### Nicht machen (LOCKED)
- Consent-Modal NICHT bei jedem Call neu zeigen — einmal pro Session reicht
- Consent-Text NICHT hardcoden — muss aus Profil ueberschreibbar sein (Fallback ist Default-Konstante)
- Umlaute NICHT nativ verwenden — POLISH-12-Encoding-Bug

### Template-Scope (LOCKED — RULE-02)

<specifics>
## Specific Ideas (aus User-Spec)

### UAT-Checkliste (10 Punkte, MUST PASS)
1. Meeting-Card klicken -> Launcher zeigt direkt Step 2 (PreCall-Option), NICHT Consent-Screen
2. Normaler Flow durch Steps 2-5 moeglich im Meeting-Modus
3. "Call starten" in Step 5 -> Consent-Modal erscheint (nicht Headset-Modal)
4. "Stattgegeben" -> Modal schliesst, Call startet im Meeting-Modus, state.mode bleibt 'meeting'
5. Zweiten Call in Meeting-Modus starten (selbe Session): Kein Consent-Modal mehr (state.consentDone)
6. Nach vollstaendigem Reset/Logout: Consent-Modal kommt beim naechsten Meeting wieder
7. "Abgelehnt" im Consent-Modal -> state.mode wird 'cold_call', Headset-Modal erscheint (falls noch nicht bestaetigt), nach Headset-Bestaetigung startet Cold Call
8. "Abbrechen" im Consent-Modal -> Modal schliesst, kein Call-Start, Launcher bleibt auf Step 5
9. Innerhalb der laufenden PiP erscheint KEIN zweites Consent-Popup mehr (Wave 4 Verifikation)
10. Cold Call direkt (ohne vorher Meeting) -> unveraendert wie Phase 06.4

</specifics>
