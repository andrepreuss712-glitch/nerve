## A3-Entscheidung: Option 1 (Session-Level Advisory-Lock) — gelockt

### Option 2 (CAS-INSERT / Unique-Index) — VERWORFEN
Ein `UNIQUE (profile_id, type)` auf `profile_opener` ist **fundamental inkompatibel**: mehrere
Opener/Pitch/Erlaubnis pro Typ und Profil sind ein **Feature** (routes/profiles.py:363-379 / :457 / :539
— UI legt beliebig viele Bausteine je Typ an). Der Index bräche die bestehende UI + Bestandsdaten.

### Option 3 (Xact-Lock halten, ein End-Commit) — VERWORFEN
`conn.rollback()` gibt den xact-Advisory-Lock frei. Die 4 TXN-FIX-rollback-Stellen (Per-Profil-Isolation)
würden damit zu **4 stillen Race-Minen** (jeder Rollback öffnet das Race-Fenster) + wäre ein
Isolations-Rückschritt zu genau der Garantie, die TXN-FIX gerade gebaut hat.

### Option 1 (Session-Level `pg_advisory_lock`) — GEWÄHLT, mit 4 Pflicht-Härtungen

**★ H-1 LOCK-LEAK in den Connection-Pool (der echte Killer — im Erstplan NICHT benannt):**
`with engine.connect()` (app.py:1420) **schließt die conn NICHT** → sie geht in den SQLAlchemy-Pool
zurück; der Pool-Reset macht `rollback`, und **`rollback` gibt session-level Advisory-Locks NICHT frei**
(nur xact-level werden am Txn-Ende freigegeben). → geleakter Lock → Worker 2..n hängen beim Boot
**unbegrenzt**. Gegenmaßnahmen (ALLE erforderlich):
- **(a)** `pg_try_advisory_lock(819)` statt blockierendem `pg_advisory_lock` (Gemini): nicht-blockierend
  → kein Boot-Hang. Wer den Lock nicht kriegt → überspringt die Migration (anderer Worker macht sie) +
  idempotenter Skip (>=LATEST) fängt den Rest. (Fables Alternative blockierend + `SET lock_timeout='30s'`
  → Timeout→WARN+return ist zulässig, aber try_advisory ist robuster → gewählt.)
- **(b)** try/finally beginnt UNMITTELBAR nach erfolgreichem Acquire und schließt den SELECT (:1435) ein
  — sonst leakt der frühe return :1436-1438 (SELECT-fail) den Lock.
- **(c)** im finally: ERST `conn.rollback()`, DANN `pg_advisory_unlock` — sonst scheitert das unlock selbst
  an `InFailedSqlTransaction` und der Lock leakt trotz finally.
- **(d)** unlock NUR im PG-Zweig (SQLite-Guard), auf DERSELBEN conn.
