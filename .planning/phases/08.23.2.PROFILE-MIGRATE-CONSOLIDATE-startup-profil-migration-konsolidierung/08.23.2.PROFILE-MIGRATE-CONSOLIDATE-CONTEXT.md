## Implementation Decisions

### A1 — Konsolidierungsrichtung (Datenverlust-Risiko, wichtigste Gabelung)

- **D-A1:** **`_migrate_profile_json()` (`app.py:1392`, Call `app.py:2078`) ist DER EINE überlebende Migrationspfad.** Der v4-Batch (`app.py:989-1031`, innerhalb `_migrate()`) wird **gelöscht**.
- **Begründung (code-verifiziert):** `_migrate()` early-returnt auf Postgres (`app.py:140-142`) → der v4-Batch ist auf Prod-PG **TOT**, läuft nie. `_migrate_profile_json` ist der einzige auf Prod-PG lebende Pfad und läuft auch auf SQLite (`BEGIN EXCLUSIVE`, `app.py:1421`) → der v4-Batch ist auch für Local-Dev redundant, sobald der Überlebende v2/v3 hebt (siehe D-A2).
- **★ KORREKTUR der stalen Backlog-Formulierung:** Der Backlog sagte wörtlich „Opener-Sync in den v4-Batch ziehen und `_migrate_profile_json` löschen". Das war VOR der TXN-FIX-Erkenntnis (v4-Batch PG-tot) geschrieben und ist **rückwärts** — wörtlich befolgt würde es den lebenden Pfad wegwerfen und den toten behalten. Die Konsolidierung läuft umgekehrt: der lebende Pfad bleibt, der tote wird demontiert.
- **Datenverlust-Absicherung (bereits korrekt im lebenden Pfad, MUSS beim Refactor erhalten bleiben):** `_migrate_profile_json` synct opener/pitch/erlaubnis via rohe INSERTs + `commit` (`app.py:1468-1509`) **VOR** dem `_mpd(_daten)`-Aufruf (`app.py:1517`); der opener-Pop sitzt IN `_mpd` (`services/profile_schema.py:304`, nur `version < 3`). Sync ist persistiert, bevor gepoppt wird → **kein stiller Opener/Pitch-Verlust**. Diese Ordnung ist invariant und darf beim Auflösen des toten Batches NICHT gebrochen werden.
- **Scope-Grenze:** NUR der v4-Batch-Block (`app.py:989-1031`) wird aus `_migrate()` entfernt — NICHT die ganze `_migrate()`-Funktion (SQLite-ALTER-Blocks + `_migrate_fragen_to_faqs()` bleiben).

### A2 — v2/v3→v4-Anhebung der Bestandsprofile (Onboarding-Launch-Gate)

- **D-A2:** Anhebung via **Skip-Schwelle heben**: in `_migrate_profile_json` die Idempotenz-Bedingung `schema_version >= 2` (`app.py:1461`) auf `>= LATEST_SCHEMA_VERSION` (v4) ändern → v2/v3-Profile fließen durch die existierende Hebe-Logik in `_mpd` (`services/profile_schema.py:255-275`) + den idempotenten Opener-Sync.
- **★ KEINE Expand/Contract-Falle (Punkt 21/22, AUTH-2-Lehre geprüft):** `_mpd` hebt **rein per JSON** — fasst KEINE DB-Spalte an (`profile_schema.py:266` „Kein DB-Zugriff"; `profiles` hat keine `schema_version`-Spalte, alles im `daten`-JSON). Kein neuer ORM-Spalten-Lesezugriff → **kein Migration-vor-Leser-Ordnungsproblem, Single-Deploy sicher.**
- **Idempotenz + Onboarding-Tragfähigkeit:** aktuell 0 v2/v3 auf Prod (Pre-Execute-Audit Pflicht re-verifizieren, Guard a macht die Lücke sichtbar). Neu angelegte Profile tragen `schema_version` (Backlog `AUTH2-ERSTPROFIL-SCHEMA-VERSION`, Fix ce57dea) → sind v4 → Hebung überspringt sie idempotent. Die Hebung greift für jedes künftige legacy-v2/v3-Profil.
- **Sync-Sicherheit für neu durchfließende v2/v3:** der Opener-Sync (`app.py:1468`) ist per `COUNT`-vor-`INSERT` idempotent (`app.py:1469-1473`) → durchfließende v2/v3 doppeln keine Opener-Rows.

### A3 — Advisory-Lock 819 (🔴 BEWUSST OFFEN — Cross-AI Fable+Gemini entscheidet)

- **D-A3:** **KEINE Festlegung im Discuss** (André-Direktive). Die Drei-Wege-Tabelle geht als offene 🔴-Entscheidung in den Plan; Cross-AI wägt sie beim Plan-Review, dann Andre-Wahl.
- **Problem (code-verifiziert):** `pg_advisory_xact_lock(819)` (`app.py:1429`) ist **xact-scoped**, aber die Schleife committet mehrfach (`app.py:1479/1486/1505/1525`). Der **erste `commit` gibt den Lock frei** → Multi-Worker-Race: zwei Worker sehen beide `COUNT=0` (`app.py:1473`) und INSERTen beide → Doppel-Row.
- **Drei-Wege-Vergleich (für Cross-AI + Andre):**

  | Option | Multi-Worker | Deadlock | Schema-Change? | Spannung mit TXN-FIX | Einfachheit |
  |---|---|---|---|---|---|
  | **1. Session-Level `pg_advisory_lock(819)`/`unlock` (try/finally)** | Ein Worker migriert, andere warten → v4-Check → idempotenter Skip | Niedrig (ein Key, keine Lock-Ordnung); Restrisiko = finally-unlock muss sicher feuern | Nein | Keine — Per-Profil-Isolation (Per-except-rollback) bleibt | Mittel |
  | **2. CAS-INSERT (`ON CONFLICT DO NOTHING`)** | Beide Worker parallel; Doppel-INSERT von PG abgewiesen; daten-UPDATE last-write-wins (identisch) | Keins | **Ja** — Unique-Index `(profile_id, type)` nötig + Dup-Row-Vorabprüfung Prod | Bringt eigene Migration + Expand/Contract-Frage rein | Hoch für INSERT-Race, aber Schema-Aufwand |
  | **3. Xact-Lock halten (mid-Loop-Commits raus, EIN End-Commit)** | Lock hält bis End-Commit → echte Serialisierung | Keins | Nein | **Kollidiert** — hebt Per-Profil-Isolation der TXN-FIX auf (ein defektes Profil rollt alle zurück, außer Savepoints) | Hoch mechanisch, aber Isolations-Rückschritt |

- **Fakt für Option 2:** `ProfileOpener` hat KEINEN Unique-Constraint auf `(profile_id, type)` (`database/models.py:192-204`) → CAS bräuchte erst eine Schema-Migration.
- **Claudian-Einschätzung (nicht bindend):** Option 1 ist der kleinste tragfähige Weg (Punkt 27), behält die Per-Profil-Isolation der TXN-FIX, kein Schema-Change. Cross-AI verifiziert/entscheidet.

### Teil B — Hardening-Funde (mechanisch, direkt in den Plan, KEIN Discuss)

- **D-B1:** Boot-Crash-Netz — Modul-Level-Call `_migrate_profile_json()` (`app.py:2078`) in try/except wrappen (wie andere Startup-Calls) + `isinstance`-Guard vor `_daten.get('meta')` (`app.py:1512`). Non-dict `daten` darf App-Start nicht crashen.
- **D-B2:** `created_at` in die 3 rohen Opener-Sync-INSERTs setzen (`app.py:1476/1483/1502`). Python-`utcnow`-Default (`models.py:201`) greift bei raw SQL NICHT → sonst NULL `created_at`. (Fakt bestätigt: `ProfileOpener.created_at = Column(DateTime, default=utcnow)`, kein `server_default`.)
- **D-B3:** Docstring `_migrate_profile_json` (`app.py:1400-1403`) ehrlich machen — die Multi-Worker-Serialisierung hält nach dem A3-Fix nur bis zum ersten Commit (bzw. je nach gewählter A3-Option neu formulieren).
- **D-B4:** Test B (`tests/test_profile_migrate_txn.py:89-118`) schärfen — echten Fehler einschleusen (defektes Profil) → beweist Rollback-Isolation WIRKLICH (andere Profile migrieren trotzdem, keine Kaskade); plus pitch/erlaubnis-Sync-Pfade testen.
