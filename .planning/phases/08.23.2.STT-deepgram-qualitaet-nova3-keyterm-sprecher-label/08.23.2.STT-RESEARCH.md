## context7 keyterm-Syntax (verbatim — SDK-Drift-Guard)

**Quelle: `/websites/developers_deepgram` — `https://developers.deepgram.com/reference/streaming` (Live Audio query params):**

> - **keyterm** (any, Optional): Key term prompting can boost specialized terminology and brands. Only compatible with Nova-3.
> - **keywords** (any, Optional): Keywords can boost or suppress specialized terminology and brands.

> Key term prompting and keywords can be used to boost or suppress specific terminology and brands. **Key term prompting is only compatible with the Nova-3 model.**

**Quelle: `https://developers.deepgram.com/docs/keyterm` — Enable Feature:**

> To enable Keyterm Prompting, add a `keyterm` parameter in the query string and set it to your chosen key term:
> `keyterm=KEYTERM`
>
> ```bash
> curl ... --url 'https://api.deepgram.com/v1/listen?model=nova-3&keyterm=KEYTERM'
> ```

**Mehrere Keyterms (verbatim, `/docs/keyterm`):**

> ### Pass Multiple Keyterms with Repeated Parameter
> Use this method to pass multiple keyterms, ensuring each is processed individually.
> ```
> ...?model=nova-3&keyterm=KEYTERM1&keyterm=KEYTERM2
> ```
>
> ### Pass Multiple Keyterms with Encoded Space
> Combine multiple keyterms into a single space-delimited value using URL encoding (`%20`). This treats the phrase as a cohesive unit for boosting.
> ```
> ...?keyterm=term1%20term2
> ```

**Interpretation für den v3-Python-SDK (`LiveOptions`):**
- Im query-String ist `keyterm` ein **wiederholter Parameter** — ein `keyterm=` pro Term.
- Ein **mehrwortiger Term** (z.B. `"Cold Call"`, `"Einwandbehandlung"`) bleibt EIN keyterm-Wert mit Space drin → wird als kohärente Phrase geboostet. Also: Liste aus Strings, wobei jeder String ein (ggf. mehrwortiger) Term ist.
- `LiveOptions` akzeptiert `keyterm=[...]` (Liste von Strings); der SDK serialisiert die Liste zu wiederholten Query-Params. **[MEDIUM — in Prod-`[DG]`-Log verifizieren dass der SDK die Liste nicht zu einem CSV-String zusammenklebt.]** Bei der v3-SDK-Linie ist das Listen-zu-repeated-param Verhalten Standard für Multi-Value-Felder (vgl. `keywords`).

**Voice-Agent / JSON-Variante (zur Querverifikation der Listen-Natur, `/docs/voice-agent-stt-models`):**
> ```json
> { "model": "nova-3", "language": "en-US", "smart_format": true, "keyterms": ["Deepgram", "Aura"] }
> ```
(Im Live-STT-WS-Pfad heißt der Parameter `keyterm` singular; in Agent/Flux-Config `keyterms` plural — NICHT verwechseln. Wir nutzen den Live-STT-WS-Pfad → `keyterm`.)

## keyterm LIMIT (Cap-Wert)

**Quelle: `/websites/developers_deepgram` — `https://developers.deepgram.com/docs/keyterm` — Key Term Limits (verbatim):**

> Key terms are limited to a total of **500 tokens per request**. Exceeding this limit will result in an error message indicating that the maximum number of tokens has been reached.

**Querverifikation (WebSearch, deepgram.com Launch-Posts 2026):** „pass up to **500 tokens (about 100 words)**". Monolingual-Deutsch-nova-3 wird mit „up to 100 domain-specific terms" beworben.

**Cap-Implikation für Layer-3-Extraktion:**
- Tokens ≈ Wortteile, nicht Zeichen. Faustregel deutscher Wortschatz: ~1.5–2 Tokens/Wort (Komposita höher). **Sicherheits-Budget: max ~80 keyterm-Einträge ODER ~250 Wörter gesamt**, dann ist man weit unter 500 Tokens.
- Konkretes Cap im Code: **harte Obergrenze `MAX_KEYTERMS = 60`** Einträge (Grundliste ~15 + bis zu ~45 Profil-Terms). Das hält uns mit Sicherheit unter 500 Tokens und ist für den Erkennungs-Boost mehr als genug.
- Über-Cap-Ordering: **Grundliste gewinnt immer** (wird zuerst eingefügt), dann Profil-Terms nach Priorität (Branche → Produktbeschreibung-Substantive → Einwand-Kategorien/Kurzlabels → FAQ/Skript-Begriffe), abgeschnitten bei `MAX_KEYTERMS`.

### Layer 3 — `build_keyterms()` Design (Signatur, Return, Dedup, Cap)

```python
import re

MAX_KEYTERMS = 60          # << 500-Token-Cap mit grossem Sicherheitsabstand
_KEYTERM_MIN_LEN = 4       # kurze Fuellwoerter (z.B. "und", "der") raus
_STOPWORDS = {"oder", "und", "der", "die", "das", "fuer", "mit", "von", "den", "ein", "eine"}

def build_keyterms(profile_daten: dict, profile_branche: str, mode: str) -> list[str]:
    """Baut die per-Call keyterm-Liste (Layer 2 fix + Layer 3 Profil-Extraktion).
    Reihenfolge = Prioritaet: Grundliste zuerst (gewinnt bei Cap), dann Profil.
    Return: deduplizierte Liste von Strings (jeder String = 1 keyterm, ggf. mehrwortig).
    Niemals persistiert — nur Transkriptions-Hint (DSGVO, siehe unten).
    """
    terms: list[str] = []
    seen: set[str] = set()   # lowercase-dedup

    def _add(t: str):
        t = (t or "").strip()
        if len(t) < _KEYTERM_MIN_LEN:
            return
        low = t.lower()
        if low in seen or low in _STOPWORDS:
            return
        if len(terms) >= MAX_KEYTERMS:
            return
        seen.add(low)
        terms.append(t)

    # Layer 2: feste Grundliste zuerst (Prioritaet, gewinnt bei Cap)
    for t in _SALES_KEYTERMS_BASE:
        _add(t)

    if not isinstance(profile_daten, dict):
        profile_daten = {}
    basis = profile_daten.get("basis") if isinstance(profile_daten.get("basis"), dict) else {}

    # Layer 3.1: Branche (DB-Column-Prioritaet, sonst basis.branche)
    _add(profile_branche or basis.get("branche") or "")

    # Layer 3.2: Markenname / Unternehmen
    _add(basis.get("unternehmen") or "")

    # Layer 3.3: Substantive aus Produktbeschreibung (Capitalized-Token-Heuristik fuer Deutsch)
    produkt = basis.get("produktbeschreibung") or ""
    for tok in re.findall(r"\b[A-ZÄÖÜ][\wäöüß\-]{3,}\b", produkt)[:10]:
        _add(tok)

    # Layer 3.4: Einwand-Kategorien + Kurzlabels (kurze Domain-Begriffe, KEINE Saetze)
    for e in (profile_daten.get("einwaende_detail") or [])[:20]:
        if isinstance(e, dict):
            _add(e.get("kategorie") or "")
            _add(e.get("kurzlabel") or "")

    return terms
```

**Design-Notizen:**
- **Tokenisierung Deutsch:** Capitalized-Token-Heuristik (`[A-ZÄÖÜ]...`) trifft im Deutschen Substantive gut (Substantive sind großgeschrieben). Bewusst simpel — kein NLP, kein neues Dependency (Margin/Automate, Punkt 12).
- **Dedup:** case-insensitive über `seen`-Set (Grundliste vs. Profil; z.B. Profil-"Einwand" wird gedroppt).
- **Cap:** `MAX_KEYTERMS` hart; Grundliste zuerst eingefügt → gewinnt strukturell.
- **`mode`-Param:** aktuell ungenutzt im Body, aber in Signatur für künftige cold_call-vs-meeting-Differenzierung (z.B. im Meeting mehr/andere Terms). Kann in Stufe-1 ignoriert werden — bewusst durchgereicht.
- **Leere Profile:** funktioniert (nur Grundliste). Keine Exceptions bei fehlenden Keys.

## Cold-Call Sprecher-Label-Fix Design

**Problem (verifiziert):** `cold_call` → `_open_deepgram_connection` setzt `diarize=is_meeting=False` (Z.317) → Deepgram liefert keine `.speaker`-Attribute → `_get_speaker` gibt `None` (Z.34-43) → `stabilize_speaker` gibt `None` → `_second_sp_seen` bleibt False → `roles_confirmed=False` (Z.70) → `sp_label='Unbekannt'`, `emit_speaker=None` (Z.82-83). Jede Cold-Call-Zeile = Unbekannt/SYSTEM.

**Fix (in `_make_on_message`, `is_final`-Zweig, um Z.78-84):**

```python
# mode via Closure-Capture (bevorzugt) ODER _session_modes.get(sid,'meeting')
if mode == 'cold_call':
    # Cold-Call ist Single-Speaker: immer der Berater (diarize=False).
    sp_label     = 'Berater'
    emit_speaker = 0
    log_sp       = 0
    roles_confirmed = True       # damit Persist (Z.116) speaker=0 schreibt statt None
elif roles_confirmed:
    sp_label     = 'Berater' if log_sp == 0 else ('Kunde' if log_sp == 1 else 'Unbekannt')
    emit_speaker = speaker
else:
    sp_label     = 'Unbekannt'
    emit_speaker = None
```

**Wiring:** `_make_on_message(sid, mode)` — `mode` beim `.on(Transcript, _make_on_message(sid, mode))` in `_open_deepgram_connection` Z.296 übergeben (mode ist dort als Parameter vorhanden, Z.288).

**Meeting-Pfad bleibt unberührt:** `mode=='meeting'` → `is_meeting=True` → `diarize=True` → bestehende `roles_confirmed`/`_second_sp_seen`-Logik unverändert. Der `if mode=='cold_call'` Zweig greift NUR im Cold-Call.

**Achtung Nebenwirkungen prüfen (Reichweite Punkt 22):**
- `merge_pending`-Key nutzt `str(speaker)` (Z.175). Im Cold-Call ist `speaker` (von `stabilize_speaker`) weiter `None` → Key `'unknown'`. Das ist OK (Merge funktioniert), aber `sp_name` (Z.168-171) basiert auf `roles_confirmed`+`speaker` → mit Fix `roles_confirmed=True` aber `speaker=None` → `sp_name='Sprecher'`. Für konsistente Cold-Call-Labels ggf. auch `sp_name='Berater'` setzen. **In Plan als expliziten Punkt aufnehmen.**
- `_second_sp_seen`/`_log_last_sp` (Z.67-76) sollten im Cold-Call-Zweig NICHT die Meeting-Heuristik anstoßen — der frühe `if mode=='cold_call'` umgeht das sauber, wenn er VOR der `_second_sp_seen`-Logik (Z.66-70) platziert wird ODER deren Ergebnis überschreibt. **Platzierung im Plan festlegen.**

## Anti-Patterns / Landmines

- **NICHT** `nerve_rt/services/stt/deepgram_adapter.py` anfassen — experimentelle Engine, NICHT der Live-Pfad. Live = `services/deepgram_service.py`.
- **Model-Swap ist NICHT optional:** `keyterm` ist **nova-3-only**. `keyterm` mit `nova-2` → Fehler/Ignore. nova-3 + keyterm MÜSSEN im selben Change landen.
- **`keyterm` vs `keywords` nicht verwechseln:** nova-2 nutzte `keywords` (anderes, schwächeres Feature). Wir entfernen ggf. kein `keywords` (war nie gesetzt) und setzen `keyterm`.
- **`keyterm` (live WS, singular) vs `keyterms` (Agent/Flux-Config, plural):** wir sind im Live-WS-Pfad → **`keyterm`**.
- **`mode` ist NICHT in `_make_on_message`** — muss verdrahtet werden (Closure-Capture bevorzugt). Ohne Wiring kein Cold-Call-Fix.
- **Reorder-Falle:** `_open_deepgram_connection` wird (Z.421) VOR dem Profil-DB-Load (Z.478+) gerufen. keyterm braucht das Profil. → Reorder nötig; nicht als Trivial-Edit behandeln.
