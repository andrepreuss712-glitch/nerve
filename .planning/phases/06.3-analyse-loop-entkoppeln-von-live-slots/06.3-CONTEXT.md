<domain>
## Phase Boundary

Den 529 `overloaded_error` beim EWB-Vorlesen strukturell unterbinden, indem der Keyword-Matcher (Phase 06.2) alleiniger Primary fuer Live-EWB wird. analyse_loop behaelt seine Intelligence-Funktionen, verliert aber jeden UI-Render-Pfad in Slot 0 und Slot 1.

**Kontext:**
- Phase 06.2 hat den Keyword-Matcher etabliert: Slot 0 <1ms, Slot 1 via streame_auto_variante parallel. Funktioniert sauber.
- analyse_loop ist der aeltere Haiku-Call-Pfad aus Phase 4.8. Feuert bei jedem Deepgram-Final sowohl Slot 0 (via analysiere_mit_claude_streaming) als auch Slot 1 (via streame_auto_variante trigger="analyse_loop").
- Problem: Zwei parallele EWB-Detect-Pfade. Beim EWB-Vorlesen fuettert der Vorlese-Text analyse_loop -> viele parallele Claude-Calls -> Anthropic 529.
- Symptom-Commits gestern (4691f38) haben den Keyword-Loop geschlossen. Der analyse_loop-Loop bleibt offen.

</domain>

<decisions>
## Implementation Decisions

### Was RAUS muss (aus services/claude_service.py analyse_loop)
- D-01: Zeilen 1047-1050: `streame_auto_variante(..., trigger="analyse_loop")`-Call entfernen. Slot 1 gehoert ab jetzt exklusiv dem Keyword-Matcher.
- D-02: Zeilen 1054-1056: `analysiere_mit_claude_streaming` darf nicht mehr in Slot 0 rendern. Empfohlener Weg: (a) In PiP-Sessions (active_sid gesetzt) auf non-streaming `analysiere_mit_claude` zurueckfallen — liefert dasselbe `ergebnis` ohne UI-Stream. Einfacher, weniger Aenderungsflaeche als Flag-Variante (b).

### Was BLEIBT (nicht anfassen, sonst Datenverlust)
- D-03: `_write_ft_assistant_event` (Zeilen 1106-1127) — FT-Trainingsdaten-Asset, Grundlage fuer spaetere eigene Sales-KI.
- D-04: Kaufbereitschafts-Tracking (1065-1099) — Basis fuer Score-UI.
- D-05: Phase-Classifier (1128-1160) — Phase 4.8 Kernfeature.
- D-06: Cold-Call-Inference (1161-1177) — Phase 4.8 Kernfeature.
- D-07: Active-Hint-Orchestration (1180-1227) — emittet allgemeine Coaching-Hints (rot/gold/orange/blau/grau) an eigenen UI-Kanal, NICHT an Slot 0/1. Diese Hints sind kein EWB und gehoeren nicht zum Keyword-Matcher.

### Architektur-Fragen (Planner entscheidet)
- D-08: Fallback-Variante (a) oder Flag-Variante (b)? Welche erzeugt weniger Regression-Risiko auf dem non-PiP-Legacy-Pfad? Empfehlung: (a).
- D-09: Der `slot1_variant_busy_until`-Lock aus 06.2 (services/live_session.py:132) — kann er vereinfacht/entfernt werden wenn nur noch ein Schreiber bleibt? Oder als Safety-Net drinlassen fuer manual_ewb oder zukuenftige Pfade?
- D-10: ANALYSE_INTERVALL — sollte bei nur noch Intelligence-Zwecken (kein UI-Stream) verlaengert werden? Weniger Claude-Calls, weniger Kosten, weniger 529-Risiko. Kandidat: 3-5s.
- D-11: Gibt es Code der `analyse_loop._last_slot` / `_last_slot_time` liest (Zeilen 1030-1031)? Wenn nur fuer eigene Logik gesetzt -> mit entfernen.

### Scope-Grenzen (nicht anfassen)
- Keyword-Matcher (Phase 06.2) — fertig, bleibt wie er ist.
- Meeting-Modus — analyse_loop laeuft dort genauso, aber das 529-Problem tritt da nicht auf (kein EWB-Vorlesen). Verhalten identisch lassen.
- manual_ewb-Pfad — unberuehrt.
- `streame_auto_variante` selbst bleibt, wird nur nicht mehr vom analyse_loop aufgerufen.
- Kein Prompt-Tuning, kein Kostenmonitoring-Umbau in dieser Phase.

</decisions>
