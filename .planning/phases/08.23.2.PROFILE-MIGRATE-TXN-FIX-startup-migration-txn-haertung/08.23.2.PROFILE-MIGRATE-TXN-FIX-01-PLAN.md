<objective>
Härtet die beiden Startup-Profil-Migrationspfade gegen die Postgres-Transaktions-Vergiftung, die
bei JEDEM Start ein versions-loses Profil unmigriert lässt und `[Schema]`-Fehler wirft.

**Root-Cause (Fable + Claudian, Code+Prod-verifiziert):** `_migrate_profile_json()` (app.py:1379)
fährt bei jedem Start `ALTER TABLE profile_opener ADD COLUMN type …` (:1423) in `try/except: pass`
OHNE rollback. Die Spalte `type` **existiert schon** → **DuplicateColumn** vergiftet die
Postgres-Transaktion → alle Folge-Statements (ProfileOpener-sync :1454, UPDATE :1504) sterben still
als `InFailedSqlTransaction`. Sichtbar nur bei einem versions-losen Profil. Postgres-only (auf
SQLite unsichtbar). Fingerabdruck `"Profile ?"` im Log.

**Scope = Option A + Wächter (LOCKED, CONTEXT.md):** (1) Mine raus, (2) rollback-Hygiene in jedem
conn-except, (3) Pro-Profil-Savepoint im v4-Batch, plus die Deferral-Guards (a)/(b)/(c). Die
Konsolidierung der zwei Pfade ist DEFERRED (Backlog `PROFILE-MIGRATE-CONSOLIDATE`); die Guards
sichern das Risiko bis dahin sichtbar/kontrolliert ab.

**★ Cross-Layer-Korrektur (Punkt 21/22 — VOR dem Plan gefangen):** `profiles` hat KEINE Spalte
`schema_version` (der v4-Batch liest `_daten.get('schema_version')` app.py:1009; `daten` = Text-JSON).
Die Guards (a)/(b) MÜSSEN `schema_version` aus dem `daten`-JSON lesen (`SELECT daten` → `json.loads`),
NICHT via nicht-existentem Spalten-SELECT und NICHT via `daten::json->>` (PG-only, Text-Spalte).

Purpose: kein vergifteter Start mehr, kein stiller Migrations-Ausfall, Regress sichtbar.
Output: app.py-Härtung + Erst-Rot-Regressions-Waechter + CLAUDE.md-Regel (+ optional grep-Guard).
