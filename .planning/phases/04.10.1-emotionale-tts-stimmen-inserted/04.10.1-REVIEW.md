## Summary

Reviewed the mood-to-voice-settings mapping (`MOOD_VOICE_ZONES`, `mood_to_voice_settings`), secretary voice presets (`SEKRETAERIN_TYPES`), and the integration of voice settings into the training routes. The core mapping logic in `training_service.py` is clean, well-structured, and properly tested. However, there is a critical scoping bug in `routes/training.py` where a nested helper function is called from a different function, which will crash at runtime on a specific code path. Two additional warnings for thread-safety and error-path issues.

## Critical Issues

### CR-01: `_detect_female` is a nested function inaccessible from `training_respond`

**File:** `routes/training.py:498`
**Issue:** `_detect_female` is defined as a nested function inside `training_start()` at line 280. It is then called at line 498 inside `training_respond()`, which is a completely separate function. This will raise a `NameError: name '_detect_female' is not defined` at runtime whenever a secretary is overcome during a training respond cycle (i.e., when `[DURCHGESTELLT]` appears in the customer response). This path is exercised every time a user successfully passes the secretary in `sekretaerin` mode.
**Fix:** Move `_detect_female` to module-level scope (before the route definitions), so it is accessible from both `training_start` and `training_respond`.
```python
# Move to module level, e.g., after line 42
def _detect_female(pd, gp):
    """Check geschlecht field or detect from common German female first names."""
    for src in [gp, pd]:
        if isinstance(src, dict) and src.get('geschlecht') == 'w':
            return True
    name = ''
    if isinstance(pd, dict):
        name = pd.get('name', '')
    if isinstance(gp, dict) and not name:
        name = gp.get('name', '')
    first = name.split()[0].rstrip(',') if name else ''
    female_names = {'anna','andrea','angelika','birgit', ...}  # keep full set
    return first.lower() in female_names
```

## Warnings

### WR-01: Session dict mutated outside lock in `training_respond`

**File:** `routes/training.py:447`
**Issue:** `neue_stimmung = session.get('stimmung', 0)` reads from the session dict at line 447, and later `session['aufgelegt'] = True` is set at line 512-513 outside of `_sessions_lock`. While the session dict reference is obtained under the lock at line 427, subsequent mutations at lines 489-514 happen inside a *different* `with _sessions_lock:` block at line 488. Between lines 447 and 488, the `generate_response_with_mood` call happens without the lock, which is correct for avoiding blocking, but the pattern of reading `session` (a mutable dict reference) without the lock and then mutating it under a separate lock acquisition creates a subtle race condition if two requests for the same user overlap.
**Fix:** This is mitigated by the fact that training is single-user-per-session, but consider documenting the thread-safety assumption. Alternatively, copy the needed values from session under the lock rather than holding a reference:
```python
with _sessions_lock:
    session = _sessions.get(g.user.id)
    if not session:
        return jsonify({'error': 'Keine aktive Session'}), 400
    current_mood = session.get('stimmung', 0)
    # copy other needed values
```

### WR-02: `db_log` may be unbound in `finally` block on early exception

**File:** `routes/training.py:745-751`
**Issue:** If `get_session()` at line 689 raises an exception, `db_log` will not be defined when the `finally` block at line 747-751 attempts `db_log.close()`. The inner `try/except` at line 748 catches this, but it silently swallows what is actually a database connection failure, making it hard to diagnose.
**Fix:** Initialize `db_log = None` before the try block, and check before closing:
```python
db_log = None
try:
    db_log = get_session()
    # ... rest of logging code
except Exception as ex:
    print(f"[Training] ConversationLog-Speicherung Fehler: {ex}")
finally:
    if db_log:
        try:
            db_log.close()
        except Exception:
            pass
```

## Info

### IN-01: Hardcoded `_CODE_VERSION` deployment hash

**File:** `routes/training.py:42`
**Issue:** `_CODE_VERSION = '45b02eb'` is a hardcoded git short hash used for deploy verification at the `/training/ping` endpoint. This value will become stale after any new commit and gives a false sense of version tracking.
**Fix:** Consider reading the version dynamically from git or a build artifact, or accept that this is intentionally manual and add a comment noting it must be updated on deploy.

### IN-02: Bare `except Exception: pass` patterns in multiple locations

**File:** `routes/training.py:92,118,256,745`
**Issue:** Several broad `except Exception` blocks silently swallow errors with only a print statement or no handling at all. While this follows the project convention of "silent failures in non-critical operations," it can make debugging production issues difficult, especially for the voice-check (line 92) and fair-use counter (line 118) paths which affect billing logic.
**Fix:** Consider logging at a higher severity or including more context in the print messages, especially for billing-related operations.
