# Cross-AI Plan Review — Phase 08.20.2

## Claude Review

### Summary

Phase 08.20.2 is a well-scoped, purposeful architectural upgrade to the PreCall briefing system. The core idea — replacing a single free-text Claude call with a structured 3-layer output (Schicht-1 structured fields, Schicht-2 hardened narrative, Schicht-3 recommendations) — is sound and directly addresses the hallucination problem in AI-generated company research. The plans are detailed and internally consistent. The wave ordering (service → DB → UI + tests) is correct. The main areas of concern are around the Schicht-3 dependency chain, the frontend precall_fields persistence flow, and a few edge cases in the validation logic.

---

### Plan 01 Review: Rebuild precall_service.py

#### Strengths
- **Graceful degradation is well-designed.** JSON parse failure → all 4 Pflichtfelder → not_found is exactly the right fallback. No crash, no empty UI.
- **not_found normalization is explicit.** The `NOT_FOUND_FIELD` constant and the validation loop that enforces `value='not_found'` + `source_url=None` closes a real trust attack vector (LLM hallucinating a value but marking it not_found).
- **Optional field pruning is correct.** Removing optional fields when confidence=not_found prevents polluting the UI with unverified optional noise.
- **Separation of Schicht-3 into its own function** (`_generiere_empfehlungen()`) is clean — it keeps the Schicht-1+2 call synchronous and testable independently.
- **Cache key includes profile_id.** Correct — without this, a user switching profiles mid-session would get stale Schicht-3 recommendations.
- **Cost tracking carried over to `_generiere_empfehlungen()`.** Important for budget visibility on a Bootstrap project.

#### Concerns
- **[HIGH] Schicht-3 call silently no-ops when `sid=None`.** If `sid` is None (e.g., user calls recherche_firma without an active session, or profile_id cache hit before session starts), `_generiere_empfehlungen()` calls `build_profile_context(user_id=user_id, sid=None)`. Depending on what `build_profile_context()` returns for sid=None, Section 8 (PreCall-Briefing) will be empty — i.e., `_generiere_empfehlungen()` runs BEFORE the briefing is in the per-sid cache. This creates a chicken-and-egg: `set_briefing_for_sid(sid, ...)` needs a non-None sid to actually cache, and `build_profile_context(sid=None)` won't see Section 8. The result is empfehlungen without PreCall context, which is less useful but not broken. The plan acknowledges this with "non-fatal" error handling. The risk is that this happens silently and the user sees impoverished empfehlungen without knowing why.
- **[MEDIUM] Two Sonnet calls per recherche_firma() increases latency.** Plan 01 adds a second Claude call (Schicht-3, max_tokens=400). Total latency is now 2× Sonnet round-trips + Brave Search. For a pre-call preparation use case this may be fine (not in the live loop), but the plan doesn't mention the user-perceived latency or whether there's a loading indicator that covers it.
- **[MEDIUM] `verified_facts` list in `_generiere_empfehlungen()` may be empty for new or obscure companies.** If all 4 Pflichtfelder are not_found, `verified_facts` is empty and the function returns `''`. This is correct per the plan, but the frontend (Plan 03) only hides Sektion C when empfehlungen is falsy — no explanation to the user about WHY there are no recommendations (insufficient data vs. API error). Low-trust obscure companies are exactly the ones where a pre-call coaching prompt would be most valuable, but they'd get no Sektion C.
- **[MEDIUM] `_brave_search()` query change may break existing behavior.** The new query `f"{firmenname} Impressum Geschäftsführer Mitarbeiterzahl {branche or ''}"` is German-biased which is correct for DACH, but the existing function also accepts `ansprechpartner`. The plan says to remove the old multi-part query logic — check whether the current query also includes ansprechpartner for context (e.g., to find LinkedIn profiles of the contact). If ansprechpartner is dropped from the query, it may reduce the quality of contact-specific search results.
- **[LOW] `extra_keys` not stripped from field dicts.** The validation loop checks that `value/source_url/confidence` are present, but doesn't remove extra keys. If Claude returns `{"value": "...", "source_url": "...", "confidence": "...", "notes": "..."}` the test `test_schicht1_field_struct_exact_keys` (Plan 04) asserts `set(val.keys()) == {'value', 'source_url', 'confidence'}` — this will FAIL because the validation in Plan 01 does not strip extra keys, only validates presence. The test and the implementation may be inconsistent.

#### Suggestions
- Add a log message when `_generiere_empfehlungen()` returns `''` due to no verified_facts: `print(f"[PreCall] Empfehlungen: keine verifizierten Felder fuer {firmenname}")`. This makes the behavior observable without adding frontend complexity.
- Consider explicitly stripping extra keys in the field validation loop: `fields[key] = {k: v for k, v in val.items() if k in ('value', 'source_url', 'confidence')}`. This ensures the 3-key contract is hard-enforced, not just checked.
- Document the sid=None behavior explicitly in `_generiere_empfehlungen()` docstring so future maintainers don't accidentally rely on Section 8 being populated.

#### Risk Assessment: **MEDIUM**

The architecture is sound. The main risk is the extra-keys contract gap between Plan 01 implementation and Plan 04 tests, which will cause a test failure unless both are aligned. The Schicht-3 latency impact and the sid=None silent degradation are known trade-offs but should be visible to the developer.

### Plan 02 Review: DB schema + route integration

#### Strengths
- **Migration uses silent-fail pattern.** Idempotent migrations via `try/except pass` is the established project pattern — correct and safe.
- **`isinstance(precall_fields_raw, dict)` guard in api_beenden.** Prevents string injection or malformed frontend payloads from crashing JSON serialization.
- **Existing `precall_briefing` column explicitly preserved.** The plan notes "no regression" — important since existing PostCall analysis may depend on precall_briefing.
- **Route verification uses Flask test client (not source-presence).** The automated verify tests check actual route existence via HTTP status codes, not grep.

#### Concerns
- **[HIGH] Frontend may not send `precall_fields` if the user doesn't go through Step 4 of the PreCall modal.** Plan 02 assumes the api_beenden POST body contains `precall_fields` — but what if the user ends the session without completing the PreCall modal (e.g., they skip it, or the session starts without a PreCall)? In that case `precall_fields_raw` is None/absent, `precall_fields_json` is None, and `ConversationLog.precall_fields` is NULL. This is fine (nullable column), but it means the PostCall analytics will have partial data for sessions that skipped PreCall. The plan doesn't address whether this is acceptable or whether there's a fallback path.
- **[MEDIUM] `profile_id` from `flask_session.get('active_profile_id')` may be None.** This is handled gracefully in recherche_firma() via the `_None` suffix in cache key, but the plan should explicitly mention this path to avoid confusion during implementation.
- **[MEDIUM] `import json as _json_pf` in the middle of api_beenden.** The plan notes to use `_json_pf` alias to avoid shadowing if `_json` is already in scope. This is a fragile approach — the implementation task should check whether `json` is already imported at the module level in app_routes.py and use that import consistently.
- **[LOW] No verification that `briefing['fields']` reaches the frontend.** The plan says `return jsonify({'briefing': briefing})` stays unchanged, and notes "the briefing dict now has `fields` and `empfehlungen` keys which the frontend will use in Plan 03." But Plan 02 has no test that verifies `fields` is present in the JSON response — it only verifies the route accepts the request. A regression in Plan 01 (missing `fields` key) would pass Plan 02's tests.

#### Suggestions
- Add a comment in api_beenden at the precall_fields extraction point noting the nullable path: `# precall_fields is None when session ended without completing PreCall modal — stored as NULL in DB`.
- Consider adding to the Plan 02 verify step: `assert 'fields' in response_data['briefing']` for a logged-in user with a mocked recherche_firma() — this would catch Plan 01 regressions early.

#### Risk Assessment: **LOW-MEDIUM**

The DB and migration work is straightforward and follows established patterns. The main risk is the frontend data flow assumption (precall_fields always sent in api_beenden). This is an integration gap between Plan 02 (backend) and Plan 03 (frontend) that could result in NULL precall_fields for many sessions.

### Plan 03 Review: UI — 3-section PreCall modal

#### Strengths
- **3-section DOM order (A→B→C) matches UX priority.** Verified data first, narrative second, recommendations third. This is the right information hierarchy for a trust-focused feature.
- **`not_found` fields always visible.** Showing "Nicht gefunden" instead of hiding absent fields is correct — it tells the user the system looked and didn't find it, rather than silently omitting the field.
- **`escHtml()` applied to all field values.** Critical for XSS prevention given field values come from Claude (which synthesizes web data).
- **Confidence-based CSS classes.** Using `confidence-` prefix on cell-level classes instead of inline styles keeps the design system consistent.
- **`Analyse anpassen` only toggles Sektion B.** Correct — the structured Schicht-1 grid should not be editable (it's sourced from AI + web, not user-entered text).

#### Concerns
- **[HIGH] `mdToHtml(empfehlungen)` on Schicht-3 output creates XSS risk if `mdToHtml` doesn't sanitize.** The plan marks T-08.20.2-10 (mdToHtml for briefingText) as "accept" because it's existing behavior — but `empfehlungen` is a NEW path through mdToHtml. If mdToHtml uses innerHTML directly without sanitization, and if Schicht-3 empfehlungen text contains user-controlled company data (via the `firmenname` interpolation in `_generiere_empfehlungen()`), this is an XSS vector. The threat model should be MITIGATE, not ACCEPT, for `empfehlungen`.
- **[MEDIUM] No loading state for the 2-call scenario.** The frontend sends the PreCall request and waits for BOTH Schicht-1+2 AND Schicht-3 calls to complete before rendering Step 4. With two Sonnet calls, total server latency may be 4-8 seconds. There's no mention of a loading indicator or progressive rendering (show Schicht-1+2 first, stream Schicht-3 when ready). This may create a poor UX with a long blank wait.
- **[MEDIUM] `FIELD_LABELS` dict in JS uses German display names but English CSS identifiers.** This is correct per CLAUDE.md rules, but the German labels (e.g., 'Geschäftsführer') will only render correctly if the page charset and JS file encoding are UTF-8. The plan doesn't mention encoding verification for pip-launcher.js.
- **[LOW] `buildFieldCell()` inner function defined in `renderStep4()` on every render call.** In a vanilla JS codebase without a module bundler, this is a minor inefficiency but not a correctness issue. Could be hoisted to module scope.
- **[LOW] `lnr-step4-edit` button only visible when `hasAnyData` is true.** But the textarea `lnr-briefing-edit` only exists when `briefingText` is non-empty (separate condition). If `hasAnyData` is true due to fields only (no text), the edit button renders but clicking it will try `document.getElementById('lnr-briefing-edit')` which returns null — the `if (!view || !edit) return;` guard handles this, but the edit button is still visible and confusingly inert.

#### Suggestions
- Clarify in Plan 03's threat model that `empfehlungen` goes through `mdToHtml()` and should be treated same as `briefingText` for XSS considerations — change T-08.20.2-10 disposition to MITIGATE or add a separate threat entry.
- Consider showing fields (Schicht-1 grid with confidence icons in a "loading" state) while Schicht-3 is being fetched. This is a UX improvement but is out of scope for this phase — add as a note to the deferred list.
- Hide `lnr-step4-edit` button when `briefingText` is empty (add `&&briefingText` condition).

#### Risk Assessment: **MEDIUM**

The UI is well-structured. The XSS risk on `empfehlungen` via `mdToHtml` and the loading state gap are the main concerns. The XSS risk depends on the existing `mdToHtml()` implementation — if it already sanitizes output, this is acceptable; if not, it's a security issue.

### Plan 04 Review: TDD — Schema contract tests

#### Strengths
- **5 tests cover the key schema invariants.** The test coverage directly maps to the D-08 decisions: required fields, confidence whitelist, not_found normalization, optional field pruning, graceful degradation.
- **Monkeypatch pattern is correct.** `monkeypatch.setattr(ps, 'claude_client', ...)` replaces the module-level attribute cleanly without requiring Flask application context.
- **Test 5 (graceful degradation) uses realistic non-JSON input.** "Sorry, ich kann das nicht beantworten." is a plausible real-world LLM refusal — good choice of test input.
- **No `inspect.getsource()` anywhere.** Compliant with CLAUDE.md test quality rule.

#### Concerns
- **[HIGH] Test 3 (`test_schicht1_field_struct_exact_keys`) will fail if Plan 01 doesn't strip extra keys.** The test asserts `set(val.keys()) == {'value', 'source_url', 'confidence'}` — but Plan 01's validation loop only normalizes malformed fields; it does NOT strip extra keys from well-formed fields. If Claude returns a field with an extra key (e.g., `"notes": "..."`), Plan 01 passes the field through unchanged, and Test 3 fails. The fix must be in Plan 01's implementation (strip extra keys), or Test 3 must be weakened to only check required-keys-are-present rather than exact-key-set equality.
- **[MEDIUM] Test 4 (optional field present when found) depends on Plan 01 NOT stripping the optional field.** The test verifies `gruendungsjahr` with `confidence='high'` appears in the result. This is correct per spec. Just ensure Plan 01's optional field pruning only removes not_found optional fields, not all optional fields — the code shows this is the intent, but it should be verified.
- **[LOW] No test for `quellen_count` or the `firmenname`/`ansprechpartner` passthrough in the return dict.** These are not schema-critical but they are part of the defined return contract and a regression there would break Plan 02's route logic.

#### Suggestions
- **Fix the extra-keys gap** before Plan 04 runs: add key-stripping to Plan 01's field validation loop. This is a one-line fix: after the confidence whitelist check, replace the field dict with only the 3 allowed keys.
- Add a sixth test (`test_schicht1_return_dict_keys`) that verifies the top-level return dict has all 5 required keys: `{'fields', 'text', 'firmenname', 'ansprechpartner', 'quellen_count'}`. This guards against Plan 02 breaking when it tries to access `briefing['fields']`.

#### Risk Assessment: **LOW**

Plan 04 is well-written. The only actionable issue is the extra-keys inconsistency with Plan 01 — it's a concrete gap that will cause a test failure on first run, requiring either a Plan 01 fix or a test adjustment.

## Consensus Summary

### Agreed Strengths
- **3-layer architecture is well-motivated and correctly implemented.** The separation of Schicht-1 (facts), Schicht-2 (narrative), Schicht-3 (recommendations) maps cleanly to the trust-and-verify goal.
- **Graceful degradation is thorough.** JSON parse errors, missing fields, API failures — all paths return a usable (if empty) result rather than crashing.
- **Wave ordering and dependencies are correct.** Service → DB → UI+Tests is the right sequence.
- **not_found enforcement is robust.** Normalizing invented values on not_found confidence fields directly addresses the hallucination risk.

### Agreed Concerns

1. **[HIGH] Extra-keys contract gap between Plan 01 and Plan 04.** Plan 01 validates but doesn't strip extra keys from field dicts. Plan 04's `test_schicht1_field_struct_exact_keys` asserts exact key equality. This will fail on first run unless Plan 01 also strips extra keys.

2. **[HIGH] Schicht-3 call depends on sid being set — silent degradation when sid=None.** The empfehlungen quality depends on Section 8 (PreCall-Briefing) being in the cache. If sid is None (session not yet started), `_generiere_empfehlungen()` produces weaker recommendations without the briefing context. This is silent and not surfaced to the user.

3. **[MEDIUM] Frontend may not send `precall_fields` if PreCall modal is skipped.** The api_beenden route assumes the frontend sends precall_fields. Sessions where the user skips PreCall will have NULL precall_fields in ConversationLog — potentially most sessions in early usage.

4. **[MEDIUM] XSS risk on `empfehlungen` via `mdToHtml()`.** Schicht-3 output goes through mdToHtml() — the existing XSS posture for this function should be verified before accepting it as safe for the new Schicht-3 path.

### Divergent Views

No divergent views (single reviewer session). The concerns above are ranked by likely impact on the phase goals.
