### WR-01: Cost-Tracker Logs Input Tokens as Output Tokens in `_generiere_empfehlungen`

**File:** `services/precall_service.py:477-483`
**Issue:** Both `log_api_cost` calls in `_generiere_empfehlungen` use `unit_type='per_1k_output_tokens'`. The first call (line 477-480) should use `'per_1k_input_tokens'` for `in_tok`. This copies the same bug pattern from `_generiere_briefing` lines 342-346 (which is correct there). In the empfehlungen function both calls pass output type, so input token costs are systematically undercounted in the cost dashboard for this call site.

**Fix:**
```python
log_api_cost('anthropic', _cost_model, user_id=user_id,
             units=in_tok/1000.0, unit_type='per_1k_input_tokens',  # <-- was per_1k_output_tokens
             context_tag='precall_empf', latency_ms=_latency_ms,
             call_site='precall_empf')
log_api_cost('anthropic', _cost_model, user_id=user_id,
             units=out_tok/1000.0, unit_type='per_1k_output_tokens',
             context_tag='precall_empf', call_site='precall_empf')
```

### WR-02: `/api/launcher/init` Fetch Missing CSRF Token

**File:** `static/pip-launcher.js:119`
**Issue:** The `fetch('/api/launcher/init')` call in the `open()` function is a GET request and does not send `X-CSRFToken`. While Flask-WTF does not enforce CSRF on GETs by default, the pattern is inconsistent with all other fetch calls in the file (which correctly include `getCsrfToken()`). More importantly, if the server-side CSRF configuration is ever tightened to cover GETs (or the endpoint is changed to POST for caching reasons), this will break silently. In addition, there is no error status check — a 4xx/5xx response is consumed as a successful JSON parse attempt, which can produce confusing silent failures.

**Fix:**
```javascript
fetch('/api/launcher/init', {
  headers: { 'X-CSRFToken': getCsrfToken() }
})
  .then(function (r) {
    if (!r.ok) throw new Error('init failed: ' + r.status);
    return r.json();
  })
  .then(function (data) { /* ... */ })
  .catch(function (err) {
    var c = content();
    if (c) c.innerHTML = '<div style="color:#f87171;text-align:center;padding:20px">Fehler beim Laden. Bitte Seite neu laden.</div>';
  });
```

### WR-03: `_briefing_cache` Is a Module-Level Mutable Dict — Thread-Safety Risk

**File:** `services/precall_service.py:21-22`
**Issue:** `_briefing_cache` is a plain `dict` mutated from request threads (write on miss, delete on eviction). Flask with `async_mode='threading'` (as configured in `app.py`) runs each request in its own thread. Concurrent requests for the same `cache_key` can cause a lost-update (two threads both see a cache miss, both call Brave + Claude) or, in the worst case with CPython dict resizing, a dict corruption under GIL contention during `del _briefing_cache[k]` while another thread iterates `_briefing_cache.items()`. At low user volume this is unlikely but not impossible.

**Fix:** Use a `threading.Lock` to guard reads and writes:
```python
import threading
_briefing_cache = {}
_cache_lock = threading.Lock()
_CACHE_TTL_S = 300

# In recherche_firma():
with _cache_lock:
    now = time.time()
    stale_keys = [k for k, (_, ts) in _briefing_cache.items() if now - ts >= _CACHE_TTL_S]
    for k in stale_keys:
        del _briefing_cache[k]
    cached = _briefing_cache.get(cache_key)

# ... after generating briefing:
with _cache_lock:
    _briefing_cache[cache_key] = (briefing, time.time())
```

**Issue:** `precall_briefing = precall_briefing[:2000]` uses a hardcoded limit with no comment or constant explaining why 2000 characters. This is not a bug but will confuse future maintainers and is inconsistent with the project convention of naming limits as constants (e.g. `_CACHE_TTL_S`).

**Fix:**

_PRECALL_BRIEFING_MAX_CHARS = 2000  # DB column TEXT but EWB-Context budget constraint

if isinstance(precall_briefing, str) and len(precall_briefing) > _PRECALL_BRIEFING_MAX_CHARS:
