## Summary

This phase delivers per-SID state isolation for WebSocket sessions (DSGVO) and related cleanup. The core infrastructure — `init_session_state`, `pop_session_state`, `set_profile_for_sid`, `get_profile_for_sid`, per-SID coaching/transcript buffers — is well-structured with correct locking and ghost-SID guards throughout. The test suite correctly uses runtime-behavior assertions (no source-presence checks).

One critical bug was found: `ls.load_learning_cards()` in `routes/app_routes.py` is called with the old one-argument signature `load_learning_cards(g.user.id)` while the function now requires two arguments `(sid, user_id)`. This causes a `TypeError` crash at runtime when `/api/set_profile` is called. Three warnings cover residual global-state reads that coexist with the new per-SID infrastructure (the HIGH-2 coexistence pattern) and a missing anrede migration column. Three info items cover minor code quality issues.

## Critical Issues

### CR-01: `load_learning_cards` called with wrong arity — crashes `/api/set_profile`

**File:** `routes/app_routes.py:800`
**Issue:** `ls.load_learning_cards(g.user.id)` passes only `user_id`. The function signature in `services/live_session.py:448` is `def load_learning_cards(sid: str, user_id: int)`, requiring `sid` as first argument. Every call to `/api/set_profile` will raise `TypeError: load_learning_cards() missing 1 required positional argument: 'user_id'` — the profile will not be updated and the endpoint will 500.

The caller is in a `try/finally` block that still closes `db`, but the exception propagates past the `db.close()` finally and causes an HTTP 500 response.

**Fix:**
```python
# routes/app_routes.py:800 — needs the WebSocket SID for per-SID state
# The SID is not available in this HTTP route context.
# Two options:
#
# Option A (correct): use the sid from flask_session if stored there at session start
sid = flask_session.get('ws_sid')   # requires storing sid at handle_start_live_session
if sid:
    ls.load_learning_cards(sid, g.user.id)
#
# Option B (safe no-op): skip load_learning_cards in the HTTP profile-set route —
# learning cards are already loaded by handle_start_live_session per-SID at call start.
# Removing this call is correct because handle_start_live_session now calls
# ls.load_learning_cards(sid, user_id) with the correct sid.
# ls.load_learning_cards(g.user.id)   ← DELETE this line
```

## Warnings

### WR-01: `_write_ft_assistant_event` reads from module-level `ls.state` — not per-SID

**File:** `services/claude_service.py:164-170`
**Issue:** `_write_ft_assistant_event` acquires `ls.state_lock` and reads `ls.state.get('ft_session_id')`, `ls.state.get('mode')`, `ls.state.get('user_id')`, etc. These are module-level globals from the old single-session model. With multiple concurrent WebSocket sessions these values reflect whichever session last wrote them. In a multi-user scenario, an FT event written for session A may record `user_id` from session B if session B started more recently.

This is a known coexistence issue flagged in `init_session_state` comments (HIGH-2), but the FT logging path is not covered by the per-SID migration done in this phase, so the data quality risk is active in production once more than one user connects simultaneously.

**Fix:** Pass `sid` into `_write_ft_assistant_event` and read from `ls._session_state[sid]['state']` instead of the module-level `ls.state`:
```python
def _write_ft_assistant_event(module, hint_type, hint_text, model_used,
                               context=None, sid=None):
    ...
    if sid:
        with ls._session_state_lock:
            _s = ls._session_state.get(sid, {}).get('state', {})
            ft_session_id = _s.get('ft_session_id')
            mode          = _s.get('mode') or 'cold_call'
            user_id       = _s.get('user_id')  # note: user_id is top-level, not in 'state'
            ...
    else:
        # legacy fallback
        with ls.state_lock:
            ft_session_id = ls.state.get('ft_session_id')
            ...
```
(Track as a follow-up in Block M / Phase 08.19.6.)

### WR-02: `analyse_loop` reads learning cards from module-level `ls.state` — per-SID write is orphaned

**File:** `services/claude_service.py:916`
**Issue:** `_lk_cards = ls.state.get('active_learning_cards', [])` in the `analyse_loop` reads from the module-level `state` dict. `load_learning_cards(sid, user_id)` now correctly writes to `_session_state[sid]['state']['active_learning_cards']` (line 456 in `live_session.py`), but `analyse_loop` never reads from `_session_state[sid]`. The per-SID write is effectively a no-op for the hot path — learning cards remain shared/last-writer-wins via the module-level `ls.state`.

**Fix:** In `analyse_loop`, read per-SID learning cards:
```python
# Inside analyse_loop, after determining active sid:
with ls._session_state_lock:
    _lk_cards = ls._session_state.get(sid, {}).get('state', {}).get('active_learning_cards', [])
```
(Also a follow-up item — same cluster as WR-01.)

### WR-03: Missing migration for `conversation_logs.anrede` column — `api_beenden` will crash on existing DBs

**File:** `app.py` (migration block, lines 246-403)
**Issue:** `ConversationLog.anrede` is used in `routes/app_routes.py:261` (`anrede=_session_anrede`) and defined in `database/models.py:309`. However, there is no `ALTER TABLE conversation_logs ADD COLUMN anrede VARCHAR(10)` in `app.py`'s `_migrate()` function. On any DB created before this column was added to the model, `db_conv.commit()` at line 264 (in `api_beenden`) will raise `OperationalError: table conversation_logs has no column named anrede`, causing the entire call-end flow to fail — no `ConversationLog` is saved, `saved_conv_id` stays `None`, and the user sees a 500 or empty postcall.

**Fix:** Add to the `conversation_logs` migration block in `app.py`:
```python
for col, typedef in [
    # ... existing entries ...
    ('anrede', 'VARCHAR(10)'),   # Phase 08 D-14: Du/Sie override per session
]:
    try:
        conn.execute(text(f'ALTER TABLE conversation_logs ADD COLUMN {col} {typedef}'))
        conn.commit()
        print(f"[DB] Migration: added conversation_logs.{col}")
    except Exception:
        pass
```

### IN-01: `datetime.utcnow()` in `admin_ewb.py` — inconsistent with project `utcnow()` helper

**File:** `routes/admin_ewb.py:190`
**Issue:** `existing.rated_at = datetime.utcnow()` uses the stdlib `datetime.utcnow()` directly. The project's `database/models.py` defines a `utcnow()` helper that uses `datetime.now(timezone.utc).replace(tzinfo=None)` (timezone-aware construction then strip tzinfo). While functionally equivalent for SQLite, it creates an inconsistency. Python 3.12 deprecates `datetime.utcnow()`.

**Fix:**
```python
from database.models import utcnow
# ...
existing.rated_at = utcnow()
```

### IN-02: `test_ab_stats.py` — `TrainingScenario.name.like('[P08-%')` has unbalanced bracket

**File:** `tests/test_ab_stats.py:118`
**Issue:** The LIKE pattern `'[P08-%'` has an opening bracket but no closing bracket. In SQL `LIKE`, square brackets are standard wildcards in some databases (SQL Server) but not in SQLite. SQLite treats `[` as a literal character, so this pattern actually works as intended on SQLite (matches strings starting with literal `[P08-`). However, the inconsistency between intended meaning and pattern syntax is a latent bug if the DB backend ever changes, and the pattern string looks like a typo (the test author likely meant `'[P08-%]'` as a character class, or simply `'[P08-%'` as a literal prefix match for SQLite).

No immediate bug on SQLite, but worth documenting clearly.

**Fix:** Add a comment clarifying this is intentional for SQLite literal-bracket matching:
```python
# SQLite LIKE: '[' is a literal character (not a wildcard like SQL Server).
# This pattern matches scenario names that literally start with '[P08-'.
count = db_session.query(TrainingScenario).filter(
    TrainingScenario.name.like('[P08-%')
).count()
```

### IN-03: `deepgram_service.py` — `slot1_variant_busy_until` read/write split across per-SID and module-level state

**File:** `services/deepgram_service.py:147-151`
**Issue:** In `_make_on_message`, `slot1_variant_busy_until` is read and written via `ls.state` (module-level) with `ls.state_lock`. The new `_session_state[sid]['state']` dict initializes `slot1_variant_busy_until: 0.0` per-SID (live_session.py line 317), but this interim-transcript handler still reads and writes the global one. With two concurrent sessions, one user's keyword-match can suppress the other user's slot-1 variant for up to 6 seconds.

**Fix:** (Follow-up, same cluster as WR-01/WR-02.) Read/write from `_session_state[sid]['state']` instead:
```python
with ls._session_state_lock:
    _busy = ls._session_state.get(sid, {}).get('state', {}).get('slot1_variant_busy_until', 0)
if _now >= _busy:
    with ls._session_state_lock:
        if sid in ls._session_state:
            ls._session_state[sid]['state']['slot1_variant_busy_until'] = _now + 6
```
