## Fixed Issues

### CR-01: `load_learning_cards` called with wrong arity — crashes `/api/set_profile`

**Files modified:** `routes/app_routes.py`
**Commit:** `cbb3842`
**Applied fix:** Removed the `ls.load_learning_cards(g.user.id)` call at line 800 (Option B from review). Replaced with a comment explaining why: the HTTP route has no WebSocket SID, and `handle_start_live_session` already calls `load_learning_cards(sid, user_id)` with the correct SID at session start. The call was a no-op in the new per-SID model and would have caused a `TypeError` (missing required positional argument `user_id`) on every `/api/set_profile` request.

### WR-03: Missing migration for `conversation_logs.anrede` column

**Files modified:** `app.py`
**Commit:** `ad23b00`
**Applied fix:** Added `('anrede', 'VARCHAR(10)')` entry to the existing `conversation_logs` ALTER TABLE migration loop (lines 246-260 in `app.py`), with inline comment `# Phase 08 D-14: Du/Sie override per session`. This ensures existing databases created before this column was added to the model will be migrated automatically on next startup, preventing `OperationalError: table conversation_logs has no column named anrede` during `api_beenden`.

## Skipped Issues

### WR-01: `_write_ft_assistant_event` reads from module-level `ls.state` — not per-SID

**File:** `services/claude_service.py:164-170`
**Reason:** Intentional deferral to Phase 08.19.6. The fix requires passing `sid` through the FT-logging call chain and reading from `ls._session_state[sid]` instead of module-level `ls.state`. This is a multi-caller refactor and out of scope for the current phase. The issue is a known coexistence pattern (HIGH-2) documented in `init_session_state` comments.
**Original issue:** In multi-user scenarios, FT events written for session A may record `user_id` from session B if session B started more recently.

### WR-02: `analyse_loop` reads learning cards from module-level `ls.state` — per-SID write is orphaned

**File:** `services/claude_service.py:916`
**Reason:** Intentional deferral to Phase 08.19.6. Same cluster as WR-01 — the fix requires `analyse_loop` to read from `ls._session_state[sid]['state']['active_learning_cards']` rather than the module-level `ls.state`. Out of scope for this phase; both WR-01 and WR-02 are tracked as a follow-up block for Phase 08.19.6.
**Original issue:** `load_learning_cards(sid, user_id)` correctly writes per-SID, but `analyse_loop` never reads the per-SID value — learning cards remain shared/last-writer-wins via module-level `ls.state`.
