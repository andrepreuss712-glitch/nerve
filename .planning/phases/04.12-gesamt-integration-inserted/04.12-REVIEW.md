## Summary

Reviewed Phase 04.12 (Gesamt-Integration) across 11 files. ## Critical Issues

### CR-01: SQL Injection via ILIKE with User-Controlled Input

**File:** `services/integration_engine.py:76-79`
**Issue:** `_persist_training_recommendation` passes `einwand_typ` directly into an `ilike` filter via f-string interpolation: `.filter(TrainingScenario.name.ilike(f'%{einwand_typ}%'))`. The `einwand_typ` value originates from `json_extract(metadata, '$.einwand_typ')` in rows fetched from `learning_events`, which is populated from user-provided data (objection types from button clicks). A malicious user who injects SQL wildcards (`%`, `_`) or specially crafted strings into objection type data could manipulate LIKE pattern matching. While SQLAlchemy parameterizes the ILIKE value preventing classic SQL injection, the LIKE pattern itself is unescaped, meaning `%` and `_` wildcards in user input alter matching behavior unexpectedly.
**Fix:** Escape LIKE wildcards in user input before passing to `ilike`:
```python
import re

def _escape_like(value):
    """Escape SQL LIKE wildcards in user input."""
    return re.sub(r'([%_])', r'\\\1', value)

# In _persist_training_recommendation:
safe_typ = _escape_like(einwand_typ)
scenario = (db_session.query(TrainingScenario)
            .filter(TrainingScenario.name.ilike(f'%{safe_typ}%'))
            .first())
```

## Warnings

### WR-01: DB Session Used After Commit in Learning Event Logging

**File:** `routes/learning.py:95-104`
**Issue:** In `api_save_card`, after `db.commit()` on line 95, the code calls `log_learning_event(db, ...)` then `db.commit()` again within a try/except. If the first commit succeeds but the learning event commit fails, the `except` prints an error but the card status change is already committed. This is acceptable behavior. However, the `log_learning_event` function explicitly states "KEIN db_session.commit() hier -- Caller committet", yet here the caller commits twice in the same session scope. More critically, the same pattern in `api_update_status` (line 156-164) and `api_mark_applied` (line 190-198) and `api_user_text` (line 225-233) all have the same double-commit pattern where a failure in the learning event commit could leave a partially-committed transaction state if the db session had other pending changes.
**Fix:** Consolidate commits -- add the learning event before the first commit, then commit once:
```python
# Before db.commit():
from services.integration_engine import log_learning_event
log_learning_event(db, g.user.id, 'learning_card_accepted', 'coach', card.call_id, {
    'card_id': card.id, 'category': card.category,
})
db.commit()  # single commit for both changes
```

### WR-02: Global Mutable State for Polling Version Tracking

**File:** `routes/app_routes.py:12`
**Issue:** `_letzte_gemeldete_version = 0` is a module-level global variable used in `api_ergebnis()` (line 147-149) via `global _letzte_gemeldete_version`. In a multi-worker deployment (e.g., gunicorn with multiple workers), each worker has its own copy of this variable, making the "neue Ergebnis" log message unreliable. More importantly, this is shared across ALL users in a single worker -- one user's polling updates will suppress the log message for another user's new results.
**Fix:** This is a logging-only variable so the impact is low, but for correctness it should be per-user or removed entirely. Consider removing the conditional print or using user-scoped tracking if the log message is valuable for debugging.

### WR-04: Raw SQL with json_extract Not Portable Beyond SQLite

**File:** `services/integration_engine.py:152-158, 176-183, 241-248`
**Issue:** The engine uses SQLite-specific `json_extract(metadata, '$.einwand_typ')` in raw SQL queries. If the database backend ever changes from SQLite to PostgreSQL (as hinted by `DATABASE_URL` support in config), these queries will fail silently or with errors. The `json_extract` function is SQLite-specific; PostgreSQL uses `->>`/`#>>` operators.
**Fix:** For now this is acceptable given the SQLite constraint, but add a comment marking these as SQLite-specific. For future portability, consider storing `einwand_typ` as a separate indexed column on `learning_events` rather than relying on JSON extraction in queries.

### WR-05: Boolean JSON Comparison May Not Match in SQLite json_extract

**File:** `services/integration_engine.py:246`
**Issue:** The query `json_extract(metadata, '$.success') = 'false'` compares against the string `'false'`. However, `json.dumps({'success': False})` produces `"success": false` (lowercase JSON boolean). SQLite's `json_extract` returns the JSON value, which for booleans is `0` or `1` (integer) in SQLite, not the string `'false'`. This means the training failure pattern detection (D-05) may never match any rows, effectively disabling the "3x Training-Scheitern" recommendation trigger.
**Fix:** Compare against the integer value that SQLite json_extract returns for JSON booleans:
```sql
AND json_extract(metadata, '$.success') = 0
```
Or alternatively, store success as a string:
```python
'success': 'true' if success else 'false',
```
