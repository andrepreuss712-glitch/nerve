## Summary

Phase 04.12 verbindet alle bestehenden NERVE-Module zu einem geschlossenen Lernökosystem. Der Kern ist eine neue `learning_events` Tabelle, die alle User-Interaktionen über alle Module hinweg loggt. Darauf aufbauend läuft eine synchrone Engine (kein Worker-Prozess), die nach jedem Call und Training Muster erkennt und Empfehlungen erzeugt.

Der Code-Audit zeigt: Die fünf Verbindungspunkte sind gut vorbereitet. `api_beenden()` und `training_end()` sind klar identifizierte synchrone Hook-Points. `generate_postcall_analysis()` kann mit minimaler Parametrisierung auch Training-Daten verarbeiten. `ObjectionEvent` enthält EWB-Klick-Daten pro Session. `CoachingReport` ist erweiterbar um Trainings-Daten.

Die grösste Implementierungsherausforderung ist die synchrone Ausführung der Engine in Request-Kontext: Bei vielen historischen Events könnte die DB-Query die Antwortzeit verlängern. Abhilfe: Queries auf die letzten 30 Tage begrenzen, Index auf `(user_id, event_type, created_at)`.

**Primary recommendation:** Beginne mit der `learning_events` Tabelle und dem Event-Logging-Helper als Wave 0. Alle anderen Verbindungen bauen darauf auf und können unabhängig getestet werden.

### Pattern 1: Event-Logging Helper

Alle Module rufen einen einzigen Helper auf — keine direkte DB-Session-Verwaltung in jedem Modul.

```python

# Source: [VERIFIED: Codebase-Pattern aus routes/app_routes.py ObjectionEvent-Bulk-Insert]

def log_learning_event(db_session, user_id, event_type, source_module,
                       source_id=None, metadata=None):
    """Schreibt einen learning_event. db_session wird vom Caller verwaltet."""
    from database.models import LearningEvent
    ev = LearningEvent(
        user_id=user_id,
        event_type=event_type,       # 'hint_used' | 'training_completed' | ...
        source_module=source_module,  # 'assistant' | 'training' | 'coach' | 'rating'
        source_id=source_id,          # conv_id oder training_session_id
        metadata=json.dumps(metadata or {}, ensure_ascii=False),
    )
    db_session.add(ev)
    # KEIN db_session.commit() hier — Caller committet
```

**Warum kein eigenes Commit im Helper:** Bestehende Pattern in `api_beenden()` (ObjectionEvent bulk-insert, dann ein Commit). Einzelne Commits pro Event würden SQLite unter Last belasten. [VERIFIED: Codebase-Analyse]

### Pattern 4: Muster-Erkennung (regelbasiert, kein LLM)

Schwellenwerte (Claude's Discretion):

| Muster | Schwellenwert | Quelle |
|--------|---------------|--------|
| Training-Schwäche erkannt | 3x scheitern am gleichen Einwand-Typ | D-05 |
| EWB → Trainings-Empfehlung | >3x gleicher Einwand-Typ geklickt | D-11 |
| Call-Schwäche → Training | 2+ Calls mit gleichem schwächsten Einwand-Typ | D-06 (Claude's Discretion für Zahl) |
| Score-Milestone | gesamt_score >= 80 beim Training | [ASSUMED] |

```python
# services/integration_engine.py
# Source: [ASSUMED — basierend auf D-05, D-11 Regeln]

def _detect_training_weakness(db, user_id, einwand_typ, lookback_days=30):
    """Zählt training_completed Events für diesen Einwand-Typ in den letzten 30 Tagen
    und prüft ob >50% Misserfolg-Markierung."""
    from database.models import LearningEvent
    from datetime import datetime, timedelta
    cutoff = datetime.now() - timedelta(days=lookback_days)
    events = db.query(LearningEvent).filter(
        LearningEvent.user_id == user_id,
        LearningEvent.event_type == 'training_completed',
        LearningEvent.created_at >= cutoff,
    ).all()
    # metadata enthält einwand_typ und success flag
    matches = [e for e in events
               if json.loads(e.metadata or '{}').get('einwand_typ') == einwand_typ]
    failures = [e for e in matches
                if not json.loads(e.metadata or '{}').get('success', True)]
    return len(failures) >= 3  # D-05 Schwellenwert
```

## Common Pitfalls

### Pitfall 1: Engine blockiert api_beenden() Response
**Was geht schief:** Wenn `run_postcall_engine()` eine langsame DB-Query auf vielen learning_events macht, verzögert sich die Antwort an den Browser. PostCall-Overlay erscheint spät.
**Warum:** Synchron im Request-Kontext (D-03 Entscheidung).
**Abhilfe:** Index auf `(user_id, event_type, created_at)` + LIMIT auf letzten 30 Tage in allen Engine-Queries. Silent-catch um Engine-Fehler zu isolieren.
**Warning Signs:** api_beenden() braucht >2s.

### Pitfall 2: generate_postcall_analysis() Duplikat-Guard blockiert Training-Lernkarten
**Was geht schief:** Beim Aufruf mit `conv_id` = Training-ConversationLog-ID prüft die Funktion ob bereits Karten für `call_id=conv_id` existieren. Bei erneutem Aufruf liefert sie `[]`.
**Warum:** T-04.11-05 Guard in coaching_service.py Zeile 62-72.
**Abhilfe:** Kein Problem — gewünschtes Verhalten. Pro Training-Session nur eine Analyse. Kein erneuter Aufruf im selben Request nötig.

### Pitfall 3: training_end() gibt `log_entry.id` nicht zurück
**Was geht schief:** `training_end()` speichert ConversationLog in separatem try-Block (Zeile 688-751), danach wird `log_entry` nicht weiter verwendet. Für Engine-Aufruf nach dem Commit braucht man `log_entry.id`.
**Warum:** Code war nur für Scoring ausgelegt, kein Post-Training Hook.
**Abhilfe:** `saved_log_id = log_entry.id` vor dem try-finally Block sichern. Engine nach dem `db_log.commit()` aufrufen, bevor `db_log.close()`.

### Pitfall 4: Persistente Dashboard-Card "Empfohlenes Training" — wann ist sie weg?
**Was geht schief:** D-12 sagt "bleibt bis Training absolviert". Aber wie weiß das Dashboard, welches Training empfohlen war?
**Warum:** Keine persistente Empfehlungs-Tabelle geplant.
**Abhilfe:** `training_recommendation` als JSON-Spalte auf User-Model speichern ODER als spezielle learning_event-Zeile mit `event_type='training_recommended'` und `source_id=einwand_typ`. Nach Training: `training_completed` Event loggen, Dashboard-Query prüft ob pending recommendation durch späteres completed Event "gecancelt" wurde.
**Empfehlung:** Einfachste Lösung — User-Model um `pending_training_recommendation TEXT` erweitern. Wird auf NULL gesetzt wenn training_completed Event mit passendem einwand_typ eingeht.

### Pitfall 5: EWB-Klick-Daten sind pro Session in ObjectionEvent, nicht nach Einwand-Typ aggregiert
**Was geht schief:** D-11 braucht ">3x gleicher Einwand-Typ über alle Sessions". `ObjectionEvent` hat `einwand_typ` + `success` pro Session, aber aggregierte Query über alle Sessions des Users ist nötig.
**Warum:** ObjectionEvent ist conversation_log-gebunden, kein User-Level-Index.
**Abhilfe:** Query: `SELECT einwand_typ, COUNT(*) FROM objection_events WHERE user_id=X GROUP BY einwand_typ HAVING COUNT(*) > 3`. Alternativ wird dieses Muster auch via `learning_events` mit `event_type='button_pressed'` erkennbar — dann genügt eine einzige Tabelle.

### Pitfall 6: Wochenbericht unterscheidet nicht zwischen Live und Training Calls
**Was geht schief:** `get_or_generate_weekly_report()` filtert aktuell `typ == 'live'` (Zeile 219). Training-Sessions haben `typ='training'`. D-08 will Cross-Modul-Insight.
**Warum:** Phase 04.11 hat nur Live-Calls einbezogen.
**Abhilfe:** Zweite separate Query für Training-Sessions dieser Woche, Ergebnis als Extra-Kontext in den Wochenbericht-Prompt injizieren. Achtung: Caching-Key bleibt Woche — Report wird nur einmal generiert, nicht bei jeder Training-Session neu.

### integration_engine.py Struktur (Gesamtübersicht)

```python
# services/integration_engine.py
# Source: [ASSUMED — basierend auf D-03, D-04, D-05, D-06, D-11]

def run_postcall_engine(db_session, user_id, conv_id, einwaende, ewb_clicks, ga_details):
    """Synchrone Engine nach Live-Call. Silent failure guaranteed."""
    try:
        # 1. learning_events für diesen Call loggen
        _log_call_events(db_session, user_id, conv_id, einwaende, ewb_clicks, ga_details)
        db_session.commit()

        # 2. Muster über historische Events checken
        rec = _detect_patterns_for_call(db_session, user_id, einwaende, ewb_clicks)

        # 3. Trainings-Empfehlung persistieren (falls Muster erkannt)
        if rec:
            _persist_training_recommendation(db_session, user_id, rec)
            db_session.commit()
    except Exception as e:
        print(f"[Engine] run_postcall_engine failed: {e}")


def run_posttraining_engine(db_session, user_id, log_id, scoring, wendepunkt_saetze, modus):
    """Synchrone Engine nach Training-Session. Silent failure guaranteed."""
    try:
        # 1. training_completed Event loggen
        _log_training_events(db_session, user_id, log_id, scoring, wendepunkt_saetze, modus)
        db_session.commit()

        # 2. Schwäche-Muster checken (D-05)
        rec = _detect_patterns_for_training(db_session, user_id, wendepunkt_saetze)

        # 3. Lernkarten-Vorschlag generieren wenn Muster erkannt (D-09)
        if rec and rec.get('needs_learning_card'):
            _trigger_training_learning_card(user_id, log_id, scoring, wendepunkt_saetze)

        # 4. Empfehlung löschen wenn Training diese Schwäche adressiert hat (D-12)
        _maybe_clear_training_recommendation(db_session, user_id, wendepunkt_saetze)
        db_session.commit()
    except Exception as e:
        print(f"[Engine] run_posttraining_engine failed: {e}")
```
