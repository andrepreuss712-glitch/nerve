# Phase 04.12: Gesamt-Integration - Context

**Gathered:** 2026-04-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Alle bestehenden Module (Live Assistent, Training, Coach-Modul, Bewertungen, EWB-Buttons) zu einem geschlossenen Lernökosystem verbinden. Zentrale `learning_events` Tabelle sammelt alle Events von Tag 1. Alle 5 Modul-Verbindungen werden verdrahtet (Phase A+B aus Briefing). Selbstverbesserungs-Kreislauf: Fehler → Lernkarte → Training → besserer Call. Plattform-weite Aggregation (Phase C, anonymisierte Daten über alle User) kommt später — nur Events sammeln, nicht auswerten.

**Nicht in Scope:** Phase C Plattform-Intelligenz (anonymisierte Aggregation, Branchen-Bibliothek, selbst-korrigierende Hinweise), Fine-Tuning basierte Optimierung.

</domain>

<decisions>
## Implementation Decisions

### learning_events Tabelle
- **D-01:** Alle 12 Event-Typen aus dem Briefing werden sofort implementiert: `hint_used`, `hint_ignored`, `button_pressed`, `learning_card_accepted`, `learning_card_rejected`, `learning_card_custom`, `learning_card_applied`, `training_completed`, `training_hangup`, `call_rated`, `score_milestone`. Daten von Tag 1 sammeln — Aggregation über User kommt später.
- **D-02:** Schema per Briefing: `id`, `user_id`, `event_type`, `source_module` (assistant|training|coach|rating), `source_id`, `metadata` (JSON), `created_at`. ForeignKey auf users.

### Verarbeitungs-Engine
- **D-03:** Synchroner Post-Call/Post-Training Hook — kein Background-Worker, kein Scheduler. Engine läuft in `api_beenden()` (nach Call) und `training/end` (nach Training). Passt zum Bootstrap-Constraint (Solo-Founder, kein separater Worker-Prozess).
- **D-04:** Engine-Flow: Events sammeln → Muster über historische Events checken → Verbindungs-Logik → Empfehlungen/Lernkarten generieren. Alles synchron im Request.

### Verbindung 1: Training ↔ Echter Call
- **D-05:** Wenn User im Training 3x am selben Einwand-Typ scheitert: System generiert automatisch Lernkarten-Vorschlag (gleicher Flow wie Post-Call Analyse) UND zeigt Dashboard-Empfehlung. User muss Lernkarte trotzdem explizit akzeptieren (bestehender Save-Flow).
- **D-06:** Richtung Call→Training: Nach echtem Call, wenn wiederkehrende Schwäche erkannt → Trainings-Empfehlung im PostCall-Overlay + persistente Dashboard-Card bis Training absolviert.

### Verbindung 2: Echter Call ↔ Coach-Modul
- **D-07:** Post-Call Analyse (coaching_service) läuft bereits. Integration erweitert den Rückkanal: Muster-Erkennung über mehrere Calls fließt in Lernkarten-Vorschläge.
- **D-08:** Wochenbericht (CoachingReport) wird erweitert um Trainings-Daten einzubeziehen. Aggregiert echte Calls UND Trainings-Sessions für vollständiges Bild ("Übst du Preis-Einwand im Training, aber im echten Call klappt es noch nicht").

### Verbindung 3: Training ↔ Coach-Modul
- **D-09:** Training-Feedback fließt in Coach-Modul: Wendepunkt-Analyse nach Training generiert Lernkarten-Vorschlag (identischer Mechanismus wie nach echtem Call). Coach → Training: Aktive Lernkarten bestimmen Trainings-Empfehlung.

### Verbindung 4: Bewertungen ↔ Alle Module
- **D-10:** Bewertungs-Diskrepanz (User-Rating vs. KI-Score) wird als learning_event geloggt, aber NICHT user-facing. Nur internes Signal. Braucht erst genug Daten für sinnvolle Nutzung. Später: KI-Score Kalibrierung basierend auf Diskrepanz-Patterns.

### Verbindung 5: EWB-Buttons ↔ Training
- **D-11:** Events sammeln + einfache Regel: Wenn EWB-Button >3x für gleichen Einwand-Typ gedrückt → Trainings-Empfehlung für diesen Einwand-Typ generieren. Kein zusätzlicher LLM-Call nötig — regelbasiert. Plattform-weite EWB-Patterns (Phase C) kommen später.

### Trainings-Empfehlungen UI
- **D-12:** Empfehlung erscheint an zwei Stellen: (1) PostCall-Overlay unter Lernkarten-Vorschlägen als zusätzlicher Block "Empfohlenes Training: [Szenario]" mit Ein-Klick-Start, (2) Dashboard-Card "Empfohlenes Training" die bleibt bis Training absolviert.

### Claude's Discretion
- Exakte Schwellenwerte für Muster-Erkennung (ab wann ist ein Muster ein Muster?)
- JSON-Struktur der metadata-Felder in learning_events
- Trainings-Empfehlungs-Algorithmus Details (welche Szenarien empfohlen werden)
- Dashboard-Card Design für Trainings-Empfehlung (innerhalb NERVE Design-System)
- Reihenfolge der Tasks und Abhängigkeiten

</decisions>
