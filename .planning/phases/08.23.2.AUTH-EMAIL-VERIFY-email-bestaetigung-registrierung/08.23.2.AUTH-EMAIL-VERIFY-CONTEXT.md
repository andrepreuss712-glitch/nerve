## Phase Boundary

**Was diese Phase liefert:** Die **normale E-Mail-Registrierung** (`api_register`, Landingpage-Formular) wird an den **bereits existierenden** E-Mail-Bestätigungs-Flow angeschlossen, sodass ein Neu-Registrierter erst nach Klick auf den Bestätigungslink Zugang zur App bekommt. Schließt das Leck: heute nimmt die Formular-Registrierung **jede Adresse ungeprüft** an.

**★ IST-STAND ~80% gebaut (Fable-Scout 2026-07-09, am echten Code verifiziert):** Ein kompletter Bestätigungs-Flow existiert seit **H-18 (Phase 08.10)**, heute nur für **Microsoft-OAuth** scharf. Vorhanden + wiederverwendbar (KEIN Neubau, Decision A):
- `send_confirmation_email` (`email_service.py:55-69`) — versendet signierten Link.
- Signierter 24h-Link: `URLSafeTimedSerializer(SECRET_KEY, salt='nerve-email-confirm')`, `max_age=86400` (`auth.py` `confirm_email` ~:365-387; setzt `email_confirmed=True` ~:375, redirect → `/login` ~:387).
- Warteseite: `confirm_email_pending.html` + Route `auth.confirm_email_pending` (~:355).
- „Erneut senden": `resend_confirm` (~:394), `@limiter.limit("3 per 10 minutes")`.
- **Sperr-Gate** in `login_required` (`auth.py:79-82`): `email_confirmed is False` → redirect `auth.confirm_email_pending`; Ausnahmen `/auth/confirm_email` + `/auth/logout` (kein Redirect-Loop).
- Resend-Versand LIVE (RESEND_API_KEY auf Server gesetzt, Claudian-verifiziert). 3 Bestandskonten alle `email_confirmed=true`.

**NICHT in dieser Phase:** Kein neuer Code/Serializer/Mail-Weg (alles da). Keine E-Mail-Region-i18n (RESEND_BASE_URL bleibt ungesetzt = US-Standard, Decision E). Keine Änderung am OAuth-Bestätigungs-Verhalten (Google bleibt bestätigt, Microsoft behält Zwang).

**★ Warum trotzdem eine Phase:** Der Flow wurde **noch NIE live gefeuert** (nur MS-OAuth-Pfad theoretisch scharf, 3 Bestandskonten alle bestätigt) → **End-to-End-Live-Test ist PFLICHT** (Sicht statt Zusicherung).

## Implementation Decisions

### GZ0 — Wurzel des Lecks + Fail-Closed-Gate + Cross-File-Naht (Punkt 14) — ★ KORRIGIERT 2026-07-09 (Claudian, Prod+Code-verifiziert)
> **★ FABLE-SCOUT-FEHLER korrigiert:** Die Leck-Wurzel ist NICHT „DB-Default True". Prod-`users.email_confirmed` ist **nullable OHNE DB-Default** (verbatim `\d users` / information_schema: `boolean`, `is_nullable=YES`, `column_default` leer; 3 Bestandskonten explizit `true`, 0 NULL-Rows aktuell). `models.py:135` `default=True` ist nur der SQLAlchemy-ORM-Default und **driftet zur Prod-Realität**. Das eigentliche Loch ist ein **FAIL-OPEN-Gate**, nicht ein Default.
- **D-01 (Leck-Wurzel, korrigiert):** Das Sperr-Gate `auth.py:79` liest `getattr(g.user,'email_confirmed',True) is False` → **NULL/None ist NICHT `is False`** → jeder Nutzer mit `email_confirmed IS NULL` **passiert UNGATED**. Erklärt Andrés freien Register-Zugang (er bekam NULL, nicht True). `api_register` setzt `email_confirmed` nicht → Insert landet NULL (kein DB-Default) → fail-open durch.
- **D-01b (★ FAIL-CLOSED PFLICHT — der Kern-Fix des Auth-Gates):** Das Gate MUSS fail-closed werden: NULL/unset = **unbestätigt → gaten**. Umstellen auf `email_confirmed is not True` (bzw. `not email_confirmed`) statt `... is False`. Ohne das bleibt das NULL-Bypass-Loch offen, egal was `api_register` setzt. (Achtung Ausnahme-Pfade `auth.py:80-82` confirm_email/logout unverändert.)
- **D-02 (email_confirmed=False in api_register — NAHT Punkt 14):** `email_confirmed=False` explizit im **FORM-Register-Pfad `api_register` selbst**, **NICHT** im geteilten `_create_org_and_user` (`auth.py` def@~182) — OAuth-Neuanlage nutzt denselben Choke-Point (`oauth.py:116`), **Google muss dort `True` bleiben** (Decision D; OAuth setzt selbst, `oauth.py:130-160`/`:147`).
- **D-03 (★ ALLE Anlage-Pfade sauber setzen — Cross-File Punkt 14/22, weil fail-closed jeden NULL-Nutzer gatet):** Sobald das Gate fail-closed ist, wird JEDER künftig-NULL-Nutzer gesperrt → alle User-Anlage-Pfade MÜSSEN `email_confirmed` explizit setzen. Der Planer baut eine **Anlage-Pfad-Inventur (Verbindungs-Karte, Punkt 22): jeder Creator × gesetzter email_confirmed-Wert × Begründung**, grep-belegt (Punkt 20). Bekannt: `api_register`→`False` (D-02); OAuth Google→`True`/Microsoft→`False` (schon so, verifizieren); **Invite-Accept `auth.py:289` (`register()`/Token-Pfad) → prüfen**: Invite-Mitglied kam über vertrauten Invite-Link an seine Mail → **wahrscheinlich `True`** setzen (Mail-Besitz via Invite bewiesen, sonst grundlos neu-gegatet); Admin-/Seed-Create-Pfade grep+prüfen. **KEIN Pfad darf still NULL lassen.**
- **D-03b (SOLL — belt-and-suspenders, kehrt die alte „nicht flippen"-Annahme um):** `models.py:135` ORM-Default **+ DB-Column-Default auf `False`** (kleine Migration `NNNN_email_confirmed_default_false.py`, Muster wie 0032), damit kein Insert-Pfad still auf NULL fällt. Die frühere „Default NICHT flippen"-Logik galt unter der **falschen** Default-True-Prämisse und ist hinfällig. **KEIN NULL→False-Backfill nötig** (0 NULL-Rows; 3 Konten = `true` bleiben unangetastet). Schild/COMMENT der Spalte nachziehen (Punkt 23: „Form-Register/NULL=False fail-closed, H-EMAIL-VERIFY").
