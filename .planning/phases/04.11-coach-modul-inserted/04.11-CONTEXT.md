# Phase 04.11: Coach-Modul - Context

**Gathered:** 2026-04-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Persönliches Lernsystem für Vertriebler: Post-Call Analyse generiert max 3 konkrete Lernkarten-Vorschläge, User verwaltet max 5 aktive Lernkarten, KI-Gedächtnis blendet passende Lernkarten im nächsten Live-Call ein (goldener Rahmen), wöchentlicher Coach-Report mit Muster-Erkennung, Langzeit-Fortschritts-Grafiken über 4-12 Wochen.

**Nicht in Scope:** Gesprächs-Timeline Visualisierung (Ebene 6 im Briefing — eigene Phase oder Backlog), learning_events Verbindungstabelle (Phase 04.12), Fine-Tuning-basierte Satz-Generierung (Zukunft).

</domain>

<decisions>
## Implementation Decisions

### Post-Call Analyse
- **D-01:** Post-Call Analyse wird automatisch nach api_beenden ausgelöst. Claude (Sonnet) analysiert das conversation_log und generiert max 3 Lernkarten-Vorschläge. Ergebnis wird in DB gespeichert und auf der Post-Call-Seite angezeigt.
- **D-02:** Analyse nutzt Sonnet (nicht Haiku) — Post-Call ist nicht zeitkritisch, Qualität der Satz-Vorschläge ist entscheidend. Passt zu Constraint "Sonnet nur Post-Call".
- **D-03:** Priorisierung der 3 Vorschläge per Briefing: 1) Fehler der Abschluss verhindert, 2) Häufigster Fehler, 3) Kleinste Verbesserung mit größter Wirkung. Priorität wird im Prompt an Claude übergeben.
- **D-04:** Vorschläge müssen konkrete Sätze sein, keine generischen Tipps. Briefing-Beispiele als Few-Shot ins Prompt. Jeder Vorschlag hat: category, original_suggestion, lernziel (kurz).

### Lernkarten Management
- **D-05:** Lernkarten leben im Dashboard-Bereich "Meine Lernkarten" — sichtbar bei jedem Login. Kartenformat wie im Briefing spezifiziert.
- **D-06:** Post-Call zeigt Vorschläge als Modal/Cards mit 3 Optionen: Speichern, Neuer Vorschlag (max 3x), Selbst eingeben. Bei "Selbst eingeben": Freitextfeld, KI prüft ob Lernziel abgedeckt.
- **D-07:** Max 5 aktive Lernkarten gleichzeitig. Bei Limit: KI fragt welche als "gelernt" markiert oder archiviert werden soll. Status-Flow: aktiv → gelernt → archiviert.
- **D-08:** DB-Tabelle `learning_cards` per Briefing-Schema. user_id, call_id (nullable FK → ConversationLog), category, original_suggestion, final_text, source (ki/user), status (aktiv/gelernt/archiviert), applied_count, timestamps.

### KI-Gedächtnis im Live-Call
- **D-09:** Vor jedem Call werden aktive Lernkarten des Users geladen und als Kontext an den Claude-Prompt im Live-Assistenten übergeben. Erkannte Situation → Lernkarte wird im Hinweis-Panel mit goldenem Rahmen und 🎯-Symbol eingeblendet.
- **D-10:** Visuell unterscheidbar: Normaler Hinweis = bestehender blauer Rahmen. Lernkarten-Erinnerung = goldener Rahmen (#E8B040 oder Gold-Ton) mit 🎯. CSS-Klasse `n-hint-learning` oder ähnlich.
- **D-11:** Nach dem Call fragt Post-Call: "Hast du deine Lernkarte angewendet?" — Ja/Nein/Ja aber anders. applied_count wird erhöht, bei "anders" kann User Satz anpassen.

### Wöchentlicher Coach-Report
- **D-12:** Coach-Report wird on-demand generiert beim Dashboard-Aufruf, mit Caching (1x pro Woche neu). Kein Cron/Scheduler nötig — Solo-Founder Bootstrap, kein Background-Worker.
- **D-13:** DB-Tabelle `coaching_reports` per Briefing-Schema. Aggregiert: Calls-Count, Avg-Readiness-Score, stärkste/schwächste Phase, Redeanteil, Report-Text (von Sonnet generiert).
- **D-14:** Report enthält: Wochen-Statistiken, erkanntes Muster (Sonnet-Analyse über alle Wochen-Calls), neuer Lernkarten-Vorschlag aus Wochenmuster.

### Langzeit-Fortschritt
- **D-15:** Grafiken über 4-12 Wochen auf dem Dashboard: Kaufbereitschafts-Score Entwicklung, Redeanteil-Verhältnis, Einwand-Erfolgsrate, Abschluss-Rate. Chart.js (bereits im Dashboard vorhanden).
- **D-16:** Daten kommen aus ConversationLog + coaching_reports Aggregation. Keine separate Datenstruktur nötig — Query-basiert.

### Claude's Discretion
- Exakte Claude-Prompt-Formulierung für Post-Call Analyse und Lernkarten-Matching
- CSS-Details der Lernkarten-Darstellung im Dashboard (innerhalb NERVE Design-System)
- Exact Chart.js Konfiguration für Langzeit-Grafiken
- Reihenfolge der Tasks (Planung entscheidet über Abhängigkeiten)

</decisions>
