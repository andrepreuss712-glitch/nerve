# Phase 04.11: Code Review Report

**Reviewed:** 2026-04-12T14:30:00Z
**Depth:** standard
**Files Reviewed:** 12

## Summary

Phase 04.11 introduces a Coach-Modul with learning cards (Lernkarten), post-call analysis via Sonnet, weekly coach reports, and longterm trend charts. The implementation is well-structured with proper authorization checks (conv_id ownership verification, user_id filtering on all card operations), duplicate guards on Sonnet calls, and max-5 active card enforcement. One XSS vulnerability was found in the live app's learning card hint rendering. Several warnings around error handling, race conditions, and model default inconsistencies were identified.

## Critical Issues

### CR-01: XSS via Learning Card Hint in Live View

**File:** `static/app.js:198`
**Issue:** The `renderLernkarteHint(text, category)` function inserts `text` directly into innerHTML without HTML escaping. The `text` parameter comes from `data.ergebnis.lernkarte_match_text` (line 710), which originates from `LearningCard.final_text` -- a field the user can set to arbitrary content via the `/api/learning_cards/<id>/user_text` endpoint. A user could craft a `final_text` containing `<script>` or `<img onerror=...>` tags that would execute when the hint renders in any session using their learning cards.
**Fix:**
```javascript
// Line 198: Use escHtml() which is already defined in app.js
function renderLernkarteHint(text, category) {
  const hint = document.createElement('div');
  hint.className = 'n-hint-learning';
  hint.innerHTML = `<div style="font-size:11px;color:#E8B040;margin-bottom:4px">&#127919; Dein Lernziel &ndash; jetzt ist der Moment</div><div style="font-size:14px">"${escHtml(text)}"</div>`;
  return hint;
}
```

## Warnings

### WR-01: LearningCard Model Default Contradicts Actual Usage

**File:** `database/models.py:563`
**Issue:** `LearningCard.status` has `default='aktiv'` and the comment lists valid values as `'aktiv' | 'gelernt' | 'archiviert'`. However, `coaching_service.py:124` creates cards with `status='vorschlag'`, and `routes/learning.py:88` queries by `status='vorschlag'`. The undocumented fourth status means cards created without an explicit status (e.g., through a future code path or manual DB insert) would incorrectly default to `'aktiv'` instead of `'vorschlag'`.
**Fix:**
```python
# database/models.py line 563
status = Column(String(20), default='vorschlag')  # 'vorschlag' | 'aktiv' | 'gelernt' | 'archiviert'
```

### WR-02: DB Commit Failure in coaching_service Silently Loses Persisted Cards

**File:** `services/coaching_service.py:128-130`
**Issue:** When the DB persist of learning card suggestions fails (line 128-129), the exception is printed but the function still returns `vorschlaege` (line 133). The caller (`routes/learning.py:45`) returns these suggestions to the frontend, which displays them as saveable cards. However, since the cards were never persisted, the subsequent `saveLernkarte()` frontend call to `/api/learning_cards?status=vorschlag` will find no matching cards, causing a silent failure. The duplicate guard (line 63) will also not fire on retry since no rows exist.
**Fix:**
```python
# services/coaching_service.py lines 128-133
except Exception as _de:
    print(f"[Coach] DB persist failed: {_de}")
    db.rollback()
    return []  # Return empty so frontend knows analysis failed
finally:
    db.close()

return vorschlaege
```

### WR-03: Race Condition Between Duplicate Guard and Card Persistence

**File:** `services/coaching_service.py:58-68` and `services/coaching_service.py:113-131`
**Issue:** The duplicate guard (lines 58-68) and the card persistence (lines 113-131) use separate DB sessions. Between the check and the insert, a concurrent request for the same `conv_id` could pass the guard, resulting in duplicate Sonnet calls and duplicate cards. While the `T-04.11-05` comment acknowledges this guard, it is not atomic. In a multi-threaded Flask app with `async_mode='threading'`, two simultaneous `/api/postcall_analysis` requests for the same conv_id could both pass the `existing > 0` check.
**Fix:** Add a unique constraint or use a single session with `SELECT ... FOR UPDATE` semantics. Alternatively, add a `UniqueConstraint` on `(user_id, call_id)` to the `LearningCard` model to catch duplicates at the DB level:
```python
# database/models.py - LearningCard class
# Not a full unique constraint since multiple cards per call are expected,
# but consider a dedicated "analysis_completed" flag on ConversationLog
```
A simpler fix is to use a threading lock around the check-then-insert:
```python
_analysis_lock = threading.Lock()

def generate_postcall_analysis(...):
    with _analysis_lock:
        # ... existing check + Sonnet call + persist logic
```

### WR-04: validate_user_text Returns Permissive Default on Error

**File:** `services/coaching_service.py:155-156`
**Issue:** When the Haiku validation call fails (any exception), the function returns `{"covers_goal": True, "feedback": ""}`. This means any user text is silently accepted and saved to the card (line 193-196 in learning.py) even if the AI validation is unavailable. This could allow nonsensical or empty-feeling text to be persisted as a learning card.
**Fix:** Return `covers_goal: False` on error so the user is prompted to retry:
```python
except Exception as e:
    print(f"[Coach] Validation failed: {e}")
    return {"covers_goal": False, "feedback": "Validierung fehlgeschlagen, bitte erneut versuchen."}
```

## Info

### IN-01: Module-Level Global Without Lock in Multi-Threaded Context

**File:** `routes/app_routes.py:12,127-149`
**Issue:** `_letzte_gemeldete_version` is a module-level integer modified in `api_ergebnis()` without any lock. With `async_mode='threading'` in SocketIO, concurrent requests can read stale values. The impact is limited to occasional duplicate or missed `[API] Neues Ergebnis` log lines.
**Fix:** Wrap reads/writes in a `threading.Lock`, or accept this as cosmetic since it only affects debug logging.

### IN-02: Triple JSON Import in live() Route Handler

**File:** `routes/app_routes.py:96-108`
**Issue:** The `live()` function imports `json` three times under different aliases (`_json`, `_json2`, `_json3`) on lines 96, 101, and 107. This is functionally harmless but reduces readability.
**Fix:** Import `json` once at the top of the file (it is not currently imported at module level in app_routes.py) and use it directly:
```python
import json  # at top of file, replacing the three inline imports
```

### IN-03: Deprecated `.query().get()` Usage

**File:** `routes/dashboard.py:370`
**Issue:** `db.query(UserModel).get(g.user.id)` uses the legacy `Query.get()` method which is deprecated in SQLAlchemy 2.0. The rest of the codebase already uses `db.get(Model, id)` in many places.
**Fix:**
```python
user = db.get(UserModel, g.user.id)
```
