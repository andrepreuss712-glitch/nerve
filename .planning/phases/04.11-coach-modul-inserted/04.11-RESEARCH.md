## Summary

This phase implements a personal learning system for sales reps: Post-Call Analysis generates max 3 learning card suggestions via Sonnet, users manage up to 5 active cards, the live assistant remembers cards during calls (golden frame), and a weekly coach report with long-term progress charts appears on the dashboard.

The existing codebase provides strong integration points. `api_beenden()` already collects all post-call data (einwaende, kaufsignale, painpoints, kb_verlauf, skript_abdeckung, dauer_sek) and persists a `ConversationLog` — the Post-Call Sonnet analysis hooks directly after this DB write. The live Claude prompt in `analysiere_mit_claude()` accepts a `kontext` parameter where learning cards can be injected. The dashboard already uses Chart.js 4.4.0 CDN. The `postcallOverlay` in `app.html` is the natural place for learning card suggestions.

**Primary recommendation:** Build in layers: (1) DB schema + migration, (2) Post-Call Sonnet analysis + learning card API, (3) Dashboard Lernkarten UI, (4) Live-call injection, (5) Weekly report + long-term charts. Each layer is independently testable.

## Common Pitfalls

### Pitfall 1: Sonnet API Latency in api_beenden
**What goes wrong:** Sonnet call takes 3-8 seconds, blocking the beenden response and making the user stare at a spinner.
**Why it happens:** Sonnet is slower than Haiku. Post-Call analysis with full conversation context is a large prompt.
**How to avoid:** Two approaches: (A) Accept the wait — user expects post-call processing. Show a loading spinner specifically for "Lernkarten werden generiert...". (B) Return postcall data immediately, then fetch suggestions via a second AJAX call (similar to existing `postcall_insights` pattern). Approach B is better UX.
**Warning signs:** Users clicking away before analysis completes.

### Pitfall 2: Learning Card Count Enforcement Race Condition
**What goes wrong:** User saves 6th card because count check happened before concurrent save.
**Why it happens:** No DB-level constraint for max 5 active cards per user.
**How to avoid:** Use a SELECT COUNT + INSERT in a single DB transaction. Even better: check count server-side before save, and handle the edge case with a friendly "max reached" message.
**Warning signs:** User seeing more than 5 active cards.

### Pitfall 3: Live Prompt Bloat from Learning Cards
**What goes wrong:** 5 active learning cards with long texts significantly increase the live Haiku prompt, adding latency and cost.
**Why it happens:** Each card text could be 50-100 tokens.
**How to avoid:** Keep the learning card context injection compact. Summarize each card to category + key phrase (not full text). Budget max ~200 additional tokens for all 5 cards combined.
**Warning signs:** Live analysis latency increasing after cards are active.

### Pitfall 4: Weekly Report Sonnet Cost
**What goes wrong:** Every dashboard load triggers a Sonnet call for users who haven't called that week.
**Why it happens:** Missing guard for "no calls this week = no report".
**How to avoid:** Only generate report if user had >= 1 call in the current week. For weeks with no calls, show "Keine Calls diese Woche — starte einen Call fuer deinen Coach-Report".
**Warning signs:** Sonnet costs climbing without corresponding user activity.

### Pitfall 5: postcallOverlay Becoming Overcrowded
**What goes wrong:** Adding learning card suggestions + "Hast du deine Lernkarte angewendet?" + existing sections makes the overlay unusably long.
**Why it happens:** The overlay already has: Redeanteil, Kaufbereitschaft, Einwaende, Kaufsignale, Painpoints, Skript-Abdeckung, CRM-Export, Insights, Sterne-Bewertung.
**How to avoid:** Use a tabbed or multi-step postcall flow. Step 1: existing analysis (compact). Step 2: learning card suggestions. Step 3: "Hast du angewendet?" question. Or: add learning card section as a collapsible area at the top of the overlay.
**Warning signs:** Scrolling required to see all postcall content.

### Pitfall 6: Gold Color Conflict with Design System
**What goes wrong:** #E8B040 gold was explicitly removed from the design system in Phase 03.1/04.3 (replaced with teal #00D4AA everywhere).
**Why it happens:** D-10 specifies golden frame for learning cards, but accumulated decisions from Phase 03.1 and 04.3 replaced all gold with teal.
**How to avoid:** D-10 is a locked decision — gold IS intentional here specifically for learning card hints (visual distinction from normal teal hints). This is the one exception. Use a dedicated CSS variable like `--learning-gold: #E8B040` scoped only to `.n-hint-learning`.
**Warning signs:** Designer confusion about gold appearing in an otherwise all-teal system.

## DB Schema Design

### learning_cards Table (per Briefing D-08)
```sql
CREATE TABLE learning_cards (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
```

## Open Questions

1. **Post-Call Analysis: Sync vs Async?**
   - What we know: Existing `postcall_insights` uses a separate AJAX call (async pattern). Sonnet is slower than Haiku.
   - What's unclear: Whether users will tolerate 3-8s extra wait in the beenden response, or need a two-phase load.
   - Recommendation: Use the async pattern (like existing `postcall_insights`). Return postcall data immediately, then fetch learning card suggestions via separate endpoint. Show spinner "Lernkarten werden generiert..." in the overlay.

2. **Learning Card Categories**
   - What we know: D-04 says category field, Briefing examples use types like 'einwand_preis', 'zu_frueh_pitch', 'redeanteil'.
   - What's unclear: Whether to use free-text categories from Sonnet or a fixed enum.
   - Recommendation: Let Sonnet choose from a predefined list (matching the existing Einwand-Typen in SYSTEM_PROMPT_BASE + coaching categories). Keeps data clean for aggregation.

3. **"Neuer Vorschlag" Implementation**
   - What we know: D-06 allows max 3x regeneration per suggestion.
   - What's unclear: Does this re-call Sonnet each time (expensive) or pre-generate 3 alternatives in the initial call?
   - Recommendation: Pre-generate 3 alternative formulations per suggestion in the initial Sonnet call. Store all in response, show one at a time. Avoids 3 additional Sonnet calls.
