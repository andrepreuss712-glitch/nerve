<decisions>
## Implementation Decisions

### D-01: Profil-Scoping-Architektur — Per-SID in-memory dict

**Entscheidung:** `_per_sid_profile: dict[str, tuple[str, dict]] = {}` in `live_session.py` (analog zu `_deepgram_sessions` in `deepgram_service.py` — Pattern existiert bereits).

**Lifecycle:**
- **Set-Hook:** `start_live_session` Socket-Event lädt `User.active_profile_id` aus DB, fetched `Profile`-Row, ruft `set_profile_for_sid(sid, name, daten)` — kein global mehr
- **Disconnect-Cleanup:** `handle_disconnect` ruft `_per_sid_profile.pop(sid, None)` — verhindert Memory-Leak nach vielen Connects
- **None-Default:** `get_profile_for_sid(sid)` für unbekannte SID returns `('', {})` + `logger.warning`. Caller (EWB-Generator, claude_service) muss damit umgehen können — kein Crash, kein Profil-Context im Prompt

**Thread-Safety:** Ein `_per_sid_lock` (threading.Lock) schützt alle Reads/Writes auf `_per_sid_profile`.

**Race-Condition:** Thread liest SID, parallel Disconnect + Pop — Lock ist atomic, aber Caller muss leeres Tuple graceful behandeln. Test-abgedeckt (Pflicht).

### D-02: State-Isolation-Scope — Tier 1 + 2 Pflicht, Tier 3 opportunistisch

**Unified dict-Ansatz:** Statt separate Modul-Globals pro Variable → `_session_state = {sid: {key: value}}`. Cleanup bei Disconnect: `_session_state.pop(sid, None)`.

**Tier 1 — DSGVO-kritisch (Profil + Identity):** Pflicht
- `active_profile_data` / `active_profile_name` → `_per_sid_profile[sid]`
- `state['user_id']`, `state['org_id']`, `state['active_profile_id']` → `_session_state[sid]['user_id']` etc.
- `state['kaufbereitschaft']`, `state['active_sid']` → per-SID

**Tier 2 — Transcript-Cross-Contamination:** Pflicht
- `conversation_log` → `_session_state[sid]['conversation_log']`
- `berater_words` / `kunde_words` → `_session_state[sid][...]`
- `roles_swapped` → `_session_state[sid]['roles_swapped']`
- `covered_phases` → `_session_state[sid]['covered_phases']`

**Tier 3 — Opportunistisch:** mitnehmen wenn Sub-Diff klein (gleiche Code-Operation)
- `kaufbereitschaft_verlauf` (chronologische Reihe zu `kaufbereitschaft` — Trennung artifiziell)
- `_bof_count`, `_pending_speaker`, `_confirmed_speaker`, `_log_last_sp` (Speaker-Stabilisierungs-State — falsche Speaker-Attribution produziert fehlerhafte Trainingsdaten)
- **Falls Plan-Phase signifikanten Zusatz-Aufwand zeigt** (z.B. Speaker-Stabilisierung-Spezialfall): defer zu Phase 08.19.5 vor 08.20, **nicht** post-launch

**Anti-Abrieb-Begründung:** Code-Operation ist für alle Tiers identisch (Modul-Global → `_session_state[sid][key]`). Jetzt sauber machen verhindert Phase 08.19.5 als Redundanz-Zyklus.

### D-03: analyse_loop + coaching_loop — Iteration über _session_state.keys()

**Entscheidung:** Bestehende global-Thread-Struktur bleibt. Jeder Loop-Tick iteriert über alle aktiven SIDs in `_session_state`. Pro SID eigener Analyse-Zyklus. Emit an `_session_state[sid]['active_sid']` für Socket-Targeting.

**Plan-01-Pflicht:** Grep auf `threading.Thread` + `while True:` + `sleep` in `services/` + andere Module — alle Background-Threads inventarisieren und je entscheiden ob SID-Map-Umstellung nötig. Coaching-loop, keyword_pipe etc. werden mitumgestellt. Kein Halb-Fix.

**In-Flight-Claude-Call nach SID-Pop:** Response wird VERWORFEN (User disconnected = kein Empfänger). Plan spezifiziert: nach jedem Claude-API-Call prüfen ob SID noch in `_session_state` — falls nicht, silent drop + log.

**Latency-Dokumentation (Pflicht in Plan, kein Fix in 08.19.4):**
- Messung Loop-Cycle-Dauer bei N=1/5/10/20/50 parallelen Sessions
- Schwellwert dokumentiert: ab wann Migration zu `ThreadPoolExecutor` oder Pro-SID-Thread nötig
- Anti-Abrieb-Code-Kommentar: `# SKALIERUNG: wenn Loop-Cycle bei N Sessions > X Sek, switch zu ThreadPool — siehe Phase Block M`

### D-04: _load_initial_profile() — Komplett löschen

**Entscheidung:** Funktion + Aufruf (`app.py:2062`) komplett entfernen. Kein Auskommentieren, kein Verschieben in Test-Helpers.

**Begründung:** `_load_initial_profile()` ist die Wurzel des heutigen DSGVO-Befunds. Behalten = jemand reaktiviert es später ohne Kontext zu kennen. CLAUDE.md Pruning-Pflicht (Nudelcode-Regel 3).

**Plan-01-Pflicht:** Nach Delete Grep nach `if active_profile_name:` / `if active_profile_data:` / anderen Default-Checks die auf globalem State basieren — explizit als "kein Default mehr verfügbar" behandeln: `logger.warning` + graceful Fallback ohne Crash.

**Test-Setup:** Wenn Tests ein Default-Profil brauchen → pytest-Fixture die `set_profile_for_sid(test_sid, ...)` ruft. Nicht `_load_initial_profile()` recyclen.

### D-05: Source-of-Truth — User.active_profile_id (DB)

**Befund:** Aktuell existieren 3 nicht-synchrone Quellen für "aktives Profil":
1. `User.active_profile_id` (DB-Spalte, FK auf `profiles.id`) — `routes/profiles.py:171, 278`
2. `flask_session['active_profile_id']` (Cookie) — `routes/profiles.py:39-40, 269, 296-297`
3. `active_profile_data` (Modul-Global in `live_session.py`) — heute gelöscht

**Bekannte Inkonsistenzen:**
- Delete-Route cleant nur Cookie, nicht DB-Spalte → Cookie zeigt auf gelöschtes Profil
- Editor-Save setzt nur DB, nicht Cookie
- `_load_initial_profile()` setzt nur Modul-Global, weder DB noch Cookie

**Entscheidung:** `User.active_profile_id` (DB) ist die Single Source of Truth.

**Caching-Regeln:**
- **HTTP-Pfade:** lesen aus DB → cachen in `flask.g.active_profile` für Request-Lifetime (nicht im Cookie)
- **WebSocket-Connect (start_live_session):** liest aus DB → cached in `_per_sid_profile[sid]` für Connection-Lifetime
- **Activate-Route (`/api/profile/select`):** schreibt ausschließlich in DB, invalidiert Cookie-Cache, sendet Push-Update an aktive WebSocket-SIDs des Users (falls live in einem Call)
- **Flask-Session-Cookie `active_profile_id`:** deprecaten oder auf reines Convenience-Feld ohne Autorität reduzieren — wird spätestens beim nächsten Login aus DB neu gefüllt

**Plan-01-Pflicht:** Alle 3 Lese-/Schreib-Stellen inventarisieren + Konsistenz-Migration (bestehende User: DB-Spalte ist Truth, Cookie bei nächstem Login neu befüllt, Modul-Global gelöscht).

### Claude's Discretion
- Interne Granularität des `_session_state`-Dict (Flat vs. nested) — Planner entscheidet basierend auf Caller-Pattern
- Logging-Level für SID-not-found-Fälle (warning vs. info)
- Genaue Threshold-Werte für Latency-Dokumentation (N, X Sek)
