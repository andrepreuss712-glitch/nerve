# Phase 08.19.4: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 08.19.4 introduces per-SID profile isolation (`_per_sid_profile`, `_session_state`, `_per_sid_transcript`) to replace the single-global pattern. The core data-structures, lock definitions, and lifecycle functions (`init_session_state`, `pop_session_state`, `set_profile_for_sid`, `get_profile_for_sid`) are correct and well-guarded. The test suite covers the key DSGVO isolation requirements with real runtime assertions (no source-presence anti-patterns).

Four warnings were found — all are race-condition risks in `claude_service.py` and `deepgram_service.py` that arose from the migration to per-SID state. None are show-stoppers for Early Access (N=1 user), but they will surface under concurrent load and should be addressed before multi-user rollout.

## Warnings

### WR-01: `_session_state` read without lock in `_qa_pipeline_dispatch`

**File:** `services/claude_service.py:1228`
**Issue:** `ls._session_state.get(sid)` is called without acquiring `ls._session_state_lock`. In the same function, the `sid`-less fallback branch (lines 1233-1236) correctly uses `ls.state_lock`. The unguarded dict read is safe in CPython under GIL for a single get, but mutating `_session_state` (e.g., `pop_session_state` on disconnect) while iterating could produce a stale/None reference that is then used at line 1229-1231 without a None-guard.

**Fix:**
```python
# Replace lines 1227-1231:
if sid:
    with ls._session_state_lock:
        _sid_st = ls._session_state.get(sid) or {}
    _user_id = _sid_st.get('user_id') or 0
    _active_sid = sid
    _active_profile_id = _sid_st.get('active_profile_id')
```

### WR-02: `sid_state` mutated outside `_session_state_lock` — `analysiert_bisher` grows unbounded

**File:** `services/claude_service.py:850-851`
**Issue:** `sid_state` is a reference to the live dict inside `_session_state`. After the lock is released at line 839, the code mutates `sid_state` (appending to `analysiert_bisher`) at line 851 outside the lock. Two threads operating on different SIDs won't collide, but a concurrent `pop_session_state` call (from disconnect) could race with the append, writing into a now-detached dict — the write is lost silently, but more importantly `analysiert_bisher` is never cleared: it grows for the entire session lifetime without a size cap. This will slowly inflate memory and prompt context per session.

**Fix:** Add a size cap and document the intentional lock-release pattern:
```python
# Line 851 — cap at 200 entries to bound memory
_existing = sid_state.get('analysiert_bisher', [])
_existing.extend(e['text'] for e in buf)
sid_state['analysiert_bisher'] = _existing[-200:]  # rolling window
```

### WR-03: `coaching_loop` reads global `coaching_buffer` instead of per-SID buffer

**File:** `services/claude_service.py:1380-1385`
**Issue:** `coaching_loop` iterates `active_sids` (per-SID pattern introduced in 08.19.4) but then reads from the **module-global** `ls.coaching_buffer` at line 1381-1385 — not from a per-SID buffer. This means:
1. All SIDs consume the same coaching segments, so the first SID to win the `if not ls.coaching_buffer` check takes all data; other SIDs see an empty buffer.
2. Coaching entries written by User A's transcript can be processed in User B's coaching loop iteration.

The per-SID transcript buffer (`_per_sid_transcript`) was introduced for `analyse_loop` but `coaching_buffer` was not migrated. This is an acknowledged partial migration, but it constitutes a cross-user data leak risk.

**Fix (minimum viable for EA):** Add a comment noting the known limitation and guard against it emitting to wrong SID. Full fix requires per-SID coaching buffer (same pattern as `_per_sid_transcript`). At minimum, correlate the segments to the SID that generated them before emitting Socket events.

### WR-04: `handle_start_live_session` uses `user_id` from outer `try` scope before inner block that sets it

**File:** `services/deepgram_service.py:376-404`
**Issue:** The per-SID init block (lines 368-404) references `user_id` (line 376: `_db2.query(_User2).filter_by(id=user_id)`). `user_id` is assigned inside the `try` block at line 336 (`user_id = flask_session.get('user_id')`). If the FT logging block (lines 331-366) raises before the assignment completes, the variable `user_id` is undefined when the per-SID init block executes — Python raises `UnboundLocalError`. The outer `except Exception as _pe` at line 403 would swallow this, silently skipping profile init, leaving the SID with an empty profile for the entire session.

**Fix:**
```python
# At the start of handle_start_live_session, before the try blocks:
user_id = flask_session.get('user_id')  # safe default, always available
# ... rest of handler uses this rather than re-assigning inside the FT try block
```

## Info

### IN-01: `load_learning_cards` writes to module-global `state` — not per-SID

**File:** `services/live_session.py:262-273`
**Issue:** `load_learning_cards(user_id)` writes to the module-global `state['active_learning_cards']`, not to `_session_state[sid]`. This means all concurrent sessions share one set of learning cards — the last call wins. `analyse_loop` reads `ls.state.get('active_learning_cards', [])` (line 856) which will reflect whichever user's cards were loaded last.

This is consistent with the acknowledged partial migration, but worth tracking for the next phase.

---

### IN-02: `_resolve_anrede` in `prompt_pipeline.py` reads module-global `state` — not per-SID

**File:** `services/prompt_pipeline.py:243-253`
**Issue:** `_resolve_anrede` reads `state['session_anrede']` from the module-global `ls.state`, not from `_session_state[sid]`. When two concurrent users have different `anrede` settings, the last `start_live_session` event wins globally. This was the pre-08.19.4 pattern; `build_profile_context` accepts a `sid` parameter but `_resolve_anrede` ignores it.

For a hardened fix, pass the SID-specific `session_anrede` from `_session_state[sid]` into `_resolve_anrede`.

---

### IN-03: `wizard_create` uses deprecated `db.query(UserModel).get(id)` form

**File:** `routes/profiles.py:174`
**Issue:** `db.query(UserModel).get(g.user.id)` uses the legacy Query API `.get()` which is deprecated in SQLAlchemy 2.0. All other callers in the codebase use the modern `db.get(UserModel, id)` form (e.g., `app_routes.py:781`). This is inconsistent and will generate deprecation warnings.

**Fix:**
```python
# Line 174:
user = db.get(UserModel, g.user.id)
```
