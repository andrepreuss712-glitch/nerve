## Summary

NERVE laueft mit `async_mode='threading'` (Python stdlib threads). Das ist verifiziert in `app.py:45`. Weder eventlet noch gevent sind in `requirements.txt` vorhanden — das ist entscheidend: `threading.Lock` ist der korrekte Lock-Typ, kein Eventlet-Semaphor noetig.

Die fuenf Kern-Fragen sind vollstaendig beantwortbar aus dem Codebase-Scan und den offiziellen Flask-SocketIO-Docs. Das entscheidende Architektur-Problem: `analyse_loop` und `coaching_loop` sind globale while-True-Threads ohne SID-Kontext. Sie lesen aktuell aus einem einzigen globalen `ls.state`-Dict und einem einzigen `ls.transcript_buffer`. Nach der Migration muss jede Variable, die heute singular ist, in `_session_state = {sid: {...}}` liegen — und die Loops iterieren per `_session_state.keys()` statt einen einzelnen State zu bedienen.

Die `_deepgram_sessions`-Pattern in `deepgram_service.py` ist das exakte Analog: ein dict `{sid: connection}`, geschuetzt durch `threading.Lock`, cleanup im `disconnect`-Handler. Dieses Pattern eins-zu-eins uebertragen.

**Primary recommendation:** Implementiere `_session_state = {sid: {...}}` als unified dict in `live_session.py` mit einem Lock, analog zu `_deepgram_sessions`. Alle 7 `get_active_profile()`-Aufrufe werden auf SID-aware API umgestellt. Loops iterieren per SID. `_load_initial_profile()` wird geloescht.

## Q1: async_mode in dieser App — Was laeuft tatsaechlich?

### Befund (VERIFIED: app.py:45)

```python
socketio = SocketIO(app, cors_allowed_origins=CORS_ORIGIN, async_mode='threading')
```

`async_mode='threading'` ist explizit gesetzt. Weder eventlet noch gevent ist in `requirements.txt` oder `requirements-rt.txt` vorhanden.

`requirements-rt.txt` enthaelt FastAPI/uvicorn/redis — das ist ein separates Deployment-Target (kein Flask), nicht relevant fuer die Live-Session.

### Was 'threading' bedeutet

[VERIFIED: flask-socketio.readthedocs.io/en/latest/api.html]

- Python stdlib `threading.Thread` + `threading.Lock` sind die korrekten Primitiven
- `async_handlers=True` (Default): Jeder SocketIO-Event-Handler laeuft in einem eigenen Thread
- Kein Monkey-Patching noetig, kein Greenlet-API
- WebSocket-Transport funktioniert in threading-Mode mit simple-websocket oder via Gunicorn
- `socketio.start_background_task()` wrappt intern `threading.Thread` — nicht noetig, aber als Alternative zu direktem `threading.Thread` nutzbar

### Implikation fuer den Plan

- Alle bestehenden `threading.Lock()` in `live_session.py` sind korrekt und bleiben unveraendert
- Kein Ersatz durch `eventlet.semaphore.Semaphore` oder `gevent.lock.RLock` noetig
- Die neuen Locks `_per_sid_lock` und `_session_state_lock` werden als `threading.Lock()` angelegt

## Q2: SID-Lifecycle-Garantien — Connect / Disconnect / Crash

### Was Flask-SocketIO garantiert

[VERIFIED: flask-socketio.readthedocs.io/en/latest/implementation_notes.html]

- **connect-Event**: Wird gefeuert wenn Client Socket.IO-Handshake abschliesst. `request.sid` ist ab diesem Moment verfuegbar.
- **disconnect-Event**: Wird gefeuert wenn Verbindung sauber getrennt wird.

### Was NICHT garantiert ist

[VERIFIED: github.com/miguelgrinberg/Flask-SocketIO/issues/1280]

Das disconnect-Event **wird NICHT zuverlaessig gefeuert** in diesen Faellen:
- Browser-Tab wird geschlossen (abhaengig von Browser und Transport)
- Seiten-Refresh
- Netzwerkunterbrechung ohne sauberes Close
- **Server-Crash**: Kein Disconnect-Event, weil der Prozess stirbt. SID existiert dann nicht mehr im naechsten Prozess (In-Memory-State weg), aber `_session_state` wird beim Neustart leer gestartet — kein Memory-Leak moeglich.

### Ping-Timeout als Fallback

[VERIFIED: flask-socketio.readthedocs.io/en/latest/api.html]

Flask-SocketIO/python-socketio feuert disconnect mit `reason=PING_TIMEOUT` wenn der Client innerhalb von `ping_timeout` Sekunden (Default: 5s bei Socket.IO v4) nicht auf einen Ping antwortet. Das ist der Hauptmechanismus fuer "abgebrochene" Verbindungen die kein sauberes Close senden.

### Praxis-Implikation fuer den Plan

1. **Haupfall (sauber):** disconnect-Event wird gefeuert → `handle_disconnect` ruft `_session_state.pop(sid, None)` + `_per_sid_profile.pop(sid, None)` + `drop_matcher(sid)` — fertig.
2. **Edge-Case (Tab-Close, Netzbruch):** Ping-Timeout feuert disconnect nach ~5s. Gleicher Handler.
3. **Server-Crash/Restart:** In-Memory-State geht verloren. Kein stale-SID-Problem, da neuer Prozess leer startet. Kein Handlungsbedarf.
4. **Memory-Leak-Schutz:** Weil SIDs bei disconnect/ping-timeout bereinigt werden, ist die worst-case accumulation begrenzt auf aktive Verbindungen + max ~5s-Zombie-SIDs.

### Existing Pattern (VERIFIED: deepgram_service.py:399-406)

```python
@sio.on('disconnect')
def handle_disconnect(sid=None):
    from flask import request
    _sid = request.sid if sid is None else sid
    _chunk_counts.pop(_sid, None)
    _close_deepgram_connection(_sid)
    ls.drop_matcher(_sid)
```

Dieses Pattern ist bereits produktiv. Die neuen `_session_state.pop(sid, None)` und `_per_sid_profile.pop(sid, None)` Aufrufe werden in denselben Handler eingefuegt.

## Q4: flask.g in WebSocket-Handlern — Verfuegbarkeit und Fallback-Pattern

### Was die Docs sagen (VERIFIED: flask-socketio.readthedocs.io/en/latest/implementation_notes.html)

**Offizieller Wortlaut:**
> "An application context is pushed before invoking an event handler making `current_app` and `g` available to the handler."
> "A request context is also pushed before invoking a handler, also making `request` and `session` available."
> "WebSocket events do not have individual requests associated with them, so the request context that started the connection is pushed for all the events that are dispatched during the life of the connection."

**Bedeutung:** `flask.g` ist in SocketIO-Event-Handlern verfuegbar. ABER: Es ist die `g` des WebSocket-Handshake-Requests, nicht die `g` eines HTTP-Requests. Da `g` per Request-Kontext lebt und bei WebSocket-Events der "Request" die initiale Connection ist, wird `g` am Anfang jedes Events FRISCH gepusht — `g` ist NICHT persistent ueber Events hinweg.

### Konkrete Implikation fuer D-05

D-05 schlaegt vor: HTTP-Pfade cachen in `flask.g.active_profile`. Das funktioniert so:

```python
# HTTP Route — g lebt Request-Lifetime, wird von before_request gepoppt
@app.before_request
def _load_user():
    # g.user wird hier gesetzt
    ...

# WebSocket Event — g ist verfuegbar aber FRISCH pro Event-Dispatch
@sio.on('some_event')
def handle_event():
    # flask.g ist leer am Anfang jedes Events
    # flask.g.active_profile muss hier frisch gesetzt werden ODER
    # man liest aus _per_sid_profile[request.sid]
```

**Problem fuer Code der aus BEIDEN Pfaden aufgerufen werden kann:**

Funktionen wie `get_active_profile()` werden heute aus:
- HTTP-Routen (z.B. `app_routes.py:97` — `get_active_profile()` in `api_status`)
- Background-Threads ohne Request-Kontext
- WebSocket-Event-Handlern
- Innerhalb von `analyse_loop` (kein Kontext)

**Empfehlung (Claude's Discretion):** Ein unified Lookup-Helper:

```python
def get_profile_for_context(sid: str = None):
    """
    Unified profile lookup:
    - WebSocket/background: nutzt _per_sid_profile[sid]
    - HTTP: nutzt flask.g falls gesetzt, sonst DB-Lookup
    """
    # 1. Explicit SID: WebSocket-Pfad
    if sid:
        return get_profile_for_sid(sid)
    # 2. Request-Kontext verfuegbar: flask.g Check
    try:
        from flask import g
        if hasattr(g, 'active_profile'):
            return g.active_profile
    except RuntimeError:
        pass  # Kein Request-Kontext (background thread)
    # 3. Fallback: leeres Profil + warning
    return ('', {})
```

[VERIFIED: claude_service.py:212, 978, 1060, 1218; prompt_pipeline.py:135; deepgram_service.py:118]

Alle 7+ `get_active_profile()`-Aufrufe gehen aktuell gegen den Module-Global. Nach der Migration braucht jeder Caller einen SID-Parameter. Die Caller-Kette:

```

  └─> _qa_pipeline_dispatch(neuer_text, line_id, kontext, ls, sio)
```

## Q5: SID in Background-Threads — Wie bekommt der Loop die SID?

### Aktuelles Pattern (VERIFIED: claude_service.py, deepgram_service.py)

**Heute** (broken fuer Multi-User): Der Loop greift auf einen einzigen globalen State zu. Die SID ist in `ls.state['active_sid']` gespeichert — aber als einzelner Wert, nicht per User.

```python
# deepgram_service.py:297 — setzt active_sid beim Connect
with ls.state_lock:
    ls.state['active_sid'] = _sid

# claude_service.py:1192 — liest active_sid im qa_pipeline_dispatch
_active_sid = ls.state.get('active_sid')
```

**Nach der Migration (D-03):** Der Loop iteriert ueber `_session_state.keys()`:

```python
def analyse_loop():
    import services.live_session as ls
    from extensions import socketio as sio
    while True:
        ls.analyse_trigger.wait(timeout=ANALYSE_INTERVALL)
        ls.analyse_trigger.clear()
        with ls.pause_lock:
            if ls.is_paused:
                continue
        # SID-Iteration statt Single-State
        with ls._session_state_lock:
            active_sids = list(ls._session_state.keys())
        for sid in active_sids:
            with ls._session_state_lock:
                sid_state = ls._session_state.get(sid)
            if not sid_state:
                continue  # SID wurde inzwischen disconnectet
            buffer = sid_state.get('transcript_buffer', [])
            if not buffer:
                continue
            # ... Claude-Call fuer diesen SID
            # Nach Claude-Call: SID-Liveness-Check
            with ls._session_state_lock:
                if sid not in ls._session_state:
                    print(f"[Claude-1] SID {sid} disconnected during call — drop result")
                    continue
            # Emit an den konkreten SID
            sio.emit('ergebnis', ergebnis_payload, room=sid)
```

### SID-Liveness-Check nach Claude-API-Call (VERIFIED: D-03 Entscheidung)

D-03 verlangt explizit: nach jedem Claude-API-Call pruefen ob SID noch in `_session_state`. Das ist korrekt weil Claude-Calls 1-3 Sekunden dauern und der User in dieser Zeit disconnecten kann.

```python
# Nach Claude-Call:
with ls._session_state_lock:
    if sid not in ls._session_state:
        print(f"[analyse_loop] SID {sid} gone during Claude call — silent drop")
        continue
# Erst jetzt sicher emittieren
sio.emit('event', data, room=sid)
```

### Warum `request.sid` in Background-Threads nicht verfuegbar ist

[VERIFIED: flask-socketio.readthedocs.io/en/latest/implementation_notes.html]

Background-Threads haben keinen Request-Kontext. `request.sid` ist nur in SocketIO-Event-Handlern verfuegbar (weil Flask-SocketIO dort automatisch einen Request-Kontext pushed). Im Background-Thread: kein `request`, kein `flask.g`.

**Die SID muss explizit uebergeben werden** — entweder als Funktionsparameter oder durch Iteration ueber `_session_state.keys()`.

## Analog Pattern — _deepgram_sessions (VERIFIED: deepgram_service.py:9-14)

Das exakte Muster das kopiert werden soll:


Lifecycle:
- **Set:** `_open_deepgram_connection(_sid, mode=mode)` in `handle_start_live_session`

```python
# live_session.py — neues Pattern (nach Migration)
_per_sid_profile: dict = {}     # {sid: (name, daten)}
_per_sid_lock = threading.Lock()

_session_state: dict = {}       # {sid: {key: value, ...}}
_session_state_lock = threading.Lock()

def set_profile_for_sid(sid: str, name: str, daten: dict):
    with _per_sid_lock:
        _per_sid_profile[sid] = (name or '', daten if isinstance(daten, dict) else {})

def get_profile_for_sid(sid: str) -> tuple:
    with _per_sid_lock:
        result = _per_sid_profile.get(sid)
    if result is None:
        import logging
        logging.getLogger(__name__).warning(f"[SID] get_profile_for_sid: unknown SID {sid}")
        return ('', {})
    return result
```

## Common Pitfalls

### Pitfall 1: Lock-Granularitaet — _session_state_lock waehrend langer Iteration

**Was schieflaeuft:** Loop haelt `_session_state_lock` waehrend einem Claude-API-Call (1-3s). Andere Threads koennen in dieser Zeit nicht disconnect-cleanup durchfuehren.

**Wie es passiert:** Naiver Ansatz: `with _session_state_lock: for sid in _session_state: ...claude_call...`

**Wie vermeiden:**
```python
# Korrekt: Lock nur fuer Snapshot, dann Lock freigeben
with _session_state_lock:
    active_sids = list(_session_state.keys())  # schneller Snapshot
# Lock freigegeben — Claude-Call ohne Lock
for sid in active_sids:
    # SID koennte inzwischen weg sein — erneuter Check
    with _session_state_lock:
        sid_state = _session_state.get(sid)
    if not sid_state:
        continue
    # ...Claude-Call...
```

**Warning sign:** Hohe Latenz bei mehreren gleichzeitigen Sessions; Disconnect-Handler blockiert.

### Pitfall 2: flask.g in Background-Threads verwenden

**Was schieflaeuft:** `flask.g.active_profile` in `analyse_loop` oder `coaching_loop` lesen — `RuntimeError: Working outside of application context`.

**Wie es passiert:** Code der in HTTP-Routern mit flask.g funktioniert wird unveraendert in einen Background-Thread kopiert.

**Wie vermeiden:** In Background-Threads immer `_per_sid_profile[sid]` oder `_session_state[sid]` verwenden. Nie `flask.g` in Threads ohne Request-Kontext.

**Warning sign:** `RuntimeError: Working outside of application context` im Loop-Log.

### Pitfall 3: analyse_loop liest nach SID-Pop noch den alten Buffer

**Was schieflaeuft:** Loop macht Snapshot der SID-Keys, holt Buffer-Daten, dann disconnectet der User. Loop schickt Claude-Ergebnis an eine SID die nicht mehr existiert.

**Wie es passiert:** `sio.emit(..., room=dead_sid)` — Flask-SocketIO wirft keinen Fehler, emittiert aber ins Leere (kein Client empfaengt). Unproblematisch fuer Korrektheit, aber Log-Noise und verschwendete Claude-API-Kosten.

**Wie vermeiden:** Liveness-Check nach jedem Claude-Call (D-03-Pflicht). Vor dem Emit pruefen ob SID noch in `_session_state`.

**Warning sign:** Claude-API-Calls ohne sichtbares Frontend-Update, `[analyse_loop] SID gone`-Log-Meldungen.

### Pitfall 4: reset_session() loescht falschen State

**Was schieflaeuft:** `reset_session()` in `live_session.py` setzt aktuell alle Globals zurueck. In der Multi-User-Version darf es nur den State der eigenen SID zuruecksetzen.

**Wie es passiert:** `reset_session()` wird beim Call-Ende gerufen und wuerde mit der alten Implementierung alle anderen User-States mitloeschen.

**Wie vermeiden:** `reset_session(sid)` mit SID-Parameter implementieren — loescht nur `_session_state.pop(sid, None)`.

**Warning sign:** Andere Users' Calls werden abgebrochen wenn ein User seinen Call beendet.

### Pitfall 5: _load_initial_profile() nach dem Delete

**Was schieflaeuft:** Code-Stelle die `if active_profile_name:` als Guard nutzt um globalen State zu pruefen bricht nach dem Delete.

**Wie es passiert:** `_load_initial_profile()` setzte `active_profile_name` global auf einen Default. Caller die diesen Default annehmen werden nach dem Delete `('')` sehen.

**Wie vermeiden:** D-04-Pflicht: Nach Delete Grep auf `if active_profile_name:` / `if active_profile_data:` / `active_profile_name or ''` durchfuehren. Jeden Treffer explizit als "kein Default mehr" behandeln — `logger.warning` + graceful Fallback.

## Best Practices aus Flask-SocketIO-Docs

[VERIFIED: flask-socketio.readthedocs.io/en/latest]

**1. SID als Room-ID nutzen:**
`sio.emit(event, data, room=sid)` sendet an genau einen Client. SID ist der built-in Private Room jedes Clients. Dieses Pattern bereits in Verwendung (`sio.emit('qa_slot1', ..., room=_active_sid)`).

**2. `socketio.start_background_task()` vs `threading.Thread`:**
Offiziell empfohlen: `socketio.start_background_task()` weil es mit dem jeweiligen async_mode kompatibel ist. In NERVE wird direkt `threading.Thread(daemon=True)` verwendet — das ist korrekt fuer `async_mode='threading'` und bleibt unveraendert.

**3. `flask.g` Scope in Event-Handlern:**
`flask.g` ist per Event-Handler-Invocation frisch. D.h.: `flask.g.active_profile` muss in jedem HTTP-Request-Handler frisch aus DB geladen werden. Ein `before_request`-Hook fuer HTTP-Pfade ist der richtige Platz. Fuer WebSocket-Pfade ist `_per_sid_profile[sid]` die korrekte Cache-Schicht.

**4. Per-SID State — Keine Standard-Rooms/Namespaces Loesung:**
Rooms und Namespaces in Flask-SocketIO sind fuer Broadcasting/Grouping, nicht fuer State-Storage. Es gibt kein built-in per-SID State-Management in Flask-SocketIO. Das Codebase-Pattern (`_deepgram_sessions = {sid: ...}`) ist der Community-Standard.
