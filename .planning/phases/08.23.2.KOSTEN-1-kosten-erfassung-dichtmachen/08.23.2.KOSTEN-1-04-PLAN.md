## 4. Edge-Case-Analyse

1. **Skip-Flut (ein defekter Name in einer Schleife):** der Zähler wächst schnell; das Dashboard darf
   nicht 5.000 einzelne Tripel rendern → nach Tripel gruppiert zählen, Anzeige begrenzen.
2. **Zähler wächst unbegrenzt im Speicher:** Anzahl **verschiedener** Tripel ist naturgemäß klein
   (endlich viele Modellnamen) → unkritisch. Trotzdem ein Deckel, falls ein Name dynamisch entsteht.
3. **Mehrere Prozesse (nerve + nerve-rt + Worker):** jeder zählt für sich → Label „pro Prozess".
   Bewusste Grenze, keine gemeinsame Zähl-Infrastruktur.
4. **`COST_DATA_COMPLETE_SINCE` in der Zukunft / falsch gesetzt:** Badge erscheint immer bzw. nie.
   Deshalb wird X beim Deploy aus dem **echten** Datum gesetzt und danach im Dashboard verifiziert.
5. **Zeitraum überspannt das Datum:** siehe Task 3 Grenzfall (`start <`, nicht `end <`).

### Race-Condition-Audit (Punkt 14)
1. **Gleichzeitiges Feuern:** mehrere Threads erhöhen den Zähler → in CPython ist ein
   `dict[key] = dict.get(key,0)+1` nicht atomar; ein verlorenes Increment ist hier **fachlich
   irrelevant** (die Aussage ist „0 oder nicht 0"). Das im Kommentar so festhalten, statt ein Lock zu
   bauen (Über-Engineering).
2. **Verbindungsabbruch mid-Operation:** n/a (kein I/O im Zähler).
3. **Wiederverbinden mit altem Zustand:** Zähler startet bei Prozess-Start neu — genau gewollt
   („seit Deploy").
4. **Tab im Hintergrund:** Dashboard-Anzeige ist ein Abruf; kein Timer-Zustand.

### Async-Bereitschafts-Naht (Punkt 26)
Der Zähler wird **synchron im Moment des Skips** geschrieben und **beim Dashboard-Abruf** gelesen →
kein Vorauslauf-Risiko. Der Historie-Marker liest eine **Konstante**, keine fremd-geschriebenen Daten.
