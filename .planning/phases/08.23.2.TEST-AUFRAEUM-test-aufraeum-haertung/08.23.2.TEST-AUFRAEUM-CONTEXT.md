## Implementation Decisions (LOCKED aus Brief + Vorab-Scouting)

### Problem-Kern (am echten Code verifiziert 2026-07-06)
- `tests/conftest.py:548-643` `_baseline_cleanup_guard` (Phase PGTEST.GREEN Plan 01): Auto-Delete
  geleakter Rows mit `[BASELINE-AUTO-FIX]`-Warnung (Z.619), Mutual-FK-Stall-Warnung (Z.634),
  Auto-Delete-Fehlschlag-Warnung (Z.640) — **alles nur Warnung, kein `pytest.fail`**.
- `alembic/versions/0026_audit_log_immutable_trigger.py`: `trg_audit_log_immutable`
  (BEFORE UPDATE OR DELETE, `RAISE EXCEPTION 'audit_log is immutable'`) **feuert AUCH für den
  Owner** (anders als RLS ohne FORCE, im Migrations-Docstring explizit vermerkt) → jeder
  Auto-Delete-Versuch auf `audit_log` scheitert → landet im `except`-Zweig (conftest.py:640) →
  `[BASELINE-AUTO-FIX] Auto-Delete fehlgeschlagen`-Warnung.
- `nerve_test` wird per `pg_dump --schema-only nerve` gebaut (`deploy.sh:158`), MIT owners+privileges →
  der Trigger **reist mit** in die Test-DB.
- FK-Zyklus-Leak (organisations/users/tenant_orgs) dokumentiert in `tests/test_signup_journey.py:62`:
  `trg_mk_tenant_org` (Migration 0011) legt bei jedem `organisations`-INSERT eine `tenant_orgs`-Row an
  (FK ohne `ondelete`) → ohne diese Row im Cleanup FK-stallt der Organisation-Delete → Leak → Warnung.

### Bewiesene Rahmen-Fakten (Orchestrator-Scouting — für RESEARCH.md-Verbindungs-Karte bestätigen)
- **Test-Rolle = `nerve_app`** (`DATABASE_URL=postgresql://nerve_app@/nerve_test`, conftest.py:70).
  Der Baseline-Guard-Delete läuft als `nerve_app`.
- **`nerve_app` ist NICHT Superuser** (conftest.py:164 löst FK-Zyklen bewusst „OHNE Superuser/
  session_replication_role/DEFERRABLE") → **Design-Option `session_replication_role='replica'`
  ist AUSGESCHLOSSEN** (braucht Superuser).
- `nerve_test` ist `OWNER postgres` (deploy.sh:153), Schema-Dump trägt Owner/Privs treu.
  **OFFEN (Research):** Wer ownt `public.audit_log` in nerve_test? (entscheidet, ob `nerve_app`
  `ALTER TABLE ... DISABLE TRIGGER` überhaupt darf).
- **Präzedenzfall im Repo:** `deploy.sh` (~Z.170) macht bereits ein **Test-only-GRANT**
  (`GRANT DELETE ON training.transcript_archive TO nerve_anon_worker`) NUR gegen `$TEST_DB`,
  während Prod verriegelt bleibt. Dasselbe Muster (test-only Aufweichung nur auf der Wegwerf-DB,
  Prod unangetastet) ist der wahrscheinlich tragfähigste Weg für audit_log.
- **CONSTRAINT — der Immutability-Trigger muss auf nerve_test PRÄSENT + feuernd bleiben:**
  `tests/test_audit_log_immutable.py` beweist Runtime, dass UPDATE/DELETE mit
  `'audit_log is immutable'` abgelehnt werden (nutzt `db_session`-Rollback, leakt selbst NICHT).
  → **Ein globaler `DROP/DISABLE TRIGGER` auf nerve_test beim Build ist VERBOTEN** (bräche diesen
  Regressions-Test / gäbe False-Green). Trigger-Bypass MUSS eng auf den Cleanup-Delete gescoped sein.

### Design-Frage (vom Brief gestellt — Research entscheidet, Cross-AI vettet)
Wie räumt der Test-Cleanup `audit_log` trotz append-only-Trigger ab, **ohne den Prod-Schutz zu
schwächen und ohne den Immutability-Regressions-Test zu brechen**? Kandidaten (Research abwägen,
Punkt 27 „einfachster tragfähiger Weg"):
1. **Scoped `ALTER TABLE audit_log DISABLE TRIGGER trg_audit_log_immutable` + `ENABLE` in try/finally**
   NUR um den audit_log-Cleanup-Delete — NUR wenn `nerve_app` `audit_log` ownt. Risiko: ALTER-Lock,
   Re-Enable-Pflicht (sonst False-Green im Immutability-Test).
2. **Test-only SECURITY-DEFINER-Helper (Owner postgres), EXECUTE an nerve_app, NUR auf nerve_test in
   deploy.sh installiert** — Baseline-Guard ruft ihn für audit_log statt Raw-DELETE. Spiegelt den
   bestehenden Test-only-GRANT-Präzedenzfall, kein ALTER-Lock, Prod bleibt völlig unberührt.
3. FK-Reihenfolge-Fix für organisations/users/tenant_orgs separat (der audit_log-Trigger und der
   FK-Zyklus sind ZWEI getrennte Leak-Ursachen — beide müssen adressiert werden).

### Erfolgs-Kriterium
- Deploy-Gate-Lauf (`pytest -m "not live and not perf"` server-side via deploy.sh) zeigt **null**
  `[BASELINE-AUTO-FIX]`- und **null** `[PGTEST-CLEANUP]`-Warnungen für audit_log/organisations/users.
- `tests/test_audit_log_immutable.py` bleibt **grün** (Trigger firing auf nerve_test intakt).
- Prod-`nerve`: Trigger + Grants **byte-identisch unverändert** (kein Migrations-Bump, der Prod
  aufweicht — die Test-only-Aufweichung lebt in deploy.sh/conftest, nicht in einer Prod-Migration).
</decisions>

- Verbindungs-Karte (Punkt 22) muss belegen: audit_log-Owner in nerve_test, wer schreibt audit_log
  im committenden Test-Pfad (services/audit.py-Aufrufer), FK-Kanten des Zyklus.
