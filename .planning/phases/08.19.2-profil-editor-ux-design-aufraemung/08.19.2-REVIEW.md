## Warnings

### WR-01: `_pitch_dual_write` / `_erlaubnis_dual_write` — re-commits after db.close() could be called

**File:** `routes/profiles.py:518` and `routes/profiles.py:618`
**Issue:** Both `_pitch_dual_write(db, pid)` and `_erlaubnis_dual_write(db, pid)` call `db.commit()` at the end of the helper. They are called *inside* the outer `try…finally` block, but after the primary `db.commit()` for the INSERT/PUT/DELETE already succeeded. If `_pitch_dual_write` raises an unhandled exception (e.g., JSON parse error on corrupt `p.daten`), the `finally: db.close()` still runs — but the dual-write commit has not happened, and the route returns the JSON success response to the client. The client believes the item was saved, but `Profile.daten['pitch']` is stale. This is a silent data inconsistency, not a crash.

```python
# routes/profiles.py:518  (pitch_erstellen)
db.add(o)
db.commit()
_pitch_dual_write(db, pid)   # <-- if this raises, client gets 201 but daten['pitch'] is not updated
return jsonify({...}), 201
```

**Fix:** Wrap the dual-write call and log/swallow the exception explicitly so the silent failure is at least observable:

```python
try:
    _pitch_dual_write(db, pid)
except Exception as _e:
    import logging; logging.getLogger(__name__).error(f"[Profile] pitch dual-write failed pid={pid}: {_e}")
```

Or, move the dual-write commit into the same transaction as the INSERT by removing the inner `db.commit()` inside the helper and relying on the outer `db.commit()`. This requires restructuring the helper slightly but is the cleaner fix.

### WR-02: `buildAndSubmit()` sends `opener` field directly into `daten_json`

**File:** `templates/profile_editor.html:1147`
**Issue:** The `buildAndSubmit()` function in the JS puts `opener: document.getElementById('vi_opener').value.trim()` into the top-level `daten` object. This gets submitted to the `/profiles/<pid>/edit` POST endpoint, which calls `_migrate_profile_data()` on the received JSON. The migration function removes `opener` from `daten` (line 280 of `profile_schema.py`: `daten.pop('opener', None)`). So the field is stripped on save — this is by design per the D-01 comment.

However, on the *next* page load the `vi_opener` field is populated via `setVal('vi_opener', DATEN.opener)` (template line 1307), but `DATEN.opener` will always be `undefined` after migration because `opener` was popped from `daten`. The field will appear blank on every edit page reload even if the user filled it in, leading to confusing UX where saving clears the Opener field displayed in section 3.

This is a UX bug hiding a data-loss appearance: the user types an opener in the simple `vi_opener` textarea, saves, and on reload it is gone (the canonical source is `ProfileOpener` table, not `daten`). If the user treats that textarea as the primary opener entry point and saves without understanding the CRUD list below, data is silently discarded.

**Fix:** Either:
1. Remove the `vi_opener` textarea from section 3 entirely (it is redundant with the `opener-list` CRUD widget directly below it), or
2. On editor GET, populate `vi_opener` from the first row of `ProfileOpener` (type='opener') and sync it into `ProfileOpener` on save instead of into `daten`.

### WR-03: `_require_own_profile()` opens a DB session but the caller cannot guarantee `db.close()`

**File:** `routes/profiles.py:679-689`
**Issue:** `_require_own_profile()` calls `get_session()` internally and returns `(profile, db)`. The caller is then responsible for calling `db.close()` in a `finally` block. In `api_faqs_create` (line 733), `_require_own_profile()` is called *after* early-return validation (lines 725-732). If validation fails, `_require_own_profile()` is never called — so no leak. But if `_require_own_profile()` returns `(None, db)` because `p is None` (line 699), the caller does handle `db.close()` in `finally`. This is fine.

The real risk is that `_require_own_profile()` is a non-obvious pattern: it returns an open session that must be closed externally. If a future caller forgets the `finally: db.close()`, the session leaks. The current callers are correct, but the pattern is fragile.

**Fix:** Document this clearly with a docstring warning, or refactor to accept a db session as parameter rather than opening one internally:

```python
def _require_own_profile(profile_id, db):
    """Check org-ownership. Returns Profile or None. Does NOT open/close db."""
    p = db.query(Profile).filter_by(id=profile_id).first()
    if not p or not hasattr(g, 'org') or g.org is None or p.org_id != g.org.id:
        return None
    return p
```

### WR-04: `crudList()` textarea content escaping is incomplete

**File:** `templates/profile_editor.html:1226`
**Issue:** When rendering a crud-card item, the `name` input value is HTML-escaped for `"` only (`replace(/"/g, '&quot;')`), but the `textarea` content only escapes `<` (`replace(/</g, '&lt;')`). A stored `inhalt` value containing `</textarea>` would break the textarea HTML. For example, if `inhalt` is `foo</textarea><script>alert(1)</script>`, the textarea closes early and injects inline HTML.

This is a stored XSS risk because `inhalt` is stored in the DB (via the PUT endpoint which accepts arbitrary strings) and then re-rendered via `innerHTML`. The data path is: authenticated user sets inhalt → stored in DB → re-injected via innerHTML in crudList.

Since only `owner`/`admin` users of the same org can write these values, the attack surface is limited to self-XSS or same-org privilege escalation, but it is still a real XSS vector.

```javascript
// Current — unsafe:
'<textarea placeholder="Inhalt...">' + (item.inhalt || '').replace(/</g, '&lt;') + '</textarea>',

// Fix — use textContent instead of innerHTML for the textarea value:
var ta = document.createElement('textarea');
ta.placeholder = 'Inhalt...';
ta.value = item.inhalt || '';   // textContent/value assignment is XSS-safe
card.appendChild(ta);
```

Or add full HTML encoding: replace `&`, `<`, `>`, `"`, `'` before injecting into innerHTML.

### IN-03: `_migrate()` in `app.py` — `profile_opener.type` backfill only matches `name='Pitch'`

**File:** `app.py:1291`
**Issue:** The backfill UPDATE for existing opener rows with type='pitch' only matches `name='Pitch'`. Rows inserted by previous code with other names (e.g. 'Neuer Pitch', 'Pitch 1') will remain with `type='opener'` and will not appear in the `pitch_liste()` endpoint which filters by `type='pitch'`. These rows become unreachable via the CRUD API.

```python
# Current — only catches exact name match:
conn.execute(_text3("UPDATE profile_opener SET type='pitch' WHERE name='Pitch' AND type='opener'"))
```

**Fix:** Given this is a one-time migration, also match common pitch-name patterns:
```python
conn.execute(_text3(
    "UPDATE profile_opener SET type='pitch' "
    "WHERE type='opener' AND (name='Pitch' OR name LIKE 'Pitch %' OR name LIKE 'Neuer Pitch%')"
))
```
This is low risk because the backfill only runs against v1 profiles (migration skips v2 profiles via the `schema_version >= 2` check).

### IN-04: `_getCsrfToken()` silently returns empty string when `<meta name="csrf-token">` is absent

**File:** `templates/profile_editor.html:1211-1213`
**Issue:** If the meta tag is not present (e.g., the page is served from a template that does not extend `base.html`, or the meta tag is removed), `_getCsrfToken()` returns `''` and all fetch mutations will be sent with an empty CSRF token. Flask-WTF will reject these requests with 400, but the UI will silently show a save-toast failure without a meaningful error to the developer.

The current meta tag is confirmed present in `base.html` (line 6: `<meta name="csrf-token" content="{{ csrf_token() }}">`), so this is not an active bug. It is a fragility in the defense-in-depth setup.

**Fix:** Add a console.warn fallback:
```javascript
function _getCsrfToken() {
  var m = document.querySelector('meta[name="csrf-token"]');
  if (!m) { console.warn('[NERVE] csrf-token meta tag missing — mutations will fail'); return ''; }
  return m.getAttribute('content');
}
```
