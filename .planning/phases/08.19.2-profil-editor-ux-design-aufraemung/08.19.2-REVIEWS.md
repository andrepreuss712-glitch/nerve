# Cross-AI Plan Review — Phase 08.19.2

## Gemini Review

### 1. Summary
Der 4-Wellen-Plan zur UI-Vereinfachung ist frontend-seitig solide strukturiert und adressiert die UX-Ziele effektiv. Die Wave-Abhängigkeiten (CSS -> HTML -> JS -> Hints) sind logisch und mindern das Risiko bei der Modifikation der 1500-Zeilen-Datei. Es existiert jedoch ein **kritischer Architektur-Bruch** zwischen dem Frontend-Plan (D-05: Multi-Entry für Pitch im JSON) und den bereits aktiven Backend-Migrationen in `app.py` und `services/profile_schema.py`. Ohne Anpassung führt der Plan zu sofortigem Datenverlust bei Bestandskunden und dazu, dass die KI neu eingegebene Pitches ignoriert.

### 2. Strengths
- Saubere Aufteilung in 4 Waves. Das hält Commits atomar und Rollbacks einfach.
- CSRF-Bug (T-05) in `crudList()` wurde erkannt und wird konsequent für alle Fetch-Methoden behoben.
- XSS-Risiken (T-06) bei dynamischer HTML-Generierung werden durch die Nutzung der existierenden `esc()` Funktion sauber mitigiert.
- Dokumentierte Pitfalls: Abhängigkeiten wie das zwingend nötige `f_branche` Feld oder die Integrität von `profile-faqs-list` für externe JS-Scripte werden im Plan korrekt respektiert.

### 3. Concerns

- **[HIGH] KI-Blindspot & UI-Duplizierung beim Pitch.** Die Backend-Migration `app.py:_migrate_profile_json()` verschiebt Bestands-Pitches bereits in die `ProfileOpener`-DB-Tabelle. Das Backend liest ausschließlich aus dieser Tabelle. Wenn Plan 03 (Task 3) neue Pitches als reines Frontend-JSON-Array (`DATEN.pitches`) speichert, **wird die KI diese Daten niemals sehen**. Gleichzeitig tauchen alte Pitches der User plötzlich im Frontend in der "Opener"-Liste auf, weil `crudList` stumpf alle Einträge der `ProfileOpener`-Tabelle lädt.

- **[HIGH] Datenverlust bei Erlaubnisfrage & Pitch durch Backend-Drop.** `services/profile_schema.py` führt bei jedem Laden älterer Profile ein hartes `.pop('erlaubnis')` und `.pop('pitch')` auf dem JSON-Blob aus. Das bedeutet: Wenn die `init()` Funktion des Frontends den Backward-Compat-Check (`DATEN.erlaubnis ? [DATEN.erlaubnis] : []`) ausführt, ist der Wert bereits `undefined`. Die alten Daten gehen beim Klick auf "Speichern" unwiederbringlich verloren.

- **[LOW] CSS-Selector Syntax beim CSRF-Fix.** Plan 03 notiert `document.querySelector(meta[name=csrf-token])`. Ohne Anführungszeichen um `csrf-token` kann das zu unsauberen DOM-Selector-Errors führen.

### 4. Suggestions
- **Pitch-Strategie an Backend anpassen:** Verwirf die Idee, Pitch als JSON-Array (`DATEN.pitches`) abzuspeichern. Pitches müssen weiterhin über die `ProfileOpener`-DB-Tabelle fließen, da die gesamte KI-Logik darauf umgestellt wurde. Benenne die "Opener"-Sektion stattdessen in "Opener & Pitch" um, oder erweitere `crudList`, um beide Typen sauber in der DB zu speichern.
- **Backend-Pop für Erlaubnisfrage stoppen:** Wenn die Erlaubnisfrage im JSON-Array überleben soll, MUSS im Backend in `services/profile_schema.py` das `daten.pop('erlaubnis', None)` entfernt werden. Sonst hat das Frontend keine Chance auf eine Daten-Migration.
- **CSRF-Fix Präzision:** Implementiere den Token-Fetcher explizit als `document.querySelector('meta[name="csrf-token"]').content` (mit Anführungszeichen im Selector).
- **Zusätzlicher Test im Checkpoint:** Füge zur 22-Item Verification Checklist einen Punkt hinzu, der prüft, ob nach dem Speichern eines bestehenden v1-Profils die alten Erlaubnis/Pitch-Einträge noch vorhanden sind.

### 5. Risk Assessment
**HIGH** — Die isolierte Betrachtung des Frontends führt hier zu einem schweren Architektur-Drift. Der Plan darf so nicht umgesetzt werden. Frontend (JSON-Storage) und Backend (`ProfileOpener` DB-Tabelle) haben stark widersprüchliche Annahmen darüber, wo der Pitch lebt. Dies führt zu lautlosem Datenverlust und funktionalen Regressionen (KI-Briefing ohne Pitch).

## Gemini Review — Run 2 (2026-04-28, final plans)

### 1. Summary
Der Plan ist strukturell exzellent in vier aufeinander aufbauende Waves (CSS → HTML/DB → JS/Security → Content) unterteilt und setzt die UX-Ziele (Reduktion von 15 auf 6 Sektionen, UI-Cleanup) sauber um. Das Hinzufügen von CSRF-Tokens für asynchrone Listen-Updates und die Tenant-Isolierung (org_id Check) schließen offene Sicherheitslücken passend zu den Erkenntnissen aus Block B. Allerdings enthält der Plan einen massiven Logik-Fehler im Zusammenspiel mit dem Backend (Schema-Drift ohne Backend-Update), der den Live-Coach im Call funktionsunfähig machen kann.

### 2. Strengths
- **Smarte Phasen-Trennung:** CSS-Vorbereitung (Wave 1) entkoppelt vom DOM-Umbau (Wave 2) minimiert das Risiko von kaputtem Layout während der Implementierung.
- **Security First:** Die neuen `pitch_liste`/`erlaubnis_liste`-Routen erhalten direkt einen `org_id`-Check (Mandanten-Isolierung) und die asynchronen `crudList`-Calls werden gegen CSRF abgesichert.
- **Risiko-Minimierung im Payload:** Das bewusste Behalten des `f_branche` Hidden-Inputs verhindert Abstürze beim JSON-Payload-Parsing im Backend.
- **UX-Fokus:** 15 Sektionen auf 6 Gruppen zu reduzieren und irrelevante Slider (Intensität) hart zu entfernen, senkt die kognitive Last für den Nutzer drastisch.

### 3. Concerns
- **[HIGH] Bruch der KI-Pipeline durch asynchronen Schema-Drift.** Plan 02 migriert "Erlaubnis" und "Pitch" in die SQL-Tabelle `ProfileOpener`. Plan 03 stoppt das Speichern dieser Felder im JSON (`DATEN`). Aber: Der Plan schließt das Backend-Update explizit aus (`build_profile_context() DEFERRED to 08.20`). Wenn das Backend weiterhin in `Profile.daten['pitch']` sucht, die Daten dort aber nicht mehr gespeichert werden, fehlen Pitch und Erlaubnisfrage künftig komplett im LLM-Prompt.
- **[HIGH] Multi-Worker Race-Conditions bei der Migration.** Plan 02 plant eine idempotente ALTER TABLE Migration und einen Backfill per Profile beim App-Boot. Wenn Gunicorn mehrere Worker zeitgleich startet, versuchen alle die Tabelle zu sperren — bei SQLite führt das zu `database is locked`-Errors.
- **[MEDIUM] Vorhandensein des CSRF-Meta-Tags.** Plan 03 verlässt sich auf `meta[name="csrf-token"]`. Dieser wird von Flask nicht automatisch ins HTML eingefügt. Wenn er in `base.html` nicht existiert, schlagen alle `crudList` Fetch-Requests fehl.
- **[LOW] Visuelles Feedback beim crudList Auto-Save.** `crudList` speichert asynchron. Wenn der große Speichern-Button diese Felder nicht mehr erfasst, braucht der Nutzer Feedback sobald er einen neuen Pitch-Eintrag hinzufügt.

### 4. Suggestions
- **Dual-Write als Workaround für HIGH #1:** Solange Phase 08.20 nicht live ist, müssen die neuen CRUD-Endpoints für Pitch und Erlaubnisfrage die Listen-Daten zusätzlich als zusammengebauten String in das `Profile.daten` JSON-Feld zurückschreiben. So bleibt `build_profile_context()` intakt.
- **Migration entkoppeln:** Die DB-Migration darf nicht im Worker-Context laufen. Entweder als separaten Schritt in `deploy.sh` auslagern oder ein File-Lock einbauen, sodass nur Worker #1 den Backfill durchführt.
- **CSRF-Tag explizit prüfen:** Sicherstellen dass `<meta name="csrf-token" content="{{ csrf_token() }}">` im `<head>` von `profile_editor.html` oder `base.html` existiert, bevor das JS darauf zugreift.
- **Toast-Integration:** `.save-toast` aus Plan 01 an den `fetch().then()` Success-Handler in `crudList` binden.

### 5. Risk Assessment
**HIGH** — Die Frontend-Aufgaben und Security-Checks sind hervorragend geplant, aber der blinde Fleck bei den Backend-Dependencies führt zu einem kritischen System-Fehler. Wenn das UI auf ein Multi-Entry SQL-Modell umgebaut wird, das lesende System (Live-Call Pipeline) aber weiterhin auf alte JSON-Pfade horcht, bricht die Qualität der EWB-Antworten ein. Dieser Issue muss vor der Ausführung über einen Dual-Write oder vorgezogenen Backend-Patch gelöst werden.

## Consensus Summary (2 Gemini Runs)

Both Gemini runs independently flagged the same critical architectural concern.

### Agreed Strengths
- 4-wave sequential execution (CSS → HTML/DB → JS → Content) is the right dependency order
- CSRF fix is comprehensive (POST, PUT, DELETE all covered)
- `org_id` check on all new pitch/erlaubnis endpoints — correct multi-tenancy
- Documented pitfalls (f_branche hidden input, sec-faqs DOM IDs) show good awareness of fragile dependencies
- Slider removal is clean and complete (HTML + JS buildAndSubmit + init setSlider calls)

### Agreed Concerns — Must Address Before Execution

**1. [HIGH] Pitch/Erlaubnisfrage pipeline break — raised by both runs**

Plan 02 moves pitch and erlaubnis into the `ProfileOpener` SQL table. Plan 03 stops serializing them in `buildAndSubmit`. But `build_profile_context()` (the function that builds the LLM prompt) is explicitly deferred to 08.20. If it still reads from `Profile.daten['pitch']`, **the AI will receive no pitch and no erlaubnis** after this phase ships. Both runs recommend a **dual-write**: new CRUD endpoints should also write back the concatenated content into `Profile.daten` until 08.20 rewires the prompt pipeline.

**2. [HIGH] Multi-worker race condition on boot migration — Run 2 only**

The ALTER TABLE + per-profile backfill runs at app boot inside `app.py`. With Gunicorn multi-worker, all workers attempt the migration simultaneously → SQLite `database is locked`. Mitigation: file-based lock or move migration to a pre-startup `deploy.sh` step.

**3. [MEDIUM] CSRF meta tag may not exist**

`_getCsrfToken()` queries `meta[name="csrf-token"]`. If this tag is absent from `base.html` / `profile_editor.html`, all crudList mutations silently fail. Explicitly verify/add `<meta name="csrf-token" content="{{ csrf_token() }}">` in Plan 03.

**4. [LOW] No save feedback for crudList auto-saves**

When a user adds a new Pitch entry it saves via crudList API, not via the main Save button. The `.save-toast` class (Plan 01) should be wired into `crudList`'s `fetch().then()` success handler.

### Divergent Views
- Run 1 flagged a potential data-loss path via `profile_schema.py` `.pop('erlaubnis')` destroying backward-compat data on first save. Run 2 did not re-flag this specifically but its dual-write suggestion addresses the same root cause. Verify whether `pop('erlaubnis')` in `profile_schema.py` still executes on profiles that have already migrated.
