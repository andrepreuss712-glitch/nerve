## Fix 1: Wizard — Vollstaendige Feld-Inventur

### Was kaputt ist (dreifaches Problem)

**Problem A — Response-Format-Mismatch:** [VERIFIED: Code-Analyse]
- Frontend (`profiles_list.html:392-400`) erwartet JSON: `res.json()` → prueft `d.ok`, liest `d.redirect`
- Backend (`profiles.py:186`) gibt `redirect(url_for('dashboard.index'))` zurueck — kein JSON
- Resultat: `res.json()` wirft Exception → catch-Block → `alert('Netzwerkfehler')`

**Problem B — Content-Type/Parser-Mismatch:** [VERIFIED: Code-Analyse]
- Frontend sendet `Content-Type: application/json` + JSON-Body
- Backend liest `request.form.get('firma', '')` — liest immer leere Strings
- Kein `X-CSRFToken` Header → Flask-WTF gibt 400 zurueck (noch vor Handler-Logik)

**Problem C — Feldnamen-Mismatch:** [VERIFIED: Code-Analyse]

| Frontend sendet | Backend liest | Im Schema? | Pflicht im Wizard? |
|-----------------|---------------|------------|---------------------|
| `name` | `firma` | `meta.firma` (str) | JA — Profilname |
| `branche` | `branche` | DB-Column (via `_normalize_branche`) | JA — Whitelist |
| `produkt` | `produkt` | `basis.produktbeschreibung` | JA — Kernfeld |
| `preismodell` | NICHT gelesen | `basis.preismodell` (str, optional) | NEIN → optional |
| `einwaende` | `einwaende` (JSON-String) | `einwaende_detail` (nach v4-Migration) | JA — Kern-Wizard |
| `phasen` | NICHT gelesen | `phasen` (List[dict]) | [D-05 klären] |
| — | `rolle` | `meta.rolle` (str) | NEIN → optional |
| — | `zielkunden` | `basis.zielkunden` (str) | JA (Wizard hat kein Feld!) |
| — | `eigener_einwand` | wird in `einwaende_list` gemergt | obsolet nach Umbau |
| — | `unternehmensgroesse` | `zielkunde.unternehmensgroesse` | JA (Wizard hat kein Feld!) |

**Fehlende Wizard-Felder (im Backend-Schema Pflicht, aber kein Frontend-Input):**
- `zielkunden` (basis.zielkunden) — fehlt komplett im Frontend-Wizard
- `unternehmensgroesse` (zielkunde.unternehmensgroesse — Pflicht-Wizard-Feld laut Schema-Kommentar)

**Frontend-Felder die das Backend nicht kennt:**
- `preismodell` → lands in `basis.preismodell` (optional) → behalten, Backend lesen
- `phasen` → `phasen: List[dict]` im Schema, aber Backend `wizard_create()` liest es nicht → D-05-Entscheidung

### Fix-Strategie (D-01 + D-02 + D-03)

**Backend-Aenderungen (`routes/profiles.py` Funktion `wizard_create`):**
1. `request.form.get(...)` → `request.get_json(force=True)` (D-01)
2. Feldnamen-Mapping nach neuer Tabelle (D-03)
3. Response: statt `redirect(...)` → `jsonify({'ok': True, 'redirect': url_for('dashboard.index')})` fuer Erfolg, `jsonify({'error': '...'})` fuer Fehler
4. Flask-WTF-CSRF via Header: `@csrf.exempt` ODER Header-Validation automatisch wenn X-CSRFToken gesetzt (Flask-WTF prueft Header automatisch bei JSON-Requests wenn korrekt konfiguriert)

**Frontend-Aenderungen (`templates/profiles_list.html` Funktion `submitWizard`):**
1. `X-CSRFToken` Header ergaenzen (Kopie aus `_getCsrfToken()` in `profile_editor.html`) (D-02)
2. Payload-Felder umbenennen: `name` → `firma`, `produkt` → `produkt` (unkritisch — Backend liest `produkt`)
3. `zielkunden`-Feld ergaenzen (neues Input-Feld oder Step ergaenzen)
4. `unternehmensgroesse`-Feld ergaenzen (Enum-Whitelist: `<10`, `10-50`, `50-250`, `250-1000`, `1000+`)

**CSRF-Mechanismus (wichtige Klarstellung):**
Flask-WTF prueft den CSRF-Token bei POST-Requests. Bei JSON-Requests (`Content-Type: application/json`) akzeptiert Flask-WTF den Token im `X-CSRFToken` HTTP-Header (nicht im Body). Das Pattern existiert bereits in `pip-launcher.js:8-11` und `profile_editor.html`. Einfach uebernehmen.

**Vorlage fuer JSON-Pattern (`routes/profiles.py:343+`):**
```python
# Bestehendes JSON-Pattern (verifiziert):
data = request.get_json(force=True) or {}
firma = data.get('firma', '').strip()
# ... dann jsonify({'ok': True, ...}) zurueck
```

### Pydantic-Validation bleibt

`wizard_create()` validiert bereits mit `ProfileSchema.model_validate()` vor DB-Write (WR-01, Zeile 164). Das bleibt unveraendert. Nach dem Feldmapping-Fix muss die Validation trotzdem gruen sein.

**Kritische Enum-Werte (`UnternehmensgroesseEnum`):** [VERIFIED: profile_schema.py:39]
```
'<10', '10-50', '50-250', '250-1000', '1000+'
```
Frontend-Chips muessen exakt diese Literal-Werte senden (laut Schema-Kommentar Zeile 26).

## Fix 3: PiP-Schliess-Bug — Technische Tiefenanalyse

### Architekturverstaendnis (aus pip-launcher.js)

**Wie PiP heute geoeffnet wird:**
1. User-Click → `startCall()` → `_openPipAndMic()` (Zeile 1339)
2. `window.documentPictureInPicture.requestWindow({width:480, height:900})` (Zeile 1361) — BRAUCHT USER-GESTURE
3. PiP-Window wird geoeffnet, `pip-live-window` DOM-Element wird via `appendChild` IN das PiP-Window verschoben (Zeile 1551)
4. Mic gestartet, Socket verbunden — State lebt im `state`-Objekt des IIFE in `pip-launcher.js`

**Warum PiP bei Navigation stirbt:**
- Das `pip-live-window` Element lebt im DOM der Ursprungsseite (wird via `appendChild` ins PiP verschoben)
- Navigation zerstoert den DOM der Ursprungsseite → PiP-Window verliert seinen Inhalt
- `pagehide` Event feuert auf PiP-Window (Zeile 1579): DOM-Element wird zurueckgeholt, `_stopMic()` wird aufgerufen
- `state.pipWindow` wird auf `null` gesetzt

**Kritische Constraint: User-Gesture fuer `requestWindow()`**
`window.documentPictureInPicture.requestWindow()` erfordert laut Chrome-Spec eine User-Activation (User-Gesture). [CITED: https://wicg.github.io/document-picture-in-picture/] Das gilt fuer Chromium 116+. Es gibt KEINEN programmatischen Weg um ohne User-Geste ein neues `documentPictureInPicture`-Window zu oeffnen.

**Was serialisierbar ist, was nicht:**
- `state.pipWindow` (Window-Handle): NICHT serialisierbar, NICHT uebertragbar
- `state.socket` (Socket.IO-Verbindung): NICHT serialisierbar (lebt in Seiten-Kontext)
- `state.mode`, `state.activeProfileId`, `state.micStarted`: serialisierbar (Strings/Booleans)
- `state.pipSlots[].text`, `state.pipSlots[].result`: serialisierbar (Strings/Objekte)
- `state.precallBriefing`: serialisierbar (Plain Object)
- `state.micStream` (MediaStream): NICHT serialisierbar, NICHT uebertragbar zwischen Seiten

### Drei Ansaetze — Technische Bewertung

**Ansatz A: BroadcastChannel + localStorage State-Transfer**

Konzept: Vor Navigation → State in `localStorage` speichern + BroadcastChannel senden. Neue Seite → erkennt `nerve_pip_active=1` in localStorage → zeigt "PiP-Wiederaufnahme"-Button.

Problem: Mic-Stream und Socket-Verbindung koennen NICHT uebertragen werden. Nach Navigation muss der User den Call neu starten — das ist kein "PiP ueberlebt Navigation", sondern "PiP wird nach Navigation neu gestartet".

Weiteres Problem: `requestWindow()` auf der neuen Seite braucht User-Geste. Der "Wiederaufnahme"-Button waere die User-Geste — das ist korrekt und ausreichend.

**Machbarkeit fuer Flask + Vanilla JS: HOCH.** Kein Framework-Wechsel, keine neuen Libs.

**Realer UX-Impact:** PiP schliesst sich bei Navigation, User sieht Banner/Button auf neuer Seite "Live-Assistent weiterlaufen lassen" — ein Klick restartet PiP. Mic-Verbindung wird neu aufgebaut. Das ist ein UX-Kompromiss — kein echtes "PiP ueberlebt Navigation".

**Ansatz B: SharedWorker / Service Worker als State-Halter**

Konzept: SharedWorker haelt State zwischen Seiten. Service Worker + Background Fetch.

Problem: Socket.IO-Verbindung lebt im Haupt-Thread, nicht im Worker. Audio-Worklet ist nicht aus Worker ansteuerbar. Mic-Stream kann nicht an Worker uebergeben werden. Worker koennte State halten, aber die aktive Call-Verbindung muss trotzdem neu aufgebaut werden nach Navigation.

**Machbarkeit fuer Flask + Vanilla JS: MITTEL** (aufwendig, loest das Kern-Problem nicht vollstaendig). SharedWorker bringt keine echte Verbesserung gegenueber localStorage fuer diesen Use-Case, weil das Kern-Problem (Mic-Stream-Unterbrechung bei Navigation) unvermeidlich ist.

**Ansatz C: URL-State `?pip=1` + Re-Launch**

Konzept: Navigation-Links werden mit `?pip=1` ergaenzt. Neue Seite erkennt Query-Param, zeigt "Call ist aktiv"-Banner, User klickt → PiP neu geoeffnet.

Problem: Navigation-Links muessen alle angepasst werden (base.html). `?pip=1` wird in URL-Bar sichtbar. Sauberere Alternative: `localStorage` statt URL-Param.

**Machbarkeit fuer Flask + Vanilla JS: HOCH.** Aber URL-Param-Ansatz ist aestetisch schlechter als localStorage.

### Empfehlung fuer Plan-Phase

**Empfohlener Ansatz: localStorage-Flag + Re-Launch-Banner (vereinfachter A)**

Implementierung:
1. Wenn PiP aktiv ist (`state.micStarted = true`), setzt `pip-launcher.js` bei `pagehide` (der bereits existiert): `localStorage.setItem('nerve_pip_was_active', '1')`
2. Neue Seite (jede Seite via `base.html`): beim Laden prueft ein kleines Inline-Script `localStorage.getItem('nerve_pip_was_active')` — wenn gesetzt: zeigt ein Banner "Dein Live-Call laeuft noch — hier klicken um fortzufahren"
3. Banner-Click → `window.NerveLauncher.open()` (User-Geste fuer neue `requestWindow()`-Anfrage)
4. Beim Oeffnen des Launchers im Step 6 (Live) direkt → `startCall()` wird ausgefuehrt
5. `nerve_pip_was_active` wird bei normalem Call-Ende (endCall) geloescht

**Einschraenkungen, die im Plan ehrlich dokumentiert werden muessen:**
- Mic-Session wird unterbrochen (Backend erkennt neue Start-Anfrage)
- Audio-Transkription hat eine Luecke waehrend der Navigation
- Socket-Verbindung wird neu aufgebaut
- Das ist kein "seamless PiP" — es ist ein "PiP-Wiederaufnahme-Flow"

**Warum trotzdem akzeptabel:**
- Acceptance-Criterion im SPEC.md ist: "PiP-Fenster bleibt offen" — das ist mit echter `documentPictureInPicture`-API UNMOEGLICH ohne User-Geste
- SPEC.md Fallback-Kriterium (Zeile 45): "Architekturentscheidung dokumentiert + Aufschub begruendet zaehlt als erfuellt"
- Recommendation: Technisch sauber dokumentieren dass echtes "PiP-ueberlebt-Navigation" mit `documentPictureInPicture` API-seitig nicht moeglich ist, und Re-Launch-Flow als pragmatischen Fix anbieten

**WICHTIG fuer Cross-AI-Briefing (D-12):**
Gemini muss `pip-launcher.js` vollstaendig als Kontext erhalten. Besonders relevant:
- `_openPipAndMic()` (Zeile 1339) — User-Gesture-Constraint

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CSRF-Validation | Eigene Token-Logik | Flask-WTF (schon aktiv) | X-CSRFToken Header wird automatisch geprueft |

## Common Pitfalls

### Pitfall 1: Wizard-Fix nur halb (Backend ODER Frontend, nicht beides)

**Was schiefgeht:** Backend auf `get_json()` umstellen, aber Frontend sendet keinen CSRF-Header → weiterhin 400. ODER Frontend-Feldnamen korrigieren, Backend liest weiterhin `request.form` → alles leer.
**Warum:** Dreifaches Problem (Response-Format + Parser + Feldnamen) erfordert gleichzeitige Aenderung beider Seiten.
**Vermeidung:** Beide Dateien im selben Commit. Validation: POST `/profiles/wizard` mit curl + korrekten Headers testen.

### Pitfall 2: Wizard-Response-Format vergessen

**Was schiefgeht:** Backend auf `get_json()` umgestellt, Felder korrigiert, aber Backend gibt immer noch `redirect(url_for('dashboard.index'))` zurueck. Frontend ruft `res.json()` auf ein 302-Response → Exception.
**Vermeidung:** Backend muss `jsonify({'ok': True, 'redirect': url_for('dashboard.index')})` zurueckgeben — nicht `redirect()`.

### Pitfall 3: Unternehmensgroesse Enum-Werte falsch

**Was schiefgeht:** Frontend-Chips senden `"klein"` oder `"<10 Mitarbeiter"` statt exakt `"<10"` → Pydantic-Validation schlaegt fehl → Flash-Message, kein Profil erstellt.
**Warum:** `ProfileSchema extra='forbid'` + `UnternehmensgroesseEnum = Literal['<10', '10-50', '50-250', '250-1000', '1000+']` (profile_schema.py:39).
**Vermeidung:** Frontend-Select-Values muessen exakt diese Strings sein. Kein Freitext.

### Pitfall 4: PiP-Fix ueberschaetzt (false expectations)

**Was schiefgeht:** Plan verspricht "PiP ueberlebt Navigation" — das ist mit `window.documentPictureInPicture` technisch unmoeglich ohne User-Geste.
**Warum:** `requestWindow()` ist User-Gesture-only. Keine programmatische Alternative.
**Vermeidung:** Plan dokumentiert ehrlich: "Re-Launch-Flow" statt "seamless survival". SPEC.md Fallback-Kriterium (Begründung + Architekturentscheidung) als primaere Erfuellung verwenden.

### Pitfall 5: Wave-Reihenfolge missachten

**Was schiefgeht:** Wave-2-Fixes starten bevor Wave-1-Findings-Bericht committed ist.
**Constraint:** SPEC.md Boundaries: "Wave 1 muss vollstaendig + committed sein bevor Wave 2 startet."
**Vermeidung:** Checkpoint-Task im Plan nach Wave 1, der explizit verifiziert ob `03 Planung/UI-Audit-Ergebnis-2026-05-XX.md` existiert und committed ist.

### Pitfall 6: Neue Wizard-Felder ohne Template-Anpassung

**Was schiefgeht:** Backend-Code liest `zielkunden` und `unternehmensgroesse` — aber im Wizard-Frontend gibt es diese Input-Felder nicht. Backend empfaengt `null`/`''` → Pydantic-Validation kippt bei `unternehmensgroesse` wenn Required.
**Vermeidung:** Neue Backend-Felder benoetigen neue Frontend-Inputs. `zielkunden` (Text-Input), `unternehmensgroesse` (Select mit Enum-Werten). Beide als optionale Felder mit Default behandeln wenn 5-Minuten-Constraint Pflicht macht (D-04).
