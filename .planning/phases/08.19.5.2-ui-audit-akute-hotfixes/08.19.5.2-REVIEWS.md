### PLAN 02 — Wave 2a: Profil-Wizard Fix

**1. Summary**

A comprehensive fix that correctly diagnoses the frontend/backend mismatch (JSON vs Form Data) and addresses the missing CSRF header, which is critical for Flask-WTF.

**2. Strengths**
- Fixes the root cause of the 400 errors (Missing CSRF + Content-Type mismatch).
- Sensible pruning: Leaving `preismodell` optional and omitting `phasen` keeps the friction low.
- Enforces strict Enum literals for `unternehmensgroesse`, preventing database validation errors.

**3. Concerns**
- **HIGH:** CSRF Token Retrieval. The plan states `_getCsrfToken()` will be copied from `profile_editor.html`. If this function relies on a `<meta name="csrf-token">` tag in the `<head>`, you must ensure `profiles_list.html` actually *has* that meta tag rendered by the server. If it's missing, the fix will fail.
- **MEDIUM:** `request.get_json(force=True)` will throw a `werkzeug.exceptions.BadRequest` if the body is completely empty or invalid JSON.
- **LOW:** Adding two new fields brings the total to 5. We must ensure the UI comfortably fits these into the 3-step design without overwhelming the user.

**4. Suggestions**
- Change `request.get_json(force=True)` to `request.get_json(silent=True) or {}`. This is safer and won't crash Flask if the payload is malformed; it will just fall back to validation errors.
- Explicitly verify the existence of the CSRF meta tag in the layout/template before implementing the JS fetch logic.
- **Field Mapping Check:** 5 fields (Firma, Branche, Produkt, Zielkunden, Unternehmensgröße) are perfectly fine for a 3-step wizard (e.g., Step 1: Basics, Step 2: Product, Step 3: Audience). This keeps friction well under 5 minutes.

**5. Risk Assessment**

**MEDIUM.** Modifying onboarding flows always carries the risk of locking out new users if the CSRF or JSON payload logic has a typo.

### PLAN 03 — Wave 2b: Dashboard + Nav + PiP

**1. Summary**

Addresses the trivial UI bugs cleanly and proposes a technically accurate, pragmatic workaround for the PiP navigation limitation inherent to Multi-Page Applications (MPAs).

**2. Strengths**
- Correctly identifies the browser constraint: `requestWindow()` requires a user gesture, making "seamless" PiP across MPA navigations impossible.
- The `localStorage` + Banner approach is the industry-standard workaround for this stack constraint.

**3. Concerns**
- **MEDIUM (Accessibility):** `onclick="location.href='...'"` on a `<div>` is not accessible to screen readers or keyboard navigation.
- **MEDIUM (State Loss):** The plan notes "Mic-Session wird bei Navigation unterbrochen". When the user clicks the banner to relaunch, does `NerveLauncher.open()` start a *brand new* session, or does it attempt to resume the broken one? If it starts a new one, the user might lose their context/coaching history for that call.

**4. Suggestions**
- **Dashboard Fix:** Instead of a `div` with `onclick`, either wrap the row contents in a semantic `<a>` tag styled as a block, or add `tabindex="0"`, `role="link"`, and a keyboard event listener (`Enter`/`Space`) alongside the click handler.
- **PiP Architecture Answer:** Yes, the `localStorage` Re-Launch-Flow is mathematically the soundest approach given the `Flask + Vanilla JS` constraint. An SPA would keep the DOM alive and wouldn't drop the PiP window, but in an MPA, a page reload destroys the window context.
- *To improve the PiP Flow:* Ensure the banner clearly states "Call paused. Click to resume." and pass the `session_id` into the `localStorage` flag so `NerveLauncher.open(resumeId)` can stitch the context back together on the backend.

**5. Risk Assessment**

**MEDIUM.** The PiP workaround involves state management across page loads, which can lead to edge cases (e.g., banner getting stuck if `pagehide` fails to clean up properly).

### Actionable Concerns (in Priority Order)

**HIGH — Plan 02: CSRF Meta-Tag Präsenz verifizieren**
- `_getCsrfToken()` liest `meta[name="csrf-token"]` — muss in `base.html` existieren, auf die `profiles_list.html` extends
- Faktisch: `base.html:6` hat `<meta name="csrf-token" content="{{ csrf_token() }}">` (aus RESEARCH.md verifiziert) — profiles_list.html extends base.html → Meta-Tag ist da
- **Aktion für Executor:** Vor dem Commit einmal `grep -n "csrf-token" templates/base.html` laufen lassen und im SUMMARY dokumentieren

**MEDIUM — Plan 02: get_json(force=True) → get_json(silent=True)**
- `force=True` + malformed Body → werkzeug BadRequest Exception statt graceful Validation
- `silent=True` gibt None zurück bei malformed JSON → `or {}` fängt es → Pydantic-Validation schlägt fehl → 400 JSON-Error (korrekt)
- **Aktion für Executor:** `request.get_json(force=True)` → `request.get_json(silent=True)` in wizard_create() ändern

**MEDIUM — Plan 03: PiP State-Loss bei Re-Launch**
- NerveLauncher.open() startet neue Session — Coaching-History des laufenden Calls geht verloren
- Verbesserung: active_session_id oder activeProfileId in localStorage-Flag mitspeichern, damit Resume-Banner Kontext anzeigen kann
- Scope-Entscheidung: Für ersten Fix akzeptabel als "Wiederaufnahme-Flow" (SPEC.md Fallback-Acceptance). Session-ID-Passing als optionale Verbesserung, nicht Blocker.

**MEDIUM — Plan 03: div onclick Accessibility**
- Für Pre-Launch B2B SaaS akzeptierter Trade-off — keine Screen-Reader-Pflicht in v1
- Mittel-Finding → Block O Backlog
