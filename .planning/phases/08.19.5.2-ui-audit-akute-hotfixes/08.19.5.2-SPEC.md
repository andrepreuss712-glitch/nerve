## Goal

Systematische UI-Inventur aller 11 Seiten (Wave 1) liefert einen priorisierten Findings-Bericht; danach werden 4 bestätigte Pre-Launch-Bugs plus alle Wave-1-kritischen Findings gefixt (Wave 2) — bevor DSGVO-Härtung (Phase 08.19.6) darauf aufbaut.

## Background

Beim UAT für Phase 08.19.5 wurden vier Bugs aufgespürt, die nichts mit 08.19.5 zu tun haben — sie waren vorher schon kaputt:

1. **Profil-Wizard** (`routes/profiles.py:100–131`): Frontend sendet JSON (`fetch` + `Content-Type: application/json`), Backend liest `request.form.get()` — Drift. Kein `X-CSRFToken`-Header → Flask-WTF gibt 400. Zusätzlich Feldnamen-Mismatch (Frontend: `name/branche/produkt/preismodell/einwaende/phasen` vs. Backend: `firma/branche/rolle/produkt/zielkunden/eigener_einwand/einwaende/unternehmensgroesse`).

2. **Sessions im Dashboard** (`templates/dashboard.html:729`): `db2-session-row`-Divs werden ohne `onclick`/`href` gerendert. Das Pattern existiert 20 Zeilen tiefer bei `db2-reco-item:749` — aber nicht bei Session-Rows.

3. **PiP-Schließ-Bug**: PiP nutzt `window.documentPictureInPicture.requestWindow()` — das Fenster ist an die Lebensdauer der Ursprungsseite gebunden. Navigation weg von der Seite → PiP schließt sich automatisch. Architekturentscheidung (BroadcastChannel, Service Worker, etc.) offen für Plan-Phase.

4. **Nav-Label** (`templates/base.html:56`): `<span class="n-nav-label">Profil</span>` — soll `Profile` sein.

Zusätzlich: André hat bei der Sterne-Bewertung festgestellt, dass er als Founder selbst nicht wusste, dass das Feature existiert ("ich wusste nicht mal selber dass das möglich sein sollte"). Das ist ein Discoverability-Problem, das größer ist als diese 4 Bugs — daher Wave 1 UI-Audit als Fundament für Block O / Visual-Polish.

## Requirements

1. **UI-Audit Findings Report**: Systematische Inventur aller 11 UI-Seiten dokumentiert in einer Findings-Datei.
   - Current: Keine vollständige Inventur existiert; unbekannte Anzahl toter Buttons/Links und nicht-entdeckbarer Features
   - Target: `03 Planung/UI-Audit-Ergebnis-2026-05-XX.md` existiert mit allen 11 Seiten (Dashboard, Profile, Live-Call, Trainings, Coach-Dashboard, Admin-Bereich, Settings, Logs, Changelog, Performance, Onboarding) inventarisiert — pro Seite: was steht drauf, was ist klickbar, was passiert beim Klick, funktioniert der Klick. Plus Discoverability-Check und Tote-Buttons-Liste. Findings sortiert nach kritisch / mittel / kosmetisch.
   - Acceptance: Datei existiert, enthält alle 11 Seiten, Findings-Spalten vorhanden, Sortierung nach 3 Prioritätsstufen sichtbar

2. **Profil-Wizard reparieren**: POST `/profiles/wizard` schlägt aktuell mit 400 fehl.
   - Current: Frontend sendet JSON, Backend liest `request.form`; kein CSRF-Token; Feldnamen-Mismatch auf beiden Seiten
   - Target: 3-Schritte-Wizard durchklicken → POST `/profiles/wizard` gibt 200 zurück → Profil wird korrekt in DB angelegt mit den vom User eingegebenen Feldern; CSRF-Token wird mitgesendet; Frontend-Feldnamen und Backend-Erwartungen sind konsistent
   - Acceptance: Neues Profil über Wizard erstellen (als eingeloggter User) → Response-Status 200 → Profil erscheint in `/profiles`-Liste mit korrekten Daten

3. **Sessions im Dashboard klickbar**: Session-Rows im Dashboard führen nirgendwo hin.
   - Current: `db2-session-row`-Divs in `dashboard.html:729` ohne `onclick`/`href`; Klick lädt `/dashboard` neu
   - Target: Jede Session-Row erhält `onclick="location.href='/session/' + s.id"` und `style="cursor:pointer"` — analog zum `db2-reco-item`-Pattern in derselben Datei
   - Acceptance: Klick auf beliebige Session-Row → Browser navigiert zu `/session/<id>` (nicht zu `/dashboard`); Cursor-Pointer-Style sichtbar beim Hover

4. **PiP-Schließ-Bug fixen (Architekturentscheidung im Plan)**: PiP schließt sich bei App-Navigation.
   - Current: `window.documentPictureInPicture.requestWindow()` bindet PiP an Lebensdauer der Ursprungsseite; Navigation zu anderer App-Seite → PiP-Fenster schließt sich
   - Target: Architekturentscheidung (BroadcastChannel + localStorage State-Transfer, Service Worker, oder anderer Ansatz) wird im Plan-Phase mit Cross-AI bestimmt und implementiert; PiP überlebt Navigation innerhalb der NERVE-App
   - Acceptance: PiP offen → User klickt auf `/profiles`-Link in Navigation → PiP-Fenster bleibt offen und zeigt weiterhin Live-Call-State (UAT-Test aus 08.19.5-Round-2 reproduzierbar grün); ⚠ Genauer Fix-Ansatz durch Plan-Phase bestimmt — falls 🔴 komplex: Architekturentscheidung dokumentiert + Aufschub begründet zählt als erfüllt

5. **Nav-Label "Profil" → "Profile"**: Hauptnavigation zeigt deutschen Begriff statt englischem.
   - Current: `templates/base.html:56` — `<span class="n-nav-label">Profil</span>`
   - Target: `<span class="n-nav-label">Profile</span>`
   - Acceptance: Hauptnavigation zeigt "Profile" statt "Profil" auf jeder Seite wo base.html gerendert wird

6. **Wave-1-kritische Findings fixen**: Alles was Wave 1 als "kritisch" einstuft kommt in Wave 2.
   - Current: Unbekannt bis Wave 1 abgeschlossen; könnten weitere tote Flows oder Pre-Launch-Blocker vorhanden sein
   - Target: Alle Findings mit Priorität "kritisch" aus dem Audit-Bericht werden in Wave 2 gefixt oder — falls zu komplex für diese Phase — mit expliziter Begründung in eine eigene Phase überführt
   - Acceptance: Wave-1-Findings-Report "kritisch"-Spalte: jedes Item entweder mit Commit-Ref als gefixt markiert oder mit Link zur neuen Phase/Backlog-Eintrag verlinkt

## Boundaries

**In scope:**
- Wave 1: Inventur aller 11 Seiten + Discoverability-Check + Tote-Buttons-Check + Findings-Bericht
- Wave 2 fix 1: Profil-Wizard POST-Route (Frontend + Backend + CSRF)
- Wave 2 fix 2: Dashboard Session-Row onclick-Handler
- Wave 2 fix 3: PiP-Schließ-Bug (Architekturentscheidung + Implementation oder begründeter Aufschub)
- Wave 2 fix 4: Nav-Label "Profil" → "Profile" in base.html
- Wave 2 fix 5: Alle Wave-1-kritischen Findings
- Findings-Bericht als Foundation für Block O Teil 2 (Visual-Polish)

**Out of scope:**
- DSGVO-Härtung — das ist Phase 08.19.6 (kommt danach, "Dach-vor-Keller")
- Visual Polish / Redesign der Seiten — das ist Block O (Findings-Bericht ist der Input dafür, aber Umsetzung nicht in dieser Phase)
- Wave-1-mittel Findings — gehen ins Backlog, werden nicht in Wave 2 gefixt
- Block-J-Mini-Adds außer den 4 explizit genannten Bugs — kein Scope-Creep
- Neue Features oder UX-Improvements ohne Bezug zu den 4 Bugs
- Localhost-CSRF-Fix (eigener Block-J-Eintrag, separater Scope)
- Performance-Optimierungen

## Constraints

- **Wave-Reihenfolge fest**: Wave 1 (Audit) muss vollständig + Findings-Bericht committed sein bevor Wave 2 (Fixes) startet. Kein paralleler Start.
- **Wave-1→Wave-2-Overflow**: Nur "kritisch"-Findings fließen automatisch in Wave 2. "Mittel"-Findings → Backlog/nächste Phase. Kein dynamischer Scope.
- **PiP-Bug ist 🔴 offen**: Architekturentscheidung gehört in Plan-Phase + Cross-AI-Review (Gemini). Spec gibt keine Implementierungsmethode vor.
- **Cross-AI mit Gemini im Plan-Phase Pflicht**: Phase ist 🟡 mittel mit Multi-File-Edits (FE + BE gleichzeitig) — beide CLAUDE.md-Trigger-Bedingungen erfüllt.
- **Pruning-Notiz pro Wave Pflicht** im PLAN.md: was wird in Wave 1 nicht gemacht, was in Wave 2 nicht.
- **Stack-Constraint**: Flask + Vanilla JS bleibt — kein Framework-Wechsel für PiP-Fix.
