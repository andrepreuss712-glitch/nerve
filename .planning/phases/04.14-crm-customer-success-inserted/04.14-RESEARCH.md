## Summary

This phase adds an internal CRM dashboard to the existing Flask-Admin setup. The admin infrastructure from Phase 04.7 is fully in place and battle-tested: `SecureModelView`, `BaseView`, `@superadmin_required`, and the `get_session()` / try-finally DB pattern. Everything needed to deliver this phase exists in the codebase already.

The core work has three parts: (1) a new `CrmNote` DB table for free-text founder notes per user, (2) a `customer_success_service.py` that computes the four status badges from existing `ConversationLog` and `User.letzte_aktivitaet` data, and (3) a Flask-Admin `BaseView` that renders a single CRM overview page under `/admin/crm`.

With only ~50 Early-Access users, live computation of all status badges on every page load is fine — no caching needed. SQLite WAL is already active.

**Primary recommendation:** Add a new `BaseView` (not `ModelView`) for the CRM overview, following the `KpiDashboardView` pattern. Use a separate `CrmNote` table (not a `User` column) for notes, following the project's standard of dedicated tables for first-class domain concepts.

### Pattern 2: CrmNote as Separate Table (recommended over User column)

**What:** A dedicated `CrmNote` table keyed by `user_id`. One active note per user (upsert pattern), or a log of notes (append pattern).

**Why table over column:** The project consistently uses dedicated tables for domain concepts — `Feedback`, `AuditLog`, `LearningCard`, `CoachingReport`. Adding `crm_note` as a `Text` column on `User` would work but breaks this convention and makes future extension harder (e.g., adding `updated_at`, `note_type`).

**Recommended schema:**
```python
# Source: [ASSUMED] — follows project SQLAlchemy patterns from models.py
class CrmNote(Base):
    __tablename__ = 'crm_notes'
    id         = Column(Integer, primary_key=True)
    user_id    = Column(Integer, ForeignKey('users.id'), nullable=False, unique=True)
    notiz      = Column(Text, nullable=True)          # free-text founder note
    updated_at = Column(DateTime, default=utcnow, onupdate=utcnow)
    created_at = Column(DateTime, default=utcnow)
```

`unique=True` on `user_id` enforces one note per user — simple upsert via `REPLACE` or query-then-update.

### Pattern 3: Status Badge Logic in Dedicated Service

**What:** `customer_success_service.py` that computes status for all users in a single DB round-trip using aggregation, not one query per user.

**Why:** At 50 users, N+1 queries are tolerable but the aggregation approach is cleaner and already matches how `admin_dashboard.py` handles multi-table stats.

**Recommended implementation:**
```python
# Source: [ASSUMED] — follows SQLAlchemy subquery pattern from admin_dashboard.py
from datetime import datetime, timedelta
from sqlalchemy import func
from database.models import User, ConversationLog, CrmNote

def get_all_user_crm_data(db):
    """Returns list of dicts, one per non-superadmin user, with status badge."""
    now = datetime.utcnow()
    cutoff_7d  = now - timedelta(days=7)
    cutoff_14d = now - timedelta(days=14)

    # Aggregate calls per user for last 30 days
    call_counts = (
        db.query(
            ConversationLog.user_id,
            func.count(ConversationLog.id).label('total_calls'),
            func.max(ConversationLog.started_at).label('last_call'),
            func.avg(ConversationLog.kb_end).label('avg_kb'),
        )
        .filter(ConversationLog.started_at >= now - timedelta(days=30))
        .group_by(ConversationLog.user_id)
        .all()
    )
    call_map = {r.user_id: r for r in call_counts}

    users = db.query(User).filter(User.is_superadmin == False).all()
    notes = {n.user_id: n for n in db.query(CrmNote).all()}

    # Compute avg_calls for "Top" threshold
    avg_calls = (sum(r.total_calls for r in call_counts) / len(call_counts)
                 if call_counts else 0)

    result = []
    for u in users:
        c = call_map.get(u.id)
        note = notes.get(u.id)
        status = _compute_status(u, c, cutoff_7d, cutoff_14d, avg_calls)
        result.append({
            'user': u,
            'status': status,
            'last_call': c.last_call if c else None,
            'total_calls_30d': c.total_calls if c else 0,
            'avg_kb': round(c.avg_kb or 0) if c else 0,
            'notiz': note.notiz if note else '',
        })
    return result


def _compute_status(user, call_agg, cutoff_7d, cutoff_14d, avg_calls):
    """D-01/D-02 status badge logic. Returns 'aktiv'|'ruhig'|'churn'|'top'."""
    last_call = call_agg.last_call if call_agg else None
    last_login = user.letzte_aktivitaet

    # Top: above-average calls AND KB trending (use avg_kb > 60 as proxy)
    if call_agg and call_agg.total_calls > avg_calls and (call_agg.avg_kb or 0) > 60:
        return 'top'

    # Churn: 14 days no call AND no login
    login_stale = (not last_login) or (last_login < cutoff_14d)
    call_stale  = (not last_call)  or (last_call  < cutoff_14d)
    if login_stale and call_stale:
        return 'churn'

    # Ruhig: 7 days no call
    if (not last_call) or (last_call < cutoff_7d):
        return 'ruhig'

    return 'aktiv'
```

### Anti-Patterns to Avoid

- **N+1 queries per user for status:** Pre-aggregate in a single query group-by, not a loop of individual DB calls.
- **Adding `crm_note` column to `User` model:** The `User` model already has 30+ columns. Use a dedicated `CrmNote` table (see Pattern 2).
- **Storing transcript text in CRM notes:** DSGVO-Modus requires no verbatim transcripts. `crm_service.py` already enforces this — the CRM note display must only show the summarized `crm_notiz` from the service output, never raw transcript.
- **Skipping the `try-finally db.close()` pattern:** All DB access in this codebase uses `get_session()` + `try-finally`. No exceptions.

## Common Pitfalls

### Pitfall 1: `db_session` vs `get_session()` confusion
**What goes wrong:** Using `db_session` (scoped session) inside a `BaseView` instead of `get_session()`.
**Why it happens:** Both are exported from `database/db.py`. Flask-Admin's `ModelView` uses `db_session` (passed at construction). Custom `BaseView` route handlers must use `get_session()` (per-request session with manual close).
**How to avoid:** Follow the pattern in `KpiDashboardView` and `PlanningListView` — always `get_session()` + `try-finally` inside `@expose` methods.
**Warning signs:** `DetachedInstanceError` after template rendering, or session not closed causing SQLite lock warnings.

### Pitfall 2: `admin.add_view` endpoint collision
**What goes wrong:** Using an endpoint name that clashes with an existing view (e.g., `endpoint='crm'` conflicts if any blueprint uses the same).
**Why it happens:** Flask-Admin endpoints share the Flask URL namespace.
**How to avoid:** Use `endpoint='crm_view'` or similar unique name. Check existing `add_view` calls in `app.py` (lines 1292-1298) before choosing a name.

### Pitfall 3: `unique=True` on `CrmNote.user_id` causing IntegrityError on duplicate save
**What goes wrong:** A second AJAX save for the same user fails with a unique constraint violation instead of updating.
**Why it happens:** `INSERT` instead of upsert.
**How to avoid:** Query first (`db.query(CrmNote).filter_by(user_id=uid).first()`), update if exists, create if not. Standard pattern in this codebase — see `routes/profiles.py`.

### Pitfall 4: Status "Top" never triggers for new users
**What goes wrong:** Users with zero calls in the 30-day window are excluded from `call_map`, so `avg_calls` is computed over a subset that excludes them — but "Top" check happens after that.
**Why it happens:** `avg_calls` denominator only counts users who have calls. Inactive users skew the threshold down.
**How to avoid:** Base `avg_calls` only on users who have at least 1 call in the period (which is what the proposed aggregation does). Document this behavior — it is correct and intentional.

### Pitfall 5: DSGVO — never display raw transcript in CRM notes
**What goes wrong:** Displaying `ConversationLog.gegenargument_details` or `painpoints_details` (raw JSON) directly in the CRM view.
**Why it happens:** The fields exist and are tempting to display as "context".
**How to avoid:** Only display aggregated numeric metrics (KB score, call count, duration) and the sanitized `crm_notiz` from `crm_service.py`. Never raw transcript segments. This is a locked DSGVO requirement from CONTEXT.md.

### Follow-up hints generation (service function)
```python
# Source: [ASSUMED] — follows crm_service.py pattern and D-09/D-10 requirements
def get_followup_hints(users_crm):
    """Returns list of actionable hints for follow-up, sorted by urgency."""
    hints = []
    for u in users_crm:
        if u['status'] == 'churn':
            hints.append({
                'user_email': u['user'].email,
                'urgency': 'high',
                'reason': 'Kein Call und kein Login seit 14+ Tagen',
            })
        elif u['status'] == 'ruhig':
            hints.append({
                'user_email': u['user'].email,
                'urgency': 'medium',
                'reason': f"Kein Call seit 7+ Tagen (letzter: {u['last_call']})",
            })
    return sorted(hints, key=lambda h: h['urgency'] == 'high', reverse=True)
```
