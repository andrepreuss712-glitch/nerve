## Fix Assessment

### FIX-01 (WR-01): `_initTeleprompter()` — Pitch resolution + `hasPitch` guard

**Lines:** 2469-2481

**Correctness:** Correct. The pitch-resolution block (lines 2469-2472) only triggers when `inhalt` is empty AND `selectedSkriptId` is falsy AND `selectedPitchId` is set — the three conditions are all necessary and sufficient. The `hasPitch` guard added to the early-return condition at line 2481 (`!hasOpener && !hasErlaubnis && !hasPitch`) correctly prevents the "Kein Skript hinterlegt" early-return when a pitch is selected.

**Regression risk:** None. The fallback is strictly additive; existing skript-only and opener-only paths are unchanged.

**Remaining gap (Info):** See IN-01 below — the pitch resolution uses `state.openerItems` as the lookup array, which is correct because pitches are stored in `openerItems` alongside opener/erlaubnis entries. However, the condition guards `!state.selectedSkriptId` which means a user who has both a skript and a pitch selected will not get the pitch in the teleprompter (pitch is only shown when no skript is selected). This is the intended product behavior per the block-sequencing comment at line 2489, but it is worth confirming.

---

### FIX-02 (WR-02): `_wireInlineEdit()` — `activeTab === 'opener'` guard

**Line:** 1214

**Correctness:** Correct. `_wireInlineEdit` is called with `type='opener'` for all three non-skript tabs (opener, erlaubnis, pitch) as seen at lines 1126, 1128, 1130. Without the guard, a user editing the erlaubnis or pitch tab inline would incorrectly overwrite `state._editedOpenerText`, causing the wrong text to appear in the opener block of the teleprompter. The `state.activeTab === 'opener'` guard restricts the state write to the genuine opener tab only.

**Regression risk (Warning):** The fix silently discards the edited text when `activeTab` is `'erlaubnis'` or `'pitch'`. The "Fertig" button completes (preview updates, `_showSaveToProfileDialog` may fire), but the edited text is not stored in any state variable — there is no `_editedErlaubnisText` or `_editedPitchText`. If the user edits the erlaubnis text inline and clicks "Fertig", their edit shows in the preview for the current render, but `_initTeleprompter()` will read `state.selectedErlaubnisId` from `openerItems` (not the edited text) and show the original, unedited content. The guard prevents the wrong-state contamination bug (correct), but the erlaubnis/pitch inline-edit feature is now effectively a no-op for the session. See WR-01 below.

### FIX-03 (WR-03): `r.ok` checks on both `fetch('/api/precall/personalize/save')` chains

**Lines:** 669, 815

**Correctness:** Correct. Both `then(r => r.json())` handlers now have `if (!r.ok) throw new Error('HTTP ' + r.status)` before `r.json()`. This prevents the promise chain from attempting to parse a non-JSON HTML error page (e.g., Flask 500), which would previously yield an opaque JSON parse error in the catch handler, masking the real HTTP status.

**Regression risk:** None. The `throw` routes into the existing `.catch` handlers at lines 739-745 and 839-846 respectively, both of which correctly re-enable the button and show a sanitized error message. The error propagation path is complete.

**Symmetry check:** The nested profile-reload fetch at line 692 already had its own `r.ok` check (`if (!r.ok) throw new Error('profile load failed: ' + r.status)`) — this was pre-existing and correct. The two new guards bring the outer fetches into parity. No asymmetry remains.

## Warnings

### WR-01: Erlaubnis and pitch inline-edits are silently dropped (no state variable)

**File:** `static/pip-launcher.js:1214`
**Issue:** The WR-02 fix correctly prevents erlaubnis/pitch edits from contaminating `_editedOpenerText`, but the edited text is not stored anywhere. `_initTeleprompter()` reads `erlaubnisText` from `state.selectedErlaubnisId` via `openerItems` (line 2501-2505) and has no path to read an `_editedErlaubnisText`. Similarly, pitch has no edited-text state. The user sees their edit in the preview (`preview.textContent = newText` at line 1203 runs unconditionally) but the teleprompter will show the original persisted text.

This is a correctness gap: the "Bearbeiten" button gives visual feedback of a successful edit, but the edit does not survive into the call.

**Fix (minimal):** Add `_editedErlaubnisText` and `_editedPitchText` state variables and wire them:

```js
// In state initializer (near line 44 — other _edited* variables):
_editedErlaubnisText: null,
_editedPitchText: null,

// In _wireInlineEdit(), after line 1214:
if (type === 'opener' && state.activeTab === 'erlaubnis') state._editedErlaubnisText = newText;
if (type === 'opener' && state.activeTab === 'pitch')     state._editedPitchText     = newText;

// In _initTeleprompter(), replace the erlaubnisText block (lines 2500-2506) with:
var erlaubnisText = '';
if (state._editedErlaubnisText) {
  erlaubnisText = state._editedErlaubnisText;
} else if (state.selectedErlaubnisId && state.openerItems && state.openerItems.length > 0) {
  var selErl = state.openerItems.find(function (o) {
    return o.id === state.selectedErlaubnisId && o.type === 'erlaubnis';
  });
  if (selErl) erlaubnisText = selErl.inhalt || '';
}
// Analogous pattern needed for pitch if _editedPitchText is introduced.
```

**Severity:** Warning — the user-visible "Bearbeiten" flow appears to work but silently does not apply the edit to the teleprompter. No data loss (original persisted text is unchanged), but UX is misleading.

### IN-02: `hasPitch` flag is computed at line 2477 but pitch content was already resolved at line 2469-2472

**File:** `static/pip-launcher.js:2469-2481`
**Issue:** The `hasPitch` flag (line 2477) is declared after the pitch resolution block. The resolution (lines 2469-2472) can set `inhalt` from the pitch, so when the early-return guard evaluates `!hasPitch` (line 2481), `inhalt` is already non-empty and the `if (!inhalt || !inhalt.trim())` outer condition (line 2479) is false — meaning `hasPitch` in the guard is never actually reached when pitch content was successfully resolved. The `hasPitch` guard only matters when `state.selectedPitchId` is set but `selPitch.inhalt` is falsy/empty. This is a very narrow case, but it means the guard is partially redundant in the common case. No bug, but the logic reads as if `hasPitch` is needed more broadly than it is.

**Fix:** No change required. Optionally add a comment clarifying the guard only fires when pitch has no `inhalt`.
