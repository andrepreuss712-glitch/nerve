## Warnings

### WR-01: Pitch-only selection shows "Kein Skript hinterlegt" in teleprompter

**File:** `static/pip-launcher.js:2472-2477`

**Issue:** `_initTeleprompter()` resolves `inhalt` from `_editedSkriptText` or `selectedSkriptId` only (lines 2461–2466). `selectedPitchId` is never resolved here. The pitch pre-resolution that happens in `startCall()` via `state._resolvedTeleprompterSkript` is consumed and nulled out in `_openPipAndMic()` at line 1597–1599, *before* `_initTeleprompter()` is called at line 2024.

Consequence: if the user selects only a pitch (no opener, no erlaubnis, no skript), `inhalt` is empty, `hasOpener` is false, `hasErlaubnis` is false, and the guard at line 2474 fires the early-return with "Kein Skript hinterlegt" — even though pitch content exists.

**Fix:** Add pitch resolution in `_initTeleprompter()` after the existing skript block, mirroring the `startCall()` pattern:

```js
// After line 2466 — add pitch fallback:
if (!inhalt && !state.selectedSkriptId && state.selectedPitchId && state.openerItems) {
  var selPitch = state.openerItems.find(function (o) { return o.id === state.selectedPitchId; });
  if (selPitch && selPitch.inhalt) inhalt = selPitch.inhalt;
}
```

Also add `hasPitch` to the early-return guard:

```js
// Line 2470 — add:
var hasPitch = !!(state.selectedPitchId);

// Line 2474 — change to:
if (!hasOpener && !hasErlaubnis && !hasPitch) {
```

### WR-02: Erlaubnis inline-edit overwrites `_editedOpenerText` instead of a dedicated erlaubnis state

**File:** `static/pip-launcher.js:1125-1126` and `1213`

**Issue:** When `state.activeTab === 'erlaubnis'`, `_wireInlineEdit` is called with `type='opener'` (line 1126). Inside `_wireInlineEdit`, the "Fertig" path stores the edited text via `if (type === 'opener') state._editedOpenerText = newText` (line 1213). This means an inline-edit made on the erlaubnis tab writes into `state._editedOpenerText`.

`_initTeleprompter()` later reads `state._editedOpenerText` as the opener block (line 2485–2486). If the user edited the erlaubnis text inline, their erlaubnis edit ends up shown as the opener block, and the real opener is shown separately — producing wrong block ordering and content.

There is no `_editedErlaubnisText` variable anywhere in the codebase.

**Fix (minimal):** Pass `type='erlaubnis'` instead of `'opener'` for the erlaubnis tab wiring, add a dedicated state variable, and handle it in `_initTeleprompter`. Alternatively, suppress the "Bearbeiten" button in the erlaubnis tab until a dedicated `_editedErlaubnisText` path is implemented:

```js
// Line 1126 — temporary safe option: do not pass to _wireInlineEdit for erlaubnis
// (remove the Bearbeiten button in erlaubnis tabContentHtml or no-op the edit btn)
```

Minimum fix for correctness: in `_initTeleprompter`, add `_editedErlaubnisText` resolution analogous to `_editedOpenerText` and use it for `erlaubnisText`.

### WR-03: Outer fetch in `_savePersonalizedAndStartCall` does not check `r.ok` before parsing JSON

**File:** `static/pip-launcher.js:669`

**Issue:** The inner (second) fetch at line 691 correctly checks `if (!r.ok) throw new Error(...)`. The outer (first) fetch at line 669 calls `.then(function (r) { return r.json(); })` without checking `r.ok`. If the `/api/precall/personalize/save` endpoint returns a 4xx or 5xx with a non-JSON body (e.g., a Flask HTML error page on 500), `r.json()` rejects the promise, and the `.catch` at line 739 surfaces a generic JSON parse error to the user — masking the real HTTP error code.

**Fix:**
```js
// Line 669 — change to:
.then(function (r) {
  if (!r.ok) throw new Error('save failed: ' + r.status);
  return r.json();
})
```

### WR-04: `saveBtn` null-dereference in R-04 fallback `.catch` handler

**File:** `static/pip-launcher.js:731-736`

**Issue:** The `.catch` handler for the inner profile-reload fetch (line 731) references `saveBtn` from the outer function scope. `saveBtn` is fetched via `document.getElementById('lnr-step4c-save')` at the top of `_savePersonalizedAndStartCall` (line 648). If the DOM element is gone by the time the catch fires (e.g., user navigated away while the fetch was pending), accessing `saveBtn.disabled` would throw and prevent `renderStep5()` from running, leaving the UI in a broken state.

`saveBtn` is already guarded (`if (saveBtn)`) at line 708 and 721 in the success path, but at line 733 the guard is applied correctly. However, `saveBtnOrigText` (line 687) is set to `saveBtn ? saveBtn.textContent : ''` which is correct. The issue is that line 733 assumes `saveBtn` is still valid without a null-check in the catch:

```js
// Line 733 — current (no null-guard):
if (saveBtn) { saveBtn.disabled = false; saveBtn.textContent = saveBtnOrigText; }
```

Actually re-reading: line 733 does have `if (saveBtn)`. This is fine — the guard is present. Downgrade: this is not a bug. See Info section instead.

*(This warning is retracted — the null-guard is present at line 733.)*

### IN-01: Comment at `_initTeleprompter` line 2503 incorrectly claims pitch is resolved

**File:** `static/pip-launcher.js:2502-2503`

**Issue:** The comment reads:
```
// _editedSkriptText > selectedSkriptId > (Pitch wenn selectedSkriptId null: selectedPitchId)
```
This is inaccurate. Pitch resolution via `selectedPitchId` does NOT happen in `_initTeleprompter()`; it was resolved earlier in `startCall()` and consumed before `_initTeleprompter` runs (see WR-01). The comment creates a false sense of correctness that masks the actual pitch-only bug.

**Fix:** Update comment to accurately reflect what the function does, and implement the pitch fallback described in WR-01.
