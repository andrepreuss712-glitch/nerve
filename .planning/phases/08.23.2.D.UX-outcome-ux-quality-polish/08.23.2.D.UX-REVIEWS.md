# Cross-AI Plan Review: Phase 08.23.2.D.UX

---

## 1. Summary

The eight plans collectively form a coherent, well-sequenced feature set building on an existing production foundation. Wave ordering is mostly sound, security fixes are properly scoped, and the score-persistence architecture is solid. However, there are two **critical inconsistencies** that will cause runtime failures if not resolved before execution: (1) Plan 08 references a "5-button accordion" for pencil-edit while Plans 05/06 establish a 7-button grid — these must match; and (2) the assumption in Plan 02 that `coaching_score` already exists is unverified and could corrupt Plan 07's atomic write. Additionally, several frontend error paths are entirely unspecified. The plans are deployable after resolving these gaps, but should not proceed to execution blind.

---

## 2. Strengths

- **Wave sequencing is mostly correct.** Schema migrations (Wave 0+1) gate security fixes and UX changes cleanly. Plan 03 can run independently once migrations land.
- **Production-safe threading pattern in CR-02.** Passing `g.user.id` as an integer value rather than the `g.user` proxy object is exactly right for Flask background threads.
- **Atomic DB write in Plan 07.** Writing `outcome + coaching_score + score_breakdown + followup_intent` in a single transaction prevents partial state.
- **JSONB with SQLite fallback in Plan 02.** The `JSON().with_variant(JSONB(), 'postgresql')` pattern handles the dual-DB reality correctly.
- **Idempotency guard in Plan 06.** `dataset.outcomeRendered = '1'` prevents double-rendering on re-entry — a common PiP bug vector.
- **Few-shot expansion in Plan 04 is appropriately scoped.** Five DACH examples with a tie-breaking ranking rule directly addresses the known live bug (Termin→Kein Interesse misclassification).
- **Pre-execute audit in Plan 01.** Running `inspect.sh` before the migration on a production-direct deploy is good practice.

---

## 3. Concerns

### HIGH

- **Plan 08 / Plan 05+06 button count mismatch.** Plan 05 specifies a 7-button grid (adds `send_info`, `gatekeeper_blocked`, `contract_signed` over the original 5). Plan 08 still says "5-button accordion" for the dashboard pencil-edit. If Plan 08 deploys with 5 buttons, users can set `send_info` or `gatekeeper_blocked` via PiP but cannot correct to those values from the dashboard. This is a functional regression.

- **coaching_score "already exists" is an unverified assumption.** Plan 02 explicitly skips adding `coaching_score` with this justification. If it was added in Phase 08.23.2.D under a different name or migration, or if that migration was partial, Plan 07's atomic write will fail with a column-not-found error at runtime. This needs a `SELECT column_name FROM information_schema.columns` verification step before Plan 02 executes, not just a comment.

- **SQLite CHECK constraint modification.** Plan 01 extends the `calls.outcome` CHECK constraint from 6 to 8 values. SQLite does not support `ALTER TABLE ... MODIFY CONSTRAINT` — Alembic handles this by dropping and recreating the table (batch_alter_table). On a production database with real data, this is a full table copy operation. If the table is large, this could lock production for minutes. The plan needs an explicit note on table size and whether a maintenance window is required.

### MEDIUM

- **No error/timeout state for score calculation in Plan 05/06.** The UX spec says: spinner → score appears. What happens if the `/correct_outcome` POST times out, returns a 500, or the score calculation throws? The spinner will hang indefinitely. A timeout (e.g., 8s) with a fallback message is missing from both plans.

- **followup_intent auto-derivation logic is unspecified in Plan 06.** Plan 06 says "POST body: `{ outcome, followup_intent }` (followup_intent auto-derived from outcome choice)" but the derivation mapping is not defined as a JS constant. Plan 01 adds the DB column but the frontend↔backend mapping could drift. Should be defined once and referenced in both Plan 06 (JS) and Plan 07 (Python).

- **CSRF meta tag existence not guaranteed in Plan 03 CR-01.** The fix pattern uses `document.querySelector('meta[name="csrf-token"]').getAttribute('content')`. If the meta tag is absent, this throws `TypeError: Cannot read properties of null`. The "must check/add csrf-token meta tag" note is not formalized as a required pre-condition with a verification step.

- **Token estimation in Plan 04 is coarse for German.** `word_count * 1.4` works for English but German compounds inflate token counts (e.g., "Gesprächspartner" = 1 word but 5-7 tokens). A 2000-token threshold computed this way may pass transcripts that actually run 2500-3000 tokens. Consider `len(text.split()) * 1.6` for German or use a conservative 1400-word ceiling.

- **Score formula backward compatibility.** Plan 07 introduces a new 5-component formula. Existing rows have `coaching_score` computed by old `_calcScore()`. Dashboard will show mixed scores (old vs. new formula) with no visual distinction. The `score_schema_version` column exists for this purpose, but dashboard rendering for version=NULL/0 rows is not addressed in Plan 08.

### LOW

- **`frage_qualitaet=0` placeholder compresses score range.** With one of five components hardcoded to 0, effective formula is 4-component, capping process_score at ~90 before the outcome multiplier. Scores set now won't be comparable to post-v2 scores. Document expected v1 score range explicitly.

- **`outcome_source` mapping labels "A" and "B" are opaque in Plan 05.** "confirmed A → ai_auto, confirmed B → ai_auto_unsicher" — A and B are not defined in the plan. Presumably A = confidence ≥ 0.70 and B = 0.70–0.89, but this should be explicit since the backend endpoint must implement the same logic.

- **`contract_signed` in Plan 05's button grid may not be in Plan 01's new constraint values.** Plan 01 adds `send_info` and `gatekeeper_blocked` to the existing constraint. If `contract_signed` was not already in the original 6 values, it won't be in the 8-value constraint, and inserting it will raise a CHECK constraint violation.

- **Wave labeling inconsistency in plan headers.** Plans 01-02 are both labeled "Wave 1" in their headers but the phase description calls them "Wave 0" and "Wave 1". Creates ambiguity about execution order when reading plan headers alone.

---

## 4. Suggestions

- **Plan 08:** Update accordion to 7 buttons, matching Plans 05/06. The `correct_outcome` endpoint already needs to handle all 7 values after Plan 01 migration.
- **Plan 02:** Add a pre-flight check task: `SELECT coaching_score FROM calls LIMIT 1` via SSH before executing migration 0007. If column missing, add it; if present, skip.
- **Plan 06:** Define the `outcome → followup_intent` mapping as a JS constant object and document it in the plan so Plan 07's backend can mirror it exactly.
- **Plan 03 CR-01:** Make "verify csrf-token meta tag exists in dashboard.html head" a named sub-task with a grep check, not a parenthetical note.
- **Plan 05:** Add an explicit error state to the score reveal flow: if POST fails or times out, show an inline error with a retry button rather than leaving the spinner running.
- **Plan 04:** Use German-adjusted multiplier (1.6 instead of 1.4) or a conservative 1400-word ceiling for the token threshold.
- **Plan 01:** Add an estimated row count check (`SELECT COUNT(*) FROM calls`) to the pre-execute audit so the migration time can be anticipated before the table rebuild begins.

---

## 5. Risk Assessment

**Overall: MEDIUM**

The plans are production-deployable after resolving the two HIGH concerns (Plan 08 button count and coaching_score column verification). The security fixes in Plan 03 are clean and low-risk. The largest operational risk is Plan 01's CHECK constraint migration on a potentially large production table — needs explicit size awareness before execution. All other concerns are either straightforward fixes or documentation gaps. The phase is well-scoped and does not show signs of over-engineering.
