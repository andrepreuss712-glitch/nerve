## Implementation Decisions

### Wave 2 — Klassifikations-Tuning

- **D-W2-01:** 7 Outcome-Klassen für Haiku-Klassifikation: `meeting_booked`, `callback`, `send_info`, `wrong_person`, `gatekeeper_blocked`, `no_interest`, `contract_signed`.
- **D-W2-02:** 5 Few-Shot-Beispiele (DACH-Snippets, 1-3 Sätze) für die häufigsten Klassen:
  1. `meeting_booked`: "Ja, das klingt interessant. Montag um 10 hätte ich Zeit."
  2. `no_interest`: "Nein danke, das ist nichts für uns. Bitte rufen Sie nicht wieder an."
  3. `callback`: "Schicken Sie mir die Unterlagen, ich melde mich nächste Woche." (ohne festen Termin)
  4. `wrong_person`: "Das macht bei uns die Frau Müller in der Geschäftsführung. Ich gebe Ihnen mal die Durchwahl."
  5. `gatekeeper_blocked`: "Frau Schmidt ist heute nicht zu sprechen. Versuchen Sie es nächste Woche." (Sekretärin, kein Durchstellen)
  - `send_info` und `contract_signed`: nur Text-Definition im System-Prompt, kein eigenes Few-Shot-Beispiel.
- **D-W2-03:** Snippet-Auswahl für Haiku-Input UMSTELLEN (Pflicht — "längste Aussagen"-Logik zerstörte Termin-Live-Test 2026-05-27):
  - **(a) Wenn Transkript < 2000 Tokens** → vollständiges Transkript übergeben
  - **(b) Wenn ≥ 2000 Tokens** → erste 30s + letzte 60s als Fallback
  - Alte "Top-3 längste Aussagen"-Logik komplett entfernen.
- **D-W2-04:** Rangfolge-Anweisung im Prompt: "Termin > Rückruf > Kein Interesse bei Überlappung" (aus SPEC REQ-7).

### Wave 3 — Outcome-Pflicht-Schritt UX

- **D-W3-01:** 7 Outcome-Typen in DB und UI:
  | DB-Wert | UI-Label |
  |---|---|
  | `meeting_booked` | Termin gebucht |
  | `callback` | Rückruf vereinbart |
  | `send_info` | Infos zusenden |
  | `wrong_person` | Falsche Person |
  | `gatekeeper_blocked` | Gatekeeper blockt |
  | `no_interest` | Kein Interesse |
  | `contract_signed` | Abschluss |
  - Alembic-Migration: CHECK-Constraint auf `calls.outcome` um `send_info` + `gatekeeper_blocked` erweitern.

- **D-W3-02:** `followup_intent`-Spalte auf `calls`-Tabelle (NEU):
  - Typ: Enum(`none`, `callback`, `meeting`, `send_info`, `retry_internal`)
  - Default: `'none'`
  - Alembic-Migration mit Altdaten-Update → alle bestehenden Calls bekommen `followup_intent='none'`
  - Ableitung bei Outcome-Wahl:
    - `meeting_booked` → `meeting`
    - `callback` → `callback`
    - `send_info` → `send_info`
    - `gatekeeper_blocked` → `retry_internal`
    - alle anderen (`wrong_person`, `no_interest`, `contract_signed`) → `none`
  - DSGVO-Rechtsgrundlage: Art. 6 Abs. 1f (berechtigtes Interesse B2B-Sales-Follow-up) — in DSGVO-Analyse-Dokument ergänzen
  - **Pflicht-Vorab-Check vor Plan-Phase:** `workspace_id`-Spalte auf `calls`-Tabelle prüfen via `inspect.sh schema calls`. Wenn nicht vorhanden → Mini-Phase davor (D-W3-02-Blocker).

- **D-W3-03:** Vereinheitlichte 7-Button-UI (SPEC 3-States A/B/C komplett wegfallen lassen):
  - **PiP-Flow:**
    1. User klickt Beenden
    2. Spinner "Ergebnis wird erkannt..." (1-2s, während postcall_analysis + Haiku klassifiziert)
    3. 7 Buttons erscheinen — immer alle sichtbar
    4. **Bei Confidence ≥ 0.70:** Haiku-Vorschlag leuchtet teal (pre-selected), Bestätigen-Button direkt klickbar
    5. **Bei Confidence < 0.70:** KEINE Vorauswahl, Unsicher-Badge "KI unsicher — bitte wählen" (Teal-Outline, kein Gelb — CLAUDE.md HART Punkt 8), Bestätigen-Button ausgegraut bis User aktiv wählt
    6. User klickt anderen Button → altes teal-Highlight geht aus, neues geht an, Bestätigen bleibt klickbar
    7. Klick Bestätigen → Spinner "Bewertung wird berechnet..." (während `correct_outcome`-POST läuft, 200-500ms)
    8. Score erscheint (`nlp-section-postcall` wird `display:block`)
    9. Outcome-Sektion schrumpft zu 1-Zeiler: `[Icon] Termin gebucht ✓`
  - Bestätigen-Button: optisch immer gleich, egal welcher Outcome aktiv ist

- **D-W3-04:** Score bleibt hidden bis Outcome-Confirm (`nlp-section-postcall` initial `display:none` nach `outcome_ready`-Event).

- **D-W3-05:** Auto-Confirm-Countdown (30s) entfällt komplett.

- **D-W3-06:** `outcome_source`-Mapping:
  - Haiku-Vorschlag bestätigt (≥ 0.70) → `ai_auto`
  - Haiku-Vorschlag bestätigt (< 0.70, aber Unsicher-Badge weg-geklickt) → `ai_auto_unsicher`
  - Anderer Button gewählt als Haiku-Vorschlag → `user_corrected`
  - Unsicher-State (<0.70) + User wählt irgendwas → `user_corrected`

- **D-W3-07:** `correct_outcome`-POST-Body: `{ outcome, followup_intent }` (followup_intent automatisch abgeleitet aus Outcome-Wahl im Frontend, mitgeschickt im Body).

### Wave 4 — Score-Persistierung + Modifier

- **D-W4-01:** Score-Modifier finale Liste (erste Schätzung, empirische Kalibrierung in Phase E):
  | Outcome | Modifier |
  |---|---|
  | `contract_signed` | 1.15 |
  | `meeting_booked` | 1.10 |
  | `wrong_person` | 1.00 |
  | `callback` | 0.95 |
  | `send_info` | 0.95 |
  | `gatekeeper_blocked` | 0.95 |
  | `no_interest` | 0.85 |

- **D-W4-02:** `correct_outcome`-Endpoint-Response-Format:
  ```json
  { "ok": true, "coaching_score": <float>, "final_score": <int>, "outcome": "<enum>", "followup_intent": "<enum>" }
  ```
  Frontend rendert `final_score` direkt — kein lokales `_calcScore()` für Re-Render nach Outcome-Confirm.

- **D-W4-03:** `postcall_analysis` berechnet KEINEN Score — nur Lernkarten (Sonnet) + Haiku-Vorschlag (für UI-Vorauswahl). Score-Berechnung ausschließlich in `correct_outcome` (atomar: UPDATE outcome + UPDATE coaching_score in einem Transaction).

- **D-W4-04:** Score-Formel (aus SPEC, REQ-11):
  - `process_score = kb_end×0.30 + behandelt_rate×0.30 + redeanteil_score×0.20 + skript×0.10 + frage_qualitaet×0.10` (frage_qualitaet = 0 in v1)
  - `final_score = clamp(round(process_score × outcome_modifier), 0, 100)`
  - HINWEIS: Das ist eine Formel-Änderung gegenüber altem `_calcScore()` (war: kb×0.40 + behandelt×0.30 + redeanteil×0.20 + skript×0.10).

- **D-W4-05:** `correct_outcome`-Endpoint im Dashboard (Pencil-Edit): gleiches Response-Format wie D-W4-02. Frontend re-rendert Score-Label in der Calls-Zeile ohne Reload.
