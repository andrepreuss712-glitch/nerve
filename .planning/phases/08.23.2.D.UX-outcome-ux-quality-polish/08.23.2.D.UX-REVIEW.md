The overall implementation is solid. Migrations are correct and reversible. The ownership filter on `correct_outcome` is present. CSRF tokens are threaded through all POST calls. XSS paths use `escHtml()` consistently. The coaching score formula is deterministic and well-tested.

Four warnings are worth addressing before EA launch. ## Warnings

### WR-01: `_select_snippets` — duplicate entries when `dauer_sek=0` and `ts_ms` is present

**File:** `services/outcome_service.py:68-78`

**Issue:** When `dauer_sek=0` (which happens for calls where duration tracking failed — see `app_routes.py:219` comment "approximation") and `log_entries` contain `ts_ms`, the "late" slice uses:

```python
late = [e.get('text', '') for e in log_entries
        if e.get('ts_ms', 0) >= (dauer_sek - 60) * 1000 and e.get('text')]
```

With `dauer_sek=0`, `(0 - 60) * 1000 = -60000`. Every entry whose `ts_ms >= -60000` — that is, every entry — enters the `late` list. Combined with the unconditional `early` list (entries with `ts_ms <= 30_000`), the returned list is `early + all_entries`, causing most of the transcript to appear twice in the Haiku prompt. This inflates token usage and may push the prompt past the `max_tokens=80` response limit indirectly (by making the user message very large).

**Fix:** Guard the late slice against negative thresholds:

```python
late_threshold_ms = max(0, (dauer_sek - 60) * 1000)
late = [e.get('text', '') for e in log_entries
        if e.get('ts_ms', 0) >= late_threshold_ms and e.get('text')]
```

### WR-02: `correct_outcome` — `outcome_note` silently becomes NULL on anonymization exception

**File:** `routes/app_routes.py:1790-1792`

**Issue:** When `anonymize()` raises an exception, the handler catches it, prints a log line, and sets `row.outcome_note = None`. The HTTP response still returns `{'ok': True, ...}` — the frontend sees success but the note the user typed is silently discarded. The user has no way to know the note was not saved.

```python
except Exception as _e_anon:
    print(f'[Phase08.23.2.D] outcome_note anonymize Fehler: {_e_anon}')
    row.outcome_note = None  # fail-safe
```

This is a data-loss risk from the user's perspective: they confirm their note and see "Bestätigt", but the note is gone.

**Fix:** Either return a warning in the response payload so the frontend can show a toast, or — preferably — bubble the anonymization error upward and return a `{'ok': False, 'error': 'note_anon_failed'}` response that lets the frontend prompt the user to try again without the note:

```python
except Exception as _e_anon:
    print(f'[Phase08.23.2.D] outcome_note anonymize Fehler: {_e_anon}')
    row.outcome_note = None
    # Signal to caller that note was dropped
    anon_note_failed = True
```

Then include `'note_dropped': True` in the success response body.

### WR-03: Dashboard accordion — `outcome_source` not set to `user_corrected` in `correct_outcome` body

**File:** `templates/dashboard.html:888-889` and `templates/dashboard.html:970-971`

**Issue:** Both the unsicher-dot inline correction handler and the pencil-edit accordion send:

```js
body: JSON.stringify({ outcome: pair[0], followup_intent: followupIntent }),
```

Neither passes `outcome_source`. The backend (`api_calls_correct_outcome`, line 1780) defaults to `'user_corrected'` when `client_outcome_source` is not in `_VALID_SOURCES`. This is the correct fallback, so no DB integrity problem exists.

However the `unsicher-dot` is only rendered for `outcome_source === 'ai_auto_unsicher'` rows (line 825-827). After the inline correction successfully updates the outcome, the `unsicher-dot` element is re-appended to the span (line 896-900) — meaning the yellow unsicher indicator stays visible even though the outcome is now `user_corrected`. The indicator disappears only on page reload.

**Fix:** Remove the dot element after a successful correction instead of re-appending it:

```js
// After successful json.ok:
if (dot && dot.parentNode) dot.parentNode.removeChild(dot);
if (pencil) outcomeSpan.appendChild(pencil);
```

The same applies to the pencil accordion handler at lines 978-981.

### WR-04: `api_calls_latest_outcome` — no ordering when `call_id_param` is provided

**File:** `routes/app_routes.py:1720-1725`

**Issue:** When `call_id_param` is provided the query is:

```python
q = db_lo.query(Call).filter(Call.user_id == g.user.id)
q = q.filter(Call.id == call_id_param)
row = q.first()
```

The `.first()` without an `ORDER BY` is fine for UUID primary-key lookups — the filter on `Call.id == call_id_param` is deterministic. However the code path without `call_id_param` uses:

```python
q = q.order_by(Call.started_at.desc())
row = q.first()
```

`started_at` is nullable (`nullable=True` in models.py:657). If the most recent call was created with `started_at=NULL` (which is possible — the field is optional), the ordering places NULLs last in PostgreSQL (default `NULLS LAST` for DESC). That is probably acceptable, but it means a call created by `create_call_for_sid()` before `started_at` is set could be skipped in favor of an older call. This is a latent inconsistency rather than a current bug, but worth noting.

**Fix:** Add a secondary sort on `Call.created_at` which is always non-null:

```python
q = q.order_by(Call.started_at.desc().nullslast(), Call.created_at.desc())
```

### IN-01: `SYSTEM_PROMPT` lists 7 outcome categories but `VALID_OUTCOMES` has 8 (includes `unknown`)

**File:** `services/outcome_service.py:82-119`

**Issue:** `SYSTEM_PROMPT` instructs Claude to classify into exactly one of 7 categories (does not include `unknown`). However `VALID_OUTCOMES` has 8 entries including `unknown`. Claude will never return `"outcome": "unknown"` based on the prompt — it is only ever set by the Python fallback paths. This asymmetry is intentional and noted implicitly in the code, but it means the `test_valid_outcomes_has_8_values` test is testing an implementation detail rather than a prompt-driven behavior. A comment explaining this asymmetry would prevent confusion.

**Fix:** Add a comment above `VALID_OUTCOMES`:

```python
# 'unknown' is NOT in the SYSTEM_PROMPT instruction set — it is only returned
# by fallback paths (short call, Claude exception, malformed JSON, out-of-enum).
# Claude is instructed to classify into 7 categories; the 8th is injected by Python.
VALID_OUTCOMES = frozenset({...})
```

frage_qualitaet = 0.0  # v1 placeholder — always 0; schema_version=2 will compute from transcript

### IN-03: `test_system_prompt_contains_examples` — borderline source-presence test

**File:** `tests/test_outcome_service.py:170-177`

**Issue:** The test checks that `SYSTEM_PROMPT` is a non-empty string containing `'<examples>'`, `'meeting_booked'`, and `'gatekeeper_blocked'`. Per CLAUDE.md's Test-Qualitaets-Regel, this is a source-presence-style test (checking that a constant string contains substrings). It would pass even if `SYSTEM_PROMPT` is dead code never passed to Claude.

The comment in the test (`# Runtime behavior check: SYSTEM_PROMPT is a non-empty string with XML examples block`) tries to justify it, but the justification is weak — the actual runtime behavior (that Haiku is called with this system prompt) is tested by `test_classify_returns_valid_outcome` which already mocks the call. This test adds no additional runtime assurance.

**Fix:** Remove the test or convert it to verify that `classify()` actually passes `SYSTEM_PROMPT` as the `system=` argument by asserting on the `mock_client.messages.create.call_args`:

```python
def test_classify_uses_system_prompt(valid_conv_data, mock_haiku_response_meeting):
    from services import outcome_service
    with patch.object(outcome_service, 'claude_client') as mock_client:
        mock_client.messages.create.return_value = mock_haiku_response_meeting
        outcome_service.classify(valid_conv_data)
    call_kwargs = mock_client.messages.create.call_args[1]
    assert call_kwargs.get('system') == outcome_service.SYSTEM_PROMPT
    assert 'gatekeeper_blocked' in call_kwargs.get('system', '')
```

### IN-04: `pip-launcher.js` — `_renderOutcomeUx` idempotency guard prevents re-render after reconnect

**File:** `static/pip-launcher.js:3666-3667`

**Issue:** The idempotency guard:

```js
if (sec.dataset.outcomeRendered === '1') return;
sec.dataset.outcomeRendered = '1';
```

prevents re-rendering when `_renderOutcomeUx` is called a second time (e.g., after a SocketIO reconnect that re-emits `outcome_ready`). If the first render populated the section with a spinner state and the connection dropped, the user sees a permanently stuck spinner on reconnect. The `api/calls/latest_outcome` fallback-pull (D-04e) also calls `_renderOutcomeUx` on success (line 2479/2956), which would silently no-op if the section was already marked rendered.

This is a known tradeoff for idempotency, but worth flagging since the guard prevents recovery from network-interrupted states.

**Fix:** Consider resetting the guard when the section is in an error/spinner state:

```js
var alreadyRendered = sec.dataset.outcomeRendered === '1';
var isStuck = alreadyRendered && sec.querySelector('.pip-outcome-confirm-btn[disabled]');
if (alreadyRendered && !isStuck) return;
sec.dataset.outcomeRendered = '1';
```
