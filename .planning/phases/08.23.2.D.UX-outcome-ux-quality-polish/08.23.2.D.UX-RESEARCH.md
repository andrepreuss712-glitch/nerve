## Topic 1: Anthropic SDK Token Counting for 2000-Token Threshold

### Verdict: Use word-count heuristic. Skip `count_tokens()` in the hot path.

### The API Exists and Works [VERIFIED: platform.claude.com/docs/en/docs/build-with-claude/token-counting]

The Python SDK has `client.messages.count_tokens()`. Call signature:

```python
response = claude_client.messages.count_tokens(
    model=_HAIKU_MODEL,
    system="<your system prompt>",
    messages=[{"role": "user", "content": transcript_text}],
)
token_count = response.input_tokens  # int
```

- Returns `{"input_tokens": <int>}` — no inference, no LLM response generated
- **Free to use** (not billed), but subject to its own RPM rate limit (100 RPM at Tier 1, separate from messages RPM)
- Result is an **estimate** — may differ slightly from actual tokens used in the real call
- Available on all current Claude models including Haiku

### Why NOT to use `count_tokens()` in this hot path

The classify path runs once per call-end, immediately before or after `postcall_analysis`. Adding a second HTTP round-trip (count_tokens → then classify) doubles the network latency for what is effectively a pre-flight check. Given the threshold is coarse (2000 tokens), a word-count heuristic is accurate enough and adds zero latency.

### Recommended: Word-Count Heuristic [ASSUMED: calibration for German text]

German text tokenizes at roughly **1 word ≈ 1.3–1.5 tokens** due to compound nouns and longer words. Conservative threshold to avoid false negatives (incorrectly routing a 1900-token transcript to the snippet path):

```python
def _estimate_tokens(text: str) -> int:
    """Conservative token estimate for German transcript text.
    German compound nouns tokenize heavier than English: ~1.4 tokens/word.
    Adds 20% buffer so we never mistakenly skip full-transcript path."""
    return int(len(text.split()) * 1.4)

def _select_snippets(log_entries: list, dauer_sek: int) -> list:
    """D.UX-W2-03: Full transcript if < 2000 tokens, else first 30s + last 60s."""
    texts = [e.get('text', '') for e in log_entries if e.get('text')]
    if not texts:
        return []

    full_text = ' '.join(texts)

    # Token estimate: 1 word ≈ 1.4 tokens for German
    if _estimate_tokens(full_text) < 2000:
        return texts  # full transcript as list of segments

    # Fallback: first 30s + last 60s by timestamp
    early = [e.get('text', '') for e in log_entries
             if e.get('ts_ms', 0) <= 30_000 and e.get('text')]
    late  = [e.get('text', '') for e in log_entries
             if e.get('ts_ms', 0) >= (dauer_sek - 60) * 1000 and e.get('text')]
    return early + late
```

### Planner Decision Point

The CONTEXT.md marks "Exakte Breakpoints für < 2000 Tokens" as Claude's Discretion. **Recommendation: use word-count heuristic.** If a transcript has exactly 1980 tokens and the heuristic says 1850 (false negative → passes full text), the worst case is Haiku receiving a slightly longer input — acceptable. The reverse (incorrectly truncating a short call) would be worse.

Word threshold to use: `len(text.split()) * 1.4 < 2000` → `len(text.split()) < 1429` words.

### What the Planner Needs

- Implementation goes in `_select_snippets()` in `outcome_service.py` — replace the entire function
- Old "Top-3 longest" logic is removed completely (D-W2-03 mandate)
- `log_entries` must include `ts_ms` field for the fallback path — verify this in the route that calls `classify()`
- No new import or dependency needed

## Topic 2: Few-Shot Prompting Structure for German 7-Class Classification

### Verdict: Examples in system prompt, XML `<examples>` tags, system+user message split.

### Official Anthropic Guidance on Few-Shot Examples [VERIFIED: platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices]

- **3–5 examples** give best results
- Wrap examples in `<example>` tags, multiple examples in `<examples>` tags
- Examples distinguish instructions from demonstrations — Claude parses tagged content more reliably
- Positive examples (showing correct behavior) are more effective than negative ones
- XML tags reduce misinterpretation when prompt mixes instructions, context, examples, and variable input

### Placement: System Prompt vs User Message

**Use system prompt for:** class definitions, ranking instructions, output format, few-shot examples.
**Use user message for:** the actual transcript input only.

Rationale: The system prompt is static across all classify() calls — it can be cached by Anthropic's prompt caching if needed later. The user message varies per call. Mixing examples into the user message makes the structure harder to parse and prevents future prompt caching.

### Confidence Score Caveat [ASSUMED: based on Claude behavior, not official docs]

Claude does NOT natively output probability distributions. When asked for `confidence: float`, it produces a **calibrated self-assessment**, not a statistical probability. This means:
- Scores cluster around 0.7–0.9 for clear cases
- Scores rarely go below 0.4 (Claude is reluctant to express very low confidence)
- The 0.65 ceiling for `< 20 words` input must be enforced in Python (post-processing), not relied on from Claude — Claude will NOT naturally respect it
- The 0.70 threshold for ai_auto vs ai_auto_unsicher is a business rule applied to Claude's output, not a calibrated statistical threshold

### Recommended Prompt Structure


## Topic 3: Alembic CHECK Constraint DROP+ADD — Patterns from NERVE Codebase

### Verdict: Established pattern exists in migration 0004. Reuse it exactly.

### Pattern Found in Migration 0004 [VERIFIED: codebase grep, file 0004_add_mode_events_to_call_events.py]

Migration 0004 is the canonical NERVE pattern for extending a CHECK constraint. It handles both PostgreSQL and SQLite:

```python
_NEW_CONSTRAINT = (
    "event_type IN ("
    "'transcript_chunk', 'suggestion_shown', 'reaction', 'phase_change', "
    "'audio_health', 'objection_detected', 'consent_optin', "
    "'mode_switch', 'mode_initial'"   # <-- added values
    ")"
)

_OLD_CONSTRAINT = (
    "event_type IN ("
    "'transcript_chunk', 'suggestion_shown', 'reaction', 'phase_change', "
    "'audio_health', 'objection_detected', 'consent_optin'"
    ")"
)

_CONSTRAINT_NAME = 'ck_call_events_event_type'

def upgrade() -> None:
    with op.batch_alter_table('call_events') as batch_op:
        batch_op.drop_constraint(_CONSTRAINT_NAME, type_='check')
        batch_op.create_check_constraint(_CONSTRAINT_NAME, _NEW_CONSTRAINT)

def downgrade() -> None:
    with op.batch_alter_table('call_events') as batch_op:
        batch_op.drop_constraint(_CONSTRAINT_NAME, type_='check')
        batch_op.create_check_constraint(_CONSTRAINT_NAME, _OLD_CONSTRAINT)
```

**How it works on each dialect:**
- **PostgreSQL:** `batch_alter_table` with `render_as_batch=True` (confirmed in `alembic/env.py`) emits `ALTER TABLE DROP CONSTRAINT` + `ALTER TABLE ADD CONSTRAINT` — the only valid way to change a CHECK in Postgres
- **SQLite:** `batch_alter_table` does CREATE+COPY+DROP internally, rebuilding the table with the new constraint definition

`render_as_batch=True` is set globally in `alembic/env.py` for BOTH offline and online modes — so all `batch_alter_table` calls get this behavior automatically.

```python
_CK_OUTCOME = 'ck_calls_outcome'

_NEW_OUTCOME_CONSTRAINT = (
    "outcome IN ('meeting_booked', 'callback', 'send_info', 'wrong_person', "
    "'gatekeeper_blocked', 'no_interest', 'contract_signed', 'unknown') OR outcome IS NULL"
)
_OLD_OUTCOME_CONSTRAINT = (
    "outcome IN ('meeting_booked', 'callback', 'no_interest', 'wrong_person', "
    "'contract_signed', 'unknown') OR outcome IS NULL"
)

_CK_FOLLOWUP = 'ck_calls_followup_intent'
_FOLLOWUP_CONSTRAINT = (
    "followup_intent IN ('none', 'callback', 'meeting', 'send_info', 'retry_internal')"
)

def upgrade() -> None:
    with op.batch_alter_table('calls') as batch_op:
        # 1. Extend outcome CHECK
        batch_op.drop_constraint(_CK_OUTCOME, type_='check')
        batch_op.create_check_constraint(_CK_OUTCOME, _NEW_OUTCOME_CONSTRAINT)
        # 2. Add followup_intent column
        batch_op.add_column(
            sa.Column('followup_intent', sa.Text(), nullable=False,
                      server_default='none')
        )
        batch_op.create_check_constraint(_CK_FOLLOWUP, _FOLLOWUP_CONSTRAINT)

def downgrade() -> None:
    with op.batch_alter_table('calls') as batch_op:
        # Revert followup_intent
        batch_op.drop_constraint(_CK_FOLLOWUP, type_='check')
        batch_op.drop_column('followup_intent')
        # Revert outcome CHECK to 6 values
        batch_op.drop_constraint(_CK_OUTCOME, type_='check')
        batch_op.create_check_constraint(_CK_OUTCOME, _OLD_OUTCOME_CONSTRAINT)
```

### Idempotency

`batch_alter_table` with `render_as_batch=True` is **not inherently idempotent** — running twice will fail on Postgres because:
- `DROP CONSTRAINT` fails if constraint does not exist
- `ADD COLUMN` fails if column already exists

Standard NERVE approach (from 0005 comments) is raw-SQL fallback for SQLite downgrade edge cases. For the upgrade path, idempotency is achieved at the deployment level: `alembic upgrade head` is only run once per deployment, tracked in `alembic_version` table. No additional guard needed per NERVE conventions.

If explicit idempotency is required (re-runnable upgrade), wrap in try/except:
```python
from sqlalchemy.exc import ProgrammingError
try:
    with op.batch_alter_table('calls') as batch_op:
        batch_op.drop_constraint(_CK_OUTCOME, type_='check')
except Exception:
    pass  # Already dropped / doesn't exist
```
— but this is NOT done in existing NERVE migrations and NOT recommended unless explicitly required.

### PostgreSQL + `batch_alter_table` Compatibility [VERIFIED: migration 0004]

Migration 0004 proves the pattern works in production Postgres. The `render_as_batch=True` in `env.py` is global — it applies to both SQLite and Postgres. On Postgres, Alembic translates `batch_alter_table` `drop_constraint` + `create_check_constraint` into `ALTER TABLE DROP CONSTRAINT / ADD CONSTRAINT` DDL (not the SQLite CREATE+COPY+DROP). This is the correct and efficient path for Postgres.

If models.py and the migration disagree, SQLite batch operations will fail on downgrade (exactly the bug documented in migration 0005 comments lines 52–59).
