## ★ KORREKTUR am Plan-02-Befehl (Operations-Lehre — für künftige manuelle Prod-Migrationen)

Der im Plan hinterlegte Befehl nutzte `DATABASE_URL=postgresql://nerve_app@/nerve` unter `sudo -u postgres`:

```
# FALSCH — peer-auth scheitert (OS-User postgres ≠ DB-User nerve_app):
ssh … 'sudo -u postgres bash -c "cd /opt/nerve/app && DATABASE_URL=postgresql://nerve_app@/nerve /opt/nerve/venv/bin/alembic upgrade head"'
→ FATAL: Peer authentication failed for user "nerve_app"
```

**Sicher fehlgeschlagen:** der Verbindungsfehler trat VOR jedem DDL auf → Prod danach als **unberührt** verifiziert (noch 0030, 0 neue Spalten). Kein Halb-Migrations-Zustand.

Danach korrekt gefahren mit `postgres@` (Muster wie `deploy.sh:174` für nerve_test):

```
# RICHTIG:
… DATABASE_URL=postgresql://postgres@/nerve … alembic upgrade head
```

**Regel für künftige manuelle Prod-Migrationen (deckt sich mit Memory `project_nerve_prod_deploy` „migrations as postgres"):** unter `sudo -u postgres` mit `postgres@`-DSN migrieren, NICHT `nerve_app@` (peer-auth bindet an den OS-User). Für Plan 03 nachziehen falls dort ein Migrations-Befehl referenziert wird — Plan 03 fasst aber nur `models.py`/`app.py` an (kein neuer alembic-Lauf), also kein Befehls-Fix nötig.
