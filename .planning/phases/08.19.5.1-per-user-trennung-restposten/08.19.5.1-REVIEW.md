## Summary

The per-SID migration work in this phase is structurally sound. `_write_ft_assistant_event` correctly reads all state from `_session_state[sid]` under `_session_state_lock` (REQ-01/WR-01), and the `analyse_loop` correctly iterates over active SIDs. The test suite covers the key isolation invariants (REQ-01, WR-01, WR-02, REQ-06, REQ-07, REQ-08) with proper runtime assertions — no source-presence false-greens detected.

Three warnings require attention: a stale global state read in `streame_manual_ewb_variante`, mixed global-vs-per-SID reads inside `analyse_loop` and `_qa_pipeline_dispatch` that undermine the per-SID isolation goal, and an obsolete helper in `test_ft_write_hooks.py` that does nothing but mutate a legacy global.

## Warnings

### WR-01: `streame_manual_ewb_variante` reads `user_id` from legacy global state, not from per-SID state

**File:** `services/claude_service.py:731-737`

**Issue:** The function receives `sid` as a parameter, but the `_user_id` it passes to `build_profile_context` is read from `ls.state` (the old global dict) under `ls.state_lock`. In a multi-session scenario, `ls.state['user_id']` holds the *last user who started a session globally*, not the user belonging to `sid`. This means a Button-Click from User A in Session SID-A could send User B's `user_id` to `build_profile_context` if User B started a session more recently. The function was migrated to per-SID for profile context (line 744 correctly passes `sid=sid`) but the `_user_id` it derives to pass to `build_profile_context(user_id=...)` is still from global state.

**Fix:**
```python
# Replace lines 731-737 with per-SID read:
try:
    import services.live_session as _ls_manual
    with _ls_manual._session_state_lock:
        _user_id = (_ls_manual._session_state.get(sid) or {}).get('user_id') or 0
except Exception:
    _user_id = 0
```

### WR-02: `analyse_loop` phase-classifier and cold-call-inference reads use global `ls.state`, not per-SID state

**File:** `services/claude_service.py:1030-1034, 1093-1095`

**Issue:** After iterating per-SID (lines 898+), the phase classifier block at line 1030 reads `current_phase`, `phase_change_count`, `mode`, and other values from `ls.state` (global), and writes results back to `ls.state` (lines 1049-1055). Similarly, `cold_call_inference` reads `mode` and `current_phase` from `ls.state` at lines 1093-1095 and writes back at line 1103. In a multi-user deployment these writes are last-write-wins across SIDs — SID-A's phase detection can overwrite SID-B's phase state. The loop variable `sid` is in scope but the per-SID `_session_state[sid]` is not used for these reads.

**Fix:** Move phase state into `_session_state[sid]['state']` and read/write under `_session_state_lock` using the loop's `sid`. This is the same pattern already applied to `is_paused`, `ft_session_id`, `active_learning_cards`, etc. This is a larger refactor — marking as warning because EA deployment is single-tenant (as noted in CLAUDE.md), but it is a correctness risk at scale.

### WR-03: `_qa_pipeline_dispatch` reads `kw_fired_for_line`, `session_anrede`, `slot1_variant_busy_until` from global `ls.state`

**File:** `services/claude_service.py:1288-1291, 1356-1357`

**Issue:** `_qa_pipeline_dispatch` is called inside the per-SID loop (line 947) with the current `sid`, but internally reads `kw_fired_for_line`, `session_anrede`, and `slot1_variant_busy_until` from the global `ls.state` dict (lines 1288-1291). The slot-1 mutex write at line 1357 also goes back to `ls.state`. With multiple concurrent SIDs, one SID's keyword-match can suppress another SID's QA dispatch because they share the same `kw_fired_for_line` key.

**Fix:** These three values (`kw_fired_for_line`, `session_anrede`, `slot1_variant_busy_until`) should be stored and read per-SID from `_session_state[sid]['state']`. The `sid` argument is already threaded into `_qa_pipeline_dispatch` — it just needs to be used for these reads.

**File:** `tests/test_ft_write_hooks.py:14-35`

**Issue:** After the Phase 08.19.5.1 migration, all three tests that use `_write_ft_assistant_event` now set up per-SID state via `ls_mod.init_session_state(...)` + direct `_session_state` writes. The `_setup_ls_state` / `_restore_ls_state` helpers (lines 14-35) mutate the old `ls.state` global and are no longer called by any test in this file. They remain as dead helper functions.

**Fix:** Remove `_setup_ls_state` and `_restore_ls_state` functions (lines 14-35). They add confusion because they imply the old global-state path is still needed.

### IN-02: `test_write_hook_swallows_exceptions` does not exercise the exception-swallowing path it claims to test

**File:** `tests/test_ft_write_hooks.py:191-207`

**Issue:** The test's docstring says "Any DB exception must NOT propagate," but the test calls `_write_ft_assistant_event` with `sid=None`, which triggers the D-01 return-early at line 166 before any DB access. The comment inside the test acknowledges this: "sid=None → Return-Early, no exception possible." The test does pass and is not a false-green (it verifies no raise on `sid=None`), but it does not cover the case it documents — a DB failure when `sid` is valid. The actual `except Exception` swallow at line 226 is untested.

**Fix (optional):** Either rename the test to `test_no_raise_when_sid_is_none` to be honest about what it covers, or add a companion test that injects a DB session that raises on `commit()` with a valid `sid` to verify the swallow at line 226.
