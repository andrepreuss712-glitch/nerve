<decisions>
## Implementation Decisions

### D-01: Fallback bei sid=None — Return-Early

**Entscheidung:** `_write_ft_assistant_event` gibt bei `sid=None` sofort zurück (kein DB-Write, kein Global-Read):

```python
if sid is None:
    print(f'[FT] skip — no sid for module={module}')
    return
```

**Begründung:** DSGVO-sicherer als Legacy-Global-Fallback — kein Cross-Session-Risiko möglich. Beide bekannten Caller (analyse_loop, coaching_loop) übergeben nach der Migration immer `sid=sid` explizit. Der `sid=None`-Pfad ist theoretisch (zukünftiger Caller der Parameter vergisst).

**Kein Legacy-Global-Fallback** (`ls.state_lock` + `ls.state`). Der alte Pfad wird vollständig ersetzt.

### D-02: Plan-Aufteilung — 1 atomarer Plan

**Entscheidung:** Ein einziger Plan für alle Änderungen:
- WR-01: `_write_ft_assistant_event` Signatur + per-SID-Read + Return-Early
- WR-01 Callers: `analyse_loop:1000` und `coaching_loop:1548` — `sid=sid` übergeben
- WR-02: `analyse_loop:916` Read-Pfad
- 2 neue Isolation-Tests in `tests/test_per_sid_migration.py`
- Pruning-Notiz

**Begründung:** Phase ist klein (~35 Zeilen Code + ~40 Zeilen Tests). Kein Wave-Overhead nötig. Passt zu Komplexität 🟡 mittel.

### D-03: Test-Strategie — monkeypatch SessionLocal

**Entscheidung:** `_write_ft_assistant_event`-Isolation-Test nutzt `monkeypatch.setattr(_db_mod, 'SessionLocal', lambda: db_session)` — identisch zum REQ-06-Pattern aus `tests/test_per_sid_migration.py`.

**Ablauf:**
1. Zwei SIDs initialisieren (`init_session_state(sid_a, user_id=1)`, `init_session_state(sid_b, user_id=2)`)
2. SessionLocal monkeypatched → In-Memory-DB
3. `_write_ft_assistant_event(module='test', ..., sid=sid_a)` aufrufen
4. `db_session.query(FtAssistantEvent).first()` → `assert row.user_id == 1` (User-A, nicht User-B)

**Warum nicht `db.add()` monkeypatchen:** Tests echten DB-Commit-Pfad (`db.add()` + `db.commit()`), nicht nur Row-Objekt-Konstruktion.

### Strukturelle Anmerkungen für Planer

**WR-01 Read-Struktur** (`_session_state[sid]` Layout aus `init_session_state`):
- `_session_state[sid]['user_id']` — top-level (für `user_id`)
- `_session_state[sid]['market']` — top-level (für `market`)
- `_session_state[sid]['language']` — top-level (für `language`)
- `_session_state[sid]['mode']` — top-level (für DSGVO-Enforcement Cold-Call)
- `_session_state[sid]['state']['ft_session_id']` — sub-key (für `ft_session_id`)
- `_session_state[sid]['state']['kaufbereitschaft']` — sub-key (für `readiness`)

**Lock:** Einmaliger `_session_state_lock`-Block für alle Felder (kein Split-Read). Kein `state_lock` mehr.

**WR-02 Read (analyse_loop:916):** Innerhalb des `for sid in active_sids:`-Loops — `sid` ist bereits verfügbar. Lock: `_session_state_lock` (konsistent mit WR-01).
