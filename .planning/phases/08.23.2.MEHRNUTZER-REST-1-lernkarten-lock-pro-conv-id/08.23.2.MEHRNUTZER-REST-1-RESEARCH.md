## 2. Die Riegel-Ablage, konkret (Forschungsfrage 2)

### 2.1 Umgebungs-Annahmen, belegt

| Fakt | Wert | Beleg |
|---|---|---|
| Prozess-/Faden-Modell | gunicorn, **1 Worker, 64 Threads** (gthread) | `deploy/nerve.service:35-36` |
| Obergrenze gleichzeitiger Analysen | ≤ 64 (ein Thread je HTTP-Request) | Folge aus obigem |
| DB-Pool | `pool_size=20`, `max_overflow=15`, `pool_timeout=10` | `database/db.py:29-32` |
| Zeitlimit des LLM-Aufrufs | 45 s, `max_retries=0` | `config.py:134`, `claude_service.py:62-64` |

`threading.Lock` ist **nicht** reentrant, und das ist im Projekt bewusst so
[ZITIERT: `services/live_session.py:308-310` via Docstring in
`tests/test_session_lock_blocking_calls_guard.py`: *„Ein RLock wuerde diesen Design-Zwang lautlos
aufloesen"*]. Die neue Ablage darf diesen Grundsatz nicht aufweichen.

### 2.2 Empfohlene Umsetzung (Skizze — der Plan formuliert sie aus)

```python
# services/coaching_service.py — ersetzt _analysis_lock
_conv_locks = {}                       # conv_id(str) -> [threading.Lock, refcount:int]
_conv_locks_guard = threading.Lock()   # schuetzt NUR die Ablage; nie ueber einem Netz-Aufruf gehalten


@contextmanager
def _analysis_lock_for(conv_id):
    """Riegel PRO conv_id. Ersetzt den fruher prozessweiten _analysis_lock.

    Der Duplikatschutz bleibt identisch stark (dieselbe Serialisierung je conv_id),
    verschiedene Anrufe blockieren sich nicht mehr.
    """
    key = str(conv_id)                        # int 5 und '5' auf DENSELBEN Riegel abbilden
    with _conv_locks_guard:                   # (1) Eintrag holen/anlegen + Zaehler HOCH
        eintrag = _conv_locks.get(key)
        if eintrag is None:
            eintrag = [threading.Lock(), 0]
            _conv_locks[key] = eintrag
        eintrag[1] += 1
    riegel = eintrag[0]
    riegel.acquire()                          # (2) AUSSERHALB des Ablage-Riegels warten
    try:
        yield
    finally:
        riegel.release()                      # (3) erst freigeben ...
        with _conv_locks_guard:               # (4) ... dann Zaehler RUNTER, unter der Ablage
            eintrag[1] -= 1
            if eintrag[1] == 0 and _conv_locks.get(key) is eintrag:
                del _conv_locks[key]
```

Im Rumpf aendert sich damit **genau eine Zeile**:

```python
 59      with _analysis_lock:            ->      with _analysis_lock_for(conv_id):
```

### 2.3 Warum genau diese Reihenfolge — die vier Fallen

1. **Zaehler HOCH vor `acquire()`, unter dem Ablage-Riegel.** Das ist der Kern. Wuerde der Zaehler
   erst nach dem `acquire()` erhoeht, koennte ein Wartender existieren, dessen Eintrag von einem
   anderen Faden mit Zaehler 0 geloescht wird → ein spaeter kommender dritter Faden legt einen
   **neuen** Riegel unter demselben Key an → **zwei Faden derselben `conv_id` laufen gleichzeitig**
   → Duplikatschutz-Loch. Genau die Fehlerklasse, die diese Phase nicht erzeugen darf. [ANNAHME zur
   Standard-Literatur, aber am Kontrollfluss oben nachvollziehbar; keine externe Quelle konsultiert]
2. **Zaehler RUNTER unter dem Ablage-Riegel** (nicht daneben) — sonst ist `-= 1` und der
   `== 0`-Test nicht atomar zueinander. `int`-Dekrement ist unter dem GIL **nicht** garantiert
   atomar in Verbindung mit dem folgenden Vergleich.
3. **`release()` VOR dem Zaehler-Dekrement.** Umgekehrt hielte man kurzzeitig beide Riegel
   gleichzeitig in **anderer** Reihenfolge als beim Erwerb → theoretische Rangfolge-Inversion. Mit
   der obigen Reihenfolge wird der Ablage-Riegel **nie** gehalten, waehrend der `conv_id`-Riegel
   gehalten wird (Erwerb: Ablage → frei → conv; Freigabe: conv frei → Ablage). Sauber.
4. **`is eintrag`-Vergleich beim Loeschen.** Streng genommen nicht noetig (ein Eintrag mit
   Zaehler > 0 kann nicht ersetzt werden), aber billig und macht die Invariante im Code sichtbar.
   Empfohlen.

**Der Ablage-Riegel wird ausschliesslich fuer Dict-Operationen gehalten** — kein `get_session`,
kein `messages.create`, kein `sleep`, kein `emit`. Das ist genau die Bau-Vorschrift, die
`tests/test_session_lock_blocking_calls_guard.py` fuer `_session_state_lock` durchsetzt; die neue
Ablage haelt sie von Anfang an ein. [VERIFIZIERT: Bauplan oben gegen den Verbots-Katalog
`tests/test_session_lock_blocking_calls_guard.py:158-166` geprueft]

### 2.4 `conv_id` = None / leer / Typ-Wechsel

- **Beide Aufrufer schliessen falsy `conv_id` aus** (`routes/learning.py:24-26` bzw. `:383-385`)
  [VERIFIZIERT]. Die Funktion ist trotzdem oeffentlich.
- **Empfehlung: KEIN Sonderfall.** `key = str(conv_id)` — `None` wird zu `'None'`, alle
  None-Aufrufe teilen sich einen Riegel. Das ist die **fail-safe** Richtung: mehr Serialisierung,
  nie weniger Schutz. Ein `if not conv_id: <ohne Riegel weiter>` waere eine echte Schwaechung und
  ist abzulehnen.
- `str()` faengt zusaetzlich den **Typ-Wechsel** ab: JSON liefert `conv_id` mal als `int`, mal als
  `str`; ohne `str()` bekaemen `5` und `"5"` **verschiedene** Riegel, obwohl `filter_by(call_id=…)`
  in Postgres denselben Datensatz meint. Das ist ein realer, heute vom globalen Riegel verdeckter
  Fehlerkandidat und muss im Plan als Entscheidung stehen. [VERIFIZIERT: `data.get('conv_id')` ohne
  Cast in `routes/learning.py:23` und `:382`]

### 2.5 Speicherwachstum — die von der Roadmap geforderte Begruendung

Die Roadmap verlangt ausdruecklich, die Wahl zu **begruenden**:

| Variante | Bewertung |
|---|---|
| **Referenz-gezaehlt (gewaehlt)** | Obergrenze = Anzahl gleichzeitig laufender Analysen ≤ 64 (Thread-Zahl). Nach dem letzten Verlassen ist der Eintrag weg. **Kein** Wachstum ueber die Zeit. Kosten: ein zusaetzlicher Ablage-Riegel + zwei kurze kritische Abschnitte. |
| Ablage ohne Aufraeumen | Waechst mit jedem Anruf → Memory-Leak. Von der Roadmap ausdruecklich als Falle benannt. **Abgelehnt.** |
| `WeakValueDictionary` | Funktioniert nur mit einem Guard um „holen-oder-anlegen" (sonst Race) — dann ist sie nicht einfacher als der Zaehler, aber ihre Korrektheit haengt zusaetzlich am GC-Zeitpunkt. **Abgelehnt** (schwerer zu beweisen, gleicher Aufwand). |

**Die Aufloesung (praezisiert, nicht aufgeweicht):** Die zu bewachende Fehlerklasse ist ein
**FUER ALLE NUTZER GEMEINSAMER** Riegel um einen Netz-Aufruf. Ein **per-Schluessel**-Riegel ist
definitionsgemaess **kein** Verstoss — er ist die Loesung. Zaehl- und Melde-Seite werden deshalb
getrennt:

| Riegel-Ausdruck | zaehlt fuer die Soll-Tabelle | verstoss-faehig |
|---|---|---|
| Name/Attribut aus der abgeleiteten Riegel-Menge (`with _analysis_lock:`) | ja | **ja** |
| `ast.Call` auf `_lock`/`_lock_for` **MIT** mindestens einem Argument (`_analysis_lock_for(conv_id)`) | ja | **nein** — per-Schluessel |
| `ast.Call` auf `_lock`/`_lock_for` **OHNE** Argument (`_hole_lock()`) | ja | **ja** — faktisch gemeinsam |

Damit bleibt der ROT-Lauf **unveraendert** (vor dem Fix steht dort `with _analysis_lock:`, ein
gemeinsamer Riegel → gemeldet), und nach dem Fix ist der Waechter gruen **und** sieht den neuen
Riegel weiterhin.

**Die dadurch entstehende NEUE Restluecke gehoert in den Pruefkatalog** (Punkt 31, sie darf nicht
verschwiegen werden): eine Fabrik, die ihr Argument **ignoriert** und trotzdem einen gemeinsamen
Riegel zurueckgibt (`def _x_lock_for(_egal): return _EIN_GLOBALER`), rutscht durch — der Sweep
sieht nur die Aufrufform, nicht den Rumpf der Fabrik. Richtung: **Durchrutscher**, nicht
Falsch-Treffer.

**Der zu (A) gehoerende Selbst-Test muss deshalb BEIDE Richtungen pruefen:** der Fabrik-Block
wird **gezaehlt** (== 1), aber **nicht gemeldet** — und ein danebenstehender
`with _globaler_lock:` mit `messages.create` **muss** gemeldet werden. Nur eine Richtung zu
pruefen beweist die Haelfte.

## 8. Haeufige Fallen dieser Phase

### Falle 1 — Der Waechter wird nach dem Fix blind statt gruen
**Was passiert:** `with _analysis_lock_for(conv_id):` ist ein **Aufruf**, kein Riegel-Name. Die
Blockzaehlung fuer `coaching_service.py` faellt auf 0.
**Erkennen:** das Datei-Soll `services/coaching_service.py` (nach dem Fix: 3) wird rot.
**Vermeiden:** Riegel-Erkennung auf Aufrufe mit `_lock`/`_lock_for`-Endung ausdehnen (§4.6 Variante A)
**und** einen Selbst-Test dafuer schreiben. **Das ist der wichtigste Einzelpunkt der Planung.**

### Falle 2 — Zaehler-Dekrement ausserhalb des Ablage-Riegels
**Was passiert:** `-= 1` und `== 0` sind nicht atomar zueinander → Eintrag wird geloescht, waehrend
ein Wartender existiert → zwei Faden derselben `conv_id` laufen gleichzeitig → doppelte Karten.
**Erkennen:** Test (b) wird flatterhaft rot (selten). Der schlimmste Fall: er bleibt gruen und der
Fehler tritt erst auf Produktion auf.
**Vermeiden:** §2.2 Schritt (4), woertlich.

### Falle 3 — `conv_id` als `int` und als `str`
**Was passiert:** `5` und `"5"` bekommen verschiedene Riegel, meinen aber denselben Datensatz →
Duplikatschutz-Loch, das der globale Riegel bisher verdeckt hat.
**Vermeiden:** `key = str(conv_id)` (§2.4). **Im Plan als Entscheidung nennen**, nicht nebenbei.

### Falle 4 — Der Test wird zur Wanduhr-Messung
**Was passiert:** „parallel < 2× seriell" flattert auf dem geteilten VPS unter Deploy-Last.
**Vermeiden:** Event-Rendezvous (§3.4). Kein `perf`-Marker — er waere die Kapitulation.

### Falle 5 — Ein `wait()` ohne Timeout haengt den Deploy
**Was passiert:** `deploy.sh:221` hat keinen pytest-Timeout; ein blockierender Test haengt den
gesamten Deploy [ZITIERT: `tests/test_session_lock_deadlock_guard.py:118-119`].
**Vermeiden:** jedes `wait`/`join` mit `timeout=`, Faden `daemon=True`.

### Falle 6 — Teil (b) als ROT-Beleg verkaufen
**Was passiert:** Teil (b) ist vor **und** nach dem Fix gruen. Wer ihn als ROT-Beleg auffuehrt,
behauptet einen Beweis, den er nicht hat.
**Vermeiden:** §3.5 — ehrlich als Gegenpol deklarieren, Falsifizierbarkeit ueber den dritten Test.

### Falle 7 — `_WHITELIST` der bestehenden Datei mitbenutzen
**Was passiert:** `_WHITELIST` enthaelt bereits Riegel-Namen (`state_lock`, `_per_sid_lock`, …) —
aber als **erlaubte Zuweisungsziele** fuer `ls.<attr> =`. Wer sie fuer die neue Klasse mitbenutzt,
