Drei Kandidaten gegen das Memory-Leak, das eine Ablage `conv_id -> Lock` ohne Aufraeumen
darstellt:

| Variante | Bewertung |
|---|---|
| **(a) Nehmer-Zaehler, Aufraeumen im `finally`** — **GEWAEHLT** | Obergrenze = Anzahl gleichzeitig laufender Analysen ≤ 64 (Thread-Zahl, `deploy/nerve.service:35-36`). Nach dem letzten Verlassen ist der Eintrag weg. **Kein** Wachstum ueber die Zeit. Kosten: ein zusaetzlicher Ablage-Riegel + zwei kurze kritische Abschnitte, ~15 Zeilen. |
| (b) Deckel-/LRU-Ablage (z.B. max 512) | Kuerzer zu schreiben — aber eine Verdraengung, **waehrend** ein Riegel gehalten wird, ist **exakt** das Duplikatschutz-Loch, das diese Phase verhindern soll. Bei 512 unwahrscheinlich, aber es ist eine **stille Bedingung statt einer Garantie**. **ABGELEHNT.** |
| (c) `WeakValueDictionary` | Braucht trotzdem einen Guard um „holen-oder-anlegen" (sonst Race) — also gleicher Aufwand, aber die Korrektheit haengt zusaetzlich am GC-Zeitpunkt. Schwerer zu beweisen. **ABGELEHNT.** |
| (d) Nie aufraeumen | Genau das Leak, das die Roadmap verbietet. **ABGELEHNT.** |

**Der Entscheidungsgrund in einem Satz:** (a) ist die einzige Variante, bei der der Duplikatschutz
**nicht von einer Groessen-Annahme abhaengt** — er bleibt beweisbar exakt so stark wie heute, und
genau das ist der erklaerte Kern-Anspruch der Phase.

<die_vier_fallen>
<!-- RESEARCH §2.3. Die Reihenfolge IST der ganze Trick. -->

1. **Zaehler HOCH vor `acquire()`, unter dem Ablage-Riegel.** Wuerde der Zaehler erst **nach** dem
   `acquire()` erhoeht, koennte ein Wartender existieren, dessen Eintrag ein anderer Faden mit
   Zaehler 0 loescht → ein dritter Faden legt einen **neuen** Riegel unter demselben Key an →
   **zwei Faden derselben `conv_id` laufen gleichzeitig** → Duplikatschutz-Loch. Genau die
   Fehlerklasse, die diese Phase nicht erzeugen darf.
2. **Zaehler RUNTER unter dem Ablage-Riegel** (nicht daneben) — `-= 1` und der `== 0`-Test sind
   sonst nicht atomar zueinander. Der GIL garantiert das **nicht** in Verbindung mit dem
   folgenden Vergleich.
3. **`release()` VOR dem Zaehler-Dekrement.** Erwerb: Ablage → frei → conv. Freigabe: conv frei →
   Ablage. So wird der Ablage-Riegel **nie** gehalten, waehrend der conv-Riegel gehalten wird →
   keine Rangfolge-Inversion.
4. **`is eintrag`-Vergleich beim Loeschen.** Streng genommen nicht noetig (ein Eintrag mit
   Zaehler > 0 kann nicht ersetzt werden), aber billig und macht die Invariante sichtbar.

**Zusaetzlich — Falle 3 der Phase (`conv_id` als `int` und als `str`):** `routes/learning.py:23`
und `:382` lesen `data.get('conv_id')` **ohne Cast**. JSON liefert mal `5`, mal `"5"`. Ohne
`key = str(conv_id)` bekaemen beide **verschiedene** Riegel, obwohl `filter_by(call_id=…)` in
Postgres **denselben** Datensatz meint — ein realer, heute vom globalen Riegel verdeckter
Fehlerkandidat. **Entscheidung: `key = str(conv_id)`.** Kein Sonderfall fuer `None`/falsy:
`None` wird zu `'None'`, alle None-Aufrufe teilen sich einen Riegel. Das ist die **fail-safe**
Richtung — mehr Serialisierung, nie weniger Schutz. Ein `if not conv_id: <ohne Riegel weiter>`
waere eine echte Schwaechung und ist abzulehnen.
</die_vier_fallen>

```python
# ── Riegel PRO conv_id (Phase 08.23.2.MEHRNUTZER-REST-1) ─────────────────────
# Ersetzt den frueher prozessweiten _analysis_lock. Der hielt waehrend des ganzen
# Sonnet-Aufrufs (config.HTTP_LLM_TIMEOUT_LONG_S = 45 s, config.py:134) ALLE Nutzer
# auf; ein zweiter wartete bis 45 s, ein dritter bis 90 s, und jeder Wartende belegte
# einen der 64 gthread-Threads (deploy/nerve.service:35-36).
#
# WARUM NEHMER-ZAEHLER statt Deckel-/LRU-Ablage (Roadmap verlangt die Begruendung):
# Eine Verdraengung, WAEHREND ein Riegel gehalten wird, ist exakt das
# Duplikatschutz-Loch, das diese Phase verhindern soll. Der Zaehler ist die einzige
# Variante, bei der der Schutz nicht von einer Groessen-Annahme abhaengt. Die Ablage
# bleibt so gross wie die Zahl der GERADE LAUFENDEN Analysen (<= 64) und ist danach
# leer — kein Wachstum ueber die Zeit.
#
# _conv_locks_guard wird AUSSCHLIESSLICH fuer Dict-Operationen gehalten: kein
# get_session, kein messages.create, kein sleep, kein emit. (Dieselbe Bau-Vorschrift,
# die tests/test_session_lock_blocking_calls_guard.py:158-166 fuer _session_state_lock
# durchsetzt.)
@contextmanager
def _analysis_lock_for(conv_id):
    """Riegel pro conv_id. Duplikatschutz identisch stark, verschiedene Anrufe
    blockieren sich nicht mehr.

    key = str(conv_id): routes/learning.py:23 und :382 lesen conv_id OHNE Cast aus dem
    JSON — 5 und "5" bekaemen sonst VERSCHIEDENE Riegel, obwohl
    filter_by(call_id=...) in Postgres denselben Datensatz meint. Kein Sonderfall fuer
    None/falsy: None wird zu 'None' und teilt sich einen Riegel. Fail-safe Richtung —
    mehr Serialisierung, nie weniger Schutz.
    """
    key = str(conv_id)
    with _conv_locks_guard:                   # (1) holen/anlegen + Zaehler HOCH
        eintrag = _conv_locks.get(key)        #     HOCH vor acquire(): sonst koennte
        if eintrag is None:                   #     ein Wartender wegge-raeumt werden
            eintrag = [threading.Lock(), 0]   #     und ein Dritter legte einen ZWEITEN
            _conv_locks[key] = eintrag        #     Riegel unter demselben Key an
        eintrag[1] += 1
    riegel = eintrag[0]
    riegel.acquire()                          # (2) warten AUSSERHALB des Ablage-Riegels
    try:
        yield
    finally:
        riegel.release()                      # (3) erst freigeben ...
        with _conv_locks_guard:               # (4) ... dann Zaehler RUNTER, unter der
            eintrag[1] -= 1                   #     Ablage: '-= 1' und '== 0' sind sonst
            if eintrag[1] == 0 and _conv_locks.get(key) is eintrag:
                del _conv_locks[key]          #     nicht atomar zueinander
```
