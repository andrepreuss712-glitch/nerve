Two **real launch-blockers** remain and must be fixed:

1. **Markdown filter renders raw HTML**. `markdown.markdown(value, extensions=['extra', 'sane_lists'])` preserves inline HTML in the input, then `{{ ... | markdown | safe }}` in `session_detail.html` marks the result as safe — any `<script>`, `<iframe>`, `<img onerror=...>` in `precall_briefing` is injected verbatim. A user who writes `<img src=x onerror=alert(1)>` in the `optinfo` field gets it echoed back by Haiku and rendered as raw HTML. Worst case with an attacker's account: XSS in one's own browser (low impact). But with a coach/team-admin viewing the session_detail of a team-member — escalation path exists. DSGVO-Stance: "AI-generated content rendered as HTML" is sensitive. **This is blocker-01 because it's 1-line to fix.**

2. **Migration script is not safe to run against live DB**. Several issues:
   - `--dry-run` documented in usage but code checks `--dry` (flag mismatch → easy footgun)

Everything else is fixable post-launch or is already fine. Detailed findings below.

## Launch-Blockers

### LB-01: Markdown filter renders raw HTML tags — XSS via PreCall-Briefing

**File:** `app.py:60-65`, `templates/session_detail.html:254`
**Severity:** LAUNCH-BLOCKER
**Risk:** XSS, DSGVO-concern (AI content with potential user-injected HTML rendered as HTML)

**Evidence:**

```python
# app.py:60-65
import markdown as _markdown
def markdown_filter(value):
    if not value:
        return ''
    return _markdown.markdown(value, extensions=['extra', 'sane_lists'])
app.jinja_env.filters['markdown'] = markdown_filter
```

```jinja
{# templates/session_detail.html:254 #}
<div class="n-session-detail-precall-body">{{ conv.precall_briefing | markdown | safe }}</div>
```

**Attack chain:**
1. User enters `<img src=x onerror="fetch('/api/admin/users?action=delete_all',{method:'POST'})">` into PreCall form field `optinfo` (max 500 chars, maxlength client-side only — backend accepts up to 500 before forwarding to Haiku)
2. `services/precall_service.py` line 139 appends it to `search_text` and sends to Haiku
3. Haiku returns briefing that echoes parts of the input (model generally passes through verbatim text when asked for summaries/integration)
4. Briefing is stored in `ConversationLog.precall_briefing` (TEXT column, no sanitization)
5. User (or admin/coach) views `/dashboard/session/<id>` → `session_detail.html` renders `{{ conv.precall_briefing | markdown | safe }}`
6. `markdown.markdown()` with `['extra', 'sane_lists']` **does NOT strip raw HTML by default** — it preserves inline HTML tags
7. `| safe` tells Jinja the result is safe → tag lands in DOM → XSS fires

**Test to reproduce (mental execution):**
```python
>>> import markdown
>>> markdown.markdown('<img src=x onerror=alert(1)>', extensions=['extra', 'sane_lists'])
'<p><img src=x onerror=alert(1)></p>'   # raw HTML preserved!
```

**Fix (1-line, minimal diff):**

Option A — use `bleach` (pip install bleach, add to requirements.txt):

```python
import markdown as _markdown
import bleach
_ALLOWED_TAGS = ['p', 'h1', 'h2', 'h3', 'h4', 'strong', 'em', 'ul', 'ol', 'li',
                 'code', 'pre', 'blockquote', 'a', 'br', 'hr']
_ALLOWED_ATTRS = {'a': ['href', 'title']}

def markdown_filter(value):
    if not value:
        return ''
    rendered = _markdown.markdown(value, extensions=['extra', 'sane_lists'])
    return bleach.clean(rendered, tags=_ALLOWED_TAGS, attributes=_ALLOWED_ATTRS,
                        strip=True)
```

Option B — use Python-Markdown's built-in safe-mode via `markdown.Markdown(safe_mode='escape')` (deprecated in 3.x but still works) or `extensions=['markdown.extensions.nl2br']` plus post-regex strip of `<script>`, `<iframe>`, `<object>`, `<embed>`, `on*=` attrs.

**Recommendation:** Option A (bleach). It's the community-standard approach, battle-tested against malformed payloads (null-byte splits, UTF-8 confusables, unicode category bypasses), and requires 3 lines of code + 1 dependency.

Add `bleach>=6.1.0` to `requirements.txt`.

**Tests to add:**
```python
# tests/test_markdown_filter.py

    from app import markdown_filter
    assert '<script>' not in markdown_filter('<script>alert(1)</script>')

def test_strips_onerror_attribute():
    from app import markdown_filter
    assert 'onerror' not in markdown_filter('<img src=x onerror=alert(1)>')

def test_preserves_safe_markdown():
    from app import markdown_filter

    assert '<strong>bold</strong>' in out
```

### LB-02: Migration script idempotency + flag footgun + race window

**File:** `scripts/migrate_polish_38_counters.py:18-82`
**Severity:** LAUNCH-BLOCKER
**Risk:** Data corruption when run against live DB, or operator accidentally thinks dry-run but writes because flag mismatch.

**Evidence 1: `--dry-run` flag mismatch**
```python
# Line 18 (docstring):
    python scripts/migrate_polish_38_counters.py --dry-run  # Dry-Run (zeigt nur was geaendert wuerde)
```

```python
# Line 80 (code):
    dry = '--dry' in sys.argv
```

Footgun: operator reads docstring, runs `--dry-run`, but `'--dry' in sys.argv` evaluates True because `'--dry'` is a substring of `'--dry-run'` (actually `in` on a list is element-wise, not substring — let me recheck).

Wait — `'--dry' in sys.argv` where `sys.argv = ['script.py', '--dry-run']` is element-wise check → `False`. So `--dry-run` would NOT trigger dry-mode, and the script would **write to DB** despite operator using the docstring-documented flag. **That's the bug.** Operator follows docs, believes they're in dry-run, actually writes to production DB.

Verified mental execution:
```python
>>> '--dry' in ['script.py', '--dry-run']
False
>>> '--dry' in ['script.py', '--dry']
True
```

**Evidence 2: Race window with live `/api/beenden`**

The migration script reads `ObjectionEvent` rows and overwrites `ConversationLog.einwaende_gesamt` based on SUM. If a live session is wrapping up *in parallel* (user clicked Beenden, `/api/beenden` is in the middle of its 2-phase commit — ConversationLog inserted with `einwaende_gesamt=len(ewb_clicks)`, but the POLISH-38 re-aggregate SELECT hasn't committed yet), the migration script could see the partial ObjectionEvent count and overwrite with an incorrect value.

Concretely: user has 5 EWB-clicks. `/api/beenden` flow:
1. Commit ConversationLog with `einwaende_gesamt=5` (POLISH-38 defensive fallback at line 422)
2. Insert 5 ObjectionEvent rows (line 453-460)
3. Commit (line 462)
4. Re-aggregate SELECT: sees 5, overwrites with 5, commits (line 482-485)

Between step 1 and 2 (typically <1ms but no atomicity guarantee in SQLite default isolation), the migration script could SELECT on ObjectionEvent for this conv_id, find 0 rows, not appear in agg_map, get skipped. That's actually *fine* (migration doesn't touch this row).

Between step 2 and 3, migration could see 5 rows without success flags set. That's also fine (same total).

**Real problem**: if `/api/beenden` fails at step 4 (reconcile) but succeeded at step 3 (bulk insert), and THEN the migration runs — the migration would reconcile correctly. That's also fine.

The real issue is **dry-run flag mismatch**. The race is defensive-fine because SQLite serializes writes. Removing LB-02 race concern from the critical path but keeping the flag fix as launch-blocker.

**Evidence 3: No `--confirm-production` safeguard**

Operator with prod shell could mistype and run the script with no dry-run. Given the flag-mismatch above, this is doubly dangerous.

**Fix (minimal diff):**

```python
# At line 79-81, replace:
if __name__ == '__main__':
    import argparse
    ap = argparse.ArgumentParser(description=__doc__)
    ap.add_argument('--dry-run', action='store_true',
                    help='Zeigt Aenderungen ohne sie zu schreiben')
    ap.add_argument('--confirm-production', action='store_true',
                    help='Pflicht wenn DATABASE_URL != sqlite:///:memory: und nicht --dry-run')
    args = ap.parse_args()

    # Safety-Gate: non-dry-run muss explizit bestaetigt werden
    if not args.dry_run and not args.confirm_production:
        import os
        if os.environ.get('DATABASE_URL', '').find(':memory:') < 0:
            print('[migrate] ABBRUCH: Production-Lauf braucht --confirm-production flag.')
            print('[migrate] Tipp: zuerst mit --dry-run pruefen.')
            sys.exit(2)

    sys.exit(main(dry_run=args.dry_run))
```

Also: consider adding a cutoff-date filter so the migration only touches `ConversationLog.created_at < cutoff` to be explicit about "historical data only":

```python
# In main(), add at top:

# ... then in query ...
.filter(ConversationLog.created_at < cutoff_date)
```

## Pre-Launch Fixes

### PL-01: `/api/beenden` is not wrapped in a single transaction

**File:** `routes/app_routes.py:411-635`
**Severity:** PRE-LAUNCH-FIX
**Risk:** Partial state visibility, orphan ObjectionEvent rows on mid-flow exception.

**Evidence:**
- Line 446: `db_conv.commit()` (ConversationLog insert)
- Line 462: `db_conv.commit()` (ObjectionEvent bulk)
- Line 485: `db_conv.commit()` (POLISH-38 reconcile)
- Line 562: `db_conv.commit()` (FtCallSession update)
- Line 615: `db_conv.commit()` (User points/minutes)

Each of these commits is wrapped in its own implicit mini-transaction. If any step between them raises an exception, partial state persists:
- ConversationLog row exists, ObjectionEvent rows don't → Timeline shows "n Einwände erkannt, 0 mit EWB behandelt"
- ConversationLog + ObjectionEvent exist, but reconcile didn't run → `einwaende_gesamt=len(ewb_clicks)` (the defensive-fallback value from line 422), which is wrong if re-aggregate would have corrected it
- Points not awarded but session saved

**Impact assessment:**
The defensive fallback at line 422 (`einwaende_gesamt=len(ewb_clicks)`) is *intentionally* aligned with the eventual reconciled value — both should equal the number of EWB-click events. So in the happy path, missing reconcile produces the same number. **The exception is** when spawn-errors cause `record_ewb_click(success=False)` entries that the reconcile correctly sums but the defensive fallback doesn't know about. For launch, this is acceptable (low-probability and the Kreuzweise-Fehler is within 1-2 counts — not user-visible misrepresentation).

**Recommended fix (non-blocking):**

Wrap steps 1-3 (ConversationLog + ObjectionEvent + reconcile) in a single nested transaction using SQLAlchemy's `begin_nested()` / `with db_conv.begin():`. Keep step 4/5 (FT logging, points) as separate transactions so failure there doesn't roll back the session save.

```python
try:
    with db_conv.begin():                                # outer txn
        conv = ConversationLog(...)
        db_conv.add(conv)
        db_conv.flush()                                  # get conv.id without commit
        saved_conv_id = conv.id

        for click in ewb_clicks:
            db_conv.add(ObjectionEvent(..., conversation_log_id=conv.id,
                                       einwand_typ=click['einwand_typ'],
                                       success=click['success']))
        db_conv.flush()

        # POLISH-38 reconcile — now guaranteed to see all just-flushed ObjectionEvent
        _agg = (db_conv.query(
                    _sqlfunc.count(ObjectionEvent.id),
                    _sqlfunc.sum(_sqlcase((ObjectionEvent.success == True, 1), else_=0)))
                .filter(ObjectionEvent.conversation_log_id == conv.id)
                .one())
        _total = int(_agg[0] or 0)
        _ok = int(_agg[1] or 0)
        if _total > 0:
            conv.einwaende_gesamt = _total
            conv.einwaende_behandelt = _ok
    # outer txn committed atomically
    print(f"[Beenden] conv.id={saved_conv_id} persisted atomically")
```

Post-launch, this can be `POST-LAUNCH` if time is tight. SQLite's default deferred-write behavior makes partial commits extremely rare in practice.

### PL-02: Race window between `record_ewb_click` and `api_beenden` reading `state['ewb_clicks']`

**File:** `routes/app_routes.py:402-403`, `services/live_session.py:406-414`
**Severity:** PRE-LAUNCH-FIX
**Risk:** Lost or double-counted EWB-click in the exact moment the user clicks Beenden right after the last EWB-click.

**Evidence:**

`record_ewb_click` correctly takes `state_lock`:
```python
# services/live_session.py:406-414
def record_ewb_click(einwand_typ: str, success: bool = False):
    import datetime as _dt
    with state_lock:
        state.setdefault('ewb_clicks', []).append({
            'einwand_typ': einwand_typ,
            'success':     bool(success),
            'ts':          _dt.datetime.utcnow().isoformat(),
        })
```

`/api/beenden` reads under lock too:
```python
# routes/app_routes.py:402-403
with ls.state_lock:
    ewb_clicks = list(ls.state.get('ewb_clicks', []))
```

**Good news:** both operations correctly hold `state_lock` for atomicity. The list-copy (`list(...)`) is under lock, so we get a consistent snapshot.

**Subtle issue:** `manual_ewb` handler in `deepgram_service.py` line 448 spawns a background task AFTER calling `record_ewb_click`:
```python
# deepgram_service.py:444-455 (POLISH-38.1)
_ewb_success = True
try:
    sio.start_background_task(_run)
except Exception as _spawn_err:
    _ewb_success = False
    ...
try:
    ls.record_ewb_click(typ, success=_ewb_success)
except Exception as e:
    print(f"[PiP] record_ewb_click error (sid={_sid}): {e}")
```

Control flow analysis: user clicks EWB → socket event → `manual_ewb` handler runs → spawns background Haiku call → records click with `success=True` → returns. User clicks Beenden immediately after → `/api/beenden` → reads `ewb_clicks`. If the click-event socket-handler was still running when Beenden POST was received, there's a potential race. But Flask-SocketIO `async_mode='threading'` serializes per-socket events, and the HTTP `/api/beenden` is a separate thread. So:

- Thread A (socketio): processing `manual_ewb`, holds nothing, about to call `record_ewb_click` (needs `state_lock`)
- Thread B (HTTP): `/api/beenden` enters, acquires `state_lock`, copies list, releases lock
- Thread A: now acquires lock, appends to list

Result: Click NOT in the copy that `/api/beenden` used. Click lands in `ls.state['ewb_clicks']` but reset_session() clears it at line 660. **Click is lost.**

**Impact:** very low frequency (user has to Beenden within ~5ms of the last EWB click). Post-call report is off-by-one for that session. Not corrupting, not data-loss in aggregate.

**Fix (optional for launch):** In `manual_ewb` handler, call `record_ewb_click` BEFORE spawning the background task. Currently it's called AFTER. That won't solve the race (still two threads) but reduces the race window to just the HTTP-handler-boundary. A true fix would require an outer lock that HTTP Beenden takes to quiesce socketio handlers, which is overkill.

**Recommendation:** leave as-is for launch. Add a Sentry/log warning if `len(ewb_clicks) != einwaende_gesamt_from_db` after reconcile — flags the race for monitoring without blocking.

### PL-06: Deepgram close handler emits raw exception content to frontend

**File:** `services/deepgram_service.py:173-180`
**Severity:** PRE-LAUNCH-FIX
**Risk:** Info disclosure (API keys in error messages, internal paths), no reconnect UX.

**Evidence:**
```python
def on_close(self, close, **kwargs):
    from extensions import socketio as sio
    print(f"[DG] Close (sid={sid}): {close}")
    try:
        sio.emit('dg_close', {'info': str(close)}, room=sid)
```

```python
def on_close(self, close, **kwargs):

    print(f"[DG] Close (sid={sid}): {close}")       # full info server-side
    try:
        sio.emit('dg_close', {'info': 'Verbindung geschlossen'}, room=sid)  # generic client-side
    except Exception:
        pass
```

Plus — add a reconnect path on frontend: if `dg_close` fires mid-session, show the user a "Verbindung unterbrochen — erneut versuchen" banner.

### POST-01: Phase-classifier writes `phasen_log` under `phasen_log_lock` but reads `covered_phases` without explicit safety note

### POST-05: Markdown filter doesn't handle bytes vs str defensively

### POST-06: Close-overlay headset-confirmed clear fires on every logged-out page render

**File:** `templates/base.html:141-147`
**Severity:** POST-LAUNCH
**Assessment:** **NOT an exploit.** The concern raised was "can an attacker trigger a page render with `g.user = None` to clear consent for a logged-in user?"

Looking at Flask's middleware flow: `g.user` is set by auth blueprint's `@before_request` hook. An attacker cannot cause `g.user=None` to be set for a logged-in user's browser session — `g.user` is server-side request-local state. The sessionStorage clear is client-side, runs on the user's own browser, only when *that* browser's request shows `g.user=None`.

The only XSS-like concern would be: does this script run on pages the user accesses while logged in but without `g.user` being set? Looking at the templates, `{% if not g.user %}` is in `base.html` which is extended by most pages. On `/login`, `/register`, `/landing`, `/impressum`, `/agb`, `/datenschutz`, `/changelog` — all public pages — it fires. A logged-in user visiting `/impressum` via a link would have `g.user=None` for that request (public route), clear their sessionStorage, then navigate back to `/live`, be prompted to re-confirm headset. **This is a UX annoyance but NOT a security issue.**

**Fix (minor UX improvement):** Clear only when the current URL is `/logout` or similar logout-equivalent, not on every public page render.

```jinja
{% if not g.user and request.path in ('/logout', '/login') %}
<script>
  try { sessionStorage.removeItem('headsetConfirmed'); } catch (e) {}
</script>
{% endif %}
```
